Stale-While-Revalidate

Serve instantly from cache, then update in the background — the caching pattern that gives you both speed AND freshness, used by HTTP headers, Service Workers, and data-fetching libraries like SWR and React Query.

Intermediate Caching Pattern HTTP / Service Worker
🍕 Daily-Life Analogy: Pizza Reheating

You're hungry NOW, so you eat the leftover pizza from the fridge (stale cache — instant). Simultaneously, you order a fresh pizza (revalidate in background). When the fresh one arrives, you swap it in for next time. You were never blocked waiting — you got something immediately and it gets fresher over time.

The Pattern: Three Levels of Implementation

1. HTTP Header Level (Browser + CDN)

// Server response header:
Cache-Control: max-age=60, stale-while-revalidate=3600

// What this means:
// - For first 60 seconds: serve from cache (completely fresh)
// - After 60s but within 3660s (60+3600):
//     1. Serve STALE version immediately (user sees it instantly)
//     2. Fetch fresh version in background
//     3. Update cache with fresh version
//     4. NEXT request gets the fresh version
// - After 3660s: cache is fully expired, must wait for network

// Key insight: The USER is never blocked. They always get an instant response.
// The trade-off: they might see slightly stale data for ONE request.

2. Service Worker Level

// sw.js — Implementing SWR in a Service Worker
self.addEventListener('fetch', (event) => {
    if (event.request.url.includes('/api/')) {
        event.respondWith(staleWhileRevalidate(event.request));
    }
});

async function staleWhileRevalidate(request) {
    const cache = await caches.open('api-cache');
    const cached = await cache.match(request);
    
    // Start network fetch regardless (the "revalidate" part)
    const networkPromise = fetch(request).then(response => {
        // Update cache with fresh response (for next time)
        cache.put(request, response.clone());
        return response;
    });
    
    // Return cached immediately if available (the "stale" part)
    // Otherwise wait for network (first visit, no cache yet)
    return cached || networkPromise;
}

3. Application Level (SWR / React Query / TanStack Query)

// React example using SWR (named after this pattern!)
import useSWR from 'swr';

function UserProfile({ userId }) {
    const { data, error, isValidating } = useSWR(
        `/api/users/${userId}`,
        fetcher,
        {
            revalidateOnFocus: true,    // Re-fetch when tab regains focus
            revalidateOnReconnect: true, // Re-fetch when coming back online
            dedupingInterval: 2000,      // Dedup identical requests within 2s
        }
    );
    
    // data is available IMMEDIATELY from cache (stale)
    // isValidating = true while background refresh happens
    // When fresh data arrives, component re-renders with new data
    
    return (
        <div>
            <h1>{data?.name}</h1> {/* Shows immediately from cache */}
            {isValidating && <span>Updating...</span>} {/* Subtle indicator */}
        </div>
    );
}

The Flow Diagram

/*
  Request #1 (no cache):
  User → [Cache miss] → Network → Response → Store in cache → Show to user
  
  Request #2 (cache fresh, within max-age):
  User → [Cache hit, fresh] → Show immediately ✅
  
  Request #3 (cache stale, within SWR window):
  User → [Cache hit, stale] → Show immediately ✅
       └→ [Background] → Network → Update cache
       → Next request gets fresh version
  
  Request #4 (cache fully expired):
  User → [Cache expired] → Network → Response → Store → Show to user
*/

Where This Is Used in Production

  • Vercel's SWR library — Named after this pattern. Used by thousands of Next.js apps for data fetching with instant cache-first rendering.
  • Cloudflare Workers — Their cf.cacheTtlByStatus with stale-while-revalidate directive serves millions of requests per second from stale cache while updating.
  • Chrome browser cache — Natively supports the stale-while-revalidate HTTP directive since Chrome 75.
  • TanStack Query (React Query) — Default behavior is SWR: show cached data immediately, refetch in background, re-render when fresh data arrives.

Common Mistakes

  • Using SWR for real-time critical data — If showing stale data for even one frame is unacceptable (bank balance, stock price), SWR is wrong. Use network-first or WebSocket.
  • Not showing staleness indicators — Users should know when data might be stale. A subtle "Updating..." indicator builds trust.
  • Infinite revalidation loops — If your fetcher triggers a state change that re-triggers the fetch, you get an infinite loop. Use deduplication.
  • Confusing HTTP SWR with library SWR — The HTTP header is browser/CDN level (no code needed). Libraries like SWR implement the same pattern at the application level for richer control.

✅ You Truly Understand Stale-While-Revalidate When...

You can explain the user experience difference between max-age=0 (always wait for network) and max-age=0, stale-while-revalidate=86400 (always serve instantly from cache, update in background) — and why the second gives better perceived performance despite potentially stale data.
