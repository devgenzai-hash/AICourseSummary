Browser Memory Leak Detection

Memory leaks in web apps cause tabs to slow down, freeze, and eventually crash — consuming gigabytes of RAM that should have been freed. Detection requires understanding the GC's reachability model, heap snapshots, and the specific patterns that prevent garbage collection in JavaScript.

Advanced Memory & GC Debugging
📚 Analogy: A Hotel That Never Checks Guests Out

Imagine a hotel where guests check in but the front desk never marks rooms as "available" when they leave. Even though the guests are long gone, the hotel thinks every room is occupied. Over time, the hotel reports "full capacity" and turns away new guests (OOM crash). A heap snapshot is like an auditor walking through every room to see which ones are actually empty. The retainer path is tracing back to find which desk clerk still has the room key (the reference preventing GC).

The Problem: Silent Growth Until Crash

// Memory leaks are SILENT — no errors, no warnings
// The tab just gets slower over minutes/hours until it crashes

// Classic leak: event listener never removed
function ChatWidget() {
  const [messages, setMessages] = useState([]);

  useEffect(() => {
    // BUG: No cleanup function! This listener is never removed.
    // Every time ChatWidget mounts/unmounts (e.g., tab switching),
    // another listener is added. Each listener holds a closure over
    // the component's state, preventing GC of the entire component tree.
    window.addEventListener('message', (e) => {
      setMessages(prev => [...prev, e.data]);
    });
  }, []);

  return <div>{messages.map(m => <p>{m}</p>)}</div>;
}

// After 50 mount/unmount cycles: 50 event listeners,
// 50 closure references, 50 component trees in memory
// Memory: 5MB → 50MB → 200MB → OOM crash

// Classic leak: timer never cleared
function Dashboard() {
  useEffect(() => {
    const id = setInterval(() => {
      fetchMetrics(); // Closure holds reference to component scope
    }, 1000);
    // BUG: No return () => clearInterval(id);
  }, []);
}

Detection Method 1: DevTools Heap Snapshots

// Chrome DevTools → Memory tab → Heap Snapshot
// The three-snapshot technique for finding leaks:

// Step 1: Take Snapshot 1 (baseline — page just loaded)
// Step 2: Perform the action that might leak (open/close modal, navigate)
// Step 3: Take Snapshot 2 (should be similar to Snapshot 1)
// Step 4: Repeat the action many times (10x)
// Step 5: Take Snapshot 3

// Compare Snapshot 1 vs 3:
// - If memory grew linearly: LEAK CONFIRMED
// - Use "Objects allocated between Snapshot 1 and Snapshot 3"
// - Sort by "Retained Size" descending
// - Look for unexpected objects (detached DOM trees, closures, arrays)

// Key DevTools columns:
// - Shallow Size: memory of the object itself (bytes)
// - Retained Size: memory freed if this object were GC'd (includes children)
// - Distance: edges from GC root to this object
// - Retainers: WHO is keeping this object alive (the reference chain)

// Programmatic detection with performance.measureUserAgentSpecificMemory()
async function measureMemory() {
  // Requires cross-origin isolation (COOP/COEP headers)
  if (!performance.measureUserAgentSpecificMemory) return;

  const result = await performance.measureUserAgentSpecificMemory();
  console.log(`Total JS memory: ${(result.bytes / 1024 / 1024).toFixed(2)} MB`);

  // result.breakdown shows per-frame memory usage
  for (const entry of result.breakdown) {
    console.log(entry.attribution, entry.bytes);
  }
}

// Periodic leak detection in production
setInterval(async () => {
  const { bytes } = await performance.measureUserAgentSpecificMemory();
  if (bytes > 500 * 1024 * 1024) { // Over 500MB
    reportMemoryLeak({ bytes, url: location.href });
  }
}, 60000);

Detection Method 2: WeakRef and FinalizationRegistry

// WeakRef: holds a reference that DOESN'T prevent GC
// FinalizationRegistry: callback when an object IS GC'd
// Together: detect if objects that SHOULD be GC'd actually ARE

// === Leak detector for React components ===
const leakDetector = new FinalizationRegistry((label) => {
  console.log(`✅ [GC] ${label} was properly garbage collected`);
});

const tracked = new Map(); // label → WeakRef

function trackForLeaks(obj, label) {
  const ref = new WeakRef(obj);
  tracked.set(label, ref);
  leakDetector.register(obj, label);
}

function checkLeaks() {
  for (const [label, ref] of tracked) {
    if (ref.deref() !== undefined) {
      console.warn(`⚠️ [LEAK] ${label} is still alive and should have been GC'd`);
    } else {
      tracked.delete(label); // Already collected, stop tracking
    }
  }
}

// Usage in a React component (development only)
function Modal({ onClose }) {
  const instanceRef = useRef({});

  useEffect(() => {
    if (process.env.NODE_ENV === 'development') {
      trackForLeaks(instanceRef.current, `Modal-${Date.now()}`);
    }
  }, []);

  // When this Modal unmounts, instanceRef.current should be GC'd
  // If it's NOT collected after a few GC cycles → LEAK
}

// Check after user interaction (give GC time to run)
setTimeout(checkLeaks, 5000);

The 5 Most Common Leak Patterns

// === PATTERN 1: Forgotten event listeners ===
class InfiniteScroll {
  constructor() {
    // LEAK: 'this' reference keeps entire class alive
    window.addEventListener('scroll', this.onScroll);
  }
  destroy() {
    // FIX: Must remove with same function reference
    window.removeEventListener('scroll', this.onScroll);
  }
  // BETTER FIX: Use AbortController
  constructor2() {
    this.controller = new AbortController();
    window.addEventListener('scroll', this.onScroll, {
      signal: this.controller.signal
    });
  }
  destroy2() { this.controller.abort(); }
}

// === PATTERN 2: Closures capturing large scopes ===
function processData() {
  const hugeArray = new Array(1_000_000).fill('x'); // 10MB
  const result = hugeArray.reduce((a, b) => a + b);

  // LEAK: returned function's closure captures hugeArray
  // even though it only uses 'result'
  return () => console.log(result);
  // FIX: null out hugeArray before returning
  // hugeArray = null; // Breaks reference, allows GC
}

// === PATTERN 3: Growing collections (Maps, Sets, Arrays) ===
const cache = new Map(); // Never evicted!
function getCachedData(key) {
  if (!cache.has(key)) {
    cache.set(key, expensiveComputation(key));
  }
  return cache.get(key);
}
// After 10,000 unique keys: cache holds 10,000 entries forever
// FIX: Use WeakMap (if keys are objects) or LRU cache with max size

// === PATTERN 4: Detached DOM trees (covered in next topic) ===
let detachedTree;
function removeModal() {
  detachedTree = document.getElementById('modal');
  detachedTree.remove(); // Removed from DOM but JS reference keeps it alive
}
// detachedTree holds entire DOM subtree in memory

// === PATTERN 5: Uncleared timers/intervals ===
function startPolling() {
  setInterval(() => {
    // This closure + everything it references stays forever
    updateDashboard(getState());
  }, 1000);
  // No reference to interval ID = can never clear it
}

Real-World Usage

  • Gmail — Notoriously fought memory leaks in their SPA. Opening/closing emails accumulated detached DOM trees. They built internal tools to track retained sizes and auto-warn when thresholds were exceeded.
  • VS Code (web) — Uses DisposableStore pattern: every resource (listener, timer, subscription) is registered as a disposable. On component teardown, dispose() cleans up all registered resources atomically.
  • React DevTools Profiler — Shows component mount/unmount pairs. If a component mounts N times but only unmounts N-1 times, you have a potential leak.
  • Production monitoring (Sentry, DataDog) — Track performance.memory.usedJSHeapSize over time. Alert when it grows monotonically without plateauing (strong leak signal).
  • SPAs with client-side routing — The #1 source of leaks. Each route change should fully tear down the previous view. Event listeners and timers from old routes are the most common leak source.

Trade-offs & Alternatives

Detection MethodStrengthsWeaknesses
Heap Snapshots (DevTools) Exact object-level detail; retainer paths; definitive proof Manual; requires reproducing the leak; slow for large heaps
performance.measureUserAgentSpecificMemory() Programmatic; works in production; per-frame breakdown Requires COOP/COEP headers; approximate; no object details
WeakRef + FinalizationRegistry Automated detection; can run in CI; proves GC behavior GC timing is non-deterministic; false negatives possible; dev-only
Allocation Timeline (DevTools) Shows what's being allocated in real-time; correlates with actions High overhead; slows the page; hard to use for intermittent leaks

Common Mistakes

  • Confusing retained size with shallow size — An object with 100 bytes shallow size might retain 50MB if it references a large tree. Always sort by retained size when hunting leaks.
  • Not forcing GC before snapshot — Memory that looks like a leak might just be pending GC. Click the trash icon (Force GC) in DevTools before taking snapshots. Otherwise you get false positives.
  • Using Map where WeakMap suffices — If your cache keys are objects (DOM nodes, class instances), WeakMap automatically drops entries when keys are GC'd. Regular Map holds keys alive forever.
  • Assuming GC runs immediately — FinalizationRegistry callbacks may fire seconds or minutes after the object becomes unreachable. Don't rely on timely GC for correctness — only use it for detection/debugging.
  • Only testing with small data — A leak of 100 bytes per action is invisible in development. In production with 10,000 users clicking 500 times per session, it's 50MB. Always test with realistic iteration counts (100+ cycles of the suspect action).

✅ You Truly Understand Memory Leak Detection When...

Given a heap snapshot, you can trace the retainer path from a suspected leaked object all the way back to the GC root, identify exactly which reference is preventing collection, determine whether it's a genuine leak or expected retention, and implement the minimal fix (removing one reference) that allows the entire retained tree to be collected.

🧪 Try This Challenge

Build a single-page app with 5 tabs (Home, Dashboard, Settings, Profile, Notifications). Each tab mounts/unmounts a complex component tree. Intentionally introduce one leak per tab (different patterns: event listener, timer, closure, Map cache, detached DOM). Then use DevTools heap snapshots to identify and fix each one. Verify that switching between all 5 tabs 100 times results in zero memory growth beyond the baseline.
