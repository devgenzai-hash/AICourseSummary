Long Tasks API

The browser API that identifies JavaScript tasks exceeding 50ms — the threshold where users perceive the UI as unresponsive and interactions feel sluggish.

Intermediate Performance Web API
🚦 Analogy: Traffic Light Monitoring

Imagine a traffic intersection where each car (task) gets a green light. If any car takes more than 50 seconds (ms) to cross, it blocks all other cars (user interactions, rendering). The Long Tasks API is the traffic camera that logs every vehicle that overstayed its green light — you can then investigate WHY those specific cars were slow.

The Problem: The 50ms Responsiveness Budget

// RAIL model (Google's UX performance model):
// Response: <100ms for user to feel instant feedback
// Animation: <16ms per frame (60fps)
// Idle: use idle time for deferred work
// Load: <1000ms for meaningful content

// WHY 50ms is the threshold:
// If a task takes 50ms, and user input arrives at the START of that task,
// the input waits 50ms (task) + processing time = ~100ms total
// 100ms is the upper bound before users perceive delay
// So 50ms per task is the budget to stay under 100ms response time

// ┌──────────────── Task (70ms) ──────────────────────┐
// │████████████████████████████████████████████████████│
// └───────────────────────────────────────────────────-┘
//        ↑ User clicks here                    ↑ Input finally processed
//        │         (blocked for remaining 55ms) │
//        └──────── perceivable delay ───────────┘

How It Works

// Basic Long Tasks observation
const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
        // Every entry here is a task that took >50ms on the main thread
        console.log('Long Task detected:', {
            duration: entry.duration,     // How long it ran (ms)
            startTime: entry.startTime,   // When it started (relative to navigationStart)
            name: entry.name,             // Always 'self' for same-origin, 'cross-origin-*' for iframes
            attribution: entry.attribution // WHERE the long task originated
        });
    }
});

// buffered:true captures long tasks that fired before this code ran
observer.observe({ type: 'longtask', buffered: true });

Production Implementation: Long Task Budget Monitor

// Real-world long task monitoring with actionable diagnostics

class LongTaskMonitor {
    #tasks = [];
    #totalBlockingTime = 0;
    #observer;

    constructor({ reportThreshold = 100, onReport }) {
        this.#observer = new PerformanceObserver((list) => {
            for (const entry of list.getEntries()) {
                // Total Blocking Time (TBT) = sum of (duration - 50ms) for all long tasks
                // TBT is the lab-measurable proxy for FID
                const blockingTime = entry.duration - 50;
                this.#totalBlockingTime += blockingTime;

                const taskInfo = {
                    duration: entry.duration,
                    blockingTime,
                    startTime: entry.startTime,
                    attribution: this.#getAttribution(entry),
                    // Capture stack context — what was the page doing?
                    pageState: {
                        url: location.href,
                        visibility: document.visibilityState,
                        // Was user interacting? (rough heuristic)
                        hadRecentInput: performance.now() - this.#lastInputTime < 500
                    }
                };

                this.#tasks.push(taskInfo);

                // Report immediately for very long tasks (likely causing visible jank)
                if (entry.duration >= reportThreshold) {
                    onReport?.({
                        type: 'critical-long-task',
                        task: taskInfo,
                        tbt: this.#totalBlockingTime
                    });
                }
            }
        });

        this.#observer.observe({ type: 'longtask', buffered: true });
        this.#trackInput();
    }

    #lastInputTime = 0;
    #trackInput() {
        // Track when user last interacted to correlate with long tasks
        ['click', 'keydown', 'pointerdown'].forEach(evt => {
            document.addEventListener(evt, () => {
                this.#lastInputTime = performance.now();
            }, { capture: true, passive: true });
        });
    }

    #getAttribution(entry) {
        const attr = entry.attribution?.[0];
        if (!attr) return 'unknown';
        if (attr.containerType === 'iframe') {
            return `iframe: ${attr.containerSrc || attr.containerName || 'anonymous'}`;
        }
        return 'self';
    }

    get totalBlockingTime() { return this.#totalBlockingTime; }
    get taskCount() { return this.#tasks.length; }
    
    getWorstTasks(n = 5) {
        return [...this.#tasks]
            .sort((a, b) => b.duration - a.duration)
            .slice(0, n);
    }

    disconnect() { this.#observer.disconnect(); }
}

// Usage
const monitor = new LongTaskMonitor({
    reportThreshold: 150, // Alert on tasks >150ms
    onReport: (data) => {
        // Send to your analytics/alerting system
        navigator.sendBeacon('/api/perf-alert', JSON.stringify(data));
    }
});

Breaking Up Long Tasks: The yield() Pattern

// Long task: processing 10,000 items in one synchronous loop
// This blocks the main thread for 200ms+
function processAllItemsBAD(items) {
    items.forEach(item => heavyComputation(item)); // 200ms blocked
}

// SOLUTION: Yield to the main thread periodically
// This breaks one 200ms task into multiple <50ms tasks

function yieldToMain() {
    // scheduler.yield() is the ideal API (Chrome 129+)
    if ('scheduler' in window && 'yield' in scheduler) {
        return scheduler.yield();
    }
    // Fallback: setTimeout(0) moves to next task
    // Downside: loses priority position in the task queue
    return new Promise(resolve => setTimeout(resolve, 0));
}

async function processAllItemsGOOD(items) {
    const CHUNK_SIZE = 100; // Process 100 items per chunk (~5ms each)
    
    for (let i = 0; i < items.length; i += CHUNK_SIZE) {
        const chunk = items.slice(i, i + CHUNK_SIZE);
        chunk.forEach(item => heavyComputation(item));
        
        // YIELD: give the browser a chance to:
        // 1. Process user input (clicks, typing)
        // 2. Run rendering pipeline (style, layout, paint)
        // 3. Run GC if needed
        if (i + CHUNK_SIZE < items.length) {
            await yieldToMain();
        }
    }
}

// ADVANCED: Use isInputPending() to yield only when user is waiting
async function processWithInputAwareness(items) {
    for (let i = 0; i < items.length; i++) {
        heavyComputation(items[i]);
        
        // Only yield if there's pending user input OR we've been running >40ms
        if (navigator.scheduling?.isInputPending() || 
            (i % 50 === 0 && i > 0)) {
            await yieldToMain();
        }
    }
}

Where This Lives in Production

  • Chrome User Experience Report (CrUX) — Long tasks feed into Total Blocking Time (TBT), which correlates with FID/INP. Used by Google Search ranking signals.
  • Next.js — The built-in performance reporter uses Long Tasks API to identify hydration cost and warn when third-party scripts cause main-thread congestion.
  • Shopify Storefront — Monitors long tasks to attribute blocking time to specific Shopify apps/widgets loaded by merchants.
  • Facebook/Meta — Internal performance monitoring uses long task attribution to track which product teams' code is blocking interactivity.

Trade-offs & Limitations

AspectDetail
GranularityOnly reports tasks >50ms. Many 45ms tasks can still cause jank but aren't captured.
AttributionOnly identifies container (iframe/window), NOT the specific function. Use DevTools for stack traces.
OverheadMinimal — browser already tracks task boundaries. Observer adds negligible cost.
Cross-originCan detect long tasks from cross-origin iframes but attribution is limited (security).
ReplacementLong Animation Frames API (LoAF) provides much richer data (scripts, render time) — shipping in Chrome 123+.

Common Mistakes

  • Assuming long tasks = slow JavaScript only — GC pauses, forced layouts, and style recalculations all count as task time.
  • Ignoring third-party scripts — Ad scripts, chat widgets, and analytics often cause the worst long tasks. Use attribution to identify them.
  • Not correlating with user input — A 200ms long task during page idle is fine. The same task during user interaction is a UX disaster.
  • Breaking tasks too aggressively — If you yield every 1ms, the overhead of task scheduling dominates. Aim for 5-50ms chunks.

✅ You Truly Understand Long Tasks When...

You can calculate Total Blocking Time from a set of long task entries, explain why TBT correlates with input delay, and refactor synchronous code into yielding chunks that keep every task under 50ms.
