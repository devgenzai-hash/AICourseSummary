ResizeObserver Loop Limits

Why ResizeObserver can trigger infinite layout loops, how the browser's "loop limit" prevents them, and the cryptic "ResizeObserver loop completed with undelivered notifications" error explained.

Advanced Observer API Browser Internals
♻️ Daily-Life Analogy: Hall of Mirrors Feedback

Imagine a room where resizing a mirror causes the adjacent mirror to resize, which causes the first mirror to resize again... infinitely. ResizeObserver's loop limit is the building inspector who says "you get 4 resize rounds maximum per frame. After that, I stop delivering notifications to prevent the building from shaking itself apart."

The Problem: Why Infinite Loops Are Possible

// The dangerous pattern: observing an element and changing its size in the callback
const observer = new ResizeObserver((entries) => {
    for (const entry of entries) {
        // ❌ INFINITE LOOP: Changing size triggers another observation
        entry.target.style.width = (entry.contentRect.width + 1) + 'px';
        // This resize triggers the observer again → which adds 1px → triggers again → ...
    }
});

Unlike MutationObserver (which delivers all mutations after the microtask), ResizeObserver integrates with the layout phase. If your callback changes layout, it can trigger another resize observation in the same frame.

How the Browser Prevents Infinite Loops

  1. Process ResizeObserver notifications after layout
  2. If callbacks change layout, re-run layout
  3. Check for new resize observations
  4. Repeat up to a DEPTH LIMIT (typically 4 iterations per frame)
  5. After limit: deliver remaining notifications in the NEXT frame and fire an error event
// The browser's internal frame loop (simplified):
function renderFrame() {
    runJavaScript();           // Event handlers, timers, etc.
    recalcStyles();
    runLayout();               // Calculate geometry
    
    // --- ResizeObserver integration point ---
    let depth = 0;
    while (hasResizeObservations() && depth < MAX_DEPTH) {
        deliverResizeObservations(); // Your callback runs here
        recalcStyles();             // Callback may have changed styles
        runLayout();                // Recalculate layout
        depth++;
    }
    
    if (hasResizeObservations()) {
        // Still have undelivered observations after max depth!
        // Schedule them for next frame and fire error event
        reportError("ResizeObserver loop completed with undelivered notifications");
    }
    // --- End ResizeObserver ---
    
    paint();
    composite();
}

The "Loop Limit Exceeded" Error

⚠️ "ResizeObserver loop completed with undelivered notifications"

This error means: your ResizeObserver callback caused a layout change that triggered more observations, and this repeated until the browser hit its depth limit. The browser DROPPED some notifications to prevent freezing. This doesn't crash the page but means some resize callbacks were skipped — potentially leaving your UI in an inconsistent state.

Code: Safe Patterns That Avoid Loops

// ✅ SAFE: Read size, update a DIFFERENT element
const observer = new ResizeObserver((entries) => {
    for (const entry of entries) {
        // Reading the observed element's size and writing to a DIFFERENT element
        // doesn't create a loop (the other element isn't observed)
        const { width } = entry.contentRect;
        otherElement.style.fontSize = (width / 20) + 'px';
    }
});

// ✅ SAFE: Use requestAnimationFrame to defer writes
const safeObserver = new ResizeObserver((entries) => {
    // Read now, write next frame — breaks the synchronous loop
    requestAnimationFrame(() => {
        for (const entry of entries) {
            entry.target.style.fontSize = (entry.contentRect.width / 10) + 'px';
        }
    });
});

// ✅ SAFE: Converging logic (change gets smaller each iteration)
const convergingObserver = new ResizeObserver((entries) => {
    for (const entry of entries) {
        const { width, height } = entry.contentRect;
        // This converges: once aspect ratio is correct, no more changes
        const targetHeight = width * 0.5625; // 16:9 ratio
        if (Math.abs(height - targetHeight) > 1) {
            entry.target.style.height = targetHeight + 'px';
        }
    }
});

Where This Is Used in Production

  • Container Queries (polyfills) — Before native container queries, polyfills used ResizeObserver to detect container size and apply conditional styles.
  • Chart libraries (D3, Chart.js) — Observe chart container resize to redraw at new dimensions. The loop error is common here when chart rendering itself changes container size.
  • Virtual scrollers — Observe item size changes to update scroll calculations (items might have dynamic content heights).

Common Mistakes

  • Changing the observed element's size in the callback — The #1 cause of the loop error. If you must do it, ensure convergence.
  • Ignoring the error in error monitoring — Many teams filter this out as "harmless." But it means UI inconsistency — some callbacks were dropped.
  • Not cleaning up observers — observer.disconnect() or observer.unobserve(el) when elements are removed. Otherwise the observer holds references preventing GC.
  • Creating many observers instead of one — One ResizeObserver can observe many elements. Creating one per element adds overhead.

✅ You Truly Understand ResizeObserver Loop Limits When...

You can explain the exact browser frame sequence that causes the loop error (layout → deliver RO → callback changes size → re-layout → deliver RO → ... → depth limit), and design a callback pattern that converges without hitting it.

🔗 Connect It

ResizeObserver connects to: Layout Thrashing (RO callbacks can cause forced layouts), CSS Containment (containment prevents size changes from propagating, reducing RO triggers), and MutationObserver (similar observer pattern, different trigger mechanism).
