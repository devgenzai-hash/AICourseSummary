Web Workers vs Service Workers

Two fundamentally different threading models in the browser — one for parallel computation, the other for network interception. Same "worker" name, completely different purposes and lifecycles.

Intermediate Threading Browser API
🏭 Daily-Life Analogy: Kitchen Staff vs Security Guard

A Web Worker is like a kitchen assistant — you hand them a task (chop vegetables, calculate tax), they do it in the back room without blocking the front counter (main thread), and hand you back the result. Hire as many as you need, fire them when done.

A Service Worker is like a security guard at the building entrance — they intercept every delivery (network request) and decide: deliver from the vault (cache), order fresh from the supplier (network), or reject it entirely. They persist even when the store is closed (page not open).

Web Worker: Parallel Computation

// main.js — Offload expensive work to avoid blocking UI
const worker = new Worker('heavy-computation.js');

// Communication is via message passing (structured clone algorithm)
// Data is COPIED, not shared (unless using SharedArrayBuffer)
worker.postMessage({
    type: 'PROCESS_IMAGE',
    pixels: imageData,  // This gets copied — expensive for large data!
});

worker.onmessage = (event) => {
    const { type, result } = event.data;
    if (type === 'RESULT') {
        renderProcessedImage(result);
    }
};

// Terminate when done — frees the OS thread
worker.terminate();

// heavy-computation.js — Runs on a separate OS thread
// Has NO access to: document, window, DOM, localStorage
// HAS access to: fetch, IndexedDB, WebSocket, crypto, timers

self.onmessage = (event) => {
    const { type, pixels } = event.data;
    
    if (type === 'PROCESS_IMAGE') {
        // Heavy computation happens here — doesn't block main thread
        const processed = applyGaussianBlur(pixels, 5);
        
        // Send result back — also copied unless using Transferable
        self.postMessage({ type: 'RESULT', result: processed });
    }
};

Service Worker: Network Proxy

// Register the service worker (from your main page)
if ('serviceWorker' in navigator) {
    navigator.serviceWorker.register('/sw.js', {
        scope: '/'  // Controls all pages under this path
    });
}

// sw.js — The Service Worker (a network-level proxy)

// INSTALL: Cache critical assets (runs once when SW is first registered)
self.addEventListener('install', (event) => {
    event.waitUntil(
        caches.open('v1').then(cache => 
            cache.addAll(['/', '/app.js', '/styles.css'])
        )
    );
});

// FETCH: Intercept EVERY network request from controlled pages
self.addEventListener('fetch', (event) => {
    event.respondWith(
        caches.match(event.request).then(cached => {
            // Return cached version if available, otherwise fetch from network
            return cached || fetch(event.request);
        })
    );
});

// PUSH: Can receive push notifications even when all tabs are closed
self.addEventListener('push', (event) => {
    const data = event.data.json();
    event.waitUntil(
        self.registration.showNotification(data.title, { body: data.body })
    );
});

Where This Is Used in Production

  • Figma — Uses Web Workers for rendering engine computations (vector math, layout algorithms) while the main thread handles UI interactions.
  • Google Docs — Service Worker provides offline editing; Web Workers handle spell-checking and autosave conflict resolution.
  • Squoosh (Google) — Web Workers run image codec WASM modules (mozjpeg, webp) without freezing the UI during compression.
  • Twitter/X — Service Worker caches the app shell and timeline data for instant re-opens.

Common Mistakes

  • Using Service Worker for computation — Service Workers are event-driven and can be terminated by the browser when idle. Don't run long computations there.
  • Forgetting postMessage serialization cost — Large objects sent to Web Workers are cloned (structured clone). For big ArrayBuffers, use Transferable objects instead.
  • Not handling Service Worker updates — A new SW version sits in "waiting" state until all tabs close. Users get stale code indefinitely without proper update flow.
  • Trying to access DOM from workers — Neither worker type has DOM access. Use postMessage to send data back to main thread for DOM updates.
