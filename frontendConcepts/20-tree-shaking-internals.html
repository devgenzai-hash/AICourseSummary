Tree Shaking Internals

How bundlers eliminate dead code by analyzing ES module import/export graphs — the static analysis that can cut your bundle size in half.

Intermediate Concept Performance
🌳 Analogy: Shaking a Tree

Imagine your code is a tree. Each function or export is a branch. Tree shaking grabs the tree by the trunk (your entry point) and shakes it — any branch (code) that isn't connected to something you're actually using falls off and gets removed from the final bundle. Dead branches = dead code.

The Problem: Importing Everything You Don't Use

// You import ONE function from lodash
import { debounce } from 'lodash';

// Without tree shaking: the ENTIRE lodash library (70KB) ships to users
// With tree shaking: only debounce and its dependencies ship (~2KB)

// BUT: tree shaking only works with ES modules (import/export)
// CommonJS (require()) is dynamic — can't be statically analyzed
const _ = require('lodash'); // NOT tree-shakeable — entire library included

How Tree Shaking Works

  1. Build the module graph — Starting from entry point, follow all imports to build a dependency graph.
  2. Mark exports as "used" or "unused" — Trace which exported bindings are actually imported somewhere.
  3. Detect side effects — Code that runs just by being imported (modifies globals, calls functions at top level) can't be removed safely.
  4. Eliminate dead code — Remove unused exports and their dependencies (if not used elsewhere).
// utils.js — Three exports, but consumer only uses one
export function add(a, b) { return a + b; }    // USED → kept
export function multiply(a, b) { return a * b; } // UNUSED → removed
export function divide(a, b) { return a / b; }   // UNUSED → removed

// app.js — Only imports add
import { add } from './utils';
console.log(add(2, 3));

// After tree shaking, bundle only contains the 'add' function

The Side Effects Problem

// This file has SIDE EFFECTS — can't be safely removed
// Even if nothing imports from it, it modifies global state
Array.prototype.customFind = function() { /* ... */ };

// package.json "sideEffects" field tells bundler what's safe to remove
{
    "name": "my-library",
    "sideEffects": false  // ALL files are pure — safe to tree-shake any unused export
}

// Or specify which files have side effects:
{
    "sideEffects": ["*.css", "./src/polyfills.js"]
    // CSS imports are side-effectful (they modify appearance)
    // Polyfills modify globals
}

Where This Is Used in Production

  • Webpack — Uses "sideEffects": false in package.json + Terser for dead code elimination.
  • Rollup — Pioneer of tree shaking. Uses ESM-first approach with aggressive dead code removal.
  • Material UI — Restructured exports so importing one component doesn't pull in all 100+ components. Each component in its own entry point.

Common Mistakes

  • Re-exporting everything from index.js — export * from './a'; export * from './b'; can defeat tree shaking in some bundlers.
  • CommonJS in node_modules — Many npm packages still ship CJS. Check for "module" or "exports" field in package.json for ESM versions.
  • Class declarations with side effects — Class decorators, static initializers, or extends expressions can be flagged as side-effectful.
  • Not setting sideEffects in package.json — Without this, bundlers must assume any file could have side effects and won't remove it.

✅ You Truly Understand Tree Shaking When...

You can look at a bundle analysis (webpack-bundle-analyzer) and explain why a particular module wasn't tree-shaken — whether it's because of side effects, CJS format, re-exports, or dynamic access patterns.

🧪 Try This Challenge

Create a library with 10 utility functions. Import only 2 in your app. Verify with bundle-analyzer that only those 2 (and their deps) end up in the final bundle. Then add a side-effectful module and observe how it defeats tree shaking.

🔗 Connect It

Tree Shaking connects to: Code Splitting (another bundle size optimization), Dynamic Import Chunking (lazy-loaded modules), and Module Federation (sharing code across applications).
