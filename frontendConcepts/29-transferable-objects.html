Transferable Objects

Zero-copy data transfer between threads — how to move ownership of ArrayBuffers, MessagePorts, and OffscreenCanvas across execution contexts without the serialization cost of structured cloning.

Intermediate Performance Browser API
📦 Daily-Life Analogy: Moving vs Photocopying

Normal postMessage is like photocopying a document before handing it to a colleague — slow, uses double the paper. Transferable is like physically handing over the original document — instant, no duplication. But now YOU no longer have it. Ownership transfers completely.

The Problem: Structured Clone Is Expensive

When you postMessage(data) to a worker, the browser uses the structured clone algorithm to deep-copy the data. For a 100MB ArrayBuffer:

  • Time: ~50-100ms to copy 100MB (blocks the sending thread during copy)
  • Memory: 200MB total (original + copy)
  • GC pressure: The copy must eventually be garbage collected

Transferable objects solve this: the buffer's ownership moves to the other thread. The operation is O(1) regardless of buffer size — it just reassigns the memory pointer.

Code: Transferring vs Cloning

// ❌ SLOW: Structured clone — copies 100MB
const buffer = new ArrayBuffer(100 * 1024 * 1024); // 100MB
worker.postMessage({ data: buffer }); // ~80ms to copy!
console.log(buffer.byteLength); // 104857600 — still have it

// ✅ FAST: Transfer — moves ownership in O(1)
const buffer2 = new ArrayBuffer(100 * 1024 * 1024);
worker.postMessage({ data: buffer2 }, [buffer2]); // Second arg = transfer list
console.log(buffer2.byteLength); // 0 — buffer is NEUTERED! You lost it.

// Modern syntax (structuredClone also supports it):
worker.postMessage({ data: buffer3 }, { transfer: [buffer3] });

Practical Pattern: Worker Image Processing Pipeline

// main.js — Transfer image data to worker, get processed result back
const worker = new Worker('image-worker.js');

async function processImage(file) {
    const arrayBuffer = await file.arrayBuffer();
    
    // Transfer TO worker (we give up access to arrayBuffer)
    worker.postMessage(
        { type: 'process', buffer: arrayBuffer },
        [arrayBuffer]  // Transfer list — zero copy!
    );
    // arrayBuffer.byteLength === 0 now
}

worker.onmessage = (e) => {
    // Worker transferred the result BACK — zero copy return
    const processedBuffer = e.data.buffer;
    const blob = new Blob([processedBuffer], { type: 'image/png' });
    document.getElementById('output').src = URL.createObjectURL(blob);
};

// image-worker.js — Receives buffer, processes, transfers back
self.onmessage = (e) => {
    const { buffer } = e.data;
    
    // Create a view to manipulate the pixel data
    const pixels = new Uint8Array(buffer);
    
    // Apply grayscale filter (modify in place)
    for (let i = 0; i < pixels.length; i += 4) {
        const avg = (pixels[i] + pixels[i+1] + pixels[i+2]) / 3;
        pixels[i] = pixels[i+1] = pixels[i+2] = avg;
    }
    
    // Transfer back — worker loses access, main thread gets it for free
    self.postMessage({ buffer: buffer }, [buffer]);
};

💡 Transfer is Always O(1)

Regardless of buffer size, transfer takes constant time because it only moves a pointer. The actual bytes never move in memory — only the ownership metadata changes. This is why it's called "zero-copy."

Where This Is Used in Production

  • Photoshop Web — Transfers pixel data (often hundreds of MB) between rendering workers and the main thread without copying.
  • Zoom Web Client — Audio/video frame buffers are transferred between decode workers and rendering for real-time performance.
  • Google Maps — Tile image data decoded in workers is transferred back as ImageBitmaps for zero-copy rendering to canvas.

Common Mistakes

  • Accessing transferred buffer after transfer — The buffer becomes detached (0 bytes). Any TypedArray view into it becomes unusable. This is a silent failure, not an error.
  • Transferring when you still need the data — If you need to keep a copy, clone first: buffer.slice(), then transfer the clone.
  • Confusing transfer list with message — The transfer list is a separate argument. Objects in the list must also appear in the message itself.
  • Trying to transfer non-transferable objects — Regular objects, strings, Maps, etc. cannot be transferred. Only specific types listed above.
