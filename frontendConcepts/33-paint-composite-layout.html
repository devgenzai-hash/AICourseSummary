Paint vs Composite vs Layout

The three stages of the rendering pipeline that determine animation performance — which CSS properties trigger which stage, and why "composite-only" animations are the holy grail of web performance.

Intermediate Rendering Pipeline Performance
🏗️ Daily-Life Analogy: Renovating a Building

Layout = changing the floor plan (moving walls, resizing rooms). Everything downstream must redo. Paint = repainting the walls a new color. Rooms stay the same size, but you need to repaint. Composite = rearranging picture frames on an already-painted wall. Nothing redraws — you just shift existing things around. The further "up" the pipeline you trigger, the more expensive the frame.

The Rendering Pipeline

/*
  Full pipeline (triggered by layout changes):
  
  JavaScript → Style → LAYOUT → Paint → Composite
  
  Paint-only (triggered by visual-only changes):
  
  JavaScript → Style → Paint → Composite
  
  Composite-only (triggered by transform/opacity):
  
  JavaScript → Style → Composite
  
  Each skipped stage = massive performance gain per frame
*/

Which Properties Trigger Which Stage

Stage TriggeredCSS PropertiesCost per Frame
Layout (most expensive) width, height, padding, margin, top, left, display, position, font-size, border-width, flex 5-50ms (recalculates geometry of affected elements + siblings + children)
Paint (moderate) color, background, box-shadow, border-color, border-radius, visibility, text-decoration, outline 1-10ms (re-rasterizes affected layers)
Composite only (cheapest) transform, opacity, filter (on composited layers), will-change <1ms (GPU moves/blends existing textures)

Code: Same Animation, Three Different Costs

/* ❌ WORST: Animating 'left' triggers LAYOUT every frame */
/* Pipeline: Style → Layout → Paint → Composite (all 4 stages!) */
.bad-animation {
    position: absolute;
    transition: left 0.3s;
}
.bad-animation:hover {
    left: 200px; /* Forces layout recalculation on every frame */
}

/* ⚠️ MEDIUM: Animating 'background-color' triggers PAINT */
/* Pipeline: Style → Paint → Composite (skips layout) */
.medium-animation {
    transition: background-color 0.3s;
}
.medium-animation:hover {
    background-color: blue; /* Repaint needed but no layout shift */
}

/* ✅ BEST: Animating 'transform' is COMPOSITE ONLY */
/* Pipeline: Style → Composite (skips both layout AND paint!) */
.good-animation {
    transition: transform 0.3s;
}
.good-animation:hover {
    transform: translateX(200px); /* GPU just moves the texture */
}

Proving It with DevTools

// Performance panel → Record during animation
// Look for these in the flame chart:

// "Paint" bars → triggered by color/background changes
// "Composite Layers" bars → always present (final composition)
//
// Goal: ONLY see "Composite Layers" during animation frames
// If you see Layout or Paint bars during animation → performance problem

// Quick visual check:
// Rendering tab → Check "Paint flashing"
// Green flashes = repaint happening
// During a transform animation, you should see NO green flashes

The Layout Thrashing Connection

// Layout is especially expensive when "forced synchronously"
// Reading geometry after writing forces the browser to layout immediately

// ❌ LAYOUT THRASH: read-write-read-write pattern
elements.forEach(el => {
    const height = el.offsetHeight;    // READ → forces layout
    el.style.height = height * 2 + 'px'; // WRITE → invalidates layout
    // Next read will force ANOTHER layout...
});

// ✅ BATCHED: all reads first, then all writes
const heights = elements.map(el => el.offsetHeight); // All reads
elements.forEach((el, i) => {
    el.style.height = heights[i] * 2 + 'px'; // All writes
});

Where This Is Used in Production

  • Every animation library — GSAP, Framer Motion, and CSS transitions all prefer transform over positional properties because they know the pipeline cost.
  • Chrome's compositor thread — Handles scroll and transform animations entirely off the main thread, which is why scrolling stays smooth even when JS is busy.
  • React Native / Flutter — These frameworks render to a layer-based compositor (Skia), similar to how browser compositing works.

Common Mistakes

  • Animating top/left instead of transform — The most common performance mistake. top/left triggers full layout. transform: translate() is composite-only.
  • Animating width/height for expand/collapse — Use transform: scaleY() or animate max-height with containment instead.
  • Assuming filter is always cheap — filter: blur() is cheap only on elements with their own compositing layer. On non-composited elements, it triggers paint.
  • Not measuring — "Composite-only" is a goal, not a guarantee. Always verify with Performance panel.
