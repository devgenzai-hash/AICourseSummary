Preload vs Prefetch vs Preconnect

Three resource hints that tell the browser what to fetch early — each with different timing, priority, and use cases. Getting these wrong wastes bandwidth or has zero effect.

Intermediate Performance Resource Loading
📬 Daily-Life Analogy: Mail Preparation

Preconnect = looking up the address and warming up the car (DNS + TCP + TLS handshake). Preload = driving there RIGHT NOW to pick up a package you NEED today (critical resource for current page). Prefetch = asking the mailman to grab something on his next idle route for tomorrow (resource for future navigation).

The Three Hints Compared

HintWhat It DoesPriorityWhen to Use
<link rel="preload">Fetch THIS resource NOW for current pageHigh (mandatory)Fonts, critical CSS, LCP images, above-fold scripts
<link rel="prefetch">Fetch resource for FUTURE navigation (low priority, idle time)LowestNext page's JS bundle, likely navigation targets
<link rel="preconnect">Establish connection (DNS + TCP + TLS) without fetchingHigh (connection only)CDNs, API origins, font providers (any cross-origin)
<link rel="dns-prefetch">Resolve DNS only (cheapest hint)Very lowThird-party origins you'll contact eventually

Code: Correct Usage

<!-- PRELOAD: "I need this NOW for the current page" -->
<!-- Browser discovers fonts late (after CSS parses). Preload fixes that. -->
<link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin>

<!-- Preload critical above-fold image (LCP candidate) -->
<link rel="preload" href="/hero.webp" as="image" fetchpriority="high">

<!-- Preload a CSS file loaded via @import (normally late-discovered) -->
<link rel="preload" href="/components.css" as="style">

<!-- ⚠️ CRITICAL: 'as' attribute is REQUIRED -->
<!-- Without 'as', browser doesn't know the priority or CORS mode -->
<!-- It downloads twice or applies wrong priority -->

<!-- PRECONNECT: "I'll need to talk to this origin soon" -->
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://api.example.com" crossorigin>
<!-- Saves 100-300ms per cross-origin connection (DNS + TCP + TLS) -->

<!-- DNS-PREFETCH: "I might talk to this origin" (cheaper than preconnect) -->
<link rel="dns-prefetch" href="https://analytics.example.com">

<!-- PREFETCH: "The user will probably navigate here next" -->
<link rel="prefetch" href="/next-page-bundle.js">
<link rel="prefetch" href="/api/next-page-data" as="fetch">
<!-- Downloaded at LOWEST priority during idle time -->
<!-- Cached for future use (5 min in Chrome) -->

Dynamic Prefetch on User Intent

// Prefetch next page when user hovers over a link (high intent signal)
document.querySelectorAll('a[data-prefetch]').forEach(link => {
    link.addEventListener('mouseenter', () => {
        const prefetchLink = document.createElement('link');
        prefetchLink.rel = 'prefetch';
        prefetchLink.href = link.href;
        document.head.appendChild(prefetchLink);
        // By the time user clicks (~200-400ms later), resource is already cached
    }, { once: true }); // Only prefetch once per link
});

⚠️ Preload Warnings: "was preloaded but not used"

If you preload a resource but don't use it within ~3 seconds, Chrome logs a console warning. This means you're wasting bandwidth. Common causes: preloading a font that's only used on a specific page (but the preload is in the global layout), or preloading below-fold images that aren't needed immediately.

Where This Is Used in Production

  • Next.js — Automatically prefetches linked pages' JS bundles on viewport visibility. Uses <link rel="prefetch"> for route chunks.
  • Google Fonts — Recommends preconnect to fonts.googleapis.com AND fonts.gstatic.com (two different origins in the font loading flow).
  • Shopify — Preloads LCP hero images and critical fonts, resulting in measurable LCP improvements across millions of storefronts.

Common Mistakes

  • Preloading everything — If you preload 10 resources, they ALL compete for bandwidth simultaneously. Preload is for 1-3 critical resources max.
  • Missing crossorigin on font preloads — Fonts always request with CORS. Without crossorigin attribute, the preload fetches without CORS, the actual font request uses CORS → double download!
  • Prefetch on slow connections — On 2G/3G, prefetching future pages wastes the user's limited bandwidth. Use navigator.connection.saveData to skip.
  • Too many preconnects — Each connection costs memory and CPU. Limit to 2-4 most critical origins.

✅ You Truly Understand Preload vs Prefetch vs Preconnect When...

You can explain why preloading a font without crossorigin causes a double download, why prefetch uses idle-time bandwidth and doesn't affect current page load, and when preconnect saves more time than preload (hint: when you don't know the exact resource URL yet).

🔗 Connect It

Resource hints connect to: Priority Hints (fetchpriority further controls preload priority), Critical Rendering Path (preload puts resources in the critical path), and HTTP/3 (preconnect establishes QUIC connections that benefit from 0-RTT on subsequent requests).
