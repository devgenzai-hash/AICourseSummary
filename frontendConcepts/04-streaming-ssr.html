Streaming SSR

Sending HTML to the browser in chunks as it's generated rather than waiting for the entire page to be ready — dramatically reducing Time to First Byte.

Advanced Concept Performance
📺 Analogy: Streaming Video vs Downloading

Traditional SSR is like downloading an entire movie before you can watch it. Streaming SSR is like Netflix — you start watching immediately while the rest buffers in the background. The header and navigation appear instantly; slower parts (database queries for the main content) arrive as they're ready.

The Problem: Blocking SSR

Traditional SSR has a serial bottleneck:

  1. Server receives request
  2. Server fetches ALL data (database calls, API requests) — blocks here
  3. Server renders ALL components to HTML — blocks here
  4. Server sends complete HTML response
  5. Browser receives and displays

If one slow API call takes 2 seconds, the entire page is delayed by 2 seconds — even the parts that were ready instantly.

How Streaming SSR Works

// React 18 Streaming SSR with renderToPipeableStream
import { renderToPipeableStream } from 'react-dom/server';

function handleRequest(req, res) {
    const { pipe } = renderToPipeableStream(
        <App />,
        {
            // Called when the shell (non-suspended content) is ready
            onShellReady() {
                res.setHeader('Content-Type', 'text/html');
                res.setHeader('Transfer-Encoding', 'chunked');
                // Start streaming immediately — don't wait for everything
                pipe(res);
            },
            onShellError(err) {
                // If the shell fails, fall back to client rendering
                res.status(500).send('<script>location.href="/client-only"</script>');
            },
            onError(err) {
                console.error(err);
            }
        }
    );
}

// The App component uses Suspense boundaries to define streaming chunks
function App() {
    return (
        <>
            {/* This renders immediately — part of the "shell" */}
            <Header />
            <Navigation />
            
            {/* This streams in when the data fetch completes */}
            <Suspense fallback={<ArticleSkeleton />}>
                <ArticleContent />  {/* Fetches from database */}
            </Suspense>
            
            {/* This streams independently — doesn't block article */}
            <Suspense fallback={<CommentsSkeleton />}>
                <Comments />  {/* Fetches from API */}
            </Suspense>
            
            <Footer />
        </>
    );
}
💡 How Streaming Sends Late Content

When a Suspense boundary resolves, React doesn't re-send the HTML. Instead, it sends a small <script> tag at the bottom of the stream that calls a function to swap the fallback with the real content. The browser executes this inline script and replaces the skeleton. This is called out-of-order streaming.

Real-World Usage

  • Next.js App Router — Uses React 18 streaming by default. Every loading.js file creates a Suspense boundary that streams.
  • Remix — Uses defer() to stream non-critical data while sending the shell immediately.
  • Shopify Hydrogen — Streams product pages; the product info loads fast while reviews stream later.

Trade-offs

  • Pro: TTFB is dramatically faster — user sees shell immediately
  • Pro: Slow data sources don't block fast ones
  • Pro: Better perceived performance (progressive loading)
  • Con: Can't set HTTP headers after streaming starts (status code, redirects)
  • Con: Error handling is more complex (can't show 500 page if data fails mid-stream)
  • Con: CDN caching is harder with chunked responses

✅ You Truly Understand Streaming SSR When...

You can explain why you can't do a redirect after the stream starts, and how Suspense boundaries define the granularity of what streams independently.
