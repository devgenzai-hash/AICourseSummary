Cache Invalidation Strategies

"There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton. How to ensure users get fresh content while maximizing cache hit rates.

Intermediate Performance Caching
📰 Daily-Life Analogy: Newspaper Delivery

Caching is keeping yesterday's newspaper on your desk (fast access). Invalidation is knowing when to throw it away and get today's edition. Too aggressive = you're reading stale news. Too conservative = you walk to the newsstand every time (slow). The art is knowing exactly when your paper becomes stale.

The Strategies

1. Content-Hash Filenames (Immutable Caching)

/* The Gold Standard for Static Assets */
/* File: app.a1b2c3d4.js (hash is in the filename) */
/*
 * Strategy:
 * - File content changes → hash changes → new filename → new URL
 * - Old file is never "invalidated" — it's just abandoned
 * - Cache forever: Cache-Control: public, max-age=31536000, immutable
 * - HTML file (entry point) is NEVER cached long (it references the hashed URLs)
 */

// Webpack/Vite output:
// index.html → Cache-Control: no-cache (always revalidate)
//   <script src="/assets/app.a1b2c3d4.js"> → Cache-Control: immutable, 1 year
//   <link href="/assets/style.e5f6g7h8.css"> → Cache-Control: immutable, 1 year

// On deploy: new hash = new URL = browser fetches fresh version
// No invalidation needed — old URLs just stop being referenced

2. Version Query Strings (Simpler But Weaker)

<!-- Less reliable than content hashing -->
<script src="/app.js?v=2.1.0"></script>

<!-- Problems:
  - Some CDNs/proxies strip query strings from cache keys
  - Must manually bump version on every change
  - All assets bust simultaneously (even unchanged ones)
-->

3. Time-Based Expiration (TTL)

// Server sends: Cache-Control: max-age=3600 (1 hour)
// Browser caches for 1 hour, then revalidates
// Good for: API responses that change hourly, news feeds
// Bad for: Critical real-time data, frequently deployed apps

// The problem: during the 1-hour window, user gets stale data
// Even after you deploy a fix, users are stuck for up to 1 hour

4. Event-Driven Invalidation (Purge)

// CDN purge on deploy (Cloudflare, Fastly, CloudFront)
// When you deploy → API call to CDN → purge specific URLs → users get fresh content

// Example: Fastly purge by surrogate key
// curl -X POST https://api.fastly.com/service/{id}/purge/article-123
// All cached responses tagged with "article-123" are instantly invalidated

// Good for: CMS content, database-driven pages
// Requires: CDN API integration in your deploy pipeline

Where This Is Used in Production

  • Every modern bundler (Webpack, Vite, esbuild) — Content hashing is the default output strategy for production builds.
  • Vercel / Netlify — Automatically applies immutable caching to hashed assets and no-cache to HTML pages.
  • Cloudflare — Surrogate keys and instant purge APIs allow surgical cache invalidation without clearing everything.
  • Next.js ISR (Incremental Static Regeneration) — Time-based revalidation at the page level with on-demand revalidation API.

Common Mistakes

  • Caching index.html with long max-age — If the HTML file is cached, users never discover the new hashed JS/CSS URLs. HTML must always revalidate.
  • Using content hashing without splitting vendors — If app code and React are in one file, changing one line busts the entire 500KB cache. Split vendor chunks.
  • Forgetting Service Worker's cache — Even after CDN purge, the SW's Cache Storage may still serve old content. SW must also update.
  • Not accounting for CDN propagation delay — After purge, edge nodes may take 1-5 seconds to propagate. Users hitting un-purged edges get stale content briefly.

✅ You Truly Understand Cache Invalidation When...

You can design a caching strategy where: hashed static assets are cached forever, HTML always revalidates, API data uses stale-while-revalidate, and you can force-update any user within seconds of a deploy — without cache-busting everything.

🧪 Try This Challenge

Set up a Vite project and deploy to a CDN. Verify: (1) JS/CSS files have content hashes and immutable headers, (2) index.html has no-cache, (3) changing one component only busts that chunk's hash, not all chunks. Bonus: add a Service Worker that respects the invalidation.
