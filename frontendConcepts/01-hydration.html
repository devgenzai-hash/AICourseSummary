Frontend Concepts / Hydration

Hydration

How server-rendered HTML becomes an interactive application in the browser — the bridge between static markup and dynamic behavior.

Intermediate Concept Browser
🌊 Daily-Life Analogy: Inflating a Bounce House

Imagine you receive a deflated bounce house (server HTML). It looks like a bounce house — you can see its shape and colors — but you can't interact with it. Hydration is the process of pumping air into it (attaching event listeners, initializing state), transforming the static structure into something interactive.

The key insight: the structure already exists. You don't rebuild the bounce house from scratch — you just make the existing one functional.

The Problem: Why Hydration Exists

Modern web apps face a fundamental tension:

  • Server-Side Rendering (SSR) gives fast first paint and SEO — the user sees content quickly
  • Client-Side Rendering (CSR) gives rich interactivity — buttons work, forms validate, state updates

Hydration solves this by doing both: render HTML on the server for speed, then "hydrate" it on the client for interactivity. Without hydration, you'd either have a slow initial load (pure CSR) or a non-interactive page (pure SSR).

How Hydration Works Internally

Step-by-Step Process

  1. Server renders HTML — Components execute on the server, producing a complete HTML string
  2. HTML is sent to browser — User sees content immediately (First Contentful Paint)
  3. JavaScript bundle downloads — The framework code + component code arrives
  4. Framework "walks" the DOM — It traverses the existing DOM tree, matching it to the component tree
  5. Event listeners are attached — Click handlers, change handlers, etc. get wired up
  6. State is initialized — Component state is set up (often from serialized server state)
  7. App is interactive — Time to Interactive (TTI) is reached
⚠️ The Hydration Mismatch Problem

If the server-rendered HTML doesn't match what the client would render, you get a hydration mismatch. React will throw warnings and may discard the server HTML entirely, defeating the purpose of SSR. Common causes: Date.now(), Math.random(), browser-only APIs like window.innerWidth.

Code: React Hydration

// server.js — Server renders the initial HTML
import { renderToString } from 'react-dom/server';
import App from './App';

function handleRequest(req, res) {
    // Execute components on server — produces HTML string
    const html = renderToString(<App initialData={data} />);
    
    // Send complete HTML — user sees content before JS loads
    res.send(`
        <!DOCTYPE html>
        <html>
        <body>
            <div id="root">\${html}</div>
            <script>
                // Serialize state so client can pick up where server left off
                window.__INITIAL_STATE__ = \${JSON.stringify(data)};
            </script>
            <script src="/bundle.js"></script>
        </body>
        </html>
    `);
}

// client.js — Client hydrates the existing HTML
import { hydrateRoot } from 'react-dom/client';
import App from './App';

// hydrateRoot does NOT rebuild the DOM — it attaches to existing HTML
// React walks the existing DOM tree and wires up event handlers
const root = hydrateRoot(
    document.getElementById('root'),
    <App initialData={window.__INITIAL_STATE__} />
);

// Key difference from createRoot:
// createRoot: builds DOM from scratch (discards existing HTML)
// hydrateRoot: reuses existing DOM, only adds interactivity

The Performance Cost of Hydration

Full hydration has a dirty secret: it's expensive. The framework must:

  • Download ALL component JavaScript (even for static content)
  • Execute ALL components on the client (to build the virtual tree)
  • Walk the entire DOM tree to reconcile
  • Attach event listeners to every interactive element

This means Time to Interactive (TTI) can be much later than First Contentful Paint (FCP). The user sees content but can't interact — the "uncanny valley" of web apps.

MetricNo Hydration (CSR)Full Hydration (SSR+CSR)
First Contentful PaintSlow (wait for JS)Fast (server HTML)
Time to InteractiveSame as FCPDelayed (hydration cost)
Bundle Size ImpactFull bundle neededFull bundle STILL needed
Main Thread WorkRender onceRender twice (server + client)

Where This Is Used in Production

  • Next.js — Uses React's hydrateRoot for all SSR pages. Their App Router leverages streaming + selective hydration for better performance.
  • Gatsby — Static HTML at build time, hydrated on load. Every page is pre-rendered then made interactive.
  • Nuxt.js (Vue) — Same pattern with Vue's createSSRApp and hydration phase.

Common Mistakes

  • Using browser APIs during render — window, document, localStorage don't exist on server. Guard with typeof window !== 'undefined'
  • Non-deterministic rendering — Date.now() produces different values on server vs client, causing mismatches
  • CSS-in-JS without server extraction — Styles must be extracted during SSR or you get a flash of unstyled content
  • Assuming instant interactivity — Users click buttons that aren't hydrated yet. Use loading states or progressive enhancement.

✅ You Truly Understand Hydration When...

You can explain why a user clicking a button 500ms after page load might get no response, and how to design around that gap.
