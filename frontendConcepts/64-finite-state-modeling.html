Frontend Concepts / Finite State Modeling

Finite State Modeling

Using formal state machines and statecharts to eliminate impossible states, prevent race conditions, and make complex UI behavior provably correct — the same mathematical model that powers traffic lights, TCP, and game AI.

Advanced Architecture State Management
📚 Analogy: A Turnstile

A subway turnstile has exactly two states: locked and unlocked. Inserting a coin transitions from locked → unlocked. Pushing the arm transitions from unlocked → locked. You cannot push through a locked turnstile. You cannot insert a coin into an already-unlocked one (it just returns it). This exhaustive, explicit mapping of (state + event → next state) is exactly what finite state machines bring to your UI code — making "impossible states impossible."

The Problem: Boolean Soup and Impossible States

// The typical approach: independent booleans
const [isLoading, setIsLoading] = useState(false);
const [isError, setIsError] = useState(false);
const [isSuccess, setIsSuccess] = useState(false);
const [data, setData] = useState(null);

// How many states is this? 2 × 2 × 2 = 8 combinations
// But only 4 are VALID: idle, loading, success, error
// The other 4 are IMPOSSIBLE but nothing prevents them:
//   isLoading=true AND isError=true  → loading AND errored?!
//   isSuccess=true AND isError=true  → succeeded AND failed?!
//   isLoading=true AND isSuccess=true → still loading but done?!

// Bugs from impossible states are SILENT — no runtime error,
// just weird UI: spinner + error message showing simultaneously

// The finite state machine approach: ONE variable, explicit transitions
type FetchState = 'idle' | 'loading' | 'success' | 'error';
// Now it's physically impossible to be loading AND errored

The Mental Model: States, Events, Transitions

A Finite State Machine (FSM) consists of exactly five things:

ComponentWhat It IsUI Example
States (finite set)All possible modes the system can be inidle, loading, success, error
EventsThings that happen (triggers)FETCH, RESOLVE, REJECT, RETRY
TransitionsRules: (current state + event) → next stateidle + FETCH → loading
Initial stateWhere the machine startsidle
Final states (optional)Terminal states (no further transitions)destroyed, completed

How It Works: From Concept to Implementation

// A minimal state machine implementation — no libraries needed
// This pattern powers XState, Robot, and similar libraries internally

function createMachine(config) {
  // The machine definition is a pure data structure — no side effects
  // This separation enables visualization, testing, and serialization
  let currentState = config.initial;

  return {
    // transition() is the HEART of the state machine:
    // Given current state + event, compute next state deterministically
    transition(event) {
      const stateNode = config.states[currentState];

      // Guard: if no transition defined for this event in this state,
      // the event is simply IGNORED — this is a feature, not a bug.
      // It prevents invalid transitions by construction.
      if (!stateNode.on || !stateNode.on[event]) {
        console.warn(`No transition for event "${event}" in state "${currentState}"`);
        return currentState;
      }

      const nextState = stateNode.on[event];
      currentState = nextState;
      return currentState;
    },

    getState() {
      return currentState;
    }
  };
}

// Usage: a fetch state machine
const fetchMachine = createMachine({
  initial: 'idle',
  states: {
    idle: {
      on: { FETCH: 'loading' }
      // Only FETCH can move us out of idle — retry, resolve etc. are ignored
    },
    loading: {
      on: {
        RESOLVE: 'success',
        REJECT: 'error'
        // Note: no FETCH transition — can't double-fetch from loading state
      }
    },
    success: {
      on: { FETCH: 'loading' }
      // Can re-fetch, but can't go to error directly from success
    },
    error: {
      on: { RETRY: 'loading' }
      // Only RETRY moves us back — deliberate user action required
    }
  }
});

// The machine GUARANTEES these scenarios are impossible:
// - Double-clicking "Submit" causing two requests (FETCH from loading = no-op)
// - Late response overwriting new data (RESOLVE from idle/error = no-op)
// - Showing error + success simultaneously (mutually exclusive states)

fetchMachine.transition('FETCH');    // idle → loading
fetchMachine.transition('FETCH');    // loading → loading (ignored! no transition defined)
fetchMachine.transition('RESOLVE');  // loading → success
fetchMachine.transition('REJECT');   // success → success (ignored! can't error from success)

Statecharts: Hierarchical and Parallel States

Real UIs outgrow flat FSMs quickly. Statecharts (David Harel, 1987) extend FSMs with three critical features:

// 1. HIERARCHICAL (nested) states — reduce state explosion
// Instead of: loggedIn_dashboard, loggedIn_settings, loggedIn_profile...
// You model: loggedIn → { dashboard, settings, profile }

const appMachine = {
  initial: 'loggedOut',
  states: {
    loggedOut: {
      on: { LOGIN: 'loggedIn' }
    },
    loggedIn: {
      // Nested machine — loggedIn is itself a container of sub-states
      initial: 'dashboard',
      states: {
        dashboard: { on: { NAV_SETTINGS: 'settings' } },
        settings: { on: { NAV_DASHBOARD: 'dashboard' } }
      },
      // Events defined HERE apply to ALL child states (event bubbling)
      on: { LOGOUT: 'loggedOut' }
      // ↑ LOGOUT works from dashboard OR settings — defined once
    }
  }
};

// 2. PARALLEL (orthogonal) states — independent concerns run simultaneously
const editorMachine = {
  type: 'parallel',
  states: {
    // These two machines operate independently within the same parent
    editMode: {
      initial: 'viewing',
      states: {
        viewing: { on: { EDIT: 'editing' } },
        editing: { on: { SAVE: 'viewing' } }
      }
    },
    connection: {
      initial: 'online',
      states: {
        online: { on: { DISCONNECT: 'offline' } },
        offline: { on: { RECONNECT: 'online' } }
      }
    }
  }
  // Current state: { editMode: 'viewing', connection: 'online' }
  // Can be editing+offline, viewing+online, etc. — all combinations valid
};

// 3. GUARDS (conditional transitions) — same event, different outcome
const paymentMachine = {
  states: {
    checkout: {
      on: {
        SUBMIT: [
          // Guards are evaluated in order — first match wins
          { target: 'processing', guard: (ctx) => ctx.balance >= ctx.total },
          { target: 'insufficientFunds' }
          // ↑ Default fallback if guard fails
        ]
      }
    }
  }
};

Real-World Usage

  • XState (Stately.ai) — The most popular statechart library for JavaScript. Used by Netflix, Lyft, and Microsoft for complex UI flows. Provides visual editor, testing tools, and auto-generated documentation from machine definitions.
  • TCP Protocol (RFC 793) — The TCP connection lifecycle (LISTEN → SYN_SENT → ESTABLISHED → FIN_WAIT → CLOSED) is a textbook FSM. Every network stack implements this exact state diagram.
  • React Router v6 — Internally models navigation as state transitions. URL changes are events, route matches are states, redirects are guarded transitions.
  • Figma — Uses state machines for their interactive prototype mode. Each frame is a state, user interactions (click, hover, drag) are events, and animations are transitions with effects.
  • Game Engines (Unity, Unreal) — Character AI controllers are hierarchical state machines: idle → walking → running → attacking, with sub-states like attacking.windup → attacking.strike → attacking.recovery.

Integration with React

// Using a state machine with React via useReducer — no library needed
// This is the pattern XState's useMachine hook implements internally

const machineConfig = {
  initial: 'idle',
  states: {
    idle: { on: { FETCH: 'loading' } },
    loading: { on: { RESOLVE: 'success', REJECT: 'error' } },
    success: { on: { FETCH: 'loading' } },
    error: { on: { RETRY: 'loading' } }
  }
};

// The reducer IS the transition function — pure, testable, predictable
function machineReducer(state, event) {
  const nextState = machineConfig.states[state.value]?.on?.[event.type];
  if (!nextState) return state; // Invalid transition → state unchanged

  return {
    value: nextState,
    context: event.data
      ? { ...state.context, ...event.data }
      : state.context
  };
}

function UserProfile() {
  const [state, send] = useReducer(machineReducer, {
    value: machineConfig.initial,
    context: { data: null, error: null }
  });

  async function fetchUser() {
    send({ type: 'FETCH' });
    try {
      const data = await api.getUser();
      send({ type: 'RESOLVE', data: { data } });
    } catch (error) {
      send({ type: 'REJECT', data: { error } });
    }
  }

  // Render based on state.value — exhaustive switch guarantees all states handled
  switch (state.value) {
    case 'idle': return <button onClick={fetchUser}>Load</button>;
    case 'loading': return <Spinner />;
    case 'success': return <Profile data={state.context.data} />;
    case 'error': return <Error onRetry={() => send({ type: 'RETRY' })} />;
  }
}

Trade-offs & Alternatives

ApproachStrengthsWeaknesses
Finite State Machine (flat) Simple, exhaustive, visualizable, no impossible states State explosion with many orthogonal concerns
Statecharts (hierarchical) Handles complex UIs; parallel states; guards; actions Learning curve; heavier; overkill for simple forms
Boolean flags (useState) Zero ceremony; familiar; fast to write Impossible states; no transition validation; bugs at scale
Redux/Zustand reducers Flexible; community tooling; time-travel debugging No formal state constraints; any transition possible
Enum + switch Simple discriminated union; no library needed No transition enforcement; easy to bypass

Common Mistakes

  • Modeling data as states — Don't create states like dataIsArray or countIs5. States represent modes of behavior, not data values. Use context/extended state for data.
  • Too many states — If your machine has 50 flat states, you need hierarchy. Parallel states and nested machines reduce exponential combinations to linear.
  • Forgetting the "do nothing" power — When an event has no defined transition, it's intentionally ignored. Developers new to FSMs add transitions for every event in every state — this defeats the purpose.
  • Side effects in transitions — Transitions should be pure computations. Side effects (API calls, DOM mutations) belong in actions/effects triggered by transitions, not the transition logic itself.
  • Not using TypeScript's exhaustive checking — If your switch statement doesn't cover all states, TypeScript can catch this at compile time with never type assertions. Skipping this loses half the safety benefit.

✅ You Truly Understand Finite State Modeling When...

You can look at any UI component with complex conditional logic and immediately identify the implicit state machine — the states, events, and transitions hiding behind the boolean flags — and refactor it into an explicit machine that makes impossible states unrepresentable and every transition auditable.
