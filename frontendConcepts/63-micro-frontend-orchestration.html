Frontend Concepts / Micro-Frontend Orchestration

Micro-Frontend Orchestration

Composing a single user-facing application from multiple independently-deployed frontend applications — enabling teams to ship features autonomously without coordinating monolithic releases.

Advanced Architecture Organization
🏙️ Analogy: Shopping Mall

A shopping mall is a single building (application) composed of independent stores (micro-frontends). Each store has its own inventory, staff, and opening hours (independent deployment). The mall provides shared infrastructure: hallways (routing), security (auth), and a directory (service discovery). Stores can renovate independently without closing the whole mall.

The Problem: Frontend Monolith at Scale

When 50+ engineers work on one SPA:

  • Coupling — Changing the checkout page breaks the search page (shared state, shared deps)
  • Deploy risk — One team's bug blocks all teams' releases
  • Build times — 30-minute builds because everything is one bundle
  • Tech debt lock-in — Can't upgrade React 16 → 18 incrementally; it's all-or-nothing
  • Team autonomy — Backend teams have microservices; frontend is still monolithic

Orchestration Approaches

Approach 1: Module Federation (Build-time Integration)

// Webpack Module Federation — micro-frontends share code at runtime
// Each micro-frontend is a separate Webpack build that exposes modules

// Shell app (host) — webpack.config.js
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
    plugins: [
        new ModuleFederationPlugin({
            name: 'shell',
            remotes: {
                // Load micro-frontends from their own deployment URLs
                // These are independently deployed applications
                cart: 'cart@https://cart.myapp.com/remoteEntry.js',
                search: 'search@https://search.myapp.com/remoteEntry.js',
                account: 'account@https://account.myapp.com/remoteEntry.js',
            },
            shared: {
                // Shared dependencies — loaded once, used by all micro-frontends
                react: { singleton: true, requiredVersion: '^18.0.0' },
                'react-dom': { singleton: true, requiredVersion: '^18.0.0' },
            }
        })
    ]
};

// Shell app — loads micro-frontends dynamically
const CartWidget = React.lazy(() => import('cart/CartWidget'));
const SearchBar = React.lazy(() => import('search/SearchBar'));

function App() {
    return (
        <Layout>
            <Suspense fallback={<SearchSkeleton />}>
                <SearchBar /> {/* Loaded from search team's deployment */}
            </Suspense>
            <Suspense fallback={<CartSkeleton />}>
                <CartWidget /> {/* Loaded from cart team's deployment */}
            </Suspense>
        </Layout>
    );
}

Approach 2: Server-Side Composition (Edge/Origin Assembly)

// Each micro-frontend serves its own HTML fragment
// A composition layer assembles the full page server-side

// Edge composition with fragment streaming:
async function composePage(request) {
    // Fetch fragments from each micro-frontend service in parallel
    const [header, content, sidebar] = await Promise.all([
        fetch('https://header-service.internal/render'),
        fetch('https://content-service.internal/render?path=' + request.path),
        fetch('https://sidebar-service.internal/render'),
    ]);
    
    // Stream composed HTML to client
    return new Response(
        createComposedStream(header.body, content.body, sidebar.body),
        { headers: { 'Content-Type': 'text/html' } }
    );
}

// Pros: Framework agnostic (React header + Vue sidebar = fine)
// Pros: No client-side coordination overhead
// Cons: Requires server infrastructure for composition
// Used by: Zalando (Project Mosaic), IKEA, many e-commerce platforms

Approach 3: Client-Side Composition (Single-SPA)

// single-spa: Meta-framework that mounts/unmounts micro-frontends
// based on URL routes

import { registerApplication, start } from 'single-spa';

// Each micro-frontend is a full application with lifecycle hooks
registerApplication({
    name: '@team-a/dashboard',
    app: () => System.import('@team-a/dashboard'), // Load from CDN
    activeWhen: ['/dashboard'],  // Mount when URL matches
});

registerApplication({
    name: '@team-b/settings',
    app: () => System.import('@team-b/settings'),
    activeWhen: ['/settings'],
});

registerApplication({
    name: '@shared/navbar',
    app: () => System.import('@shared/navbar'),
    activeWhen: () => true, // Always active (layout component)
});

start(); // Begin routing and mounting

// Each micro-frontend exports lifecycle functions:
// bootstrap() — one-time initialization
// mount(props) — render into DOM container
// unmount(props) — clean up (remove event listeners, etc.)

Communication Between Micro-Frontends

// Micro-frontends need to communicate without tight coupling
// Pattern: Event Bus (Custom Events)

// Shared event contract (npm package: @company/mfe-events)
const MFE_EVENTS = {
    CART_UPDATED: 'mfe:cart:updated',
    USER_LOGGED_IN: 'mfe:auth:login',
    NAVIGATION_REQUESTED: 'mfe:nav:request',
};

// Cart micro-frontend dispatches:
window.dispatchEvent(new CustomEvent(MFE_EVENTS.CART_UPDATED, {
    detail: { itemCount: 3, total: 49.99 }
}));

// Header micro-frontend listens:
window.addEventListener(MFE_EVENTS.CART_UPDATED, (event) => {
    updateCartBadge(event.detail.itemCount);
});

// Rules for healthy communication:
// 1. Events are fire-and-forget (no response expected)
// 2. Payloads are plain objects (no component references)
// 3. Event names are namespaced (prevent collisions)
// 4. Contracts are versioned in a shared package
// 5. Each MFE works WITHOUT the event (graceful degradation)

Shared State and Dependencies

// Problem: Duplicate React = crash (two React instances fight over DOM)
// Solution: Import maps (native browser) or Module Federation shared

// Import map approach (framework agnostic):
<script type="importmap">
{
    "imports": {
        "react": "https://cdn.myapp.com/shared/react@18.2.0/index.js",
        "react-dom": "https://cdn.myapp.com/shared/react-dom@18.2.0/index.js",
        "@company/design-system": "https://cdn.myapp.com/shared/ds@3.0.0/index.js"
    }
}
</script>

// Now all micro-frontends that import 'react' get the same instance
// No bundling needed — browser resolves the shared dependency

// Shared auth state (common requirement):
// Option A: Shared cookie/token — each MFE reads independently
// Option B: Auth MFE exposes a subscribe function via window
window.__AUTH_API__ = {
    getUser: () => currentUser,
    subscribe: (cb) => { listeners.add(cb); return () => listeners.delete(cb); },
    getToken: () => accessToken,
};
⚠️ CSS Isolation Is Critical

Without isolation, micro-frontends' styles bleed into each other. Solutions: (1) CSS Modules or CSS-in-JS with unique prefixes, (2) Shadow DOM for hard isolation, (3) Naming conventions (BEM with team prefix: .team-a__button), (4) @layer for controlled cascade. Shadow DOM provides the strongest guarantee but limits shared design system usage.

Where This Lives in Production

  • IKEA — Server-side composition with fragments. Each product category team owns their micro-frontend. Deployed independently 10+ times/day per team.
  • Spotify — Desktop app uses iframes and a custom plugin system. Each "squad" owns a section of the UI as an independent app.
  • Zalando — Project Mosaic: server-side fragment composition. 100+ teams, each owning a UI fragment (product card, checkout, recommendations).
  • AWS Console — Each service (S3, EC2, Lambda) is a separate micro-frontend composed in a shell application. Different teams, different release cycles.
  • Bit.dev — Component-level micro-frontends. Individual components (not pages) are versioned, published, and composed across projects.

Common Mistakes

  • Micro-frontends for a small team — The coordination overhead (shared contracts, version management, infrastructure) outweighs benefits for < 3 teams.
  • Shared mutable global state — Two micro-frontends writing to the same global store creates implicit coupling worse than a monolith. Use events or API calls.
  • Version drift in shared dependencies — React 18.1 in header + React 18.3 in sidebar can cause subtle bugs. Pin shared deps and upgrade in lockstep.
  • Ignoring performance budget — Each micro-frontend adds its own bundle. Without shared dependencies, you ship React 5 times. Bundle size explodes.
  • Breaking the "independent deployment" contract — If deploying micro-frontend A requires deploying B simultaneously, you've rebuilt a distributed monolith.

✅ You Truly Understand Micro-Frontend Orchestration When...

You can design a system where Team A ships a React 19 micro-frontend alongside Team B's React 18 micro-frontend, both sharing a design system, communicating via events, and deployed independently — without either team needing to know or care about the other's React version.
