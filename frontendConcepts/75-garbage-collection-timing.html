Garbage Collection Timing

How V8's garbage collector decides WHEN to pause your JavaScript — and why your smooth 60fps animation suddenly drops to 15fps for 30ms.

Advanced Performance Browser Internals
🗑️ Analogy: Cleaning While Cooking

Imagine cooking a complex meal. You generate waste (peels, wrappers, scraps) constantly. You can't stop entirely to clean (your food burns), but you also can't let trash pile up forever (you run out of counter space). The GC is the sous-chef who cleans in between your movements — but sometimes has to yell "STOP! I need 30 seconds to take out the trash."

The Problem: Stop-the-World Pauses

JavaScript is single-threaded. When the garbage collector runs, it must pause your code. In V8 (Chrome, Node.js), GC pauses range from 0.1ms to 200ms+ depending on heap size and object graph complexity. On a 16.6ms frame budget (60fps), even a 5ms GC pause can cause visible jank.

V8's Generational GC Architecture

// V8 divides the heap into two spaces based on object age
// This is the "Generational Hypothesis": most objects die young

// ┌──────────────────────────────────────────────────────┐
// │  YOUNG GENERATION (Scavenger)                        │
// │  ┌─────────────┐  ┌─────────────┐                   │
// │  │  Semi-space  │  │  Semi-space  │  ~1-8MB each     │
// │  │  (from)      │  │  (to)        │                  │
// │  └─────────────┘  └─────────────┘                   │
// │  GC Pause: 1-5ms, runs frequently                   │
// ├──────────────────────────────────────────────────────┤
// │  OLD GENERATION (Mark-Sweep-Compact)                 │
// │  ┌──────────────────────────────────────────┐        │
// │  │  Objects that survived 2+ minor GCs      │        │
// │  │  Size: up to several GB                  │        │
// │  └──────────────────────────────────────────┘        │
// │  GC Pause: 10-200ms+ (without incremental marking)  │
// └──────────────────────────────────────────────────────┘

How GC Timing Works Internally

1. Minor GC (Scavenge) — Triggered by Allocation

// Minor GC fires when the young generation's "from" semi-space is full
// Typical trigger: ~1-8MB of allocations since last minor GC

function createManyTemporaryObjects() {
    for (let i = 0; i < 100000; i++) {
        // Each object allocates in young generation
        // When semi-space fills (~4MB default), scavenge triggers
        const temp = { x: i, y: i * 2, label: `item-${i}` };
        processItem(temp);
        // temp becomes unreachable → collected in next scavenge
    }
}

// Scavenge Algorithm (Cheney's semi-space copying):
// 1. Swap "from" and "to" spaces
// 2. Copy LIVE objects from old-from to new-to
// 3. Update all pointers
// 4. Old from-space is now empty (dead objects abandoned in place)
// Cost: O(live objects), NOT O(total objects) — fast if most die

2. Major GC (Mark-Sweep-Compact) — The Expensive One

// Major GC fires when:
// - Old generation exceeds its size limit
// - V8 detects high promotion rate (too many objects surviving)
// - Explicit gc() call (Node.js --expose-gc flag only)

// V8 uses THREE strategies to reduce pause time:

// Strategy 1: INCREMENTAL MARKING
// Instead of marking all objects at once, mark in small steps
// interleaved with JavaScript execution
//
// |--JS--|--mark--|--JS--|--mark--|--JS--|--sweep--|
//         ~1ms     ~5ms    ~1ms          ~2ms

// Strategy 2: CONCURRENT MARKING (since V8 6.4, Chrome 64)
// Helper threads mark objects IN PARALLEL with JS execution
// Main thread only does the final "remark" step (~1-2ms)
//
// Main:   |------JavaScript execution------|--remark--|--JS--|
// Helper: |--------concurrent marking------|

// Strategy 3: LAZY SWEEPING
// Don't sweep all dead objects immediately
// Sweep pages lazily when allocation needs them

3. Idle-Time GC — The Smart Scheduler

// V8 integrates with the browser's task scheduler (Blink)
// It uses idle callbacks to schedule GC during frame deadlines

// 60fps = 16.6ms per frame
// If rendering + JS finishes in 10ms, there's 6.6ms of idle time
// V8 uses this idle time for incremental GC work

// ┌────────────────── 16.6ms frame ──────────────────┐
// │ JS(4ms) │ Style(1ms) │ Layout(2ms) │ Paint(3ms) │ IDLE(6.6ms) │
// │                                                   │ ← GC here  │
// └─────────────────────────────────────────────────────────────────┘

// Chrome's scheduler tells V8: "You have X ms of idle time"
// V8 responds: "I'll do Y incremental marking steps in that budget"

// This is why GC pauses are WORSE when:
// - Your frame is already overbudget (no idle time)
// - You're running heavy animations
// - Background tabs don't get idle callbacks

Detecting GC Pauses in Production

// Method 1: PerformanceObserver for long tasks (indirect)
const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
        // GC pauses show up as gaps in your task execution
        // A long task with no obvious JS cause = likely GC
        console.warn(`Long task: ${entry.duration}ms`);
    }
});
observer.observe({ type: 'longtask', buffered: true });

// Method 2: Timestamp gaps (rough but works everywhere)
let lastTime = performance.now();
function detectPauses() {
    const now = performance.now();
    const delta = now - lastTime;
    
    // requestAnimationFrame fires every ~16.6ms
    // If delta > 50ms, something paused the main thread
    if (delta > 50) {
        console.warn(`Possible GC pause: ${delta.toFixed(1)}ms gap`);
    }
    lastTime = now;
    requestAnimationFrame(detectPauses);
}
requestAnimationFrame(detectPauses);

// Method 3: Chrome DevTools → Performance panel
// Record a trace → look for "Minor GC" and "Major GC" events
// Yellow = JS, Purple = Layout, Green = Paint, Gray = GC

// Method 4: Node.js --trace-gc flag
// node --trace-gc app.js
// Outputs: Scavenge 3.4 (5.2) -> 2.1 (5.2) MB, 1.2 / 0.0 ms

Allocation Patterns That Cause GC Pressure

// BAD: Allocating in hot loops creates massive GC pressure
function renderFrame(objects) {
    objects.forEach(obj => {
        // Creates a new object EVERY FRAME for EVERY object
        const transformed = {
            x: obj.x * Math.cos(angle) - obj.y * Math.sin(angle),
            y: obj.x * Math.sin(angle) + obj.y * Math.cos(angle),
            color: `rgb(${obj.r}, ${obj.g}, ${obj.b})` // new string too!
        };
        draw(transformed);
    });
}

// GOOD: Pre-allocate and reuse (object pooling)
const transformPool = Array.from({ length: 1000 }, () => ({ x: 0, y: 0, color: '' }));

function renderFrameOptimized(objects) {
    objects.forEach((obj, i) => {
        // REUSE existing object — zero allocations per frame
        const t = transformPool[i];
        t.x = obj.x * Math.cos(angle) - obj.y * Math.sin(angle);
        t.y = obj.x * Math.sin(angle) + obj.y * Math.cos(angle);
        // Avoid template literals in hot paths — they allocate
        draw(t);
    });
}

// GOOD: Use TypedArrays for numeric data (no per-element GC overhead)
const positions = new Float64Array(2000); // 1000 x,y pairs
// One contiguous allocation, GC treats it as a single object

WeakRef and FinalizationRegistry: GC-Aware Code

// WeakRef: Hold a reference that doesn't prevent GC
// Use case: caches that automatically evict when memory is tight

class ImageCache {
    #cache = new Map(); // key → WeakRef<ImageBitmap>
    #registry;

    constructor() {
        // FinalizationRegistry: get notified AFTER an object is GC'd
        // WARNING: timing is non-deterministic — may never fire
        this.#registry = new FinalizationRegistry((key) => {
            // Clean up the WeakRef entry from our map
            // This runs on a microtask AFTER GC collects the image
            this.#cache.delete(key);
            console.log(`Cache entry evicted by GC: ${key}`);
        });
    }

    set(key, imageBitmap) {
        const ref = new WeakRef(imageBitmap);
        this.#cache.set(key, ref);
        // Register so we're notified when the image is collected
        this.#registry.register(imageBitmap, key);
    }

    get(key) {
        const ref = this.#cache.get(key);
        if (!ref) return undefined;
        
        const value = ref.deref(); // Returns undefined if GC'd
        if (!value) {
            this.#cache.delete(key); // Eagerly clean up stale entry
        }
        return value;
    }
}

// CRITICAL: Never rely on finalization for correctness!
// It's for optimization only — GC timing is non-deterministic

Where This Lives in Production

  • V8 (Chrome, Node.js, Deno) — Orinoco GC: concurrent marking + parallel scavenging. Reduced average GC pause from ~10ms to ~1ms since Chrome 64.
  • Three.js / PixiJS — Game loops use object pooling extensively to avoid per-frame allocations that trigger young-gen GC during animation.
  • React Fiber scheduler — Yields to the main thread between fiber units specifically so GC can run during idle periods without causing visible jank.
  • Google Maps — Uses TypedArrays for tile coordinate data and object pools for map markers to keep GC pauses under 4ms during pan/zoom.

Common Mistakes

  • Allocating closures in animation loops — Each () => {} is a new object. Move callbacks outside loops or use named functions.
  • String concatenation in hot paths — Template literals and + create new string objects. Pre-build strings or use arrays.
  • Thinking delete frees memory immediately — It doesn't. It only removes the property; GC decides when to reclaim.
  • Over-relying on FinalizationRegistry — It's advisory, not guaranteed. Design code to work without it.
  • Ignoring promoted objects — Objects that survive to old gen stay there until major GC (expensive). Avoid long-lived objects with short-lived references.

✅ You Truly Understand GC Timing When...

You can look at a Chrome Performance trace, identify GC events (Minor GC vs Major GC), explain why they fired at that specific moment (allocation trigger vs idle schedule), and predict which code changes would reduce their frequency and duration.
