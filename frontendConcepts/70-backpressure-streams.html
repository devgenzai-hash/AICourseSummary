Backpressure in Streams API

When a producer generates data faster than a consumer can process it, backpressure is the mechanism that slows the producer down — preventing memory exhaustion, dropped data, and out-of-memory crashes in streaming pipelines.

Advanced Async Patterns Performance
📚 Analogy: A Factory Assembly Line

Imagine a factory where Station A stamps metal parts at 100/minute, but Station B can only paint them at 30/minute. Without backpressure, unpainted parts pile up between stations until they overflow onto the floor (memory exhaustion). With backpressure, Station B signals "I'm full!" and Station A slows down or pauses until B catches up. The conveyor belt between them has a fixed buffer capacity — this is the highWaterMark in the Streams API.

The Problem: Unbounded Buffering Kills Memory

// Without backpressure: producer doesn't know consumer is slow

// Scenario: Reading a 2GB file and writing to IndexedDB
// File reader produces chunks at ~500MB/s
// IndexedDB writes at ~50MB/s (10x slower)

// NAIVE approach (no backpressure):
const response = await fetch('/large-file.bin');
const reader = response.body.getReader();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  // Problem: read() returns chunks ASAP — doesn't wait for processing
  // If processChunk is slow, chunks queue up in memory
  processChunk(value); // What if this takes 100ms per chunk?
}

// Result: 500MB of chunks buffered in memory waiting to be processed
// On mobile: tab crashes with OOM (out of memory)

// WITH backpressure (await in the loop):
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  await processChunk(value); // AWAIT! Next read() only after processing
  // This creates backpressure: reader pauses until consumer is ready
}
// Memory: constant ~64KB (one chunk at a time) regardless of file size

How the Streams API Implements Backpressure

// The Web Streams API has BUILT-IN backpressure via internal queues
// Key concept: desiredSize tells the producer when to pause

// ReadableStream internal queue:
// - Has a highWaterMark (max bytes to buffer before signaling "full")
// - desiredSize = highWaterMark - queueSize
// - When desiredSize <= 0: STOP producing (backpressure active)
// - When desiredSize > 0: keep producing (consumer is keeping up)

const readable = new ReadableStream({
  // Called by the stream when it needs more data
  pull(controller) {
    // controller.desiredSize tells us how much room is in the buffer
    // If desiredSize <= 0, the consumer hasn't read enough yet
    // The stream WON'T call pull() again until desiredSize > 0

    const chunk = generateData();
    controller.enqueue(chunk);

    // After enqueue, desiredSize decreases by chunk.byteLength
    // When it hits 0 or below, pull() won't be called — BACKPRESSURE!
    console.log(`desiredSize: ${controller.desiredSize}`);
  },

  start(controller) {
    // Initial setup — called once when stream is created
  },

  cancel(reason) {
    // Consumer cancelled the stream — clean up resources
  }
}, {
  // Queuing strategy: controls buffer size and backpressure threshold
  highWaterMark: 3,  // Buffer up to 3 chunks before applying backpressure
  size(chunk) { return 1; } // Each chunk counts as 1 unit
});

// WritableStream also has internal queue with backpressure:
const writable = new WritableStream({
  async write(chunk, controller) {
    // If this is slow, the writable's queue fills up
    // When full, writer.ready Promise won't resolve until there's room
    await slowDatabaseWrite(chunk);
  }
}, {
  highWaterMark: 5 // Allow 5 chunks to queue before blocking the producer
});

Pipe Chains: Automatic Backpressure Propagation

// pipeTo() and pipeThrough() automatically propagate backpressure
// through the entire pipeline — this is the killer feature

// Pipeline: Network → Decompress → Parse → Write to DB
const response = await fetch('/data.json.gz');

await response.body
  // Step 1: Decompress (TransformStream)
  .pipeThrough(new DecompressionStream('gzip'))
  // Step 2: Decode bytes to text (TransformStream)
  .pipeThrough(new TextDecoderStream())
  // Step 3: Parse JSON lines (custom TransformStream)
  .pipeThrough(jsonLineParser())
  // Step 4: Write to database (WritableStream)
  .pipeTo(databaseWriter());

// Backpressure flows BACKWARDS through the chain:
// DB writer is slow → parser queue fills → decoder queue fills
// → decompressor queue fills → network fetch PAUSES reading
// The browser literally stops pulling bytes off the network socket!

// Custom TransformStream with backpressure awareness
function jsonLineParser() {
  let buffer = '';

  return new TransformStream({
    transform(chunk, controller) {
      buffer += chunk;
      const lines = buffer.split('\n');
      buffer = lines.pop(); // Keep incomplete last line in buffer

      for (const line of lines) {
        if (line.trim()) {
          // enqueue() respects backpressure automatically
          // If downstream is full, this TransformStream's
          // readable side applies backpressure to its writable side
          controller.enqueue(JSON.parse(line));
        }
      }
    },
    flush(controller) {
      // Called when input stream ends — emit final buffered data
      if (buffer.trim()) {
        controller.enqueue(JSON.parse(buffer));
      }
    }
  });
}

Manual Backpressure with writer.ready

// When you need fine-grained control over backpressure
// (not using pipe, writing manually to a stream)

async function writeWithBackpressure(writable, chunks) {
  const writer = writable.getWriter();

  for (const chunk of chunks) {
    // writer.ready resolves when there's room in the queue
    // If the queue is full (backpressure active), this AWAITS
    await writer.ready;

    // Now we know there's room — safe to write
    writer.write(chunk);
    // Note: don't await write() — that waits for the chunk to be
    // fully processed, which defeats pipelining.
    // await writer.ready is the correct backpressure signal.
  }

  await writer.close();
}

// Real example: uploading a large file with progress
async function uploadFile(file, url) {
  const CHUNK_SIZE = 64 * 1024; // 64KB chunks
  let offset = 0;

  const readable = new ReadableStream({
    async pull(controller) {
      if (offset >= file.size) {
        controller.close();
        return;
      }

      const slice = file.slice(offset, offset + CHUNK_SIZE);
      const chunk = await slice.arrayBuffer();
      controller.enqueue(new Uint8Array(chunk));
      offset += CHUNK_SIZE;

      // Update progress — pull() is only called when downstream wants data
      // So progress updates naturally reflect actual upload speed
      updateProgress(offset / file.size);
    }
  });

  // fetch() with a ReadableStream body — backpressure from network!
  await fetch(url, {
    method: 'POST',
    body: readable,
    duplex: 'half' // Required for streaming upload
  });
}

Real-World Usage

  • Node.js Streams — The original backpressure implementation. pipe() handles backpressure automatically. stream.write() returns false when the buffer is full — you must wait for the 'drain' event.
  • fetch() Response Body — response.body is a ReadableStream. If you read slowly, the browser pauses the TCP receive window, telling the server to slow down (network-level backpressure).
  • Service Workers — Streaming responses use TransformStreams. Backpressure ensures the service worker doesn't buffer an entire response in memory before forwarding to the page.
  • Video Transcoding (FFmpeg.wasm) — Processing frames through WASM is slower than decoding. Backpressure prevents decoded frames from flooding memory while WASM processes them.
  • Kafka (concept) — Consumer groups that can't keep up cause topic partition lag. The lag metric IS backpressure visibility. Kafka doesn't drop messages — it applies backpressure to producers via flow control.

Trade-offs & Alternatives

StrategyStrengthsWeaknesses
Backpressure (pause producer) No data loss; bounded memory; automatic flow control Producer is idle while consumer catches up; increased latency
Dropping (discard excess) Constant memory; producer never blocked; simple Data loss; not suitable for all use cases (fine for video frames)
Buffering (unbounded queue) No data loss; producer never blocked Memory grows without bound; OOM crash; delayed processing
Sampling (take every Nth item) Bounded memory; predictable load; good for metrics Lossy; misses bursts; not suitable for ordered data

Common Mistakes

  • Not awaiting in read loops — while (true) { const chunk = await reader.read(); process(chunk); } has backpressure. But while (true) { const chunk = await reader.read(); promises.push(processAsync(chunk)); } does NOT — you're reading faster than processing.
  • Confusing writer.write() with writer.ready — await writer.write(chunk) waits for the chunk to be consumed. await writer.ready waits for room in the buffer. For backpressure, use ready; for completion, use write().
  • Setting highWaterMark too high — A highWaterMark of 100MB means the stream buffers 100MB before applying backpressure. For most cases, the default (1 chunk or ~64KB for byte streams) is correct.
  • Not implementing cancel() — If the consumer aborts (user navigates away), the readable's cancel() is called. If you don't implement it, resources (file handles, network connections) leak.
  • Blocking the transform — A TransformStream that does CPU-heavy work in transform() blocks the main thread. Use a Web Worker or chunk the work to avoid frame drops.

✅ You Truly Understand Backpressure When...

You can trace how backpressure propagates backwards through a pipe chain: from a slow WritableStream through multiple TransformStreams all the way back to the original ReadableStream source — and you know exactly which desiredSize values and Promise resolutions control each stage's pause/resume behavior.
