IndexedDB

The browser's built-in NoSQL database — transactional, indexed, capable of storing gigabytes, and the foundation of offline-first web apps. Also: why its API is infamously painful and how to tame it.

Intermediate Storage Browser API
🗄️ Daily-Life Analogy: A Filing Cabinet with Indexes

localStorage is a single drawer where everything is a string. IndexedDB is a full filing cabinet system: multiple drawers (object stores), organized with index tabs (indexes), supporting atomic operations (transactions) where either all changes commit or none do. You can store entire objects, blobs, and files — not just strings.

Code: IndexedDB from Scratch

// Opening a database — the upgrade mechanism handles schema migrations
function openDB() {
    return new Promise((resolve, reject) => {
        // Version 2 → if user has version 1, onupgradeneeded fires
        const request = indexedDB.open('myApp', 2);
        
        // onupgradeneeded: ONLY place you can create/modify object stores and indexes
        request.onupgradeneeded = (event) => {
            const db = event.target.result;
            const oldVersion = event.oldVersion;
            
            // Migration pattern: handle each version bump
            if (oldVersion < 1) {
                // Version 0 → 1: Create initial stores
                const store = db.createObjectStore('articles', { keyPath: 'id' });
                store.createIndex('by_date', 'publishedAt');
                store.createIndex('by_author', 'authorId');
            }
            if (oldVersion < 2) {
                // Version 1 → 2: Add new store for drafts
                db.createObjectStore('drafts', { keyPath: 'id', autoIncrement: true });
            }
        };
        
        request.onsuccess = () => resolve(request.result);
        request.onerror = () => reject(request.error);
    });
}

// CRUD operations — all transactional
async function crudExamples() {
    const db = await openDB();
    
    // CREATE: Add an article
    const tx = db.transaction('articles', 'readwrite');
    tx.objectStore('articles').put({
        id: 'article-1',
        title: 'Understanding IndexedDB',
        authorId: 'user-42',
        publishedAt: new Date(),
        body: '...', // Can store large strings, blobs, anything
    });
    await tx.complete; // Transaction committed atomically
    
    // READ: Get by primary key
    const readTx = db.transaction('articles', 'readonly');
    const article = await wrapRequest(
        readTx.objectStore('articles').get('article-1')
    );
    
    // QUERY: Get all articles by author using index
    const authorArticles = await wrapRequest(
        readTx.objectStore('articles')
            .index('by_author')
            .getAll('user-42') // Uses the index for fast lookup
    );
    
    // RANGE QUERY: Articles from last 7 days
    const weekAgo = new Date(Date.now() - 7 * 24 * 60 * 60 * 1000);
    const range = IDBKeyRange.lowerBound(weekAgo);
    const recentArticles = await wrapRequest(
        readTx.objectStore('articles')
            .index('by_date')
            .getAll(range)
    );
}

// Helper: wrap IDBRequest in a Promise
function wrapRequest(request) {
    return new Promise((resolve, reject) => {
        request.onsuccess = () => resolve(request.result);
        request.onerror = () => reject(request.error);
    });
}

Why the Raw API Is Painful (and What to Use Instead)

💡 Use a Wrapper Library

The raw IndexedDB API uses callbacks, not Promises. Transaction lifecycle is confusing. In production, use: idb (Jake Archibald, 1KB) for a thin Promise wrapper, or Dexie.js for a richer query API. These don't add abstraction cost — they just make the API ergonomic.

Where This Is Used in Production

  • Gmail Offline — Stores emails, attachments, and drafts in IndexedDB for full offline functionality.
  • Notion — Local cache of workspace data in IndexedDB enables instant page loads and offline editing.
  • Figma — Stores file data locally for fast re-opens without network round trips.
  • Firebase Firestore (offline persistence) — The local cache of Firestore documents lives in IndexedDB.

Common Mistakes

  • Using localStorage for structured data — JSON.parse(localStorage.getItem(...)) is synchronous, blocks main thread, and is limited to 5MB. Use IndexedDB.
  • Forgetting transaction auto-close — Transactions auto-close when there are no pending requests. If you await something non-IDB (like fetch) mid-transaction, the transaction closes and subsequent operations fail.
  • Not handling version conflicts — If the user has your app open in two tabs and you deploy a new version, the onblocked event fires. Handle it gracefully.
  • Storing sensitive data without encryption — IndexedDB is readable by any script on the origin. Encrypt sensitive data before storage.

✅ You Truly Understand IndexedDB When...

You can explain why a transaction auto-closes if you insert an await fetch() between two put() operations (hint: the event loop iteration completes the transaction), and how to restructure the code to keep the transaction alive.
