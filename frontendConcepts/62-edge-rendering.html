Frontend Concepts / Edge Rendering

Edge Rendering

Executing server-side rendering logic at CDN edge locations (300+ PoPs worldwide) instead of a single origin server — combining the speed of CDN-served static files with the dynamism of server rendering.

Advanced Infrastructure Performance
🏪 Analogy: Local Branch vs Headquarters

Traditional SSR is like every customer calling corporate headquarters (origin server in us-east-1) for every order. Edge rendering is like opening local franchise locations in every city. Each location can handle requests immediately using local inventory (edge cache + compute), only calling HQ for things they can't resolve locally.

The Problem: Origin Server Latency

A user in Tokyo requesting an SSR page from a server in Virginia:

  • Network round trip: ~150-200ms (speed of light through fiber)
  • TLS handshake: another 1-2 roundtrips (~150-400ms)
  • Server processing: 50-500ms
  • Total TTFB: 350-1100ms — before any content appears

Edge rendering moves the compute to a location <10ms from the user. Tokyo user hits Tokyo edge. São Paulo user hits São Paulo edge.

How Edge Rendering Works

// Edge functions run in lightweight V8 isolates (not full Node.js)
// They start in <5ms (cold start) vs 500ms+ for traditional servers

// Next.js Edge Runtime example:
// app/api/hello/route.ts
export const runtime = 'edge'; // ← Deploys to all edge locations

export async function GET(request) {
    // This executes at the edge PoP closest to the user
    // Available APIs: fetch, crypto, streams, Web APIs
    // NOT available: fs, child_process, native modules
    
    const geo = request.geo; // Edge provides geolocation automatically
    const data = await fetch('https://api.example.com/data', {
        headers: { 'X-Region': geo.region }
    });
    
    return Response.json(await data.json());
}

Edge SSR: Full Page Rendering at the Edge

// Next.js page with edge rendering:
// app/products/[id]/page.tsx
export const runtime = 'edge';

export default async function ProductPage({ params }) {
    // This React Server Component renders AT THE EDGE
    // Data fetch goes to nearest database replica or API
    const product = await fetch(
        `https://api.myshop.com/products/${params.id}`,
        { next: { revalidate: 60 } } // Cache for 60s at edge
    );
    
    return (
        <ProductLayout>
            <ProductImage src={product.image} />
            <ProductDetails product={product} />
            <PriceDisplay 
                price={product.price} 
                currency={detectCurrency(request)} {/* Geo-based */}
            />
        </ProductLayout>
    );
}

// Performance comparison:
// Origin SSR (Virginia):  TTFB 200-800ms for global users
// Edge SSR:               TTFB 20-50ms for all users everywhere
// Static CDN:             TTFB 10-30ms but no dynamic content

⚠️ The Database Problem

Edge compute is fast, but if your database is in one region, every edge location must make a long request to that region. Solutions: (1) Globally distributed databases (CockroachDB, PlanetScale, Turso), (2) Read replicas at edge (DynamoDB Global Tables), (3) Cache aggressively at edge (stale-while-revalidate), (4) Separate read path (edge) from write path (origin).

Patterns: What Works at the Edge

// Pattern 1: Personalization at edge (no origin roundtrip)
export default function middleware(request) {
    const country = request.geo.country;
    const response = NextResponse.next();
    
    // Rewrite to country-specific version (pre-rendered at build time)
    if (country === 'DE') {
        return NextResponse.rewrite(new URL('/de' + request.pathname, request.url));
    }
    
    // A/B testing at edge — no client-side flicker
    const bucket = request.cookies.get('experiment')?.value 
        || (Math.random() < 0.5 ? 'A' : 'B');
    response.cookies.set('experiment', bucket);
    
    return response;
}

// Pattern 2: Edge caching with stale-while-revalidate
export async function GET(request) {
    const data = await fetch('https://api.example.com/feed', {
        next: { 
            revalidate: 10,  // Stale after 10s, revalidate in background
            tags: ['feed']   // On-demand revalidation via tag
        }
    });
    return Response.json(await data.json());
}

// Pattern 3: Streaming at edge (start sending immediately)
export async function GET() {
    const encoder = new TextEncoder();
    const stream = new ReadableStream({
        async start(controller) {
            // Send shell immediately
            controller.enqueue(encoder.encode('<html><body>'));
            
            // Stream content as it becomes available
            const data = await fetchSlowAPI();
            controller.enqueue(encoder.encode(`<div>${data}</div>`));
            
            controller.enqueue(encoder.encode('</body></html>'));
            controller.close();
        }
    });
    
    return new Response(stream, {
        headers: { 'Content-Type': 'text/html' }
    });
}

Where This Lives in Production

  • Vercel Edge Functions — Powers Next.js middleware and edge-rendered pages. Uses Cloudflare's network under the hood. <5ms cold start.
  • Cloudflare Workers — Pioneer of edge compute. 300+ locations. Used by Discord (API routing), Shopify (Oxygen), and thousands of production apps.
  • Deno Deploy — Edge runtime using Deno's V8 isolates. Fresh framework renders at the edge by default.
  • AWS CloudFront Functions / Lambda@Edge — CloudFront Functions for lightweight transforms (1ms limit), Lambda@Edge for heavier compute (5s limit).
  • Netlify Edge Functions — Deno-based edge functions integrated with their deploy pipeline.

Common Mistakes

  • Moving all logic to edge without considering data locality — If your DB is in us-east-1, edge compute in Tokyo still takes 200ms for DB queries. Edge shines when data is cached or globally distributed.
  • Using Node.js-specific APIs at edge — Buffer, process.env patterns, require() — use Web standard APIs instead (Uint8Array, env bindings, import).
  • Not handling cold starts for WebSocket-like patterns — Edge functions are stateless. You can't hold connections between requests. Use Durable Objects or external state.
  • Ignoring the 128MB memory limit — Processing large files, rendering complex PDFs, or running ML models won't work. These need origin functions.

✅ You Truly Understand Edge Rendering When...

You can architect a system that uses edge rendering for the HTML shell + cached data, streams dynamic personalized content from edge, and falls back to origin only for mutations — explaining the latency profile at each step.
