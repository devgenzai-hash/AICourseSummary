IntersectionObserver Internals

How the browser efficiently detects element visibility without scroll listeners — the internal scheduling, threshold system, and why it's asynchronous (not real-time).

Intermediate Observer API Browser API
👁️ Daily-Life Analogy: Security Camera Zones

Instead of having a guard constantly scanning the entire warehouse (scroll events checking getBoundingClientRect()), you install smart cameras with motion zones (IntersectionObserver). The cameras only alert you when something enters or exits a defined zone. They don't fire continuously — just at crossing points. Much cheaper than constant monitoring.

The Problem: Scroll-Based Visibility Detection Is Expensive

// ❌ THE OLD WAY: Forces layout on every scroll frame
window.addEventListener('scroll', () => {
    elements.forEach(el => {
        // getBoundingClientRect() forces synchronous layout recalculation
        const rect = el.getBoundingClientRect(); // EXPENSIVE per element
        if (rect.top < window.innerHeight && rect.bottom > 0) {
            el.classList.add('visible');
        }
    });
});
// Problems: fires 60x/sec, forces layout per element, blocks scrolling

How IntersectionObserver Works Internally

  1. Registration — You tell the browser "watch these elements against this root"
  2. Browser schedules checks — Checks happen during idle time or between frames, NOT synchronously on scroll
  3. Geometry calculation — Browser uses its internal layout tree (already computed) — no forced reflow
  4. Threshold crossing — Callback fires only when intersection ratio crosses a threshold you defined
  5. Asynchronous delivery — Entries are batched and delivered asynchronously (like requestIdleCallback timing)
⚠️ It's NOT Real-Time

IntersectionObserver callbacks are asynchronous and batched. There can be a delay of 1-2 frames between when an element actually enters the viewport and when your callback fires. For pixel-perfect scroll-linked animations, you need scroll events or the new Scroll Timeline API. IntersectionObserver is for lazy loading, analytics, infinite scroll — not pixel-sync animations.

Code: Full-Featured IntersectionObserver

// Create observer with options
const observer = new IntersectionObserver(
    (entries, observer) => {
        entries.forEach(entry => {
            // entry.isIntersecting — boolean: is it visible?
            // entry.intersectionRatio — 0.0 to 1.0: how much is visible?
            // entry.boundingClientRect — element's rect (no forced layout!)
            // entry.rootBounds — root's rect
            // entry.intersectionRect — the overlapping area
            // entry.time — high-resolution timestamp of the observation
            
            if (entry.isIntersecting) {
                // Element is visible — load it
                loadImage(entry.target);
                observer.unobserve(entry.target); // Stop watching (one-shot)
            }
        });
    },
    {
        // root: null = viewport (default). Can be any scrollable ancestor.
        root: null,
        
        // rootMargin: expand/shrink the detection area
        // "200px" = fire callback 200px BEFORE element enters viewport
        rootMargin: '200px 0px', // top/bottom left/right — preload before visible
        
        // threshold: which intersection ratios trigger the callback
        // [0] = fire when any pixel enters/exits (default)
        // [0, 0.5, 1.0] = fire at 0%, 50%, and 100% visibility
        threshold: [0, 0.25, 0.5, 0.75, 1.0],
    }
);

// Observe elements (very cheap — just registers them)
document.querySelectorAll('img[data-src]').forEach(img => {
    observer.observe(img);
});

Advanced: Infinite Scroll with Sentinel

// Pattern: observe a "sentinel" element at the bottom of the list
const sentinel = document.getElementById('scroll-sentinel');

const infiniteScrollObserver = new IntersectionObserver(
    (entries) => {
        if (entries[0].isIntersecting) {
            // Sentinel is visible → user scrolled near the bottom → load more
            loadNextPage();
        }
    },
    { rootMargin: '400px' } // Start loading 400px before sentinel is visible
);

infiniteScrollObserver.observe(sentinel);
// The sentinel is a zero-height div at the end of your list
// When new items load, the sentinel naturally moves down

Internal Scheduling: When Does the Check Happen?

TriggerWhen Observer ChecksNotes
ScrollAfter compositing, before next paintBatched — not per-scroll-pixel
ResizeAfter layout, before next paintViewport size change triggers re-check
DOM mutationAfter style/layout recalcAdding/removing elements triggers re-check
Element property changeAfter layoutChanging display: none → block triggers

Where This Is Used in Production

  • Every lazy-loading library — loading="lazy" in browsers uses IntersectionObserver internally to determine when to start fetching images.
  • Google Analytics / ad viewability — Tracking whether ads were actually "seen" (50%+ visible for 1+ second) uses threshold-based observation.
  • React/Vue virtual lists — Libraries like react-intersection-observer trigger rendering of items as they approach the viewport.
  • Scroll-driven animations (fallback) — Before Scroll Timeline API, IntersectionObserver with multiple thresholds was the performant way to trigger scroll animations.

Common Mistakes

  • Not unobserving after one-shot use — For lazy loading, call observer.unobserve(entry.target) after loading. Otherwise, the callback keeps firing on every scroll.
  • Using it for scroll-linked animations — The async nature means 1-2 frame lag. Use Scroll Timeline or scroll events for pixel-perfect sync.
  • Creating a new observer per element — One observer can watch many elements. Creating one per element wastes resources.
  • Forgetting the initial callback — IntersectionObserver fires immediately on observe() with the current state. Handle the "already visible" case.

✅ You Truly Understand IntersectionObserver When...

You can explain why it's more performant than scroll events (hint: uses the browser's internal layout data, doesn't force reflow, batches callbacks asynchronously), and why it's NOT suitable for frame-perfect scroll-linked animations.
