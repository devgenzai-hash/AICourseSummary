Frontend Concepts / Code Splitting Strategies

Code Splitting Strategies

How to break a monolithic JavaScript bundle into smaller chunks that load on demand — reducing initial page load time from seconds to milliseconds.

Intermediate Concept Performance
📦 Analogy: Moving Houses

Imagine moving into a new apartment. Without code splitting, the moving truck brings everything you own before you can sit down — furniture, winter clothes, holiday decorations, tools for projects you haven't started. With code splitting, the truck brings only what you need today (bed, desk, essentials) and the rest arrives when you actually need it. Your time-to-livable drops dramatically.

The Problem: The Monolithic Bundle

// Without code splitting, your bundler produces ONE massive file:
// bundle.js → 2.4MB (all routes, all features, all libraries)

// User visits your landing page → downloads 2.4MB before seeing anything
// 90% of that code is for pages/features they haven't visited yet

// On 3G connection: 2.4MB ≈ 8+ seconds of download + parse + execute
// On 4G connection: 2.4MB ≈ 2-3 seconds — still too slow for FCP

// The goal: initial bundle should be < 100KB for fast First Contentful Paint
// Everything else loads later, on demand

How Code Splitting Works Internally

Code splitting creates split points — boundaries where the bundler cuts the dependency graph into separate chunks. Each chunk is a separate HTTP-requestable file that loads independently.

// The bundler builds a dependency graph:
//
//   entry.js
//     ├── Header.js (always needed)
//     ├── Footer.js (always needed)
//     ├── HomePage.js (route: /)
//     │     └── HeroAnimation.js
//     ├── Dashboard.js (route: /dashboard)  ← SPLIT POINT
//     │     ├── Chart.js
//     │     ├── DataTable.js
//     │     └── d3.js (180KB library)
//     └── Settings.js (route: /settings)    ← SPLIT POINT
//           └── FormBuilder.js
//
// Result: 3 chunks instead of 1 monolithic bundle
// chunk-main.js    → entry + Header + Footer + HomePage (50KB)
// chunk-dashboard.js → Dashboard + Chart + DataTable + d3 (200KB)
// chunk-settings.js  → Settings + FormBuilder (15KB)

Strategy 1: Route-Based Splitting

The most common and highest-impact strategy. Each route/page becomes its own chunk. Users only download code for the page they're visiting.

// React with React.lazy() — route-level splitting
import React, { Suspense, lazy } from 'react';
import { BrowserRouter, Routes, Route } from 'react-router-dom';

// Each lazy() call creates a split point
// Webpack/Vite will create a separate chunk for each
const Home = lazy(() => import('./pages/Home'));
const Dashboard = lazy(() => import('./pages/Dashboard'));
const Settings = lazy(() => import('./pages/Settings'));
const AdminPanel = lazy(() => import('./pages/AdminPanel'));

// Suspense provides a fallback while chunks load
function App() {
  return (
    <BrowserRouter>
      <Suspense fallback={<LoadingSpinner />}>
        <Routes>
          <Route path="/" element={<Home />} />
          <Route path="/dashboard" element={<Dashboard />} />
          <Route path="/settings" element={<Settings />} />
          <Route path="/admin" element={<AdminPanel />} />
        </Routes>
      </Suspense>
    </BrowserRouter>
  );
}

// Result: navigating to /dashboard triggers a network request
// for chunk-dashboard.js ONLY when the user actually goes there

Strategy 2: Component-Based Splitting

Split expensive components that aren't immediately visible — modals, dropdowns, heavy widgets, charts below the fold.

// Split a heavy modal that users rarely open
import { lazy, Suspense, useState } from 'react';

// ExportModal contains xlsx library (300KB) — most users never open it
const ExportModal = lazy(() => import('./ExportModal'));

function DataPage() {
  const [showExport, setShowExport] = useState(false);

  return (
    <div>
      <h1>Data</h1>
      <button onClick={() => setShowExport(true)}>Export</button>

      {showExport && (
        <Suspense fallback={<p>Loading export tool...</p>}>
          <ExportModal onClose={() => setShowExport(false)} />
        </Suspense>
      )}
    </div>
  );
}

// The xlsx library and ExportModal code only downloads when user
// clicks "Export" — saving 300KB from initial load for 95% of users

Strategy 3: Vendor Splitting

Separate third-party libraries from your application code. Vendor code changes rarely, so it gets cached long-term while your app code can update without re-downloading all dependencies.

// webpack.config.js — Manual vendor splitting via optimization.splitChunks
module.exports = {
  optimization: {
    splitChunks: {
      cacheGroups: {
        // All node_modules code goes into vendor chunk
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          chunks: 'all',
          // This chunk changes ONLY when dependencies update
          // → cached by browser for weeks/months between deploys
        },
        // Separate chunk for heavy libs that not all pages need
        heavyLibs: {
          test: /[\\/]node_modules[\\/](d3|chart\.js|moment)[\\/]/,
          name: 'heavy-libs',
          chunks: 'all',
          priority: 10, // Higher priority = matched first
          // Only pages using charts download this 200KB chunk
        },
      },
    },
  },
};

// Result:
// vendors.abc123.js  → react, react-dom, router (80KB) — cached long-term
// heavy-libs.def456.js → d3, chart.js (200KB) — only loaded by dashboard
// app.ghi789.js → your code (40KB) — changes with each deploy

Strategy 4: Conditional Feature Splitting

Load code paths only when certain conditions are met — user roles, feature flags, A/B tests, device capabilities.

// Load admin tools only for admin users
async function loadAdminTools(user) {
  if (user.role !== 'admin') return null;

  // This import() only executes for admins
  // Regular users never download admin-tools chunk (150KB)
  const { AdminToolbar } = await import('./admin/AdminToolbar');
  return AdminToolbar;
}

// Load polyfills only for browsers that need them
async function loadPolyfills() {
  const needsPolyfill = !('IntersectionObserver' in window);

  if (needsPolyfill) {
    // Only old browsers download this 30KB polyfill bundle
    await import('./polyfills/intersection-observer');
  }
}

// Feature flag driven splitting
async function loadExperiment(flags) {
  if (flags.newCheckoutFlow) {
    // Only users in the experiment group download new checkout code
    return import('./checkout/NewCheckoutFlow');
  }
  return import('./checkout/ClassicCheckout');
}

Strategy 5: Preloading & Prefetching Split Chunks

Code splitting creates a latency cost when navigating. Prefetching eliminates this by loading chunks before the user needs them — during idle time or based on user intent signals.

// Webpack magic comments for prefetch/preload hints
const Dashboard = lazy(() => import(
  /* webpackPrefetch: true */
  './pages/Dashboard'
));
// Adds <link rel="prefetch" href="chunk-dashboard.js"> to document head
// Browser downloads it during idle time with lowest priority
// When user navigates to /dashboard → chunk is already in cache!

// Intent-based preloading — load on hover/focus (user is about to click)
function NavLink({ to, children }) {
  const preload = () => {
    // Trigger chunk download when user hovers over nav link
    // Average hover-to-click time: 200-400ms — enough to start download
    if (to === '/dashboard') import('./pages/Dashboard');
    if (to === '/settings') import('./pages/Settings');
  };

  return (
    <Link to={to} onMouseEnter={preload} onFocus={preload}>
      {children}
    </Link>
  );
}

// Intersection Observer preloading — load when section comes into viewport
function useVisibilityPreload(importFn) {
  const ref = useRef(null);
  const loaded = useRef(false);

  useEffect(() => {
    const observer = new IntersectionObserver(([entry]) => {
      if (entry.isIntersecting && !loaded.current) {
        loaded.current = true;
        importFn(); // Start loading chunk when element enters viewport
      }
    }, { rootMargin: '200px' }); // 200px ahead of viewport

    if (ref.current) observer.observe(ref.current);
    return () => observer.disconnect();
  }, []);

  return ref;
}

Strategy 6: Granularity Tuning with splitChunks

// Too few chunks: large downloads, poor caching
// Too many chunks: HTTP overhead, waterfall requests
// The sweet spot depends on HTTP/2 multiplexing and bundle sizes

module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',
      // Minimum size before a chunk is created (bytes)
      minSize: 20000, // 20KB — below this, overhead of extra request isn't worth it
      // Maximum size hint — try to split chunks larger than this
      maxSize: 244000, // 244KB — keeps chunks under HTTP/2 initial congestion window
      // Minimum number of chunks that share a module before it's split out
      minChunks: 2, // Module must be used by 2+ chunks to be worth extracting
      // Maximum parallel requests for on-demand loading
      maxAsyncRequests: 6, // Limit waterfall depth on slower connections
    },
  },
};

// Vite equivalent (uses Rollup under the hood)
// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          // Explicit control over chunk composition
          'vendor-react': ['react', 'react-dom', 'react-router-dom'],
          'vendor-charts': ['d3', 'recharts'],
          'vendor-utils': ['lodash-es', 'date-fns'],
        },
      },
    },
  },
};

Where This Is Used in Production

  • Next.js — Automatic route-based code splitting. Every page in pages/ or app/ directory becomes its own chunk. Also splits shared modules used by 2+ pages into a commons chunk.
  • Webpack (used by CRA, Next.js) — optimization.splitChunks with intelligent defaults. Uses the SplitChunksPlugin internally with size-based heuristics.
  • Vite / Rollup — Uses manualChunks for explicit control or automatic splitting based on dynamic imports. Vite pre-bundles dependencies separately from source code.
  • Shopify Storefront — Splits checkout flow from browsing flow. Users browsing products don't download checkout logic (saved ~400KB per session for non-buyers).

Trade-offs & Alternatives

ApproachProsCons
Route-based splitting Highest impact, simple to implement Latency on navigation if not prefetched
Component-based splitting Fine-grained control over what loads when Complexity; too many chunks can hurt perf
Vendor splitting Excellent caching; vendor chunk rarely changes All vendor code loads upfront (even unused libs)
No splitting (monolithic) Simple; no loading states; no waterfall Terrible initial load; wastes bandwidth
Module Federation Share code across separately deployed apps Complex setup; version mismatch risks

Common Mistakes

  • Splitting too aggressively — Creating 50+ tiny chunks (2-5KB each) creates HTTP waterfall overhead. Each chunk has request latency + TCP setup cost, even with HTTP/2.
  • Not providing loading feedback — Users click a link, nothing happens for 500ms while chunk loads. Always use Suspense boundaries or loading indicators at split points.
  • Forgetting shared dependencies — If Route A and Route B both import a shared 100KB library, and you don't extract it into a common chunk, users download it twice (once per route chunk).
  • Cache busting all chunks on deploy — Use content-hash filenames ([name].[contenthash].js) so unchanged chunks keep their cache across deploys.
  • Not analyzing the result — Use webpack-bundle-analyzer or rollup-plugin-visualizer to see actual chunk sizes. Splitting without measuring is guessing.
  • Dynamic imports in tight loops — import() inside render or frequently-called functions can trigger duplicate network requests or race conditions.

✅ You Truly Understand Code Splitting When...

You can look at a webpack-bundle-analyzer treemap and immediately identify: which chunks are too large, which shared modules should be extracted, which routes could benefit from lazy loading, and why some chunks aren't being cached effectively between deploys.

Take a React app with 5+ routes. Implement route-based splitting with React.lazy(). Add prefetching on hover for the top 2 most-visited routes. Use webpack-bundle-analyzer to verify: (1) each route is a separate chunk, (2) shared vendor code is in a commons chunk, (3) the initial bundle is under 100KB gzipped. Measure TTI before and after.
