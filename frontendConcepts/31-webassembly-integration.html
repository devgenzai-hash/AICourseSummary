WebAssembly Integration

Running compiled C/C++/Rust at near-native speed in the browser — how Wasm modules load, communicate with JavaScript, manage memory, and when the overhead isn't worth it.

Advanced Performance WebAssembly
🏎️ Daily-Life Analogy: A Race Car Engine in a Family Car

JavaScript is your family car — comfortable, flexible, good for daily driving. WebAssembly is dropping a Formula 1 engine into specific parts of that car. The engine only understands fuel and mechanical input (numbers and linear memory), so you need an adapter layer (JS glue code) to connect it to the car's dashboard (DOM) and steering (events). The engine is blazing fast for what it does, but the adapter overhead means you don't use it for everything.

The Problem: Why WebAssembly Exists

  • JavaScript is interpreted/JIT-compiled — Even with V8's optimizations, there's a ceiling for CPU-bound operations like codecs, physics, and cryptography
  • Existing C/C++/Rust codebases — Decades of optimized native code (SQLite, FFmpeg, OpenCV) couldn't run in browsers
  • Predictable performance — JS can deoptimize unexpectedly. Wasm has consistent, near-native performance
  • Memory safety at speed — Wasm runs in a sandboxed linear memory with no access to host memory

How Wasm Works in the Browser

// The loading and instantiation pipeline:
// 1. Fetch .wasm binary (much smaller than equivalent JS)
// 2. Compile to machine code (can stream-compile while downloading)
// 3. Instantiate with imports (JS functions Wasm can call)
// 4. Call exported functions from JS

// Streaming compilation — starts compiling before download finishes
const { instance, module } = await WebAssembly.instantiateStreaming(
    fetch('/compute.wasm'),
    {
        // "imports" — JS functions that Wasm can call back into
        env: {
            log: (value) => console.log('Wasm says:', value),
            now: () => performance.now(),
        },
        // Memory can be shared between JS and Wasm
        js: {
            memory: new WebAssembly.Memory({ initial: 256, maximum: 512 })
        }
    }
);

// Call exported Wasm functions — looks like regular JS functions
const result = instance.exports.fibonacci(42); // Runs at near-native speed
const hash = instance.exports.sha256(dataPtr, dataLen);

Memory Model: The Linear Memory

// Wasm has ONE linear memory — a contiguous ArrayBuffer
// JS and Wasm share this memory via typed arrays

const memory = instance.exports.memory; // WebAssembly.Memory
const buffer = new Uint8Array(memory.buffer);

// To pass a string TO Wasm:
function passStringToWasm(str) {
    const encoder = new TextEncoder();
    const bytes = encoder.encode(str);
    
    // Allocate memory inside Wasm's heap (call Wasm's allocator)
    const ptr = instance.exports.malloc(bytes.length + 1);
    
    // Write bytes directly into Wasm's linear memory
    const view = new Uint8Array(memory.buffer);
    view.set(bytes, ptr);
    view[ptr + bytes.length] = 0; // Null-terminate for C strings
    
    return { ptr, len: bytes.length };
}

// To read a string FROM Wasm:
function readStringFromWasm(ptr, len) {
    const view = new Uint8Array(memory.buffer, ptr, len);
    return new TextDecoder().decode(view);
}

When Wasm Is Faster (and When It's Not)

ScenarioWasm vs JSWhy
Tight numerical loops (physics, crypto)Wasm 5-20x fasterNo GC pauses, SIMD, predictable codegen
Image/video processingWasm 3-10x fasterExisting optimized C codecs (FFmpeg)
String manipulationJS often fasterJS strings are native; Wasm must copy through linear memory
DOM manipulationJS always winsWasm can't access DOM — must call back to JS
Small function callsJS fasterJS→Wasm call overhead (~100ns) dominates
Parsing (JSON, XML)Depends on sizeSmall: JS wins. Large (>1MB): Wasm wins
⚠️ The JS↔Wasm Boundary Cost

Every call between JS and Wasm has overhead (~50-200ns). If you call a Wasm function in a loop 1 million times, the boundary crossing cost dominates. Instead, move the loop INTO Wasm: pass the entire array, process it all in Wasm, return the result. Minimize boundary crossings.

Where This Is Used in Production

  • Figma — The rendering engine is C++ compiled to Wasm. Complex vector math and rendering paths run at near-native speed in the browser.
  • Google Meet — Background blur/replacement uses a TensorFlow Lite model compiled to Wasm for real-time video segmentation.
  • Photoshop Web — Core image manipulation (filters, transforms, color science) is C++ compiled to Wasm.
  • SQLite (via sql.js) — The entire SQLite database engine runs in the browser as Wasm, enabling local-first applications.
  • AutoCAD Web — 35+ years of C++ CAD code runs in the browser via Wasm.

Common Mistakes

  • Using Wasm for DOM-heavy work — Every DOM operation requires a JS callback. The boundary crossing negates any speed gain.
  • Forgetting memory.buffer can be invalidated — When Wasm memory grows (memory.grow()), the underlying ArrayBuffer is detached. All TypedArray views become invalid. Re-create views after growth.
  • Not using streaming compilation — WebAssembly.instantiateStreaming() starts compiling while downloading. WebAssembly.instantiate(arrayBuffer) waits for full download first.
  • Over-estimating Wasm's advantage — For typical web app logic (fetch, parse JSON, update UI), JavaScript is fine. Wasm shines for computational kernels, not business logic.

✅ You Truly Understand WebAssembly Integration When...

You can explain how a string gets from JavaScript into Wasm (encode → allocate in linear memory → pass pointer), why calling Wasm in a tight JS loop is slow (boundary cost), and when you'd choose Wasm over optimized JS (sustained CPU-bound computation with minimal JS interop).
