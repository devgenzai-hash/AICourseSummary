Frontend Concepts / Suspense Boundaries

Suspense Boundaries

React's declarative loading state primitive — a component boundary that catches "suspended" children and shows fallback UI until async work completes, enabling streaming SSR and progressive disclosure.

Intermediate React Rendering
🎭 Analogy: Theater Curtains

A <Suspense> boundary is like a theater curtain. While actors (async components) are preparing backstage, the audience sees the curtain (fallback). When all actors within that curtain section are ready, the curtain rises to reveal the scene. You can have multiple curtains in one theater — each section reveals independently as it becomes ready.

The Problem: All-or-Nothing Loading

Without Suspense, pages either:

  • Show nothing until ALL data loads (blocking render)
  • Show content + manual spinners everywhere (if (loading) return <Spinner/>)
  • Flash intermediate states (content → spinner → content)

Suspense provides a declarative way to define loading boundaries — where loading UI appears and what scope of content it covers.

How Suspense Works Internally

// The Suspense contract:
// 1. A child component "suspends" by THROWING a Promise
// 2. React catches it at the nearest Suspense boundary
// 3. Boundary shows fallback while Promise is pending
// 4. When Promise resolves, React re-renders the suspended subtree

// Internal mechanism (simplified):
function renderFiber(fiber) {
    try {
        const result = fiber.type(fiber.props); // Call component function
        return result;
    } catch (thrown) {
        if (thrown instanceof Promise) {
            // Component suspended! Find nearest Suspense ancestor
            const boundary = findSuspenseBoundary(fiber);
            
            // Show fallback content at this boundary
            boundary.showFallback();
            
            // When the Promise resolves, retry rendering this subtree
            thrown.then(() => {
                retryRender(fiber);
            });
        } else {
            throw thrown; // Real error — propagate to Error Boundary
        }
    }
}

Boundary Placement Strategy

// BAD: One giant Suspense wrapping everything
// Entire page shows spinner until ALL data is ready
<Suspense fallback={<PageSpinner />}>
    <Header />       {/* Fast — but blocked by slow siblings */}
    <MainContent />  {/* Slow fetch */}
    <Sidebar />      {/* Medium fetch */}
</Suspense>

// GOOD: Granular boundaries — each section loads independently
<Header />  {/* Shows immediately (no async) */}

<Suspense fallback={<ContentSkeleton />}>
    <MainContent />  {/* Shows when content data arrives */}
</Suspense>

<Suspense fallback={<SidebarSkeleton />}>
    <Sidebar />  {/* Shows independently when sidebar data arrives */}
</Suspense>

// Result: Progressive loading — fastest parts appear first
// Each skeleton is specific to the content it replaces
// No layout shift because skeletons match final layout dimensions

Suspense + Streaming SSR

// On the server, Suspense boundaries define STREAMING chunks
// React sends HTML progressively as each boundary resolves

// Server sends initial HTML immediately:
// <div id="header">...rendered header...</div>
// <div id="content"><!--$?--><template>Loading...</template><!--/$--></div>
// ↑ Suspense fallback as HTML placeholder

// When content data arrives (could be 500ms later):
// Server streams a <script> that replaces the placeholder:
// <script>$RC("content", "<div>...actual content...</div>")</script>
// Browser swaps placeholder with real content — no full page reload

// This means: user sees the page structure INSTANTLY
// Each section fills in as data becomes available
// No JavaScript needed for the initial content swap (pure HTML streaming)

Suspense with Transitions

import { useTransition, Suspense } from 'react';

function TabContainer() {
    const [tab, setTab] = useState('home');
    const [isPending, startTransition] = useTransition();

    function switchTab(newTab) {
        // Without transition: immediately shows Suspense fallback (spinner)
        // With transition: keeps showing current tab (slightly faded)
        //   until new tab data is ready — then swaps atomically
        startTransition(() => {
            setTab(newTab);
        });
    }

    return (
        <>
            <TabBar 
                active={tab} 
                onSelect={switchTab}
                pending={isPending} {/* Show subtle loading indicator */}
            />
            <div style={{ opacity: isPending ? 0.7 : 1 }}>
                <Suspense fallback={<TabSkeleton />}>
                    <TabContent tab={tab} />
                </Suspense>
            </div>
        </>
    );
}

// Behavior:
// 1. User clicks "Settings" tab
// 2. startTransition marks this as non-urgent
// 3. React starts rendering Settings component
// 4. Settings suspends (data not ready) — but because it's a transition:
//    - React does NOT show the fallback spinner
//    - Instead keeps showing the Home tab (with isPending = true)
// 5. When Settings data arrives → atomic swap to new content
// Result: No "flash of loading state" — smooth perceived transition
⚠️ Suspense ≠ Error Handling

Suspense catches Promises (loading states), NOT errors. If a fetch fails, you need an Error Boundary above or alongside the Suspense boundary. The pattern is: <ErrorBoundary><Suspense>...</Suspense></ErrorBoundary> to handle both loading and error states.

Nested Suspense: Fine-Grained Control

// Nested boundaries create a reveal hierarchy
// Each level can show its own loading state

<Suspense fallback={<PageSkeleton />}>
    {/* Outer boundary: catches any unhandled suspensions */}
    <NavigationBar />
    
    <Suspense fallback={<FeedSkeleton />}>
        {/* Inner boundary: just the feed has its own loading state */}
        <Feed />
        
        <Suspense fallback={<CommentsSkeleton />}>
            {/* Deepest: comments can load even later */}
            <Comments />
        </Suspense>
    </Suspense>
    
    <Suspense fallback={<AdsSkeleton />}>
        <Ads /> {/* Ads load independently — don't block main content */}
    </Suspense>
</Suspense>

// Reveal order: NavBar → Feed → Comments (and Ads whenever ready)
// If NavigationBar suspends, the OUTER boundary catches it → full page skeleton

Where This Lives in Production

  • Next.js App Router — Every loading.tsx file creates a Suspense boundary. Streaming SSR uses these boundaries to send HTML chunks progressively.
  • Facebook — The News Feed uses nested Suspense boundaries. Stories, posts, comments, and ads all have independent boundaries enabling fastest-first rendering.
  • Remix — <Await> component wraps deferred loader data, using Suspense internally for streaming.
  • Shopify Hydrogen — Streaming product pages where price/availability (slow API) loads after product images (fast CDN).

Common Mistakes

  • Too few boundaries (one big spinner) — Defeats the purpose. Place boundaries around independently-loadable sections.
  • Too many boundaries (spinner soup) — 20 tiny skeletons popping in feels chaotic. Group related content in one boundary.
  • Skeletons that don't match content layout — Causes layout shift (CLS). Skeletons must reserve the exact same space as real content.
  • Not combining with transitions for navigation — Without startTransition, route changes flash the fallback. Use transitions for in-app navigation.
  • Suspending on every render — If your data fetching doesn't cache, each re-render re-suspends. Use a cache layer (React Query, SWR, Relay).

✅ You Truly Understand Suspense Boundaries When...

You can explain the difference between a Suspense boundary catching a suspension during (a) initial render, (b) a transition, and (c) streaming SSR — and how the behavior differs in each case (fallback vs stale content vs HTML placeholder).
