Frontend Concepts / CORS Preflight

CORS Preflight

Why the browser sends an OPTIONS request before your actual request — the security mechanism that protects servers from unexpected cross-origin mutations, and how to avoid the latency penalty.

Intermediate Security HTTP / CORS
📞 Daily-Life Analogy: Calling Ahead Before Visiting

You want to deliver a heavy package (PUT request with custom headers) to a building on another street (cross-origin). Before driving there, you call ahead: "Hey, do you accept deliveries from my street? Can I bring a 50kg package?" (OPTIONS preflight). The building says "Yes, we accept deliveries from your street, up to 100kg, and you can use the back entrance" (CORS headers). Now you make the actual trip. Without the call, the building would refuse you at the door — wasted trip.

The Problem: Why Preflight Exists

/*
  Before CORS existed, browsers enforced same-origin policy strictly.
  Servers ASSUMED: "If a request reaches me, it's from my own pages."
  
  When CORS was introduced, a dangerous scenario emerged:
  
  1. Evil site at evil.com has JavaScript that sends:
     DELETE https://bank.com/api/account/123
     Authorization: Bearer stolen-token
     
  2. If the browser just sent this directly, the bank's server would
     process it (it was designed before CORS — it trusts all requests).
     
  3. PREFLIGHT prevents this: the browser first asks bank.com:
     "Hey, does evil.com have permission to send DELETE with Auth headers?"
     Bank says NO → browser never sends the actual DELETE.
     
  Preflight protects SERVERS that were built before CORS existed.
  It ensures they explicitly opt-in to cross-origin requests.
*/

When Does a Preflight Happen?

Request TypePreflight?Why
GET with standard headers❌ No (simple request)GET doesn't mutate data, standard headers were always possible via forms
POST with Content-Type: application/x-www-form-urlencoded❌ No (simple)HTML forms could always do this — servers already expect it
POST with Content-Type: application/json✅ YesJSON content type wasn't possible without JS — server might not expect cross-origin JSON
PUT, DELETE, PATCH✅ YesThese methods weren't possible from HTML forms — servers might not expect cross-origin mutations
Any request with custom headers✅ YesCustom headers (Authorization, X-Custom) require explicit server permission

"Simple" (Non-Preflighted) Requests

// These NEVER trigger preflight:
// Methods: GET, HEAD, POST
// Headers: Accept, Accept-Language, Content-Language, Content-Type (only if value is:
//   application/x-www-form-urlencoded, multipart/form-data, or text/plain)

// ✅ No preflight (simple request)
fetch('https://api.other.com/data', { method: 'GET' });

// ✅ No preflight (form-compatible POST)
fetch('https://api.other.com/submit', {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: 'name=hello&value=world'
});

// ❌ TRIGGERS preflight (JSON content type)
fetch('https://api.other.com/data', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' }, // ← not "simple"
    body: JSON.stringify({ name: 'hello' })
});

// ❌ TRIGGERS preflight (custom header)
fetch('https://api.other.com/data', {
    headers: { 'Authorization': 'Bearer token123' } // ← custom header
});

The Preflight Flow

/*
  Step 1: Browser sends OPTIONS (automatically, you can't prevent it):
  
  OPTIONS /api/users HTTP/1.1
  Host: api.other.com
  Origin: https://mysite.com
  Access-Control-Request-Method: PUT
  Access-Control-Request-Headers: Content-Type, Authorization
  
  Step 2: Server responds (if it allows this):
  
  HTTP/1.1 204 No Content
  Access-Control-Allow-Origin: https://mysite.com
  Access-Control-Allow-Methods: GET, POST, PUT, DELETE
  Access-Control-Allow-Headers: Content-Type, Authorization
  Access-Control-Max-Age: 86400        ← Cache this preflight for 24 hours!
  
  Step 3: Browser NOW sends the actual request:
  
  PUT /api/users HTTP/1.1
  Host: api.other.com
  Origin: https://mysite.com
  Content-Type: application/json
  Authorization: Bearer token123
  
  {"name": "Akash"}
*/

Avoiding Preflight Latency

// Strategy 1: Access-Control-Max-Age (cache the preflight)
// Server sends: Access-Control-Max-Age: 86400
// Browser caches the preflight result for 24 hours
// Subsequent requests to same URL skip the OPTIONS call
// Chrome caps at 7200 (2 hours), Firefox at 86400 (24 hours)

// Strategy 2: Same-origin proxy (avoid CORS entirely)
// Instead of: fetch('https://api.other.com/data')
// Use: fetch('/api/proxy/data') → your server forwards to other.com
// No cross-origin = no CORS = no preflight

// Strategy 3: Use simple requests where possible
// If your API can accept form-encoded data for non-sensitive endpoints,
// you avoid preflight on those requests

// Strategy 4: Batch requests
// Instead of 10 separate cross-origin calls (each with preflight),
// combine into 1 GraphQL or batch endpoint (1 preflight total)

Server-Side Configuration

// Express.js CORS configuration
const cors = require('cors');

app.use(cors({
    origin: ['https://mysite.com', 'https://staging.mysite.com'],
    methods: ['GET', 'POST', 'PUT', 'DELETE'],
    allowedHeaders: ['Content-Type', 'Authorization'],
    credentials: true,      // Allow cookies cross-origin
    maxAge: 86400,            // Cache preflight for 24h
}));

// ⚠️ NEVER use in production:
// Access-Control-Allow-Origin: *     (allows ALL origins)
// + credentials: true                 (doesn't work anyway — browser rejects)
// Wildcard + credentials is explicitly forbidden by the spec

Where This Is Used in Production

  • Every cross-origin API call — Any time your frontend at app.example.com calls api.example.com, CORS applies (different subdomain = different origin).
  • GraphQL APIs — Almost always trigger preflight (POST with application/json). GraphQL servers universally handle OPTIONS.
  • CDN-hosted SPAs — SPAs on Vercel/Netlify calling APIs on different domains deal with CORS on every data fetch.

Common Mistakes

  • Thinking CORS is security for the CLIENT — CORS protects SERVERS from unexpected cross-origin requests. The browser enforces it, but it's the server's protection mechanism.
  • Using Access-Control-Allow-Origin: * with credentials — The spec forbids this combination. You must echo the specific origin when using credentials: true.
  • Not setting Access-Control-Max-Age — Without it, every single non-simple request triggers a preflight OPTIONS call. On mobile, that's 100-300ms added latency per request.
  • Forgetting Vary: Origin — If your server sends different CORS headers per origin and a CDN caches the response, the CDN might serve wrong CORS headers. Add Vary: Origin.
  • Debugging on the wrong layer — "CORS error" in the console often means the SERVER isn't sending the right headers, not that your frontend code is wrong.

✅ You Truly Understand CORS Preflight When...

You can explain why POST with Content-Type: text/plain skips preflight (HTML forms could always do this, so servers already handle it) but POST with Content-Type: application/json triggers preflight (only possible via JS, servers might not expect it cross-origin).

🧪 Try This Challenge

Set up two local servers on different ports. Make a cross-origin fetch() with a custom header. Observe the preflight in DevTools Network tab (filter by "Other" to see OPTIONS). Then add Access-Control-Max-Age: 600 and verify the second request skips the preflight.

🔗 Connect It

CORS Preflight connects to: SameSite Cookies (cross-origin cookie sending rules), HTTP/3 (preflight latency reduced by 0-RTT connections), and Preconnect (warming the connection before the preflight reduces total latency).
