Frontend Concepts / WebRTC

WebRTC

Browser-native peer-to-peer communication for video, audio, and arbitrary data — without routing through a server. The protocol stack behind Google Meet, Discord, and every video call you've ever made in a browser.

Advanced Networking Real-time
📚 Analogy: Making a Phone Call Before Cell Phones

Imagine calling someone before direct-dial existed. You'd pick up, tell an operator (the signaling server) who you want to reach. The operator contacts the other person, confirms they're available, and then connects your lines directly — after that, the operator hangs up and you talk peer-to-peer. WebRTC works the same way: a signaling server helps peers FIND each other, but once connected, data flows directly between browsers without touching any server.

The Problem: Server-Relayed Communication is Slow and Expensive

// Traditional approach: ALL data goes through a server
//
// Alice's Browser → Server → Bob's Browser
//        50ms    +   50ms   = 100ms round-trip (minimum)
//
// Problems for real-time communication:
// 1. LATENCY: 100ms+ delay makes video calls feel laggy
// 2. BANDWIDTH COST: server pays for relaying every byte of video
// 3. SCALABILITY: 100 users in a call = server handles 100 video streams
// 4. PRIVACY: server can inspect/store all communication
//
// WebRTC solution: Direct peer-to-peer connection
//
// Alice's Browser ←→ Bob's Browser
//        30ms direct (no server hop)
//
// Server only needed for initial connection setup (signaling)
// After that, data flows directly between peers

The Connection Flow: Signaling → ICE → DTLS → SRTP/SCTP

// WebRTC connection establishment has 4 phases:
//
// Phase 1: SIGNALING (exchange connection metadata via YOUR server)
//   - SDP Offer/Answer (Session Description Protocol)
//   - ICE Candidates (network addresses to try)
//
// Phase 2: ICE (Interactive Connectivity Establishment)
//   - Try direct connection (host candidates)
//   - Try NAT traversal via STUN server (reflexive candidates)
//   - Fall back to relay via TURN server (relay candidates)
//
// Phase 3: DTLS Handshake (encryption setup)
//   - End-to-end encryption between peers
//   - Even the signaling server can't decrypt the data
//
// Phase 4: Media/Data Transfer
//   - SRTP for audio/video (secure real-time protocol)
//   - SCTP over DTLS for data channels (reliable or unreliable)

// ============ COMPLETE WORKING EXAMPLE ============

// === PEER A (the caller) ===
async function createOffer(signalingChannel) {
  // Create the peer connection with STUN/TURN servers for NAT traversal
  const pc = new RTCPeerConnection({
    iceServers: [
      { urls: 'stun:stun.l.google.com:19302' },  // Free Google STUN
      {
        urls: 'turn:your-turn-server.com:3478',  // Your TURN relay (fallback)
        username: 'user',
        credential: 'pass'
      }
    ]
  });

  // Gather ICE candidates as they're discovered
  // These are potential network paths to reach this peer
  pc.onicecandidate = (event) => {
    if (event.candidate) {
      // Send candidate to remote peer via signaling server
      signalingChannel.send({
        type: 'ice-candidate',
        candidate: event.candidate
      });
    }
  };

  // Create a data channel for arbitrary data (chat, game state, files)
  const dataChannel = pc.createDataChannel('messages', {
    ordered: true,      // Guarantee message order (like TCP)
    maxRetransmits: 3   // Retry up to 3 times (semi-reliable)
  });

  dataChannel.onopen = () => console.log('Data channel open!');
  dataChannel.onmessage = (e) => console.log('Received:', e.data);

  // Create SDP offer (describes our media capabilities)
  const offer = await pc.createOffer();
  await pc.setLocalDescription(offer);

  // Send offer to remote peer via signaling server
  signalingChannel.send({ type: 'offer', sdp: offer });

  // Wait for answer from remote peer
  signalingChannel.onMessage(async (msg) => {
    if (msg.type === 'answer') {
      await pc.setRemoteDescription(msg.sdp);
    }
    if (msg.type === 'ice-candidate') {
      await pc.addIceCandidate(msg.candidate);
    }
  });

  return { pc, dataChannel };
}

// === PEER B (the answerer) ===
async function handleOffer(offer, signalingChannel) {
  const pc = new RTCPeerConnection({
    iceServers: [{ urls: 'stun:stun.l.google.com:19302' }]
  });

  pc.onicecandidate = (event) => {
    if (event.candidate) {
      signalingChannel.send({ type: 'ice-candidate', candidate: event.candidate });
    }
  };

  // Listen for data channels created by the remote peer
  pc.ondatachannel = (event) => {
    const channel = event.channel;
    channel.onmessage = (e) => console.log('Got message:', e.data);
    channel.onopen = () => channel.send('Hello from Peer B!');
  };

  // Set the offer and create an answer
  await pc.setRemoteDescription(offer.sdp);
  const answer = await pc.createAnswer();
  await pc.setLocalDescription(answer);

  // Send answer back via signaling
  signalingChannel.send({ type: 'answer', sdp: answer });

  return pc;
}

Adding Media Streams (Video/Audio)

// Get user's camera and microphone
async function startVideoCall(pc) {
  // getUserMedia prompts user permission for camera/mic
  const localStream = await navigator.mediaDevices.getUserMedia({
    video: {
      width: { ideal: 1280 },
      height: { ideal: 720 },
      frameRate: { max: 30 }
    },
    audio: {
      echoCancellation: true,   // Prevent feedback loops
      noiseSuppression: true,   // Filter background noise
      autoGainControl: true    // Normalize volume levels
    }
  });

  // Display local video (mirror for self-view)
  document.getElementById('localVideo').srcObject = localStream;

  // Add each track to the peer connection
  // This triggers renegotiation — new SDP offer with media info
  localStream.getTracks().forEach(track => {
    pc.addTrack(track, localStream);
  });

  // Listen for remote tracks (other peer's video/audio)
  pc.ontrack = (event) => {
    // event.streams[0] contains the remote media stream
    document.getElementById('remoteVideo').srcObject = event.streams[0];
  };

  return localStream;
}

// Screen sharing — replaces video track with screen capture
async function shareScreen(pc, localStream) {
  const screenStream = await navigator.mediaDevices.getDisplayMedia({
    video: { cursor: 'always' }
  });

  // Replace the video track (keep audio from mic)
  const videoSender = pc.getSenders().find(s => s.track?.kind === 'video');
  await videoSender.replaceTrack(screenStream.getVideoTracks()[0]);

  // When user stops sharing, revert to camera
  screenStream.getVideoTracks()[0].onended = () => {
    videoSender.replaceTrack(localStream.getVideoTracks()[0]);
  };
}

NAT Traversal: STUN and TURN

// Most devices are behind NATs (Network Address Translators)
// Your laptop doesn't have a public IP — the router does
// Problem: how does Peer B find Peer A's actual network address?
//
// STUN (Session Traversal Utilities for NAT):
//   - A lightweight server that tells you your PUBLIC IP:port
//   - You send a packet to STUN, it replies with your external address
//   - Free to operate (Google runs public ones)
//   - Works for ~80% of NAT configurations
//
// TURN (Traversal Using Relays around NAT):
//   - A relay server for when direct connection fails
//   - Symmetric NATs block STUN — TURN is the fallback
//   - Expensive: ALL data routes through the TURN server
//   - ~15-20% of connections need TURN (corporate firewalls, strict NATs)
//
// ICE tries candidates in order of preference:
// 1. Host candidate (direct LAN connection — fastest, same network)
// 2. Server-reflexive (STUN-discovered public address — fast, cross-network)
// 3. Relay candidate (TURN server — slow but always works)

// Monitor connection state and quality
pc.onconnectionstatechange = () => {
  console.log('Connection state:', pc.connectionState);
  // States: new → connecting → connected → disconnected → failed → closed
};

// Get real-time stats (bandwidth, latency, packet loss)
async function getConnectionStats(pc) {
  const stats = await pc.getStats();
  stats.forEach(report => {
    if (report.type === 'candidate-pair' && report.state === 'succeeded') {
      console.log(`RTT: ${report.currentRoundTripTime * 1000}ms`);
      console.log(`Bandwidth: ${report.availableOutgoingBitrate / 1000}kbps`);
    }
    if (report.type === 'inbound-rtp' && report.kind === 'video') {
      console.log(`Packets lost: ${report.packetsLost}`);
      console.log(`Frames decoded: ${report.framesDecoded}`);
    }
  });
}

Real-World Usage

  • Google Meet — Uses WebRTC with a Selective Forwarding Unit (SFU). Each participant sends one stream to the server; the server forwards selected streams to each participant (no transcoding, just routing).
  • Discord — Voice channels use WebRTC with a custom SFU. Data channels carry real-time presence (typing indicators, voice activity detection).
  • Cloudflare Calls — A WebRTC platform that handles TURN relay at edge locations globally. Developers get low-latency video without managing TURN infrastructure.
  • PeerJS / simple-peer — Abstraction libraries that simplify WebRTC's complex signaling dance into a few lines of code for P2P data transfer.
  • WebTorrent — Uses WebRTC data channels for browser-to-browser BitTorrent file sharing. No server needed after initial peer discovery.

Trade-offs & Alternatives

ApproachStrengthsWeaknesses
WebRTC (P2P) Low latency; no server bandwidth cost; E2E encrypted; works for media Complex setup; NAT issues; doesn't scale past ~6 peers without SFU
WebSockets Simple; works everywhere; reliable delivery; server can broadcast All data through server; higher latency; server bandwidth cost
Server-Sent Events Simplest; HTTP-based; auto-reconnect; great for notifications Server→client only; no P2P; no binary; higher latency
WebTransport HTTP/3 based; unreliable datagrams; multiplexed streams; modern Newer API; less browser support; requires server (not P2P)

Common Mistakes

  • Forgetting TURN servers — Without TURN, ~15-20% of users can't connect (corporate firewalls, symmetric NATs). Always configure TURN as fallback. Budget for TURN bandwidth costs.
  • Not handling ICE restart — Network changes (WiFi → cellular) invalidate ICE candidates. Listen for iceconnectionstatechange → "disconnected" and trigger ICE restart with pc.restartIce().
  • Assuming P2P scales to many participants — Full mesh (everyone connected to everyone) works for ~4-6 peers. Beyond that, each additional peer doubles bandwidth. Use an SFU (Selective Forwarding Unit) for group calls.
  • Ignoring the "perfect negotiation" pattern — Two peers creating offers simultaneously causes a "glare" collision. Implement the official "perfect negotiation" pattern to handle role assignment (polite vs. impolite peer).
  • Not cleaning up media tracks — Forgetting to call track.stop() leaves camera/mic indicators active. Always stop tracks when the call ends or component unmounts.

✅ You Truly Understand WebRTC When...

You can explain the full connection lifecycle: why signaling needs a separate channel, how ICE discovers candidate paths through NATs, why STUN is free but TURN is expensive, and how SDP describes media capabilities. You know when to use data channels vs. media tracks, and when P2P breaks down requiring an SFU.
