Frontend Concepts / Module Federation

Module Federation

How independently deployed JavaScript applications share code at runtime — enabling true micro-frontend architectures without duplicating dependencies.

Advanced Architecture Webpack 5+
🏗️ Daily-Life Analogy: International Power Adapters

Imagine different countries (teams) each build their own electrical appliances (apps). Without Module Federation, if you want to use a Japanese appliance in the US, you'd need to rebuild the entire appliance. With Module Federation, you define a universal adapter interface — each country exposes its appliances through a standard plug, and any other country can import and use them without rebuilding.

The key insight: each app is independently deployed but can dynamically consume modules from other apps at runtime — no build-time dependency required.

The Problem: Why Module Federation Exists

Large organizations face a fundamental scaling problem:

  • Monolithic frontends become unmanageable — 50+ developers touching one repo means slow CI, merge conflicts, and coupled deployments
  • npm packages require version coordination — updating a shared component means rebuilding every consumer
  • iframes provide isolation but kill performance and UX (no shared state, no shared dependencies, poor accessibility)
  • Traditional micro-frontends (e.g., single-spa) still duplicate React, lodash, etc. across every sub-app

Module Federation solves this by enabling runtime code sharing between independently built and deployed applications. App A can import a component from App B's deployed bundle — no npm publish cycle needed.

How Module Federation Works Internally

Core Concepts

TermDefinitionAnalogy
HostThe app that consumes remote modulesThe app loading the plugin
RemoteThe app that exposes modules for othersThe plugin provider
SharedDependencies used by both (deduplicated)Shared runtime like React
ContainerThe runtime manifest generated per remoteThe adapter/plug interface
ExposeWhat a remote makes availableThe public API surface

Runtime Resolution Flow

  1. Host boots up — Webpack runtime initializes the shared scope (a registry of available shared modules)
  2. Remote entry loaded — Host fetches remoteEntry.js from the remote's CDN (a tiny manifest file)
  3. Shared scope negotiation — Remote checks if the host already has compatible versions of shared deps (e.g., React 18.x). If yes, it reuses them. If not, it loads its own.
  4. Module requested — When host code hits import('app2/Button'), webpack resolves it through the remote's container
  5. Chunk loaded on demand — Only the requested module's chunk is fetched from the remote's server
  6. Module returned — The remote module is returned as a regular ES module — host code uses it normally
⚠️ Version Mismatch Hell

If the host has React 18.2 and the remote was built with React 18.3, the shared scope negotiation determines whether they're "compatible." By default, webpack uses semver ranges. If they're incompatible, the remote loads its own copy of React — resulting in two React instances. This causes hooks to break (different React contexts), doubling bundle size, and subtle state bugs.

Code: Webpack 5 Module Federation Configuration

// webpack.config.js — REMOTE APP (the one exposing modules)
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
    // Each remote needs a unique public path — this is where chunks are fetched from
    output: {
        publicPath: 'https://team-checkout.cdn.example.com/',
        uniqueName: 'checkout_app',  // Prevents global variable collisions between remotes
    },
    plugins: [
        new ModuleFederationPlugin({
            // Name used by hosts to reference this remote
            name: 'checkout',
            
            // The manifest file — hosts fetch this to discover available modules
            filename: 'remoteEntry.js',
            
            // What this app makes available to other apps
            exposes: {
                './CartWidget': './src/components/CartWidget',
                './CheckoutFlow': './src/components/CheckoutFlow',
                './useCart': './src/hooks/useCart',
            },
            
            // Shared dependencies — prevents loading React twice
            shared: {
                react: { 
                    singleton: true,      // Only ONE instance of React in the page
                    requiredVersion: '^18.0.0',
                    eager: false,         // Load async (don't bundle into initial chunk)
                },
                'react-dom': { 
                    singleton: true, 
                    requiredVersion: '^18.0.0' 
                },
            },
        }),
    ],
};

// webpack.config.js — HOST APP (the one consuming remote modules)
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
    plugins: [
        new ModuleFederationPlugin({
            name: 'shell',
            
            // Declare where to find remote containers
            remotes: {
                // Format: "internalName@URL_to_remote_entry"
                // At runtime, webpack fetches this URL to discover the remote's modules
                checkout: 'checkout@https://team-checkout.cdn.example.com/remoteEntry.js',
            },
            
            shared: {
                react: { singleton: true, requiredVersion: '^18.0.0' },
                'react-dom': { singleton: true, requiredVersion: '^18.0.0' },
            },
        }),
    ],
};

// Host app consuming the remote module — looks like a normal dynamic import
import React, { lazy, Suspense } from 'react';

// This triggers: fetch remoteEntry.js → negotiate shared scope → fetch CartWidget chunk
const CartWidget = lazy(() => import('checkout/CartWidget'));

function App() {
    return (
        <div>
            <h1>Main Store</h1>
            {/* Remote module loads on demand — user sees fallback during load */}
            <Suspense fallback={<div>Loading cart...</div>}>
                <CartWidget />
            </Suspense>
        </div>
    );
}

The remoteEntry.js — What's Actually Generated

// Simplified version of what remoteEntry.js contains
// This is the "container" that webpack generates for the remote
var checkout;
(() => {
    // The container exposes two methods:
    var moduleMap = {
        './CartWidget': () => Promise.all([
            __webpack_require__.e("src_components_CartWidget_js")
        ]).then(() => () => __webpack_require__("./src/components/CartWidget.js")),
    };
    
    checkout = {
        // get() — returns a factory for the requested module
        get: (module) => moduleMap[module](),
        
        // init() — receives the shared scope from the host
        // This is where version negotiation happens
        init: (shareScope) => {
            // Register this remote's shared modules into the shared scope
            // If host already has React 18.x, this remote will reuse it
            __webpack_require__.S = shareScope;
        }
    };
})();

Where This Is Used in Production

  • Spotify — Uses Module Federation to compose their desktop app from independent team bundles (player, search, library, social). Each team deploys independently multiple times per day.
  • Walmart — Their e-commerce platform federates checkout, product catalog, and recommendation modules across different team domains, enabling independent deploys for 20+ teams.
  • SAP — Their Fiori platform uses Module Federation to allow enterprise customers to extend the UI with custom federated modules without rebuilding the core application.

single-spaFramework-agnostic routingDuplicates shared deps, complex lifecycle

Common Mistakes

  • Not setting singleton: true for React — Results in two React instances, breaking hooks and context. Always singleton React and React-DOM.
  • Forgetting eager: false — If shared modules are eagerly loaded, the async boundary breaks and the app crashes on boot.
  • Hardcoding remote URLs — In production, remote URLs should be configurable (env vars, runtime config) so you can point to staging/canary versions.
  • No fallback for remote failures — If the remote CDN is down, the host crashes. Always wrap remote imports in error boundaries.
  • Sharing too many or too few deps — Sharing everything bloats the shared scope; sharing nothing defeats the purpose. Share framework deps + design system only.

✅ You Truly Understand Module Federation When...

You can explain what happens at runtime when a host app encounters import('remote/Component') — including the network requests made, the shared scope negotiation, and what happens when versions are incompatible.
