RAG Course / ANN & Reranking

Stage 3: ANN Retrieval + Reranking

Quickly pull top candidates from millions of docs, then deeply compare query vs retrieved chunks for precision.

Intermediate Advanced 10M Scale Code
🏠 Daily-Life Analogy: Hiring Process

Imagine you're hiring one developer from 10 million resumes. You can't read all 10 million carefully.

Stage 1 (ANN): Your HR software quickly scans all 10 million resumes and pulls out the top 100 that roughly match your requirements. It's fast but imperfect — maybe 20 of those 100 aren't great fits.

Stage 2 (Reranker): Now a senior hiring manager carefully reads those 100 resumes, comparing each one deeply against the job description. They reorder the list so the truly best 10 candidates are at the top.

Together: ANN handles speed (100M → 100), reranker handles precision (100 → top 10).

What Is ANN (Approximate Nearest Neighbor)?

The problem: You have 100 million vectors (one per chunk). A user asks a question. You need to find the 20 most similar vectors. Comparing against ALL 100 million would take too long.

ANN solution: Instead of checking every single vector (exact search), use clever data structures that find "approximately" the closest vectors in a fraction of the time. You trade a tiny bit of accuracy for massive speed gains.

In numbers:

  • Exact search (brute force): Compare query against ALL 100M vectors → 100% accurate but takes 5-10 seconds
  • ANN search: Use smart shortcuts → 95-99% accurate but takes 5-50 milliseconds

That 95-99% accuracy is fine because the reranker fixes any mistakes in the next step.

How ANN Works (The Intuition)

📍 Analogy: Finding the Nearest Coffee Shop

Imagine finding the nearest coffee shop in a city of 10 million buildings. You wouldn't check the distance to EVERY building.

Instead, you'd: (1) Know which neighborhood you're in, (2) Only check coffee shops in nearby neighborhoods. That's essentially what ANN does — it organizes vectors into "neighborhoods" so you only search the relevant ones.

Popular ANN Algorithms

Algorithm How It Works (Simple) Speed Accuracy Memory Best For
HNSW Builds a network of "shortcuts" between similar vectors (like highway system) Very Fast ~98% High General purpose, best quality
IVF Groups vectors into clusters, searches only nearest clusters Fast ~95% Medium Large scale, memory-constrained
ScaNN Google's method: quantizes vectors + smart scoring Very Fast ~97% Low Very large scale (Google-level)
FAISS IVF-PQ Clusters + compresses vectors (lossy compression) Fastest ~93% Very Low Billion+ vectors, cost-sensitive

HNSW Deep Dive (Most Popular Choice)

HNSW = Hierarchical Navigable Small World. Think of it like a city with multiple layers:

  • Top layer (highway): A few "landmark" vectors connected across long distances — gets you to the right neighborhood fast
  • Middle layers (main roads): More vectors, shorter connections — narrows down the area
  • Bottom layer (streets): ALL vectors with local connections — finds the exact closest ones

Search starts at the top (fast, rough) and descends to the bottom (slow, precise). Total time: milliseconds.

import faiss
import numpy as np

# Build an HNSW index for 100M vectors of dimension 1024
dimension = 1024
num_vectors = 100_000_000  # 100M chunks

# HNSW parameters
M = 32          # Number of connections per node (higher = better recall, more memory)
ef_construction = 200  # Build-time quality (higher = slower build, better index)
ef_search = 128       # Search-time quality (higher = slower search, better recall)

# Create the index
index = faiss.IndexHNSWFlat(dimension, M)
index.hnsw.efConstruction = ef_construction
index.hnsw.efSearch = ef_search

# Add vectors (in production, do this in batches)
# index.add(all_vectors)  # numpy array of shape (100M, 1024)

# Search
def ann_search(query_vector, top_k=100):
    """Find approximate nearest neighbors in milliseconds."""
    query = np.array([query_vector]).astype('float32')
    distances, indices = index.search(query, top_k)
    return indices[0], distances[0]  # chunk IDs + distances
📊 Memory Math at 10M Docs

10M docs × 10 chunks each = 100M vectors. Each vector is 1024 dimensions × 4 bytes = 4KB.

  • Brute force: 100M × 4KB = ~400GB RAM (impossible for most)
  • HNSW: ~400GB + ~100GB graph overhead = ~500GB (need big machines)
  • IVF-PQ (compressed): ~25-50GB (affordable, slight accuracy loss)
  • Solution: Use IVF-PQ for initial recall, then re-score top candidates with full vectors

What Is Reranking?

Simple explanation: After ANN gives you the top 100 candidates (rough ranking), a reranker carefully reads each candidate alongside the original query and produces a precise relevance score.

Why is it needed?

  • ANN uses simple distance between vectors — fast but shallow understanding
  • A reranker uses a full neural network (cross-encoder) that reads BOTH the query AND the document together — slow but deep understanding
  • Think of ANN as a "glance" and reranking as a "careful read"

Bi-Encoder vs Cross-Encoder

Aspect Bi-Encoder (ANN stage) Cross-Encoder (Reranking stage)
How it works Encodes query and document SEPARATELY, then compares vectors Encodes query and document TOGETHER, understanding their relationship
Analogy Comparing two photos side by side Having two people sit in the same room and talk
Speed Super fast (vectors pre-computed) Slow (must process each pair fresh)
Accuracy Good (~85-90%) Excellent (~95-99%)
Can handle Millions of candidates Only 20-100 candidates (too slow for more)
Used for Initial retrieval (Stage 2-3) Final ranking (after ANN)

Implementing a Reranker

from sentence_transformers import CrossEncoder

# Load a cross-encoder reranking model
reranker = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-12-v2')

def rerank_results(
    query: str,
    candidates: List[Dict],
    top_k: int = 10
) -> List[Dict]:
    """
    Rerank candidate chunks using a cross-encoder.
    
    Takes top ~100 candidates from ANN and produces 
    a precise top-10 ranking.
    """
    # Create query-document pairs for the cross-encoder
    pairs = [(query, chunk["content"]) for chunk in candidates]
    
    # Score all pairs (cross-encoder reads both together)
    scores = reranker.predict(pairs)
    
    # Attach scores and sort
    for chunk, score in zip(candidates, scores):
        chunk["rerank_score"] = float(score)
    
    # Sort by rerank score (highest = most relevant)
    reranked = sorted(candidates, key=lambda x: x["rerank_score"], reverse=True)
    
    return reranked[:top_k]

Using Cohere Rerank (Production API)

import cohere

co = cohere.Client("your-api-key")

def cohere_rerank(query: str, documents: List[str], top_k: int = 10):
    """Use Cohere's production reranking API."""
    response = co.rerank(
        model="rerank-english-v3.0",
        query=query,
        documents=documents,
        top_n=top_k
    )
    
    return [
        {
            "index": result.index,
            "relevance_score": result.relevance_score,
            "document": documents[result.index]
        }
        for result in response.results
    ]

The Complete Two-Stage Pipeline

class TwoStageRetriever:
    """
    Production retrieval: ANN for speed → Reranker for precision.
    
    Stage A: ANN pulls top 100 from 100M chunks (~20ms)
    Stage B: Cross-encoder reranks 100 → top 10 (~200ms)
    Total: ~220ms for precise retrieval from 100M chunks
    """
    
    def __init__(self, ann_index, reranker, embedding_model):
        self.ann_index = ann_index
        self.reranker = reranker
        self.embedding_model = embedding_model
        self.chunk_store = {}  # chunk_id → chunk content + metadata
    
    def retrieve(self, query: str, initial_k: int = 100, final_k: int = 10) -> List[Dict]:
        """Full two-stage retrieval pipeline."""
        
        # Stage A: Fast ANN retrieval (100M → 100)
        query_vector = self.embedding_model.embed(query)
        ann_ids, ann_distances = self.ann_index.search(query_vector, initial_k)
        
        # Load full chunk content for reranking
        candidates = []
        for chunk_id, distance in zip(ann_ids, ann_distances):
            chunk = self.chunk_store.get(chunk_id)
            if chunk:
                chunk["ann_distance"] = float(distance)
                candidates.append(chunk)
        
        # Stage B: Precise reranking (100 → 10)
        reranked = self.reranker.rerank(query, candidates, top_k=final_k)
        
        # Add retrieval metadata for observability (Stage 10)
        for i, result in enumerate(reranked):
            result["final_rank"] = i + 1
            result["retrieval_stages"] = ["ann", "rerank"]
        
        return reranked
✅ Why Two Stages Work Better Than One

ANN alone (100 results): Maybe 60-70% of your top 10 are truly relevant

ANN + Reranker (reranked to 10): 90-95% of your top 10 are truly relevant

The reranker's deep understanding catches the subtle differences that vector distance misses — like understanding that "annual leave policy" is more relevant to "vacation rules" than "annual performance review" even though both contain "annual."

🏢 What Production Systems Actually Do

  • FAISS (Meta) — Most popular open-source ANN library. Supports HNSW, IVF, PQ. Used by most RAG systems.
  • Qdrant — Production vector DB with built-in HNSW, filtering, and payload storage
  • Cohere Rerank — Most popular reranking API. Drop-in improvement for any retrieval system.
  • ColBERT — Late-interaction model that's faster than cross-encoders but nearly as accurate
  • Typical pipeline: Retrieve 100-200 candidates → Rerank to top 5-20 → Feed to LLM

📋 Summary

  • Brute-force search at 100M vectors is too slow — ANN makes it milliseconds
  • HNSW is the most popular ANN algorithm — best balance of speed and accuracy
  • ANN gives rough candidates; reranking gives precise relevance ordering
  • Cross-encoders deeply compare query+document together for superior accuracy
  • Two-stage pipeline: ANN (100M→100, 20ms) + Rerank (100→10, 200ms) = fast AND precise
  • At 10M docs, this two-stage approach is non-negotiable for quality

🧠 Mental Model

100,000,000 chunks (all your documents) ↓ [ANN Search] — ~20ms "Give me roughly the best 100" ↓ 100 candidates ↓ [Cross-Encoder Reranker] — ~200ms "Now carefully read each one vs the query" ↓ Top 10 precise results ↓ → Feed to LLM (Stage 5) Think: FUNNEL Wide at top (fast, rough) → Narrow at bottom (slow, precise)

❌ Beginner Mistakes to Avoid

  • Skipping reranking: "ANN results are good enough" — they're NOT. At 10M docs, ANN noise is significant. Reranking improves precision by 20-40%.
  • Reranking too many: Don't rerank 1000 candidates — cross-encoders are slow. 50-200 is the sweet spot.
  • Wrong ANN parameters: Setting ef_search too low saves time but misses relevant results. Benchmark to find your sweet spot.
  • Ignoring memory limits: HNSW for 100M 1024-dim vectors needs ~500GB RAM. Plan for IVF-PQ or disk-based indices if budget-constrained.
  • Not using metadata pre-filtering: Filter by metadata BEFORE ANN search to reduce the candidate space dramatically.
