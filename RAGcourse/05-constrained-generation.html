RAG Course / Constrained Generation

Stage 5: Constrained Generation

The model is ONLY allowed to answer using retrieved context. Nothing invented. Nothing from its training data. Zero hallucination by design.

Intermediate Concept Code Production
🏠 Daily-Life Analogy: Open-Book Exam

Imagine two types of exams:

Closed-book exam (normal LLM): The student answers from memory. They might remember wrong, mix up facts, or just make something up if they don't know. This is how ChatGPT normally works — it generates from "memory" (training data).

Open-book exam (constrained RAG): The student is given specific pages from the textbook and can ONLY write answers that come directly from those pages. If the answer isn't on the pages they were given, they must write "I don't have enough information to answer this."

Constrained generation = forcing the AI to take an open-book exam. Every answer must come from the retrieved documents, never from "memory."

What Is Constrained Generation?

Constrained generation means designing your prompt and system so that the LLM is strictly limited to:

  • Only use information from the retrieved context provided
  • Never invent facts, figures, dates, or claims not in the context
  • Explicitly refuse to answer if the context doesn't contain the answer
  • Never supplement with information from its training data

This is THE most important defense against hallucination. All previous stages (retrieval, reranking, confidence scoring) exist to get the right context here. This stage ensures the model ONLY uses that context.

🚨 Why This Matters

Without constraints, even with perfect retrieval, LLMs will:

  • Add "helpful" details that aren't in the source (hallucination)
  • Merge information from context with training data (contamination)
  • Fill gaps with plausible-sounding but incorrect information (confabulation)
  • Extrapolate beyond what the source actually says (over-inference)

The Constrained Prompt Template

Basic Template

# The most important prompt in your entire RAG system

SYSTEM_PROMPT = """You are a precise information retrieval assistant.

STRICT RULES (NEVER BREAK THESE):
1. Answer ONLY using the provided context below.
2. If the context does not contain the answer, say: 
   "I don't have sufficient information in the available documents to answer this question."
3. NEVER use your training knowledge to supplement answers.
4. NEVER invent, guess, or assume information not explicitly stated in the context.
5. If the context partially answers the question, provide what you can and explicitly 
   state what information is missing.
6. Always indicate which specific source(s) your answer comes from.
7. If sources conflict, present both views and note the conflict.

CONTEXT (Retrieved Documents):
---
{retrieved_context}
---

CONFIDENCE LEVELS OF SOURCES:
{confidence_annotations}
"""

USER_PROMPT = """Based ONLY on the context above, answer this question:

{user_query}

Remember: If the answer is not in the context, say so. Do not guess."""

Grounding Techniques (How to Enforce Constraints)

Technique 1: Context-Only Prompting

The simplest approach — just tell the model firmly in the prompt. Works surprisingly well with strong models.

Technique 2: Extractive + Abstractive Hybrid

Simple: First extract relevant sentences verbatim, then let the model rephrase them into a natural answer.

def constrained_generate(query: str, context_chunks: List[Dict]) -> Dict:
    """
    Two-step constrained generation:
    1. Extract relevant sentences (grounding)
    2. Synthesize into natural answer (generation)
    """
    
    # Step 1: Extract key sentences that answer the query
    extraction_prompt = f"""Given this query: "{query}"

Extract ONLY the sentences from the context below that directly answer the query.
Do not add any information. Only copy exact sentences.

Context:
{format_context(context_chunks)}

Relevant sentences (copy exactly):"""
    
    extracted = llm.generate(extraction_prompt)
    
    # Step 2: Synthesize extracted sentences into a natural answer
    synthesis_prompt = f"""Using ONLY these extracted facts, write a clear answer to: "{query}"

Extracted facts:
{extracted}

Rules:
- Use ONLY the facts above
- Do not add ANY information not in the extracted facts
- Cite which fact supports each claim
- If facts are insufficient, say so

Answer:"""
    
    answer = llm.generate(synthesis_prompt)
    
    return {
        "answer": answer,
        "extracted_evidence": extracted,
        "sources": [c["chunk_id"] for c in context_chunks]
    }

Technique 3: Structured JSON Output

Force the model to output structured JSON that includes citations. This makes it harder to hallucinate because every claim must have a linked source.

STRUCTURED_PROMPT = """Answer the query using ONLY the provided context.
Return your response as valid JSON matching this schema:

Context:
{context}

Query: {query}
"""

Technique 4: NLI Verification (Post-Generation Check)

NLI (Natural Language Inference) — after the model generates an answer, automatically verify that each claim is supported by the context.

from transformers import pipeline

# NLI model checks if a claim is supported by evidence
nli_model = pipeline("text-classification", model="roberta-large-mnli")

def verify_answer_grounding(
    answer: str, 
    context_chunks: List[Dict]
) -> Dict:
    """
    Post-generation verification: check if each sentence 
    in the answer is actually supported by the context.
    
    NLI = Natural Language Inference
    Checks: does the context ENTAIL (support) this claim?
    """
    context_text = " ".join([c["content"] for c in context_chunks])
    
    # Split answer into individual claims/sentences
    sentences = answer.split(".")
    
    verification_results = []
    for sentence in sentences:
        sentence = sentence.strip()
        if not sentence:
            continue
        
        # Check if context supports (entails) this sentence
        result = nli_model(
            f"{context_text}",  # premise (evidence)
            sentence,            # hypothesis (claim)
        )
        
        # NLI outputs: entailment, neutral, contradiction
        label = result[0]["label"]
        score = result[0]["score"]
        
        verification_results.append({
            "claim": sentence,
            "verdict": label,  # "ENTAILMENT" = supported
            "confidence": score,
            "is_grounded": label == "ENTAILMENT" and score > 0.8
        })
    
    # Overall grounding score
    grounded_count = sum(1 for r in verification_results if r["is_grounded"])
    total_claims = len(verification_results)
    
    return {
        "grounding_score": grounded_count / total_claims if total_claims > 0 else 0,
        "claims": verification_results,
        "ungrounded_claims": [
            r["claim"] for r in verification_results 
            if not r["is_grounded"]
        ],
        "should_regenerate": grounded_count / total_claims < 0.8
    }

Complete Constrained Generation Pipeline

class ConstrainedGenerator:
    """
    Generate answers ONLY from retrieved context.
    Includes verification and fallback.
    """
    
    def __init__(self, llm, nli_verifier):
        self.llm = llm
        self.verifier = nli_verifier
        self.max_retries = 2
    
    def generate(
        self, 
        query: str, 
        context_chunks: List[Dict],
        min_grounding_score: float = 0.8
    ) -> Dict:
        """Generate a constrained, verified answer."""
        
        # Format context with source annotations
        formatted_context = self._format_context(context_chunks)
        
        # Generate answer with strict constraints
        prompt = self._build_prompt(query, formatted_context)
        answer = self.llm.generate(prompt, temperature=0.1)  # Low temp = less creative
        
        # Verify grounding (is the answer actually supported?)
        verification = self.verifier.verify(answer, context_chunks)
        
        if verification["grounding_score"] >= min_grounding_score:
            return {
                "answer": answer,
                "grounding_score": verification["grounding_score"],
                "sources": [c["chunk_id"] for c in context_chunks],
                "status": "grounded"
            }
        else:
            # Answer has ungrounded claims → regenerate or refuse
            return self._handle_ungrounded(
                query, context_chunks, verification
            )
    
    def _handle_ungrounded(self, query, chunks, verification):
        """Handle case where generated answer isn't fully grounded."""
        
        # Try once more with stricter prompt
        stricter_prompt = self._build_strict_prompt(
            query, chunks, verification["ungrounded_claims"]
        )
        retry_answer = self.llm.generate(stricter_prompt, temperature=0.0)
        retry_verification = self.verifier.verify(retry_answer, chunks)
        
        if retry_verification["grounding_score"] >= 0.8:
            return {"answer": retry_answer, "status": "grounded_retry"}
        
        # Still not grounded → trigger fallback (Stage 7)
        return {
            "answer": None,
            "status": "insufficient_evidence",
            "reason": "Could not generate a fully grounded answer",
            "partial_info": verification.get("grounded_claims", [])
        }
📊 At 10M Documents Scale
  • Temperature: Use 0.0-0.2 for constrained generation. Higher temperature = more creativity = more hallucination risk
  • Context window management: With many retrieved chunks, you may hit token limits. Prioritize high-confidence chunks (from Stage 4)
  • Latency consideration: NLI verification adds ~100-300ms. Worth it for high-stakes answers. Optional for casual queries.
  • Model choice: At this stage, even a smaller model with perfect context beats a large model with bad context

🏢 What Production Systems Actually Do

  • GPT-4 + strict system prompt — Most common approach. Works well with good prompt engineering.
  • Claude's constitutional approach — Built-in tendency to refuse when unsure, good for constrained generation
  • Structured output (JSON mode) — Forces citation with every claim, reducing uncited hallucination
  • Post-generation NLI check — Used by enterprises for high-stakes (legal, medical, financial) applications
  • Multi-step generation — Extract → Verify → Synthesize pipeline for maximum grounding

📋 Summary

  • Constrained generation = the model can ONLY answer from retrieved context, never from training data
  • The system prompt is your primary defense — be explicit, firm, and repetitive about constraints
  • Use low temperature (0.0-0.2) to reduce creative generation
  • Verify grounding post-generation using NLI models to catch any leaked hallucination
  • If grounding fails, trigger the fallback (Stage 7) — never serve an ungrounded answer
  • Structured output (JSON with citations) makes hallucination harder by design

🧠 Mental Model

Context (from Stages 1-4): ┌─────────────────────────────┐ │ "Vacation policy: 20 days" │ ← Source A (confidence: 0.95) │ "Remote workers: +5 days" │ ← Source B (confidence: 0.82) └─────────────────────────────┘ Query: "How many vacation days do remote workers get?" CONSTRAINED answer: "Remote workers get 25 days (20 base + 5 remote bonus) [Source A, B]" ✅ Every fact traceable to context UNCONSTRAINED answer: "Remote workers typically get 25-30 days plus national holidays..." ❌ "typically" — not in context ❌ "25-30" — context says exactly 25 ❌ "national holidays" — invented, not in context

Think of it as: A courtroom witness who can only testify about what they personally saw (the documents), not what they think might be true.

❌ Beginner Mistakes to Avoid

  • Weak system prompts: "Try to use the context" is too weak. Use "ONLY use the context. NEVER add information not in the context."
  • High temperature: Using temperature > 0.3 with constrained generation defeats the purpose. Creativity = hallucination risk.
  • No verification step: Trusting the model to follow instructions perfectly. Always verify grounding for high-stakes answers.
  • Not handling "I don't know": If you don't give the model a graceful way to say "insufficient info," it'll make something up instead.
  • Stuffing too much context: More context ≠ better. If irrelevant chunks are included, the model might use them incorrectly.
