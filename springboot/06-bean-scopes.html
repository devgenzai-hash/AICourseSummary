Bean Scopes & Proxy Mechanisms

How Spring manages bean lifecycle boundaries — from singletons to request-scoped proxies, and the CGLIB magic that makes short-lived beans injectable into long-lived ones.

advanced spring internal
🏨 The Hotel Reception Desk Analogy

Think of a singleton bean as the hotel building itself — there's exactly one, and everyone shares it. A prototype bean is like a disposable coffee cup — you get a brand new one each time you ask. A request-scoped bean is like a hotel room key card — it belongs to one guest for the duration of their stay (HTTP request), and the same card number may be reused for the next guest. Now here's the twist: the concierge desk (a singleton) needs to hand you the right key card for YOUR stay. The concierge can't hold one specific card permanently — it needs a magic drawer (the CGLIB proxy) that always produces the correct card for whoever is standing in front of it at that moment. That's exactly what scoped proxies do: they're the magic drawer that resolves to the right instance based on the current context.

1. The Six Bean Scopes

Spring provides six built-in scopes. Only singleton and prototype work in any ApplicationContext; the other four require a web-aware context (like WebApplicationContext).

Scope Instances Lifecycle Managed? Destruction Callback? Use Case
singleton One per IoC container ✅ Full ✅ @PreDestroy called Stateless services, repositories, configs
prototype New instance every getBean() ⚠️ Creation only ❌ Never called Stateful commands, builders, non-thread-safe objects
request One per HTTP request ✅ Full ✅ On request completion Request-specific data, audit context
session One per HTTP session ✅ Full ✅ On session invalidation User preferences, shopping cart
application One per ServletContext ✅ Full ✅ On context shutdown App-wide shared state (rarely used)
websocket One per WebSocket session ✅ Full ✅ On WS session close Per-connection state in WebSocket handlers 
// Declaring scopes
@Component
@Scope("singleton") // Default — you don't actually need this
public class PaymentService { }

@Component
@Scope("prototype")
public class ShoppingCart { }

@Component
@Scope(value = WebApplicationContext.SCOPE_REQUEST, proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestAuditContext { }

@Component
@RequestScope // Shorthand — includes proxyMode = TARGET_CLASS
public class CurrentUserContext { }

@Component
@SessionScope // Shorthand for session scope with proxy
public class UserPreferences { }

2. How Request/Session Scopes Work Internally

Web scopes rely on RequestContextHolder — a ThreadLocal-based registry that stores the current RequestAttributes for the executing thread. The scope implementation uses this to store and retrieve bean instances.

// RequestContextHolder — the backbone of web scopes
public abstract class RequestContextHolder {

    private static final ThreadLocal<RequestAttributes> requestAttributesHolder =
        new NamedInheritableThreadLocal<>("Request attributes");

    public static RequestAttributes currentRequestAttributes() {
        RequestAttributes attributes = requestAttributesHolder.get();
        if (attributes == null) {
            throw new IllegalStateException(
                "No thread-bound request found — are you outside a web request?");
        }
        return attributes;
    }
}

// RequestScope implementation — stores beans as request attributes
public class RequestScope extends AbstractRequestAttributesScope {

    @Override
    protected int getScope() {
        return RequestAttributes.SCOPE_REQUEST;
    }
}

public abstract class AbstractRequestAttributesScope implements Scope {

    @Override
    public Object get(String name, ObjectFactory<?> objectFactory) {
        RequestAttributes attributes = RequestContextHolder.currentRequestAttributes();

        // Try to find existing bean instance in current request
        Object scopedObject = attributes.getAttribute(name, getScope());

        if (scopedObject == null) {
            // First access in this request — create new instance
            scopedObject = objectFactory.getObject();
            attributes.setAttribute(name, scopedObject, getScope());

            // Retrieve again for potential wrapper (session serialization, etc.)
            Object retrieved = attributes.getAttribute(name, getScope());
            if (retrieved != null) {
                scopedObject = retrieved;
            }
        }
        return scopedObject;
    }
}

3. Why proxyMode is Mandatory for Narrow Scopes in Singletons

Consider the problem: a singleton bean is created once at startup. Its dependencies are injected once. If you inject a request-scoped bean directly, the singleton holds a reference to one specific instance — but request-scoped beans change with every HTTP request!

// ❌ BROKEN — Without proxy, singleton gets ONE instance forever
@Component
@Scope("request") // No proxyMode!
public class RequestData {
    private String clientIp;
    // ...
}

@Service // Singleton by default
public class AuditService {
    @Autowired
    private RequestData requestData; // 💥 BeanCreationException!
    // Spring can't inject request-scoped bean during singleton creation
    // because there's no active request at startup time
}

// ✅ CORRECT — With proxy, singleton gets a smart delegate
@Component
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestData {
    private String clientIp;
    // ...
}

@Service
public class AuditService {
    @Autowired
    private RequestData requestData; // ✅ Injects a CGLIB PROXY

    public void audit() {
        // Each call goes through the proxy → resolves current request's instance
        String ip = requestData.getClientIp(); // Proxy delegates to correct instance
    }
}
🔍 What the Proxy Actually Does

When you call requestData.getClientIp(), the proxy intercepts and does: (1) Gets the current thread's RequestAttributes from RequestContextHolder, (2) Looks up the bean by name in those attributes, (3) Creates it via ObjectFactory if it doesn't exist yet for this request, (4) Delegates the getClientIp() call to that real instance.

4. CGLIB Proxy: Runtime Subclass Generation

CGLIB (Code Generation Library) creates a subclass at runtime that overrides every non-final method. Each overridden method goes through an interceptor chain before (optionally) calling the real target.

// What CGLIB generates conceptually (simplified):
public class RequestData$$EnhancerBySpringCGLIB$$a1b2c3 extends RequestData {

    private MethodInterceptor interceptor; // Set by Spring

    @Override
    public String getClientIp() {
        // Instead of calling super.getClientIp(), delegate to interceptor
        return (String) interceptor.intercept(
            this,
            RequestData.class.getMethod("getClientIp"),
            new Object[]{},
            methodProxy
        );
    }
}

// Spring's scoped proxy interceptor logic:
class ScopedProxyMethodInterceptor implements MethodInterceptor {

    private final BeanFactory beanFactory;
    private final String targetBeanName;

    @Override
    public Object intercept(Object obj, Method method, Object[] args,
                            MethodProxy proxy) {
        // Resolve the REAL bean from the correct scope
        Object target = beanFactory.getBean(targetBeanName);
        // Invoke the method on the real instance
        return method.invoke(target, args);
    }
}
⚠️ CGLIB Limitations
  • final classes cannot be proxied — CGLIB cannot extend them. You'll get a BeanCreationException.
  • final methods are not intercepted — they call the proxy's own (empty) state, not the target's.
  • The proxy's constructor runs without calling the real constructor (uses Objenesis) — so field initializers in the proxy are skipped.
  • Self-invocation within the target bypasses the proxy (same AOP pitfall).

6. Singleton Thread Safety

Singletons are shared across all threads. If your singleton has mutable fields, multiple threads can corrupt them simultaneously. Spring does NOT add any synchronization — thread safety is your responsibility.

// ❌ DANGEROUS — mutable singleton state
@Service
public class CounterService {
    private int count = 0; // 💥 Race condition!

    public void increment() {
        count++; // Not atomic — read-modify-write
    }
}

// ✅ SAFE — approaches for thread-safe singletons
@Service
public class CounterService {
    // Option 1: AtomicInteger
    private final AtomicInteger count = new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet(); // Atomic CAS operation
    }
}

@Service
public class UserService {
    // Option 2: Stateless design (PREFERRED)
    private final UserRepository repo; // Immutable reference to another singleton

    public User findUser(Long id) {
        return repo.findById(id); // No mutable state — inherently thread-safe
    }
}

@Service
public class CacheService {
    // Option 3: ConcurrentHashMap for mutable collections
    private final Map<String, Object> cache = new ConcurrentHashMap<>();
}

7. The Prototype-in-Singleton Trap

⚠️ Critical Pitfall: Prototype Injected into Singleton

When you inject a prototype bean into a singleton, the prototype is resolved once at singleton creation time. The singleton then holds that same instance forever — defeating the purpose of prototype scope entirely. Spring does not re-resolve dependencies after initial injection.

// ❌ THE TRAP — prototype is resolved once and cached in singleton
@Component
@Scope("prototype")
public class Command {
    private UUID id = UUID.randomUUID();
    public UUID getId() { return id; }
}

@Service // Singleton!
public class CommandExecutor {
    @Autowired
    private Command command; // 💥 Same UUID every time!

    public void execute() {
        System.out.println(command.getId()); // Always prints the same UUID
    }
}

// Also note: Spring NEVER calls @PreDestroy on prototypes!
@Component
@Scope("prototype")
public class ExpensiveResource {
    @PreDestroy
    public void cleanup() {
        // ❌ This is NEVER called! Spring forgets about prototypes after creation.
        // YOU must manage destruction yourself.
    }
}

8. ObjectFactory/ObjectProvider — Correct Prototype Injection

To get a new prototype instance on each use within a singleton, use ObjectProvider (or its simpler parent ObjectFactory). These are lazy lookup handles — each call to getObject() triggers a fresh getBean() call.

// ✅ SOLUTION 1: ObjectProvider (recommended)
@Service
public class CommandExecutor {

    private final ObjectProvider<Command> commandProvider;

    public CommandExecutor(ObjectProvider<Command> commandProvider) {
        this.commandProvider = commandProvider;
    }

    public void execute() {
        Command cmd = commandProvider.getObject(); // New instance each time!
        System.out.println(cmd.getId()); // Different UUID every call
    }
}

// ✅ SOLUTION 2: ObjectFactory (simpler interface)
@Service
public class CommandExecutor {

    private final ObjectFactory<Command> commandFactory;

    public CommandExecutor(ObjectFactory<Command> commandFactory) {
        this.commandFactory = commandFactory;
    }

    public void execute() {
        Command cmd = commandFactory.getObject(); // Fresh prototype
    }
}

// ✅ SOLUTION 3: Provider (JSR-330) — javax.inject.Provider
@Service
public class CommandExecutor {

    @Autowired
    private Provider<Command> commandProvider;

    public void execute() {
        Command cmd = commandProvider.get(); // Fresh prototype
    }
}

// ✅ SOLUTION 4: @Lookup method injection
@Service
public abstract class CommandExecutor {

    @Lookup
    protected abstract Command createCommand(); // Spring overrides via CGLIB

    public void execute() {
        Command cmd = createCommand(); // Fresh prototype each call
    }
}
🔍 ObjectProvider vs ObjectFactory

ObjectProvider extends ObjectFactory with extra capabilities: getIfAvailable() (returns null instead of exception), getIfUnique() (handles multiple beans), stream() (iterate all matching beans), and orderedStream() (ordered by @Order). Prefer ObjectProvider unless you explicitly want the fail-fast behavior of ObjectFactory.

9. Custom Scope Implementation — Tenant Scope Example

In multi-tenant applications, you often need beans scoped to the current tenant. Spring lets you register custom scopes by implementing the Scope interface.

// Step 1: Implement the Scope interface
public class TenantScope implements Scope {

    private final Map<String, Map<String, Object>> tenantBeans = new ConcurrentHashMap<>();
    private final Map<String, Map<String, Runnable>> destructionCallbacks = new ConcurrentHashMap<>();

    @Override
    public Object get(String name, ObjectFactory<?> objectFactory) {
        String tenantId = TenantContext.getCurrentTenant();
        Map<String, Object> beans = tenantBeans
            .computeIfAbsent(tenantId, k -> new ConcurrentHashMap<>());

        return beans.computeIfAbsent(name, k -> objectFactory.getObject());
    }

    @Override
    public Object remove(String name) {
        String tenantId = TenantContext.getCurrentTenant();
        Map<String, Object> beans = tenantBeans.get(tenantId);
        return beans != null ? beans.remove(name) : null;
    }

    @Override
    public void registerDestructionCallback(String name, Runnable callback) {
        String tenantId = TenantContext.getCurrentTenant();
        destructionCallbacks
            .computeIfAbsent(tenantId, k -> new ConcurrentHashMap<>())
            .put(name, callback);
    }

    @Override
    public Object resolveContextualObject(String key) {
        return TenantContext.getCurrentTenant();
    }

    @Override
    public String getConversationId() {
        return TenantContext.getCurrentTenant();
    }

    // Called when a tenant is removed/offboarded
    public void destroyTenant(String tenantId) {
        Map<String, Runnable> callbacks = destructionCallbacks.remove(tenantId);
        if (callbacks != null) {
            callbacks.values().forEach(Runnable::run);
        }
        tenantBeans.remove(tenantId);
    }
}

// Step 2: Register the custom scope
@Configuration
public class TenantScopeConfig {

    @Bean
    public static CustomScopeConfigurer tenantScopeConfigurer() {
        CustomScopeConfigurer configurer = new CustomScopeConfigurer();
        configurer.addScope("tenant", new TenantScope());
        return configurer;
    }
}

// Step 3: Use it!
@Component
@Scope(value = "tenant", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class TenantDataSource {
    // One instance per tenant — auto-resolved based on TenantContext
    private final DataSource dataSource;

    public TenantDataSource() {
        String tenant = TenantContext.getCurrentTenant();
        this.dataSource = createDataSourceForTenant(tenant);
    }
}

10. @RefreshScope — Dynamic Bean Recreation

@RefreshScope from Spring Cloud is a custom scope that destroys and recreates beans when a /actuator/refresh event occurs. It's used for beans that read @Value properties that may change at runtime (e.g., from Spring Cloud Config Server).

// Bean that reads externalized config — recreated on refresh
@Component
@RefreshScope
public class FeatureFlags {

    @Value("${feature.new-checkout:false}")
    private boolean newCheckoutEnabled;

    @Value("${feature.dark-mode:false}")
    private boolean darkModeEnabled;

    // When config changes and /actuator/refresh is called:
    // 1. This bean is destroyed (@PreDestroy called)
    // 2. On next access, a NEW instance is created
    // 3. @Value is re-resolved from the updated Environment
}

// How RefreshScope works internally (simplified):
public class RefreshScope extends GenericScope {

    // Cache of created beans
    private final Map<String, BeanLifecycleWrapper> cache = new ConcurrentHashMap<>();

    @Override
    public Object get(String name, ObjectFactory<?> objectFactory) {
        // Return cached instance, or create if not present
        BeanLifecycleWrapper wrapper = cache.computeIfAbsent(name,
            k -> new BeanLifecycleWrapper(name, objectFactory));
        return wrapper.getBean();
    }

    // Called on /actuator/refresh
    public boolean refresh(String name) {
        BeanLifecycleWrapper wrapper = cache.remove(name);
        if (wrapper != null) {
            wrapper.destroy(); // Calls @PreDestroy
            return true;
        }
        return false;
    }

    // Refresh ALL beans in this scope
    public void refreshAll() {
        cache.keySet().forEach(this::refresh);
    }
}

// Triggering refresh programmatically:
@Autowired
private RefreshScope refreshScope;

public void onConfigChange() {
    refreshScope.refreshAll(); // Destroys all @RefreshScope beans
    // Next access creates fresh instances with new config values
}
🔍 RefreshScope is also proxy-based

@RefreshScope beans are wrapped in a CGLIB proxy, just like request-scoped beans. The proxy resolves through the RefreshScope.get() method. When the cache is cleared during a refresh, the next method call through the proxy triggers re-creation. This means existing references to the proxy continue to work — they automatically pick up the new instance.

🧠 Deep Understanding Check

Mental Model: Scope as a Map Lookup

Every scope is fundamentally a keyed cache:

  • Singleton: key = bean name, cache = the container itself (one global map)
  • Prototype: no cache — always creates new (conceptually, cache size = 0)
  • Request: key = bean name, cache = request attributes (per-request map)
  • Session: key = bean name, cache = session attributes (per-session map)
  • Custom (tenant): key = bean name, cache = your custom map per context
  • Refresh: key = bean name, cache = a clearable ConcurrentHashMap

The proxy simply does: scope.get(beanName, factoryThatCreatesTheBean) on every method call.

💼 Interview Challenge

"Your team has a singleton service that holds a HashMap as a local cache. Under load, the application throws ConcurrentModificationException intermittently. Explain the root cause and three different solutions, including one that uses bean scopes."

Expert answer framework:

  1. Root cause — HashMap is not thread-safe. Singleton beans are shared across all request threads. Concurrent reads and writes cause structural corruption (infinite loops on resize) or CME during iteration.
  2. Solution 1 (Concurrent collection) — Replace with ConcurrentHashMap. Thread-safe for concurrent access, lock-striping minimizes contention.
  3. Solution 2 (Request scope) — If the cache is request-specific, make it @RequestScope. Each request gets its own map — no sharing, no contention.
  4. Solution 3 (Immutable + Refresh) — Use an immutable map rebuilt periodically. Wrap in @RefreshScope or use AtomicReference<Map> for lock-free reads with periodic full replacement.
