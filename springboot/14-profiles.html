Profile Management

How Spring Boot switches between configurations for different environments — the activation mechanisms, profile-specific beans, and multi-profile strategies used in production.

intermediate spring production
🎭 The Theater Stage Analogy

Profiles are like theater stage configurations. The same theater building (your application code) can host a comedy night, a rock concert, or an opera — each requiring different lighting, sound, and set pieces. When the director says "tonight is jazz night" (activating a profile), the stage crew loads the jazz lighting rig, the jazz sound board, and the jazz backdrop. Beans marked with @Profile("jazz") appear on stage; beans marked @Profile("opera") stay in storage. The "default" profile is what's on stage when no one has specified what show to run.

1. What Profiles Are

A profile is a named logical group of bean definitions and configuration properties that can be selectively activated. Profiles allow the same application to behave differently based on the deployment environment without changing code:

// Profiles are just string labels attached to beans or config
// They answer: "Should this bean/config exist in the current environment?"

// A bean registered to the "dev" profile:
@Profile("dev")
@Bean
public DataSource devDataSource() {
    return new EmbeddedDatabaseBuilder()
        .setType(EmbeddedDatabaseType.H2)
        .build();
}

// A bean registered to the "prod" profile:
@Profile("prod")
@Bean
public DataSource prodDataSource() {
    HikariDataSource ds = new HikariDataSource();
    ds.setJdbcUrl("jdbc:postgresql://prod-host:5432/mydb");
    ds.setMaximumPoolSize(50);
    return ds;
}

2. Activating Profiles

Method Example Priority
Command-line argument --spring.profiles.active=prod,metrics Highest
Environment variable SPRING_PROFILES_ACTIVE=prod,metrics High
System property -Dspring.profiles.active=prod High
application.properties spring.profiles.active=dev Low (easily overridden)
Programmatic (SpringApplication) app.setAdditionalProfiles("metrics") Additive (merges) 
// Programmatic activation — adds profiles without removing active ones
public static void main(String[] args) {
    SpringApplication app = new SpringApplication(MyApp.class);

    // These are ADDITIONAL — they merge with active profiles
    app.setAdditionalProfiles("metrics", "tracing");

    app.run(args);
}

// Programmatic activation with ConfigurableEnvironment
@Component
public class DynamicProfileActivator
        implements ApplicationContextInitializer<ConfigurableApplicationContext> {

    @Override
    public void initialize(ConfigurableApplicationContext ctx) {
        ConfigurableEnvironment env = ctx.getEnvironment();

        // Check external condition and activate profile
        if (System.getenv("KUBERNETES_SERVICE_HOST") != null) {
            env.addActiveProfile("kubernetes");
        }
    }
}

3. The Default Profile

// Beans with @Profile("default") are ONLY active when NO profiles are set
// As soon as ANY profile is activated, "default" beans disappear

@Configuration
public class DataSourceConfig {

    @Bean
    @Profile("default")  // Only when nothing is set
    public DataSource localDataSource() {
        // H2 in-memory for local "just run it" development
        return new EmbeddedDatabaseBuilder()
            .setType(EmbeddedDatabaseType.H2)
            .build();
    }

    @Bean
    @Profile("prod")
    public DataSource productionDataSource() {
        // Real database for production
        return DataSourceBuilder.create()
            .url("jdbc:postgresql://prod:5432/db")
            .build();
    }
}

// You can also change the default profile name:
// spring.profiles.default=local
// Now @Profile("local") activates when nothing is explicitly set
⚠️ Common Mistake

Setting spring.profiles.active=dev DISABLES the "default" profile. If you have beans with @Profile("default") for local development AND set spring.profiles.active in your application.properties, those "default" beans will never load — even locally. Use spring.profiles.default to rename the fallback profile instead.

4. @Profile on @Configuration Classes and @Bean Methods

// ═══ Class-level: entire configuration is conditional ═══
@Configuration
@Profile("dev")
public class DevToolsConfiguration {

    // ALL beans in this class only exist when "dev" is active
    @Bean
    public DataSeeder dataSeeder() { return new DataSeeder(); }

    @Bean
    public MockEmailService emailService() { return new MockEmailService(); }
}

// ═══ Method-level: fine-grained per bean ═══
@Configuration
public class EmailConfiguration {

    @Bean
    @Profile("dev")
    public EmailService mockEmail() {
        return new ConsoleEmailService(); // prints to stdout
    }

    @Bean
    @Profile("prod")
    public EmailService realEmail() {
        return new SmtpEmailService(); // sends real emails
    }
}

// How it works internally: ProfileCondition evaluates the annotation
class ProfileCondition implements Condition {
    @Override
    public boolean matches(ConditionContext context, AnnotatedTypeMetadata metadata) {
        MultiValueMap<String, Object> attrs =
            metadata.getAllAnnotationAttributes(Profile.class.getName());
        String[] profiles = (String[]) attrs.getFirst("value");

        for (String profile : profiles) {
            if (context.getEnvironment().acceptsProfiles(
                    Profiles.of(profile))) {
                return true;
            }
        }
        return false;
    }
}

5. Profile-Specific Property Files

# File naming convention: application-{profile}.yml
# These files are automatically loaded when the profile is active

# application.yml — always loaded (base config)
server:
  port: 8080
spring:
  application:
    name: order-service

# application-dev.yml — loaded when "dev" profile active
server:
  port: 8081
spring:
  datasource:
    url: jdbc:h2:mem:devdb
logging:
  level:
    com.company: DEBUG

# application-prod.yml — loaded when "prod" profile active
server:
  port: 443
spring:
  datasource:
    url: jdbc:postgresql://prod-cluster:5432/orders
    hikari:
      maximum-pool-size: 50
logging:
  level:
    root: WARN
    com.company: INFO
🔍 Key Insight

Profile-specific files don't replace the base application.yml — they merge on top. Properties in application-prod.yml override the same keys in application.yml, but any keys only in the base file still apply. This means your base file holds common defaults, and profile files hold only the overrides.

6. Profile Groups (Boot 2.4+)

# application.yml — defining profile groups
# A single profile activation can trigger multiple sub-profiles

spring:
  profiles:
    group:
      production:
        - proddb
        - prodmq
        - prodmetrics
      staging:
        - stagingdb
        - stagingmq
        - prodmetrics   # reuse production metrics config
      local:
        - localdb
        - devmq
        - devmetrics

# Now activating just "production" also activates proddb, prodmq, prodmetrics
# Command: java -jar app.jar --spring.profiles.active=production
# Active profiles: production, proddb, prodmq, prodmetrics

# Each sub-profile has its own config file:
# application-proddb.yml    → PostgreSQL connection pool settings
# application-prodmq.yml    → RabbitMQ production cluster config
# application-prodmetrics.yml → Prometheus/Grafana endpoints
🔍 Key Insight

Profile groups solve the "profile explosion" problem. Before groups, teams would use --spring.profiles.active=prod,proddb,prodmq,prodmetrics everywhere — fragile and error-prone. With groups, a single --spring.profiles.active=production activates everything consistently. It's like defining "presets" for your environment.

7. Multi-Profile Beans and Negative Profiles

// ═══ Multi-profile: active in ANY of the listed profiles ═══
@Bean
@Profile({"dev", "test"})  // Active in dev OR test (logical OR)
public EmailService mockEmailService() {
    return new MockEmailService();
}

// ═══ Negative profiles: active when profile is NOT set ═══
@Bean
@Profile("!production")  // Active in everything EXCEPT production
public CorsFilter permissiveCors() {
    // Allow all origins in non-prod environments
    return new CorsFilter(CorsConfiguration.applyPermitDefaultValues());
}

// ═══ Combining positive and negative ═══
@Bean
@Profile({"cloud", "!local"})  // "cloud" OR "not local" — careful!
public ServiceDiscovery eurekaDiscovery() {
    return new EurekaServiceDiscovery();
}

// ═══ Complex expressions with Profiles.of() (programmatic) ═══
// For AND logic, you need nested conditions or custom Condition class
boolean matches = environment.acceptsProfiles(
    Profiles.of("prod & cloud")  // AND logic (Boot 2.4+)
);

boolean matches2 = environment.acceptsProfiles(
    Profiles.of("dev | test")  // OR logic
);

8. Why NOT to Use Profiles for Feature Flags

// ❌ WRONG: Using profiles as feature flags
@Profile("dark-mode-enabled")  // Don't do this!
@Bean
public ThemeService darkModeTheme() { ... }

// Problems:
// 1. Requires restart to toggle features
// 2. Profiles are for ENVIRONMENTS, not features
// 3. Combinatorial explosion: dev+dark-mode+beta+new-checkout...
// 4. Can't toggle per-user or gradually roll out

// ✅ CORRECT: Use @ConditionalOnProperty for feature flags
@Bean
@ConditionalOnProperty(
    name = "app.features.dark-mode",
    havingValue = "true",
    matchIfMissing = false
)
public ThemeService darkModeTheme() { ... }

// Even better: use a feature flag library (LaunchDarkly, Unleash, Flagsmith)
// that supports runtime toggling without restart
⚠️ Profiles = Environments, Not Features

Profiles answer "WHERE is this running?" (dev/staging/prod). Feature flags answer "WHAT should be enabled?" These are orthogonal concerns. You might want dark-mode in prod but not staging, beta-checkout in staging but not dev — this requires a matrix that profiles can't cleanly express. Use @ConditionalOnProperty or a dedicated feature flag system.

9. Industry Pattern: Docker + Profile Groups

// ═══════════════════════════════════════════════════════════
// Production deployment with profile groups and Docker
// ═══════════════════════════════════════════════════════════

# application.yml — profile groups definition
spring:
  profiles:
    group:
      production:
        - proddb
        - prodcache
        - prodmq
        - observability
      staging:
        - stagingdb
        - stagingcache
        - stagingmq
        - observability
      local:
        - h2db
        - localcache
        - embedded-mq

# Dockerfile — activating via environment variable
FROM eclipse-temurin:21-jre
COPY target/app.jar /app.jar
ENV SPRING_PROFILES_ACTIVE=production
ENTRYPOINT ["java", "-jar", "/app.jar"]

# docker-compose.yml — override per service
services:
  order-service:
    image: company/order-service:latest
    environment:
      - SPRING_PROFILES_ACTIVE=staging
      - DB_HOST=staging-postgres

# Kubernetes deployment.yaml — ConfigMap for profile
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
        - name: order-service
          env:
            - name: SPRING_PROFILES_ACTIVE
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: active-profiles

🎯 Key Takeaways

  • Profiles are named logical groups that control which beans and config are active in the current environment
  • Activation priority: CLI args > env vars > system properties > application.properties — higher sources override lower ones
  • Default profile is a fallback that activates ONLY when no explicit profiles are set
  • Profile-specific files (application-{profile}.yml) merge on top of the base config, not replace it
  • Profile groups (Boot 2.4+) let one profile activation trigger multiple sub-profiles — reducing deployment complexity
  • Negative profiles (@Profile("!production")) activate beans when a profile is NOT active
  • Don't use profiles for feature flags — use @ConditionalOnProperty or dedicated feature flag systems instead
  • Industry standard: Docker env vars + profile groups + Kubernetes ConfigMaps for clean environment switching

🏋️ Mastery Check

  1. You have spring.profiles.active=dev in application.properties and SPRING_PROFILES_ACTIVE=prod as an env var. Which profile is active? What if you also pass --spring.profiles.active=staging on the CLI?
  2. A bean has @Profile({"dev", "test"}). Does this mean the bean is active when BOTH profiles are set, or when EITHER is set? How would you express AND logic?
  3. Explain why @Profile("default") beans disappear when you set spring.profiles.active=dev. How would you keep a fallback that works alongside active profiles?
  4. Design a profile strategy for an app deployed to: local dev, CI pipeline, staging, and 3 regional production clusters (us-east, eu-west, ap-south).
  5. Your team uses @Profile("integration-test") to mock external services in tests. Why is this problematic? What's a better approach?

💼 Interview Challenge

"Your application needs to connect to different databases in dev, staging, and production, but also needs feature-specific config that's independent of the environment. How do you structure your profiles and properties?"

Expert answer framework:

  1. Separate environment from feature: Use profiles (dev/staging/prod) for environment-specific config and @ConditionalOnProperty for feature toggles.
  2. Profile groups: Group related sub-profiles — production activates proddb, prodcache, prodmq so each concern has its own file.
  3. Feature properties in base config: app.features.new-checkout=true in application.yml, overrideable per environment in application-prod.yml if needed.
  4. Never put secrets in profile files: Use environment variables or Vault for credentials — profile files should only contain non-sensitive config.
