Conditional Annotations Deep Dive

The gatekeepers of bean creation — how Spring evaluates conditions to decide whether a bean should exist in the current environment.

intermediate spring concept
🚦 The Bouncer Analogy

Conditional annotations are like bouncers at different VIP sections of a club. Each bouncer checks different criteria: one checks your outfit (@ConditionalOnClass — do you have the right library?), another checks the guest list (@ConditionalOnBean — is a required bean already registered?), another checks your invitation code (@ConditionalOnProperty — is the right config set?). A bean only gets "in" if ALL its bouncers say yes. And crucially — the class-level bouncer checks first: if you fail at the door, none of the room-level bouncers even look at you.

1. The Complete @Conditional Family

Annotation Condition Checks Typical Use
@ConditionalOnClass Class exists on classpath (checked via ASM, not Class.forName) Gate entire auto-config on library presence
@ConditionalOnMissingClass Class does NOT exist on classpath Provide fallback when library absent
@ConditionalOnBean Bean of type/name already registered Add supplemental beans when primary exists
@ConditionalOnMissingBean Bean of type/name NOT registered Provide default that user can override
@ConditionalOnProperty Property has specific value (or exists/not exists) Feature toggles, environment-specific beans
@ConditionalOnResource Resource (file) exists on classpath Load config only when config file present
@ConditionalOnWebApplication Running in a web context (SERVLET or REACTIVE) Web-only beans (filters, interceptors)
@ConditionalOnNotWebApplication NOT running in a web context CLI or batch-only beans
@ConditionalOnExpression SpEL expression evaluates to true Complex conditional logic
@ConditionalOnJava JVM version matches range Version-specific optimizations
@ConditionalOnCloudPlatform Running on specific cloud (K8s, Cloud Foundry, etc.) Cloud-native integrations
@ConditionalOnSingleCandidate Exactly one bean of type (or one @Primary) Avoid ambiguity errors

2. The Condition Interface & SpringBootCondition

Every conditional annotation is backed by a class implementing the Condition interface:

// The core interface (from Spring Framework)
@FunctionalInterface
public interface Condition {
    boolean matches(
        ConditionContext context,
        AnnotatedTypeMetadata metadata);
}

// Spring Boot's enhanced base class (adds logging & reporting)
public abstract class SpringBootCondition implements Condition {

    @Override
    public final boolean matches(
            ConditionContext context,
            AnnotatedTypeMetadata metadata) {

        String classOrMethodName = getClassOrMethodName(metadata);
        ConditionOutcome outcome = getMatchOutcome(context, metadata);

        // Record in ConditionEvaluationReport (for --debug output)
        recordConditionEvaluation(context, classOrMethodName, outcome);

        return outcome.isMatch();
    }

    // Subclasses implement this
    public abstract ConditionOutcome getMatchOutcome(
        ConditionContext context,
        AnnotatedTypeMetadata metadata);
}

ConditionContext — What's Available During Evaluation

public interface ConditionContext {
    BeanDefinitionRegistry getRegistry();       // Check registered BeanDefinitions
    ConfigurableListableBeanFactory getBeanFactory(); // Full bean factory access
    Environment getEnvironment();             // Properties & profiles
    ResourceLoader getResourceLoader();       // Load classpath resources
    ClassLoader getClassLoader();             // Check class presence
}

3. @ConditionalOnClass — The ASM Trick

The most subtle aspect of @ConditionalOnClass: it checks class presence without loading the class. This avoids ClassNotFoundException at evaluation time.

// How @ConditionalOnClass is declared
@Conditional(OnClassCondition.class)
public @interface ConditionalOnClass {
    // These class references are read as STRINGS from bytecode
    Class<?>[] value() default {};
    String[] name() default {};
}

// Inside OnClassCondition (simplified)
class OnClassCondition extends FilteringSpringBootCondition {

    @Override
    public ConditionOutcome getMatchOutcome(
            ConditionContext context, AnnotatedTypeMetadata metadata) {

        ClassLoader classLoader = context.getClassLoader();
        List<String> onClasses = getCandidates(metadata, ConditionalOnClass.class);

        List<String> missing = filter(onClasses, ClassNameFilter.MISSING, classLoader);

        if (!missing.isEmpty()) {
            return ConditionOutcome.noMatch(
                "@ConditionalOnClass did not find: " + missing);
        }
        return ConditionOutcome.match();
    }
}
⚠️ The ASM Reading Detail

When you write @ConditionalOnClass(DataSource.class), the DataSource.class literal is compiled into bytecode as the string "javax.sql.DataSource". Spring reads this string from annotation metadata using ASM — it NEVER resolves the class reference. This means the annotation can reference classes that don't exist on the classpath without causing a ClassNotFoundException during metadata reading.

4. Condition Evaluation Ordering

Conditions are evaluated in a specific, optimized order to fail fast on the cheapest checks:

// FilteringSpringBootCondition processing order:

// 1. OnClassCondition (CHEAPEST — ASM string check, no reflection)
//    → If class not on classpath, skip immediately

// 2. OnWebApplicationCondition (CHEAP — one check against context type)
//    → If not a web app and condition requires web, skip

// 3. OnBeanCondition (MODERATE — searches BeanDefinitionRegistry)
//    → @ConditionalOnBean, @ConditionalOnMissingBean, @ConditionalOnSingleCandidate

// 4. OnPropertyCondition (MODERATE — Environment lookup)
//    → @ConditionalOnProperty

// 5. OnResourceCondition (MODERATE — classpath resource check)
//    → @ConditionalOnResource

// 6. OnExpressionCondition (EXPENSIVE — SpEL evaluation)
//    → @ConditionalOnExpression
🔍 Key Insight

The pre-filter stage (AutoConfigurationImportFilter) evaluates ONLY class conditions and web application conditions during import selection — before the full auto-config class is even parsed. This eliminates ~60% of candidates without loading their bytecode, making startup significantly faster.

5. @ConditionalOnProperty — Feature Toggles

// Basic usage: bean only created if property matches
@Bean
@ConditionalOnProperty(
    prefix = "myapp.feature",
    name = "cache",
    havingValue = "true",
    matchIfMissing = false  // default: don't match if property absent
)
public CacheManager cacheManager() {
    return new ConcurrentMapCacheManager();
}

// application.properties
myapp.feature.cache=true   // → bean IS created
myapp.feature.cache=false  // → bean NOT created
// (property absent)         // → bean NOT created (matchIfMissing=false)

// Industry pattern: feature toggle system
@Configuration
@ConditionalOnProperty(prefix = "features", name = "new-checkout", havingValue = "true")
public class NewCheckoutConfig {

    @Bean
    public CheckoutService checkoutService() {
        return new NewCheckoutService();
    }
}

@Configuration
@ConditionalOnProperty(prefix = "features", name = "new-checkout", havingValue = "false", matchIfMissing = true)
public class LegacyCheckoutConfig {

    @Bean
    public CheckoutService checkoutService() {
        return new LegacyCheckoutService();
    }
}

6. Creating a Custom @Conditional

// Step 1: Define the annotation
@Target({ ElementType.TYPE, ElementType.METHOD })
@Retention(RetentionPolicy.RUNTIME)
@Conditional(OnLinuxCondition.class)
public @interface ConditionalOnLinux { }

// Step 2: Implement the Condition
public class OnLinuxCondition extends SpringBootCondition {

    @Override
    public ConditionOutcome getMatchOutcome(
            ConditionContext context,
            AnnotatedTypeMetadata metadata) {

        String os = context.getEnvironment()
            .getProperty("os.name", "").toLowerCase();

        if (os.contains("linux")) {
            return ConditionOutcome.match(
                "Running on Linux: " + os);
        }
        return ConditionOutcome.noMatch(
            "Not running on Linux: " + os);
    }
}

// Step 3: Use it
@Bean
@ConditionalOnLinux
public FileWatcher inotifyFileWatcher() {
    return new InotifyFileWatcher(); // Uses Linux inotify API
}
🔍 Key Insight

Extending SpringBootCondition instead of implementing Condition directly gives you automatic logging and registration in the ConditionEvaluationReport. Your custom condition will appear in --debug output and the /actuator/conditions endpoint just like built-in conditions.

7. @ConditionalOnBean / @ConditionalOnMissingBean Gotchas

⚠️ Evaluation Timing is Everything

Bean conditions check the BeanDefinitionRegistry, not instantiated beans. This means they depend on processing order. If your @Configuration class hasn't been processed yet when the condition evaluates, @ConditionalOnBean will say "bean not found" even though it will be registered later. This is why auto-configs use DeferredImportSelector — to run AFTER user configs.

// DANGEROUS: Using @ConditionalOnBean in user code
@Configuration
public class ConfigA {
    @Bean
    @ConditionalOnBean(DataSource.class)
    public JdbcTemplate jdbcTemplate(DataSource ds) {
        return new JdbcTemplate(ds);
    }
}

// If DataSourceAutoConfiguration hasn't run yet → condition FAILS
// This is unpredictable in user code — use @ConditionalOnBean only in auto-configs

// SAFE: Using @ConditionalOnMissingBean in auto-configuration
@AutoConfiguration
public class MyAutoConfig {
    @Bean
    @ConditionalOnMissingBean
    public MyService myService() {
        return new DefaultMyService();
    }
}
// Auto-config runs AFTER user code → safely checks if user defined MyService

🎯 Key Takeaways

  • 12+ built-in conditionals cover class presence, bean existence, property values, resources, web context, JVM version, and cloud platform
  • Condition interface has a single matches() method; SpringBootCondition adds logging and reporting
  • ConditionContext provides access to BeanFactory, Environment, ResourceLoader, ClassLoader — everything needed for evaluation
  • @ConditionalOnClass uses ASM to check class names as strings — never loads the class, avoiding ClassNotFoundException
  • Evaluation order is optimized: class conditions (cheapest) → web conditions → bean conditions → property conditions → expression conditions (most expensive)
  • @ConditionalOnBean/@ConditionalOnMissingBean are order-dependent — safe in auto-configs (deferred), dangerous in user code
  • Custom conditionals extend SpringBootCondition to get automatic report integration

💼 Interview Challenge

"You have a multi-module project where Module A defines a @Bean of type CacheManager, and Module B has @ConditionalOnMissingBean(CacheManager.class) to provide a default. Sometimes Module B's default wins even though Module A's bean exists. Diagnose and fix."

Expert answer framework:

  1. Root cause — @ConditionalOnMissingBean in Module B is evaluating before Module A's configuration is parsed. This happens when Module B is a regular @Configuration (not auto-config) and processing order isn't guaranteed.
  2. Diagnosis — Run with --debug and check the conditions report for Module B's bean. It will show "OnMissingBean: no bean of type CacheManager found" even though Module A defines one.
  3. Fix — Move Module B's conditional bean into an auto-configuration class (so it runs after all user configs via DeferredImportSelector). Or use @DependsOn / @AutoConfigureAfter if it's already an auto-config.
