DispatcherServlet Internals

The Front Controller that routes every HTTP request in Spring MVC — how it initializes, what strategies it delegates to, and the complete dispatch algorithm.

advanced spring internal
🏢 The Airport Control Tower Analogy

DispatcherServlet is like an airport control tower. Every plane (HTTP request) entering the airspace must check in with the tower first — no direct runway access allowed. The tower doesn't fly planes itself; it delegates: it checks the flight registry (HandlerMapping) to find the right gate, assigns a ground crew (HandlerAdapter) to handle the plane, runs security checks (Interceptors), and coordinates the departure (View rendering). If something goes wrong, it routes to emergency services (ExceptionResolver). One tower coordinates everything — that's the Front Controller pattern.

1. DispatcherServlet: A Regular Servlet

DispatcherServlet extends HttpServlet — it's just a standard Jakarta Servlet registered with the Servlet container. The entire Spring MVC framework operates within this single servlet.

// ═══ Inheritance hierarchy ═══
// HttpServlet (Jakarta Servlet API)
//   └── HttpServletBean (Spring: property binding)
//       └── FrameworkServlet (Spring: WebApplicationContext management)
//           └── DispatcherServlet (Spring: request dispatching)

// In Spring Boot, DispatcherServletAutoConfiguration registers it:
@AutoConfiguration(after = ServletWebServerFactoryAutoConfiguration.class)
@ConditionalOnClass(DispatcherServlet.class)
@ConditionalOnWebApplication(type = Type.SERVLET)
public class DispatcherServletAutoConfiguration {

    @Bean(name = "dispatcherServlet")
    public DispatcherServlet dispatcherServlet(
            WebMvcProperties webMvcProperties) {
        DispatcherServlet dispatcherServlet = new DispatcherServlet();
        dispatcherServlet.setDispatchOptionsRequest(
            webMvcProperties.isDispatchOptionsRequest());
        dispatcherServlet.setDispatchTraceRequest(
            webMvcProperties.isDispatchTraceRequest());
        dispatcherServlet.setThrowExceptionIfNoHandlerFound(
            webMvcProperties.isThrowExceptionIfNoHandlerFound());
        return dispatcherServlet;
    }

    // Registered to "/" by default via DispatcherServletRegistrationBean
    @Bean
    public DispatcherServletRegistrationBean dispatcherServletRegistration(
            DispatcherServlet dispatcherServlet,
            WebMvcProperties webMvcProperties) {
        DispatcherServletRegistrationBean registration =
            new DispatcherServletRegistrationBean(
                dispatcherServlet, webMvcProperties.getServlet().getPath());
        registration.setName("dispatcherServlet");
        registration.setLoadOnStartup(-1);
        return registration;
    }
}
🔍 Default URL Mapping

Spring Boot maps DispatcherServlet to "/" by default (spring.mvc.servlet.path=/). This means ALL requests go through it. You can change this (e.g., spring.mvc.servlet.path=/api) to have it handle only a subset of URLs, leaving room for other servlets or static resources served directly by the container.

2. Initialization: The 9 Strategy Beans

When the WebApplicationContext refreshes, DispatcherServlet.onRefresh() initializes 9 infrastructure strategies by looking up beans from the context:

// ═══ DispatcherServlet.onRefresh() — called once at startup ═══
@Override
protected void onRefresh(ApplicationContext context) {
    initStrategies(context);
}

protected void initStrategies(ApplicationContext context) {
    initMultipartResolver(context);       // 1. File upload handling
    initLocaleResolver(context);         // 2. Locale/i18n determination
    initThemeResolver(context);          // 3. Theme resolution (deprecated)
    initHandlerMappings(context);        // 4. URL → Handler mapping
    initHandlerAdapters(context);        // 5. Handler invocation adapters
    initHandlerExceptionResolvers(context); // 6. Exception handling
    initRequestToViewNameTranslator(context); // 7. Default view name
    initViewResolvers(context);          // 8. View resolution
    initFlashMapManager(context);        // 9. Flash attributes for redirects
}

3. The doDispatch() Algorithm

Every request flows through doDispatch() — the heart of Spring MVC. Here's the complete algorithm with the actual internal logic:

// ═══ Simplified view of DispatcherServlet.doDispatch() ═══
protected void doDispatch(HttpServletRequest request,
                           HttpServletResponse response) throws Exception {

    HttpServletRequest processedRequest = request;
    HandlerExecutionChain mappedHandler = null;
    boolean multipartRequestParsed = false;
    ModelAndView mv = null;
    Exception dispatchException = null;

    try {
        // ─── Step 1: Check for multipart (file upload) ───
        processedRequest = checkMultipart(request);
        multipartRequestParsed = (processedRequest != request);

        // ─── Step 2: Find HandlerExecutionChain ───
        // (handler + interceptors for this request)
        mappedHandler = getHandler(processedRequest);
        if (mappedHandler == null) {
            noHandlerFound(processedRequest, response);
            return;
        }

        // ─── Step 3: Find the HandlerAdapter ───
        HandlerAdapter ha = getHandlerAdapter(mappedHandler.getHandler());

        // ─── Step 4: Handle Last-Modified (GET/HEAD only) ───
        String method = request.getMethod();
        boolean isGet = HttpMethod.GET.matches(method);
        if (isGet || HttpMethod.HEAD.matches(method)) {
            long lastModified = ha.getLastModified(request, mappedHandler.getHandler());
            if (new ServletWebRequest(request, response)
                    .checkNotModified(lastModified) && isGet) {
                return;
            }
        }

        // ─── Step 5: Execute pre-handle interceptors ───
        if (!mappedHandler.applyPreHandle(processedRequest, response)) {
            return; // Interceptor vetoed — stop processing
        }

        // ─── Step 6: INVOKE THE HANDLER ───
        mv = ha.handle(processedRequest, response, mappedHandler.getHandler());

        // ─── Step 7: Apply default view name if needed ───
        applyDefaultViewName(processedRequest, mv);

        // ─── Step 8: Execute post-handle interceptors ───
        mappedHandler.applyPostHandle(processedRequest, response, mv);

    } catch (Exception ex) {
        dispatchException = ex;
    }

    // ─── Step 9: Process result (render view or handle exception) ───
    processDispatchResult(processedRequest, response,
        mappedHandler, mv, dispatchException);
}
⚠️ The "No Handler Found" Scenario

When no handler matches a request, behavior depends on throwExceptionIfNoHandlerFound. If false (default in Boot 2.x): sends a 404 response directly, bypassing @ControllerAdvice. If true (default in Boot 3.x): throws NoHandlerFoundException, which CAN be caught by @ControllerAdvice. This was a common source of confusion — "Why doesn't my global exception handler catch 404s?"

4. Key Strategy Deep Dives

MultipartResolver

// ═══ MultipartResolver: file upload handling ═══
// Spring Boot auto-configures StandardServletMultipartResolver
// Configuration properties:
//   spring.servlet.multipart.enabled=true
//   spring.servlet.multipart.max-file-size=1MB
//   spring.servlet.multipart.max-request-size=10MB
//   spring.servlet.multipart.file-size-threshold=0

// The checkMultipart() call in doDispatch wraps the request:
protected HttpServletRequest checkMultipart(HttpServletRequest request) {
    if (this.multipartResolver != null
            && this.multipartResolver.isMultipart(request)) {
        return this.multipartResolver.resolveMultipart(request);
        // Returns a MultipartHttpServletRequest with file access
    }
    return request;
}

5. HandlerExecutionChain: Handler + Interceptors

// ═══ HandlerExecutionChain bundles handler with its interceptors ═══
public class HandlerExecutionChain {
    private final Object handler;  // The controller method (HandlerMethod)
    private final List<HandlerInterceptor> interceptorList;

    boolean applyPreHandle(HttpServletRequest request,
                           HttpServletResponse response) {
        for (int i = 0; i < this.interceptorList.size(); i++) {
            HandlerInterceptor interceptor = this.interceptorList.get(i);
            if (!interceptor.preHandle(request, response, this.handler)) {
                // Interceptor vetoed! Trigger afterCompletion for
                // all interceptors that already passed preHandle
                triggerAfterCompletion(request, response, null);
                return false;
            }
            this.interceptorIndex = i;
        }
        return true;
    }
}

// ═══ getHandler() iterates through all HandlerMappings ═══
protected HandlerExecutionChain getHandler(HttpServletRequest request) {
    if (this.handlerMappings != null) {
        for (HandlerMapping mapping : this.handlerMappings) {
            HandlerExecutionChain handler = mapping.getHandler(request);
            if (handler != null) {
                return handler;  // First match wins!
            }
        }
    }
    return null;  // No handler found → 404
}

6. Exception Handling in doDispatch

// ═══ processDispatchResult handles exceptions ═══
private void processDispatchResult(
        HttpServletRequest request,
        HttpServletResponse response,
        HandlerExecutionChain mappedHandler,
        ModelAndView mv,
        Exception exception) throws Exception {

    if (exception != null) {
        // Try each HandlerExceptionResolver in order
        mv = processHandlerException(request, response,
            mappedHandler.getHandler(), exception);
    }

    if (mv != null && !mv.wasCleared()) {
        render(mv, request, response);  // Render view
    }

    // Always call afterCompletion on interceptors
    if (mappedHandler != null) {
        mappedHandler.triggerAfterCompletion(request, response, exception);
    }
}

// ═══ Exception resolver chain ═══
// 1. ExceptionHandlerExceptionResolver → @ExceptionHandler methods
// 2. ResponseStatusExceptionResolver → @ResponseStatus annotations
// 3. DefaultHandlerExceptionResolver → Spring MVC built-in exceptions
🔍 Order Matters

HandlerMappings and HandlerExceptionResolvers are ordered. DispatcherServlet iterates through them sequentially — the first one that returns a non-null result wins. This is why @Order annotations on your custom HandlerExceptionResolver beans matter. ExceptionHandlerExceptionResolver (which processes @ControllerAdvice) is typically registered with the highest priority.

7. DispatcherServlet vs Traditional Servlet Architecture

Aspect Traditional (Multiple Servlets) DispatcherServlet (Front Controller)
Request routing web.xml maps URLs to individual servlets Single entry point delegates to handlers
Cross-cutting concerns Duplicated across each servlet or via filters only Centralized via interceptors and strategy beans
Configuration Per-servlet init-params Spring beans — injectable, testable, conditional
Handler types Must extend HttpServlet Any object (POJO controllers, functional endpoints)
View technology Each servlet manages its own rendering Pluggable ViewResolvers (Thymeleaf, JSON, etc.)
Testability Requires servlet container MockMvc tests without a server

🎯 Key Takeaways

  • DispatcherServlet is a standard HttpServlet — registered by DispatcherServletAutoConfiguration and mapped to "/" in Spring Boot
  • onRefresh() initializes 9 strategies: MultipartResolver, LocaleResolver, ThemeResolver, HandlerMapping, HandlerAdapter, HandlerExceptionResolver, RequestToViewNameTranslator, ViewResolver, FlashMapManager
  • doDispatch() is the heart: find handler → find adapter → pre-interceptors → invoke → post-interceptors → render/write
  • HandlerExecutionChain bundles the handler with its applicable interceptors
  • First match wins: HandlerMappings are iterated in order; the first returning non-null wins
  • Exception handling is a strategy: exception resolvers are tried in order until one handles the exception
  • Boot 3.x throws on 404: NoHandlerFoundException can now be caught by @ControllerAdvice

💼 Interview Challenge

"Walk me through exactly what happens inside Spring MVC from the moment an HTTP request hits Tomcat until the response is sent back. Be specific about class names."

Expert answer framework:

  1. Tomcat layer: NioEndpoint → Http11Processor → CoyoteAdapter → Container pipeline → FilterChain
  2. DispatcherServlet.doDispatch(): checkMultipart → getHandler (iterates HandlerMappings) → getHandlerAdapter → applyPreHandle → ha.handle() → applyPostHandle → processDispatchResult
  3. Handler invocation detail: HandlerAdapter resolves arguments (@RequestBody via Jackson, @PathVariable from URI template), invokes method via reflection, processes return value (@ResponseBody via HttpMessageConverter)
  4. Error path: Exception caught → processHandlerException iterates HandlerExceptionResolvers → ExceptionHandlerExceptionResolver finds @ExceptionHandler → renders error response
  5. Always: triggerAfterCompletion on interceptors, cleanup multipart if parsed
