AOP Internals (Proxies, Weaving, Pointcuts)

How Spring wraps your beans in proxies to add cross-cutting behavior — the BeanPostProcessor that creates proxies, pointcut matching algorithms, and why self-invocation is AOP's Achilles heel.

advanced spring internal
🎭 The Celebrity Bodyguard Analogy

Imagine a celebrity (your bean) who needs security (logging), a publicist (transaction management), and a nutritionist (validation) — but doesn't want to think about any of that while acting. So the agency hires a body double (proxy) who looks identical to the celebrity from the outside. Anyone wanting to talk to the celebrity actually talks to the body double first. The double checks the security clearance (before advice), lets the celebrity do their thing (method execution), then handles the press release (after advice). The celebrity never knows this is happening — they just act. But here's the catch: when the celebrity talks to themselves in the mirror (self-invocation), the body double isn't in between — that's why this.method() bypasses AOP.

1. What AOP Actually Does — Separating Cross-Cutting Concerns

Aspect-Oriented Programming solves a fundamental problem in software design: cross-cutting concerns — behavior that spans multiple unrelated classes but doesn't fit neatly into an object hierarchy.

// WITHOUT AOP — cross-cutting concerns pollute business logic
public class OrderService {

    public Order placeOrder(OrderRequest request) {
        // 🔒 Security check (cross-cutting)
        if (!securityContext.hasPermission("ORDER_CREATE")) {
            throw new AccessDeniedException(...);
        }

        // 📊 Logging (cross-cutting)
        log.info("Placing order for user={}", request.getUserId());
        long start = System.nanoTime();

        try {
            // 💼 ACTUAL BUSINESS LOGIC (only 3 lines!)
            Order order = validateAndCreate(request);
            inventory.reserve(order.getItems());
            return orderRepo.save(order);

        } catch (Exception e) {
            // 📊 Error logging (cross-cutting)
            log.error("Order failed", e);
            metrics.increment("order.failures");
            throw e;
        } finally {
            // 📊 Metrics (cross-cutting)
            metrics.record("order.duration", System.nanoTime() - start);
        }
    }
}

// WITH AOP — business logic is clean, concerns are separate
@Service
public class OrderService {

    @Secured("ORDER_CREATE")
    @Timed("order.duration")
    @Transactional
    public Order placeOrder(OrderRequest request) {
        // Pure business logic — that's it!
        Order order = validateAndCreate(request);
        inventory.reserve(order.getItems());
        return orderRepo.save(order);
    }
}
💡 The Core Insight

AOP doesn't add new functionality — it separates WHERE concerns are defined from WHERE they're applied. The security, logging, and transaction logic still exists, but it's defined once in an aspect and applied declaratively via pointcuts.

2. Spring AOP is Proxy-Based — Not Bytecode Modification

This is the most critical architectural decision in Spring AOP. Unlike AspectJ (which rewrites your .class files), Spring AOP works by wrapping your beans in proxy objects at runtime. This happens during Phase 9 of the bean lifecycle — postProcessAfterInitialization.

3. AnnotationAwareAspectJAutoProxyCreator — The Proxy Factory

This is the BeanPostProcessor responsible for creating all AOP proxies. It's automatically registered when you use @EnableAspectJAutoProxy (or Spring Boot's auto-configuration).

// Inheritance hierarchy — understanding what each layer adds
BeanPostProcessor
  └── AbstractAutoProxyCreator              // Core proxy creation logic
        └── AbstractAdvisorAutoProxyCreator   // Advisor matching
              └── AspectJAwareAdvisorAutoProxyCreator  // AspectJ ordering
                    └── AnnotationAwareAspectJAutoProxyCreator  // @Aspect parsing

// The critical method — called for EVERY bean in the container
public abstract class AbstractAutoProxyCreator
        implements BeanPostProcessor {

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        if (bean != null) {
            Object cacheKey = getCacheKey(bean.getClass(), beanName);

            // Skip if already processed (circular reference handling)
            if (!this.earlyProxyReferences.contains(cacheKey)) {
                return wrapIfNecessary(bean, beanName, cacheKey);
            }
        }
        return bean;
    }

    protected Object wrapIfNecessary(Object bean, String beanName, Object cacheKey) {
        // STEP 1: Find all advisors that apply to this bean
        Object[] specificInterceptors = getAdvicesAndAdvisorsForBean(
            bean.getClass(), beanName, null);

        if (specificInterceptors != DO_NOT_PROXY) {
            this.advisedBeans.put(cacheKey, Boolean.TRUE);

            // STEP 2: Create the proxy!
            Object proxy = createProxy(
                bean.getClass(), beanName, specificInterceptors, new SingletonTargetSource(bean));

            this.proxyTypes.put(cacheKey, proxy.getClass());
            return proxy;  // ← PROXY replaces original bean in container!
        }

        this.advisedBeans.put(cacheKey, Boolean.FALSE);
        return bean;  // No matching advisors → return bean unchanged
    }
}
🔍 Key Insight

This BeanPostProcessor runs for every single bean in your application context. For each bean, it evaluates all pointcut expressions against all methods. If ANY advisor matches, a proxy is created. This is why overly broad pointcuts can impact startup performance.

4. JDK Dynamic Proxy — Interface-Based Proxying

When your bean implements at least one interface, Spring (by default) uses the JDK's built-in Proxy.newProxyInstance() to create a proxy class that implements the same interfaces.

// How JDK Dynamic Proxy works internally

// Your bean implements an interface:
public interface OrderService {
    Order placeOrder(OrderRequest request);
}

@Service
public class OrderServiceImpl implements OrderService {
    public Order placeOrder(OrderRequest request) { ... }
}

// Spring creates a proxy like this (conceptually):
OrderService proxy = (OrderService) Proxy.newProxyInstance(
    classLoader,
    new Class<?>[] { OrderService.class },  // implements same interface
    new JdkDynamicAopProxy(advised)               // invocation handler
);

// The generated proxy class (decompiled) looks like:
public final class $Proxy42 extends Proxy implements OrderService {

    public Order placeOrder(OrderRequest request) {
        // Delegates EVERYTHING to InvocationHandler
        return (Order) h.invoke(this, m3, new Object[]{ request });
        //                       ↑ the InvocationHandler
    }
}

// Spring's InvocationHandler — where advice gets executed
final class JdkDynamicAopProxy implements InvocationHandler {

    private final AdvisedSupport advised;  // holds target + advisors

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) {
        // 1. Get the chain of interceptors for THIS method
        List<Object> chain = this.advised
            .getInterceptorsAndDynamicInterceptionAdvice(method, targetClass);

        if (chain.isEmpty()) {
            // No advice → invoke target directly (fast path)
            return AopUtils.invokeJoinpointUsingReflection(target, method, args);
        }

        // 2. Create invocation and proceed through interceptor chain
        MethodInvocation invocation = new ReflectiveMethodInvocation(
            proxy, target, method, args, targetClass, chain);
        return invocation.proceed();  // Chain of Responsibility pattern
    }
}

5. CGLIB Proxy — Subclass-Based Proxying

When your bean has no interfaces, or when proxyTargetClass=true, Spring uses CGLIB (Code Generation Library) to generate a subclass of your bean class at runtime using the ASM bytecode library.

// Your bean WITHOUT an interface:
@Service
public class PaymentProcessor {
    public Receipt processPayment(Payment payment) { ... }
}

// CGLIB generates a subclass at runtime (conceptually):
public class PaymentProcessor$$EnhancerBySpringCGLIB$$7a3b2c1d
        extends PaymentProcessor {

    private MethodInterceptor[] callbacks;

    @Override
    public Receipt processPayment(Payment payment) {
        // Intercepts the call — does NOT call super directly
        MethodProxy methodProxy = CGLIB$processPayment$0$Proxy;
        return (Receipt) callbacks[0].intercept(
            this, method, new Object[]{ payment }, methodProxy
        );
    }

    // CGLIB also generates a "super" method for invoking original
    final Receipt CGLIB$processPayment$0(Payment payment) {
        return super.processPayment(payment);  // actual target method
    }
}

// Spring's CGLIB MethodInterceptor (similar role to InvocationHandler)
private static class DynamicAdvisedInterceptor implements MethodInterceptor {

    @Override
    public Object intercept(Object proxy, Method method,
            Object[] args, MethodProxy methodProxy) {

        // Same logic as JDK proxy: get interceptor chain, proceed
        List<Object> chain = advised
            .getInterceptorsAndDynamicInterceptionAdvice(method, targetClass);

        if (chain.isEmpty()) {
            // Fast path — call original method directly via MethodProxy
            return methodProxy.invoke(target, args);
        }

        CglibMethodInvocation invocation = new CglibMethodInvocation(
            proxy, target, method, args, targetClass, chain, methodProxy);
        return invocation.proceed();
    }
}
⚠️ CGLIB Constraints
  • final classes cannot be proxied — CGLIB needs to create a subclass
  • final methods are not intercepted — they cannot be overridden in the subclass
  • private methods are invisible to the proxy — only public/protected methods are intercepted
  • The constructor of the target class is called twice in older Spring versions (once for target, once for proxy subclass) — Spring 4+ uses Objenesis to avoid this

6. When Each Proxy Type Is Chosen

Criteria JDK Dynamic Proxy CGLIB Proxy
Mechanism Implements same interface(s) Generates subclass via ASM bytecode
Trigger condition Bean implements ≥1 interface AND proxyTargetClass=false No interface OR proxyTargetClass=true
Proxy type $Proxy42 (implements interface) MyClass$$EnhancerBySpringCGLIB$$xxxx (extends class)
Cast-safe to Interface type only Both class type and interface type
final classes ✅ Works (proxies the interface) ❌ Cannot proxy — throws exception
final methods ✅ Intercepted (interface method isn't final) ❌ Not intercepted — silently skipped

// The decision logic inside DefaultAopProxyFactory
public class DefaultAopProxyFactory implements AopProxyFactory {

    @Override
    public AopProxy createAopProxy(AdvisedSupport config) {

        if (config.isOptimize() ||
            config.isProxyTargetClass() ||                  // ← Spring Boot sets this TRUE
            hasNoUserSuppliedProxyInterfaces(config)) {    // ← No interfaces

            Class<?> targetClass = config.getTargetClass();

            if (targetClass.isInterface() || Proxy.isProxyClass(targetClass)) {
                return new JdkDynamicAopProxy(config);  // Interface → JDK anyway
            }
            return new ObjenesisCglibAopProxy(config);   // ← CGLIB proxy
        }

        return new JdkDynamicAopProxy(config);          // ← JDK proxy
    }
}

// Spring Boot 2.0+ sets this in AopAutoConfiguration:
@Configuration
@EnableAspectJAutoProxy(proxyTargetClass = true)  // CGLIB by default!
public class AopAutoConfiguration { }

7. Pointcut Expressions — How Spring Matches Methods

Pointcuts define where advice should be applied. Spring parses these expressions into an AST and evaluates them against every method of every proxied bean.

// ═══════════════════════════════════════════════════════════════════
// execution() — THE most common. Matches method signatures.
// ═══════════════════════════════════════════════════════════════════

// Pattern: execution(modifiers? return-type declaring-type? method-name(params) throws?)

@Pointcut("execution(* com.app.service.*.*(..))")
//          │         │                │ │  │
//          │         │                │ │  └─ any params
//          │         │                │ └──── any method name
//          │         │                └────── any class in package
//          │         └───────────────────────  in com.app.service
//          └─────────────────────────────────  any return type

// More specific examples:
@Pointcut("execution(public String com.app.service.UserService.findById(Long))")

// Subpackages with ..
@Pointcut("execution(* com.app..*Service.*(..))")  // any *Service in any subpackage

// ═══════════════════════════════════════════════════════════════════
// within() — Matches all methods in matching classes
// ═══════════════════════════════════════════════════════════════════

@Pointcut("within(com.app.service..*)")  // all methods in service package
@Pointcut("within(com.app.service.OrderService)")  // all methods in OrderService

// ═══════════════════════════════════════════════════════════════════
// @annotation() — Matches methods WITH a specific annotation
// ═══════════════════════════════════════════════════════════════════

@Pointcut("@annotation(com.app.annotation.Audited)")  // any @Audited method
@Pointcut("@annotation(org.springframework.transaction.annotation.Transactional)")

// ═══════════════════════════════════════════════════════════════════
// args() — Matches by argument types at RUNTIME
// ═══════════════════════════════════════════════════════════════════

@Pointcut("args(com.app.model.Order, ..)")  // first arg is Order

// ═══════════════════════════════════════════════════════════════════
// bean() — Spring-specific! Matches by bean name
// ═══════════════════════════════════════════════════════════════════

@Pointcut("bean(*Service)")      // all beans ending with "Service"
@Pointcut("bean(orderService)")  // specific bean by name

// ═══════════════════════════════════════════════════════════════════
// Combining pointcuts with logical operators
// ═══════════════════════════════════════════════════════════════════

@Pointcut("execution(* com.app.service.*.*(..)) && !execution(* *.get*(..))")
// All service methods EXCEPT getters

@Pointcut("@annotation(Audited) || @annotation(Transactional)")
// Methods with EITHER annotation
🔍 Pointcut Matching Performance

Pointcut matching happens at startup time, not runtime. Spring evaluates each pointcut against every method once during proxy creation and caches the result. At runtime, the interceptor chain is a pre-computed list — no pattern matching occurs per invocation. However, args() pointcuts require runtime type checking because they match on actual argument types (polymorphism), making them slightly more expensive.

8. Advice Types & Their Execution Order

@Aspect
@Component
public class LoggingAspect {

    // ┌─────────────────────────────────────────────────────────────┐
    // │ EXECUTION ORDER (single aspect, same pointcut):             │
    // │                                                             │
    // │  @Around (before proceed) → @Before → METHOD → @AfterReturning → @After → @Around (after proceed)
    // │                                                             │
    // │  On exception:                                              │
    // │  @Around (before proceed) → @Before → METHOD THROWS → @AfterThrowing → @After → @Around (catch)
    // └─────────────────────────────────────────────────────────────┘

    // 1. @Before — runs BEFORE the method
    @Before("execution(* com.app.service.*.*(..))")
    public void logBefore(JoinPoint jp) {
        log.info("Entering: {}", jp.getSignature().toShortString());
    }

    // 2. @AfterReturning — runs after successful return
    @AfterReturning(pointcut = "execution(* com.app.service.*.*(..))",
                    returning = "result")
    public void logReturn(JoinPoint jp, Object result) {
        log.info("Returned: {} → {}", jp.getSignature().toShortString(), result);
    }

    // 3. @AfterThrowing — runs only when exception is thrown
    @AfterThrowing(pointcut = "execution(* com.app.service.*.*(..))",
                   throwing = "ex")
    public void logException(JoinPoint jp, Throwable ex) {
        log.error("Exception in {}: {}", jp.getSignature().toShortString(), ex.getMessage());
    }

    // 4. @After — runs ALWAYS (like finally block), success OR failure
    @After("execution(* com.app.service.*.*(..))")
    public void logAfter(JoinPoint jp) {
        log.info("Completed: {}", jp.getSignature().toShortString());
    }

    // 5. @Around — MOST POWERFUL. Wraps the entire execution.
    @Around("execution(* com.app.service.*.*(..))")
    public Object logAround(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        try {
            Object result = pjp.proceed();  // ← CALLS THE ACTUAL METHOD
            return result;
        } catch (Throwable t) {
            log.error("Failed after {}ms", (System.nanoTime() - start) / 1_000_000);
            throw t;
        } finally {
            log.info("Duration: {}ms", (System.nanoTime() - start) / 1_000_000);
        }
    }
}
⚠️ Ordering Across Multiple Aspects

When multiple aspects apply to the same method, use @Order to control execution order. Lower values execute first (outermost). Without @Order, the order is undefined and may vary between JVM runs.

@Aspect @Order(1)  // Executes FIRST (outermost wrapper)
public class SecurityAspect { }

@Aspect @Order(2)  // Executes SECOND (inside security)
public class TransactionAspect { }

@Aspect @Order(3)  // Executes LAST (innermost, closest to target)
public class LoggingAspect { }

// Call flow: Security → Transaction → Logging → METHOD → Logging → Transaction → Security

9. Why Self-Invocation Bypasses AOP — The Achilles Heel

🚨 CRITICAL: Self-Invocation Breaks AOP

When a method calls another method on the same bean using this.method(), the call goes directly to the target object — bypassing the proxy entirely. This means @Transactional, @Cacheable, @Async, and any other AOP-based annotation on the called method will not work.

@Service
public class OrderService {

    @Transactional
    public void processOrder(Order order) {
        // ... processing logic ...
        sendNotification(order);  // ← THIS IS this.sendNotification()
        //                              goes DIRECTLY to target, not through proxy!
    }

    @Async  // ❌ THIS WILL NOT EXECUTE ASYNCHRONOUSLY!
    public void sendNotification(Order order) {
        // Intended to run in separate thread, but @Async is IGNORED
        // because the call bypassed the proxy
        emailService.send(order.getEmail(), "Order confirmed");
    }
}

// WHY? Because inside processOrder(), 'this' refers to the TARGET object,
// not the PROXY that wraps it.
//
//   External caller → Proxy.processOrder() → Target.processOrder()
//                                                    │
//                                                    └→ this.sendNotification()
//                                                       ↑ DIRECT call to target!
//                                                         Proxy is not involved!

Solutions to the Self-Invocation Problem

// ═══════════════════════════════════════════════════════════════════
// SOLUTION 1: Self-injection (recommended in Spring Boot)
// ═══════════════════════════════════════════════════════════════════

@Service
public class OrderService {

    @Autowired
    private OrderService self;  // ← Injects the PROXY, not the target!

    @Transactional
    public void processOrder(Order order) {
        self.sendNotification(order);  // ← Goes through the proxy! ✅
    }

    @Async
    public void sendNotification(Order order) { ... }
}

// ═══════════════════════════════════════════════════════════════════
// SOLUTION 2: AopContext.currentProxy() — explicit proxy access
// ═══════════════════════════════════════════════════════════════════

// First, enable: @EnableAspectJAutoProxy(exposeProxy = true)

@Service
public class OrderService {

    @Transactional
    public void processOrder(Order order) {
        ((OrderService) AopContext.currentProxy())
            .sendNotification(order);  // ← Through proxy! ✅
    }

    @Async
    public void sendNotification(Order order) { ... }
}
// ⚠️ Ugly, couples code to Spring AOP internals. Prefer self-injection.

// ═══════════════════════════════════════════════════════════════════
// SOLUTION 3: Refactor to separate beans (cleanest architecture)
// ═══════════════════════════════════════════════════════════════════

@Service
public class OrderService {

    @Autowired
    private NotificationService notificationService;  // separate bean!

    @Transactional
    public void processOrder(Order order) {
        notificationService.sendNotification(order);  // ← Different bean = through proxy! ✅
    }
}

@Service
public class NotificationService {
    @Async
    public void sendNotification(Order order) { ... }  // ✅ AOP works!
}

10. Performance Cost of AOP Proxies

// Benchmark results (JMH, Spring 6.1, JDK 21, x86_64)
// ═══════════════════════════════════════════════════════════════════
//
// Direct method call (no proxy):           ~2 ns/op
// CGLIB proxy (no advice matches):        ~15 ns/op  (fast path)
// CGLIB proxy (1 @Around advice):        ~100 ns/op
// JDK proxy (1 @Around advice):          ~120 ns/op
// CGLIB proxy (3 stacked advices):       ~250 ns/op
//
// ═══════════════════════════════════════════════════════════════════
// Context: A typical database call takes 1,000,000+ ns (1ms)
//          A typical HTTP call takes 10,000,000+ ns (10ms)
//
// Conclusion: AOP overhead is NEGLIGIBLE for business operations
//             but SIGNIFICANT for tight loops (e.g., 10M iterations)
// ═══════════════════════════════════════════════════════════════════
💡 When to Worry About AOP Performance
  • Don't worry: Service layer methods, repository calls, controller handlers — all have I/O that dwarfs proxy overhead
  • Do worry: Utility methods called millions of times in computation-heavy loops (don't AOP these)
  • Startup cost: Each proxied bean adds ~0.1-0.5ms to startup (pointcut matching). 1000 proxied beans ≈ 100-500ms startup penalty

11. AspectJ Compile-Time Weaving vs Spring AOP

Feature Spring AOP (Runtime Proxies) AspectJ (Compile-Time Weaving)
Mechanism Wraps beans in proxy objects at runtime Modifies .class bytecode at compile time (ajc compiler)
Self-invocation ❌ Doesn't work (proxy not involved) ✅ Works (bytecode is modified in-place)
Scope Spring beans only Any Java class (even non-Spring)
Joinpoints Method execution only Method, constructor, field access, exception handler
Performance Slight runtime overhead per call Zero runtime overhead (code is inline)
Complexity Zero build setup (just annotations) Requires ajc compiler or load-time weaver

// Enabling AspectJ load-time weaving with Spring
@Configuration
@EnableLoadTimeWeaving  // Uses Java agent (-javaagent:aspectjweaver.jar)
public class AspectJConfig { }

// With AspectJ, self-invocation WORKS because bytecode is modified:
// BEFORE weaving:
public void processOrder(Order order) {
    sendNotification(order);  // this.sendNotification()
}

// AFTER AspectJ weaving (decompiled):
public void processOrder(Order order) {
    // Advice code is INLINED into the method body
    sendNotification$original(order);
}

private void sendNotification$original(Order order) {
    // Original code + woven aspect code runs here
    // No proxy needed — bytecode was rewritten!
}

12. Industry Patterns — AOP in Production

Nearly every major Spring feature you use daily is implemented via AOP proxies:

// ═══════════════════════════════════════════════════════════════════
// Spring's built-in AOP-powered annotations
// ═══════════════════════════════════════════════════════════════════

@Transactional       // → TransactionInterceptor (begin/commit/rollback)
@Cacheable           // → CacheInterceptor (check cache → return or invoke)
@Async               // → AsyncExecutionInterceptor (submit to thread pool)
@Retryable           // → RetryOperationsInterceptor (retry on exception)
@PreAuthorize        // → MethodSecurityInterceptor (check permissions)
@Validated           // → MethodValidationInterceptor (validate args/return)

// ═══════════════════════════════════════════════════════════════════
// Custom AOP pattern: @Audited — audit trail for sensitive operations
// ═══════════════════════════════════════════════════════════════════

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Audited {
    String action() default "";
}

@Aspect
@Component
public class AuditAspect {

    @Autowired private AuditRepository auditRepo;
    @Autowired private SecurityContext securityContext;

    @Around("@annotation(audited)")
    public Object audit(ProceedingJoinPoint pjp, Audited audited) throws Throwable {
        String user = securityContext.getCurrentUser();
        String action = audited.action().isEmpty()
            ? pjp.getSignature().getName() : audited.action();

        try {
            Object result = pjp.proceed();
            auditRepo.save(new AuditEntry(user, action, "SUCCESS", pjp.getArgs()));
            return result;
        } catch (Throwable t) {
            auditRepo.save(new AuditEntry(user, action, "FAILED", t.getMessage()));
            throw t;
        }
    }
}

// Usage — clean and declarative:
@Service
public class AccountService {

    @Audited(action = "TRANSFER_FUNDS")
    @Transactional
    public void transfer(Account from, Account to, BigDecimal amount) {
        from.debit(amount);
        to.credit(amount);
    }
}

// ═══════════════════════════════════════════════════════════════════
// Custom AOP pattern: @RateLimited — API rate limiting
// ═══════════════════════════════════════════════════════════════════

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RateLimited {
    int maxRequests() default 100;
    int windowSeconds() default 60;
}

@Aspect
@Component
public class RateLimitAspect {

    private final Map<String, RateLimiter> limiters = new ConcurrentHashMap<>();

    @Around("@annotation(rateLimited)")
    public Object rateLimit(ProceedingJoinPoint pjp, RateLimited rateLimited) throws Throwable {
        String key = pjp.getSignature().toLongString();
        RateLimiter limiter = limiters.computeIfAbsent(key,
            k -> RateLimiter.create(rateLimited.maxRequests() / (double) rateLimited.windowSeconds()));

        if (!limiter.tryAcquire()) {
            throw new RateLimitExceededException("Rate limit exceeded");
        }
        return pjp.proceed();
    }
}

💼 Interview Challenge

"Your team reports that @Transactional isn't rolling back on exceptions in a specific service method. The method is public, non-final, and the exception IS a RuntimeException. What's your debugging approach?"

Expert answer framework:

  1. Check self-invocation — Is the method being called from within the same bean? If yes, the proxy is bypassed.
  2. Verify proxy creation — Add log.info(getClass().getName()) in the method. If it shows your class name (not $$EnhancerByCGLIB$$), you're not proxied.
  3. Check exception type — @Transactional only rolls back on RuntimeException and Error by default. For checked exceptions, use rollbackFor.
  4. Check propagation — REQUIRES_NEW creates a new transaction; if the inner one rolls back but the outer one catches the exception, the outer commits.
  5. Check try-catch — If you catch the exception inside the method and don't rethrow, the proxy sees no exception → no rollback.
