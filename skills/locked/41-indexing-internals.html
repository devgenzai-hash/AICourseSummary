Indexing Internals

Understanding how databases organize data for fast retrieval — the internal structures that turn O(n) full table scans into O(log n) lookups and the trade-offs every index imposes on write performance.

💡 Real-World Analogy

Imagine a textbook with 1000 pages. Without an index, finding “B-Tree” means reading every page from start to finish (sequential scan). With the index at the back, you look up “B-Tree → pages 142, 305, 718” and jump directly there. The index itself takes space (extra pages), and every time you add content, you must update the index too — but the lookup speedup is worth it for frequently searched terms. You wouldn’t index every single word though — that would make the index bigger than the book.

Why Indexes Exist

Without an index, every query requires a sequential scan — reading every row in the table to find matches. For a table with 10 million rows, that means 10 million row comparisons for a single lookup:

Access Method Time Complexity 10M Rows 100M Rows Use Case
Sequential Scan O(n) ~10M comparisons ~100M comparisons No index, or query returns most rows
B-Tree Index Scan O(log n) ~23 comparisons ~27 comparisons Equality, range queries, ORDER BY
Hash Index O(1) ~1 lookup ~1 lookup Exact equality only (no ranges)
Bitmap Index Scan O(n/page_size) Scan matching pages Scan matching pages Low-cardinality columns, OR conditions

B-Tree / B+Tree Structure

The B+Tree is the dominant index structure in relational databases (PostgreSQL, MySQL, SQL Server, Oracle). It’s a balanced tree where:

  • All data lives in leaf nodes (linked in order for range scans)
  • Internal nodes contain only keys and child pointers (maximizing fanout)
  • The tree stays balanced — all leaves are at the same depth
  • Typical fanout of 100-500 means 3-4 levels handles billions of rows

B+Tree Properties

Property B-Tree B+Tree
Data location Any node (internal + leaf) Leaf nodes only
Leaf linking No sibling pointers Doubly-linked list of leaves
Range scans Requires tree traversal Follow leaf pointers (sequential)
Internal node size Larger (holds data) Smaller (keys only → higher fanout)
Used by MongoDB (WiredTiger) PostgreSQL, MySQL InnoDB, SQL Server

Hash Indexes

Hash indexes provide O(1) lookup for exact equality only. They cannot support range queries, ORDER BY, or partial matching:

  • Key is hashed to a bucket number
  • Bucket contains pointers to matching rows
  • Collisions handled via chaining or linear probing
  • PostgreSQL supports hash indexes (crash-safe since v10)
  • Ideal for: join keys, exact lookups where ranges are never needed

LSM Trees (Log-Structured Merge Trees)

LSM trees optimize for write-heavy workloads by buffering writes in memory and flushing sorted runs to disk:

Aspect B+Tree LSM Tree
Write pattern Random I/O (update page in place) Sequential I/O (append to log)
Write throughput Moderate High (10-100x for writes)
Read performance Fast (single tree traversal) Slower (check multiple levels)
Space amplification Low (update in place) Higher (duplicate keys across levels)
Background work Minimal Compaction (merging sorted runs)
Used by PostgreSQL, MySQL, SQL Server RocksDB, LevelDB, Cassandra, ScyllaDB

Index Scan vs Sequential Scan

The query planner decides whether to use an index based on selectivity — what fraction of rows the query returns:

  • <5-10% of rows: Index scan wins (few random I/Os beat full scan)
  • >10-20% of rows: Sequential scan wins (sequential I/O is faster than many random reads)
  • Covering index: Always wins if all needed columns are in the index (no heap lookup)

Covering Indexes

A covering index includes all columns needed by a query, eliminating the need to fetch the actual row from the heap/clustered index:

-- Regular index: must fetch row for 'email'
-- CREATE INDEX idx_users_name ON users(name);
-- SELECT name, email FROM users WHERE name = 'Alice';
--   Index scan on idx_users_name → heap fetch for email

-- Covering index: all data in the index itself
-- CREATE INDEX idx_users_name_email ON users(name) INCLUDE (email);
-- SELECT name, email FROM users WHERE name = 'Alice';
--   Index-only scan → no heap fetch needed

When NOT to Index

  • Small tables: Sequential scan of 1000 rows is faster than index overhead
  • Low selectivity: Boolean columns, status fields with 2-3 values — index returns too many rows
  • Write-heavy tables: Each index adds overhead to every INSERT/UPDATE/DELETE
  • Frequently updated columns: Index must be reorganized on every change
  • Wide indexes: If the index is as large as the table, it provides no benefit

B-Tree Node Implementation

A simplified B-Tree node class showing the core insertion and search logic:

from typing import List, Optional, Any
import time
import random
import bisect

class BTreeNode:
    """A node in a B-Tree index structure.

    Each node holds up to (2*t - 1) keys and (2*t) children.
    When full, it splits into two nodes and pushes the
    median key up to the parent.
    """

    def __init__(self, t: int, leaf: bool = True):
        self.t = t          # Minimum degree
        self.leaf = leaf    # True if leaf node
        self.keys: List[int] = []
        self.children: List['BTreeNode'] = []
        self.values: List[Any] = []  # Data pointers (leaf only)

    def is_full(self) -> bool:
        return len(self.keys) == 2 * self.t - 1

    def search(self, key: int) -> Optional[Any]:
        """Search for a key in O(log n) time.

        Uses binary search within each node, then
        descends to the appropriate child.
        """
        idx = bisect.bisect_left(self.keys, key)

        # Found in current node
        if idx < len(self.keys) and self.keys[idx] == key:
            return self.values[idx] if self.leaf else key

        # Leaf node -- key not found
        if self.leaf:
            return None

        # Descend to child
        return self.children[idx].search(key)


class BTree:
    """B-Tree implementation for demonstrating index behavior.

    Minimum degree t=3 means each node holds 2-5 keys
    and 3-6 children (except root which can have fewer).
    """

    def __init__(self, t: int = 3):
        self.t = t
        self.root = BTreeNode(t, leaf=True)
        self.height = 0
        self.node_count = 1

    def search(self, key: int) -> Optional[Any]:
        return self.root.search(key)

    def insert(self, key: int, value: Any = None):
        """Insert a key-value pair into the B-Tree.

        If root is full, split it first (tree grows upward).
        """
        root = self.root

        if root.is_full():
            # Root is full -- create new root and split
            new_root = BTreeNode(self.t, leaf=False)
            new_root.children.append(self.root)
            self._split_child(new_root, 0)
            self.root = new_root
            self.height += 1
            self.node_count += 2

        self._insert_non_full(self.root, key, value)

    def _split_child(self, parent: BTreeNode, idx: int):
        """Split a full child node at position idx."""
        t = self.t
        child = parent.children[idx]
        new_node = BTreeNode(t, leaf=child.leaf)

        # Move upper half of keys to new node
        mid = t - 1
        parent.keys.insert(idx, child.keys[mid])
        parent.values.insert(idx, child.values[mid] if child.leaf else None)
        parent.children.insert(idx + 1, new_node)

        new_node.keys = child.keys[mid + 1:]
        new_node.values = child.values[mid + 1:] if child.leaf else []
        child.keys = child.keys[:mid]
        child.values = child.values[:mid] if child.leaf else []

        if not child.leaf:
            new_node.children = child.children[mid + 1:]
            child.children = child.children[:mid + 1]

        self.node_count += 1

    def _insert_non_full(self, node: BTreeNode, key: int, value: Any):
        """Insert into a node that is guaranteed not full."""
        idx = bisect.bisect_left(node.keys, key)

        if node.leaf:
            node.keys.insert(idx, key)
            node.values.insert(idx, value)
        else:
            if node.children[idx].is_full():
                self._split_child(node, idx)
                if key > node.keys[idx]:
                    idx += 1
            self._insert_non_full(node.children[idx], key, value)


# --- Performance comparison: indexed vs sequential ---

def benchmark_lookup(n: int = 100000, searches: int = 1000):
    """Compare B-Tree index lookup vs linear scan.

    Demonstrates why indexes exist: O(log n) vs O(n).
    """
    # Build dataset
    data = list(range(n))
    random.shuffle(data)

    # Build B-Tree index
    tree = BTree(t=50)
    for i, key in enumerate(data):
        tree.insert(key, f"row_{key}")

    search_keys = random.sample(range(n), searches)

    # B-Tree indexed lookup
    start = time.perf_counter()
    for key in search_keys:
        result = tree.search(key)
    indexed_time = time.perf_counter() - start

    # Linear scan (no index)
    start = time.perf_counter()
    for key in search_keys:
        for row in data:
            if row == key:
                break
    scan_time = time.perf_counter() - start

    print(f"Dataset size: {n:,} rows")
    print(f"Searches: {searches:,}")
    print(f"B-Tree height: {tree.height} levels")
    print(f"B-Tree nodes: {tree.node_count:,}")
    print(f"Indexed lookup: {indexed_time:.4f}s")
    print(f"Sequential scan: {scan_time:.4f}s")
    print(f"Speedup: {scan_time / indexed_time:.1f}x faster with index")


if __name__ == "__main__":
    benchmark_lookup(n=100000, searches=500)

🏭 Industry Practice

PostgreSQL B-Tree: Default index type. Pages are 8KB. A typical 3-level B-Tree with fanout ~300 indexes ~27 million keys. Supports INCLUDE columns for covering indexes since v11. Uses the buffer pool — hot index pages stay in RAM. EXPLAIN (ANALYZE, BUFFERS) shows actual page hits.

MySQL InnoDB Clustered Index: The primary key is the table. Data rows are stored in primary key order inside the B+Tree leaf pages. Secondary indexes store the primary key as their row pointer, meaning secondary lookups require a second B-Tree traversal (bookmark lookup). This is why InnoDB strongly favors short integer primary keys.

RocksDB LSM Tree: Used by CockroachDB, TiKV, and MyRocks. Writes go to an in-memory MemTable (skip list), then flush to sorted SSTable files on disk. Compaction merges levels: L0 → L1 → L2. Bloom filters on each level skip unnecessary reads. Write amplification is the key tuning challenge.

MongoDB Indexes: WiredTiger storage engine uses B-Trees. Supports compound indexes, multikey indexes (for arrays), text indexes, and geospatial (2dsphere). The _id field always has a unique index. .explain("executionStats") shows if an index was used and how many documents were examined.

📋 Key Takeaways

  • B+Trees provide O(log n) lookups with high fanout — 3-4 levels handles billions of rows
  • Leaf nodes are linked for efficient range scans without revisiting internal nodes
  • Hash indexes give O(1) equality lookups but cannot support ranges or ordering
  • LSM trees trade read performance for write throughput via sequential I/O and background compaction
  • Covering indexes eliminate heap fetches — the fastest possible read path
  • Don’t index everything — each index slows writes and consumes storage

🧠 Mental Model

A database index is a pre-sorted shortcut structure. The fundamental trade-off: spend storage and write-time maintaining sorted order so that read-time can binary search instead of scanning. Every index is a bet that “reads on this column will be frequent enough to justify the write overhead.”

  B+TREE INDEX STRUCTURE (fanout = 4):

  Level 0 (Root):         [  30  |  60  |  90  ]
                          /    |      |      \
  Level 1 (Internal): [10|20] [40|50] [70|80] [95|99]
                       / | \   / | \   / | \    / | \
  Level 2 (Leaves): [1-9][11-19][21-29] ... [91-94][96-99]
                      ↔      ↔      ↔           ↔      ↔
                    (leaves linked for range scans)

  LOOKUP "key = 42":
  Root:  30 < 42 < 60  →  go to second child
  L1:    40 < 42 < 50  →  go to second child
  Leaf:  scan [41,42,43] →  found! Return row pointer

  Total I/Os: 3 (one per level) regardless of table size

  WITHOUT INDEX:
  ┌─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┐
  │1│2│3│4│...scanning every row...│41│42│✓│
  └─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┘
  Must read all rows until match found: O(n)

⚠️ Common Mistakes

  • Indexing every column: Each index must be updated on every INSERT/UPDATE/DELETE. A table with 10 indexes means 10 additional writes per row modification. Only index columns that appear in WHERE, JOIN, or ORDER BY clauses of frequent queries. Use pg_stat_user_indexes to find unused indexes.
  • Ignoring index selectivity: An index on a boolean is_active column (50% true) is nearly useless — the database will prefer a sequential scan. Indexes shine when they narrow results to <5% of rows. Check cardinality before creating indexes.
  • Forgetting write amplification: B-Tree updates cause random I/O and page splits. For write-heavy workloads (IoT, logging, time-series), LSM-tree databases (RocksDB, Cassandra) provide 10-100x better write throughput by converting random writes to sequential appends.
  • Not using covering indexes: A query that uses an index but still fetches rows from the heap (bookmark lookup) can be slower than a sequential scan if it hits many rows. Adding INCLUDE columns to make the index covering eliminates the second I/O entirely — index-only scan is the fastest path.

  2. Measure index overhead: In PostgreSQL, create a table with 1M rows. Benchmark INSERT throughput with 0, 1, 3, and 5 indexes. Measure how each additional index degrades write performance and quantify the storage overhead.
  3. Covering index optimization: Write a query that performs a bookmark lookup (uses index + heap fetch). Create a covering index with INCLUDE and verify using EXPLAIN (ANALYZE, BUFFERS) that it becomes an index-only scan with fewer buffer hits.
  4. LSM vs B-Tree benchmark: Using RocksDB (via python-rocksdb) and SQLite, insert 1M random keys and measure write throughput. Then perform 10K random point lookups and measure read latency. Compare the read/write trade-off between the two storage engines.
