System Design/ Mutex & Locks

Mutex & Locks

The fundamental tool for protecting shared data. A mutex ensures only one thread can access a resource at a time.

Beginner Concept Code
The Hotel Room Key

A mutex is like a hotel room with one key:

  • Only the person holding the key can enter
  • Everyone else waits at the front desk
  • When done, you return the key
  • Forget to return it? Nobody else can ever enter = deadlock

Mutex = MUTual EXclusion. Only one thread at a time.

What Is a Mutex?

A mutex has two states: locked or unlocked. Only the locking thread can unlock it. Others block until available.

OperationWhat HappensIf Already Locked?
lock()/acquire()Take ownershipThread blocks (waits)
unlock()/release()Release ownershipN/A
try_lock()Try to lock, return immediatelyReturns False

Python Implementation

import threading

mutex = threading.Lock()
shared_data = {"count": 0}

def safe_update(thread_id):
    for i in range(1000):
        with mutex:  # Acquires on enter, releases on exit
            shared_data["count"] += 1

# === Reentrant Lock (RLock) ===
rlock = threading.RLock()

def outer():
    with rlock:
        print("Outer acquired")
        inner()  # Would DEADLOCK with regular Lock!

def inner():
    with rlock:  # Same thread re-acquires — OK with RLock
        print("Inner acquired")

# === Try-Lock (Non-blocking) ===
def try_work():
    acquired = mutex.acquire(blocking=False)
    if acquired:
        try:
            shared_data["count"] += 1
        finally:
            mutex.release()
    else:
        print("Busy, will try later")

# === Timed Lock ===
def timed_work():
    acquired = mutex.acquire(timeout=2.0)
    if acquired:
        try:
            shared_data["count"] += 1
        finally:
            mutex.release()
    else:
        print("Timeout! Could not acquire in 2s")

Lock vs RLock vs Condition

TypeRe-entrant?Use Case
Lock()No — deadlocks if same thread acquires twiceSimple mutual exclusion
RLock()Yes — same thread can acquire many timesRecursive/nested locking
Condition()Built on Lock/RLockWait for a condition to be true

Lock Granularity: Fine vs Coarse

# COARSE-GRAINED: One lock for everything (simple but slow)
class CoarseDB:
    def __init__(self):
        self.lock = threading.Lock()
        self.users = {}
        self.orders = {}

    def update_user(self, uid, data):
        with self.lock:  # Blocks ALL operations
            self.users[uid] = data

# FINE-GRAINED: Separate locks (complex but fast)
class FineDB:
    def __init__(self):
        self.user_lock = threading.Lock()
        self.order_lock = threading.Lock()
        self.users = {}
        self.orders = {}

    def update_user(self, uid, data):
        with self.user_lock:  # Only blocks user ops
            self.users[uid] = data

Industry Usage

  • PostgreSQL — lwlocks and spinlocks for different structures
  • Go sync.Mutex — Simple Lock()/Unlock() with no re-entrancy
  • Rust Mutex<T> — Compiler FORCES you to acquire lock before accessing data
  • Java synchronized — Built-in monitor lock on every object

📝 Summary

  • A mutex ensures only one thread accesses a shared resource at a time
  • Always use context managers (with lock:) to prevent forgetting to unlock
  • RLock allows same thread to acquire multiple times (for recursive functions)
  • Fine-grained locks allow more parallelism than coarse-grained
  • Lock contention is the #1 performance killer in concurrent systems

🧠 Mental Model

MUTEX STATE MACHINE: [UNLOCKED] --acquire()--> [LOCKED by T1] [LOCKED] --release()--> [UNLOCKED] T2 calls acquire() while locked --> T2 BLOCKS until T1 releases GRANULARITY: One lock for all <---------> One lock per item (simple, slow) (complex, fast)

❌ Common Beginner Mistakes

  • Forgetting to release — Exception leaves lock held forever. Use with lock: always.
  • Acquiring Lock twice (same thread) — Deadlocks! Use RLock for re-entrancy.
  • Holding locks during I/O — Others blocked for network latency. Do I/O outside lock.
  • Wrong lock instance — Each thread creating its own Lock object defeats the purpose.

  2. Add blocking: producer waits when full, consumer waits when empty (use Condition).
