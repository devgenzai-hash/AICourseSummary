System Design / Threads vs Processes

Threads vs Processes

The two fundamental ways a computer does multiple things at once. Understanding this is the foundation of everything in concurrency and system design.

Beginner Concept Code
🏠 Daily-Life Analogy: Restaurant Kitchen

Think of a process as an entire restaurant — it has its own building, its own kitchen, its own ingredients, its own staff. Two restaurants don't share anything. If one restaurant burns down, the other is fine.

A thread is like a chef inside one restaurant. Multiple chefs share the same kitchen, the same fridge, the same stove. They can work faster together (one chops, one cooks), but they have to be careful not to grab the same knife at the same time.

  • Process = Separate restaurant — Own space, own resources, completely independent
  • Thread = Chef in the same kitchen — Shares space and resources, faster communication, but needs coordination

What Is a Process?

A process is a running program. When you open Chrome, that's a process. When you open Spotify, that's another process. Each process gets its own:

  • Memory space — Its own private chunk of RAM that nobody else can touch
  • CPU time — The operating system gives it turns to run
  • Resources — File handles, network connections, etc.

Processes are isolated. If Chrome crashes, Spotify keeps playing. The operating system makes sure one process can't mess with another's memory.

What Is a Thread?

A thread is a lightweight unit of execution inside a process. One process can have many threads. All threads within the same process share:

  • The same memory — They can all read and write the same variables
  • The same files — They share open file handles
  • The same code — They run different parts of the same program

But each thread has its own:

  • Stack — Its own local variables and function call history
  • Program counter — Where it currently is in the code
  • Registers — CPU register values

Side-by-Side Comparison

Feature Process Thread
Memory Own separate memory space Shares memory with other threads in same process
Creation cost Expensive (needs new memory space) Cheap (just a new stack)
Communication Slow (IPC: pipes, sockets, shared memory) Fast (just read shared variables)
Isolation Strong — crash doesn't affect others Weak — one thread crash kills all threads
Context switch Slow (TLB flush, memory map swap) Fast (just swap stack and registers)
Use case Isolation needed, CPU-bound separate tasks Shared state, I/O-bound, need speed
Example Chrome tabs (each tab = process) Web server handling requests

Technical Deep Dive

How the OS Manages Processes

When the OS creates a process, it sets up a Process Control Block (PCB) containing:

  • PID — Process ID (unique identifier)
  • State — Running, Ready, Waiting, Terminated
  • Memory map — Virtual-to-physical address translation table
  • Open file descriptors — Which files/sockets are open
  • CPU registers — Saved when process is paused

Each process has its own virtual address space. This means process A's memory address 0x1000 points to completely different physical RAM than process B's address 0x1000. The Memory Management Unit (MMU) hardware translates these addresses.

How Threads Work Internally

Threads share the process's virtual address space but each gets:

  • Thread Control Block (TCB) — Thread ID, state, priority
  • Own stack — Typically 1-8 MB (local variables, function calls)
  • Thread-Local Storage (TLS) — Variables private to each thread
💡 Key Insight

Because threads share memory, they can communicate by just writing to a shared variable. But this is also why race conditions happen — two threads writing to the same variable at the same time can corrupt data. This is the central challenge of concurrent programming.

Code Examples

Creating Processes in Python

import multiprocessing
import os

def worker(name):
    """Each process runs this function independently."""
    pid = os.getpid()
    print(f"Worker {name} running in process {pid}")
    # Each process has its own memory - changes here don't affect other processes
    result = sum(range(1000000))
    print(f"Worker {name} done: {result}")

if __name__ == "__main__":
    print(f"Main process PID: {os.getpid()}")
    
    # Create 4 separate processes
    processes = []
    for i in range(4):
        p = multiprocessing.Process(target=worker, args=(f"P{i}",))
        processes.append(p)
        p.start()  # Each gets its own memory space
    
    # Wait for all processes to complete
    for p in processes:
        p.join()
    
    print("All processes completed")

Creating Threads in Python

import threading
import os

# Shared variable — ALL threads can see and modify this
shared_counter = 0

def worker(name):
    """Each thread runs this function, sharing memory with others."""
    global shared_counter
    pid = os.getpid()
    tid = threading.current_thread().name
    print(f"Worker {name} in process {pid}, thread {tid}")
    
    # WARNING: This is NOT thread-safe! (We'll fix this in Topic 5: Mutex)
    for _ in range(100000):
        shared_counter += 1  # Race condition here!

if __name__ == "__main__":
    print(f"Main process PID: {os.getpid()}")
    
    # Create 4 threads — all share the same memory space
    threads = []
    for i in range(4):
        t = threading.Thread(target=worker, args=(f"T{i}",))
        threads.append(t)
        t.start()
    
    for t in threads:
        t.join()
    
    # Expected: 400000, Actual: less than 400000 (race condition!)
    print(f"Counter: {shared_counter} (expected 400000)")
⚠️ The Race Condition Preview

Notice the thread example gives wrong results! The counter won't reach 400,000 because multiple threads modify shared_counter simultaneously. This is called a race condition — we'll learn to fix it in Topic 3 and Topic 5.

Process Communication (IPC)

import multiprocessing

def producer(queue):
    """Process that produces data."""
    for i in range(5):
        queue.put(f"item_{i}")
        print(f"Produced: item_{i}")
    queue.put(None)  # Sentinel to signal "done"

def consumer(queue):
    """Process that consumes data."""
    while True:
        item = queue.get()  # Blocks until item available
        if item is None:
            break
        print(f"Consumed: {item}")

if __name__ == "__main__":
    # Queue enables safe communication between processes
    queue = multiprocessing.Queue()
    
    p1 = multiprocessing.Process(target=producer, args=(queue,))
    p2 = multiprocessing.Process(target=consumer, args=(queue,))
    
    p1.start()
    p2.start()
    p1.join()
    p2.join()
Go Example: Goroutines (Lightweight Threads)

Go uses goroutines — extremely lightweight threads managed by Go's runtime rather than the OS. You can spawn millions of them.

package main

import (
    "fmt"
    "sync"
)

func worker(id int, wg *sync.WaitGroup) {
    defer wg.Done()
    fmt.Printf("Worker %d starting\n", id)
    // Do some work...
    sum := 0
    for i := 0; i < 1000000; i++ {
        sum += i
    }
    fmt.Printf("Worker %d done: %d\n", id, sum)
}

func main() {
    var wg sync.WaitGroup
    
    // Launch 4 goroutines (super cheap — only ~2KB stack each)
    for i := 1; i <= 4; i++ {
        wg.Add(1)
        go worker(i, &wg)  // "go" keyword creates a goroutine
    }
    
    wg.Wait()  // Wait for all goroutines to finish
    fmt.Println("All workers completed")
}

Key difference: A goroutine uses ~2KB of stack (grows as needed), while an OS thread uses ~1-8MB. That's why Go can handle millions of goroutines while Java struggles with thousands of threads.

When to Use Processes vs Threads

Use Processes When:

  • You need isolation — One crash shouldn't kill everything (Chrome uses processes for tabs)
  • CPU-bound work in Python — Python's GIL prevents true thread parallelism for CPU work
  • Security boundary — You don't want code sharing memory (sandboxing)
  • Different languages — A Python process can communicate with a Go process via IPC

Use Threads When:

  • Shared state is needed — Multiple workers updating the same data structure
  • I/O-bound work — Waiting for network/disk (threads can do other work while one waits)
  • Low latency needed — Thread creation and communication is much faster
  • Memory efficiency — Threads share memory, processes duplicate it

🏢 Industry Use Cases

  • Chrome browser — Each tab is a separate process (isolation: one tab crash doesn't kill all tabs)
  • Nginx — Master process + worker processes (each worker handles thousands of connections with threads/events)
  • PostgreSQL — One process per connection (isolation, stability)
  • Java web servers (Tomcat) — One thread per request (shared memory, efficient)
  • Node.js — Single-threaded event loop + worker threads for CPU-heavy tasks
  • Go services — Thousands of goroutines (lightweight threads) per server

Python's GIL: The Elephant in the Room

Python has a Global Interpreter Lock (GIL) — a mutex that allows only one thread to execute Python code at a time. This means:

  • CPU-bound tasks — Threads DON'T give you parallelism in Python. Use processes instead.
  • I/O-bound tasks — Threads WORK fine because the GIL is released during I/O waits.
import multiprocessing
import threading
import time

def cpu_heavy():
    """CPU-bound work."""
    total = 0
    for i in range(10_000_000):
        total += i * i
    return total

# Threading (GIL prevents true parallelism for CPU work)
start = time.time()
threads = [threading.Thread(target=cpu_heavy) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(f"Threads: {time.time() - start:.2f}s")  # ~4s (no speedup!)

# Multiprocessing (true parallelism, bypasses GIL)
start = time.time()
procs = [multiprocessing.Process(target=cpu_heavy) for _ in range(4)]
for p in procs: p.start()
for p in procs: p.join()
print(f"Processes: {time.time() - start:.2f}s")  # ~1s (4x speedup!)

📝 Summary

  • A process is an independent program with its own memory — isolated and safe but expensive
  • A thread is a lightweight execution unit inside a process — shares memory, cheap but dangerous
  • Processes communicate via IPC (pipes, queues, sockets) — slow but safe
  • Threads communicate via shared memory — fast but needs synchronization (locks)
  • Python's GIL makes threads useless for CPU work — use processes for CPU parallelism
  • Go's goroutines are the best of both worlds — cheap like threads, millions possible

❌ Common Beginner Mistakes

  • Using threads for CPU-bound work in Python — The GIL prevents parallelism. Use multiprocessing or move to Go/Rust.
  • Sharing mutable state between threads without locks — This causes race conditions (data corruption). Always protect shared data.
  • Creating too many OS threads — Each thread uses 1-8MB of stack. 10,000 threads = 10-80GB of memory. Use thread pools.
  • Ignoring process startup cost — Spawning a process is ~100x slower than creating a thread. Don't create/destroy processes per-request.
  • Assuming shared memory is immediately visible — CPU caches mean one thread's write might not be visible to another immediately (see Topic 10: Memory Visibility).

🏋️ Hands-On Exercise

Goal: See the difference between threads and processes firsthand.

  1. Write a program that calculates the sum of squares from 1 to 10,000,000
  2. Time it with: (a) single-threaded, (b) 4 threads, (c) 4 processes
  3. Observe: threads are NOT faster for CPU work in Python (GIL), but processes ARE
  4. Modify to do I/O work instead (e.g., sleep(0.1) simulating network calls) — now threads ARE faster than sequential
  5. Bonus: Print the PID and thread name in each worker to prove processes get different PIDs but threads share one PID

Success criteria: You can explain WHY processes beat threads for CPU work in Python, and WHY threads beat sequential for I/O work.
