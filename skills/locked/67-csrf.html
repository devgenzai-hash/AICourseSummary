CSRF Protection

Intermediate Security Pattern

CSRF Protection

Defending state-changing requests from unauthorized cross-origin exploitation

💡 Real-World Analogy

A bank requiring you to show a unique ticket number they gave you before processing any transaction — proving you initiated the request from their counter, not a forged letter. Without that ticket, anyone could write a letter pretending to be you, and the bank would blindly execute it.

What Is CSRF?

Cross-Site Request Forgery (CSRF) is an attack where a malicious website tricks a user’s browser into making an unwanted request to a trusted site where the user is already authenticated. Because browsers automatically attach cookies to requests, the trusted site cannot distinguish between a legitimate user action and a forged one.

How the Attack Works

The attacker exploits the browser’s automatic cookie attachment — when a victim visits a malicious page, hidden forms or image tags fire requests to the target site, carrying the victim’s session cookies along for the ride.

Attack Vector Mechanism Example
Hidden Form Auto-submitting form via JavaScript <form action="bank.com/transfer" method="POST">
Image Tag GET request via img src <img src="bank.com/transfer?to=attacker&amt=1000">
Link Click Social engineering + GET side effects Disguised anchor tags in emails or forums
XHR/Fetch Cross-origin request with credentials fetch("bank.com/api/transfer", {credentials: "include"})

Protection Strategies

1. Synchronizer Token Pattern

The server generates a unique, unpredictable token per session (or per request) and embeds it in forms. On submission, the server validates the token matches what it issued — an attacker cannot guess this value.

import secrets
import hashlib
from functools import wraps

class CSRFProtection:
    """Synchronizer token pattern implementation."""

    def __init__(self, secret_key: str):
        self.secret_key = secret_key
        self.token_store = {}  # session_id -> token

    def generate_token(self, session_id: str) -> str:
        """Generate a cryptographically secure CSRF token."""
        raw_token = secrets.token_hex(32)
        # Bind token to session to prevent token fixation
        bound_token = hashlib.sha256(
            f"{raw_token}:{session_id}:{self.secret_key}".encode()
        ).hexdigest()
        self.token_store[session_id] = bound_token
        return bound_token

    def validate_token(self, session_id: str, token: str) -> bool:
        """Validate submitted token against stored token."""
        stored = self.token_store.get(session_id)
        if not stored:
            return False
        # Constant-time comparison prevents timing attacks
        return secrets.compare_digest(stored, token)

2. Double-Submit Cookie

The server sets a random value in both a cookie and expects it as a request parameter. Since attackers cannot read cookies from another domain, they cannot replicate the value in the request body.

import secrets
from http.cookies import SimpleCookie

class DoubleSubmitCSRF:
    """Double-submit cookie CSRF protection."""

    def set_csrf_cookie(self, response) -> str:
        """Set CSRF token in a cookie and return the value."""
        token = secrets.token_hex(32)
        response.set_cookie(
            "csrf_token",
            token,
            httponly=False,  # JS must read this
            secure=True,
            samesite="Strict",
            max_age=3600
        )
        return token

    def validate_double_submit(self, cookie_token: str, header_token: str) -> bool:
        """Compare cookie value against header/body value."""
        if not cookie_token or not header_token:
            return False
        return secrets.compare_digest(cookie_token, header_token)

3. SameSite Cookie Attribute

Modern browsers support the SameSite attribute, which controls whether cookies are sent with cross-origin requests — providing built-in CSRF mitigation at the browser level.

# SameSite cookie configuration examples

def configure_session_cookie(app):
    """Configure session cookie with SameSite protection."""
    app.config["SESSION_COOKIE_SAMESITE"] = "Lax"
    app.config["SESSION_COOKIE_SECURE"] = True
    app.config["SESSION_COOKIE_HTTPONLY"] = True

# SameSite values explained:
# "Strict" — Cookie never sent on cross-site requests
#            Best security, but breaks top-level navigations
# "Lax"    — Cookie sent on top-level GET navigations only
#            Good default, protects POST/PUT/DELETE
# "None"   — Cookie always sent (requires Secure flag)
#            Use only when cross-site access is needed

SAMESITE_COMPARISON = {
    "Strict": {
        "cross_site_link": False,
        "cross_site_form_get": False,
        "cross_site_form_post": False,
        "cross_site_xhr": False,
    },
    "Lax": {
        "cross_site_link": True,
        "cross_site_form_get": True,
        "cross_site_form_post": False,
        "cross_site_xhr": False,
    },
}

4. Custom Request Headers

Adding custom headers like X-Requested-With leverages CORS preflight — browsers block cross-origin requests with non-standard headers unless the server explicitly allows it.

class CustomHeaderCSRF:
    """CSRF protection via custom headers and CORS."""

    CSRF_HEADER = "X-CSRF-Token"
    SAFE_METHODS = {"GET", "HEAD", "OPTIONS"}

    def csrf_middleware(self, request, handler):
        """Middleware that enforces CSRF token on state-changing requests."""
        if request.method in self.SAFE_METHODS:
            return handler(request)

        # Check Origin header against allowed origins
        origin = request.headers.get("Origin")
        if origin and origin not in self.allowed_origins:
            return forbidden_response("Invalid origin")

        # Verify custom header presence
        csrf_token = request.headers.get(self.CSRF_HEADER)
        if not csrf_token:
            return forbidden_response("Missing CSRF token")

        # Validate token
        if not self.validate_token(request.session_id, csrf_token):
            return forbidden_response("Invalid CSRF token")

        return handler(request)

CORS and Its Role

Cross-Origin Resource Sharing (CORS) complements CSRF protection by controlling which origins can make requests. However, CORS alone is not sufficient — simple requests (form submissions) bypass preflight checks entirely.

Defense Layer What It Prevents Limitation
CSRF Tokens Forged state-changing requests Requires server-side storage or crypto
SameSite Cookies Cross-site cookie attachment Older browsers lack support
CORS Unauthorized cross-origin reads Does not block simple POST requests
Custom Headers Simple cross-origin requests Requires CORS preflight enforcement
Origin/Referer Check Requests from unexpected sources Headers can be stripped by proxies

🏭 Industry Implementations

  • Django — Built-in CSRF middleware using synchronizer tokens; {% csrf_token %} template tag; cookie-to-header pattern for AJAX
  • Spring Security — CsrfFilter with repository-based token storage; per-request or per-session tokens; integrates with Thymeleaf
  • Express (csurf) — Double-submit cookie approach; token exposed via req.csrfToken(); middleware validates on non-safe methods
  • Rails — protect_from_forgery with authenticity tokens; meta tag injection for JavaScript requests; per-form tokens since Rails 5

📋 Key Takeaways

  • CSRF exploits the browser’s automatic cookie attachment to forge authenticated requests
  • Synchronizer tokens are the gold standard — unpredictable, session-bound, validated server-side
  • SameSite=Lax provides excellent default protection for modern browsers
  • Defense in depth: combine tokens + SameSite + Origin checks for robust protection
  • Never perform state-changing operations via GET requests

    │  (User)  │ ←────────────── │          │
    └──────────┘  form + token    └──────────┘
         │                              │

    CSRF Attack (Blocked):
    ┌──────────┐                  ┌──────────┐
    │  Evil    │  POST /transfer  │  Server  │
    │  Site    │ ──────────────→ │          │
    └──────────┘  Cookie: auto    └──────────┘

                                    ✗ Request rejected

⚠️ Common Mistakes

  • Token in GET parameters — Tokens leak via Referer headers, browser history, and server logs; always use POST body or custom headers
  • Global static token — Using the same token for all users or sessions defeats the purpose; tokens must be unique and unpredictable per session
  • Relying solely on CORS — Simple requests (form POSTs) bypass preflight; CORS protects reads, not writes
  • Skipping token validation on AJAX — Assuming JavaScript requests are safe because of same-origin policy; misconfigured CORS can expose your API

🔨 Hands-On Exercises

  1. Implement synchronizer tokens — Build a Flask app with login form that generates per-session CSRF tokens and validates them on form submission
  2. Double-submit cookie — Create a REST API that sets a CSRF cookie and requires the same value in X-CSRF-Token header for all POST requests
  3. SameSite audit — Inspect your application’s cookies using browser DevTools; identify which cookies lack SameSite attributes and fix them
  4. Attack simulation — Create a malicious HTML page that attempts a CSRF attack against your protected app; verify the attack is blocked and review server logs
