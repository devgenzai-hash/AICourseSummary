System Design/ Lock-Free & Wait-Free Algorithms

Lock-Free & Wait-Free Algorithms

Data structures that work correctly under concurrency WITHOUT any locks. Maximum performance, maximum difficulty.

Advanced Concept Code
The Self-Service Gas Station

Lock-based: Only one car can use the pump at a time. Others queue up.

Lock-free: Multiple cars can try to pump simultaneously. If two grab the same nozzle, one retries. At least one always makes progress.

Wait-free: Every car is GUARANTEED to finish pumping within a bounded number of steps. No starvation possible.

Progress Guarantees

LevelGuaranteePerformanceDifficulty
Blocking (locks)None — can deadlockGood in low contentionEasy
Lock-freeAt least ONE thread progressesGreat under contentionHard
Wait-freeALL threads progress in bounded stepsBest worst-caseExtremely hard

Lock-Free Stack (using CAS)

import threading

class Node:
    def __init__(self, value, next_node=None):
        self.value = value
        self.next = next_node

class LockFreeStack:
    def __init__(self):
        self._top = None
        self._lock = threading.Lock()  # Simulates CAS

    def _cas(self, expected, new_value):
        with self._lock:
            if self._top is expected:
                self._top = new_value
                return True
            return False

    def push(self, value):
        while True:
            old_top = self._top
            new_node = Node(value, old_top)
            if self._cas(old_top, new_node):
                return  # Success!
            # CAS failed — someone else pushed. Retry.

    def pop(self):
        while True:
            old_top = self._top
            if old_top is None:
                return None
            new_top = old_top.next
            if self._cas(old_top, new_top):
                return old_top.value  # Success!
            # CAS failed — retry

When to Use Lock-Free

Decision Guide

Use locks when: correctness matters more than speed, low contention, complex operations.
Use lock-free when: high contention, real-time requirements (cannot afford to block), simple operations (counter, stack, queue).

Industry Usage

  • Java ConcurrentLinkedQueue — Lock-free queue using CAS (Michael-Scott algorithm)
  • LMAX Disruptor — Lock-free ring buffer for ultra-low-latency trading (millions msgs/sec)
  • Linux kernel RCU — Read-Copy-Update: readers never block, writers do the work
  • Intel TBB — Lock-free concurrent containers for C++

📝 Summary

  • Lock-free: at least one thread always makes progress (no deadlock possible)
  • Wait-free: ALL threads make progress in bounded steps (strongest guarantee)
  • Built on CAS (Compare-And-Swap) retry loops
  • Faster than locks under high contention but much harder to implement correctly
  • Use for simple structures: counters, stacks, queues
  • Not worth it for complex operations — locks are simpler and usually fast enough

🧠 Mental Model

LOCK-BASED: Thread A: [acquire lock] → work → [release] Thread B: [waiting......] → [acquire] → work → [release] Risk: A holds lock forever = B stuck forever (deadlock) LOCK-FREE (CAS loop): Thread A: read → compute → CAS(success!) → done Thread B: read → compute → CAS(FAIL! retry) → read → compute → CAS(success!) → done Guarantee: At least one thread always succeeds per round

❌ Common Beginner Mistakes

  • Using lock-free when not needed — Locks are simpler and often fast enough. Profile first.
  • ABA problem — CAS can succeed incorrectly if value changes A→B→A. Use version counters.
  • Memory reclamation — When can you safely free a popped node? Other threads might still read it.
  • Testing difficulty — Lock-free bugs are extremely rare and hard to reproduce. Formal verification needed.

🏋 Hands-On Exercise

  1. Implement a lock-free counter using CAS retry loop. Test with 10 threads.
  2. Implement a lock-free stack (push/pop). Verify correctness under contention.
  3. Benchmark: lock-free stack vs lock-based stack with 10 threads, 1M operations.
  4. Demonstrate ABA problem with a lock-free stack (hint: pop node, push it back).
