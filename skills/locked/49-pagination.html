Architecture Patterns → Pagination
Beginner Architecture Pattern

Pagination

Breaking large result sets into manageable chunks — the difference between returning 10 million rows at once (crash) and delivering them 25 at a time (smooth). Every API that returns lists needs a pagination strategy.

💡 Real-World Analogy

Imagine you want to read a novel. You could print the entire book on a single endless scroll of paper — good luck finding chapter 7 or carrying it around. Instead, books are divided into pages. You read page 1, flip to page 2, and so on. You can jump to any page number, bookmark your position, and carry a manageable chunk at a time. Pagination in APIs works the same way — instead of dumping an entire database table into one response, you serve it page by page, letting the client request exactly the slice they need.

Why Pagination Matters

  • Memory: Loading 10M rows into memory at once will OOM your server and the client
  • Network: A 500MB JSON response takes forever to transfer and parse
  • Database: Full table scans without LIMIT are expensive and block other queries
  • UX: Users don’t want to scroll through 10,000 results — they want the first 20
  • Cost: Every byte transferred costs money at scale (bandwidth, CDN, egress fees)

Offset-Based Pagination (LIMIT/OFFSET)

The simplest approach — skip N rows, then return the next M rows:

  • SQL: SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 40
  • API: GET /posts?page=3&per_page=20
  • Easy to implement, easy to understand, supports jumping to arbitrary pages
  • Problem: The database must still scan and discard the first N rows before returning results

Why OFFSET Is Slow for Large Datasets

  • OFFSET 1000000 means the DB reads 1,000,000 rows, throws them away, then returns the next 20
  • Performance degrades linearly — page 1 is fast, page 50,000 is painfully slow
  • If rows are inserted/deleted between requests, items shift — you see duplicates or miss entries
  • The DB cannot use an index efficiently when it must count rows to skip

Cursor-Based Pagination

Instead of “skip N rows,” use a pointer to the last seen item and fetch the next batch after it:

  • SQL: SELECT * FROM posts WHERE created_at < :cursor ORDER BY created_at DESC LIMIT 20
  • API: GET /posts?after=2024-01-15T10:30:00Z&limit=20
  • The cursor is typically a timestamp, an ID, or an encoded opaque token
  • Performance is constant regardless of how deep into the dataset you are — it’s always an indexed seek
  • Trade-off: You cannot jump to “page 500” — you must traverse sequentially

Keyset Pagination

A specific form of cursor pagination using the sort key columns as the cursor:

  • For unique sort keys: WHERE id > :last_id ORDER BY id LIMIT 20
  • For non-unique sort keys: WHERE (created_at, id) > (:last_time, :last_id) ORDER BY created_at, id LIMIT 20
  • Uses a composite condition to handle ties in the sort column
  • Requires a stable, unique tiebreaker column (usually the primary key)

The Total Count Problem

  • Users expect “Showing 1–20 of 1,234,567 results” but COUNT(*) on large tables is expensive
  • Solutions: Cache the count, show “1,000+ results” with an estimate, or omit total entirely
  • PostgreSQL: SELECT reltuples FROM pg_class WHERE relname = 'posts' for a fast estimate
  • Cursor-based APIs often omit total count and just signal has_next_page: true/false

Infinite Scroll vs Page Numbers

  • Page numbers (Google search): User can jump to any page, requires knowing total pages — pairs with offset pagination
  • Infinite scroll (Twitter, Instagram): Load more as user scrolls down — pairs perfectly with cursor pagination
  • “Load more” button: A hybrid — cursor-based but user-initiated rather than scroll-triggered
Dimension Offset (LIMIT/OFFSET) Cursor-Based Keyset
Performance at Depth Degrades linearly (O(n)) Constant (O(1) seek) Constant (O(1) seek)
Random Page Access Yes — jump to any page No — sequential only No — sequential only
Consistency Duplicates/gaps on insert/delete Stable — no duplicates Stable — no duplicates
Implementation Trivial Moderate (encode cursor) Moderate (composite WHERE)

Python & SQL Examples

import base64
import json
from typing import List, Optional, Tuple
from dataclasses import dataclass


# ═══════════════════════════════════════════════════
# Sample data (simulating database rows)
# ═══════════════════════════════════════════════════

@dataclass
class Post:
    id: int
    title: str
    created_at: str  # ISO timestamp

# Simulated database of 100 posts
POSTS = [
    Post(id=i, title=f"Post #{i}", created_at=f"2024-01-{i:02d}T12:00:00Z")
    for i in range(1, 101)
]


# ═══════════════════════════════════════════════════
# APPROACH 1: Offset-Based Pagination
# ═══════════════════════════════════════════════════

def paginate_offset(page: int, per_page: int = 20) -> dict:
    """
    Classic offset pagination.
    SQL equivalent: SELECT * FROM posts
                    ORDER BY id
                    LIMIT :per_page OFFSET :offset
    """
    offset = (page - 1) * per_page
    # Database scans ALL rows up to offset, then returns per_page
    results = POSTS[offset:offset + per_page]
    total = len(POSTS)

    return {
        "data": [p.__dict__ for p in results],
        "page": page,
        "per_page": per_page,
        "total": total,
        "total_pages": (total + per_page - 1) // per_page,
        "has_next": offset + per_page < total
    }


# ═══════════════════════════════════════════════════
# APPROACH 2: Cursor-Based Pagination
# ═══════════════════════════════════════════════════

def encode_cursor(post_id: int, created_at: str) -> str:
    """Encode cursor as opaque base64 token."""
    payload = json.dumps({"id": post_id, "ts": created_at})
    return base64.b64encode(payload.encode()).decode()

def decode_cursor(cursor: str) -> dict:
    """Decode opaque cursor back to values."""
    payload = base64.b64decode(cursor.encode()).decode()
    return json.loads(payload)

def paginate_cursor(after: Optional[str] = None, limit: int = 20) -> dict:
    """
    Cursor-based pagination using post ID as cursor.
    SQL equivalent: SELECT * FROM posts
                    WHERE id > :cursor_id
                    ORDER BY id
                    LIMIT :limit
    """
    if after:
        cursor_data = decode_cursor(after)
        last_id = cursor_data["id"]
        # Indexed seek — constant time regardless of position
        results = [p for p in POSTS if p.id > last_id][:limit]
    else:
        results = POSTS[:limit]

    # Build next cursor from last item
    next_cursor = None
    if results and len(results) == limit:
        last = results[-1]
        next_cursor = encode_cursor(last.id, last.created_at)

    return {
        "data": [p.__dict__ for p in results],
        "next_cursor": next_cursor,
        "has_next": next_cursor is not None
    }


# ═══════════════════════════════════════════════════
# APPROACH 3: Keyset Pagination (composite key)
# ═══════════════════════════════════════════════════

def paginate_keyset(
    after_ts: Optional[str] = None,
    after_id: Optional[int] = None,
    limit: int = 20
) -> dict:
    """
    Keyset pagination with composite sort (created_at, id).
    SQL equivalent: SELECT * FROM posts
                    WHERE (created_at, id) > (:after_ts, :after_id)
                    ORDER BY created_at, id
                    LIMIT :limit
    """
    if after_ts and after_id:
        results = [
            p for p in POSTS
            if (p.created_at, p.id) > (after_ts, after_id)
        ][:limit]
    else:
        results = POSTS[:limit]

    return {
        "data": [p.__dict__ for p in results],
        "next_after_ts": results[-1].created_at if results else None,
        "next_after_id": results[-1].id if results else None,
        "has_next": len(results) == limit
    }


# ═══════════════════════════════════════════════════
# Demo: Compare approaches
# ═══════════════════════════════════════════════════

print("=== Pagination Strategies ===")
print()

# Offset-based: page 3
print("--- Offset Pagination (page 3) ---")
page3 = paginate_offset(page=3, per_page=5)
print(f"  Items: {[d['id'] for d in page3['data']]}")
print(f"  Total: {page3['total']}, Pages: {page3['total_pages']}")
print()

# Cursor-based: first page, then next page
print("--- Cursor Pagination ---")
first_page = paginate_cursor(limit=5)
print(f"  Page 1: {[d['id'] for d in first_page['data']]}")
print(f"  Next cursor: {first_page['next_cursor'][:20]}...")

second_page = paginate_cursor(after=first_page["next_cursor"], limit=5)
print(f"  Page 2: {[d['id'] for d in second_page['data']]}")
print()

# Keyset: traverse by (created_at, id)
print("--- Keyset Pagination ---")
ks_page1 = paginate_keyset(limit=5)
print(f"  Page 1: {[d['id'] for d in ks_page1['data']]}")

ks_page2 = paginate_keyset(
    after_ts=ks_page1["next_after_ts"],
    after_id=ks_page1["next_after_id"],
    limit=5
)
print(f"  Page 2: {[d['id'] for d in ks_page2['data']]}")

🏭 Industry Practice

GitHub API: Uses cursor-based pagination with opaque after cursors in its GraphQL API. The REST API uses Link headers with rel="next" URLs. GitHub chose cursors because repositories can have thousands of commits/issues where offset pagination would be too slow.

Stripe API: Uses cursor-based pagination with starting_after and ending_before parameters. Each object’s ID serves as the cursor. This provides stable pagination even as new charges/events are created in real-time. Example: GET /v1/charges?limit=25&starting_after=ch_abc123.

Twitter/X API: Uses cursor-based pagination with opaque pagination_token values. The timeline API returns a next_token in each response that encodes the position. This handles the extremely high write rate (thousands of tweets/second) without duplicates or gaps in user timelines.

📋 Key Takeaways

  • Offset pagination is simple but degrades as OFFSET grows — the DB scans and discards all skipped rows
  • Cursor pagination uses a pointer to the last seen item — constant performance at any depth
  • Keyset pagination is cursor pagination using sort column values as the cursor (transparent, not encoded)
  • Use offset for small datasets or admin panels where random page access matters
  • Use cursor for APIs, feeds, infinite scroll, or any dataset over ~10,000 rows
  • Avoid expensive COUNT(*) on large tables — use estimates or omit totals entirely

🧠 Mental Model

Offset is like telling a librarian “skip the first 5,000 books, then give me the next 20.” The librarian must walk past 5,000 shelves every time. Cursor is like leaving a bookmark — “start from this bookmark and give me the next 20.” The librarian goes directly to the bookmark.

  OFFSET PAGINATION (page 5, per_page=20):
  ══════════════════════════════════════════════════════

  Row 1 ─┐
  Row 2  │
  ...    │  ← DB scans and DISCARDS these (OFFSET 80)
  Row 79 │     Cost grows with page number!
  Row 80 ─┘
  Row 81 ─┐
  Row 82  │
  ...    │  ← Returns these 20 rows (LIMIT 20)
  Row 99 │
  Row 100─┘

  SQL: SELECT * FROM posts ORDER BY id LIMIT 20 OFFSET 80


  CURSOR PAGINATION (after=post_80):
  ══════════════════════════════════════════════════════

  [Index] ──► Row 80 (cursor)
                │
                ▼ (direct seek, no scanning!)
  Row 81 ─┐
  Row 82  │
  ...    │  ← Returns these 20 rows immediately
  Row 99 │
  Row 100─┘

  SQL: SELECT * FROM posts WHERE id > 80 ORDER BY id LIMIT 20


  PERFORMANCE COMPARISON:
  ══════════════════════════════════════════════════════

  Page Number:    1    10   100  1000  10000
  Offset Time:   1ms  3ms  20ms 180ms 1800ms  ← linear growth
  Cursor Time:   1ms  1ms  1ms  1ms   1ms     ← constant!

⚠️ Common Mistakes

  • Using OFFSET for infinite scroll: As users scroll deeper, each subsequent page gets slower. After page 500, the query spends most of its time scanning rows it will discard. Switch to cursor-based pagination for any scroll-based UI — performance stays constant at any depth.
  • Non-unique cursors: If your cursor is a timestamp and multiple rows share the same timestamp, you’ll skip or duplicate rows at page boundaries. Always include a unique tiebreaker (usually the primary key) in your cursor: WHERE (created_at, id) > (:ts, :id).
  • Exposing raw database IDs as cursors: If your cursor is just ?after_id=42, clients can guess IDs and enumerate your data. Encode cursors as opaque tokens (base64) so they can’t be manipulated. This also lets you change the underlying implementation without breaking clients.
  • Running COUNT(*) on every paginated request: On a table with 50 million rows, SELECT COUNT(*) FROM posts WHERE active = true can take seconds. Cache the count, use an approximate count, or simply return has_next_page without a total. Most users never navigate past page 5 anyway.

🎯 Exercises

  1. Benchmark offset vs cursor: Create a table with 1 million rows. Query pages 1, 100, 1000, and 10000 using both OFFSET and cursor (WHERE id > X). Measure and graph the query time for each approach. At what page number does OFFSET become unacceptably slow?
  2. Build a cursor-based API: Implement a REST endpoint that returns paginated results with opaque cursors. The response should include data, next_cursor, and has_next. Test it by fetching all pages sequentially and verifying no items are duplicated or skipped even when new rows are inserted mid-pagination.
  3. Handle the consistency problem: Simulate a feed where new items are inserted between paginated requests. Show that offset pagination produces duplicates (same item on page 2 and page 3). Then implement cursor pagination and prove it produces a consistent, gap-free traversal.
  4. Implement total count estimation: For a large table, implement three strategies: exact COUNT(*), cached count (refresh every 60s), and PostgreSQL reltuples estimate. Compare accuracy vs. performance for each. Build an API response that uses the fastest acceptable option based on table size.
