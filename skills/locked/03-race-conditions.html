System Design/ Race Conditions

Race Conditions

When two threads try to change the same data at the same time and chaos ensues — the #1 most common concurrency bug.

Beginner Concept Code
Two People, One Bank Account

Imagine you and your partner both have debit cards for the same bank account with $1,000. At the exact same moment:

  • You check balance: $1,000 — withdraw $800
  • Partner checks balance: $1,000 — withdraw $700

Both see $1,000, both think the withdrawal is safe. Result: $1,500 withdrawn from a $1,000 account. The bank loses money because two operations "raced" against each other.

What Is a Race Condition?

A race condition occurs when program behavior depends on the relative timing of two or more threads. The result is different depending on who "wins the race."

Technical definition: two or more threads access shared data, at least one writes, and there's no synchronization controlling order.

The Classic Example: Counter Increment

counter += 1 looks atomic but is actually THREE steps: READ → ADD → WRITE

import threading

counter = 0

def increment():
    global counter
    for _ in range(100_000):
        counter += 1  # NOT atomic! READ then ADD then WRITE

# Launch 10 threads all incrementing the same counter
threads = [threading.Thread(target=increment) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()

print(f"Expected: 1,000,000")
print(f"Actual:   {counter}")  # Something LESS! e.g. 834,291
Why It Breaks

Thread A reads counter=100, Thread B reads counter=100. Both add 1, both write 101. We lost an increment! This happens thousands of times during a run.

Types of Race Conditions

TypeDescriptionExample
Check-then-actCheck a condition then act on it — but condition changes in betweenif file_exists then read_file (deleted between check and read)
Read-modify-writeRead a value, change it, write back — another thread modifies in betweencounter += 1
Compound operationsMultiple ops that need to be atomic but are notTransfer: debit A then credit B (crash between = money lost)

The Fix: Synchronization

import threading

counter = 0
lock = threading.Lock()

def safe_increment():
    global counter
    for _ in range(100_000):
        with lock:
            counter += 1

threads = [threading.Thread(target=safe_increment) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()
print(f"Result: {counter}")  # Always exactly 1,000,000

Real-World Race Condition: Double-Spending

import threading, time

class BankAccount:
    def __init__(self, balance):
        self.balance = balance
        self.lock = threading.Lock()

    def unsafe_withdraw(self, amount):
        if self.balance >= amount:   # CHECK
            time.sleep(0.001)         # Simulates processing
            self.balance -= amount    # ACT — balance may have changed!
            return True
        return False

    def safe_withdraw(self, amount):
        with self.lock:
            if self.balance >= amount:
                self.balance -= amount
                return True
            return False

account = BankAccount(1000)
threads = [threading.Thread(target=account.unsafe_withdraw, args=(800,)) for _ in range(5)]
for t in threads: t.start()
for t in threads: t.join()
print(f"Balance: ${account.balance}")  # Could be NEGATIVE!

Famous Race Condition Bugs

  • Therac-25 (1985-87) — Radiation machine race condition caused 100x lethal doses. 3 deaths.
  • Northeast Blackout (2003) — Race condition in alarm software hid cascading failures. 55 million lost power.
  • Mars Pathfinder (1997) — Priority inversion race caused spacecraft resets on Mars.

📝 Summary

  • Race condition: outcome depends on thread timing — unpredictable
  • Happens when threads share data without synchronization and at least one writes
  • counter += 1 is NOT atomic — it is read, modify, write (three steps)
  • Fix: use locks, atomic operations, or avoid shared mutable state
  • Check-then-act is the most common race condition pattern

🧠 Mental Model

Thread A: READ(100) ────────── ADD(101) ── WRITE(101) Thread B: READ(100) ── ADD(101) ── WRITE(101) ^ Both read 100, both write 101 = LOST update! WITH LOCK: Thread A: [LOCK] READ(100) ADD(101) WRITE(101) [UNLOCK] Thread B: (waiting...) [LOCK] READ(101)...

❌ Common Beginner Mistakes

  • "It works on my machine" — Race conditions are timing-dependent; may not show in testing but explode in production.
  • Only protecting writes — Reads of shared state need locks too.
  • Using sleep() as synchronization — Never rely on timing for correctness.
  • Locking too little — check-then-act needs BOTH under one lock.

🏋 Hands-On Exercise

  1. Create a shared list. Have 5 threads each append 1000 items. Check the final length.
  2. Fix it with a lock and verify it is always exactly 5000.
  3. Create a bank transfer that debits one account and credits another. Show money loss without locks.
  4. Fix it to be atomic (both operations inside one lock).
