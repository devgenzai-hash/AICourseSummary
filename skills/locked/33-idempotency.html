Intermediate Resilience Pattern

Idempotency

Designing operations that can be safely retried without causing unintended side effects — the cornerstone of reliable distributed systems.

💡 Real-World Analogy

Think of pressing an elevator button. No matter how many times you press it — once, twice, or fifty times in frustration — the elevator is only called once. The result is the same regardless of how many times the operation is performed. That’s idempotency: repeated applications produce the same outcome as a single application.

What Is Idempotency?

An operation is idempotent if performing it multiple times has the same effect as performing it once. Mathematically: f(f(x)) = f(x). In distributed systems, this property is critical because networks are unreliable — requests can be duplicated, retried, or delivered out of order.

Why Idempotency Matters

Consider a payment API. A client sends a “charge $50” request but the response times out. Did the charge go through? The client has no way to know. Without idempotency, retrying could charge the customer twice. With idempotency, the retry is safe — the system recognizes it as a duplicate and returns the original result.

HTTP Methods and Idempotency

The HTTP specification defines idempotency expectations for each method:

HTTP Method Idempotent? Safe? Explanation
GET Yes Yes Reading data never changes state
PUT Yes No Sets resource to a specific state; repeating is harmless
DELETE Yes No Deleting an already-deleted resource is a no-op
POST No No Creates new resources; duplicates cause multiple creations
PATCH Not guaranteed No Depends on the patch operation (increment vs set)

Implementing Idempotent APIs

Idempotency Keys

The most common approach is using idempotency keys — unique client-generated tokens sent with each request. The server stores the key and its result; if the same key arrives again, the stored result is returned without re-executing the operation.

import uuid
import time
from typing import Dict, Any, Optional

class IdempotencyStore:
    """Stores idempotency keys and their results."""

    def __init__(self, ttl_seconds: int = 86400):
        self._store: Dict[str, dict] = {}
        self._ttl = ttl_seconds

    def get(self, key: str) -> Optional[dict]:
        """Retrieve stored result for an idempotency key."""
        entry = self._store.get(key)
        if entry and time.time() - entry["created_at"] < self._ttl:
            return entry["result"]
        return None

    def store(self, key: str, result: dict) -> None:
        """Store the result of an operation."""
        self._store[key] = {
            "result": result,
            "created_at": time.time()
        }

# Usage in a payment endpoint
idempotency_store = IdempotencyStore()

def process_payment(idempotency_key: str, amount: float, customer_id: str) -> dict:
    # Check if we already processed this request
    existing = idempotency_store.get(idempotency_key)
    if existing:
        return existing  # Return cached result

    # Process the payment (side effect happens only once)
    result = {
        "payment_id": str(uuid.uuid4()),
        "amount": amount,
        "customer_id": customer_id,
        "status": "completed"
    }

    # Store result before returning
    idempotency_store.store(idempotency_key, result)
    return result

Database-Level Idempotency with UPSERT

For database operations, UPSERT (INSERT ... ON CONFLICT UPDATE) and unique constraints provide idempotency at the storage layer:

import sqlite3

def upsert_user_balance(conn: sqlite3.Connection, user_id: str, balance: float):
    """Set user balance idempotently — safe to retry."""
    conn.execute("""
        INSERT INTO accounts (user_id, balance, updated_at)
        VALUES (?, ?, CURRENT_TIMESTAMP)
        ON CONFLICT(user_id)
        DO UPDATE SET balance = excluded.balance,
                      updated_at = CURRENT_TIMESTAMP
    """, (user_id, balance))
    conn.commit()

def idempotent_create_order(conn: sqlite3.Connection, order_id: str, items: list):
    """Create order using client-generated ID as natural idempotency key."""
    try:
        conn.execute("""
            INSERT INTO orders (order_id, items, status)
            VALUES (?, ?, 'pending')
        """, (order_id, str(items)))
        conn.commit()
        return {"order_id": order_id, "status": "created"}
    except sqlite3.IntegrityError:
        # Duplicate — return existing order
        row = conn.execute(
            "SELECT order_id, status FROM orders WHERE order_id = ?",
            (order_id,)
        ).fetchone()
        return {"order_id": row[0], "status": row[1]}

Idempotent vs Non-Idempotent Operations

Operation Type Idempotent Example Non-Idempotent Example
Assignment balance = 100 balance += 50
Database UPDATE SET x = 5 UPDATE SET x = x + 1
File system Write entire file contents Append to file
API PUT /users/123 {name: "Alice"} POST /emails/send
Queue Set message as processed Increment retry counter

🏭 Industry Practice

Stripe uses idempotency keys extensively. Every mutating API call accepts an Idempotency-Key header. Keys are stored for 24 hours. If a request with the same key arrives, Stripe returns the cached response — even if it was an error. This makes their payment API safe to retry on network failures without risking double charges.

AWS uses client tokens for idempotent EC2 instance launches. Calling RunInstances with the same client token within 48 hours returns the same instance IDs without launching new ones.

📋 Key Takeaways

  • Idempotent operations produce the same result regardless of how many times they execute
  • Idempotency keys are client-generated tokens that identify unique requests
  • GET, PUT, and DELETE are inherently idempotent; POST typically is not
  • Database UPSERT and unique constraints provide storage-level idempotency
  • Always store the result alongside the key to return consistent responses on retries
  • Set a TTL on idempotency records to prevent unbounded storage growth

🧠 Mental Model

Think of idempotency as a checkpoint system. Before executing, check if you’ve been here before. If yes, return the saved result. If no, execute, save, and return.

Request arrives with Key "abc-123"
        │
        ▼
┌─────────────────────┐
│  Key exists in DB?  │
└─────────────────────┘
     │           │
    YES          NO
     │           │
     ▼           ▼
┌─────────┐  ┌──────────────┐
│ Return  │  │ Execute op   │
│ cached  │  │ Store result │
│ result  │  │ Return result│
└─────────┘  └──────────────┘

⚠️ Common Mistakes

  • Using server-generated keys: The client must generate the idempotency key — otherwise retries after timeout create new keys each time, defeating the purpose.
  • Not handling concurrent duplicates: Two identical requests arriving simultaneously can both pass the “key not found” check. Use database locks or compare-and-swap to prevent this race condition.
  • Ignoring partial failures: If an operation fails midway, storing the error as the cached result means retries will always return the error. Distinguish between retryable and permanent failures.
  • No TTL on stored keys: Without expiration, idempotency storage grows forever. Set a reasonable TTL (e.g., 24–48 hours) based on your retry window.

🎯 Exercises

  1. Build an idempotent transfer API: Implement a money transfer endpoint that accepts an idempotency key. Verify that calling it three times with the same key only moves money once.
  2. Handle concurrent duplicates: Modify your implementation to handle two simultaneous requests with the same idempotency key using database-level locking.
  3. Design TTL cleanup: Add a background process that expires old idempotency records. Test that expired keys allow re-execution.
  4. Convert a non-idempotent endpoint: Take a POST /notifications/send endpoint and redesign it to be idempotent using a combination of idempotency keys and deduplication.
