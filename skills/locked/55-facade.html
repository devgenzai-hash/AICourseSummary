Facade

Providing a simple unified interface to a complex subsystem — hiding internal complexity behind one easy-to-use entry point.

💡 Real-World Analogy

Think of a hotel concierge. You want dinner, a taxi, and theater tickets. Instead of calling the restaurant, the cab company, and the box office yourself, you tell the concierge what you need — one person handles all three services behind the scenes. You don’t deal with each service separately, you don’t need to know their phone numbers or booking protocols. The concierge is the facade — a single, simple interface to a complex set of subsystems.

What Is the Facade Pattern?

  • Intent: Provide a unified interface to a set of interfaces in a subsystem — making the subsystem easier to use
  • Classification: Structural pattern (GoF) — controls how classes and objects are composed
  • Key principle: Simplification through abstraction — hide complexity, expose simplicity
  • Coupling reduction: Clients depend only on the facade, not on dozens of subsystem classes
  • Not restrictive: The facade doesn’t prevent direct subsystem access — it provides a convenient shortcut

When to Use Facade

  • Wrapping complex libraries: When a third-party library has dozens of classes but you only need a subset of functionality
  • Simplifying microservice calls: One facade method orchestrates calls to multiple services (inventory + payment + shipping)
  • Legacy system integration: Hide messy legacy APIs behind a clean modern interface
  • Layer boundaries: Each architectural layer exposes a facade to the layer above
  • Reducing compile dependencies: Clients import only the facade, not the entire subsystem

Facade vs Adapter vs Proxy

Aspect Facade Adapter Proxy
Purpose Simplify a complex subsystem Convert one interface to another Control access to an object
Scope Wraps an entire subsystem Wraps a single class/interface Wraps a single object
Interface Defines a new simplified interface Matches an existing target interface Same interface as the wrapped object
Client knows? May not know subsystem exists Knows the target interface Thinks it’s talking to the real object
Direction Simplifies (many → one) Converts (incompatible → compatible) Controls (add checks/lazy load)

Order Processing Facade — Orchestrating Subsystems

from dataclasses import dataclass
from typing import List


# ═══════════════════════════════════════════════════
# SUBSYSTEM 1: Inventory Management
# ═══════════════════════════════════════════════════

class InventoryService:
    """Complex inventory subsystem with many methods."""

    def __init__(self):
        self._stock = {"LAPTOP": 10, "MOUSE": 50, "KEYBOARD": 30}

    def check_availability(self, item_id: str, qty: int) -> bool:
        available = self._stock.get(item_id, 0) >= qty
        print(f"  [Inventory] {item_id}: {'available' if available else 'OUT OF STOCK'}")
        return available

    def reserve_item(self, item_id: str, qty: int) -> str:
        self._stock[item_id] -= qty
        reservation_id = f"RES-{item_id}-{qty}"
        print(f"  [Inventory] Reserved {qty}x {item_id} → {reservation_id}")
        return reservation_id

    def release_reservation(self, reservation_id: str) -> None:
        print(f"  [Inventory] Released reservation {reservation_id}")


# ═══════════════════════════════════════════════════
# SUBSYSTEM 2: Payment Processing
# ═══════════════════════════════════════════════════

class PaymentService:
    """Complex payment subsystem — fraud checks, authorization, capture."""

    def validate_card(self, card_number: str) -> bool:
        valid = len(card_number) == 16
        print(f"  [Payment] Card validation: {'PASS' if valid else 'FAIL'}")
        return valid

    def authorize_payment(self, amount: float, card: str) -> str:
        auth_code = f"AUTH-{int(amount)}"
        print(f"  [Payment] Authorized ${amount:.2f} → {auth_code}")
        return auth_code

    def capture_payment(self, auth_code: str) -> str:
        txn_id = f"TXN-{auth_code}"
        print(f"  [Payment] Captured {auth_code} → {txn_id}")
        return txn_id

    def refund(self, txn_id: str) -> None:
        print(f"  [Payment] Refunded {txn_id}")


# ═══════════════════════════════════════════════════
# SUBSYSTEM 3: Shipping
# ═══════════════════════════════════════════════════

class ShippingService:
    """Complex shipping subsystem — rates, labels, tracking."""

    def calculate_shipping(self, item_id: str, address: str) -> float:
        rate = 9.99
        print(f"  [Shipping] Rate for {item_id} → ${rate}")
        return rate

    def create_shipment(self, item_id: str, address: str) -> str:
        tracking = f"TRACK-{item_id[:4]}"
        print(f"  [Shipping] Shipment created → {tracking}")
        return tracking


# ═══════════════════════════════════════════════════
# THE FACADE — One simple method for the client
# ═══════════════════════════════════════════════════

@dataclass
class OrderResult:
    success: bool
    order_id: str
    tracking: str
    message: str


class OrderFacade:
    """Facade — simplifies the entire order process into one call."""

    def __init__(self):
        self._inventory = InventoryService()
        self._payment = PaymentService()
        self._shipping = ShippingService()

    def place_order(self, item_id: str, qty: int,
                     card: str, address: str) -> OrderResult:
        """One method to rule them all — orchestrates the entire flow."""

        # Step 1: Check inventory
        if not self._inventory.check_availability(item_id, qty):
            return OrderResult(False, "", "", "Item out of stock")

        # Step 2: Reserve item
        reservation = self._inventory.reserve_item(item_id, qty)

        # Step 3: Validate and charge payment
        if not self._payment.validate_card(card):
            self._inventory.release_reservation(reservation)
            return OrderResult(False, "", "", "Invalid card")

        shipping_cost = self._shipping.calculate_shipping(item_id, address)
        total = qty * 99.99 + shipping_cost

        auth = self._payment.authorize_payment(total, card)
        txn = self._payment.capture_payment(auth)

        # Step 4: Ship it
        tracking = self._shipping.create_shipment(item_id, address)

        order_id = f"ORD-{txn}"
        return OrderResult(True, order_id, tracking, "Order placed!")


# ═══════════════════════════════════════════════════
# Client code — blissfully simple
# ═══════════════════════════════════════════════════

facade = OrderFacade()
print("=== Place Order via Facade ===")
result = facade.place_order(
    item_id="LAPTOP",
    qty=1,
    card="4111111111111111",
    address="123 Main St"
)
print(f"\nResult: {result}")

Home Theater Facade — Classic Example

# ═══════════════════════════════════════════════════
# Complex subsystem classes
# ═══════════════════════════════════════════════════

class Amplifier:
    def on(self): print("  Amplifier ON")
    def set_volume(self, level: int): print(f"  Amplifier volume → {level}")
    def set_surround(self): print("  Amplifier surround mode")
    def off(self): print("  Amplifier OFF")

class Projector:
    def on(self): print("  Projector ON")
    def set_input(self, source: str): print(f"  Projector input → {source}")
    def wide_screen(self): print("  Projector widescreen mode")
    def off(self): print("  Projector OFF")

class StreamingPlayer:
    def on(self): print("  StreamingPlayer ON")
    def play(self, movie: str): print(f"  Playing: {movie}")
    def stop(self): print("  StreamingPlayer stopped")
    def off(self): print("  StreamingPlayer OFF")

class Lights:
    def dim(self, level: int): print(f"  Lights dimmed to {level}%")
    def on(self): print("  Lights ON (full)")


# ═══════════════════════════════════════════════════
# The Facade — two simple methods for movie night
# ═══════════════════════════════════════════════════

class HomeTheaterFacade:
    """One-click movie night — hides 10+ subsystem calls."""

    def __init__(self):
        self._amp = Amplifier()
        self._projector = Projector()
        self._player = StreamingPlayer()
        self._lights = Lights()

    def watch_movie(self, movie: str) -> None:
        """Start movie night with one call."""
        print(f"=== Starting Movie: {movie} ===")
        self._lights.dim(10)
        self._projector.on()
        self._projector.set_input("streaming")
        self._projector.wide_screen()
        self._amp.on()
        self._amp.set_surround()
        self._amp.set_volume(7)
        self._player.on()
        self._player.play(movie)

    def end_movie(self) -> None:
        """Shut everything down with one call."""
        print("=== Ending Movie Night ===")
        self._player.stop()
        self._player.off()
        self._amp.off()
        self._projector.off()
        self._lights.on()


# Client — simple!
theater = HomeTheaterFacade()
theater.watch_movie("Inception")
print()
theater.end_movie()

🏭 Industry Practice

AWS SDK (High-Level vs Low-Level): AWS provides both low-level clients (raw API calls with pagination, retries, serialization) and high-level resource objects like s3.Bucket('my-bucket').upload_file('data.csv'). The high-level API is a facade over dozens of low-level operations — multipart uploads, checksums, transfer acceleration — hidden behind one method call.

jQuery as a DOM Facade: Before modern frameworks, jQuery’s $('#id').fadeIn().css({color: 'red'}) was a facade over verbose, browser-inconsistent DOM APIs. Instead of document.getElementById + checking IE quirks + manual animation loops, one clean interface handled it all.

Logging Frameworks: Python’s logging.info("message") is a facade over handlers, formatters, filters, log levels, rotation, and output destinations. You call one method; behind the scenes it routes to files, syslog, email, or monitoring services.

ORMs as Database Facades: Django ORM, SQLAlchemy, and Prisma are facades over raw SQL. User.objects.filter(age__gt=18) hides query building, connection pooling, parameterization, and result mapping. One line replaces dozens of SQL + cursor operations.

📋 Key Takeaways

  • Facade provides a simple interface to a complex subsystem — one entry point, many operations behind it
  • Reduces coupling — clients depend on the facade, not on subsystem internals
  • Does NOT restrict access — power users can still reach subsystem classes directly
  • Different from Adapter (converts interfaces) and Proxy (controls access to one object)
  • Common at layer boundaries — each layer exposes a facade to the layer above
  • Simplest of the structural patterns — if you’re wrapping complexity, you’re probably building a facade

🧠 Mental Model

Think of the facade as a remote control for your entire home theater. The remote has two buttons: “Watch Movie” and “End Movie.” Behind those buttons, it sends IR signals to the projector, amplifier, streaming box, and lights. You could use each device’s own remote, but the facade remote makes the common workflows trivial.

  FACADE PATTERN STRUCTURE:
  ══════════════════════════════════════════════════════

  WITHOUT Facade (client talks to everything):

  ┌──────────┐    ┌─────────────────┐
  │  Client  │───→│ InventoryService │
  │          │───→│ PaymentService   │
  │          │───→│ ShippingService  │
  │          │───→│ NotifyService    │
  │          │───→│ FraudCheck       │
  └──────────┘    └─────────────────┘
  Client must know 5 APIs, handle errors, orchestrate order


  WITH Facade (client talks to one thing):

  ┌──────────┐    ┌─────────────┐    ┌─────────────────┐
  │  Client  │───→│ OrderFacade │───→│ InventoryService │
  │          │    │             │───→│ PaymentService   │
  └──────────┘    │  place_order│───→│ ShippingService  │
   one method     │  cancel     │───→│ NotifyService    │
   one result     │             │───→│ FraudCheck       │
                  └─────────────┘    └─────────────────┘
                  Orchestration hidden inside facade


  FACADE vs ADAPTER vs PROXY:
  ══════════════════════════════════════════════════════

  Facade:   [Client] → [Simple API] → [Complex Subsystem]
            Purpose: Simplify (many → one)

  Adapter:  [Client] → [Expected API] → [Incompatible API]
            Purpose: Convert (interface A → interface B)

  Proxy:    [Client] → [Same API + controls] → [Real Object]
            Purpose: Control access (lazy load, auth, cache)

⚠️ Common Mistakes

  • God facade that does everything: A facade should simplify common workflows, not become a massive class with 50 methods that duplicates the entire subsystem API. If your facade is growing unbounded, split it into multiple focused facades (OrderFacade, ReportFacade, AdminFacade).
  • Hiding too much — no escape hatch: A good facade doesn’t lock clients out of the subsystem. Power users may need direct access for edge cases. Don’t make subsystem classes private/internal unless you’re certain no one will ever need them.
  • Facade with business logic: The facade should orchestrate, not implement. If you’re putting validation rules, calculations, or transformations in the facade, that logic belongs in the subsystem services. The facade just calls them in the right order.
  • Tight coupling inside the facade: If your facade directly instantiates all subsystems in its constructor, it becomes hard to test. Inject dependencies or use a service locator so you can mock subsystems in tests and swap implementations.

🎯 Exercises

  1. Travel booking facade: Build a TravelFacade that orchestrates FlightService, HotelService, and CarRentalService behind a single book_trip(destination, dates, preferences) method. Handle partial failures — if hotel booking fails after flight is booked, roll back the flight reservation.
  2. Cloud deployment facade: Create a DeployFacade that wraps DockerService, KubernetesService, DNSService, and MonitoringService. One deploy(image, env) call should build the image, push to registry, update k8s deployment, configure DNS, and set up alerts.
  3. Facade with dependency injection: Refactor the OrderFacade to accept subsystem instances via its constructor instead of creating them internally. Write unit tests that inject mock services and verify the facade calls them in the correct order with correct arguments.
  4. Layered facades: Design a two-level facade system: a UserFacade that uses an AuthFacade and a ProfileFacade internally. The top-level register_user() calls auth facade for account creation, then profile facade for setup. Demonstrate how facades can compose other facades.
