System Design/ ACID Properties

ACID Properties

The four guarantees every reliable database transaction must provide. ACID is why your bank doesn't lose money when two people transfer at the same time.

Beginner Database Concept
🏠 Daily-Life Analogy: Sending a Package

Imagine you're sending a gift box to a friend. For the delivery to be "ACID compliant," all four things must be true:

  • Atomicity: The package either arrives completely or not at all. No "half the items arrived." If the truck crashes, everything comes back to you.
  • Consistency: The package follows all rules. If you're not allowed to ship liquids, the system rejects your package BEFORE it enters the system.
  • Isolation: Even if 1000 packages are being delivered simultaneously, each one is handled as if it's the only package in the world. Nobody else's package interferes with yours.
  • Durability: Once the delivery is confirmed, it STAYS confirmed. Even if the delivery company's computer crashes, the record of delivery persists.

What Are ACID Properties?

ACID is a set of four properties that guarantee database transactions are processed reliably. If a database is "ACID compliant," it means every transaction (a group of operations) is safe, correct, and won't corrupt your data — even during crashes, power failures, or concurrent access.

A — Atomicity (All or Nothing)

Simple Explanation

A transaction is like a single action — even if it involves multiple steps. Either ALL steps complete successfully, or NONE of them happen. There is no "half-done" state.

Technical Explanation

Atomicity is implemented using a Write-Ahead Log (WAL) or undo log. Before any change is made to the actual data, the database writes the intended changes to a log. If the transaction fails midway, the database reads the log and rolls back (undoes) all partial changes.

# Atomicity Example: Bank Transfer
# Either BOTH operations succeed, or NEITHER happens

import sqlite3

def transfer_money(from_account, to_account, amount):
    conn = sqlite3.connect('bank.db')
    try:
        cursor = conn.cursor()

        # Step 1: Deduct from sender
        cursor.execute(
            "UPDATE accounts SET balance = balance - ? WHERE id = ?",
            (amount, from_account)
        )

        # Step 2: Add to receiver
        cursor.execute(
            "UPDATE accounts SET balance = balance + ? WHERE id = ?",
            (amount, to_account)
        )

        # BOTH succeed → commit (make permanent)
        conn.commit()
        print("Transfer complete!")

    except Exception as e:
        # ANY step fails → rollback (undo everything)
        conn.rollback()
        print(f"Transfer failed, rolled back: {e}")

    finally:
        conn.close()

# Without atomicity: money could be deducted from sender
# but never added to receiver = money vanishes!
Key Insight: Atomicity doesn't mean "fast" or "instant." It means "undoable." The database can take its time, but if anything goes wrong at ANY point, it will cleanly undo all partial work.

C — Consistency (Rules Are Never Broken)

Simple Explanation

The database has rules (constraints). Every transaction must leave the database in a valid state. If a transaction would break a rule, the entire transaction is rejected.

Technical Explanation

Consistency ensures that all defined rules — foreign keys, unique constraints, check constraints, triggers — are satisfied before AND after every transaction. The database validates constraints at commit time.

# Consistency Example: Rules that can never be violated

# Rule: Account balance can NEVER go negative
# Rule: Total money in the system must stay constant

CREATE TABLE accounts (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    balance DECIMAL(10,2) CHECK (balance >= 0)  -- Constraint!
);

-- This transaction FAILS because it violates the constraint:
BEGIN;
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;  -- balance = -500? REJECTED!
ROLLBACK;  -- Automatic — constraint violation

-- Foreign key consistency:
CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),  -- Must reference valid user
    total DECIMAL(10,2)
);

-- This FAILS: can't create order for non-existent user
INSERT INTO orders (user_id, total) VALUES (9999, 50.00);  -- REJECTED!
Don't Confuse: ACID Consistency ≠ CAP Consistency. ACID-C means "database rules are never broken." CAP-C means "all nodes see the same data." Completely different concepts with the same word!

I — Isolation (Transactions Don't Interfere)

Simple Explanation

Even when thousands of transactions run at the same time, each one behaves as if it's the ONLY transaction running. One transaction's half-finished work is invisible to others.

Technical Explanation

Isolation is implemented using locks, MVCC (Multi-Version Concurrency Control), or timestamp ordering. Different isolation levels provide different guarantees (see Topic 40 for deep dive).

# Isolation Problem: Two people buying the last concert ticket

import threading
import sqlite3

# WITHOUT isolation (broken!):
def buy_ticket_unsafe(user):
    conn = sqlite3.connect('tickets.db')
    cursor = conn.cursor()

    # Both threads read: 1 ticket available
    cursor.execute("SELECT count FROM tickets WHERE event='concert'")
    count = cursor.fetchone()[0]

    if count > 0:
        # Both threads think they can buy!
        cursor.execute("UPDATE tickets SET count = count - 1 WHERE event='concert'")
        conn.commit()
        print(f"{user} bought a ticket!")  # OVERSOLD!

# WITH isolation (safe!):
def buy_ticket_safe(user):
    conn = sqlite3.connect('tickets.db', isolation_level='EXCLUSIVE')
    cursor = conn.cursor()

    try:
        # This locks the row — other transactions must wait
        cursor.execute("SELECT count FROM tickets WHERE event='concert' FOR UPDATE")
        count = cursor.fetchone()[0]

        if count > 0:
            cursor.execute("UPDATE tickets SET count = count - 1 WHERE event='concert'")
            conn.commit()
            print(f"{user} bought a ticket!")
        else:
            print(f"{user}: Sorry, sold out!")
    except:
        conn.rollback()

D — Durability (Saved Means Saved Forever)

Simple Explanation

Once a transaction is committed (confirmed), it stays committed — even if the power goes out, the server crashes, or a meteor hits the data center. The data is permanently saved.

Technical Explanation

Durability is implemented by writing committed data to non-volatile storage (disk/SSD) before confirming the commit. Techniques include:

  • Write-Ahead Log (WAL): Write the transaction to a log file on disk BEFORE modifying the data files
  • fsync(): Force the OS to flush data from RAM to disk
  • Replication: Write to multiple machines so even hardware failure can't lose it
# Durability: What happens under the hood

class DurableDatabase:
    """Simplified view of how databases ensure durability"""

    def commit_transaction(self, transaction):
        # Step 1: Write to WAL (Write-Ahead Log) on disk
        self.write_to_wal(transaction)

        # Step 2: fsync — force OS to flush to physical disk
        self.fsync_wal()

        # Step 3: NOW tell the client "committed!"
        # Even if we crash here, the WAL has the data
        return "COMMITTED"

        # Step 4 (background): Apply WAL entries to actual data files
        # This can happen lazily — the WAL IS the source of truth

    def recover_after_crash(self):
        """Called when database restarts after a crash"""
        # Read WAL and replay any committed transactions
        # that weren't yet applied to data files
        wal_entries = self.read_wal()
        for entry in wal_entries:
            if entry.status == "committed":
                self.apply_to_data_files(entry)
            else:
                self.discard(entry)  # Uncommitted = rollback

ACID vs BASE: Two Philosophies

Not every system needs full ACID. Distributed systems often use BASE instead — a more relaxed approach that trades strict consistency for availability and performance.

PropertyACIDBASE
Full NameAtomicity, Consistency, Isolation, DurabilityBasically Available, Soft state, Eventually consistent
Philosophy"Everything must be perfect NOW""Things will be correct EVENTUALLY"
ConsistencyStrict — always correctEventual — correct after some delay

Real-World ACID in Action

# Complete ACID transaction: E-commerce order
import psycopg2

def place_order(user_id, product_id, quantity):
    conn = psycopg2.connect("dbname=shop")
    conn.autocommit = False  # Enable transaction mode

    try:
        cursor = conn.cursor()

        # ISOLATION: Lock the inventory row so no one else can modify it
        cursor.execute(
            "SELECT stock FROM products WHERE id = %s FOR UPDATE",
            (product_id,)
        )
        stock = cursor.fetchone()[0]

        # CONSISTENCY: Check business rules
        if stock < quantity:
            raise ValueError("Not enough stock!")

        # ATOMICITY: All these happen together or not at all
        cursor.execute(
            "UPDATE products SET stock = stock - %s WHERE id = %s",
            (quantity, product_id)
        )
        cursor.execute(
            "INSERT INTO orders (user_id, product_id, qty) VALUES (%s, %s, %s)",
            (user_id, product_id, quantity)
        )
        cursor.execute(
            "UPDATE users SET order_count = order_count + 1 WHERE id = %s",
            (user_id,)
        )

        # DURABILITY: commit writes to WAL on disk before confirming
        conn.commit()
        print("Order placed successfully!")

    except Exception as e:
        # ATOMICITY: Any failure → undo everything
        conn.rollback()
        print(f"Order failed: {e}")

    finally:
        conn.close()
Advanced: Write-Ahead Log (WAL) Deep Dive

The WAL is the secret weapon behind both Atomicity and Durability. Here's how it works step by step:

  1. Before modifying data: Write the intended change to the WAL file on disk.
  2. Call fsync(): Ensure the WAL entry is physically on disk (not in OS buffer).
  3. Modify the actual data pages: Now change the real data (in memory first, then disk later).
  4. On commit: Write a "COMMIT" record to the WAL.
  5. On crash recovery: Replay WAL from last checkpoint. Committed entries get applied. Uncommitted entries get discarded.

This is why PostgreSQL's pg_wal/ directory exists and why you should never delete WAL files manually!

📝 Summary

  • Atomicity: All-or-nothing. Transaction fully completes or fully rolls back.
  • Consistency: All rules/constraints are satisfied after every transaction.
  • Isolation: Concurrent transactions don't see each other's uncommitted work.
  • Durability: Once committed, data survives any failure.
  • ACID is implemented via WAL, locks/MVCC, constraints, and fsync.
  • BASE is the alternative for systems that prioritize availability over strict consistency.
  • ACID-C ≠ CAP-C — they're entirely different concepts.

❌ Common Beginner Mistakes

  • Not using transactions for multi-step operations — If you do step 1 and step 2 as separate queries without a transaction, a crash between them = corrupted data.
  • Confusing ACID-C with CAP-C — ACID consistency = rules enforcement. CAP consistency = all nodes agree. Completely different.
  • Assuming all databases are ACID — MongoDB wasn't fully ACID until v4.0. Redis is not ACID. Know your database!
  • Long-running transactions — Holding locks for minutes (while waiting for user input) blocks everyone else. Keep transactions short!
  • Ignoring isolation levels — Default isolation may not prevent all anomalies. Understand what your level guarantees (see Topic 40).
