Design Patterns → Adapter
Beginner Pattern Design Pattern

Adapter

Making incompatible interfaces work together — a structural pattern that acts as a bridge between two classes that couldn’t otherwise collaborate.

💡 Real-World Analogy

Think of a travel power adapter. Your US laptop charger has a flat two-prong plug, but the European socket expects round pins. You don’t rewire your charger or rebuild the socket — you buy a small adapter that sits between them. The adapter converts one interface (US plug shape) to another (European socket shape) without changing either device. The Adapter pattern does exactly this for code — wrapping one class’s interface so it looks like another interface that clients expect.

What Is the Adapter Pattern?

  • Intent: Convert the interface of a class into another interface that clients expect — making incompatible classes work together
  • Classification: Structural pattern (GoF) — controls how classes are composed
  • Also known as: Wrapper — it wraps an existing class with a new interface
  • Key principle: Neither the client nor the adaptee needs to change — only the adapter knows about both
  • Open/Closed Principle: You can introduce new adapters without modifying existing code

When to Use Adapter

  • Legacy integration: You have working legacy code with an old interface that doesn’t match your new system
  • Third-party libraries: A vendor library has a different method signature than what your code expects
  • Multiple implementations: PayPal, Stripe, and Square all have different APIs but you want one unified payment interface
  • Testing: Adapting a real service interface to a mock/stub for unit tests
  • Migration: Gradually switching from one system to another — the adapter lets both coexist

Object Adapter vs Class Adapter

Object Adapter (Composition)

  • The adapter holds a reference to the adaptee object (composition)
  • Delegates calls to the adaptee, translating method names and parameters
  • More flexible — can adapt any subclass of the adaptee
  • The standard approach in Python (and most languages without multiple inheritance)

Class Adapter (Inheritance)

  • The adapter inherits from both the target interface and the adaptee (multiple inheritance)
  • Overrides methods to translate between interfaces
  • Less flexible — tied to a specific adaptee class, can’t adapt subclasses
  • Possible in Python (supports multiple inheritance) but rarely used in practice
Aspect Object Adapter Class Adapter Facade
Mechanism Composition (has-a) Inheritance (is-a) Composition (has-many)
Adaptee access Through reference Through self (inherited) Multiple subsystems
Flexibility Adapts any subclass Fixed to one class Simplifies interface

Python Implementation — Payment Gateway Adapter

from abc import ABC, abstractmethod
from typing import Dict


# ═══════════════════════════════════════════════════
# Target Interface — what our application expects
# ═══════════════════════════════════════════════════

class PaymentProcessor(ABC):
    """
    Unified payment interface that our app depends on.
    All payment gateways must look like this.
    """

    @abstractmethod
    def charge(self, amount: float, currency: str, token: str) -> Dict:
        """Charge a payment method. Returns transaction result."""
        ...

    @abstractmethod
    def refund(self, transaction_id: str, amount: float) -> Dict:
        """Refund a previous transaction."""
        ...


# ═══════════════════════════════════════════════════
# Adaptee 1 — Stripe's actual API (different interface)
# ═══════════════════════════════════════════════════

class StripeSDK:
    """Third-party Stripe SDK with its own method names."""

    def create_charge(self, amount_cents: int, currency: str,
                      source: str, metadata: Dict = None) -> Dict:
        # Stripe uses cents, not dollars
        print(f"  [Stripe] Charging {amount_cents} cents ({currency})")
        return {
            "id": "ch_stripe_abc123",
            "status": "succeeded",
            "amount": amount_cents,
        }

    def create_refund(self, charge_id: str, amount_cents: int) -> Dict:
        print(f"  [Stripe] Refunding {amount_cents} cents on {charge_id}")
        return {"id": "re_stripe_xyz", "status": "succeeded"}


# ═══════════════════════════════════════════════════
# Adaptee 2 — PayPal's actual API (completely different)
# ═══════════════════════════════════════════════════

class PayPalClient:
    """Third-party PayPal SDK with its own conventions."""

    def send_payment(self, recipient_token: str,
                     amount: str, currency_code: str) -> Dict:
        # PayPal uses string amounts like "19.99"
        print(f"  [PayPal] Sending ${amount} {currency_code}")
        return {
            "payment_id": "PAY-paypal-789",
            "state": "approved",
            "amount": amount,
        }

    def reverse_payment(self, payment_id: str, amount: str) -> Dict:
        print(f"  [PayPal] Reversing ${amount} on {payment_id}")
        return {"refund_id": "REF-paypal-456", "state": "completed"}


# ═══════════════════════════════════════════════════
# Adapter 1 — Makes Stripe look like PaymentProcessor
# ═══════════════════════════════════════════════════

class StripeAdapter(PaymentProcessor):
    """Adapts Stripe SDK to our unified PaymentProcessor interface."""

    def __init__(self, stripe: StripeSDK):
        self._stripe = stripe  # composition — holds reference

    def charge(self, amount: float, currency: str, token: str) -> Dict:
        # Convert dollars to cents (Stripe requirement)
        amount_cents = int(amount * 100)
        result = self._stripe.create_charge(amount_cents, currency, token)
        # Normalize response to our format
        return {
            "transaction_id": result["id"],
            "success": result["status"] == "succeeded",
            "amount": amount,
        }

    def refund(self, transaction_id: str, amount: float) -> Dict:
        amount_cents = int(amount * 100)
        result = self._stripe.create_refund(transaction_id, amount_cents)
        return {
            "refund_id": result["id"],
            "success": result["status"] == "succeeded",
        }


# ═══════════════════════════════════════════════════
# Adapter 2 — Makes PayPal look like PaymentProcessor
# ═══════════════════════════════════════════════════

class PayPalAdapter(PaymentProcessor):
    """Adapts PayPal SDK to our unified PaymentProcessor interface."""

    def __init__(self, paypal: PayPalClient):
        self._paypal = paypal

    def charge(self, amount: float, currency: str, token: str) -> Dict:
        # Convert float to string (PayPal requirement)
        amount_str = f"{amount:.2f}"
        result = self._paypal.send_payment(token, amount_str, currency)
        return {
            "transaction_id": result["payment_id"],
            "success": result["state"] == "approved",
            "amount": amount,
        }

    def refund(self, transaction_id: str, amount: float) -> Dict:
        amount_str = f"{amount:.2f}"
        result = self._paypal.reverse_payment(transaction_id, amount_str)
        return {
            "refund_id": result["refund_id"],
            "success": result["state"] == "completed",
        }


# ═══════════════════════════════════════════════════
# Client code — works with ANY PaymentProcessor
# ═══════════════════════════════════════════════════

def checkout(processor: PaymentProcessor, amount: float, token: str):
    """Client doesn't know or care which gateway is underneath."""
    result = processor.charge(amount, "USD", token)
    print(f"  Result: {result}")
    return result


# Usage — swap gateways without changing client code
print("=== Stripe via Adapter ===")
stripe_processor = StripeAdapter(StripeSDK())
checkout(stripe_processor, 29.99, "tok_visa_123")

print("=== PayPal via Adapter ===")
paypal_processor = PayPalAdapter(PayPalClient())
checkout(paypal_processor, 29.99, "buyer@email.com")

XML to JSON Adapter

import json
from typing import Any, Dict


# ═══════════════════════════════════════════════════
# Legacy system returns XML-like dicts
# ═══════════════════════════════════════════════════

class LegacyXMLService:
    """Old service that returns data in XML-style nested dicts."""

    def get_user_xml(self, user_id: int) -> Dict:
        # Simulates parsed XML structure
        return {
            "root": {
                "@version": "1.0",
                "user": {
                    "@id": str(user_id),
                    "name": {"#text": "Alice Johnson"},
                    "email": {"#text": "alice@example.com"},
                    "role": {"#text": "admin"},
                }
            }
        }


# ═══════════════════════════════════════════════════
# Modern interface our new code expects
# ═══════════════════════════════════════════════════

class UserService(ABC):
    """Modern interface — returns flat JSON-style dicts."""

    @abstractmethod
    def get_user(self, user_id: int) -> Dict[str, Any]:
        ...


# ═══════════════════════════════════════════════════
# Adapter — translates XML structure to JSON
# ═══════════════════════════════════════════════════

class XMLToJSONAdapter(UserService):
    """Adapts the legacy XML service to return flat JSON dicts."""

    def __init__(self, legacy_service: LegacyXMLService):
        self._legacy = legacy_service

    def get_user(self, user_id: int) -> Dict[str, Any]:
        # Get XML-style data from legacy system
        xml_data = self._legacy.get_user_xml(user_id)

        # Transform nested XML structure → flat JSON
        user_node = xml_data["root"]["user"]
        return {
            "id": int(user_node["@id"]),
            "name": user_node["name"]["#text"],
            "email": user_node["email"]["#text"],
            "role": user_node["role"]["#text"],
        }


# Usage
adapter = XMLToJSONAdapter(LegacyXMLService())
user = adapter.get_user(42)
print(json.dumps(user, indent=2))
# {"id": 42, "name": "Alice Johnson", "email": "alice@example.com", "role": "admin"}

🏭 Industry Practice

JDBC Drivers (Java): Every database vendor (MySQL, PostgreSQL, Oracle) has a completely different wire protocol. JDBC drivers are adapters — they implement the standard java.sql.Connection interface while internally speaking each database’s native protocol. Your code just calls connection.executeQuery() regardless of the underlying database.

Python DB-API (PEP 249): Similar to JDBC — libraries like psycopg2, mysql-connector, and sqlite3 all implement the same DB-API interface (connect(), cursor(), execute()). Each is an adapter that makes a different database engine conform to one standard interface.

Cloud Provider SDKs: Libraries like Apache Libcloud adapt AWS, GCP, and Azure APIs into a unified interface. Instead of learning three different APIs for launching VMs, you learn one interface and swap providers via adapter classes.

React Component Wrappers: When using a third-party React component that doesn’t match your prop conventions, you write a wrapper component (adapter) that translates your props into the format the library expects. Same pattern, different language.

📋 Key Takeaways

  • Adapter converts one interface into another — making incompatible classes collaborate without modification
  • Object adapter (composition) is preferred — more flexible and doesn’t require multiple inheritance
  • Neither the client nor the adaptee changes — only the adapter bridges the gap
  • Adapter differs from Facade: adapter converts one interface to another; facade simplifies a complex subsystem
  • Essential for integrating third-party libraries, legacy systems, and multiple vendors behind one interface
  • Follows Open/Closed Principle — add new adapters without modifying existing code

🧠 Mental Model

Think of the Adapter as a translator at a business meeting. The French CEO and the Japanese investor don’t speak each other’s language, but the translator converts messages between them in real-time. Neither person needs to learn a new language — the translator handles the conversion.

  ADAPTER vs FACADE vs DECORATOR:
  ══════════════════════════════════════════════════════

  Adapter:   Interface A  →  Interface B  (convert)
  Facade:    Complex APIs →  Simple API   (simplify)
  Decorator: Interface A  →  Interface A  (enhance)

⚠️ Common Mistakes

  • Adapter doing too much work: An adapter should only translate interfaces — not add business logic, validation, or caching. If your adapter is 200+ lines with complex logic, you’ve built a service, not an adapter. Keep it thin — translate and delegate.
  • Not normalizing error handling: Stripe throws StripeError, PayPal throws PayPalException. If your adapter doesn’t catch and re-raise as a unified exception type, clients still need to know which vendor is underneath, defeating the purpose.
  • Leaking adaptee details: If your adapter returns Stripe’s raw response format or exposes Stripe-specific fields, the client becomes coupled to Stripe. Always normalize the return value to your own domain types.
  • Confusing Adapter with Facade: Adapter makes one interface look like a different expected interface. Facade provides a simpler interface to a complex subsystem. If you’re simplifying rather than converting, you want a Facade, not an Adapter.

🎯 Exercises

  1. Notification Adapter: You have three notification services: TwilioSMS (uses send_sms(phone, body)), SendGridEmail (uses send(to, subject, html)), and SlackWebhook (uses post_message(channel, text)). Create a unified Notifier interface with notify(recipient, message) and write an adapter for each service.
  2. Legacy Database Adapter: A legacy system stores user data as CSV strings: "name,email,role". Your new system expects User dataclass objects. Write an adapter that wraps the legacy CSVDatabase class and returns proper User objects, handling the parsing and type conversion.
  3. Temperature Sensor Adapter: You have two temperature sensor libraries — one returns Fahrenheit floats, the other returns Celsius strings with units (e.g., "23.5°C"). Create a unified TemperatureSensor interface that always returns Kelvin as a float. Write adapters for both.
  4. Test Double Adapter: Take a real HTTP client class with methods like get(url) and post(url, data). Write a MockHTTPAdapter that implements the same interface but returns pre-configured responses from a dictionary. Use it in a unit test to verify your code works without making real HTTP calls.
