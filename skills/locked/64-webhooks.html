Webhooks

Event-driven HTTP callbacks — push notifications for the web

🔔 Real-World Analogy

A doorbell — instead of checking every 5 minutes whether someone is at the door (polling), the visitor presses the bell and you are notified instantly. Webhooks work the same way: the source system rings your endpoint whenever an event occurs, eliminating wasteful repeated checks.

What Are Webhooks?

A webhook is a user-defined HTTP callback — a URL that a service calls (via POST) whenever a specific event happens. The consumer registers the URL once, then receives real-time push notifications without repeatedly asking "has anything changed?"

Webhooks vs Polling

Aspect Polling Webhooks
Direction Consumer pulls from provider Provider pushes to consumer
Latency Up to polling interval (seconds–minutes) Near real-time (sub-second)
Bandwidth Wasted on empty responses Only used when events occur
Complexity Simple — consumer controls timing Consumer must expose a public endpoint
Reliability Consumer retries naturally Provider needs retry & dead-letter logic
Scalability Load grows linearly with subscribers Provider sends only when events fire

Webhook Security — HMAC Signatures

Why Verify?

Any attacker who discovers your endpoint can forge payloads. HMAC (Hash-based Message Authentication Code) signatures let the receiver prove the payload truly originated from the expected sender — without exposing the secret in transit.

How It Works

  1. Provider and consumer share a secret key at registration time
  2. Provider computes HMAC-SHA256(secret, raw_body) and sends it in a header
  3. Consumer recomputes the HMAC over the received body and compares
  4. If they match → authentic; if not → reject with 403

Retry Policies & Reliability

Exponential Backoff

When a delivery fails (timeout or 5xx), the provider should retry with increasing delays — e.g., 1s, 5s, 30s, 2m, 15m, 1h. After exhausting retries, move the event to a dead-letter queue for manual inspection.

Idempotency in Handlers

Because retries can deliver the same event multiple times, webhook handlers must be idempotent. Use a unique event ID (provided in the payload) to deduplicate — store processed IDs and skip duplicates.

Code — Webhook Sender with HMAC

import hmac
import hashlib
import json
import time
import requests

class WebhookSender:
    """Sends webhook events with HMAC-SHA256 signing and retry logic."""

    def __init__(self, secret: str, max_retries: int = 5):
        self.secret = secret.encode("utf-8")
        self.max_retries = max_retries
        self.backoff_factors = [1, 5, 30, 120, 900]

    def _sign(self, payload_bytes: bytes) -> str:
        # Compute HMAC-SHA256 signature over raw body
        signature = hmac.new(self.secret, payload_bytes, hashlib.sha256)
        return "sha256=" + signature.hexdigest()

    def send(self, url: str, event_type: str, data: dict) -> bool:
        # Build the payload with metadata
        payload = {
            "event_id": generate_uuid(),
            "event_type": event_type,
            "timestamp": int(time.time()),
            "data": data,
        }
        body = json.dumps(payload, separators=(",", ":"))
        body_bytes = body.encode("utf-8")
        signature = self._sign(body_bytes)

        headers = {
            "Content-Type": "application/json",
            "X-Webhook-Signature": signature,
            "X-Webhook-Event": event_type,
        }

        for attempt in range(self.max_retries):
            try:
                resp = requests.post(url, data=body_bytes, headers=headers, timeout=10)
                if resp.status_code in (200, 201, 204):
                    return True
            except requests.RequestException:
                pass
            # Exponential backoff before next retry
            time.sleep(self.backoff_factors[attempt])

        return False  # All retries exhausted

Code — Webhook Receiver with Verification

import hmac
import hashlib
from flask import Flask, request, jsonify

app = Flask(__name__)
WEBHOOK_SECRET = "your-shared-secret"
processed_events: set = set()

def verify_signature(payload: bytes, signature: str) -> bool:
    # Recompute and compare in constant time
    expected = "sha256=" + hmac.new(
        WEBHOOK_SECRET.encode("utf-8"),
        payload,
        hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, signature)

@app.route("/webhooks/receive", methods=["POST"])
def handle_webhook():
    # Step 1 — Verify authenticity
    signature = request.headers.get("X-Webhook-Signature", "")
    if not verify_signature(request.data, signature):
        return jsonify({"error": "Invalid signature"}), 403

    # Step 2 — Parse event payload
    event = request.get_json()
    event_id = event.get("event_id")

    # Step 3 — Idempotency check
    if event_id in processed_events:
        return jsonify({"status": "already_processed"}), 200

    # Step 4 — Process the event
    process_event(event)
    processed_events.add(event_id)

    return jsonify({"status": "accepted"}), 200

Reliability Patterns

Dead-Letter Queue

After all retries fail, persist the event in a dead-letter queue. An operator can inspect failures, fix the consumer endpoint, and replay events manually or automatically.

Delivery Guarantees

  • At-least-once — most webhook systems deliver this; duplicates are possible
  • At-most-once — fire-and-forget with no retries (rare, unreliable)
  • Exactly-once — impossible in distributed systems; approximate via idempotency keys

Timestamp & Replay Protection

Include a timestamp in the signed payload. Receivers reject events older than 5 minutes to prevent replay attacks where an attacker resends a captured valid request.

🏭 Industry Examples

  • Stripe — sends payment events (charge.succeeded, invoice.paid) with HMAC-SHA256 signatures; provides a webhook dashboard and auto-disables unhealthy endpoints
  • GitHub — fires webhooks for push, PR, issue events; signs payloads with X-Hub-Signature-256 header
  • Slack Events API — posts events to your server; requires URL verification challenge and request signing
  • Twilio — sends SMS/call status callbacks; validates with request signing using auth token
  • Shopify — notifies merchants of order, product, and cart events with HMAC-SHA256 verification

📋 Summary

  • Webhooks are HTTP POST callbacks triggered by events — push, not pull
  • Always verify authenticity using HMAC signatures with constant-time comparison
  • Implement idempotency — deduplicate using event IDs to handle retries safely
  • Use exponential backoff with dead-letter queues for reliable delivery
  • Reject stale payloads via timestamp validation to prevent replay attacks
  • Design handlers to respond fast (< 5s) and offload processing to background workers

⚠️ Common Mistakes

  • No signature verification — accepting any POST to your endpoint lets attackers inject fake events; always verify HMAC before processing
  • Synchronous heavy processing — doing database writes or API calls inside the handler causes timeouts; acknowledge fast and process in a background queue
  • Ignoring idempotency — retries deliver duplicate events; without deduplication you double-charge customers or send duplicate emails
  • No replay protection — without timestamp validation, an attacker can replay captured valid payloads indefinitely; reject events older than your tolerance window
