Intermediate API Concept

GraphQL

A query language for APIs that gives clients the power to ask for exactly what they need — nothing more, nothing less.

🍴 The Analogy — Buffet vs Fixed Menu

REST is like a fixed menu — you order “Dish #7” and get everything the chef decided to include, whether you want the garnish or not. GraphQL is a buffet — you walk up with your plate and pick exactly the items you want. No more paying for food you won’t eat (over-fetching), no more going back to the counter three times for sides (under-fetching).

Why GraphQL Exists

Facebook created GraphQL in 2012 to solve a mobile performance problem. Their News Feed required data from dozens of REST endpoints — users, posts, comments, likes, media. Each round-trip added latency on slow 3G connections. GraphQL collapsed those requests into a single, precise query.

The Over-Fetching / Under-Fetching Problem

Over-fetching — a GET /users/42 returns 30 fields when you only need name and avatar. Wasted bandwidth, wasted parsing time.

Under-fetching — you need a user’s posts and each post’s comments. REST forces GET /users/42, then GET /users/42/posts, then GET /posts/{id}/comments for each post. Multiple round-trips.

GraphQL solves both — one request, one response, shaped exactly like your query.

Core Concepts

Schema — The Contract

The schema defines every type, field, and relationship available. It’s strongly typed using SDL (Schema Definition Language):

type User {
    id: ID!
    name: String!
    email: String!
    posts: [Post!]!
}

type Post {
    id: ID!
    title: String!
    body: String!
    author: User!
    comments: [Comment!]!
}

type Query {
    user(id: ID!): User
    posts(limit: Int): [Post!]!
}

Queries — Reading Data

Clients describe the shape of the response they want:

query {
    user(id: "42") {
        name
        posts {
            title
            comments {
                body
            }
        }
    }
}

The response mirrors this structure exactly — no extra fields, no missing data.

Mutations — Writing Data

Mutations modify server-side state and return the updated result:

mutation {
    createPost(title: "GraphQL 101", body: "...") {
        id
        title
        author { name }
    }
}

Subscriptions — Real-Time Data

Subscriptions use WebSockets to push updates when data changes:

subscription {
    newComment(postId: "99") {
        body
        author { name }
    }
}

Python Implementation

Schema & Resolvers with Strawberry

import strawberry
from typing import List

@strawberry.type
class User:
    id: str
    name: str
    email: str

@strawberry.type
class Post:
    id: str
    title: str
    body: str
    author: User

@strawberry.type
class Query:
    @strawberry.field
    def user(self, id: str) -> User:
        # In production → fetch from DB
        return User(id=id, name="Alice", email="alice@dev.io")

    @strawberry.field
    def posts(self, limit: int = 10) -> List[Post]:
        return fetch_posts(limit)

schema = strawberry.Schema(query=Query)

Solving N+1 with DataLoader

The N+1 problem — if you query 50 posts and each needs its author, a naive resolver fires 50 separate DB queries. DataLoader batches them into one:

from strawberry.dataloader import DataLoader

async def batch_load_users(user_ids: List[str]) -> List[User]:
    # Single query: SELECT * FROM users WHERE id IN (...)
    users = await db.fetch_users_by_ids(user_ids)
    return [users[uid] for uid in user_ids]

user_loader = DataLoader(load_fn=batch_load_users)

# In resolver — automatically batched
async def resolve_author(self) -> User:
    return await user_loader.load(self.author_id)

Federation — Scaling GraphQL

Apollo Federation lets you split a monolithic schema across multiple services. Each service owns its types, and a gateway composes them into one unified graph:

# Users service
type User @key(fields: "id") {
    id: ID!
    name: String!
}

# Posts service — extends User
extend type User @key(fields: "id") {
    id: ID! @external
    posts: [Post!]!
}

🏞 Industry Usage

  • Facebook — Created GraphQL in 2012; powers the News Feed on mobile
  • GitHub API v4 — Entire public API is GraphQL; REST v3 is legacy
  • Shopify — Storefront API uses GraphQL for flexible e-commerce queries
  • Apollo — Open-source ecosystem — Client, Server, Federation, Studio
  • Hasura — Instant GraphQL APIs over Postgres with real-time subscriptions
  • Netflix — Uses federation to compose 1000+ microservices into one graph

📋 Key Takeaways

  • GraphQL is a query language and runtime — not a database
  • Single endpoint, client-driven data shape — eliminates over/under-fetching
  • Strongly typed schema acts as a contract between frontend and backend
  • DataLoader solves the N+1 problem through automatic batching
  • Federation enables scaling across teams and services
  • Trade-off — caching is harder than REST; complexity cost is real

🧠 Mental Model

Think of GraphQL as a typed, composable SQL for your API. The schema is your DDL, queries are your SELECT statements, mutations are INSERT/UPDATE, and the resolver layer is your query engine that knows how to fetch data from any backing service.

⚠️ Common Mistakes

  1. Ignoring the N+1 problem — Without DataLoader or batching, nested queries explode into hundreds of DB calls. Always profile resolver execution.
  2. Exposing the entire database schema — GraphQL schemas should model the domain, not mirror table structure. Design for client use-cases.
  3. No query depth/complexity limits — Malicious clients can craft deeply nested queries that DOS your server. Set max depth (e.g., 7) and complexity scoring.
  4. Treating mutations like REST POST — Mutations should be named actions (publishPost) not generic CRUD. Model the intent, not the operation.

💻 Exercises

  1. Schema Design — Design a GraphQL schema for a Twitter clone with users, tweets, likes, and followers. Include queries for a user’s timeline and a single tweet with its like count.
  2. DataLoader Implementation — Given a posts query returning 100 posts each with an author field, implement a DataLoader that batches author lookups into a single SQL query.
  3. Security Hardening — Add query depth limiting (max 5), complexity analysis (max cost 1000), and persisted queries to a GraphQL server. Test with a malicious nested query.
  4. REST-to-GraphQL Migration — Take three related REST endpoints (/users, /users/:id/posts, /posts/:id/comments) and wrap them behind a single GraphQL schema using resolvers that call the existing REST APIs.
