System Design/ Deadlocks

Deadlocks

When two or more threads are stuck waiting for each other forever — like two cars meeting on a one-lane bridge, neither willing to back up.

Beginner Concept Code
The Dining Philosophers Problem

Imagine 5 philosophers sitting at a round table with 5 forks (one between each pair). To eat, each needs TWO forks.

  • Everyone picks up their LEFT fork at the same time
  • Everyone waits for their RIGHT fork... which their neighbor is holding
  • Nobody can eat. Nobody will put down their fork. Everyone starves.

This is a deadlock. Each person holds one resource and waits for another that someone else holds.

What Is a Deadlock?

A deadlock occurs when two or more threads are each waiting for a resource held by one of the others. Nobody can proceed. The program hangs forever.

The Four Conditions (ALL must be true for deadlock)

ConditionMeaningBreak it to prevent deadlock
Mutual ExclusionResources can only be held by one threadUse sharable resources where possible
Hold and WaitThread holds one resource while waiting for anotherAcquire all resources at once or none
No PreemptionResources cannot be forcibly taken awayAllow timeouts or forced release
Circular WaitA cycle: A waits for B, B waits for AOrder your lock acquisition!

Classic Deadlock Example

import threading, time

lock_a = threading.Lock()
lock_b = threading.Lock()

def thread_1():
    with lock_a:
        print("T1 holds A, waiting for B...")
        time.sleep(0.1)
        with lock_b:  # BLOCKED — T2 holds B!
            print("T1 got both")

def thread_2():
    with lock_b:
        print("T2 holds B, waiting for A...")
        time.sleep(0.1)
        with lock_a:  # BLOCKED — T1 holds A!
            print("T2 got both")

# DEADLOCK: T1 has A wants B, T2 has B wants A
t1 = threading.Thread(target=thread_1)
t2 = threading.Thread(target=thread_2)
t1.start(); t2.start()
t1.join(); t2.join()  # Hangs forever!

Prevention: Lock Ordering

# FIX: Always acquire locks in the SAME order (A before B)
def thread_1_fixed():
    with lock_a:
        with lock_b:
            print("T1 got both safely")

def thread_2_fixed():
    with lock_a:  # Same order as T1! A then B
        with lock_b:
            print("T2 got both safely")

Prevention: Timeout-Based

def thread_with_timeout():
    acquired_a = lock_a.acquire(timeout=1.0)
    if not acquired_a:
        return  # Give up, try later
    try:
        acquired_b = lock_b.acquire(timeout=1.0)
        if not acquired_b:
            return  # Release A and back off
        try:
            # Do work with both locks
            pass
        finally:
            lock_b.release()
    finally:
        lock_a.release()

Deadlock Detection

import threading

# Python's faulthandler can dump threads stuck in deadlock
import faulthandler
faulthandler.enable()
# If program hangs, press Ctrl+C to see thread tracebacks
# In production: use watchdog timers and thread dumps

Real-World Deadlock Stories

  • Databases — PostgreSQL, MySQL detect deadlocks automatically and kill one transaction (victim selection).
  • Operating Systems — Resource Allocation Graphs detect cycles = deadlock.
  • Kubernetes — Pod scheduling deadlocks when resources are over-committed.
  • Microservices — Distributed deadlock: Service A calls B, B calls A, both timeout.

📝 Summary

  • Deadlock: threads permanently stuck waiting for each other's resources
  • Requires ALL four conditions: mutual exclusion, hold-and-wait, no preemption, circular wait
  • Prevention #1: Always acquire locks in the SAME global order
  • Prevention #2: Use timeouts — give up and retry if lock not acquired in time
  • Prevention #3: Acquire all needed locks at once (atomically)
  • Detection: thread dumps, watchdog timers, database deadlock detectors

🧠 Mental Model

DEADLOCK CYCLE: Thread 1: holds [Lock A] --wants--> [Lock B] ^ | | v Thread 2: holds [Lock B] --wants--> [Lock A] Both wait forever. CIRCULAR DEPENDENCY. FIX (ordered acquisition): Thread 1: acquire A, then B --> gets both Thread 2: acquire A, then B --> waits for A, gets both after T1 releases

❌ Common Beginner Mistakes

  • Inconsistent lock ordering — Thread 1 takes A then B; Thread 2 takes B then A. Always use same order!
  • Holding locks across I/O — Network calls while holding locks dramatically increases deadlock risk.
  • Nested locks without planning — Each new nested lock is a deadlock opportunity.
  • No timeout strategy — Without timeouts, deadlocks hang forever silently.

🏋 Hands-On Exercise

  1. Create a deadlock with two threads and two locks. Observe the hang.
  2. Fix it using consistent lock ordering.
  3. Implement a transfer function between two bank accounts using lock ordering (always lock lower account ID first).
  4. Add deadlock detection: a watchdog thread that prints warning if main thread is stuck for > 5 seconds.
