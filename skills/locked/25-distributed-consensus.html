System Design/ Distributed Consensus

Distributed Consensus

Getting multiple nodes to agree on one value even when some machines fail or messages arrive late. The hardest problem in distributed systems.

Advanced Concept Distributed
🏠 Daily-Life Analogy: Planning Dinner with Friends Over Text

You and 4 friends are trying to decide where to eat tonight — but you can only communicate via text messages (no group call).

  • Messages can be delayed (someone's phone has bad signal)
  • Someone might have their phone off (crashed node)
  • Two people might suggest different restaurants at the same time

You need a protocol: someone proposes a restaurant, everyone votes, and once a majority agrees (3 out of 5), that's final — even if the other 2 haven't responded yet.

That's distributed consensus: getting a majority to agree on a single value despite delays, failures, and conflicting proposals.

What Is Distributed Consensus?

Consensus means all (or a majority of) nodes in a distributed system agree on the same value. This is needed for:

  • Leader election (who is the leader?)
  • Replicated state machines (what's the next log entry?)
  • Distributed transactions (commit or abort?)
  • Configuration changes (what's the current cluster membership?)

The Three Properties of Consensus

PropertyMeaningPlain English
AgreementAll non-faulty nodes decide the same valueEveryone who responds gives the same answer
ValidityThe decided value was actually proposed by someoneThe answer must be one of the options on the table
TerminationEvery non-faulty node eventually decidesWe don't wait forever — a decision IS made

The FLP Impossibility Result

Fischer-Lynch-Paterson (1985): In an asynchronous system where even ONE node can crash, it is mathematically impossible to guarantee consensus will always be reached. This is a proven theorem.

So how do real systems work? They use timeouts to assume when a node has failed (making the system partially synchronous). This makes consensus possible in practice, just not guaranteed in 100% of edge cases.

Raft Consensus (Understandable by Design)

Raft was designed in 2014 specifically to be understandable (unlike Paxos). It's the most widely used consensus algorithm in modern systems.

Raft's Core Idea: Replicated Log

All nodes maintain a log of commands. The leader appends entries to the log and replicates them to followers. Once a majority has the entry, it's committed.

from enum import Enum
from dataclasses import dataclass
from typing import List, Optional

class NodeState(Enum):
    FOLLOWER = "follower"
    CANDIDATE = "candidate"
    LEADER = "leader"

@dataclass
class LogEntry:
    term: int           # Which election term this was created in
    command: str        # The actual command (e.g., "SET x = 5")
    committed: bool = False

class RaftNode:
    """Simplified Raft consensus node"""

    def __init__(self, node_id, cluster_size):
        self.id = node_id
        self.state = NodeState.FOLLOWER
        self.current_term = 0
        self.log: List[LogEntry] = []
        self.commit_index = -1     # Last committed entry
        self.cluster_size = cluster_size
        self.votes_received = 0
        self.next_index = {}        # For leader: next log index to send to each follower

    def client_request(self, command):
        """Client sends a command — only leader can handle this"""
        if self.state != NodeState.LEADER:
            return "ERROR: Not the leader. Redirect to leader."

        # Step 1: Append to local log
        entry = LogEntry(term=self.current_term, command=command)
        self.log.append(entry)
        print(f"Leader: Appended '{command}' at index {len(self.log)-1}")

        # Step 2: Replicate to followers (send AppendEntries RPC)
        acks = self._replicate_to_followers(entry)

        # Step 3: If majority acknowledges, commit
        majority = (self.cluster_size // 2) + 1
        if acks >= majority:
            entry.committed = True
            self.commit_index = len(self.log) - 1
            print(f"Leader: Committed '{command}' (got {acks}/{self.cluster_size} acks)")
            return f"SUCCESS: '{command}' committed"
        else:
            print(f"Leader: Cannot commit — only {acks}/{majority} acks")
            return "ERROR: Could not reach majority"

    def _replicate_to_followers(self, entry):
        """Send AppendEntries to all followers, count acks"""
        acks = 1  # Leader counts itself
        # In real Raft: parallel RPCs to all followers
        # Each follower appends to their log and responds
        for i in range(self.cluster_size - 1):
            # Simulate: follower accepts and appends
            acks += 1  # In reality, might timeout or fail
        return acks

    def receive_append_entries(self, leader_term, entries, leader_commit):
        """Follower receives log entries from leader"""
        if leader_term < self.current_term:
            return False  # Reject — stale leader

        # Accept the leader's authority
        self.current_term = leader_term
        self.state = NodeState.FOLLOWER

        # Append new entries to our log
        for entry in entries:
            self.log.append(entry)

        # Update commit index
        if leader_commit > self.commit_index:
            self.commit_index = min(leader_commit, len(self.log) - 1)

        return True  # ACK — entry replicated


# Demo
leader = RaftNode(1, cluster_size=5)
leader.state = NodeState.LEADER
leader.current_term = 1

# Client sends commands
leader.client_request("SET x = 10")
leader.client_request("SET y = 20")
print(f"\nLeader's log: {[(e.command, e.committed) for e in leader.log]}")

Paxos: The Original (But Hard to Understand)

Paxos (by Leslie Lamport, 1989) was the first proven consensus algorithm. It's correct but notoriously difficult to implement. Raft is essentially "Paxos made understandable."

FeaturePaxosRaft
Designed forCorrectness proofUnderstandability
LeaderAny proposer can leadSingle strong leader

Membership changesComplexBuilt-in (joint consensus)
ImplementationsGoogle Chubby, Spanneretcd, Consul, CockroachDB
DifficultyVery hard to implement correctlyHard but more approachable

Two-Phase Commit (2PC) — Simple But Fragile

2PC is the simplest consensus protocol — used for distributed transactions (not replication).

class TwoPhaseCoordinator:
    """Coordinator for Two-Phase Commit"""

    def __init__(self, participants):
        self.participants = participants  # List of database nodes

    def execute_transaction(self, transaction):
        # PHASE 1: PREPARE (ask everyone if they CAN commit)
        print("Phase 1: Sending PREPARE to all participants...")
        votes = []
        for p in self.participants:
            vote = p.prepare(transaction)  # "YES I can commit" or "NO"
            votes.append(vote)
            print(f"  {p.name} votes: {vote}")

        # PHASE 2: COMMIT or ABORT
        if all(votes):
            # Everyone said YES → COMMIT
            print("Phase 2: All voted YES → sending COMMIT")
            for p in self.participants:
                p.commit(transaction)
            return "COMMITTED"
        else:
            # Someone said NO → ABORT everyone
            print("Phase 2: Someone voted NO → sending ABORT")
            for p in self.participants:
                p.abort(transaction)
            return "ABORTED"

class Participant:
    def __init__(self, name):
        self.name = name

    def prepare(self, transaction):
        # Check: can I execute this? Do I have resources?
        return True  # YES, I can commit

    def commit(self, transaction):
        print(f"  {self.name}: COMMITTED ✓")

    def abort(self, transaction):
        print(f"  {self.name}: ABORTED ✗")

# Demo
participants = [Participant("DB-East"), Participant("DB-West"), Participant("DB-EU")]
coordinator = TwoPhaseCoordinator(participants)
coordinator.execute_transaction("Transfer $100")
2PC's Fatal Flaw: If the coordinator crashes AFTER sending PREPARE but BEFORE sending COMMIT/ABORT, all participants are stuck in limbo forever — they've locked their resources but don't know whether to commit or abort. This is why 2PC is called a "blocking protocol."

Three-Phase Commit (3PC) — Attempt to Fix 2PC

3PC adds a "pre-commit" phase to prevent the blocking problem. However, it's still vulnerable to network partitions and is rarely used in practice.

Consensus in Production

Who Uses What

  • etcd (Raft) — Kubernetes' brain. Stores all cluster state. Every kubectl command goes through Raft consensus.
  • Consul (Raft) — HashiCorp's service mesh. Service discovery and config stored via Raft.
  • Zookeeper (ZAB) — Kafka's coordinator. Uses Zookeeper Atomic Broadcast (similar to Raft).
  • Google Spanner (Paxos) — Globally distributed SQL database. Each shard uses Paxos for replication.
  • CockroachDB (Raft) — Distributed SQL. Each range (chunk of data) has its own Raft group.
  • TiDB (Raft) — Uses Raft for distributed transactions and replication.

Why Odd Numbers of Nodes?

Consensus clusters should have odd numbers of nodes (3, 5, 7). Here's why:

Cluster SizeMajority NeededCan Tolerate FailuresNotes
3 nodes21 failureMinimum production setup
4 nodes31 failureSame tolerance as 3! Wastes a node.
5 nodes32 failuresCommon production choice
7 nodes43 failuresHigh-availability requirement

📝 Summary

  • Distributed consensus = getting multiple nodes to agree on one value despite failures
  • FLP theorem: consensus is impossible to guarantee in fully asynchronous systems
  • Raft: understandable consensus via strong leader, log replication, majority commits
  • Paxos: correct but complex; used by Google internally
  • 2PC: simple but blocking — coordinator crash = stuck participants
  • Use odd cluster sizes (3, 5, 7) to maximize fault tolerance
  • In practice: use etcd/Consul/Zookeeper — don't implement consensus yourself

🧠 Mental Model

Raft Consensus (normal operation): Client: "SET x = 5" │ ▼ [Leader] ──AppendEntries──→ [Follower 1] ✓ ACK │ ──AppendEntries──→ [Follower 2] ✓ ACK │ ──AppendEntries──→ [Follower 3] ✗ (slow/down) │ ──AppendEntries──→ [Follower 4] ✓ ACK │ ▼ Got 4/5 acks (majority = 3) → COMMITTED! Apply "SET x = 5" to state machine Reply to client: "OK" Key insight: We don't need ALL nodes — just majority. That's why it tolerates failures!

❌ Common Beginner Mistakes

  • Implementing consensus yourself — This is one of the hardest problems in CS. Use etcd, Consul, or Zookeeper unless you're writing a database.
  • Confusing consensus with leader election — Leader election IS a consensus problem, but consensus is broader (any agreed-upon value).
  • Using 2PC for everything — 2PC blocks on coordinator failure. Use Saga pattern (Topic 32) for long-running distributed transactions.
  • Even-numbered clusters — 4 nodes tolerates the same failures as 3 but costs more. Always use odd numbers.
  • Ignoring network latency — Consensus requires round-trips. Across continents, each commit adds 100-300ms latency.
