Intermediate Resilience Pattern

Throttling

Controlling the rate at which work is processed by delaying or degrading responses — keeping systems alive under pressure rather than rejecting requests outright.

💡 Real-World Analogy

Think of speed bumps on a road. They don’t stop you from driving — they slow you down. A rate limiter is like a roadblock that says “road closed, turn around” (hard reject). Throttling is the speed bump that says “you can keep going, but you’ll do it at 20 mph instead of 60.” During a traffic jam, you might also get routed to a smaller road (degraded service) rather than being told to go home entirely.

Throttling vs Rate Limiting

These two concepts are often confused, but they serve different purposes and behave differently under load:

Aspect Rate Limiting Throttling
Response to excess Hard reject (HTTP 429) Slow down, queue, or degrade
Client experience Error — must retry later Slower but still gets a response
Goal Enforce strict quotas Maintain system stability
Scope Per-client or per-API-key System-wide or per-priority-class
Trigger Client exceeds their quota System load exceeds capacity
Data loss Requests are dropped Requests are delayed or degraded

Throttling Strategies

1. Queue-Based Throttling

Excess requests are placed in a queue and processed at a controlled rate. Callers block until their request is served or a timeout expires.

2. Priority-Based Throttling

Assign priority classes to requests. Under load, low-priority requests are delayed or dropped while high-priority ones proceed normally.

3. Graceful Degradation

Instead of full responses, return cheaper approximations — cached data, lower resolution, fewer results — to reduce per-request cost.

4. Adaptive Throttling

Dynamically adjust the processing rate based on real-time system metrics (CPU, memory, queue depth, latency percentiles).

Queue-Based Throttler

A throttler that queues incoming requests and releases them at a controlled rate using an asyncio semaphore and delay:

import asyncio
import time
from collections import deque

class Throttler:
    """Queue-based throttler that delays excess requests.

    Instead of rejecting requests, queues them and
    processes at a controlled rate (requests_per_second).
    """

    def __init__(self, requests_per_second: float,
                 max_queue_size: int = 100):
        self._interval = 1.0 / requests_per_second
        self._max_queue = max_queue_size
        self._semaphore = asyncio.Semaphore(1)
        self._last_release = 0.0
        self._queue_depth = 0

    async def acquire(self, timeout: float = 30.0) -> bool:
        """Wait for permission to proceed.

        Returns True if acquired within timeout,
        False if queue is full or timeout expired.
        """
        if self._queue_depth >= self._max_queue:
            return False  # Queue full — shed load

        self._queue_depth += 1
        try:
            async with asyncio.timeout(timeout):
                async with self._semaphore:
                    now = time.monotonic()
                    wait = self._last_release + self._interval - now
                    if wait > 0:
                        await asyncio.sleep(wait)
                    self._last_release = time.monotonic()
                    return True
        except asyncio.TimeoutError:
            return False
        finally:
            self._queue_depth -= 1

    @property
    def queue_depth(self) -> int:
        return self._queue_depth


# Usage: 10 requests per second with queue of 50
throttler = Throttler(requests_per_second=10, max_queue_size=50)

async def handle_request(request_id: int):
    allowed = await throttler.acquire(timeout=5.0)
    if allowed:
        print(f"Request {request_id}: processed")
    else:
        print(f"Request {request_id}: timed out in queue")

Priority Queue Throttling

Under load, not all requests are equal. Payment processing should take precedence over analytics. Priority throttling ensures critical work proceeds while less important work is delayed:

import asyncio
import heapq
import time
from dataclasses import dataclass, field
from enum import IntEnum

class Priority(IntEnum):
    CRITICAL = 0   # Payment, auth
    HIGH = 1       # User-facing reads
    NORMAL = 2     # Standard operations
    LOW = 3        # Background jobs, analytics

@dataclass(order=True)
class PrioritizedRequest:
    priority: int
    timestamp: float = field(compare=True)
    future: asyncio.Future = field(compare=False)

class PriorityThrottler:
    """Throttler that processes higher-priority requests first.

    Under load, LOW priority requests may be delayed
    significantly or dropped when queue is full.
    """

    def __init__(self, requests_per_second: float,
                 max_queue: int = 200):
        self._interval = 1.0 / requests_per_second
        self._max_queue = max_queue
        self._heap: list = []
        self._processing = False
        self._loop = None

    async def submit(self, priority: Priority,
                       timeout: float = 30.0) -> bool:
        """Submit a request with given priority.

        Returns True when the request is allowed to proceed.
        Returns False on timeout or queue overflow.
        """
        if len(self._heap) >= self._max_queue:
            return False

        loop = asyncio.get_event_loop()
        future = loop.create_future()
        entry = PrioritizedRequest(
            priority=priority,
            timestamp=time.monotonic(),
            future=future
        )
        heapq.heappush(self._heap, entry)

        if not self._processing:
            asyncio.create_task(self._process_queue())

        try:
            async with asyncio.timeout(timeout):
                return await future
        except asyncio.TimeoutError:
            return False

    async def _process_queue(self):
        self._processing = True
        while self._heap:
            entry = heapq.heappop(self._heap)
            if not entry.future.done():
                entry.future.set_result(True)
            await asyncio.sleep(self._interval)
        self._processing = False


# Critical requests processed first, LOW waits longest
pt = PriorityThrottler(requests_per_second=50)

async def payment_handler():
    await pt.submit(Priority.CRITICAL)
    # Process payment...

async def analytics_handler():
    await pt.submit(Priority.LOW)
    # Log analytics event...

Adaptive Throttling

Static throttle rates are fragile — they’re either too aggressive (waste capacity) or too lenient (don’t protect under spikes). Adaptive throttling adjusts the rate based on real-time system health:

import time
import threading

class AdaptiveThrottler:
    """Adjusts throttle rate based on system load.

    Monitors a load metric (0.0 to 1.0) and scales
    the allowed request rate between min and max.
    Above critical_load, only essential requests pass.
    """

    def __init__(self, min_rps: float = 10,
                 max_rps: float = 1000,
                 critical_load: float = 0.9):
        self._min_rps = min_rps
        self._max_rps = max_rps
        self._critical_load = critical_load
        self._current_load = 0.0
        self._lock = threading.Lock()

    def update_load(self, load: float):
        """Update current system load (0.0 to 1.0).

        Call this periodically from a health monitor.
        """
        with self._lock:
            self._current_load = max(0.0, min(1.0, load))

    @property
    def current_rate(self) -> float:
        """Current allowed requests per second."""
        with self._lock:
            load = self._current_load
        # Linear interpolation: high load → low rate
        rate = self._max_rps - (
            load * (self._max_rps - self._min_rps)
        )
        return max(self._min_rps, rate)

    @property
    def is_critical(self) -> bool:
        with self._lock:
            return self._current_load >= self._critical_load

    def should_allow(self, is_essential: bool = False) -> bool:
        """Decide whether to allow a request.

        Essential requests pass even under critical load.
        Non-essential requests are probabilistically shed.
        """
        if is_essential:
            return True
        if self.is_critical:
            return False  # Only essential traffic

        import random
        with self._lock:
            load = self._current_load
        # Probabilistic shedding: higher load → more drops
        accept_probability = 1.0 - (load * 0.8)
        return random.random() < accept_probability


# Example: monitor feeds load every second
throttler = AdaptiveThrottler(
    min_rps=10, max_rps=500, critical_load=0.85
)

# Simulated load spike
throttler.update_load(0.3)   # Normal: ~350 rps allowed
throttler.update_load(0.7)   # High: ~157 rps allowed
throttler.update_load(0.9)   # Critical: essential only

Graceful Degradation Strategies

When throttling, you can offer reduced functionality rather than just slowing down:

Load Level Strategy Example
Normal (0-50%) Full service All features, fresh data, full results
Elevated (50-70%) Reduced freshness Serve from cache even if slightly stale
High (70-85%) Feature shedding Disable recommendations, autocomplete, previews
Critical (85-95%) Essential only Only auth, payments, core reads
Emergency (>95%) Static fallback Serve static error page from CDN

🏭 Industry Practice

AWS API Throttling: Returns HTTP 429 “Too Many Requests” with exponential backoff guidance. AWS services use token bucket internally — each API has a bucket rate (steady-state) and burst capacity. DynamoDB throttles per-partition when provisioned capacity is exceeded.

YouTube Video Quality: Classic graceful degradation. Under bandwidth pressure, video resolution drops from 4K → 1080p → 720p → 480p. The service continues (you still watch the video) but at reduced quality. The client doesn’t get an error — just a degraded experience.

CDN Throttling (Cloudflare/Akamai): Edge servers throttle origin requests during traffic spikes. They serve stale cache entries and batch multiple client requests into a single origin fetch (request coalescing), protecting backend servers from collapse.

Netflix: Uses priority-based throttling extensively. During peak hours, background operations (recommendations recomputation, A/B test logging) are throttled to preserve capacity for stream playback — the one thing users absolutely cannot tolerate failing.

📋 Key Takeaways

  • Throttling slows or degrades; rate limiting hard-rejects — use both together for defense in depth
  • Queue-based throttling delays requests but preserves them; clients get responses, just slower
  • Priority throttling ensures critical operations (payments, auth) always proceed under load
  • Adaptive throttling adjusts dynamically based on CPU, memory, queue depth, or latency
  • Graceful degradation offers reduced functionality instead of complete failure
  • Always set queue size limits and timeouts — unbounded queues lead to memory exhaustion

🧠 Mental Model

Rate limiting is a bouncer at the door (you’re in or out). Throttling is the highway traffic management system — speed limits drop during congestion, HOV lanes prioritize carpools, and when it’s really bad, on-ramp signals meter traffic one car at a time. Everyone eventually gets through, just slower.

⚠️ Common Mistakes

  • Unbounded queues in throttlers: Without a max queue size, a sustained traffic spike fills memory until the process OOMs. Always set a queue limit and return 503 when the queue is full — a bounded delay is acceptable, infinite queueing is not.
  • Throttling without priority differentiation: Treating all requests equally means a surge of analytics events can delay payment processing. Always classify requests by business impact and throttle low-priority work first.
  • Static throttle rates that never adapt: A fixed “100 rps” throttle wastes capacity when the system is healthy and doesn’t protect enough when hardware degrades. Monitor actual system metrics and adjust rates dynamically.
  • Confusing throttling with backpressure: Throttling is proactive (you slow down before failure). Backpressure is reactive (downstream signals it’s overwhelmed). Use throttling at entry points and backpressure between internal services for complete protection.

🎯 Exercises

  1. Build a queue-based throttler: Implement the async Throttler class. Send 100 concurrent requests to it configured at 10 rps. Verify requests are spaced ~100ms apart and measure total time to process all 100.
  2. Priority throttling under load: Create a PriorityThrottler with 4 priority levels. Simulate a traffic spike with 80% LOW requests and 20% CRITICAL. Verify CRITICAL requests complete within 100ms while LOW waits seconds.
  3. Adaptive throttler with health metrics: Build an AdaptiveThrottler that reads CPU usage (use psutil). Run a CPU-intensive workload and verify the throttler reduces allowed rate as CPU climbs above thresholds.
  4. Graceful degradation middleware: Build a FastAPI middleware that returns full responses when load is low, cached responses at medium load, and a minimal static response at critical load. Simulate load with concurrent requests.
