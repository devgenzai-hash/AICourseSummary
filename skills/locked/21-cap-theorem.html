System Design/ CAP Theorem

CAP Theorem

You can only pick two out of three: Consistency, Availability, and Partition Tolerance. Every distributed system must choose which trade-off to live with.

Advanced Concept Distributed
🏠 Daily-Life Analogy: The Phone Game Between Friends

Imagine you have three friends in different cities. They all share one bank account and need to know the balance at all times.

Consistency: All three friends always see the same balance. If one spends $50, the others instantly know.

Availability: Any friend can check or spend from the account at any time — the "bank" never says "system down, come back later."

Partition Tolerance: Even when phone lines between cities go down (network partition), the system still works somehow.

Here's the catch: you can't have all three perfectly at the same time. If the phone line goes down (partition happens), you must choose:

  • Option A (CP): Freeze the account until communication is restored. Everyone sees the same balance (consistent), but some friends can't access it (not available).
  • Option B (AP): Let everyone keep spending independently. Everyone can access it (available), but balances might not match (not consistent).

What Is the CAP Theorem?

The CAP theorem (also called Brewer's Theorem, proposed by Eric Brewer in 2000) states that a distributed data system can only guarantee two out of three properties simultaneously:

PropertySimple MeaningTechnical Definition
ConsistencyEveryone sees the same data at the same timeEvery read receives the most recent write or an error. All nodes return the same value for the same query at any point in time.
AvailabilityThe system always responds — never says "I'm busy"Every request receives a (non-error) response, without guarantee that it contains the most recent write.
Partition ToleranceThe system survives when network connections breakThe system continues to operate despite arbitrary message loss or failure of part of the network.

Why You Can't Have All Three

In any real distributed system, network partitions WILL happen. Cables get cut. Data centers lose connectivity. This means Partition Tolerance is not optional — it's a requirement. So the real choice is:

The Real Choice: When a network partition occurs, do you sacrifice Consistency (AP) or Availability (CP)? You MUST pick one.

CP System (Consistency + Partition Tolerance)

When a partition happens, the system refuses to serve requests that might return stale data. It waits until communication is restored.

  • Behavior: Returns errors or timeouts during partition rather than stale data
  • Use when: Correctness is critical (bank transfers, inventory counts, leader election)
  • Examples: MongoDB (in strong consistency mode), HBase, Zookeeper, etcd, Redis (with WAIT command)

AP System (Availability + Partition Tolerance)

When a partition happens, the system keeps serving requests but different nodes might return different (stale) data.

  • Behavior: Always returns data, but it might be outdated during partitions
  • Use when: Uptime is critical, eventual consistency is acceptable (social feeds, DNS, shopping carts)
  • Examples: Cassandra, DynamoDB, CouchDB, DNS

CA System (Consistency + Availability) — Only Without Partitions

A system that gives both C and A but can't handle network partitions. This is essentially a single-node system (like a traditional SQL database on one machine).

  • Behavior: Perfect consistency and availability, but crashes entirely if there's a network issue
  • Examples: Single-node PostgreSQL, single-node MySQL (technically not "distributed")

CAP in Practice: The Spectrum

Real systems don't fit neatly into CP or AP boxes. They exist on a spectrum and often let you configure the trade-off per operation.

# Example: Cassandra lets you tune consistency per query
# This is how you choose CP vs AP at the query level

from cassandra.cluster import Cluster
from cassandra import ConsistencyLevel

cluster = Cluster(['node1', 'node2', 'node3'])
session = cluster.connect('my_keyspace')

# AP mode: Read from ANY node (fast, might be stale)
stmt = session.prepare("SELECT * FROM users WHERE id = ?")
stmt.consistency_level = ConsistencyLevel.ONE  # Just one node needs to respond
result = session.execute(stmt, [user_id])

# CP mode: Read from QUORUM (majority must agree — consistent but slower)
stmt.consistency_level = ConsistencyLevel.QUORUM  # Majority of nodes must respond
result = session.execute(stmt, [user_id])

# Strongest CP: ALL nodes must respond (slowest, most consistent)
stmt.consistency_level = ConsistencyLevel.ALL
result = session.execute(stmt, [user_id])

PACELC: The Extended CAP Theorem

CAP only talks about what happens during a partition. But what about when things are normal? That's where PACELC comes in:

PACELC: If there's a Partition, choose Availability or Consistency. Else (normal operation), choose Latency or Consistency.

This is more practical because even without partitions, you still face a trade-off between response speed and data freshness:

  • PA/EL (DynamoDB, Cassandra): During partition → Available. Normal time → Low Latency. (Sacrifice consistency both times)
  • PC/EC (MongoDB strong mode, Zookeeper): During partition → Consistent. Normal time → Consistent. (Sacrifice availability/latency both times)
  • PA/EC (Some configs): During partition → Available. Normal time → Consistent. (Best of both worlds but complex)
# PACELC decision matrix in code
class PACELCDecision:
    def __init__(self, system_name):
        self.system = system_name

    def during_partition(self, prefer):
        """During network partition: choose 'availability' or 'consistency'"""
        if prefer == "availability":
            return "Serve stale data, fix later (AP)"
        return "Reject requests until partition heals (CP)"

    def normal_operation(self, prefer):
        """No partition: choose 'latency' or 'consistency'"""
        if prefer == "latency":
            return "Read from nearest replica (fast, maybe stale)"
        return "Read from leader/quorum (slower, always fresh)"

# Example decisions
dynamo = PACELCDecision("DynamoDB")
print(dynamo.during_partition("availability"))  # PA
print(dynamo.normal_operation("latency"))       # EL

zookeeper = PACELCDecision("Zookeeper")
print(zookeeper.during_partition("consistency"))  # PC
print(zookeeper.normal_operation("consistency"))  # EC

Common Misconceptions About CAP

Myth 1: "CAP means you permanently give up one property."
Reality: You only lose one property during a partition. When the network is healthy, you can have all three.
Myth 2: "Consistency in CAP = ACID consistency."
Reality: CAP consistency means "all nodes see the same data at the same time" (linearizability). ACID consistency means "the database moves from one valid state to another" (integrity constraints). They're different concepts.
Myth 3: "You must choose CP or AP for the entire system."
Reality: Different parts of your system can make different choices. Your payment service might be CP while your recommendation service is AP.

Implementing CAP Trade-offs in Code

import time
import random

class DistributedStore:
    """Simulates a distributed key-value store with CAP trade-offs"""

    def __init__(self, mode="ap"):
        self.mode = mode  # "cp" or "ap"
        self.nodes = {
            "node1": {},
            "node2": {},
            "node3": {},
        }
        self.partition_active = False

    def write(self, key, value):
        """Write to the store — behavior depends on CAP mode"""
        if self.partition_active:
            if self.mode == "cp":
                # CP: Refuse write if we can't reach all nodes
                raise Exception("Write rejected: cannot guarantee consistency during partition")
            else:
                # AP: Write to reachable nodes only (might create inconsistency)
                reachable = self._get_reachable_nodes()
                for node in reachable:
                    self.nodes[node][key] = value
                return f"Written to {len(reachable)} nodes (may be inconsistent)"
        else:
            # No partition: write to all nodes (both C and A satisfied)
            for node in self.nodes:
                self.nodes[node][key] = value
            return "Written to all nodes successfully"

    def read(self, key):
        """Read from the store — behavior depends on CAP mode"""
        if self.partition_active:
            if self.mode == "cp":
                # CP: Refuse read if we can't verify consistency
                raise Exception("Read rejected: cannot guarantee consistency during partition")
            else:
                # AP: Return whatever data we have (might be stale)
                reachable = self._get_reachable_nodes()
                node = reachable[0]
                return self.nodes[node].get(key, None)
        else:
            # No partition: read from any node (all are consistent)
            return self.nodes["node1"].get(key, None)

    def _get_reachable_nodes(self):
        # Simulate: during partition, only some nodes are reachable
        return ["node1"]  # Only one node reachable

    def simulate_partition(self):
        self.partition_active = True
        print("⚡ Network partition! Nodes can't talk to each other.")

    def heal_partition(self):
        self.partition_active = False
        # Sync all nodes (anti-entropy repair)
        master_data = self.nodes["node1"]
        for node in self.nodes:
            self.nodes[node] = dict(master_data)
        print("✅ Partition healed. Nodes synchronized.")

# Demo: CP System
cp_store = DistributedStore(mode="cp")
cp_store.write("balance", 1000)
cp_store.simulate_partition()
try:
    cp_store.read("balance")  # FAILS — CP refuses during partition
except Exception as e:
    print(f"CP response: {e}")

# Demo: AP System
ap_store = DistributedStore(mode="ap")
ap_store.write("balance", 1000)
ap_store.simulate_partition()
result = ap_store.read("balance")  # WORKS — might be stale though
print(f"AP response: {result}")  # Returns 1000 (could be outdated)

Advanced: Formal Proof of CAP Impossibility

The proof is surprisingly simple:

  1. Assume we have two nodes (N1, N2) with a network partition between them.
  2. A client writes value V1 to N1.
  3. Another client reads from N2.
  4. Since N1 can't communicate with N2 (partition), N2 doesn't know about V1.
  5. N2 must either: (a) return stale data (violates Consistency) or (b) refuse to respond (violates Availability).

This proves that during a partition, you cannot simultaneously guarantee both Consistency and Availability. QED.

📝 Summary

  • CAP = Consistency + Availability + Partition Tolerance — pick any 2
  • Since partitions are unavoidable in distributed systems, the real choice is CP vs AP
  • CP systems refuse to serve during partitions (guarantee correct answers)
  • AP systems always serve but might give stale data during partitions
  • PACELC extends CAP: what trade-off do you make when there IS no partition?
  • Most real systems are tunable — you choose per operation, not per system
  • CAP consistency ≠ ACID consistency — don't confuse them

🧠 Mental Model

Network Partition Happens: ┌─────────┐ ✂️ BROKEN ✂️ ┌─────────┐ │ Node A │ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ │ Node B │ │ data: X │ │ data: ? │ └─────────┘ └─────────┘ CP Choice: "Sorry, can't serve you until I verify with Node A" AP Choice: "Here's what I have — might be wrong but at least you get an answer" Rule of thumb: - Money/inventory/elections → CP (wrong answer = disaster) - Social feeds/analytics/caches → AP (slow answer = disaster)

❌ Common Beginner Mistakes

  • Thinking CAP is binary — It's a spectrum. Systems can be "mostly CP" with AP fallbacks for certain operations.
  • Ignoring PACELC — CAP only matters during failures. Most of the time your system is healthy — the latency vs consistency trade-off matters more day-to-day.
  • Choosing AP for everything — "Eventual consistency" sounds easy until you have to resolve conflicts (last-write-wins can lose data).
  • Confusing CAP-C with ACID-C — They're completely different concepts with the same name.
  • Thinking single-machine databases have CAP trade-offs — CAP only applies to distributed (multi-node) systems.
