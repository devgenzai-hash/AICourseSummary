System Design/ Read-Write Locks

Read-Write Locks

Allow multiple readers simultaneously but only one writer at a time. Perfect when reads vastly outnumber writes (which is most systems!).

Intermediate Pattern Code
A Library Reading Room

A library reading room with a special book:

  • Many people can read the book simultaneously (readers don't conflict)
  • But when someone needs to edit/update the book, everyone else must leave the room
  • While the editor works, no readers are allowed in
  • Once done editing, readers can come back in

Why Read-Write Locks?

A regular mutex blocks everyone — even readers who could safely run together. Read-write locks (RWLock) exploit the fact that concurrent reads are safe.

ScenarioRegular LockRead-Write Lock
5 readers, 0 writersSequential (slow)All 5 simultaneous (fast!)
1 writer workingOthers waitOthers wait (same)
95% reads, 5% writesAll sequential95% concurrent!
 
import threading
import time

class ReadWriteLock:
    def __init__(self):
        self._readers = 0
        self._lock = threading.Lock()
        self._write_lock = threading.Lock()

    def acquire_read(self):
        with self._lock:
            self._readers += 1
            if self._readers == 1:
                self._write_lock.acquire()  # First reader blocks writers

    def release_read(self):
        with self._lock:
            self._readers -= 1
            if self._readers == 0:
                self._write_lock.release()  # Last reader unblocks writers

    def acquire_write(self):
        self._write_lock.acquire()

    def release_write(self):
        self._write_lock.release()

# Usage
rwlock = ReadWriteLock()
cache = {"key": "value"}

def reader(name):
    rwlock.acquire_read()
    try:
        print(f"[{name}] Reading: {cache}")
        time.sleep(0.5)  # Multiple readers here simultaneously!
    finally:
        rwlock.release_read()

def writer(name, value):
    rwlock.acquire_write()
    try:
        cache["key"] = value
        print(f"[{name}] Wrote: {value}")
        time.sleep(0.2)
    finally:
        rwlock.release_write()

Reader vs Writer Priority

Starvation Risk!

Reader-preferring: New readers keep entering → writer waits forever (writer starvation).
Writer-preferring: Waiting writer blocks new readers → readers starve.
Fair: Alternates between readers and writers (most complex).

Industry Usage

  • Database query caches — Many SELECT queries (read) vs occasional UPDATE (write)
  • DNS caches — Millions of lookups (read) vs rare record updates (write)
  • Configuration stores — Read constantly, update occasionally
  • Go sync.RWMutex — Built-in read-write lock, writer-preferring

📝 Summary

  • RWLock: multiple simultaneous readers OR one exclusive writer
  • Huge speedup when reads >> writes (90%+ reads = common case)
  • Writer starvation: continuous readers can block writers forever
  • Writer-preferring locks prevent writer starvation but may slow readers
  • Python: no built-in RWLock (use third-party or implement yourself)
  • Best for: caches, config stores, DNS, any read-heavy shared data

🧠 Mental Model

REGULAR LOCK: R1 | R2 | R3 | W1 | R4 | R5 (all sequential) READ-WRITE LOCK: R1 R2 R3 | W1 | R4 R5 R6 R7 (readers overlap!) ^^^^^^^^ ^^^^^^^^^^^^^ concurrent! concurrent! RULE: Readers: unlimited concurrent (they don't modify) Writer: exclusive access (must be alone)

❌ Common Beginner Mistakes

  • Using RWLock when writes are frequent — If writes are 50%, regular lock may be faster (less overhead).
  • Upgrading read to write — Cannot do: acquire_read() then acquire_write() = deadlock. Must release read first.
  • Not considering starvation — Reader-preferring locks can starve writers in read-heavy workloads.
  • Holding read lock too long — Long reads still block writers. Keep read sections short.

🏋 Hands-On Exercise

  1. Implement a ReadWriteLock. Test with 10 readers and 2 writers.
  2. Show writer starvation: continuous readers that prevent any writer from executing.
  3. Fix it with a writer-preferring variant.
  4. Benchmark: RWLock vs regular Lock with 95% reads / 5% writes. Show the speedup.
