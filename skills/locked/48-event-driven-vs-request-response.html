Intermediate Architecture Concept

Event-Driven vs Request/Response

Two fundamental communication paradigms — one blocks and waits for an answer, the other fires a message and moves on. Choosing the right model determines your system’s coupling, scalability, and failure characteristics.

💡 Real-World Analogy

Think of ordering food at a counter (request/response) — you walk up, place your order, and stand there waiting until the cashier hands you your food. You’re blocked until you get a reply. Now imagine a dinner bell system (event-driven) — you place your order, take a seat, and go about your business. When the food is ready, a bell rings and your number is called. You’re free to do other things in the meantime, and the kitchen processes orders at its own pace without caring whether you’re standing at the counter or sitting across the room.

Request/Response Model

The simplest and most intuitive communication pattern. A client sends a request and synchronously waits for the server to process it and return a response:

  • Synchronous: The caller is blocked until the response arrives (or a timeout occurs)
  • Direct coupling: The client must know exactly which service to call and how to reach it
  • Immediate feedback: Success or failure is known right away
  • Simple mental model: Function call semantics — input in, output out
  • Examples: HTTP REST APIs, gRPC calls, database queries, function invocations

When Request/Response Shines

  • The caller needs the result before it can continue (e.g., fetching user profile for display)
  • Operations that require immediate confirmation (payment processing, authentication)
  • Simple CRUD operations with low latency requirements
  • Internal service calls within a bounded context where coupling is acceptable

Event-Driven Model

Instead of direct calls, services communicate by producing and consuming events. The producer fires an event and moves on without waiting for a response:

  • Asynchronous: The producer doesn’t wait — fire and forget (or fire and eventually confirm)
  • Loose coupling: Producer doesn’t know (or care) who consumes the event
  • Temporal decoupling: Producer and consumer don’t need to be online at the same time
  • Fan-out: One event can trigger actions in multiple consumers simultaneously
  • Examples: Kafka topics, RabbitMQ queues, AWS SNS/SQS, WebSocket notifications

When Event-Driven Shines

  • The producer doesn’t need an immediate answer (e.g., “order placed” → triggers shipping, email, analytics)
  • Multiple systems need to react to the same action (fan-out)
  • Throughput matters more than latency — process millions of events per second
  • Services have different uptime requirements — events buffer during downtime

Pub/Sub Pattern

A specific event-driven pattern where publishers emit events to a topic and subscribers listen on that topic:

  • Publishers don’t know subscribers exist — they just publish to a topic
  • Subscribers register interest in topics and receive all matching events
  • Broker (Kafka, RabbitMQ, Redis Pub/Sub) mediates between publishers and subscribers
  • Adding a new consumer requires zero changes to the publisher

Event Sourcing Basics

Instead of storing current state, you store a sequence of events that led to the current state:

  • Every state change is captured as an immutable event (e.g., OrderCreated, ItemAdded, OrderShipped)
  • Current state is derived by replaying events from the beginning
  • Provides a complete audit trail and enables temporal queries (“what was the state at time T?”)
  • Naturally pairs with event-driven architectures — stored events are also publishable events

Message Brokers & Event Buses

  • Message Queue (RabbitMQ, SQS): Point-to-point — each message consumed by exactly one consumer
  • Event Stream (Kafka, Kinesis): Log-based — events are appended and multiple consumers can read independently
  • Event Bus (EventBridge, NATS): Lightweight routing of events to interested subscribers
  • Key difference: Queues delete messages after consumption; streams retain them for replay
Dimension Request/Response Event-Driven
Coupling Tight — caller knows callee Loose — producer/consumer independent
Latency Low (direct call) Higher (broker in between)
Scalability Limited by callee capacity Horizontal — add more consumers
Failure Handling Immediate error propagation Retry/dead-letter queues, eventual consistency
Debugging Easy — follow the call stack Hard — distributed tracing needed
Data Freshness Always current (synchronous) Eventually consistent
Fan-out Caller must call each service One event, N subscribers automatically
Temporal Coupling Both must be online simultaneously Consumer can process later

Python Examples

import time
import queue
import threading
from typing import Callable, Dict, List, Any


# ═══════════════════════════════════════════════════
# PATTERN 1: Request/Response (Synchronous)
# ═══════════════════════════════════════════════════

class OrderService:
    """Synchronous request/response — caller waits for result."""

    def __init__(self):
        self.orders: Dict[str, dict] = {}

    def create_order(self, user_id: str, items: list) -> dict:
        # Step 1: Validate inventory (synchronous call)
        stock = self._check_inventory(items)
        if not stock["available"]:
            return {"error": "Out of stock"}

        # Step 2: Charge payment (synchronous call)
        payment = self._process_payment(user_id, stock["total"])
        if not payment["success"]:
            return {"error": "Payment failed"}

        # Step 3: Create order (synchronous)
        order_id = f"ORD-{len(self.orders) + 1}"
        self.orders[order_id] = {
            "user_id": user_id,
            "items": items,
            "status": "confirmed"
        }

        # Caller blocked until ALL steps complete
        return {"order_id": order_id, "status": "confirmed"}

    def _check_inventory(self, items: list) -> dict:
        time.sleep(0.05)  # Simulated network call
        return {"available": True, "total": 99.99}

    def _process_payment(self, user_id: str, amount: float) -> dict:
        time.sleep(0.1)  # Simulated payment gateway
        return {"success": True, "tx_id": "TXN-42"}


# ═══════════════════════════════════════════════════
# PATTERN 2: Event-Driven (Asynchronous)
# ═══════════════════════════════════════════════════

class EventBus:
    """Simple in-process event bus for pub/sub communication."""

    def __init__(self):
        self._subscribers: Dict[str, List[Callable]] = {}
        self._event_log: list = []

    def subscribe(self, event_type: str, handler: Callable):
        if event_type not in self._subscribers:
            self._subscribers[event_type] = []
        self._subscribers[event_type].append(handler)

    def publish(self, event_type: str, data: dict):
        """Fire and forget — producer doesn't wait for consumers."""
        event = {"type": event_type, "data": data, "time": time.time()}
        self._event_log.append(event)

        for handler in self._subscribers.get(event_type, []):
            # Each handler runs independently (async in production)
            threading.Thread(target=handler, args=(data,)).start()


class EventDrivenOrderService:
    """Event-driven — publishes events, doesn't wait for downstream."""

    def __init__(self, bus: EventBus):
        self.bus = bus
        self.orders: Dict[str, dict] = {}

    def create_order(self, user_id: str, items: list) -> dict:
        # Create order immediately — don't wait for downstream
        order_id = f"ORD-{len(self.orders) + 1}"
        self.orders[order_id] = {
            "user_id": user_id,
            "items": items,
            "status": "pending"
        }

        # Publish event — consumers react independently
        self.bus.publish("order.created", {
            "order_id": order_id,
            "user_id": user_id,
            "items": items
        })

        # Return immediately — caller is NOT blocked
        return {"order_id": order_id, "status": "pending"}


# ─── Consumers: independent services reacting to events ───

class InventoryConsumer:
    def handle_order_created(self, data: dict):
        print(f"  [Inventory] Reserving stock for {data['order_id']}")
        time.sleep(0.05)

class EmailConsumer:
    def handle_order_created(self, data: dict):
        print(f"  [Email] Sending confirmation for {data['order_id']}")
        time.sleep(0.02)

class AnalyticsConsumer:
    def handle_order_created(self, data: dict):
        print(f"  [Analytics] Tracking event for {data['order_id']}")
        time.sleep(0.01)


# ═══════════════════════════════════════════════════
# Demo: Comparing both approaches
# ═══════════════════════════════════════════════════

print("=== Request/Response vs Event-Driven ===")
print()

# Request/Response — synchronous, blocking
print("--- Request/Response (synchronous) ---")
sync_service = OrderService()
start = time.time()
result = sync_service.create_order("user-1", ["widget", "gadget"])
elapsed = time.time() - start
print(f"  Result: {result}")
print(f"  Time: {elapsed*1000:.0f}ms (blocked entire duration)")
print()

# Event-Driven — asynchronous, non-blocking
print("--- Event-Driven (asynchronous) ---")
bus = EventBus()
inventory = InventoryConsumer()
email = EmailConsumer()
analytics = AnalyticsConsumer()

bus.subscribe("order.created", inventory.handle_order_created)
bus.subscribe("order.created", email.handle_order_created)
bus.subscribe("order.created", analytics.handle_order_created)

async_service = EventDrivenOrderService(bus)
start = time.time()
result = async_service.create_order("user-1", ["widget", "gadget"])
elapsed = time.time() - start
print(f"  Result: {result}")
print(f"  Time: {elapsed*1000:.0f}ms (returned immediately)")
print(f"  (Consumers processing in background...)")
time.sleep(0.2)  # Let background threads finish for demo

🏭 Industry Practice

Apache Kafka: The backbone of event-driven architectures at LinkedIn, Netflix, and Uber. Kafka provides a distributed commit log where events are appended, retained for configurable periods, and consumed by multiple consumer groups independently. A single Kafka cluster can handle millions of events per second with strong ordering guarantees per partition.

AWS SNS/SQS: Amazon’s managed pub/sub (SNS) and message queue (SQS) services. SNS fans out events to multiple SQS queues, Lambda functions, or HTTP endpoints. SQS provides at-least-once delivery with dead-letter queues for failed messages. This pattern powers most serverless event-driven architectures on AWS.

RabbitMQ: A traditional message broker supporting multiple patterns — work queues, pub/sub, routing, and RPC. Used when you need flexible routing rules, priority queues, or message acknowledgment semantics beyond what Kafka provides. Popular in enterprise systems and microservice migrations.

📋 Key Takeaways

  • Request/response is synchronous — the caller blocks until it gets a reply (simple but tightly coupled)
  • Event-driven is asynchronous — the producer fires an event and moves on (loose coupling, higher scalability)
  • Use request/response when you need immediate confirmation or the caller depends on the result
  • Use event-driven when multiple services need to react, or when throughput matters more than latency
  • Most production systems use a hybrid — synchronous for queries, event-driven for commands and side-effects
  • Event-driven adds complexity: eventual consistency, debugging difficulty, and message ordering challenges

🧠 Mental Model

Request/response is a phone call — both parties must be present and engaged simultaneously. Event-driven is a mailbox — the sender drops a letter and walks away; the recipient picks it up whenever they’re ready.

  REQUEST/RESPONSE:
  ══════════════════════════════════════════════════════

  Client ──── request ────►  Server
    │                          │
    │  (blocked, waiting...)   │ (processing...)
    │                          │
    │  ◄──── response ─────   │
    ▼                          ▼
  continues                  done


  EVENT-DRIVEN:
  ══════════════════════════════════════════════════════

  Producer ──── event ────►  [Message Broker]
    │                          │ │ │
    │ (continues immediately)  │ │ └──► Consumer A (email)
    │                          │ └────► Consumer B (analytics)
    ▼                          └──────► Consumer C (inventory)
  does other work
                             (each consumer processes independently)

  User ──► API Gateway ──► Order Service

              ┌───── sync ─────┤───── async ─────┐

              │                │             │  │  │

⚠️ Common Mistakes

  • Using events when you need immediate confirmation: If the user is staring at a screen waiting for “payment successful,” don’t make it event-driven. The payment response must be synchronous. Use events for side-effects (send receipt email, update analytics) that happen after the synchronous confirmation.
  • Ignoring event ordering: Events may arrive out of order across partitions. If you process OrderShipped before OrderCreated, your system breaks. Design consumers to be idempotent and handle out-of-order delivery, or use partition keys to guarantee ordering for related events.
  • Not handling consumer failures: If a consumer crashes mid-processing, the event is lost unless you have acknowledgment and retry mechanisms. Always implement dead-letter queues for events that fail after N retries, and monitor DLQ depth as a critical alert.
  • Building a distributed monolith: If your “event-driven” system has services that can’t function without specific other services processing their events in a specific order, you’ve just built a distributed monolith with extra latency. True event-driven means each consumer is independently deployable and degradable.

🎯 Exercises

  1. Build a hybrid order system: Create an order service that uses synchronous request/response for payment validation but publishes events for downstream actions (shipping, email, analytics). Measure the response time difference vs. a fully synchronous chain that calls all services sequentially.
  2. Implement a dead-letter queue: Build an event consumer that intentionally fails on certain messages. Implement retry logic (3 attempts with exponential backoff) and route failed messages to a dead-letter queue. Build a monitoring dashboard that shows DLQ depth and allows manual replay.
  3. Event ordering challenge: Simulate out-of-order event delivery for an e-commerce system (OrderCreated, ItemAdded, PaymentReceived, OrderShipped). Build a consumer that reconstructs correct order state regardless of arrival order using event timestamps and sequence numbers.
  4. Fan-out performance test: Compare request/response fan-out (service calls 5 downstream services sequentially) vs. event-driven fan-out (publish one event, 5 consumers react in parallel). Measure total latency and throughput under load for both approaches with 1000 requests.
