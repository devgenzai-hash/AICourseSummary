System Design/ Happens-Before Relationship

Happens-Before Relationship

The formal guarantee that one operation's effects are visible to another. Without this, concurrent programs are unpredictable.

Intermediate Concept Theory
Sending a Letter

If you mail a letter (write) and your friend receives it (read), there is a happens-before relationship: you wrote before they read.

But if you both write letters to each other at the same time, there is NO happens-before — neither can see the other's letter. The order is undefined.

In concurrency: if A happens-before B, then B is guaranteed to see everything A did. Without it, B might see stale data.

What Is Happens-Before?

The happens-before relationship is a formal ordering guarantee between operations in different threads. If operation A happens-before operation B, then:

  • All memory writes done by A are visible to B
  • A is guaranteed to have completed before B starts

Rules That Establish Happens-Before

RuleDescriptionExample
Program orderWithin one thread, earlier statements HB later onesx=1; y=2; → x=1 HB y=2
Lock release → acquireUnlock HB next lock of same mutexT1 unlocks → T2 locks = T2 sees T1's writes
Thread startStarting a thread HB that thread's first actiont.start() HB first line in t's run()
Thread joinThread's last action HB join() returnt.join() returns → you see all of t's writes
Volatile write → readWrite to volatile HB subsequent readJava volatile, C++ atomic
TransitivityIf A HB B, and B HB C, then A HB CChain of guarantees

Practical Implications

import threading

shared_data = {}
lock = threading.Lock()

def writer():
    shared_data["result"] = 42
    shared_data["ready"] = True
    lock.release()  # This creates a happens-before edge

def reader():
    lock.acquire()  # Matches writer's release = happens-before!
    # GUARANTEED to see result=42 and ready=True
    assert shared_data["ready"] == True
    assert shared_data["result"] == 42

# Using join() for happens-before
result = [None]

def compute():
    result[0] = heavy_calculation()

t = threading.Thread(target=compute)
t.start()
t.join()  # Everything in compute() happens-before this line
print(result[0])  # Guaranteed to see the computed value

What Has NO Happens-Before?

# DANGER: No synchronization = no happens-before = no guarantee
flag = False
data = 0

def writer_unsafe():
    global data, flag
    data = 42
    flag = True  # No lock, no barrier

def reader_unsafe():
    if flag:  # Might see True...
        print(data)  # But data might still be 0! (reordering/visibility)
    # Without happens-before, seeing flag=True does NOT guarantee data=42

Language Memory Models

  • Java Memory Model (JMM) — Formally defines happens-before for synchronized, volatile, final fields
  • C++ Memory Model — seq_cst (default) provides total ordering; relaxed allows reordering
  • Go Memory Model — Channel send HB channel receive; sync ops establish HB
  • Python — GIL + lock semantics provide implicit HB (but only through proper synchronization)

📝 Summary

  • Happens-before (HB) guarantees one operation's effects are visible to another
  • Without HB, there are NO guarantees about what another thread sees
  • Lock release HB next lock acquire (same lock) — the fundamental rule
  • Thread.join() establishes HB — after join, you see all of that thread's work
  • Transitivity: A HB B, B HB C → A HB C
  • No synchronization = no HB = potential visibility bugs

🧠 Mental Model

HAPPENS-BEFORE CHAIN: T1: write(x=42) → release(lock) ↓ (happens-before) T2: acquire(lock) → read(x) ← sees 42! NO HAPPENS-BEFORE: T1: write(x=42) T2: read(x) ← might see 0 or 42. UNDEFINED!

❌ Common Beginner Mistakes

  • Assuming sequential consistency — Without sync, operations can appear in any order to other threads.
  • Flag-based signaling without barriers — Setting a boolean flag without a lock does NOT guarantee visibility.
  • Confusing program order with global order — Within YOUR thread, order is preserved. Across threads, anything goes.
  • Thinking "it works in testing" — x86 has strong ordering that hides bugs. ARM/production may expose them.

🏋 Hands-On Exercise

  1. Identify all happens-before relationships in a producer-consumer with locks.
  2. Show code where flag=True is set by thread A, but thread B reads flag=True and still sees stale data.
  3. Fix it with proper synchronization (lock or Event).
  4. Draw a happens-before graph for a 3-thread scenario with two shared locks.
