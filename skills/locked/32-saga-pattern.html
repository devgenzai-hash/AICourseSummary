System Design/ Saga Pattern

Saga Pattern

Managing distributed transactions without distributed locks. When you can't do one ACID transaction across services, use compensating actions instead.

Advanced Distributed Pattern
🏠 Daily-Life Analogy: Planning a Wedding

Booking a wedding involves multiple vendors: venue, caterer, photographer. You can't book them atomically. Instead:

  • Book venue ✔
  • Book caterer ✔
  • Book photographer... REJECTED (not available)

Now you undo previous bookings: cancel caterer, cancel venue. These "undo" actions are compensating transactions. The whole sequence is a saga.

Why Not Distributed Transactions?

ApproachHowProblem
2PC (Two-Phase Commit)Lock all resources, commit togetherBlocking, slow, coordinator crash = stuck
Saga PatternEach step commits independently; compensate on failureMore complex logic, but non-blocking

Orchestration Saga (Central Coordinator)

class OrderSagaOrchestrator:
    """Central coordinator for order processing saga"""

    def __init__(self):
        self.steps = [
            {"action": self.create_order,
             "compensation": self.cancel_order},
            {"action": self.charge_payment,
             "compensation": self.refund_payment},
            {"action": self.reserve_inventory,
             "compensation": self.release_inventory},
            {"action": self.arrange_shipping,
             "compensation": self.cancel_shipping},
        ]

    def execute(self, order):
        """Run saga: if any step fails, compensate previous"""
        completed = []

        for step in self.steps:
            try:
                step["action"](order)
                completed.append(step)
                print(f"  OK: {step['action'].__name__}")
            except Exception as e:
                print(f"  FAIL: {step['action'].__name__}: {e}")
                self._compensate(completed, order)
                return "SAGA FAILED"

        return "SAGA COMPLETED"

    def _compensate(self, completed, order):
        """Run compensations in REVERSE order"""
        for step in reversed(completed):
            try:
                step["compensation"](order)
                print(f"  UNDO: {step['compensation'].__name__}")
            except Exception as e:
                print(f"  UNDO FAILED: {e} (needs manual fix!)")

    # Actions
    def create_order(self, o): print("    Creating order...")
    def charge_payment(self, o): print("    Charging payment...")
    def reserve_inventory(self, o): print("    Reserving stock...")
    def arrange_shipping(self, o):
        raise Exception("Shipping unavailable!")

    # Compensations
    def cancel_order(self, o): print("    Cancelling order...")
    def refund_payment(self, o): print("    Refunding payment...")
    def release_inventory(self, o): print("    Releasing stock...")
    def cancel_shipping(self, o): print("    Cancelling shipping...")

# Demo
saga = OrderSagaOrchestrator()
result = saga.execute({"id": 1, "total": 29.99})
print(result)
# OK: create_order
# OK: charge_payment
# OK: reserve_inventory
# FAIL: arrange_shipping: Shipping unavailable!
# UNDO: release_inventory
# UNDO: refund_payment
# UNDO: cancel_order
# SAGA FAILED

Choreography Saga (Event-Based)

No central coordinator. Each service listens for events and reacts:

class OrderService:
    def create_order(self, order):
        self.save(order, status="PENDING")
        emit("OrderCreated", order)  # PaymentService listens

    def on_payment_failed(self, order_id):
        self.update(order_id, status="CANCELLED")  # Compensation

class PaymentService:
    def on_order_created(self, order):
        try:
            self.charge(order.user_id, order.total)
            emit("PaymentCompleted", order)
        except PaymentError:
            emit("PaymentFailed", order)  # Triggers rollback

class InventoryService:
    def on_payment_completed(self, order):
        try:
            self.reserve(order.items)
            emit("InventoryReserved", order)
        except OutOfStockError:
            emit("InventoryFailed", order)  # Triggers refund

Choreography vs Orchestration

AspectChoreographyOrchestration
CoordinationDecentralized (events)Centralized (orchestrator)
CouplingLooseTighter (orchestrator knows all)
DebuggingHard (events bounce around)Easy (one place to look)
ComplexitySimple for 2-3 stepsHandles complex flows well
SPOFNoneOrchestrator (but replicable)

Real-World Saga Usage

  • Uber — Trip lifecycle saga (match → start → end → charge)
  • Netflix Conductor — Orchestration engine for multi-service workflows
  • Amazon — Order processing (payment → inventory → shipping)
  • Temporal/Cadence — Workflow engines with built-in saga/retry/compensation

📝 Summary

  • Saga = sequence of local transactions with compensating actions
  • Use when you can't do a single ACID transaction across services
  • Choreography: decentralized via events (simple but hard to debug)
  • Orchestration: central coordinator (easier to understand)
  • Compensations must be idempotent (may run multiple times)
  • Not all actions are compensable (can't "unsend" an email)

🧠 Mental Model

Happy path: [Create] → [Pay] → [Reserve] → [Ship] → DONE Failure at step 3: [Create] → [Pay] → [Reserve FAIL] | Compensate in reverse: | [Cancel] ← [Refund] ←--+ Each step COMMITS independently. No global lock held during the saga. If something fails, you UNDO, not ROLLBACK.

❌ Common Beginner Mistakes

  • Non-idempotent compensations — "Refund $10" must check if already refunded.
  • Compensation itself fails — Need retry or dead-letter queue for failed compensations.
  • Using sagas for single-DB operations — Just use a regular transaction!
  • No saga state persistence — Must persist current step to resume after crash.

🏋 Hands-On Exercise

  1. Implement OrderSagaOrchestrator. Make step 3 fail randomly. Verify compensations run correctly.
  2. Add state persistence: save step to DB. Simulate crash mid-saga and resume.
  3. Implement choreography version with an event bus. Compare debugging difficulty.
  4. Design a saga for travel booking (flight + hotel + car). What if hotel fails after flight is booked?
