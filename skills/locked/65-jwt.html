JWT (JSON Web Tokens)

Stateless, self-contained tokens for secure authentication and authorization

Intermediate Security Concept

💡 Analogy

A passport — it contains your identity info, is signed by an authority (the government), and can be verified by any border agent without calling back to the authority. The stamp and watermarks prove authenticity, the expiry date limits validity, and anyone can read the name but nobody can forge the signature.

What Is a JWT?

A JSON Web Token is a compact, URL-safe means of representing claims between two parties. It enables stateless authentication — the server doesn’t need to store session state because all the information lives inside the token itself.

Token Structure

Every JWT consists of three Base64url-encoded parts separated by dots:

header.payload.signature
Part Purpose Example Content
Header Declares token type and signing algorithm {"alg": "HS256", "typ": "JWT"}
Payload Contains claims (user data, permissions, metadata) {"sub": "user123", "exp": 1717200000}
Signature Verifies integrity — proves the token wasn’t tampered with HMAC-SHA256 of header + payload + secret

Signing Algorithms

HS256 vs RS256

Feature HS256 (Symmetric) RS256 (Asymmetric)
Key type Shared secret Public/private key pair
Sign & verify Same key for both Private signs, public verifies
Use case Single service, internal APIs Distributed systems, third-party consumers
Performance Faster Slower (RSA operations)
Security trade-off Secret must be shared with verifiers Only public key is distributed

Registered Claims

Claim Name Purpose
iss Issuer Who created and signed the token
sub Subject The user or entity the token represents
exp Expiration Time Unix timestamp after which the token is invalid
iat Issued At When the token was created
aud Audience Intended recipient(s) of the token
nbf Not Before Token is not valid before this time
jti JWT ID Unique identifier to prevent replay attacks

Access Tokens vs Refresh Tokens

Property Access Token Refresh Token
Lifetime Short (5–15 minutes) Long (days to weeks)
Purpose Authorize API requests Obtain new access tokens
Storage Memory or short-lived cookie Secure HTTP-only cookie or server-side
Sent to Resource servers Auth server only
Revocation Difficult (stateless) Easier (stored server-side)

Token Revocation Challenge

Since JWTs are stateless, the server doesn’t track issued tokens. This creates a fundamental challenge — you can’t invalidate a token before its expiry without introducing state. Common strategies:

  • Short expiry times — limit the damage window
  • Token blocklist — store revoked token IDs (jti) in a fast cache like Redis
  • Token versioning — increment a user’s token version on logout, reject old versions
  • Refresh token rotation — issue a new refresh token on each use, detect reuse as theft

Implementation — Python

Creating a JWT

import hmac
import hashlib
import base64
import json
import time

def base64url_encode(data: bytes) -> str:
    # URL-safe Base64 without padding
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode("ascii")

def create_jwt(payload: dict, secret: str, algorithm: str = "HS256") -> str:
    # 1. Build the header
    header = {"alg": algorithm, "typ": "JWT"}
    header_encoded = base64url_encode(json.dumps(header).encode())

    # 2. Add standard claims to payload
    payload.setdefault("iat", int(time.time()))
    payload.setdefault("exp", payload["iat"] + 900)  # 15 min default
    payload_encoded = base64url_encode(json.dumps(payload).encode())

    # 3. Create the signature
    signing_input = f"{header_encoded}.{payload_encoded}"
    signature = hmac.new(
        secret.encode(),
        signing_input.encode(),
        hashlib.sha256
    ).digest()
    signature_encoded = base64url_encode(signature)

    # 4. Combine all three parts
    return f"{header_encoded}.{payload_encoded}.{signature_encoded}"

# Usage
token = create_jwt(
    payload={"sub": "user_42", "role": "admin"},
    secret="super-secret-key-do-not-hardcode"
)
print(token)
# eyJhbGciOiJIUzI1NiIs...<payload>...<signature>

Verifying a JWT

def verify_jwt(token: str, secret: str) -> dict:
    # 1. Split the token
    parts = token.split(".")
    if len(parts) != 3:
        raise ValueError("Invalid token format")

    header_encoded, payload_encoded, signature_encoded = parts

    # 2. Recompute the signature
    signing_input = f"{header_encoded}.{payload_encoded}"
    expected_sig = hmac.new(
        secret.encode(),
        signing_input.encode(),
        hashlib.sha256
    ).digest()
    expected_encoded = base64url_encode(expected_sig)

    # 3. Constant-time comparison prevents timing attacks
    if not hmac.compare_digest(signature_encoded, expected_encoded):
        raise ValueError("Invalid signature")

    # 4. Decode and validate claims
    padding = "=" * (4 - len(payload_encoded) % 4)
    payload = json.loads(base64.urlsafe_b64decode(payload_encoded + padding))

    # 5. Check expiration
    if payload.get("exp", 0) < time.time():
        raise ValueError("Token has expired")

    return payload

Token Refresh Flow

import uuid

class TokenService:
    def __init__(self, secret: str):
        self.secret = secret
        self.refresh_tokens = {}  # In production: use Redis or a DB
        self.revoked_jtis = set()

    def issue_token_pair(self, user_id: str, role: str) -> dict:
        # Short-lived access token
        access_token = create_jwt(
            payload={
                "sub": user_id,
                "role": role,
                "jti": str(uuid.uuid4()),
                "exp": int(time.time()) + 900,   # 15 minutes
            },
            secret=self.secret
        )

        # Long-lived refresh token
        refresh_id = str(uuid.uuid4())
        self.refresh_tokens[refresh_id] = {
            "user_id": user_id,
            "role": role,
            "expires": time.time() + 604800,  # 7 days
        }

        return {
            "access_token": access_token,
            "refresh_token": refresh_id,
            "expires_in": 900,
        }

    def refresh(self, refresh_token: str) -> dict:
        # Validate the refresh token
        token_data = self.refresh_tokens.get(refresh_token)
        if not token_data:
            raise ValueError("Invalid refresh token")
        if token_data["expires"] < time.time():
            del self.refresh_tokens[refresh_token]
            raise ValueError("Refresh token expired")

        # Rotate: delete old, issue new pair
        del self.refresh_tokens[refresh_token]
        return self.issue_token_pair(
            token_data["user_id"], token_data["role"]
        )

    def revoke(self, token: str):
        # Add the jti to the blocklist
        payload = verify_jwt(token, self.secret)
        self.revoked_jtis.add(payload["jti"])

    def is_revoked(self, token: str) -> bool:
        payload = verify_jwt(token, self.secret)
        return payload.get("jti") in self.revoked_jtis

🏭 Industry Usage

  • Auth0 — Issues JWTs as access tokens, supports RS256 with JWKS endpoints for key rotation
  • Firebase Auth — Returns signed JWTs that can be verified client-side or server-side
  • AWS Cognito — Issues JWT-based ID tokens and access tokens for user pool authentication
  • Okta — Enterprise identity platform using JWTs with custom claims for RBAC
  • Modern APIs — GitHub, Stripe, Twilio, and most SaaS APIs accept Bearer JWT tokens

📋 Summary

  • JWTs are self-contained tokens with three parts: header, payload, and signature
  • They enable stateless authentication — no server-side session storage needed
  • HS256 uses a shared secret; RS256 uses a public/private key pair for distributed verification
  • Short-lived access tokens + long-lived refresh tokens balance security and UX
  • Token revocation requires trade-offs — blocklists, versioning, or short expiry windows
  • Always validate: signature, expiration, issuer, and audience claims

⚠️ Common Mistakes

  • Storing secrets in the token — JWTs are encoded, not encrypted. Anyone can decode the payload with Base64. Never put passwords, credit card numbers, or sensitive PII in claims.
  • Using long expiry times — A 24-hour access token means a stolen token grants 24 hours of access. Keep access tokens short (5–15 min) and use refresh tokens for continuity.
  • Not validating all claims — Checking the signature alone is insufficient. Always verify exp, iss, aud, and nbf to prevent token reuse across services.
  • Accepting the algorithm from the header — The “alg: none” attack tricks servers into accepting unsigned tokens. Always enforce the expected algorithm server-side, never trust the token’s header.

💻 Exercises

  1. Build from scratch — Implement JWT creation and verification without any library. Manually Base64url-encode the header and payload, sign with HMAC-SHA256, and verify by recomputing the signature.
  2. Token refresh service — Build a FastAPI endpoint that issues token pairs, implements refresh token rotation, and detects token reuse (issue a new refresh token each time, invalidate the family if an old one is reused).
  3. Revocation system — Design a Redis-backed token blocklist. Store revoked JTIs with TTL matching the token’s remaining lifetime. Measure the latency overhead of checking the blocklist on every request.
  4. RS256 migration — Convert an HS256-based auth system to RS256. Set up a JWKS endpoint that serves the public key, implement key rotation with overlapping validity periods, and verify tokens using the kid header claim.
