Intermediate API Pattern

API Gateway

A single entry point that sits between clients and your microservices — handling routing, authentication, rate limiting, and request aggregation so individual services don’t have to.

💡 Real-World Analogy

Think of a hotel front desk. Guests don’t walk directly to housekeeping, the kitchen, or maintenance when they need something. They go to the front desk, which understands the request, verifies the guest is checked in, and routes the request to the right department. The front desk might even combine responses — “Your room is ready, breakfast is at 7am, and your dry cleaning will arrive at 3pm” — all from a single interaction. An API Gateway works the same way for your microservices.

What Does an API Gateway Do?

  • Request routing: Maps incoming URLs to the correct backend service — /users/* → User Service, /orders/* → Order Service
  • Authentication & authorization: Validates tokens (JWT, API keys) once at the gateway instead of in every service
  • Rate limiting: Protects backends from being overwhelmed — 1000 requests/min per client, no matter which services they call
  • Request transformation: Converts between protocols (REST → gRPC), adds headers, rewrites paths
  • Response aggregation: Combines data from multiple services into a single response for the client
  • Caching: Stores frequent responses to reduce backend load
  • Logging & monitoring: Centralized access logs, latency metrics, error tracking

Single Entry Point for Microservices

The Problem Without a Gateway

  • Clients must know the address of every service — tight coupling to infrastructure
  • Each service implements its own auth, rate limiting, and CORS — duplicated logic everywhere
  • Changing service URLs breaks all clients — no abstraction layer
  • Mobile clients make 5–10 API calls per screen — high latency on slow networks

The Gateway Solution

  • Clients talk to one URL — api.company.com — the gateway handles the rest
  • Services can move, scale, or split without clients knowing
  • Cross-cutting concerns live in one place — update auth logic once, applied everywhere
  • The gateway can aggregate multiple service calls into one client response

Backend for Frontend (BFF) Pattern

  • One gateway per client type: Web BFF, Mobile BFF, Third-Party BFF
  • Each BFF is optimized for its client — mobile gets compressed payloads, web gets full data
  • The mobile BFF aggregates aggressively (fewer round-trips on cellular networks)
  • The web BFF might allow fine-grained queries (faster networks, more screen real-estate)
  • Teams own their BFF — the mobile team controls their gateway without blocking the web team

Gateway vs Service Mesh

  • API Gateway: North-south traffic (client → services). Handles external concerns like auth, rate limiting, protocol translation
  • Service Mesh: East-west traffic (service → service). Handles internal concerns like mTLS, retries, circuit breaking between services
  • They complement each other — the gateway guards the perimeter, the mesh secures internal communication
  • Some tools blur the line — Envoy can act as both gateway and sidecar proxy
Concern API Gateway Service Mesh Both?
Authentication JWT/API key validation mTLS between services Yes — different layers
Rate Limiting Per-client limits Per-service limits Yes — different scopes
Load Balancing Across service instances Across pods/containers Yes — different levels
Protocol Translation REST → gRPC for clients Not typically Gateway only
Observability Access logs, external metrics Distributed tracing, internal metrics Yes — complementary

Python Implementation

import time
import hashlib
import json
from dataclasses import dataclass, field
from typing import Dict, List, Callable, Optional
from collections import defaultdict


# ═══════════════════════════════════════════════════
# Request / Response models
# ═══════════════════════════════════════════════════

@dataclass
class Request:
    method: str
    path: str
    headers: Dict[str, str] = field(default_factory=dict)
    body: Optional[str] = None
    client_ip: str = "127.0.0.1"


@dataclass
class Response:
    status: int
    body: dict
    headers: Dict[str, str] = field(default_factory=dict)


# ═══════════════════════════════════════════════════
# Rate Limiter (Token Bucket)
# ═══════════════════════════════════════════════════

class RateLimiter:
    def __init__(self, max_requests: int, window_seconds: int):
        self.max_requests = max_requests
        self.window = window_seconds
        self.requests: Dict[str, List[float]] = defaultdict(list)

    def is_allowed(self, client_id: str) -> bool:
        now = time.time()
        window_start = now - self.window
        # Remove expired timestamps
        self.requests[client_id] = [
            ts for ts in self.requests[client_id]
            if ts > window_start
        ]
        if len(self.requests[client_id]) >= self.max_requests:
            return False
        self.requests[client_id].append(now)
        return True


# ═══════════════════════════════════════════════════
# Authentication Middleware
# ═══════════════════════════════════════════════════

class AuthMiddleware:
    def __init__(self):
        # Simulated valid API keys
        self.valid_keys = {
            "key-abc123": {"client": "mobile-app", "tier": "premium"},
            "key-def456": {"client": "web-app", "tier": "free"},
        }

    def authenticate(self, request: Request) -> Optional[dict]:
        api_key = request.headers.get("X-API-Key")
        if not api_key:
            return None
        return self.valid_keys.get(api_key)


# ═══════════════════════════════════════════════════
# Service Registry & Backend Services
# ═══════════════════════════════════════════════════

class BackendService:
    def __init__(self, name: str, base_url: str):
        self.name = name
        self.base_url = base_url

    def handle(self, request: Request) -> Response:
        # Simulate service response
        return Response(
            status=200,
            body={"service": self.name, "path": request.path}
        )


# ═══════════════════════════════════════════════════
# API Gateway
# ═══════════════════════════════════════════════════

class APIGateway:
    def __init__(self):
        self.routes: Dict[str, BackendService] = {}
        self.auth = AuthMiddleware()
        self.rate_limiter = RateLimiter(max_requests=100, window_seconds=60)
        self.middleware: List[Callable] = []

    def register_route(self, path_prefix: str, service: BackendService):
        """Register a path prefix to route to a backend service."""
        self.routes[path_prefix] = service

    def _find_service(self, path: str) -> Optional[BackendService]:
        """Match request path to a registered service."""
        for prefix, service in sorted(
            self.routes.items(), key=lambda x: len(x[0]), reverse=True
        ):
            if path.startswith(prefix):
                return service
        return None

    def handle_request(self, request: Request) -> Response:
        """Main gateway logic — auth, rate limit, route."""

        # Step 1: Authentication
        client_info = self.auth.authenticate(request)
        if not client_info:
            return Response(
                status=401,
                body={"error": "Unauthorized — invalid or missing API key"}
            )

        # Step 2: Rate Limiting
        client_id = client_info["client"]
        if not self.rate_limiter.is_allowed(client_id):
            return Response(
                status=429,
                body={"error": "Rate limit exceeded"},
                headers={"Retry-After": "60"}
            )

        # Step 3: Route to backend service
        service = self._find_service(request.path)
        if not service:
            return Response(
                status=404,
                body={"error": f"No service found for path: {request.path}"}
            )

        # Step 4: Forward request to service
        response = service.handle(request)
        response.headers["X-Gateway"] = "api-gateway-v1"
        return response

    def aggregate_requests(self, requests: List[Request]) -> Response:
        """Combine multiple service calls into one response."""
        results = {}
        for req in requests:
            service = self._find_service(req.path)
            if service:
                resp = service.handle(req)
                results[service.name] = resp.body
        return Response(status=200, body={"aggregated": results})


# ═══════════════════════════════════════════════════
# Demo: API Gateway in action
# ═══════════════════════════════════════════════════

gateway = APIGateway()

# Register backend services
gateway.register_route("/api/users", BackendService("user-service", "http://users:8001"))
gateway.register_route("/api/orders", BackendService("order-service", "http://orders:8002"))
gateway.register_route("/api/products", BackendService("product-service", "http://products:8003"))

# Authenticated request → routes correctly
req = Request(
    method="GET",
    path="/api/users/123",
    headers={"X-API-Key": "key-abc123"}
)
print("Authenticated:", gateway.handle_request(req).body)

# Missing API key → 401
bad_req = Request(method="GET", path="/api/users/123", headers={})
print("No auth:", gateway.handle_request(bad_req).body)

# Aggregation — one call fetches from multiple services
agg = gateway.aggregate_requests([
    Request(method="GET", path="/api/users/123", headers={}),
    Request(method="GET", path="/api/orders?user=123", headers={}),
])
print("Aggregated:", json.dumps(agg.body, indent=2))

🏭 Industry Practice

Kong: Open-source API gateway built on nginx/OpenResty. Plugin-based architecture — add auth, rate limiting, logging without modifying your services. Used by companies processing billions of requests per day. Supports declarative configuration via YAML for GitOps workflows.

AWS API Gateway: Fully managed, serverless gateway. Integrates natively with Lambda, Cognito (auth), and CloudWatch (monitoring). Supports REST, HTTP, and WebSocket APIs. Charges per request — no idle costs, but can get expensive at massive scale.

Netflix Zuul / Spring Cloud Gateway: Zuul was Netflix’s battle-tested gateway handling billions of requests. Spring Cloud Gateway is its modern successor — built on reactive programming (Project Reactor) for non-blocking I/O. Used when your backend is JVM-based.

Envoy Proxy: Originally built by Lyft, now a CNCF graduated project. Can serve as both an API gateway (edge proxy) and service mesh sidecar. Its xDS API allows dynamic configuration without restarts — critical for Kubernetes environments where services appear and disappear constantly.

📋 Key Takeaways

  • An API Gateway provides a single entry point for all client requests — routing, auth, and rate limiting happen in one place
  • Without a gateway, every microservice must implement cross-cutting concerns independently — duplication and inconsistency
  • The BFF pattern creates specialized gateways per client type — mobile, web, and third-party get optimized experiences
  • Gateways handle north-south traffic (external → internal), while service meshes handle east-west traffic (service → service)
  • Request aggregation reduces round-trips — critical for mobile clients on high-latency networks
  • The gateway is a single point of failure — it must be highly available, horizontally scaled, and carefully monitored

🧠 Mental Model

Think of the API Gateway as an airport’s main terminal. All passengers (requests) enter through one building, go through security (auth), get directed to their gate (routing), and the terminal manages crowd control (rate limiting). Airlines (services) don’t each build their own terminal.

⚠️ Common Mistakes

  • Putting business logic in the gateway: The gateway should route, authenticate, and rate-limit — not transform data or execute domain rules. If your gateway has if/else branches based on business entities, that logic belongs in a service. Keep the gateway thin and generic.
  • Single gateway for all client types: Mobile needs compressed, aggregated responses. Web needs fine-grained APIs. Third parties need stable versioned endpoints. One gateway trying to serve all three becomes a bloated mess. Use the BFF pattern instead.
  • No health checks on backends: The gateway routes to a service that’s down, returning 502 errors to clients. Always implement health checks so the gateway can remove unhealthy instances from the routing pool and return graceful fallback responses.
  • Gateway as a single point of failure: If your gateway goes down, everything goes down. Deploy multiple gateway instances behind a load balancer. Use blue-green deployments for gateway updates. Never deploy a single gateway instance in production.

🎯 Exercises

  1. Build a gateway with middleware chain: Implement a gateway where middleware functions are composable. Each middleware can modify the request, short-circuit the response, or pass to the next. Implement logging, auth, rate limiting, and CORS as separate middleware. Test that order matters (auth before rate-limit).
  2. Implement request aggregation: Build an endpoint /api/dashboard that fetches from 3 services concurrently (user profile, recent orders, recommendations) and returns a combined response. Handle partial failures — if one service is slow, return what you have after a timeout with a “degraded” flag.
  3. Add API versioning: Extend the gateway to support versioned routes (/v1/users, /v2/users). Version can also come from a header (Accept: application/vnd.api.v2+json). Route different versions to different service deployments. Implement a deprecation warning header for v1 clients.
  4. Implement circuit breaking at the gateway: If a backend service returns 5xx errors more than 50% of the time in the last 30 seconds, stop forwarding requests to it (open circuit). After 10 seconds, allow one request through (half-open). If it succeeds, close the circuit. Track state per-service and expose a health dashboard.
