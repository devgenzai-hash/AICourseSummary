System Design/ Replication

Replication

Keeping copies of data on multiple nodes so one machine dying doesn't kill the whole system. The foundation of fault tolerance.

Advanced Distributed Concept
🏠 Daily-Life Analogy: Photocopying Important Documents

You have one original copy of your passport. If your house burns down, it's gone forever. So you make copies:

  • One copy at your parents' house (different location = different server)
  • One copy in a safe deposit box (another location)
  • A photo on your phone (yet another copy)

Now even if one place gets destroyed, you still have the information. That's replication — keeping the same data in multiple places so losing one doesn't mean losing everything.

But there's a problem: if you update your passport (new photo), you need to update ALL copies. What if you update one but forget the others? Now they're inconsistent. This is the core challenge of replication.

Why Replicate?

ReasonHow Replication HelpsExample
Fault toleranceIf one node dies, others have the dataDatabase server crashes → failover to replica
Read scalabilitySpread read load across multiple copies1 million users reading → 5 replicas handle reads
Low latencyPlace replicas closer to users geographicallyUS data replicated to Europe → European users read locally

Three Replication Architectures

1. Single-Leader (Master-Slave) Replication

One node (leader/master) accepts ALL writes. It then replicates changes to followers (slaves/replicas). Followers can serve reads.

class SingleLeaderReplication:
    """Single leader: one writer, many readers"""

    def __init__(self):
        self.leader_data = {}
        self.followers = [{}, {}, {}]  # 3 follower copies
        self.replication_log = []      # Write-Ahead Log for replication

    def write(self, key, value):
        """All writes go to leader ONLY"""
        self.leader_data[key] = value
        log_entry = {"op": "SET", "key": key, "value": value}
        self.replication_log.append(log_entry)

        # Replicate to followers (async or sync)
        self._replicate_to_followers(log_entry)
        return "Written to leader"

    def read(self, key, from_leader=False):
        """Reads can go to any node (leader or follower)"""
        if from_leader:
            return self.leader_data.get(key)
        # Read from random follower (load balancing)
        import random
        follower = random.choice(self.followers)
        return follower.get(key)  # Might be slightly stale!

    def _replicate_to_followers(self, log_entry):
        for follower in self.followers:
            follower[log_entry["key"]] = log_entry["value"]

# Usage
db = SingleLeaderReplication()
db.write("user:1", {"name": "Alice", "age": 30})
print(db.read("user:1"))  # Read from follower (fast)

2. Multi-Leader Replication

Multiple nodes can accept writes. Each leader replicates to others. Used for multi-datacenter setups.

The Conflict Problem: If two leaders accept conflicting writes (User edits profile in US and EU simultaneously), you need conflict resolution. Strategies: last-write-wins (LWW), merge, or custom resolution. 
class MultiLeaderReplication:
    """Multiple writers — requires conflict resolution"""

    def __init__(self):
        self.dc_us = {}   # US datacenter
        self.dc_eu = {}   # EU datacenter
        self.conflicts = []

    def write_us(self, key, value, timestamp):
        self.dc_us[key] = {"value": value, "ts": timestamp}
        self._sync_to_eu(key)

    def write_eu(self, key, value, timestamp):
        self.dc_eu[key] = {"value": value, "ts": timestamp}
        self._sync_to_us(key)

    def _resolve_conflict(self, key, local, remote):
        """Last-Write-Wins (LWW) conflict resolution"""
        if remote["ts"] > local["ts"]:
            return remote  # Remote wins
        return local      # Local wins

    def _sync_to_eu(self, key):
        if key in self.dc_eu:
            # Conflict! Both DCs have written to same key
            winner = self._resolve_conflict(key, self.dc_eu[key], self.dc_us[key])
            self.dc_eu[key] = winner
        else:
            self.dc_eu[key] = self.dc_us[key]

3. Leaderless Replication

No designated leader. ANY node accepts writes. Reads go to multiple nodes and use quorum to determine the correct value. Used by Cassandra and DynamoDB.

class LeaderlessReplication:
    """No leader — write to multiple, read from multiple"""

    def __init__(self, num_replicas=3):
        self.replicas = [{} for _ in range(num_replicas)]
        self.n = num_replicas

    def write(self, key, value, w=2):
        """Write to at least W replicas (quorum write)"""
        successes = 0
        for replica in self.replicas:
            replica[key] = {"value": value, "version": self._next_version()}
            successes += 1
            if successes >= w:
                return f"Written to {w}/{self.n} replicas"

    def read(self, key, r=2):
        """Read from at least R replicas — take newest version"""
        responses = []
        for replica in self.replicas[:r]:
            if key in replica:
                responses.append(replica[key])

        if not responses:
            return None
        # Return the most recent version
        return max(responses, key=lambda x: x["version"])["value"]

    def _next_version(self):
        import time
        return time.time_ns()

Synchronous vs Asynchronous Replication

TypeHow It WorksProsCons
SynchronousLeader waits for ALL followers to confirm before responding to clientStrong consistency — followers always up-to-dateSlow — one slow follower blocks everything
AsynchronousLeader responds immediately, replicates in backgroundFast — leader never waitsData loss if leader dies before replication completes
Semi-synchronousLeader waits for ONE follower (not all)Balance of speed and safetyMost common in practice (PostgreSQL default)

Replication Lag: The Nasty Problem

With async replication, followers are always slightly behind the leader. This delay is called replication lag.

# Replication lag causes stale reads

# 1. User writes (goes to leader)
db.write("profile", {"name": "Alice Updated"})  # Leader: ✓

# 2. User immediately reads (goes to follower)
result = db.read("profile")  # Follower: still has old "Alice"!
# User sees stale data! "I just saved, where's my update?!"

# Solutions:
# 1. Read-after-write consistency: route reads to leader for recently-written keys
# 2. Monotonic reads: always read from same replica (sticky sessions)
# 3. Causal consistency: track dependencies and ensure order

class ReadAfterWriteConsistency:
    """Ensure user sees their own writes"""

    def __init__(self, leader, followers):
        self.leader = leader
        self.followers = followers
        self.recent_writes = {}  # user_id → last_write_timestamp

    def read(self, key, user_id):
        # If user recently wrote, read from leader (guaranteed fresh)
        if user_id in self.recent_writes:
            last_write = self.recent_writes[user_id]
            if time.time() - last_write < 5:  # Within 5 seconds
                return self.leader.read(key)  # Read from leader!
        # Otherwise, read from any follower (faster)
        return random.choice(self.followers).read(key)

Real-World Replication

  • PostgreSQL — Streaming replication (async by default, sync optional). WAL records shipped to replicas.
  • MySQL — Binary log replication. Semi-sync mode waits for one replica ACK.
  • MongoDB — Replica sets with automatic failover. Write concern configurable per operation.
  • Cassandra — Leaderless replication with tunable consistency (W, R, N).
  • Redis — Async replication by default. Redis Sentinel for automatic failover.

📝 Summary

  • Replication = keeping copies of data on multiple nodes
  • Single-leader: one writer, many readers (simplest, most common)
  • Multi-leader: multiple writers (multi-DC), requires conflict resolution
  • Leaderless: any node reads/writes, uses quorum (Cassandra, DynamoDB)
  • Sync replication = safe but slow. Async = fast but can lose data.
  • Replication lag causes stale reads — fix with read-after-write consistency

🧠 Mental Model

Single-Leader: Client ──write──→ [LEADER] ──replicate──→ [Follower 1] │ [Follower 2] │ [Follower 3] Client ──read──→ [Any Follower] (might be slightly stale) Leaderless (Quorum: W=2, R=2, N=3): Client ──write──→ [Node 1] ✓ [Node 2] ✓ (W=2 met → success!) [Node 3] ✗ (down, will catch up later) Client ──read──→ [Node 1] → v2 [Node 2] → v2 (R=2 met, both agree → v2 is correct)

❌ Common Beginner Mistakes

  • Reading from replicas expecting latest data — Async replicas are always slightly behind. Design for eventual consistency or use read-after-write.
  • Not planning for leader failure — If the leader dies, who becomes the new leader? Automatic failover is essential.
  • Ignoring conflict resolution in multi-leader — Last-write-wins loses data. Think about what "correct" means for your use case.
  • Too many replicas — More replicas = more write overhead. 3-5 is typical. More doesn't always mean better.
