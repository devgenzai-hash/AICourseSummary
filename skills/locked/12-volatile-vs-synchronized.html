System Design/ Volatile vs Synchronized

Volatile vs Synchronized

Two different tools for thread communication. Volatile ensures visibility; synchronized ensures both visibility AND atomicity.

Intermediate Concept Code
Megaphone vs Private Room

Volatile (megaphone): When you update a value, you shout it through a megaphone. Everyone hears the latest value immediately. But if two people shout at once, it is chaos.

Synchronized (private room): Only one person can enter the room. Inside, they can read and write freely. Others wait. Guarantees both visibility AND exclusive access.

The Two Problems of Concurrency

ProblemDescriptionSolution
VisibilityThread B doesn't see Thread A's writesvolatile / memory barriers
AtomicityCompound operations get interleavedsynchronized / locks

When Volatile Is Enough

import threading

# Volatile-equivalent in Python: threading.Event or explicit barriers
# Use case: simple flag (one writer, many readers)

stop_event = threading.Event()  # Acts like a volatile boolean

def worker():
    while not stop_event.is_set():  # Always reads latest value
        do_work()

def controller():
    time.sleep(5)
    stop_event.set()  # Immediately visible to all threads

# Volatile is sufficient when:
# 1. Only ONE thread writes, others only read
# 2. The write doesn't depend on the current value
# 3. No compound check-then-act operations

When You Need Synchronized (Locks)

import threading

counter = 0
lock = threading.Lock()

# Volatile would NOT fix this — it's a read-modify-write!
def increment():
    global counter
    with lock:  # Need atomicity AND visibility
        counter += 1  # READ + ADD + WRITE must be indivisible

# Synchronized needed when:
# 1. Multiple threads write to the same variable
# 2. Read-modify-write operations (counter++, check-then-act)
# 3. Multiple variables must be consistent together

Comparison Table

FeatureVolatileSynchronized/Lock
VisibilityYesYes
AtomicityOnly for single read/writeYes (entire block)
BlockingNever blocksCan block waiting threads
PerformanceFast (no lock overhead)Slower (acquire/release)
Use caseFlags, status variablesCounters, state machines, compound ops

Python Equivalents

import threading

# "Volatile" equivalents in Python:
# - threading.Event (boolean flag)
# - queue.Queue (thread-safe communication)
# - Value from multiprocessing (with explicit lock)

# "Synchronized" equivalents:
# - threading.Lock / RLock
# - threading.Condition
# - threading.Semaphore

# Best practice: Use Event for simple signals, Lock for data protection
class SafePublisher:
    def __init__(self):
        self._data = None
        self._ready = threading.Event()

    def publish(self, value):
        self._data = value
        self._ready.set()  # Memory barrier + signal

    def consume(self):
        self._ready.wait()  # Blocks until set, with memory barrier
        return self._data  # Guaranteed to see the published value

Language Implementations

  • Java volatile — Guarantees visibility, prevents reordering, does NOT provide atomicity for compound ops
  • Java synchronized — Visibility + atomicity + mutual exclusion
  • C++ volatile — Only prevents compiler optimization (NOT thread-safe! Use std::atomic instead)
  • Go — No volatile keyword; use channels or sync/atomic package

📝 Summary

  • Volatile solves visibility (all threads see latest value) but NOT atomicity
  • Synchronized (locks) solve both visibility AND atomicity
  • Use volatile/Event for simple flags with one writer, many readers
  • Use locks for counter++, check-then-act, and multi-variable updates
  • C++ volatile is NOT thread-safe — it only prevents compiler optimizations
  • Python: threading.Event = volatile-like; threading.Lock = synchronized

🧠 Mental Model

VOLATILE: Thread A writes → ALL threads see new value immediately But: if two threads write simultaneously, last one wins (no ordering) SYNCHRONIZED: Thread A enters → does work → exits Thread B enters → sees ALL of A's changes → does work → exits Ordering AND visibility guaranteed! DECISION: Simple flag (stop/start)? → Event (volatile) counter += 1? → Lock (synchronized) check-then-act? → Lock (synchronized)

❌ Common Beginner Mistakes

  • Using volatile for counter++ — Volatile does NOT make read-modify-write atomic!
  • C++ volatile for threading — C++ volatile is for hardware registers, NOT threads. Use std::atomic.
  • Over-synchronizing — Using locks when a simple Event/flag would suffice kills performance.
  • Under-synchronizing — Using only a flag when compound atomicity is needed causes races.

🏋 Hands-On Exercise

  1. Implement a stop flag using threading.Event — show it works correctly with 10 worker threads.
  2. Try to use Event instead of Lock for a counter — show it fails.
  3. Build a "double-checked locking" pattern: check flag, then lock, then check again.
  4. Measure performance: Event.is_set() vs lock.acquire()/release() in a tight loop.
