Singleton

Ensuring a class has only one instance and providing a global point of access to it — the most famous (and most controversial) design pattern in software engineering.

💡 Real-World Analogy

There’s only one president of a country at a time. When anyone in the government says “the president,” everyone knows exactly who they’re referring to — there’s no ambiguity. You don’t create a new president every time you need a decision made; you always go to THE existing one. The Singleton pattern works the same way — no matter how many parts of your code request the instance, they all get the same one.

What Is the Singleton Pattern?

  • Intent: Guarantee that a class has exactly one instance across the entire application
  • Classification: Creational pattern (GoF) — controls how objects are created
  • Key constraint: The constructor is private/controlled — you cannot call new Singleton() freely
  • Access: A static method (usually get_instance()) returns the single instance, creating it on first call
  • Lifecycle: The instance lives for the entire lifetime of the application

Why Use Singleton?

  • Shared state: Application-wide configuration that every module needs to read
  • Expensive resources: Database connection pools where creating multiple pools wastes memory and connections
  • Coordination: A logging framework where all log messages must go through a single writer
  • Hardware access: A printer spooler — only one process should talk to the printer at a time
  • Caching: An in-memory cache that must be consistent across all request handlers

Thread-Safe Implementations

The Problem with Naïve Singleton

  • If two threads call get_instance() simultaneously and the instance doesn’t exist yet, both may create one
  • You end up with two instances — violating the entire purpose of the pattern
  • This is a classic race condition on the instance creation check

Double-Checked Locking

  • Check if instance exists (no lock) → if not, acquire lock → check again → create
  • The second check inside the lock prevents the race condition
  • The first check outside the lock avoids the overhead of locking on every access after creation
  • In Java, the instance field must be volatile to prevent instruction reordering

Python’s Module-Level Singleton

  • Python modules are only imported once — the module itself is a singleton
  • Simply define your instance at module level: _config = Config()
  • Python’s GIL makes module import thread-safe by default
  • This is the most Pythonic approach — no metaclass magic needed

Why Singleton Is Controversial

  • Testing nightmare: Singletons carry state between tests — test order matters and tests aren’t isolated
  • Hidden dependencies: Any code can access the singleton globally, making dependency graphs invisible
  • Tight coupling: Code depends on a specific concrete class rather than an interface
  • Violates SRP: The class manages its own lifecycle and does its actual job
  • Concurrency issues: Mutable shared state is the root of all concurrency bugs

Alternatives to Singleton

  • Dependency Injection: Create one instance and pass it to whoever needs it — explicit, testable, no global state
  • Module-level instance: In Python, just instantiate at module scope and import it
  • Scoped lifetime: Use a DI container (Spring, FastAPI Depends) to manage “one per request” or “one per app”
  • Monostate (Borg): Multiple instances share the same state dict — less restrictive than true Singleton

Python Implementations

import threading
from typing import Any, Dict


# ═══════════════════════════════════════════════════
# APPROACH 1: Metaclass Singleton (strict enforcement)
# ═══════════════════════════════════════════════════

class SingletonMeta(type):
    """
    Thread-safe Singleton metaclass.
    Any class using this metaclass will have only one instance.
    """
    _instances: Dict[type, Any] = {}
    _lock: threading.Lock = threading.Lock()

    def __call__(cls, *args, **kwargs):
        # Double-checked locking pattern
        if cls not in cls._instances:
            with cls._lock:
                # Second check after acquiring lock
                if cls not in cls._instances:
                    instance = super().__call__(*args, **kwargs)
                    cls._instances[cls] = instance
        return cls._instances[cls]


class DatabasePool(metaclass=SingletonMeta):
    """Connection pool — only one should exist."""

    def __init__(self, host: str = "localhost", max_conns: int = 10):
        self.host = host
        self.max_conns = max_conns
        self.connections = []
        print(f"  Pool created: {host}, max={max_conns}")

    def get_connection(self):
        return f"conn@{self.host}"


# ═══════════════════════════════════════════════════
# APPROACH 2: Decorator Singleton (simple and clean)
# ═══════════════════════════════════════════════════

def singleton(cls):
    """Decorator that makes a class a singleton."""
    instances = {}
    lock = threading.Lock()

    def get_instance(*args, **kwargs):
        if cls not in instances:
            with lock:
                if cls not in instances:
                    instances[cls] = cls(*args, **kwargs)
        return instances[cls]

    return get_instance


@singleton
class AppConfig:
    """Application configuration — loaded once, read everywhere."""

    def __init__(self):
        self.settings = {
            "debug": False,
            "db_url": "postgres://localhost/myapp",
            "cache_ttl": 300
        }
        print("  Config loaded from environment")

    def get(self, key: str, default=None):
        return self.settings.get(key, default)

# ═══════════════════════════════════════════════════
# APPROACH 4: Borg / Monostate Pattern
# ═══════════════════════════════════════════════════

class Borg:
    """
    Multiple instances, but all share the same state.
    Unlike Singleton, id(a) != id(b), but a.__dict__ is b.__dict__
    """
    _shared_state: Dict[str, Any] = {}

    def __init__(self):
        self.__dict__ = self._shared_state


class Logger(Borg):
    def __init__(self, level: str = "INFO"):
        super().__init__()
        if not hasattr(self, "_initialized"):
            self.level = level
            self.messages = []
            self._initialized = True
            print(f"  Logger initialized: level={level}")

    def log(self, msg: str):
        self.messages.append(f"[{self.level}] {msg}")


# ═══════════════════════════════════════════════════
# APPROACH 5: Thread-Safe with Lock (explicit control)
# ═══════════════════════════════════════════════════

class CacheManager:
    _instance = None
    _lock = threading.Lock()

    def __new__(cls):
        if cls._instance is None:
            with cls._lock:
                if cls._instance is None:
                    cls._instance = super().__new__(cls)
                    cls._instance._cache = {}
        return cls._instance

    def set(self, key: str, value: Any):
        self._cache[key] = value

    def get(self, key: str) -> Any:
        return self._cache.get(key)

print("--- Metaclass Singleton ---")

print()

# Decorator approach
print("--- Decorator Singleton ---")
cfg1 = AppConfig()
cfg2 = AppConfig()
print(f"  Same instance? {cfg1 is cfg2}")  # True
print(f"  Debug: {cfg1.get('debug')}")
print()

# Borg pattern
print("--- Borg / Monostate ---")
log1 = Logger("DEBUG")
log2 = Logger("ERROR")
log1.log("test message")
print(f"  Same object? {log1 is log2}")  # False (different objects)
print(f"  Same state? {log1.messages is log2.messages}")  # True
print(f"  log2 sees: {log2.messages}")
print()

# Thread-safe __new__
print("--- Thread-Safe __new__ ---")
cache1 = CacheManager()
cache1.set("user:1", {"name": "Alice"})
cache2 = CacheManager()
print(f"  Same instance? {cache1 is cache2}")  # True
print(f"  cache2 sees: {cache2.get('user:1')}")

🏭 Industry Practice

Database Connection Pools: Libraries like SQLAlchemy use a single engine instance per application. The engine manages a connection pool internally — creating multiple engines would waste database connections and memory. In practice, you create one engine = create_engine(...) at startup and share it via dependency injection.

Logging Frameworks: Python’s built-in logging module uses a singleton-like pattern — logging.getLogger("name") always returns the same logger for a given name. The logger registry is a module-level dictionary, making it a natural singleton without any metaclass tricks.

Spring Framework (Java): By default, all Spring beans are singletons scoped to the application context. The IoC container creates one instance and injects it everywhere. This gives you singleton semantics with full testability — you can override beans in test configurations.

Configuration Managers: Tools like python-decouple, dynaconf, and Django’s settings module all follow singleton semantics — configuration is loaded once at startup and remains immutable throughout the application lifecycle.

📋 Key Takeaways

  • Singleton ensures exactly one instance exists — useful for connection pools, config, caches, and loggers
  • Naïve implementations have race conditions — use double-checked locking with a threading lock
  • In Python, the module-level instance is the simplest and most idiomatic singleton approach
  • Singleton makes testing difficult because global state leaks between tests — prefer dependency injection
  • The Borg/Monostate pattern shares state without enforcing identity — a less restrictive alternative
  • Modern frameworks (Spring, FastAPI) solve the “one instance” problem through DI containers, not Singleton classes

🧠 Mental Model

Think of Singleton as a phone number for a pizza shop. Everyone in town dials the same number and reaches the same kitchen. You don’t build a new pizza shop every time someone wants a pizza — you all share the one that exists.

  SINGLETON LIFECYCLE:
  ══════════════════════════════════════════════════════

  First call: get_instance()
  ┌─────────────────────────────────┐
  │  instance == None?  → YES       │
  │  acquire lock                   │
  │  instance == None?  → YES       │
  │  instance = Class()  ← CREATED  │

  All subsequent calls: get_instance()
  ┌─────────────────────────────────┐
  │  instance == None?  → NO        │
  │  return instance  ← INSTANT     │
  │  (no lock needed!)              │
  └─────────────────────────────────┘

  check: None? YES  │   (blocked on lock)
  create instance   │
  release lock ─────┘

                        check: None? NO ← saved!

⚠️ Common Mistakes

  • Forgetting thread safety: A naïve if _instance is None: _instance = Cls() has a race condition. Two threads can both see None and both create instances. Always use a lock (or rely on Python’s import mechanism for module-level singletons).
  • Making everything a Singleton: Not every “I only need one” scenario requires the Singleton pattern. If you only create one instance anyway, just... create one instance and pass it around. Reserve Singleton for cases where multiple instances would cause actual bugs.
  • Mutable singleton state without synchronization: A singleton logger or cache is accessed from multiple threads. If you mutate its internal state (appending to lists, updating dicts) without locks, you get corrupted data. The singleton guarantees one instance, not thread-safe operations on that instance.
  • Testing without reset mechanism: Singletons persist across test cases, causing flaky tests that depend on execution order. Always provide a _reset() or _clear() method for testing, or better yet, use dependency injection so tests can supply their own mock instance.

🎯 Exercises

  1. Prove the race condition: Implement a naïve Singleton (no lock) and spawn 100 threads that all call get_instance() simultaneously. Add a time.sleep(0.001) inside __init__ to widen the race window. Count how many times __init__ runs — it should be more than once, proving the bug.
  2. Build a thread-safe registry: Create a ServiceRegistry singleton that maps service names to instances. Implement register(name, instance) and get(name). Ensure thread safety for both reads and writes. Write a test that registers services from 10 threads concurrently.
  3. Compare DI vs Singleton: Build a small app with a DatabaseService. First implement it as a Singleton, then refactor to use dependency injection. Write unit tests for both versions — observe how much easier mocking is with DI. Measure the lines of test setup code for each approach.
  4. Implement a resettable Singleton: Create a configuration singleton that supports reload() to re-read from disk and _reset_for_testing() to destroy the instance. Ensure reload() is atomic — readers should never see a half-loaded config. Use a read-write lock to allow concurrent reads but exclusive writes.
