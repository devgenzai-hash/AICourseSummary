Intermediate Resilience Pattern

Circuit Breaker

A self-healing pattern that prevents cascading failures by failing fast when a downstream service is unhealthy.

💡 Real-World Analogy

Think of an electrical circuit breaker in your home. When too much current flows through a circuit (short circuit or overload), the breaker trips — cutting power instantly to prevent a fire. You can’t just flip it back immediately; you must wait, check what caused the overload, and then cautiously reset it. If the problem persists, it trips again. The software circuit breaker works the same way: it “trips” after too many failures, stops sending requests to the failing service, and periodically tests if recovery has occurred.

The Three States

A circuit breaker operates as a finite state machine with three states:

State Behavior Transitions To Trigger
Closed All requests pass through normally Open Failure count exceeds threshold
Open All requests fail immediately (no call made) Half-Open Timeout period expires
Half-Open Limited requests pass through as a test Closed or Open Test succeeds → Closed; Test fails → Open

Why Circuit Breakers Prevent Cascading Failures

Without a circuit breaker, when Service B goes down, Service A keeps sending requests — each one timing out after 30 seconds. This exhausts Service A’s thread pool, causing it to fail. Then Service C, which depends on A, also fails. The circuit breaker stops this chain reaction by failing fast (milliseconds, not seconds) once the downstream is confirmed unhealthy.

Full Implementation

A production-quality circuit breaker with state machine, failure tracking, and decorator pattern:

import time
import threading
from enum import Enum
from functools import wraps
from typing import Callable, Optional

class State(Enum):
    CLOSED = "closed"
    OPEN = "open"
    HALF_OPEN = "half_open"

class CircuitBreakerOpen(Exception):
    """Raised when circuit is open and calls are rejected."""
    pass

class CircuitBreaker:
    """State-machine circuit breaker with configurable thresholds."""

    def __init__(self,
                 failure_threshold: int = 5,
                 recovery_timeout: float = 30.0,
                 half_open_max_calls: int = 3,
                 success_threshold: int = 2):
        self._failure_threshold = failure_threshold
        self._recovery_timeout = recovery_timeout
        self._half_open_max_calls = half_open_max_calls
        self._success_threshold = success_threshold

        self._state = State.CLOSED
        self._failure_count = 0
        self._success_count = 0
        self._half_open_calls = 0
        self._last_failure_time: Optional[float] = None
        self._lock = threading.Lock()

    @property
    def state(self) -> State:
        return self._state

    def _should_attempt_reset(self) -> bool:
        """Check if enough time has passed to try half-open."""
        if self._last_failure_time is None:
            return False
        elapsed = time.time() - self._last_failure_time
        return elapsed >= self._recovery_timeout

    def _transition_to(self, new_state: State):
        """Transition to a new state with reset counters."""
        old_state = self._state
        self._state = new_state
        if new_state == State.CLOSED:
            self._failure_count = 0
            self._success_count = 0
        elif new_state == State.HALF_OPEN:
            self._half_open_calls = 0
            self._success_count = 0

    def call(self, func: Callable, *args, **kwargs):
        """Execute func through the circuit breaker."""
        with self._lock:
            if self._state == State.OPEN:
                if self._should_attempt_reset():
                    self._transition_to(State.HALF_OPEN)
                else:
                    raise CircuitBreakerOpen(
                        f"Circuit open. Retry after "
                        f"{self._recovery_timeout}s")

            if self._state == State.HALF_OPEN:
                if self._half_open_calls >= self._half_open_max_calls:
                    raise CircuitBreakerOpen(
                        "Half-open call limit reached")
                self._half_open_calls += 1

        # Execute outside the lock
        try:
            result = func(*args, **kwargs)
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise

    def _on_success(self):
        with self._lock:
            if self._state == State.HALF_OPEN:
                self._success_count += 1
                if self._success_count >= self._success_threshold:
                    self._transition_to(State.CLOSED)
            elif self._state == State.CLOSED:
                self._failure_count = 0  # Reset on success

    def _on_failure(self):
        with self._lock:
            self._last_failure_time = time.time()
            if self._state == State.HALF_OPEN:
                self._transition_to(State.OPEN)
            elif self._state == State.CLOSED:
                self._failure_count += 1
                if self._failure_count >= self._failure_threshold:
                    self._transition_to(State.OPEN)

Decorator Pattern Usage

Wrapping service calls with a circuit breaker decorator for clean integration:

def circuit_protected(failure_threshold=5,
                       recovery_timeout=30.0,
                       fallback=None):
    """Decorator that wraps a function with a circuit breaker."""
    breaker = CircuitBreaker(
        failure_threshold=failure_threshold,
        recovery_timeout=recovery_timeout
    )

    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            try:
                return breaker.call(func, *args, **kwargs)
            except CircuitBreakerOpen:
                if fallback:
                    return fallback(*args, **kwargs)
                raise
        wrapper.breaker = breaker  # Expose for inspection
        return wrapper
    return decorator

State Transition Diagram

Current State Event Next State Action
Closed Success Closed Reset failure counter
Closed Failure (count < threshold) Closed Increment failure counter
Closed Failure (count ≥ threshold) Open Start recovery timer
Open Any request Open Reject immediately (fail fast)
Open Recovery timeout expires Half-Open Allow limited test requests
Half-Open Test success (≥ threshold) Closed Resume normal traffic
Half-Open Test failure Open Restart recovery timer

🏭 Industry Practice

Netflix Hystrix (now in maintenance): Pioneered the circuit breaker pattern in microservices. Used thread pool isolation and request collapsing alongside circuit breaking. Each downstream dependency got its own breaker with independent thresholds.

resilience4j (Java): The modern successor to Hystrix. Provides lightweight, composable decorators for circuit breaker, rate limiter, retry, and bulkhead — all configurable via annotations or programmatic API.

Polly (.NET): Microsoft’s go-to resilience library. Supports circuit breaker policies that can be combined with retry, timeout, and fallback policies in a single policy wrap.

AWS Step Functions: AWS provides circuit breaker patterns via Step Functions state machines, using CloudWatch alarms to detect failures and DynamoDB to store breaker state across Lambda invocations.

📋 Key Takeaways

  • Circuit breakers prevent cascading failures by failing fast instead of waiting for timeouts
  • Three states: Closed (normal), Open (rejecting), Half-Open (testing recovery)
  • Key parameters: failure threshold, recovery timeout, and success threshold for reset
  • Always provide a fallback (cached data, default response, graceful degradation)
  • Each downstream dependency should have its own circuit breaker instance
  • Monitor breaker state transitions as a key operational metric

🧠 Mental Model

Think of the circuit breaker as a traffic light between your service and a dependency. Green (Closed) = go ahead. Red (Open) = stop immediately, don’t even try. Yellow (Half-Open) = proceed with caution, one car at a time.

        ┌─────────────────────────────────────────┐
        │              CLOSED (Green)              │
        │         All requests pass through        │
        │         Counting failures...             │
        └──────────────────┬──────────────────────┘
                           │ failures >= threshold
                           ▼
        ┌─────────────────────────────────────────┐
        │              OPEN (Red)                  │

⚠️ Common Mistakes

  • Sharing one breaker across all dependencies: If Service A and Service B share a circuit breaker, a failure in B also blocks calls to healthy Service A. Each dependency needs its own breaker with independent thresholds.
  • Setting thresholds too low or too high: Too low (1–2 failures) causes false trips on transient errors. Too high (50+ failures) defeats the purpose — cascading damage occurs before the breaker opens. Start with 5–10 failures in a 60-second window.
  • No fallback strategy: Opening the circuit without a fallback returns errors to users. Always provide degraded responses: cached data, default values, or queued-for-later semantics.
  • Counting timeouts as successes: If your HTTP client returns a timeout exception that you catch silently, the breaker never sees failures. Ensure all relevant exceptions (timeouts, connection refused, 5xx responses) increment the failure counter.

🎯 Exercises

  1. Implement the full state machine: Build a CircuitBreaker class that transitions between all three states. Write unit tests that simulate failure sequences and verify correct state transitions.
  2. Add sliding window failure detection: Modify the breaker to use a time-based sliding window (e.g., 5 failures in 60 seconds) instead of a simple counter. This prevents old failures from triggering the breaker.
  3. Build a circuit breaker dashboard: Create a monitoring endpoint that exposes each breaker’s state, failure count, last failure time, and total calls. Simulate traffic and watch state changes in real-time.
  4. Cascade prevention test: Set up three services (A → B → C). Kill C and demonstrate that without a circuit breaker, A fails. Add breakers and show A degrades gracefully with fallback responses.
