IoC Container & BeanFactory

The heart of Spring — how Inversion of Control actually works at the bytecode level, and why BeanFactory is the foundation everything else builds upon.

Core Concept Spring Framework Internals
🏭 Daily-Life Analogy: The Restaurant Kitchen

Think of the IoC container as a restaurant kitchen manager. Instead of each waiter going to the market, buying ingredients, and cooking their own dishes (traditional "new Object()" approach), the kitchen manager prepares everything centrally and hands fully-prepared dishes to waiters when they need them.

The waiter (your class) doesn't know HOW the dish was prepared, WHERE ingredients came from, or what other dishes share the same sauce. It just declares what it needs and receives it. That's Inversion of Control — the control of object creation is inverted from your code to the container.

What is Inversion of Control?

IoC is a design principle (not a pattern) where the flow of control is inverted compared to traditional programming:

  • Traditional: Your code creates dependencies → OrderService service = new OrderService(new OrderRepository())
  • IoC: A container creates dependencies and injects them into your code

Spring's IoC container implements this via Dependency Injection (DI) — the most common form of IoC. But IoC is broader: it also covers the Template Method pattern, Strategy pattern, and Service Locator.

BeanFactory: The Root Interface

BeanFactory is the root interface of Spring's IoC container. It defines the fundamental contract for managing beans:

public interface BeanFactory {
    // Core method — retrieve a bean by name
    Object getBean(String name) throws BeansException;
    
    // Type-safe retrieval
    <T> T getBean(Class<T> requiredType) throws BeansException;
    
    // Check existence without instantiation
    boolean containsBean(String name);
    
    // Scope checks
    boolean isSingleton(String name);
    boolean isPrototype(String name);
}
💡 Key Insight

BeanFactory uses lazy initialization by default — beans are created only when first requested via getBean(). This is crucial for understanding memory behavior. ApplicationContext (its child) does eager initialization of singletons at startup.

DefaultListableBeanFactory — The Real Implementation

Almost everything in Spring ultimately delegates to DefaultListableBeanFactory. It maintains:

  • beanDefinitionMap — A ConcurrentHashMap<String, BeanDefinition> storing metadata (class name, scope, init-method, constructor args, etc.)
  • singletonObjects — The first-level cache: ConcurrentHashMap<String, Object> holding fully initialized singletons
  • earlySingletonObjects — Second-level cache for beans in the process of creation (handles circular dependencies)
  • singletonFactories — Third-level cache: ObjectFactory<?> lambdas that can create early bean references

Three-Level Cache: Solving Circular Dependencies

This is one of Spring's most clever internal mechanisms. When Bean A depends on Bean B, and Bean B depends on Bean A:

@Service
public class OrderService {
    @Autowired
    private PaymentService paymentService; // Depends on PaymentService
}

@Service
public class PaymentService {
    @Autowired
    private OrderService orderService; // Circular! Depends on OrderService
}

Spring resolves this with three maps (the "three-level cache"):

  1. singletonObjects (Level 1) — Fully initialized beans. Final destination.
  2. earlySingletonObjects (Level 2) — Partially created beans (instantiated but not yet injected). Exposed early.
  3. singletonFactories (Level 3) — ObjectFactory lambdas that wrap the early bean reference (needed for AOP proxies).

Resolution Flow:

Create OrderService → Put ObjectFactory in L3 → Inject PaymentService → Create PaymentService → Needs OrderService → Get from L3 factory → Move to L2 → Complete both → L1
⚠️ Constructor Injection Breaks Circular Dependencies

The three-level cache only works for field/setter injection. With constructor injection, the bean can't be instantiated at all without its dependency — there's no "partially created" state. Spring will throw BeanCurrentlyInCreationException. This is actually a good thing — circular dependencies are a design smell, and constructor injection forces you to fix them.

BeanDefinition: The Blueprint

Every bean starts as a BeanDefinition — metadata describing HOW to create the bean:

public interface BeanDefinition {
    String getBeanClassName();          // "com.example.OrderService"
    String getScope();                  // "singleton" or "prototype"
    boolean isLazyInit();               // Delay creation?
    String getInitMethodName();          // Call after creation
    String getDestroyMethodName();       // Call before destruction
    ConstructorArgumentValues getConstructorArgumentValues();
    MutablePropertyValues getPropertyValues();
    String getFactoryMethodName();       // For @Bean methods
    boolean isPrimary();                // @Primary annotation
}

When you annotate a class with @Component, Spring creates a ScannedGenericBeanDefinition. When you use @Bean in a config class, it creates a ConfigurationClassBeanDefinition. These are registered into the beanDefinitionMap during startup.

How getBean() Works Internally

When you call context.getBean("orderService"), here's the actual execution path inside AbstractBeanFactory.doGetBean():

// Simplified pseudocode of AbstractBeanFactory.doGetBean()
protected <T> T doGetBean(String name, Class<T> requiredType) {
    // 1. Transform name (strip "&" prefix for FactoryBeans, resolve aliases)
    String beanName = transformedBeanName(name);
    
    // 2. Check singleton cache FIRST (fast path)
    Object sharedInstance = getSingleton(beanName);
    if (sharedInstance != null) {
        return getObjectForBeanInstance(sharedInstance, name);
    }
    
    // 3. Check parent BeanFactory (hierarchical containers)
    BeanFactory parentBeanFactory = getParentBeanFactory();
    if (parentBeanFactory != null && !containsBeanDefinition(beanName)) {
        return parentBeanFactory.getBean(name, requiredType);
    }
    
    // 4. Get merged BeanDefinition (handle parent bean definitions)
    RootBeanDefinition mbd = getMergedLocalBeanDefinition(beanName);
    
    // 5. Handle depends-on (create dependencies first)
    String[] dependsOn = mbd.getDependsOn();
    if (dependsOn != null) {
        for (String dep : dependsOn) {
            getBean(dep); // Recursive call!
        }
    }
    
    // 6. Create bean based on scope
    if (mbd.isSingleton()) {
        sharedInstance = getSingleton(beanName, () -> createBean(beanName, mbd));
    } else if (mbd.isPrototype()) {
        Object prototypeInstance = createBean(beanName, mbd);
        return prototypeInstance;
    }
    
    return adaptBeanInstance(name, sharedInstance, requiredType);
}

Industry Production Pattern: Custom BeanFactoryPostProcessor

@Component
public class EncryptedPropertyPostProcessor 
        implements BeanFactoryPostProcessor {
    
    @Override
    public void postProcessBeanFactory(
            ConfigurableListableBeanFactory beanFactory) {
        
        // This runs BEFORE any beans are created
        // Use case: decrypt encrypted properties from vault
        
        String[] beanNames = beanFactory.getBeanDefinitionNames();
        for (String beanName : beanNames) {
            BeanDefinition bd = beanFactory.getBeanDefinition(beanName);
            MutablePropertyValues pvs = bd.getPropertyValues();
            
            for (PropertyValue pv : pvs.getPropertyValueList()) {
                if (pv.getValue() instanceof String val 
                        && val.startsWith("ENC(")) {
                    // Decrypt before bean instantiation
                    String decrypted = decrypt(val);
                    pvs.addPropertyValue(pv.getName(), decrypted);
                }
            }
        }
    }
}
🏢 Industry Usage

Netflix uses custom BeanFactoryPostProcessors to dynamically modify bean definitions based on region-specific configurations. Spring Cloud Vault uses this mechanism to inject secrets from HashiCorp Vault before beans are created. This is the hook that makes Spring infinitely extensible.

Common Mistakes

  • Using new to create Spring-managed beans — If you do new OrderService(), Spring doesn't manage it. No injection, no AOP, no lifecycle callbacks. Always let the container create beans.
  • Confusing BeanFactory with ApplicationContext — In Spring Boot, you always get an ApplicationContext. Don't use raw BeanFactory unless building a framework.
  • Ignoring circular dependency warnings — Spring 6+ / Boot 3+ prohibits circular references by default. Refactor with @Lazy or redesign.
  • Heavy logic in constructors — The container might call your constructor during startup. Expensive I/O in constructors delays application start.

✅ You Truly Understand IoC Container When...

You can explain why calling new MyService() bypasses all Spring features (AOP, transactions, events), and you can trace the exact path from @Autowired annotation to the three-level cache resolution that satisfies it.

🧪 Interview Challenge

Question: "Why does Spring need THREE levels of cache for circular dependency resolution? Why not just two?" Answer: Level 3 (ObjectFactory) is needed because of AOP — the early reference might need to be a proxy, not the raw object. The factory decides whether to return the raw bean or its AOP proxy.
