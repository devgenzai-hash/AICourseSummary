Bean Lifecycle & Callbacks

Every step from instantiation to destruction — the 11 phases a bean goes through and every hook you can use to intercept them.

Core Concept Spring Framework Internals
🏥 Daily-Life Analogy: Hospital Patient Journey

A bean's lifecycle is like a patient going through a hospital: Registration (BeanDefinition), Triage (BeanPostProcessor.before), Admission (instantiation), Vitals Check (property population), Doctor Consultation (initialization callbacks), Treatment (ready for use), and finally Discharge (destruction). At each stage, different specialists (PostProcessors) can intervene.

The Complete Bean Lifecycle — All 11 Phases

// The EXACT order Spring processes a bean:

// Phase 1: Instantiation
//   → Constructor called (via reflection or CGLIB)

// Phase 2: Populate Properties
//   → @Autowired fields injected
//   → @Value properties resolved
//   → Setter injection called

// Phase 3: BeanNameAware.setBeanName()
// Phase 4: BeanFactoryAware.setBeanFactory()
// Phase 5: ApplicationContextAware.setApplicationContext()

// Phase 6: BeanPostProcessor.postProcessBeforeInitialization()
//   → @PostConstruct is processed HERE by CommonAnnotationBeanPostProcessor

// Phase 7: InitializingBean.afterPropertiesSet()

// Phase 8: Custom init-method (from @Bean(initMethod="..."))

// Phase 9: BeanPostProcessor.postProcessAfterInitialization()
//   → AOP proxies are created HERE
//   → @Async proxies created HERE
//   → @Transactional proxies created HERE

// ═══════ BEAN IS NOW READY FOR USE ═══════

// Phase 10: @PreDestroy (on shutdown)
// Phase 11: DisposableBean.destroy() / custom destroy-method

Each Phase in Detail

Phase 1-2: Instantiation & Property Population

@Service
public class OrderService {
    
    private final OrderRepository repo; // Injected in Phase 2
    
    // Phase 1: Constructor called
    public OrderService(OrderRepository repo) {
        System.out.println("1. Constructor — bean instantiated");
        this.repo = repo;
        // NOTE: With constructor injection, Phase 1 and 2 happen together
        // With field injection, the field is null during constructor!
    }
    
    @Autowired
    private PaymentGateway gateway; // Injected AFTER constructor (Phase 2)
}

Phase 3-5: Aware Interfaces

@Service
public class AwareBean implements 
        BeanNameAware, BeanFactoryAware, ApplicationContextAware {
    
    private String beanName;
    private BeanFactory factory;
    private ApplicationContext context;
    
    @Override
    public void setBeanName(String name) {
        // Phase 3: Spring tells you your own bean name
        this.beanName = name; // "awareBean"
    }
    
    @Override
    public void setBeanFactory(BeanFactory factory) {
        // Phase 4: Access to the BeanFactory (rarely needed)
        this.factory = factory;
    }
    
    @Override
    public void setApplicationContext(ApplicationContext ctx) {
        // Phase 5: Access to full ApplicationContext
        // Use case: publish events, access resources
        this.context = ctx;
    }
}
⚠️ Avoid Aware Interfaces in Business Code

Implementing ApplicationContextAware couples your bean to Spring. In production, prefer @Autowired ApplicationContext or better yet, inject only what you need. Aware interfaces are for framework-level code (custom annotations, dynamic proxies).

Phase 6-9: The PostProcessor Dance

@Component
public class TimingBeanPostProcessor implements BeanPostProcessor {
    
    @Override
    public Object postProcessBeforeInitialization(
            Object bean, String beanName) {
        // Phase 6: Called BEFORE @PostConstruct
        // The bean exists, properties are set, but not yet initialized
        if (bean.getClass().isAnnotationPresent(Timed.class)) {
            // Record start time for initialization timing
        }
        return bean; // MUST return bean (or a replacement!)
    }
    
    @Override
    public Object postProcessAfterInitialization(
            Object bean, String beanName) {
        // Phase 9: Called AFTER all initialization
        // THIS is where proxies are created!
        // You can return a completely different object here
        
        if (bean.getClass().isAnnotationPresent(Timed.class)) {
            // Return a JDK/CGLIB proxy that adds timing
            return createTimingProxy(bean);
        }
        return bean;
    }
}

The Three Initialization Callbacks (Phases 6, 7, 8)

@Service
public class CacheService implements InitializingBean {
    
    @Autowired
    private RedisTemplate redis;
    
    // Called in Phase 6 (via CommonAnnotationBeanPostProcessor)
    @PostConstruct
    public void postConstruct() {
        System.out.println("1st: @PostConstruct — redis is available here");
        // Good for: lightweight initialization using injected deps
    }
    
    // Called in Phase 7
    @Override
    public void afterPropertiesSet() {
        System.out.println("2nd: InitializingBean — Spring interface callback");
        // Couples to Spring — prefer @PostConstruct in app code
    }
    
    // Called in Phase 8 (configured externally)
    public void customInit() {
        System.out.println("3rd: custom init-method");
        // Used when you can't modify the class (third-party libs)
    }
}

// Configuration for custom init-method:
@Bean(initMethod = "customInit", destroyMethod = "customDestroy")
public CacheService cacheService() {
    return new CacheService();
}

Destruction Phase (Application Shutdown)

@Service
public class ConnectionPoolService implements DisposableBean {
    
    private HikariDataSource dataSource;
    
    @PreDestroy
    public void preDestroy() {
        // Called first during shutdown
        log.info("Draining active connections...");
        dataSource.getHikariPoolMXBean().softEvictConnections();
    }
    
    @Override
    public void destroy() {
        // Called second
        log.info("Closing datasource");
        dataSource.close();
    }
}
💡 Prototype Beans Don't Get Destroyed!

Spring does NOT call @PreDestroy or destroy() on prototype-scoped beans. Once the container hands you a prototype instance, it forgets about it. You must manage cleanup yourself. This is a common source of memory leaks.

Industry Pattern: SmartInitializingSingleton

@Component
public class EndpointRegistry implements SmartInitializingSingleton {
    
    @Autowired
    private List<RestEndpoint> endpoints;
    
    @Override
    public void afterSingletonsInstantiated() {
        // Called AFTER ALL singletons are fully created
        // Unlike @PostConstruct which fires per-bean,
        // this guarantees every other bean is ready
        
        // Industry use: register all endpoints with service mesh
        endpoints.forEach(ep -> serviceMesh.register(ep));
    }
}

✅ You Truly Understand Bean Lifecycle When...

You can explain why @Transactional doesn't work when called from within the same class (the proxy is created in Phase 9 — AFTER initialization — so internal calls bypass it), and you know the exact order: @PostConstruct → afterPropertiesSet() → init-method.

🧪 Interview Challenge

"If you have a bean with both @PostConstruct and InitializingBean, which runs first?" — @PostConstruct always runs first. It's processed by CommonAnnotationBeanPostProcessor in Phase 6 (before), while afterPropertiesSet() is Phase 7.
