Custom Spring Boot Starters

How to build reusable auto-configured libraries that integrate seamlessly — the same mechanism that powers spring-boot-starter-web and spring-boot-starter-data-jpa.

advanced spring production
🔌 The USB Device Analogy

A custom starter is like a USB device. When you plug a USB keyboard into your computer, the OS detects it (@ConditionalOnClass), loads the appropriate driver (@AutoConfiguration), applies default settings (@ConfigurationProperties), but lets you override them in System Preferences (@ConditionalOnMissingBean). The keyboard manufacturer ships the device + driver together (starter + autoconfigure modules). You don't configure anything manually — plug it in and it works. That's exactly what a well-built starter does: add the dependency, and everything auto-configures.

1. Anatomy of a Starter: Two Modules

A proper Spring Boot starter consists of two separate modules:

Module Purpose Contains
{company}-spring-boot-starter Dependency aggregator (what users add to their pom.xml) Only pom.xml with dependencies — NO code
{company}-spring-boot-autoconfigure The actual auto-configuration logic @AutoConfiguration classes, @ConfigurationProperties, META-INF registration 
// Project structure:
//
// acme-spring-boot-starter/          ← Starter module
//   └── pom.xml                       ← Just dependencies
//
// acme-spring-boot-autoconfigure/     ← Autoconfigure module
//   ├── src/main/java/
//   │   └── com/acme/autoconfigure/
//   │       ├── AcmeAutoConfiguration.java
//   │       └── AcmeProperties.java
//   └── src/main/resources/
//       └── META-INF/
//           └── spring/
//               └── org.springframework.boot.autoconfigure.AutoConfiguration.imports

// ═══ Starter pom.xml — just pulls in dependencies ═══
<project>
    <artifactId>acme-spring-boot-starter</artifactId>
    <dependencies>
        <dependency>
            <groupId>com.acme</groupId>
            <artifactId>acme-spring-boot-autoconfigure</artifactId>
        </dependency>
        <dependency>
            <groupId>com.acme</groupId>
            <artifactId>acme-client-library</artifactId>
        </dependency>
    </dependencies>
</project>
🔍 Naming Convention

Official Spring starters: spring-boot-starter-{name}. Third-party starters: {name}-spring-boot-starter. This isn't enforced but is a strong community convention documented by Spring Boot. Examples: mybatis-spring-boot-starter, camel-spring-boot-starter.

2. Creating the Auto-Configuration Class

// ═══ Boot 3.x: Use @AutoConfiguration ═══
@AutoConfiguration
@ConditionalOnClass(AcmeClient.class)  // Only activate if library is on classpath
@EnableConfigurationProperties(AcmeProperties.class)
public class AcmeAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean  // Users can override by defining their own
    public AcmeClient acmeClient(AcmeProperties properties) {
        return new AcmeClient(
            properties.getEndpoint(),
            properties.getApiKey(),
            properties.getTimeout()
        );
    }

    @Bean
    @ConditionalOnMissingBean
    @ConditionalOnProperty(
        prefix = "acme",
        name = "health.enabled",
        havingValue = "true",
        matchIfMissing = true  // enabled by default
    )
    public AcmeHealthIndicator acmeHealthIndicator(AcmeClient client) {
        return new AcmeHealthIndicator(client);
    }
}

// ═══ Boot 2.x equivalent: @Configuration + spring.factories ═══
@Configuration("acmeAutoConfiguration")
@ConditionalOnClass(AcmeClient.class)
@EnableConfigurationProperties(AcmeProperties.class)
public class AcmeAutoConfiguration {
    // Same beans...
}
// Registered in META-INF/spring.factories:
// org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
//   com.acme.autoconfigure.AcmeAutoConfiguration

3. @ConfigurationProperties for Starter Configuration

@ConfigurationProperties(prefix = "acme")
public class AcmeProperties {

    /**
     * The endpoint URL for the Acme service.
     */
    private String endpoint = "https://api.acme.com/v2";

    /**
     * API key for authentication. Required.
     */
    private String apiKey;

    /**
     * Connection timeout.
     */
    private Duration timeout = Duration.ofSeconds(5);

    /**
     * Health check configuration.
     */
    private final Health health = new Health();

    // Getters and setters...
    public String getEndpoint() { return endpoint; }
    public void setEndpoint(String endpoint) { this.endpoint = endpoint; }
    public String getApiKey() { return apiKey; }
    public void setApiKey(String apiKey) { this.apiKey = apiKey; }
    public Duration getTimeout() { return timeout; }
    public void setTimeout(Duration timeout) { this.timeout = timeout; }
    public Health getHealth() { return health; }

    public static class Health {
        private boolean enabled = true;
        public boolean isEnabled() { return enabled; }
        public void setEnabled(boolean enabled) { this.enabled = enabled; }
    }
}

// Users configure via application.yml:
// acme:
//   endpoint: https://custom.acme.com/v3
//   api-key: ${ACME_API_KEY}
//   timeout: 10s
//   health:
//     enabled: false

4. Providing Sensible Defaults with @ConditionalOnMissingBean

@AutoConfiguration
@ConditionalOnClass(AcmeClient.class)
@EnableConfigurationProperties(AcmeProperties.class)
public class AcmeAutoConfiguration {

    // ═══ Pattern: provide default, allow override ═══

    @Bean
    @ConditionalOnMissingBean(AcmeClient.class)
    public AcmeClient acmeClient(AcmeProperties props) {
        // This bean is ONLY created if the user hasn't defined their own
        return AcmeClient.builder()
            .endpoint(props.getEndpoint())
            .apiKey(props.getApiKey())
            .timeout(props.getTimeout())
            .build();
    }

    @Bean
    @ConditionalOnMissingBean(AcmeSerializer.class)
    public AcmeSerializer acmeSerializer() {
        // Default: Jackson-based serialization
        return new JacksonAcmeSerializer();
    }
}

// ═══ User's application — overriding the default ═══
@Configuration
public class MyAcmeConfig {

    @Bean
    public AcmeClient acmeClient() {
        // This WINS over the auto-configured bean
        // because user beans are processed BEFORE auto-configuration
        return AcmeClient.builder()
            .endpoint("https://custom-proxy.internal/acme")
            .retries(5)
            .circuitBreaker(true)
            .build();
    }
}
🔍 Key Insight

@ConditionalOnMissingBean is the cornerstone of starter design. It implements the "opinionated defaults" philosophy: your starter works out of the box with zero config, but users can override ANY bean by simply defining their own. Auto-configuration classes are processed AFTER user-defined @Configuration classes, ensuring user beans always take precedence.

5. Testing Your Auto-Configuration

class AcmeAutoConfigurationTest {

    private final ApplicationContextRunner contextRunner =
        new ApplicationContextRunner()
            .withConfiguration(
                AutoConfigurations.of(AcmeAutoConfiguration.class));

    @Test
    void shouldCreateClientWhenClassPresent() {
        contextRunner
            .withPropertyValues("acme.api-key=test-key")
            .run(context -> {
                assertThat(context).hasSingleBean(AcmeClient.class);
                assertThat(context).hasSingleBean(AcmeHealthIndicator.class);
            });
    }

    @Test
    void shouldNotCreateClientWhenClassMissing() {
        contextRunner
            .withClassLoader(new FilteredClassLoader(AcmeClient.class))
            .run(context -> {
                assertThat(context).doesNotHaveBean(AcmeClient.class);
            });
    }

    @Test
    void shouldBackOffWhenUserDefinesOwnBean() {
        contextRunner
            .withUserConfiguration(CustomClientConfig.class)
            .run(context -> {
                assertThat(context).hasSingleBean(AcmeClient.class);
                // Verify it's the USER's bean, not ours
                assertThat(context.getBean(AcmeClient.class).getEndpoint())
                    .isEqualTo("https://custom.endpoint");
            });
    }

    @Test
    void shouldDisableHealthWhenPropertySet() {
        contextRunner
            .withPropertyValues(
                "acme.api-key=test",
                "acme.health.enabled=false")
            .run(context -> {
                assertThat(context).doesNotHaveBean(AcmeHealthIndicator.class);
            });
    }

    @Configuration
    static class CustomClientConfig {
        @Bean
        AcmeClient acmeClient() {
            return new AcmeClient("https://custom.endpoint", "key", null);
        }
    }
}

7. Proper Dependency Management

<!-- autoconfigure module pom.xml -->
<project>
    <artifactId>acme-spring-boot-autoconfigure</artifactId>

    <dependencies>
        <!-- Spring Boot — provided, not transitive -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-autoconfigure</artifactId>
        </dependency>

        <!-- The library you're wrapping — OPTIONAL dependency -->
        <!-- Users must explicitly add it (or the starter does) -->
        <dependency>
            <groupId>com.acme</groupId>
            <artifactId>acme-client-library</artifactId>
            <optional>true</optional>
        </dependency>

        <!-- Annotation processor for config metadata -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-configuration-processor</artifactId>
            <optional>true</optional>
        </dependency>

        <!-- Test dependencies -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>
</project>
⚠️ Don't Leak Dependencies

Mark dependencies as <optional>true</optional> in the autoconfigure module. This prevents them from becoming transitive dependencies of consumers. The starter module is where you declare non-optional dependencies — it's the "battery pack" that brings everything needed. The autoconfigure module should compile against APIs without forcing them onto consumers.

8. Industry Pattern: Company-Wide Starters

// ═══════════════════════════════════════════════════════════
// Real-world: Netflix, Uber, and large companies create
// internal starters to enforce standards across 100s of services
// ═══════════════════════════════════════════════════════════

// company-platform-spring-boot-starter brings in:
//   ├── company-logging-spring-boot-starter
//   │     → Structured JSON logging, correlation IDs, log shipping
//   ├── company-metrics-spring-boot-starter
//   │     → Prometheus metrics, standard dashboards, SLO tracking
//   ├── company-security-spring-boot-starter
//   │     → OAuth2 resource server, RBAC, audit logging
//   ├── company-tracing-spring-boot-starter
//   │     → Distributed tracing, span propagation, sampling
//   └── company-resilience-spring-boot-starter
//         → Circuit breakers, retries, rate limiting, bulkheads

@AutoConfiguration
@ConditionalOnClass(MeterRegistry.class)
@AutoConfigureAfter(MetricsAutoConfiguration.class)
public class CompanyMetricsAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public MeterRegistryCustomizer<MeterRegistry> companyMetricsCustomizer(
            Environment env) {
        return registry -> registry.config()
            .commonTags(
                "service", env.getProperty("spring.application.name"),
                "team", env.getProperty("company.team", "unknown"),
                "env", env.getProperty("company.environment", "local")
            );
    }

    @Bean
    @ConditionalOnMissingBean
    public CompanySloTracker sloTracker(MeterRegistry registry) {
        // Automatically tracks p99 latency, error rate, availability
        return new CompanySloTracker(registry);
    }
}

// Service teams just add ONE dependency:
// <dependency>
//   <groupId>com.company.platform</groupId>
//   <artifactId>company-platform-spring-boot-starter</artifactId>
//   <version>${platform.version}</version>
// </dependency>
//
// Result: logging, metrics, security, tracing, resilience — all configured
// All 200+ services behave consistently. Platform team upgrades ONE version.

🎯 Key Takeaways

  • Two modules: starter (dependency aggregator, no code) + autoconfigure (the actual logic) — separation enables optional dependencies
  • Naming: third-party starters use {name}-spring-boot-starter, not spring-boot-starter-{name}
  • @AutoConfiguration (Boot 3.x) or @Configuration + spring.factories (Boot 2.x) for the auto-config class
  • @ConditionalOnClass gates activation on library presence — starter only activates if the user actually has the library
  • @ConditionalOnMissingBean implements "provide defaults, allow override" — the cornerstone of starter design
  • ApplicationContextRunner is the testing tool — fast, no real Spring context, tests all conditional paths
  • Registration: Boot 3.x uses .imports file (one class per line), Boot 2.x uses spring.factories
  • Industry pattern: company-wide platform starters enforce standards (logging, metrics, security) across hundreds of microservices

🏋️ Mastery Check

  1. Why does a starter need TWO modules? What breaks if you combine them into one?
  2. Your auto-configured bean should be created AFTER Spring's DataSourceAutoConfiguration. How do you enforce ordering?
  3. A user reports that your starter's bean conflicts with their custom bean. What's the most likely cause and fix?
  4. Explain why dependencies in the autoconfigure module should be <optional>true</optional> but the starter module should declare them non-optional.
  5. Design a starter that auto-configures a caching layer: Redis if available, Caffeine as fallback, simple HashMap if neither is present.

💼 Interview Challenge

"Your company has 200 microservices. You want to add standardized distributed tracing, structured logging, and health checks to all of them with minimal code changes per service. Design the solution."

Expert answer framework:

  1. Create a platform starter: company-platform-spring-boot-starter that aggregates tracing, logging, and health starters.
  2. Use @ConditionalOnClass: Each sub-starter only activates if its required libraries are on the classpath.
  3. @ConditionalOnMissingBean everywhere: Teams that need custom behavior can override any bean — no conflicts.
  4. Version management: Use a BOM (Bill of Materials) so all services share compatible versions. One platform team PR updates all 200 services.
  5. @ConditionalOnProperty for opt-out: company.tracing.enabled=false lets teams disable specific features without removing the dependency.
