Handler Mapping & Adapters

How Spring matches an incoming URL to the right controller method — the mapping registry, path matching algorithms, and the adapter pattern that invokes handlers.

intermediate spring internal
📞 The Call Center Routing Analogy

HandlerMapping is like the automated phone menu at a call center. When you dial in, the system matches your input ("Press 1 for billing, 2 for support") to the right department — that's the mapping. HandlerAdapter is the headset interface — it doesn't matter if the agent uses a desktop phone, mobile, or VoIP; the adapter normalizes how the call is connected. The call center (DispatcherServlet) doesn't need to know the internal workings of each department — it just needs the phone menu to route and the adapter to connect.

1. HandlerMapping Interface

// ═══ The core contract ═══
public interface HandlerMapping {

    /**
     * Return a HandlerExecutionChain for this request,
     * or null if no match found.
     */
    @Nullable
    HandlerExecutionChain getHandler(HttpServletRequest request)
        throws Exception;
}

// DispatcherServlet iterates ALL registered HandlerMappings in order:
for (HandlerMapping mapping : this.handlerMappings) {
    HandlerExecutionChain handler = mapping.getHandler(request);
    if (handler != null) return handler; // First match wins!
}

2. RequestMappingHandlerMapping: The Primary Mapper

// ═══ At startup: scans all @Controller beans ═══
// RequestMappingHandlerMapping implements InitializingBean
// afterPropertiesSet() → initHandlerMethods()

protected void initHandlerMethods() {
    // Get ALL beans from the ApplicationContext
    for (String beanName : getCandidateBeanNames()) {
        Class<?> beanType = obtainApplicationContext()
            .getType(beanName);

        // Check if bean has @Controller or @RequestMapping at class level
        if (isHandler(beanType)) {
            detectHandlerMethods(beanName);
        }
    }
}

// isHandler() checks for:
protected boolean isHandler(Class<?> beanType) {
    return AnnotatedElementUtils.hasAnnotation(beanType, Controller.class) ||
           AnnotatedElementUtils.hasAnnotation(beanType, RequestMapping.class);
}

// For each handler method, builds a RequestMappingInfo:
protected void detectHandlerMethods(Object handler) {
    Class<?> handlerType = (handler instanceof String beanName)
        ? obtainApplicationContext().getType(beanName) : handler.getClass();

    Map<Method, RequestMappingInfo> methods =
        MethodIntrospector.selectMethods(handlerType,
            (Method method) -> getMappingForMethod(method, handlerType));

    methods.forEach((method, mapping) -> {
        registerHandlerMethod(handler, method, mapping);
        // Stored in MappingRegistry as: RequestMappingInfo → HandlerMethod
    });
}
🔍 The MappingRegistry

All mappings are stored in an internal MappingRegistry — a thread-safe data structure that maps RequestMappingInfo objects to HandlerMethod instances. At runtime, matching is a lookup operation, not a scan. You can see all registered mappings at /actuator/mappings endpoint.

3. RequestMappingInfo: All Conditions Must Match

// ═══ RequestMappingInfo combines multiple conditions ═══
// ALL conditions must match for a request to map to this handler

@RequestMapping(
    path = "/api/users/{id}",        // PatternsRequestCondition
    method = RequestMethod.GET,       // RequestMethodsRequestCondition
    params = "version=2",             // ParamsRequestCondition
    headers = "X-API-VERSION=2",      // HeadersRequestCondition
    consumes = "application/json",    // ConsumesRequestCondition
    produces = "application/json"     // ProducesRequestCondition
)
public User getUser(@PathVariable Long id) { ... }

// ═══ RequestMappingInfo matching algorithm ═══
public RequestMappingInfo getMatchingCondition(HttpServletRequest request) {
    RequestMethodsRequestCondition methods =
        this.methodsCondition.getMatchingCondition(request);
    if (methods == null) return null;  // Method doesn't match → skip

    ParamsRequestCondition params =
        this.paramsCondition.getMatchingCondition(request);
    if (params == null) return null;  // Params don't match → skip

    HeadersRequestCondition headers =
        this.headersCondition.getMatchingCondition(request);
    if (headers == null) return null;

    ConsumesRequestCondition consumes =
        this.consumesCondition.getMatchingCondition(request);
    if (consumes == null) return null;

    ProducesRequestCondition produces =
        this.producesCondition.getMatchingCondition(request);
    if (produces == null) return null;

    PatternsRequestCondition patterns =
        this.patternsCondition.getMatchingCondition(request);
    if (patterns == null) return null;

    // ALL conditions passed → return matching info
    return new RequestMappingInfo(patterns, methods, params,
        headers, consumes, produces, this.customCondition);
}

4. Path Matching: AntPathMatcher vs PathPatternParser

Feature AntPathMatcher (Legacy) PathPatternParser (Boot 3.x Default)
Algorithm String-based regex matching at runtime Pre-compiled pattern tree, segment-by-segment
Performance Slower — pattern compiled on each request 6-8x faster — compiled once at startup
Wildcard patterns ? * ** ? * ** {*pathVariable}
Suffix matching Supported (/users.json) Not supported (security risk)
Trailing slash Matches with or without / Strict — /users ≠ /users/ by default
Capture groups {name:regex} {name:regex} + {*rest} for tail capture 
// ═══ Pattern examples ═══

// Basic path variable
@GetMapping("/users/{id}")       // matches /users/42

// Regex constraint on path variable
@GetMapping("/users/{id:\\d+}")  // matches /users/42, NOT /users/abc

// Single wildcard (one path segment)
@GetMapping("/users/*/orders")  // matches /users/john/orders

// Double wildcard (zero or more segments) — AntPathMatcher
@GetMapping("/api/**")           // matches /api/anything/deep/nested

// Tail capture (PathPatternParser) — captures rest of path
@GetMapping("/files/{*path}")    // matches /files/a/b/c.txt → path="a/b/c.txt"

// ═══ Switching to AntPathMatcher (if needed) ═══
// application.properties:
// spring.mvc.pathmatch.matching-strategy=ant_path_matcher
⚠️ Boot 3.x Breaking Change

PathPatternParser does NOT support suffix pattern matching (e.g., /users.json) or trailing slash matching by default. If your API relied on these, you must either switch back to ant_path_matcher strategy or explicitly add route declarations. Suffix matching was removed because it caused security vulnerabilities (path traversal via /api/users.json..%2F..%2Fetc/passwd).

5. HandlerAdapter: The Adapter Pattern

// ═══ HandlerAdapter interface ═══
public interface HandlerAdapter {

    // Can this adapter handle this type of handler?
    boolean supports(Object handler);

    // Invoke the handler and return ModelAndView
    @Nullable
    ModelAndView handle(HttpServletRequest request,
                        HttpServletResponse response,
                        Object handler) throws Exception;
}

// ═══ Why the adapter pattern? ═══
// Handlers can be MANY different types:
//   - HandlerMethod (annotated @RequestMapping methods)
//   - Controller interface (legacy)
//   - HttpRequestHandler (simple servlet-like)
//   - RouterFunction (functional endpoints)
// The adapter normalizes invocation to a single interface.

// DispatcherServlet finds the right adapter:
protected HandlerAdapter getHandlerAdapter(Object handler) {
    for (HandlerAdapter adapter : this.handlerAdapters) {
        if (adapter.supports(handler)) {
            return adapter;
        }
    }
    throw new ServletException("No adapter for handler");
}
HandlerAdapter Handles How It Invokes
RequestMappingHandlerAdapter HandlerMethod (@RequestMapping methods) Resolves arguments, invokes via reflection, processes return value
HandlerFunctionAdapter RouterFunction handlers Calls HandlerFunction.handle(ServerRequest)
HttpRequestHandlerAdapter HttpRequestHandler (resource serving) Calls handleRequest(request, response)
SimpleControllerHandlerAdapter Controller interface (legacy) Calls handleRequest(request, response)

6. HandlerMethodArgumentResolver: Populating Method Parameters

// ═══ How RequestMappingHandlerAdapter resolves method arguments ═══
// Each annotation/type has a dedicated resolver:

public interface HandlerMethodArgumentResolver {
    boolean supportsParameter(MethodParameter parameter);
    Object resolveArgument(MethodParameter parameter,
                           ModelAndViewContainer mavContainer,
                           NativeWebRequest webRequest,
                           WebDataBinderFactory binderFactory);
}

// ═══ Built-in resolvers (26+ registered by default) ═══
@GetMapping("/users/{id}")
public ResponseEntity<User> getUser(
    @PathVariable Long id,                // PathVariableMethodArgumentResolver
    @RequestParam String fields,          // RequestParamMethodArgumentResolver
    @RequestHeader("X-Tenant") String tenant, // RequestHeaderMethodArgumentResolver
    @CookieValue String session,          // ServletCookieValueMethodArgumentResolver
    HttpServletRequest request,           // ServletRequestMethodArgumentResolver
    Principal principal                   // PrincipalMethodArgumentResolver
) { ... }

@PostMapping("/users")
public User createUser(
    @RequestBody UserDto dto,             // RequestResponseBodyMethodProcessor
    @Valid @ModelAttribute UserForm form  // ModelAttributeMethodProcessor
) { ... }

7. Custom HandlerMethodArgumentResolver

// ═══ Example: Resolve the current authenticated tenant ═══

// Step 1: Create a custom annotation
@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface CurrentTenant {}

// Step 2: Implement the resolver
public class CurrentTenantArgumentResolver
        implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        return parameter.hasParameterAnnotation(CurrentTenant.class);
    }

    @Override
    public Object resolveArgument(
            MethodParameter parameter,
            ModelAndViewContainer mavContainer,
            NativeWebRequest webRequest,
            WebDataBinderFactory binderFactory) {

        HttpServletRequest request =
            webRequest.getNativeRequest(HttpServletRequest.class);
        String tenantId = request.getHeader("X-Tenant-ID");

        if (tenantId == null) {
            throw new MissingTenantException("X-Tenant-ID header required");
        }
        return tenantService.resolve(tenantId);
    }
}

// Step 3: Register it
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addArgumentResolvers(
            List<HandlerMethodArgumentResolver> resolvers) {
        resolvers.add(new CurrentTenantArgumentResolver());
    }
}

// Step 4: Use it in controllers — clean and reusable
@GetMapping("/data")
public List<Data> getData(@CurrentTenant Tenant tenant) {
    return dataService.findByTenant(tenant);
}

8. HandlerMethodReturnValueHandler: Processing Results

// ═══ After handler method executes, return value is processed ═══
public interface HandlerMethodReturnValueHandler {
    boolean supportsReturnType(MethodParameter returnType);
    void handleReturnValue(Object returnValue,
                           MethodParameter returnType,
                           ModelAndViewContainer mavContainer,
                           NativeWebRequest webRequest);
}

// Common return value handlers:
// ─────────────────────────────────────────────────────────
// Return Type              → Handler
// ─────────────────────────────────────────────────────────
// @ResponseBody Object     → RequestResponseBodyMethodProcessor
//                            (uses HttpMessageConverter → JSON)
// ResponseEntity<T>       → HttpEntityMethodProcessor
// String (view name)       → ViewNameMethodReturnValueHandler
// ModelAndView             → ModelAndViewMethodReturnValueHandler
// void                     → (response already written or 204)
// DeferredResult<T>       → DeferredResultMethodReturnValueHandler
// CompletableFuture<T>    → (handled as DeferredResult)
🔍 @ResponseBody Short-Circuit

When a handler method is annotated with @ResponseBody (or the class with @RestController), the RequestResponseBodyMethodProcessor writes directly to the response via HttpMessageConverter and sets mavContainer.setRequestHandled(true). This tells DispatcherServlet to skip view resolution entirely — no ViewResolver is consulted.

🎯 Key Takeaways

  • HandlerMapping.getHandler() returns a HandlerExecutionChain (handler + interceptors) — first non-null result wins
  • RequestMappingHandlerMapping scans @Controller beans at startup, builds a registry of RequestMappingInfo → HandlerMethod
  • RequestMappingInfo combines 6 conditions (path, method, params, headers, consumes, produces) — ALL must match
  • PathPatternParser (Boot 3.x default) is 6-8x faster than AntPathMatcher — pre-compiled at startup, no suffix matching
  • HandlerAdapter decouples DispatcherServlet from handler types — adapter pattern allows different handler styles (annotated, functional, legacy)
  • ArgumentResolvers turn HTTP request data into method parameters — 26+ built-in, extensible via WebMvcConfigurer
  • ReturnValueHandlers process method return values — @ResponseBody bypasses view resolution entirely

💼 Interview Challenge

"A developer adds @GetMapping('/users/{name}') and @GetMapping('/users/{id}') on different methods. What happens? How would you fix it?"

Expert answer framework:

  1. Ambiguous mapping error at startup: Both patterns are identical from a path-matching perspective — {name} and {id} are both single-segment wildcards. Spring cannot distinguish them.
  2. Fix option 1: Use regex constraints: /users/{id:\\d+} vs /users/{name:[a-zA-Z]+} — now they're distinct patterns.
  3. Fix option 2: Different path structure: /users/by-id/{id} vs /users/by-name/{name}.
  4. Fix option 3: Single handler that inspects the variable: parse as Long, if it fails treat as name lookup.
  5. Root cause understanding: Path variables are just "match one segment" — the variable name is irrelevant for matching. Only the pattern structure and constraints matter.
