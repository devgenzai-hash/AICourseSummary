spring.factories & META-INF

The SPI (Service Provider Interface) mechanism that makes Spring Boot's plugin architecture possible — how JARs register their auto-configurations without classpath scanning.

intermediate spring internal
📋 The Yellow Pages Analogy

Imagine each business in a city publishes its services in a shared Yellow Pages directory. When you need a plumber, you don't walk door-to-door asking "are you a plumber?" — you open the directory and find all registered plumbers instantly. spring.factories is Spring Boot's Yellow Pages: each JAR "publishes" what services it provides (auto-configs, listeners, initializers) in a well-known file. At startup, Spring reads ALL directories from ALL JARs simultaneously — no scanning, no guessing, just explicit registration.

1. META-INF/spring.factories Format (Boot 2.x)

The classic format is a Java properties file where keys are interface/class names and values are comma-separated implementation class names:

# File location: META-INF/spring.factories (inside any JAR)
# Format: key=value1,value2,value3
# Backslash for line continuation

# Auto-configuration classes
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
  com.mycompany.library.autoconfigure.MyServiceAutoConfiguration,\
  com.mycompany.library.autoconfigure.MyRepositoryAutoConfiguration

# Application context initializers
org.springframework.context.ApplicationContextInitializer=\
  com.mycompany.library.init.MyContextInitializer

# Application listeners
org.springframework.context.ApplicationListener=\
  com.mycompany.library.listener.MyStartupListener

# Environment post-processors
org.springframework.boot.env.EnvironmentPostProcessor=\
  com.mycompany.library.env.VaultPropertySourcePostProcessor

# Failure analyzers
org.springframework.boot.diagnostics.FailureAnalyzer=\
  com.mycompany.library.diagnostics.ConnectionFailureAnalyzer

# Auto-configuration import filters (fast pre-filtering)
org.springframework.boot.autoconfigure.AutoConfigurationImportFilter=\
  com.mycompany.library.filter.MyImportFilter
🔍 Key Insight

The same key can appear in spring.factories files across MANY different JARs. SpringFactoriesLoader aggregates all values from all JARs — it doesn't stop at the first match. This is what makes the plugin architecture work: each library JAR contributes its own entries, and Spring Boot merges them all.

2. Spring Boot 3.x: The New Format

Spring Boot 3.x introduced a new, simpler file specifically for auto-configuration registration:

# File: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
# One fully-qualified class name per line
# Comments with # are supported
# No key-value format — just class names

com.mycompany.library.autoconfigure.MyServiceAutoConfiguration
com.mycompany.library.autoconfigure.MyRepositoryAutoConfiguration
com.mycompany.library.autoconfigure.MyWebAutoConfiguration

Why the Change?

Aspect spring.factories (Boot 2.x) AutoConfiguration.imports (Boot 3.x)
Scope Multi-purpose (auto-configs, listeners, initializers, etc.) Auto-configuration only
Format Key=value, comma-separated, backslash continuation One class per line
Parsing complexity Properties parsing + string splitting Line-by-line reading
Merge conflicts Frequent (single key with growing list) Rare (one class per line = easy git merge)
IDE support Generic properties file Dedicated tooling (class completion)
Boot 2.x compat Native Not read by Boot 2.x
⚠️ Migration Note

In Boot 3.x, spring.factories is still used for non-auto-configuration entries (listeners, initializers, failure analyzers, etc.). Only auto-configuration registration moved to the new .imports file. If you're migrating a library, you need BOTH files during the transition period if you support Boot 2.x and 3.x simultaneously.

3. SpringFactoriesLoader — The Loading Mechanism

public final class SpringFactoriesLoader {

    public static final String FACTORIES_RESOURCE_LOCATION =
        "META-INF/spring.factories";

    // Core method: loads ALL factory names for a given type from ALL JARs
    public static List<String> loadFactoryNames(
            Class<?> factoryType, ClassLoader classLoader) {

        String factoryTypeName = factoryType.getName();

        // Load and cache all spring.factories content
        return loadSpringFactories(classLoader)
            .getOrDefault(factoryTypeName, Collections.emptyList());
    }

    private static Map<String, List<String>> loadSpringFactories(
            ClassLoader classLoader) {

        // CHECK CACHE FIRST — loaded only once per classloader
        Map<String, List<String>> result = cache.get(classLoader);
        if (result != null) {
            return result;
        }

        result = new HashMap<>();

        // THE KEY LINE: reads from ALL JARs on classpath
        Enumeration<URL> urls = classLoader.getResources(
            FACTORIES_RESOURCE_LOCATION);

        while (urls.hasMoreElements()) {
            URL url = urls.nextElement();
            // Parse each spring.factories file
            Properties properties = PropertiesLoaderUtils
                .loadProperties(new UrlResource(url));

            for (Map.Entry<?, ?> entry : properties.entrySet()) {
                String factoryTypeName = ((String) entry.getKey()).trim();
                String[] factoryNames = StringUtils
                    .commaDelimitedListToStringArray((String) entry.getValue());

                for (String factoryName : factoryNames) {
                    result.computeIfAbsent(factoryTypeName, k -> new ArrayList<>())
                        .add(factoryName.trim());
                }
            }
        }

        // Cache for subsequent calls
        cache.put(classLoader, result);
        return result;
    }
}
🔍 Key Insight

ClassLoader.getResources() is the magic — it returns URLs from ALL JARs that contain a file at the given path. Unlike getResource() (singular) which returns only the first match, getResources() iterates the entire classpath. This is a standard Java SPI-like pattern used by ServiceLoader as well.

4. What Gets Registered in spring.factories

# All supported factory types in Spring Boot:

# ─── CORE BOOTSTRAPPING ───
org.springframework.boot.autoconfigure.EnableAutoConfiguration
# Auto-configuration classes (moved to .imports file in Boot 3.x)

org.springframework.context.ApplicationContextInitializer
# Runs BEFORE context refresh — modify context before beans load

org.springframework.context.ApplicationListener
# Event listeners registered before context exists

org.springframework.boot.SpringApplicationRunListener
# Hook into SpringApplication lifecycle events

# ─── ENVIRONMENT ───
org.springframework.boot.env.EnvironmentPostProcessor
# Modify Environment (add property sources) before context refresh

org.springframework.boot.env.PropertySourceLoader
# Load custom property file formats (.yaml, .toml, etc.)

# ─── DIAGNOSTICS ───
org.springframework.boot.diagnostics.FailureAnalyzer
# Transform exceptions into human-readable startup error messages

# ─── AUTO-CONFIGURATION SUPPORT ───
org.springframework.boot.autoconfigure.AutoConfigurationImportFilter
# Fast pre-filter before full @Conditional evaluation

org.springframework.boot.autoconfigure.AutoConfigurationImportListener
# Notified when auto-configuration import selection completes

# ─── TESTING ───
org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc
# Test slice configurations

5. Why spring.factories Instead of Classpath Scanning?

Concern Classpath Scanning spring.factories / .imports
Discovery speed O(n) — scans all .class files in packages O(k) — reads only factory files (one per JAR)
Package convention Requires shared base package No package convention needed
Explicit registration Implicit (anything with @Component is found) Explicit (only listed classes are loaded)
Third-party JARs Must be in scan path Self-registering (JAR brings its own factory file)
Ordering control Limited (file system order) Full control via @AutoConfigureOrder
Startup performance Degrades with classpath size Scales well (one small file per JAR)
🔍 Key Insight

The fundamental problem: a third-party library JAR can't assume its package will be in the application's @ComponentScan base packages. By using spring.factories, the library self-registers its contributions — the application just needs the JAR on its classpath, and the auto-config "activates" via the factory mechanism.

6. Caching & Performance

// SpringFactoriesLoader uses a static ConcurrentReferenceHashMap
private static final Map<ClassLoader, Map<String, List<String>>> cache =
    new ConcurrentReferenceHashMap<>();

// First call: reads all META-INF/spring.factories from all JARs
//   → Iterates ClassLoader.getResources()
//   → Parses properties files
//   → Stores aggregated map in cache

// Subsequent calls: instant HashMap lookup
//   → O(1) retrieval from cache

// The cache uses weak references → eligible for GC if ClassLoader is collected
// In practice: loaded once at startup, never re-read

7. Industry Pattern: Shared Library Auto-Registration

The most common real-world use case: creating a shared library that auto-registers beans across multiple microservices.

// ═══════════════════════════════════════════════════════════
// Your shared library: company-commons-spring-boot-starter
// ═══════════════════════════════════════════════════════════

// src/main/java/com/company/commons/autoconfigure/
@AutoConfiguration
@ConditionalOnClass(RestTemplate.class)
public class CompanyHttpAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public RestTemplate companyRestTemplate(
            CompanyHttpProperties properties) {
        RestTemplate template = new RestTemplate();
        // Add company-standard interceptors: tracing, auth, retries
        template.getInterceptors().add(new TracingInterceptor());
        template.getInterceptors().add(new AuthHeaderInterceptor(properties));
        return template;
    }
}

// For Boot 3.x: create this file
// src/main/resources/META-INF/spring/
//   org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.company.commons.autoconfigure.CompanyHttpAutoConfiguration
com.company.commons.autoconfigure.CompanyMetricsAutoConfiguration
com.company.commons.autoconfigure.CompanySecurityAutoConfiguration

// For Boot 2.x backward compat: also create this file
// src/main/resources/META-INF/spring.factories
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
  com.company.commons.autoconfigure.CompanyHttpAutoConfiguration,\
  com.company.commons.autoconfigure.CompanyMetricsAutoConfiguration,\
  com.company.commons.autoconfigure.CompanySecurityAutoConfiguration

// ═══════════════════════════════════════════════════════════
// Any microservice — just add the dependency
// ═══════════════════════════════════════════════════════════

// pom.xml
<dependency>
    <groupId>com.company</groupId>
    <artifactId>company-commons-spring-boot-starter</artifactId>
    <version>2.1.0</version>
</dependency>

// That's it! RestTemplate with tracing + auth is now available
// No @Import, no @ComponentScan changes needed
⚠️ Starter Naming Convention

Official Spring Boot starters use the pattern spring-boot-starter-*. Third-party starters should use *-spring-boot-starter (name first). This isn't enforced technically but is a strong community convention that Spring Boot documentation explicitly recommends.

8. The Loading Mechanism: ClassLoader.getResources()

// How Java finds ALL files at the same path across multiple JARs:

ClassLoader cl = Thread.currentThread().getContextClassLoader();

// getResource() → returns FIRST match only
URL single = cl.getResource("META-INF/spring.factories");

// getResources() → returns ALL matches from ALL JARs
Enumeration<URL> all = cl.getResources("META-INF/spring.factories");

// With 50 JARs on classpath, this might return URLs like:
// jar:file:/libs/spring-boot-autoconfigure-3.2.0.jar!/META-INF/spring.factories
// jar:file:/libs/spring-boot-actuator-autoconfigure-3.2.0.jar!/META-INF/spring.factories
// jar:file:/libs/company-commons-starter-2.1.0.jar!/META-INF/spring.factories
// jar:file:/libs/spring-data-jpa-3.2.0.jar!/META-INF/spring.factories
// ... one from each JAR that includes the file

🎯 Key Takeaways

  • spring.factories is a key=value properties file at META-INF/spring.factories that registers extensions (auto-configs, listeners, initializers, etc.)
  • SpringFactoriesLoader.loadFactoryNames() reads ALL spring.factories from ALL JARs using ClassLoader.getResources()
  • Boot 3.x migrated auto-configs to META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (one class per line, easier merges)
  • spring.factories still used in Boot 3.x for non-auto-config entries: listeners, initializers, environment post-processors, failure analyzers
  • Advantages over scanning: no package convention, explicit registration, faster startup, self-registering JARs
  • Caching: factories are loaded once per ClassLoader and stored in a ConcurrentReferenceHashMap
  • Industry pattern: shared starter JARs use factory files to auto-register cross-cutting concerns across all microservices

💼 Interview Challenge

"You've created a company-wide Spring Boot starter library, but teams report that its auto-configured beans conflict with their own beans. Some teams want the defaults, others want to override them. Design a solution that satisfies both."

Expert answer framework:

  1. Use @ConditionalOnMissingBean on all auto-configured beans — teams that define their own beans automatically override the defaults.
  2. Use @ConditionalOnProperty with matchIfMissing=true for feature toggles — teams can disable specific features via company.commons.tracing.enabled=false.
  3. Document the conditions — publish a "conditions reference" showing what each auto-config checks and how to override or disable it.
  4. Use @AutoConfiguration ordering — ensure your starter runs AFTER potential user overrides by not using @AutoConfigureBefore unnecessarily.
