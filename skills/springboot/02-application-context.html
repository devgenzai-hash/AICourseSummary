ApplicationContext Lifecycle

The complete startup sequence from SpringApplication.run() to "Started in X seconds" — every phase, every hook, every extension point.

Advanced Spring Boot Internals
🚀 Daily-Life Analogy: Aircraft Takeoff Checklist

Starting a Spring Boot application is like an aircraft pre-flight checklist. There's a strict sequence: check fuel (load configuration), check instruments (create context), warm engines (instantiate beans), verify controls (post-process), get tower clearance (publish events), then finally — wheels up (application ready). Skip a step? You crash.

The Complete Startup Sequence

When you call SpringApplication.run(MyApp.class, args), here's EXACTLY what happens internally:

1. SpringApplication constructor → 2. Load SpringApplicationRunListeners → 3. Prepare Environment → 4. Create ApplicationContext → 5. Prepare Context → 6. Refresh Context → 7. After Refresh → 8. Runners

Phase 1: SpringApplication Constructor

public SpringApplication(Class<?>... primarySources) {
    // a) Store primary configuration classes
    this.primarySources = Set.of(primarySources);
    
    // b) Detect application type: SERVLET, REACTIVE, or NONE
    this.webApplicationType = WebApplicationType.deduceFromClasspath();
    // Checks: Is Spring MVC on classpath? → SERVLET
    //         Is WebFlux on classpath? → REACTIVE
    //         Neither? → NONE (background app)
    
    // c) Load ApplicationContextInitializers from spring.factories
    this.initializers = getSpringFactoriesInstances(
        ApplicationContextInitializer.class);
    
    // d) Load ApplicationListeners from spring.factories
    this.listeners = getSpringFactoriesInstances(
        ApplicationListener.class);
    
    // e) Detect main application class (for logging)
    this.mainApplicationClass = deduceMainApplicationClass();
}

Phase 2: The run() Method — Event Broadcasting

public ConfigurableApplicationContext run(String... args) {
    // Start timing
    StopWatch stopWatch = new StopWatch();
    stopWatch.start();
    
    // Load RunListeners (broadcast events during startup)
    SpringApplicationRunListeners listeners = getRunListeners(args);
    listeners.starting(); // EVENT: ApplicationStartingEvent
    
    try {
        // Parse command-line args
        ApplicationArguments applicationArguments = 
            new DefaultApplicationArguments(args);
        
        // Prepare Environment (properties, profiles)
        ConfigurableEnvironment environment = prepareEnvironment(
            listeners, applicationArguments);
        listeners.environmentPrepared(environment);
        // EVENT: ApplicationEnvironmentPreparedEvent
        
        // Print Banner (that Spring logo)
        printBanner(environment);
        
        // Create the ApplicationContext
        context = createApplicationContext();
        // For SERVLET → AnnotationConfigServletWebServerApplicationContext
        // For REACTIVE → AnnotationConfigReactiveWebServerApplicationContext
        
        // Prepare context (apply initializers, register beans)
        prepareContext(context, environment, listeners, 
                      applicationArguments);
        listeners.contextPrepared(context);
        // EVENT: ApplicationContextInitializedEvent
        
        // THE BIG ONE — refresh the context
        refreshContext(context);
        // EVENT: ApplicationPreparedEvent → ContextRefreshedEvent
        
        // Post-startup
        afterRefresh(context, applicationArguments);
        listeners.started(context);
        // EVENT: ApplicationStartedEvent
        
        // Run ApplicationRunner and CommandLineRunner beans
        callRunners(context, applicationArguments);
        listeners.ready(context);
        // EVENT: ApplicationReadyEvent
        
    } catch (Throwable ex) {
        listeners.failed(context, ex);
        // EVENT: ApplicationFailedEvent
        throw new IllegalStateException(ex);
    }
    
    return context;
}

Phase 6: The Refresh — Where Everything Happens

AbstractApplicationContext.refresh() is the most critical method in all of Spring. It contains 12 ordered steps:

public void refresh() {
    // 1. Prepare — set start date, active flag, property sources
    prepareRefresh();
    
    // 2. Get fresh BeanFactory (or create new one)
    ConfigurableListableBeanFactory beanFactory = obtainFreshBeanFactory();
    
    // 3. Prepare BeanFactory — register standard beans
    //    (ClassLoader, Environment, SystemProperties)
    prepareBeanFactory(beanFactory);
    
    // 4. Allow subclass post-processing of BeanFactory
    postProcessBeanFactory(beanFactory);
    
    // 5. ★ Invoke BeanFactoryPostProcessors ★
    //    This is where @Configuration classes are parsed!
    //    ConfigurationClassPostProcessor runs here.
    //    Component scanning happens here.
    invokeBeanFactoryPostProcessors(beanFactory);
    
    // 6. Register BeanPostProcessors (for later use)
    //    AutowiredAnnotationBeanPostProcessor registered here
    registerBeanPostProcessors(beanFactory);
    
    // 7. Initialize MessageSource (i18n)
    initMessageSource();
    
    // 8. Initialize ApplicationEventMulticaster
    initApplicationEventMulticaster();
    
    // 9. Subclass hook — create embedded web server here
    onRefresh();
    
    // 10. Register ApplicationListeners
    registerListeners();
    
    // 11. ★ Instantiate ALL remaining singletons ★
    //     This is where your @Service, @Repository beans get created
    finishBeanFactoryInitialization(beanFactory);
    
    // 12. Publish ContextRefreshedEvent, start lifecycle beans
    finishRefresh();
}
🔥 Critical Understanding

Step 5 (BeanFactoryPostProcessors) is where ConfigurationClassPostProcessor parses ALL your @Configuration classes, processes @ComponentScan, @Import, @Bean methods, and registers the resulting BeanDefinitions. Step 11 then instantiates them. These two steps are the backbone of Spring.

Event Timeline

EventWhenUse Case
ApplicationStartingEventBefore anything except listenersVery early logging setup
ApplicationEnvironmentPreparedEventEnvironment ready, no context yetModify properties before context
ApplicationContextInitializedEventContext created, before bean loadingAdd bean definitions programmatically
ApplicationPreparedEventDefinitions loaded, before refreshLast chance before bean creation
ContextRefreshedEventAll beans created and wiredPost-initialization logic
ApplicationStartedEventContext refreshed, before runnersFinal checks before app logic
ApplicationReadyEventRunners executed, fully readySignal for load balancer / health check
ApplicationFailedEventStartup failedAlert, cleanup, graceful logging

Industry Pattern: Custom ApplicationContextInitializer

public class VaultPropertyInitializer 
        implements ApplicationContextInitializer<ConfigurableApplicationContext> {
    
    @Override
    public void initialize(ConfigurableApplicationContext context) {
        // Runs BEFORE bean definitions are loaded
        // Perfect for adding dynamic property sources
        
        ConfigurableEnvironment env = context.getEnvironment();
        
        // Add Vault secrets as highest-priority property source
        Map<String, Object> vaultSecrets = fetchFromVault(env);
        env.getPropertySources().addFirst(
            new MapPropertySource("vault", vaultSecrets));
    }
}

// Register in META-INF/spring.factories:
// org.springframework.context.ApplicationContextInitializer=\
//   com.example.VaultPropertyInitializer

Shutdown Lifecycle

When the JVM shuts down (SIGTERM, Ctrl+C, or context.close()):

  1. ContextClosedEvent published — listeners can react
  2. Lifecycle beans stopped (web server stops accepting new requests)
  3. @PreDestroy methods called on all beans
  4. DisposableBean.destroy() called
  5. Custom destroy-methods called
  6. BeanFactory destroyed — all references cleared

✅ You Truly Understand ApplicationContext Lifecycle When...

You can explain exactly when your @PostConstruct method runs relative to ApplicationReadyEvent, and why the embedded Tomcat starts BEFORE your beans are fully initialized (step 9 vs step 11 in refresh).

🧪 Interview Challenge

"What's the difference between ApplicationStartedEvent and ApplicationReadyEvent?" — Started fires before CommandLineRunners execute. Ready fires after. If your runner throws an exception, Ready never fires but Started already did.

Connects to: Bean Lifecycle (what happens in step 11), Auto-Configuration (how @Conditional is evaluated in step 5), Graceful Shutdown (the ContextClosedEvent sequence).
