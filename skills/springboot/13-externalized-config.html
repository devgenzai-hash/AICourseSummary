Externalized Configuration

How Spring Boot resolves properties from 17+ sources with strict priority ordering — from command-line args down to default properties.

intermediate spring production
🏗️ The Override Stack Analogy

Think of externalized config like CSS specificity. Your stylesheet defines base styles, but inline styles override them, and !important overrides everything. Spring Boot's property resolution works the same way: application.properties sets defaults (like a stylesheet), environment variables override those (like inline styles), and command-line args override everything (like !important). The system checks 17+ layers from top to bottom, and the FIRST match wins — higher-priority sources shadow lower ones without removing them.

1. Property Source Ordering (Highest to Lowest Priority)

When Spring Boot resolves a property like server.port, it walks through these sources in strict order. The first source that defines the property wins:

# Source Example
1 Command line arguments --server.port=9090
2 SPRING_APPLICATION_JSON {"server.port": 9090} as env var or system prop
3 ServletConfig init params web.xml servlet init-param
4 ServletContext init params web.xml context-param
5 JNDI attributes (java:comp/env) Application server JNDI bindings
6 Java System properties (System.getProperties()) -Dserver.port=9090
7 OS environment variables SERVER_PORT=9090
8 RandomValuePropertySource (random.*) ${random.int}, ${random.uuid}
9 application-{profile}.properties (outside JAR) ./config/application-prod.yml
10 application-{profile}.properties (inside JAR) classpath:application-prod.yml
11 application.properties (outside JAR) ./config/application.yml
12 application.properties (inside JAR) classpath:application.yml
13 @PropertySource on @Configuration classes @PropertySource("classpath:custom.properties")
14 Default properties (SpringApplication.setDefaultProperties) Programmatic fallback values
🔍 Key Insight

Profile-specific files ALWAYS override non-profile files, regardless of location. So application-prod.properties inside your JAR overrides application.properties outside your JAR — because profile-specific sources sit higher in the priority stack.

2. @ConfigurationProperties: Type-Safe Configuration

Instead of scattering @Value annotations everywhere, @ConfigurationProperties binds an entire prefix into a structured POJO:

// application.yml:
// company:
//   mail:
//     host: smtp.company.com
//     port: 587
//     default-recipients:
//       - admin@company.com
//       - ops@company.com

@ConfigurationProperties(prefix = "company.mail")
@Validated
public class MailProperties {

    @NotBlank
    private String host;

    @Min(1)
    @Max(65535)
    private int port = 25; // default value

    private List<String> defaultRecipients = new ArrayList<>();

    // Getters and setters required for mutable binding
    public String getHost() { return host; }
    public void setHost(String host) { this.host = host; }
    public int getPort() { return port; }
    public void setPort(int port) { this.port = port; }
    public List<String> getDefaultRecipients() { return defaultRecipients; }
    public void setDefaultRecipients(List<String> r) { this.defaultRecipients = r; }
}

3. Relaxed Binding Rules

Spring Boot's "relaxed binding" means ALL of these map to the same property:

Format Example Where Used
Kebab-case (canonical) company.mail.default-recipients .properties / .yml files (recommended)
Camel case company.mail.defaultRecipients .properties / .yml files
Underscore company.mail.default_recipients .properties / .yml files
Upper case (env vars) COMPANY_MAIL_DEFAULTRECIPIENTS OS environment variables
⚠️ Environment Variable Gotcha

For environment variables, dots and hyphens aren't allowed in most shells. Spring Boot converts COMPANY_MAIL_DEFAULT_RECIPIENTS by lowercasing and replacing _ with . — but nested properties and list indices require specific patterns: COMPANY_MAIL_DEFAULTRECIPIENTS_0 for list index 0.

4. @ConfigurationProperties vs @Value

Feature @ConfigurationProperties @Value
Relaxed binding ✅ Full support ❌ Exact match only
Meta-data support ✅ IDE auto-complete via annotation processor ❌ No metadata
Validation ✅ JSR-303 @Validated ❌ Not supported
SpEL expressions ❌ Not supported ✅ Full SpEL
Complex types (Map, List, nested) ✅ Natural binding ⚠️ Limited/cumbersome
Immutable binding ✅ @ConstructorBinding ✅ final fields
Fail-fast on missing ❌ Silent null (unless @Validated) ✅ Throws on startup if missing

5. Immutable @ConfigurationProperties with @ConstructorBinding

@ConfigurationProperties(prefix = "company.security")
@ConstructorBinding  // Boot 2.x: required on class. Boot 3.x: required on constructor if multiple
public class SecurityProperties {

    private final String jwtSecret;
    private final Duration tokenExpiry;
    private final List<String> allowedOrigins;

    public SecurityProperties(
            String jwtSecret,
            @DefaultValue("1h") Duration tokenExpiry,
            @DefaultValue({"http://localhost:3000"}) List<String> allowedOrigins) {
        this.jwtSecret = jwtSecret;
        this.tokenExpiry = tokenExpiry;
        this.allowedOrigins = allowedOrigins;
    }

    // Only getters — truly immutable
    public String getJwtSecret() { return jwtSecret; }
    public Duration getTokenExpiry() { return tokenExpiry; }
    public List<String> getAllowedOrigins() { return allowedOrigins; }
}

// Registration (required for @ConstructorBinding classes)
@Configuration
@EnableConfigurationProperties(SecurityProperties.class)
public class SecurityConfig {
    // SecurityProperties is now available for injection
}
🔍 Key Insight

@ConstructorBinding enables true immutability — no setters needed. Spring Boot uses constructor parameter names (via -parameters compiler flag or @Name annotation) to match property names. @DefaultValue provides fallbacks for optional properties. In Boot 3.x, if there's only one constructor, @ConstructorBinding is inferred automatically.

6. Config File Formats: YAML vs Properties

# ═══ application.properties format ═══
server.port=8080
spring.datasource.url=jdbc:postgresql://localhost:5432/mydb
spring.datasource.username=admin
spring.datasource.hikari.maximum-pool-size=20
app.features.dark-mode=true
app.features.beta-users[0]=user1@test.com
app.features.beta-users[1]=user2@test.com

# ═══ application.yml equivalent ═══
# Hierarchical, less repetition, but YAML gotchas
server:
  port: 8080

spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/mydb
    username: admin
    hikari:
      maximum-pool-size: 20

app:
  features:
    dark-mode: true
    beta-users:
      - user1@test.com
      - user2@test.com

Multi-Document YAML (Profile Sections)

# Single file with profile-specific sections separated by ---
# application.yml

# Default (all profiles)
server:
  port: 8080
spring:
  application:
    name: my-service

---
# Activated when 'dev' profile is active
spring:
  config:
    activate:
      on-profile: dev
  datasource:
    url: jdbc:h2:mem:devdb

---
# Activated when 'prod' profile is active
spring:
  config:
    activate:
      on-profile: prod
  datasource:
    url: jdbc:postgresql://prod-host:5432/proddb
    hikari:
      maximum-pool-size: 50

7. spring.config.import — External Config Sources

# application.yml — importing external config (Boot 2.4+)

spring:
  config:
    import:
      # Import from filesystem
      - file:./config/secrets.properties
      - file:/etc/myapp/database.yml

      # Import from classpath
      - classpath:shared/common-defaults.yml

      # Import from config tree (Kubernetes secrets mounted as files)
      - configtree:/run/secrets/

      # Import optional sources (don't fail if missing)
      - optional:file:./local-overrides.properties

      # Import from custom sources (Vault, Consul, etc.)
      - vault://secret/myapp
      - consul:myapp/config
⚠️ Boot 2.4 Breaking Change

Before Boot 2.4, spring.config.location and spring.config.additional-location were the primary mechanisms for external config. Boot 2.4 introduced spring.config.import as a more declarative replacement. The old properties still work but spring.config.import is now preferred — it supports custom backends (Vault, Consul) via ConfigDataLocationResolver.

8. Industry Pattern: Environment-Specific Configuration

// ═══════════════════════════════════════════════════════════
// Production setup: layered configuration resolution
// ═══════════════════════════════════════════════════════════

// Priority stack in a Kubernetes deployment:
//
// 1. Command line: java -jar app.jar --spring.profiles.active=prod
// 2. K8s ConfigMap mounted as env vars: SERVER_PORT, DB_HOST
// 3. K8s Secret mounted as config tree: /run/secrets/db-password
// 4. Profile-specific: application-prod.yml (inside JAR)
// 5. Base config: application.yml (inside JAR)

// application.yml — base with sensible defaults
spring:
  config:
    import:
      - optional:configtree:/run/secrets/
  datasource:
    url: jdbc:h2:mem:localdb  // safe default for local dev
    username: sa

// application-prod.yml — production overrides
spring:
  datasource:
    url: jdbc:postgresql://${DB_HOST:localhost}:5432/${DB_NAME:myapp}
    username: ${DB_USERNAME}
    password: ${db-password}  // resolved from configtree
    hikari:
      maximum-pool-size: ${DB_POOL_SIZE:20}
      connection-timeout: 5000

// ConfigDataLocationResolver — custom implementation for Vault
public class VaultConfigDataLocationResolver
        implements ConfigDataLocationResolver<VaultConfigDataResource> {

    @Override
    public boolean isResolvable(ConfigDataLocationResolverContext context,
                                  ConfigDataLocation location) {
        return location.hasPrefix("vault://");
    }

    @Override
    public List<VaultConfigDataResource> resolve(
            ConfigDataLocationResolverContext context,
            ConfigDataLocation location) {
        String path = location.getNonPrefixedValue("vault://");
        return List.of(new VaultConfigDataResource(path));
    }
}

🎯 Key Takeaways

  • 17+ property sources are checked in strict priority order — command-line args override everything, defaults are the fallback of last resort
  • @ConfigurationProperties provides type-safe, validated, IDE-supported configuration binding to structured POJOs
  • Relaxed binding maps kebab-case, camelCase, underscore, and UPPER_CASE to the same property transparently
  • @ConstructorBinding enables truly immutable configuration classes — no setters, final fields, thread-safe by design
  • spring.config.import (Boot 2.4+) is the modern way to pull config from external sources including Vault, Consul, and Kubernetes config trees
  • Profile-specific files always win over non-profile files regardless of file location (inside/outside JAR)
  • Industry standard: layer K8s ConfigMaps + Secrets + profile-specific properties for environment separation without code changes

💼 Interview Challenge

"Your microservice needs database credentials that rotate every 24 hours. How do you handle this with Spring Boot's externalized configuration without restarting the service?"

Expert answer framework:

  1. Use spring.config.import with Vault: vault://secret/myapp/db — Vault handles rotation, Spring Cloud Vault client refreshes the lease.
  2. @RefreshScope on DataSource config — combined with Spring Cloud Config's /actuator/refresh endpoint to reload properties without restart.
  3. HikariCP's connection validation — even without refresh, set connection-test-query so stale connections fail fast and new ones use current credentials.
  4. Alternative: ConfigDataLocationResolver custom implementation that polls Vault on a schedule and fires EnvironmentChangeEvent.
