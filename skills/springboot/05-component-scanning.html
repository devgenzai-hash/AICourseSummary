Component Scanning & Classpath Scanning

How Spring discovers your beans without explicit registration — the bytecode-reading, classpath-traversing machinery behind @ComponentScan.

concept spring internal
🔍 The Census Bureau Analogy

Imagine the government needs to find every registered business in a city. They don't call each business and ask "do you exist?" — that would require loading every business into memory first. Instead, they scan the registry office records (metadata on file) without disturbing any actual business. They check each record's "type" field: Restaurant? Clinic? Shop? Only those matching the desired categories get a follow-up visit. That's exactly how Spring's component scanning works: it reads .class file metadata using ASM bytecode analysis — never loading classes into the JVM — and only instantiates the ones that pass its filters.

1. How ClassPathBeanDefinitionScanner Works Internally

The ClassPathBeanDefinitionScanner is the core engine that traverses the classpath, reads bytecode metadata, applies filters, and registers matching classes as BeanDefinition objects in the BeanDefinitionRegistry.

The Scanning Pipeline

// The entry point — called when @ComponentScan is processed
public class ClassPathBeanDefinitionScanner extends ClassPathScanningCandidateComponentProvider {

    public int scan(String... basePackages) {
        int beanCountAtScanStart = this.registry.getBeanDefinitionCount();

        doScan(basePackages);

        // Register annotation config processors (@Autowired, @Required, etc.)
        if (this.includeAnnotationConfig) {
            AnnotationConfigUtils.registerAnnotationConfigProcessors(this.registry);
        }

        return (this.registry.getBeanDefinitionCount() - beanCountAtScanStart);
    }

    protected Set<BeanDefinitionHolder> doScan(String... basePackages) {
        Set<BeanDefinitionHolder> beanDefinitions = new LinkedHashSet<>();

        for (String basePackage : basePackages) {
            // STEP 1: Find candidate components (bytecode scanning)
            Set<BeanDefinition> candidates = findCandidateComponents(basePackage);

            for (BeanDefinition candidate : candidates) {
                // STEP 2: Resolve scope metadata (@Scope annotation)
                ScopeMetadata scopeMetadata = this.scopeMetadataResolver
                    .resolveScopeMetadata(candidate);
                candidate.setScope(scopeMetadata.getScopeName());

                // STEP 3: Generate bean name
                String beanName = this.beanNameGenerator
                    .generateBeanName(candidate, this.registry);

                // STEP 4: Apply default values (lazy-init, autowire-mode, etc.)
                if (candidate instanceof AbstractBeanDefinition) {
                    postProcessBeanDefinition(
                        (AbstractBeanDefinition) candidate, beanName);
                }

                // STEP 5: Process common annotations (@Lazy, @Primary, @DependsOn)
                if (candidate instanceof AnnotatedBeanDefinition) {
                    AnnotationConfigUtils.processCommonDefinitionAnnotations(
                        (AnnotatedBeanDefinition) candidate);
                }

                // STEP 6: Check for duplicates and register
                if (checkCandidate(beanName, candidate)) {
                    BeanDefinitionHolder definitionHolder =
                        new BeanDefinitionHolder(candidate, beanName);
                    definitionHolder = AnnotationConfigUtils
                        .applyScopedProxyMode(scopeMetadata, definitionHolder, this.registry);
                    beanDefinitions.add(definitionHolder);
                    registerBeanDefinition(definitionHolder, this.registry);
                }
            }
        }
        return beanDefinitions;
    }
}
🔍 Key Insight

The scanner operates in 6 distinct steps: bytecode scan → scope resolution → name generation → default values → annotation processing → registration. Each step is individually overridable, making the scanner highly extensible.

2. ASM Bytecode Reading — Scanning Without Loading

This is the most critical insight about component scanning: Spring never calls Class.forName() during scanning. Instead, it reads raw .class file bytes using the ASM bytecode library and extracts annotation metadata directly from the bytecode structure.

⚠️ Why Not Use Class.forName()?
  • Static initializers — Loading a class runs its static {} blocks, which might connect to databases, start threads, or crash
  • Dependency chains — Loading class A might require class B which requires class C... ClassNotFoundException cascades
  • PermGen/Metaspace pressure — Loading thousands of classes just to check annotations wastes memory
  • Performance — Class loading is expensive (verification, linking, initialization); bytecode reading is a simple file parse

The MetadataReader Pipeline

// Spring's bytecode reading infrastructure
public interface MetadataReader {
    // The resource (jar entry or file) for this .class file
    Resource getResource();

    // Class-level metadata (name, superclass, interfaces) — WITHOUT loading
    ClassMetadata getClassMetadata();

    // All annotations on the class — read directly from bytecode
    AnnotationMetadata getAnnotationMetadata();
}

public class SimpleMetadataReader implements MetadataReader {

    private final AnnotationMetadata annotationMetadata;

    SimpleMetadataReader(Resource resource, ClassLoader classLoader) {
        // Read raw bytes from the .class file
        SimpleAnnotationMetadataReadingVisitor visitor =
            new SimpleAnnotationMetadataReadingVisitor(classLoader);

        // ASM ClassReader parses the bytecode structure
        getClassReader(resource).accept(visitor,
            ClassReader.SKIP_DEBUG | ClassReader.SKIP_CODE | ClassReader.SKIP_FRAMES);
            // ↑ SKIP_CODE: Don't read method bodies (huge savings!)
            // ↑ SKIP_DEBUG: Don't read debug info (line numbers, var names)
            // ↑ SKIP_FRAMES: Don't read stack map frames

        this.annotationMetadata = visitor.getMetadata();
    }

    private ClassReader getClassReader(Resource resource) {
        try (InputStream is = resource.getInputStream()) {
            return new ClassReader(is); // ASM reads the bytecode
        }
    }
}

What ASM Extracts From Bytecode

// A .class file has this binary structure (simplified):
//
// ┌────────────────────────────────────────────────────┐
// │ Magic Number: 0xCAFEBABE                           │
// │ Version: 61.0 (Java 17)                            │
// │ Constant Pool: strings, class refs, method refs    │
// │ Access Flags: public, final, abstract...           │
// │ This Class: com/app/service/OrderService            │
// │ Super Class: java/lang/Object                      │
// │ Interfaces: []                                     │
// │ Fields: [...]                                      │
// │ Methods: [...]                                     │
// │ Attributes:                                        │
// │   RuntimeVisibleAnnotations:     ← SPRING READS THIS
// │     @Service                                       │
// │     @Transactional                                 │
// └────────────────────────────────────────────────────┘
//
// ASM with SKIP_CODE reads ONLY the header + annotations section
// Typical .class file: 5-50KB. Annotation section: 100-500 bytes.
// Spring reads ~1% of the actual file content during scanning!

// What Spring can determine WITHOUT loading the class:
AnnotationMetadata metadata = metadataReader.getAnnotationMetadata();

metadata.getClassName();            // "com.app.service.OrderService"
metadata.isInterface();             // false
metadata.isAbstract();              // false
metadata.isFinal();                 // false
metadata.hasAnnotation("org.springframework.stereotype.Service"); // true
metadata.hasMetaAnnotation("org.springframework.stereotype.Component"); // true!
metadata.getAnnotationAttributes("org.springframework.stereotype.Service");
// {value="orderService"}
💡 Meta-Annotation Detection

When Spring checks if a class has @Component, it also checks meta-annotations. Since @Service is annotated with @Component, any class with @Service automatically matches the @Component filter. ASM reads the annotation bytecode of the annotation class itself to discover this hierarchy.

3. Include/Exclude Filters

The scanner uses a chain of TypeFilter objects to decide which classes become beans. By default, the include filter matches @Component (and its meta-annotations). You can add custom filters:

@Configuration
@ComponentScan(
    basePackages = "com.app",
    includeFilters = {
        // Match classes annotated with a custom annotation
        @Filter(type = FilterType.ANNOTATION, classes = MyCustomBean.class),

        // Match classes assignable to a specific type
        @Filter(type = FilterType.ASSIGNABLE_TYPE, classes = Plugin.class),

        // Match classes whose name matches a regex
        @Filter(type = FilterType.REGEX, pattern = ".*Gateway$"),

        // Full custom logic
        @Filter(type = FilterType.CUSTOM, classes = MyTypeFilter.class)
    },
    excludeFilters = {
        // Exclude all @Repository classes (maybe using a separate data config)
        @Filter(type = FilterType.ANNOTATION, classes = Repository.class),

        // Exclude test doubles
        @Filter(type = FilterType.REGEX, pattern = ".*Mock.*")
    }
)
public class AppConfig {}

TypeFilter Implementations

Filter Type Implementation Class What It Checks Loads Class?
ANNOTATION AnnotationTypeFilter Class has the specified annotation (or meta-annotation) ❌ No — reads bytecode
ASSIGNABLE_TYPE AssignableTypeFilter Class extends/implements the specified type ⚠️ May load class for complex hierarchies
REGEX RegexPatternTypeFilter Fully-qualified class name matches regex ❌ No — uses class name from metadata
ASPECTJ AspectJTypeFilter AspectJ type pattern expression ⚠️ May load class
CUSTOM Your TypeFilter impl Whatever you want Up to you

Internal: How Filters Are Applied

// Inside ClassPathScanningCandidateComponentProvider
protected boolean isCandidateComponent(MetadataReader metadataReader) {

    // EXCLUDE filters checked FIRST — early exit for performance
    for (TypeFilter tf : this.excludeFilters) {
        if (tf.match(metadataReader, this.metadataReaderFactory)) {
            return false; // Excluded! Skip immediately.
        }
    }

    // INCLUDE filters — must match at least one
    for (TypeFilter tf : this.includeFilters) {
        if (tf.match(metadataReader, this.metadataReaderFactory)) {
            return isConditionMatch(metadataReader); // Also check @Conditional
        }
    }

    return false; // No include filter matched
}

// AnnotationTypeFilter.match() — the most common filter
public class AnnotationTypeFilter extends AbstractTypeHierarchyTraversingFilter {

    private final Class<? extends Annotation> annotationType;
    private final boolean considerMetaAnnotations;

    @Override
    protected boolean matchSelf(MetadataReader metadataReader) {
        AnnotationMetadata metadata = metadataReader.getAnnotationMetadata();

        // Direct annotation check (fast path)
        if (metadata.hasAnnotation(this.annotationType.getName())) {
            return true;
        }

        // Meta-annotation check (e.g., @Service has @Component as meta)
        if (this.considerMetaAnnotations) {
            return metadata.hasMetaAnnotation(this.annotationType.getName());
        }
        return false;
    }
}
💡 Filter Ordering Matters

Exclude filters are checked before include filters. This means you can have a broad include filter (@Component) and surgically exclude specific classes. The exclude always wins.

4. basePackages Resolution from @ComponentScan

The basePackages attribute determines the root directories that the scanner will traverse. The resolution process converts Java package names to filesystem/jar paths:

// Multiple ways to specify scan targets

// Way 1: Explicit package strings
@ComponentScan(basePackages = {"com.app.service", "com.app.repository"})

// Way 2: Type-safe package references (preferred!)
@ComponentScan(basePackageClasses = {ServiceMarker.class, RepoMarker.class})
// Uses the PACKAGE of these classes as the base package
// Refactoring-safe: package renames are caught by compiler

// Way 3: No value specified — uses the package of the annotated class
@ComponentScan  // scans package of THIS @Configuration class

// Way 4: Spring Boot's @SpringBootApplication (includes @ComponentScan)
@SpringBootApplication  // scans from the main class's package DOWN

Internal: Package-to-Path Conversion

// ClassPathScanningCandidateComponentProvider.findCandidateComponents()
private Set<BeanDefinition> scanCandidateComponents(String basePackage) {
    Set<BeanDefinition> candidates = new LinkedHashSet<>();

    // Convert package name to resource path pattern
    // "com.app.service" → "classpath*:com/app/service/**/*.class"
    String packageSearchPath = ResourcePatternResolver.CLASSPATH_ALL_URL_PREFIX +
        resolveBasePackage(basePackage) + '/' + this.resourcePattern;
    // resourcePattern defaults to "**/*.class"

    // PathMatchingResourcePatternResolver scans:
    // - File system directories (exploded classes)
    // - JAR files (scans jar entries)
    // - Nested JARs (Spring Boot fat jar)
    Resource[] resources = this.resourcePatternResolver
        .getResources(packageSearchPath);

    for (Resource resource : resources) {
        MetadataReader metadataReader = this.metadataReaderFactory
            .getMetadataReader(resource);

        if (isCandidateComponent(metadataReader)) {
            ScannedGenericBeanDefinition sbd =
                new ScannedGenericBeanDefinition(metadataReader);
            sbd.setSource(resource);

            if (isCandidateComponent(sbd)) {
                candidates.add(sbd);
            }
        }
    }
    return candidates;
}
⚠️ Why @SpringBootApplication Package Placement Matters

Since @SpringBootApplication includes @ComponentScan with no explicit basePackages, it scans from its own package down. If you place your main class in com.app, it scans com.app.**. If you accidentally put it in com.app.config, it misses com.app.service! Always place the main class at the root package.

5. How @ComponentScan is Processed by ConfigurationClassPostProcessor

ConfigurationClassPostProcessor is the BeanDefinitionRegistryPostProcessor that kicks off the entire annotation-based configuration machinery. It's registered automatically and has the highest priority among all post-processors.

// ConfigurationClassPostProcessor — the orchestrator
public class ConfigurationClassPostProcessor
        implements BeanDefinitionRegistryPostProcessor, PriorityOrdered {

    @Override
    public void postProcessBeanDefinitionRegistry(BeanDefinitionRegistry registry) {
        // 1. Find all @Configuration classes in the registry
        List<BeanDefinitionHolder> configCandidates = new ArrayList<>();
        for (String beanName : registry.getBeanDefinitionNames()) {
            BeanDefinition beanDef = registry.getBeanDefinition(beanName);
            if (ConfigurationClassUtils.checkConfigurationClassCandidate(beanDef, metadataReaderFactory)) {
                configCandidates.add(new BeanDefinitionHolder(beanDef, beanName));
            }
        }

        // 2. Parse each @Configuration class
        ConfigurationClassParser parser = new ConfigurationClassParser(
            metadataReaderFactory, problemReporter, environment, resourceLoader, componentScanParser, registry);

        parser.parse(configCandidates);

        // 3. Load bean definitions from parsed configuration
        ConfigurationClassBeanDefinitionReader reader =
            new ConfigurationClassBeanDefinitionReader(registry, ...);
        reader.loadBeanDefinitions(parser.getConfigurationClasses());
    }
}

// Inside ConfigurationClassParser — processing @ComponentScan
protected void processConfigurationClass(ConfigurationClass configClass) {
    // ...
    SourceClass sourceClass = asSourceClass(configClass);

    do {
        sourceClass = doProcessConfigurationClass(configClass, sourceClass);
    } while (sourceClass != null);
}

protected SourceClass doProcessConfigurationClass(ConfigurationClass configClass, SourceClass sourceClass) {
    // Process @ComponentScan annotations
    Set<AnnotationAttributes> componentScans =
        AnnotationConfigUtils.attributesForRepeatable(
            sourceClass.getMetadata(), ComponentScans.class, ComponentScan.class);

    for (AnnotationAttributes componentScan : componentScans) {
        // TRIGGER THE ACTUAL SCAN
        Set<BeanDefinitionHolder> scannedBeanDefinitions =
            this.componentScanParser.parse(componentScan,
                sourceClass.getMetadata().getClassName());

        // RECURSIVE: Check if scanned classes are ALSO @Configuration classes
        for (BeanDefinitionHolder holder : scannedBeanDefinitions) {
            if (ConfigurationClassUtils.checkConfigurationClassCandidate(
                    holder.getBeanDefinition(), this.metadataReaderFactory)) {
                // Found another @Configuration! Parse it too (recursive)
                parse(holder.getBeanDefinition().getBeanClassName(), holder.getBeanName());
            }
        }
    }
    // ... also process @Import, @Bean, @ImportResource, etc.
}
🔍 The Recursive Nature

Component scanning is recursive. If the scanner discovers a class that is itself a @Configuration class with its own @ComponentScan, that scan is also executed. This is how modular Spring applications compose — each module can define its own scan boundaries.

6. Why Scanning is Expensive

Component scanning is one of the most expensive operations during Spring application startup. Here's why:

Cost Factor Impact Typical Numbers
Classpath size Every .class file in every jar matching the base package must be opened and read Enterprise app: 50,000-200,000 .class files
JAR traversal Each JAR is a ZIP file — scanning requires reading the central directory of every JAR Spring Boot fat jar: 100-300 nested JARs
I/O operations Each .class file requires a separate InputStream open/read/close 10,000+ file reads for a medium app
ASM parsing Even with SKIP_CODE, the bytecode parser must validate the constant pool ~0.1ms per class file
Broad packages Scanning "com" instead of "com.myapp" includes ALL libraries under "com.*" Can add 5-30 seconds to startup 
// Real-world measurement of scanning cost
// Application with basePackage = "com" (TOO BROAD!)

// DEBUG output from ClassPathBeanDefinitionScanner:
// Scanned 47,832 candidate class resources
// Identified 342 candidate components
// Time: 8.4 seconds
//
// After narrowing to "com.myapp":
// Scanned 1,247 candidate class resources

//
// 28x speedup just by narrowing the base package!
⚠️ The Hidden Cost: MetadataReaderFactory Caching

CachingMetadataReaderFactory caches parsed MetadataReader objects to avoid re-reading the same .class file. However, in Spring Boot with a fat JAR, the first scan still pays the full I/O cost. The cache only helps when the same class is checked by multiple filters or during recursive configuration parsing.

7. Spring Boot's Component Index: META-INF/spring.components

To solve the scanning performance problem, Spring 5 introduced the Component Index — a compile-time optimization that pre-computes which classes are components, eliminating runtime classpath scanning entirely.

How It Works

// Step 1: Add the indexer to your build
// Maven pom.xml
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-context-indexer</artifactId>
    <optional>true</optional>
</dependency>

// Step 2: At COMPILE TIME, the annotation processor generates:
// META-INF/spring.components
//
// com.app.service.OrderService=org.springframework.stereotype.Component
// com.app.service.PaymentService=org.springframework.stereotype.Component
// com.app.repository.UserRepository=org.springframework.stereotype.Component
// com.app.controller.OrderController=org.springframework.stereotype.Component
// com.app.config.SecurityConfig=org.springframework.stereotype.Component

// Step 3: At RUNTIME, Spring reads this flat file instead of scanning

Internal: How the Index is Used

// ClassPathScanningCandidateComponentProvider.findCandidateComponents()
public Set<BeanDefinition> findCandidateComponents(String basePackage) {

    // CHECK: Is the component index available?
    if (this.componentsIndex != null && indexSupportsIncludeFilters()) {
        // FAST PATH: Read from pre-computed index
        return addCandidateComponentsFromIndex(this.componentsIndex, basePackage);
    } else {
        // SLOW PATH: Full classpath scanning
        return scanCandidateComponents(basePackage);
    }
}

// Fast path: Read from index file
private Set<BeanDefinition> addCandidateComponentsFromIndex(
        CandidateComponentsIndex index, String basePackage) {

    Set<BeanDefinition> candidates = new LinkedHashSet<>();

    for (TypeFilter filter : this.includeFilters) {
        String stereotype = extractStereotype(filter);
        if (stereotype != null) {
            // O(1) lookup from the index instead of O(n) classpath scan!
            Set<String> types = index.getCandidateTypes(basePackage, stereotype);

            for (String type : types) {
                MetadataReader metadataReader =
                    metadataReaderFactory.getMetadataReader(type);
                if (isCandidateComponent(metadataReader)) {
                    candidates.add(new ScannedGenericBeanDefinition(metadataReader));
                }
            }
        }
    }
    return candidates;
}
💡 When the Index Falls Back to Scanning

The component index is all-or-nothing per module. If ANY JAR on the classpath has components but lacks a META-INF/spring.components file, Spring falls back to full classpath scanning for the entire application. ALL modules must generate the index for it to be effective.

Aspect Runtime Scanning Component Index
When work happens Every application startup Once at compile time
Startup cost O(n) where n = all .class files in packages O(k) where k = actual components
I/O operations Thousands of file reads One file read
Supports custom filters ✅ Full flexibility ⚠️ Only standard stereotypes
Build tool support No build changes needed Requires annotation processor

8. Performance Optimization: Narrowing basePackages

The single most impactful optimization for Spring startup time is narrowing your scan boundaries. Every unnecessary package in the scan path multiplies the work.

// ❌ BAD: Scanning the root package (includes ALL dependencies under "com")
@ComponentScan("com")
// Scans: com.google.*, com.fasterxml.*, com.zaxxer.*, com.app.*, ...
// Result: 50,000+ class files read, 8+ seconds wasted

// ❌ MEDIOCRE: Scanning the company root
@ComponentScan("com.mycompany")
// Still too broad if you have shared libraries under com.mycompany.*

// ✅ GOOD: Scanning only your application's packages
@ComponentScan(basePackages = {
    "com.mycompany.orderservice.service",
    "com.mycompany.orderservice.repository",
    "com.mycompany.orderservice.controller",
    "com.mycompany.orderservice.config"
})

// ✅ BEST: Type-safe marker interfaces (refactoring-safe)
@ComponentScan(basePackageClasses = {
    ServicePackage.class,     // Empty marker interface in each package
    RepositoryPackage.class,
    ControllerPackage.class
})

Advanced: Lazy Initialization as a Complement

// Spring Boot 2.2+ global lazy initialization
// application.properties
spring.main.lazy-initialization=true

// This doesn't reduce SCAN time (classes are still discovered)
// But it reduces INSTANTIATION time (beans created on first use)
//
// Scanning: 1,000 classes checked → 200 BeanDefinitions registered
// Without lazy-init: All 200 beans instantiated at startup
// With lazy-init: Only ~20 eagerly needed beans created (web server, etc.)

// ⚠️ Trade-off: First request is slower (beans created on demand)
// ⚠️ Misconfiguration errors deferred to runtime
💡 Measuring Scan Time

Add -Dspring.context.indexer.enabled=false and enable logging.level.org.springframework.context.annotation=DEBUG to see exactly how many classes are scanned and how long it takes. For production profiling, use Spring Boot's startup actuator endpoint: /actuator/startup (requires spring.main.applicationStartup=buffering).

9. Stereotype Annotations: All the Same to the Scanner!

A common misconception: @Service, @Repository, @Controller, and @Component are different. To the component scanner, they are identical. The scanner only sees @Component — the rest are meta-annotated with it.

// Look at the actual Spring source code for these annotations:

// @Service — just @Component with a different name
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Component  // ← THIS is what the scanner sees
public @interface Service {
    @AliasFor(annotation = Component.class)
    String value() default "";
}

// @Repository — just @Component + exception translation
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Component  // ← Same thing
public @interface Repository {
    @AliasFor(annotation = Component.class)
    String value() default "";
}

// @Controller — just @Component + web layer semantics
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Component  // ← Same thing
public @interface Controller {
    @AliasFor(annotation = Component.class)
    String value() default "";
}

So Why Use Different Annotations?

Annotation Scanning Behavior Additional Runtime Behavior
@Component Detected as bean candidate None
@Service Same as @Component None (purely semantic — marks business logic layer)
@Repository Same as @Component PersistenceExceptionTranslationPostProcessor wraps data access exceptions into Spring's DataAccessException hierarchy
@Controller Same as @Component RequestMappingHandlerMapping scans for @RequestMapping methods only on @Controller beans
@RestController Same as @Component (via @Controller) @Controller + @ResponseBody on all methods
@Configuration Same as @Component CGLIB proxy for @Bean method inter-references (full mode) + parsed for @Bean, @Import, @ComponentScan
💡 The Real Value of Stereotype Annotations

They serve three purposes beyond scanning: (1) Semantics — developers instantly understand the class's role, (2) AOP targeting — you can write pointcuts like @within(org.springframework.stereotype.Service), (3) Specific post-processing — @Repository gets exception translation, @Controller gets handler mapping registration.

10. Industry Pattern: Custom Stereotype Annotations

In large organizations, teams create custom stereotype annotations that compose Spring's stereotypes with additional metadata. This provides convention-over-configuration within the codebase.

Pattern 1: Domain-Specific Service Layer

// Custom annotation that combines @Service with transaction and logging
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Service                          // ← Inherits @Component behavior (scannable)
@Transactional                    // ← All methods are transactional by default
@Validated                        // ← Method parameters are validated
public @interface DomainService {
    @AliasFor(annotation = Service.class)
    String value() default "";
}

// Usage — clean, intention-revealing code
@DomainService
public class OrderFulfillmentService {

    public void fulfill(@Valid FulfillmentRequest request) {
        // Automatically transactional + validated — no annotations needed here
    }
}

Pattern 2: Infrastructure Gateway

// Custom annotation for external service integrations
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Component
@Scope("singleton")
public @interface ExternalGateway {

    // Which external system this gateway talks to
    String system();

    // Circuit breaker timeout in milliseconds
    int timeout() default 5000;

    // Retry attempts on transient failure
    int retries() default 3;

    @AliasFor(annotation = Component.class, attribute = "value")
    String value() default "";

Pattern 3: Scheduled Job Discovery

// Custom annotation for discoverable background jobs
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Component
public @interface ScheduledJob {

    String cron();
    String description();
    boolean enabledByDefault() default true;
    String value() default "";
}

@ScheduledJob(
    cron = "0 0 2 * * ?",
    description = "Purge expired sessions from database"
)
public class SessionPurgeJob implements Runnable {

    @Override
    public void run() {
        // Purge logic
    }
}

// A custom BeanPostProcessor discovers all @ScheduledJob beans
// and registers them with the scheduler, using attributes for config
@Component
public class ScheduledJobRegistrar implements BeanPostProcessor {

    private final TaskScheduler scheduler;

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        ScheduledJob annotation = AnnotationUtils.findAnnotation(
            bean.getClass(), ScheduledJob.class);

        if (annotation != null && annotation.enabledByDefault()) {
            CronTrigger trigger = new CronTrigger(annotation.cron());
            scheduler.schedule((Runnable) bean, trigger);
        }
        return bean;
    }
}
💡 Why Custom Stereotypes Work

Because Spring's AnnotationTypeFilter checks meta-annotations recursively, any annotation that is itself annotated (directly or transitively) with @Component will be discovered by the scanner. You can stack as many layers of meta-annotations as you want — the scanner will still find them.

🎯 Key Takeaways

  • ClassPathBeanDefinitionScanner converts packages to classpath resource paths and traverses all .class files
  • ASM bytecode reading (MetadataReader) checks annotations WITHOUT calling Class.forName() — no class loading, no static initializers, no dependency chains
  • Exclude filters are checked first, then include filters must match. Default include filter is AnnotationTypeFilter(@Component)
  • ConfigurationClassPostProcessor orchestrates the entire process — it finds @ComponentScan directives and triggers scanning recursively
  • Scanning cost is O(n) where n = total .class files in base packages. Narrowing packages is the #1 optimization
  • spring-context-indexer generates META-INF/spring.components at compile time, converting O(n) scan to O(k) lookup
  • @Service, @Repository, @Controller are just @Component with semantic meaning — the scanner treats them identically
  • Custom stereotypes compose @Component with domain annotations for convention-over-configuration

💼 Interview Challenge

"Your Spring Boot application takes 45 seconds to start in production. The team suspects component scanning. How would you diagnose and fix this?"

Expert answer framework:

  1. Measure — Enable DEBUG logging for org.springframework.context.annotation to see how many class resources are scanned. Use /actuator/startup with buffering ApplicationStartup.
  2. Diagnose — Check if basePackages is too broad (e.g., "com" or "org"). Check total .class count in scan paths. Check if fat JAR has hundreds of dependency JARs being traversed.
  3. Optimize (ordered by impact) — (a) Narrow basePackages to only application packages, (b) Add spring-context-indexer to all modules, (c) Enable spring.main.lazy-initialization=true if first-request latency is acceptable, (d) Consider Spring Native/GraalVM which eliminates runtime scanning entirely via AOT processing.
