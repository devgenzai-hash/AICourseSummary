Auto-Configuration Mechanism

How Spring Boot configures hundreds of libraries automatically — the @Conditional evaluation engine that decides what beans to create based on your classpath and properties.

advanced spring internal
🏨 The Smart Hotel Analogy

Imagine checking into a hotel that automatically configures your room based on what's in your luggage. Brought a laptop? A desk and ethernet cable appear. Packed swim trunks? Pool access is activated. Have a business card from a partner company? The conference room is reserved. You never fill out a preferences form — the hotel inspects what you brought (classpath) and what you've said (properties) to decide what services to enable. That's auto-configuration: conditional infrastructure provisioning based on classpath presence and declared preferences.

1. AutoConfigurationImportSelector — The Entry Point

AutoConfigurationImportSelector implements DeferredImportSelector, which means it runs after all regular @Configuration classes have been processed. This is critical — it ensures user-defined beans exist before auto-config conditions are evaluated.

public class AutoConfigurationImportSelector
        implements DeferredImportSelector, BeanClassLoaderAware,
                   ResourceLoaderAware, BeanFactoryAware, EnvironmentAware {

    @Override
    public String[] selectImports(AnnotationMetadata annotationMetadata) {
        if (!isEnabled(annotationMetadata)) {
            return NO_IMPORTS;
        }
        AutoConfigurationEntry autoConfigurationEntry =
            getAutoConfigurationEntry(annotationMetadata);
        return StringUtils.toStringArray(
            autoConfigurationEntry.getConfigurations());
    }

    protected AutoConfigurationEntry getAutoConfigurationEntry(
            AnnotationMetadata annotationMetadata) {

        // Step 1: Load ALL candidate configurations from factory files
        List<String> configurations = getCandidateConfigurations(
            annotationMetadata, attributes);
        // Boot 3.x: ~150 classes loaded from AutoConfiguration.imports

        // Step 2: Remove duplicates
        configurations = removeDuplicates(configurations);

        // Step 3: Apply exclusions (from annotation + properties)
        Set<String> exclusions = getExclusions(annotationMetadata, attributes);
        configurations.removeAll(exclusions);

        // Step 4: Filter by AutoConfigurationImportFilter
        // (fast pre-filter using OnBeanCondition, OnClassCondition, OnWebApplicationCondition)
        configurations = getConfigurationClassFilter()
            .filter(configurations);

        // Step 5: Fire AutoConfigurationImportEvent
        fireAutoConfigurationImportEvents(configurations, exclusions);

        return new AutoConfigurationEntry(configurations, exclusions);
    }
}
🔍 Key Insight

The DeferredImportSelector interface is the secret to auto-configuration working correctly. Regular @Import runs inline with parsing. Deferred imports run AFTER all user @Configuration classes are parsed — so when @ConditionalOnMissingBean checks execute, your custom beans are already registered in the BeanDefinitionRegistry.

3. Anatomy of an Auto-Configuration Class

@AutoConfiguration(after = DataSourceAutoConfiguration.class)
@ConditionalOnClass({ DataSource.class, JdbcTemplate.class })
@ConditionalOnSingleCandidate(DataSource.class)
@EnableConfigurationProperties(JdbcProperties.class)
public class JdbcTemplateAutoConfiguration {

    @Bean
    @Primary
    @ConditionalOnMissingBean(JdbcOperations.class)
    public JdbcTemplate jdbcTemplate(
            DataSource dataSource, JdbcProperties properties) {
        JdbcTemplate jdbcTemplate = new JdbcTemplate(dataSource);
        JdbcProperties.Template template = properties.getTemplate();
        jdbcTemplate.setFetchSize(template.getFetchSize());
        jdbcTemplate.setMaxRows(template.getMaxRows());
        return jdbcTemplate;
    }
}
🔍 Key Insight

Notice the layered conditions: @ConditionalOnClass on the class level gates the entire config (if JdbcTemplate isn't on classpath, nothing loads). @ConditionalOnMissingBean on the method level means: "only create this bean if the user hasn't already defined one." This is why you can always override auto-configured beans.

4. Auto-Configuration Ordering

Order matters — some auto-configs depend on beans created by others. Spring Boot provides ordering annotations:

@AutoConfiguration(
    before = WebMvcAutoConfiguration.class,
    after = DataSourceAutoConfiguration.class
)
public class MyAutoConfiguration { }

// Legacy (Boot 2.x) — still supported but deprecated
@AutoConfigureBefore(WebMvcAutoConfiguration.class)
@AutoConfigureAfter(DataSourceAutoConfiguration.class)
@AutoConfigureOrder(Ordered.HIGHEST_PRECEDENCE)
public class MyAutoConfiguration { }
Ordering Mechanism Scope Use Case
@AutoConfiguration(after=...) Between auto-configs only Ensure DataSource exists before JdbcTemplate config
@AutoConfiguration(before=...) Between auto-configs only Register error handlers before WebMvc setup
@AutoConfigureOrder Absolute ordering among auto-configs When relative before/after isn't sufficient
@Order / @Priority Does NOT affect auto-config ordering Only for bean injection ordering
⚠️ Common Misconception

@Order has NO effect on auto-configuration loading order. It only affects bean injection order (e.g., which filter comes first in a chain). Use @AutoConfiguration(before/after) exclusively for controlling auto-config sequence.

5. How Conditions Are Evaluated

The ConditionEvaluator processes @Conditional annotations at two phases:

// Phase 1: Configuration class parsing (ConfigurationClassParser)
// "Should I even parse this @Configuration class?"
if (this.conditionEvaluator.shouldSkip(
        configClass.getMetadata(), ConfigurationPhase.PARSE_CONFIGURATION)) {
    return; // Skip entire class — no beans registered
}

// Phase 2: Bean registration (ConfigurationClassBeanDefinitionReader)
// "Should I register this specific @Bean method?"
if (this.conditionEvaluator.shouldSkip(
        metadata, ConfigurationPhase.REGISTER_BEAN)) {
    return; // Skip this bean — but other beans in the class may register
}

The ConditionEvaluationReport

Every condition evaluation is recorded in the ConditionEvaluationReport, accessible via:

// Programmatic access
ConditionEvaluationReport report = ConditionEvaluationReport
    .get(applicationContext.getBeanFactory());

6. Why Auto-Configuration Runs After User Beans

The deferred import processing ensures this ordering:

📐 Processing Order

┌─────────────────────────────────────────────────────────────────┐
│                    ConfigurationClassParser                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│  PHASE 1: Parse user @Configuration classes                      │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ @Configuration UserConfig { @Bean myDataSource() {...} }    ││
│  │ @Configuration SecurityConfig { @Bean myFilter() {...} }    ││
│  └─────────────────────────────────────────────────────────────┘│
│                           ▼                                      │
│  PHASE 2: Process DeferredImportSelector (auto-configs)          │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ DataSourceAutoConfiguration                                  ││
│  │   └── @ConditionalOnMissingBean(DataSource.class)           ││
│  │       → SKIPPED: user already defined 'myDataSource'        ││
│  │                                                              ││
│  │ WebMvcAutoConfiguration                                      ││
│  │   └── @ConditionalOnMissingBean(WebMvcConfigurer.class)     ││
│  │       → MATCHED: no user WebMvcConfigurer → creates default ││
│  └─────────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────────┘
🔍 Key Insight

This is why @ConditionalOnMissingBean works reliably: by the time auto-configuration conditions are evaluated, ALL user-defined beans are already registered as BeanDefinitions. The condition can check "does this bean already exist?" with confidence.

7. Debugging: "Why Is This Bean Being Created?"

In industry, the most common auto-config debugging scenario is unexpected bean creation. Here's the diagnostic playbook:

// Step 1: Enable the conditions report
// application.properties
debug=true

// Step 2: Search for the auto-config class in the report
// Look for "Positive matches" — it tells you exactly which conditions passed

// Step 3: Use actuator for runtime inspection
// GET /actuator/conditions
{
  "contexts": {
    "application": {
      "positiveMatches": {
        "DataSourceAutoConfiguration": [{
          "condition": "OnClassCondition",
          "message": "@ConditionalOnClass found required classes 'javax.sql.DataSource'"
        }]
      }
    }
  }
}

// Step 4: If you want to prevent it
@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)

🎯 Key Takeaways

  • AutoConfigurationImportSelector is a DeferredImportSelector — it runs AFTER user configs, making @ConditionalOnMissingBean reliable
  • Boot 3.x uses META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (one class per line)
  • Boot 2.x used META-INF/spring.factories with key-value format (still supported for backward compat)
  • Ordering uses @AutoConfiguration(before/after) — NOT @Order which is for bean injection only
  • Conditions are evaluated at two phases: class parsing (should I load this config?) and bean registration (should I create this bean?)
  • ConditionEvaluationReport records every decision — access via --debug, actuator /conditions, or programmatically
  • Import filtering provides a fast pre-filter before full condition evaluation (checks class presence via ASM)

💼 Interview Challenge

"Your microservice starts up and connects to a Redis instance you didn't configure. Other developers say 'it just works.' How do you trace where this behavior comes from and how to control it?"

Expert answer framework:

  1. Diagnose — Run with --debug and search for "Redis" in the conditions report. Find RedisAutoConfiguration in "Positive matches." It matched because spring-data-redis is on the classpath (transitive dependency).
  2. Trace — Check @ConditionalOnClass(RedisConnectionFactory.class) → present. Check @ConditionalOnMissingBean(RedisConnectionFactory.class) → no user bean found. So Boot creates a LettuceConnectionFactory with default localhost:6379.
  3. Control — Either (a) exclude the auto-config, (b) set spring.data.redis.host in properties, (c) define your own RedisConnectionFactory bean, or (d) remove the transitive dependency if Redis isn't needed.
