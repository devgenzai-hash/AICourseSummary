Largest Contentful Paint (LCP)

The Core Web Vital that measures when the largest visible content element finishes rendering — the moment the user perceives the page as "loaded" because the main content is visible.

Intermediate Core Web Vital Loading Performance
🖼️ Analogy: Hanging a Gallery Exhibition

Visitors don't consider a gallery "open" when the door unlocks (TTFB) or when the first small sign is hung (FCP). They consider it open when the main centerpiece painting is on the wall. LCP is the moment that centerpiece appears — typically the hero image, headline, or primary content block.

The Problem: What "Loaded" Means to Users

// Previous metrics failed to capture perceived load completion:
//
// DOMContentLoaded — fires when HTML parses (user sees nothing yet)
// Load event — fires when ALL resources finish (too late, page already usable)
// FCP — fires at first paint (could be a tiny header or loading spinner)
//
// LCP answers: "When did the user see the MAIN content?"
//
// Timeline of a typical page load:
// 0ms      500ms     1000ms    1500ms    2000ms    2500ms
// |─────────|─────────|─────────|─────────|─────────|
// [TTFB 200ms]
//           [FCP: navigation renders at 600ms]
//                     [Hero image loads...]
//                                    [LCP: hero image paints at 1800ms]
//                                                    [Load event at 2400ms]
//
// Google thresholds: Good: ≤2.5s | Needs Improvement: 2.5-4s | Poor: >4s

What Elements Are LCP Candidates?

// The browser evaluates these element types as LCP candidates:
//
// 1. <img> elements (including <img> inside <picture>)
// 2. <image> inside <svg>
// 3. <video> poster image (or first frame)
// 4. Elements with background-image via url() (NOT gradients)
// 5. Block-level text elements (<p>, <h1>-<h6>, <div> with text)
//
// Size is computed as: visible area within viewport
// - Clipped/overflow:hidden areas don't count
// - Margin, padding, border DON'T count
// - Elements fully outside viewport don't count
//
// LCP candidate can CHANGE as the page loads:
// - First LCP candidate: <h1> renders (large text block)
// - New LCP candidate: hero image loads (larger than h1)
// - Final LCP: the LAST reported candidate before user input

// NOT LCP candidates:
// - Elements with opacity: 0 (invisible)
// - Full-screen background images used as backgrounds (debatable)
// - Placeholders/loading skeletons (low-entropy images are excluded)

Measuring LCP

const observer = new PerformanceObserver((list) => {
    const entries = list.getEntries();
    // LCP fires multiple times — LAST entry before user input is the final LCP
    const lastEntry = entries[entries.length - 1];
    
    console.log({
        lcp: lastEntry.startTime,       // When the element was painted
        element: lastEntry.element,     // The DOM element (for debugging)
        size: lastEntry.size,           // Visual size in pixels²
        url: lastEntry.url,             // Image URL (if image-based LCP)
        loadTime: lastEntry.loadTime,   // When resource finished loading
        renderTime: lastEntry.renderTime // When element was painted (more precise)
    });
});

observer.observe({ type: 'largest-contentful-paint', buffered: true });

// IMPORTANT: LCP reporting stops after first user input
// This prevents user-triggered content (e.g., clicking to reveal an image)
// from being counted as LCP
['keydown', 'click', 'pointerdown'].forEach(type => {
    document.addEventListener(type, () => observer.disconnect(), { once: true });
});

The Four Phases of LCP (Optimization Framework)

// LCP can be decomposed into four sub-parts:
//
// ┌─────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
// │  TTFB   │→ │ Resource Load │→ │ Resource     │→ │ Element      │
// │         │  │ Delay         │  │ Duration     │  │ Render Delay │
// └─────────┘  └──────────────┘  └──────────────┘  └──────────────┘
//  Server time   Time before       Download         Time after load
//  + network     browser starts    time of the      until paint
//               requesting LCP     LCP resource     (blocked by CSS,
//               resource                            JS, or rendering)

// Phase 1: TTFB — Server response time + network
// Fix: CDN, server-side caching, edge rendering, HTTP/3

// Phase 2: Resource Load Delay — Time WASTED before requesting LCP resource
// Common waste: LCP image URL buried in CSS or JS (not in HTML)
// Fix: Preload the LCP image! Make it discoverable by the preload scanner

// BAD: LCP image only discoverable after CSS loads and parses
// .hero { background-image: url('hero.jpg'); }

// GOOD: Tell the browser about it immediately
<link rel="preload" as="image" href="hero.jpg" fetchpriority="high">

// ALSO: Use fetchpriority="high" on the LCP <img> itself
<img src="hero.jpg" fetchpriority="high" alt="Hero">

// Phase 3: Resource Duration — Actual download time
// Fix: Optimize image size (WebP/AVIF, responsive srcset), use CDN

// Phase 4: Element Render Delay — After resource loads, before paint
// Causes: render-blocking CSS, JS that blocks rendering, lazy loading
// Fix: Remove render-blocking resources, NEVER lazy-load LCP image

// BAD: Lazy loading the LCP image delays its render
<img src="hero.jpg" loading="lazy"> // NEVER do this for above-the-fold images!

// GOOD: Eager load + high priority for LCP
<img src="hero.jpg" loading="eager" fetchpriority="high" decoding="sync">

Complete LCP Optimization Checklist

// Server-side optimizations:
// ✓ CDN for static assets (reduce TTFB to <200ms for cached content)
// ✓ Edge rendering / SSR (content in first response, no JS required)
// ✓ 103 Early Hints (send preload headers before response is ready)
// ✓ HTTP/3 + 0-RTT (eliminate connection setup overhead)

// Resource discovery optimizations:
// ✓ LCP image in HTML (not CSS/JS) — let preload scanner find it
// ✓ <link rel="preload"> for LCP resources hidden in CSS
// ✓ fetchpriority="high" on LCP element
// ✓ Avoid client-side rendering for LCP content

// Resource size optimizations:
// ✓ Modern formats (AVIF > WebP > JPEG) with <picture> fallbacks
// ✓ Responsive images (srcset) — don't send 4K image to mobile
// ✓ Proper image compression (quality 75-80 for hero images)

// Render optimization:
// ✓ Inline critical CSS (above-the-fold styles in <head>)
// ✓ Defer non-critical CSS with media="print" trick
// ✓ NEVER lazy-load above-the-fold images
// ✓ Avoid decode: async for LCP images (use sync)
// ✓ Remove render-blocking JS from <head>

// Example: Optimal LCP image markup
<picture>
    <source srcset="hero.avif" type="image/avif">
    <source srcset="hero.webp" type="image/webp">
    <img
        src="hero.jpg"
        alt="Product showcase"
        width="1200"
        height="600"
        fetchpriority="high"
        decoding="sync"
    >
</picture>

Where This Lives in Production

  • Google Search — LCP is a Core Web Vital ranking signal. Sites with LCP > 4s on mobile may be penalized in rankings.
  • Shopify Storefront — Automatically adds fetchpriority="high" to the first product image and preloads it via Early Hints.
  • Next.js Image Component — Uses priority prop to add fetchpriority="high" and preload link for LCP images.
  • Cloudflare Automatic Platform Optimization — Rewrites HTML to inline critical CSS and preload LCP resources at the edge.

Common Mistakes

  • Lazy-loading LCP images — loading="lazy" on above-the-fold images significantly delays LCP. Only lazy-load below-the-fold content.
  • LCP resource behind a redirect chain — Each redirect adds 100-300ms. Serve the final image URL directly.
  • Using CSS background-image for hero — Hidden from preload scanner. If you must, add an explicit preload link.
  • Client-side rendering the LCP element — If React must hydrate before the hero renders, LCP waits for JS. Use SSR/SSG for LCP content.
  • Ignoring TTFB — Even a perfectly optimized frontend can't overcome a 3-second server response time.

✅ You Truly Understand LCP When...

You can identify the LCP element on any page using DevTools Performance panel, decompose its timing into the four sub-parts (TTFB, resource load delay, download, render delay), and prescribe specific fixes for whichever phase dominates.

🧪 Try This Challenge

Take a page with LCP > 4s. Use WebPageTest to identify the four phases. Apply fixes (preload, fetchpriority, format optimization, inline CSS) and verify LCP drops below 2.5s. Document which fix contributed most.
