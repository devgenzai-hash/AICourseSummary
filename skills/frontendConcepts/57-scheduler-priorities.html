Frontend Concepts / Scheduler Priorities

Scheduler Priorities

How React (and the browser) decide which work is urgent and which can wait — the priority system that makes concurrent rendering feel responsive even during heavy computation.

Advanced React Internals Performance
🏥 Analogy: Emergency Room Triage

An ER doesn't treat patients first-come-first-served. A heart attack (user typing in an input) gets immediate attention, while a sprained ankle (loading new search results) can wait. React's scheduler is the triage nurse — it assigns priority levels to work units and ensures the most urgent updates are processed first, even if it means pausing lower-priority work mid-way.

The Problem: Not All Updates Are Equal

In a complex app, many state updates happen simultaneously:

  • User types in an input (must feel instant — 16ms budget)
  • Search results update (can take 200-500ms without feeling slow)
  • Analytics ping fires (user doesn't perceive at all)
  • Large list re-renders (acceptable to defer)

Without priorities, all updates are synchronous and block each other. Typing feels sluggish because React is busy rendering 10,000 search results.

React's Priority Levels

// React's internal scheduler (packages/scheduler) defines priority lanes:
// These map to how urgently work must be committed to the screen

// Priority 1: Immediate / Sync (Discrete events)
//   - Click, keydown, focus
//   - Must commit in current frame (can't be interrupted)
//   - Example: toggling a checkbox, closing a modal

// Priority 2: User-blocking (Continuous events)
//   - Input text, scroll, drag
//   - Should commit quickly but can be batched across frames
//   - Example: text input onChange, slider value

// Priority 3: Normal (Transitions)
//   - Non-urgent state updates, data fetching results
//   - Can be interrupted by higher-priority work
//   - Example: updating search results, navigation content

// Priority 4: Low / Idle
//   - Offscreen rendering, prefetching
//   - Only processed when main thread is idle
//   - Example: pre-rendering next page, analytics

startTransition: Opting Into Low Priority

import { useState, startTransition } from 'react';

function SearchPage() {
    const [inputValue, setInputValue] = useState('');
    const [searchResults, setSearchResults] = useState([]);

    function handleChange(e) {
        const value = e.target.value;
        
        // HIGH PRIORITY: Update input immediately (user sees their keystrokes)
        setInputValue(value);
        
        // LOW PRIORITY: Update results can be interrupted
        // If user types again before results render, React abandons
        // the in-progress results render and starts fresh
        startTransition(() => {
            const filtered = hugeList.filter(item => 
                item.name.includes(value)
            );
            setSearchResults(filtered);
        });
    }

    return (
        <>
            {/* Input always feels responsive */}
            <input value={inputValue} onChange={handleChange} />
            
            {/* Results may lag behind input — that's OK */}
            <ResultsList items={searchResults} />
        </>
    );
}

How the Scheduler Works Internally

// React's scheduler is a cooperative multi-tasking system
// It works in 5ms time slices (configurable based on frame budget)

// Simplified scheduler loop (actual code in packages/scheduler):
function workLoop(deadline) {
    while (workQueue.length > 0) {
        const task = workQueue.peek(); // Highest priority task
        
        // Should we yield to the browser?
        // Yes if: we've used our 5ms slice AND there's pending user input
        if (shouldYield()) {
            break; // Give browser a chance to handle events, paint
        }
        
        // Execute one unit of work (render one fiber/component)
        const continuationTask = task.callback();
        
        if (continuationTask) {
            // Task isn't done — put it back with same priority
            task.callback = continuationTask;
        } else {
            // Task complete — remove from queue
            workQueue.pop();
        }
    }
    
    // Schedule next slice if work remains
    if (workQueue.length > 0) {
        scheduleCallback(workLoop); // Uses MessageChannel (not setTimeout)
    }
}

// shouldYield() checks:
// 1. Has 5ms elapsed since we started this slice?
// 2. Is there pending user input (isInputPending API)?
// 3. Is there a higher-priority task queued?

// WHY MessageChannel instead of setTimeout?
// setTimeout has a minimum 4ms delay (clamped by browsers)
// MessageChannel fires at the start of next event loop turn (0ms delay)
// This gives React sub-millisecond scheduling resolution

The Lane System (React 18+)

// React 18 replaced the old "expiration time" system with "Lanes"
// Lanes are bitmasks — each bit represents a priority level

// Lane definitions (simplified from ReactFiberLane.js):
const SyncLane          = 0b0000000000000000000000000000001; // Discrete
const InputContinuous   = 0b0000000000000000000000000000100; // Drag, scroll
const DefaultLane       = 0b0000000000000000000000000010000; // Normal
const TransitionLanes   = 0b0000000001111111111111111000000; // Transitions
const IdleLane          = 0b0100000000000000000000000000000; // Idle

// WHY bitmasks? Efficient priority comparison:
// - Check if update is included: (lanes & updateLane) !== 0
// - Merge priorities: lanes | newLane
// - Find highest priority: lanes & -lanes (lowest set bit)
// - Multiple transition lanes allow concurrent transitions

// Each transition gets its own lane — React can render multiple
// transitions simultaneously and commit them independently

Browser Scheduling APIs

// The browser also has its own priority system:

// 1. requestAnimationFrame — fires before next paint (visual updates)
requestAnimationFrame(() => {
    // Guaranteed to run before browser paints
    // Use for: animations, layout reads, visual updates
    element.style.transform = `translateX(${x}px)`;
});

// 2. requestIdleCallback — fires when main thread is idle
requestIdleCallback((deadline) => {
    // Only runs when browser has nothing else to do
    // deadline.timeRemaining() tells you how much time you have
    while (deadline.timeRemaining() > 0 && tasks.length > 0) {
        doNonUrgentWork(tasks.pop());
    }
}, { timeout: 2000 }); // Max wait before forced execution

// 3. scheduler.postTask() — NEW Priority-aware scheduling API
// Available in Chrome 94+, standardization in progress
scheduler.postTask(() => { /* urgent UI work */ }, { priority: 'user-blocking' });
scheduler.postTask(() => { /* data processing */ }, { priority: 'user-visible' });
scheduler.postTask(() => { /* analytics */ }, { priority: 'background' });

// React's scheduler WILL eventually migrate to scheduler.postTask()
// when it has broader browser support

Where This Lives in Production

  • React 18+ — The entire concurrent features set (startTransition, useDeferredValue, Suspense) relies on the internal scheduler and lane system.
  • Facebook/Meta — The scheduler was built for Facebook's news feed, which renders thousands of items while keeping typing responsive. Production-proven at billion-user scale.
  • Chrome (scheduler.postTask) — Chrome ships the Prioritized Task Scheduling API, letting any code (not just React) benefit from priority scheduling.
  • Angular (Signals + zoneless) — Angular 17+ with signals moves toward fine-grained reactivity with priority awareness, inspired by React's approach.

Common Mistakes

  • Wrapping everything in startTransition — Discrete interactions (checkbox, toggle) should NOT be transitions. Users expect instant feedback for click actions.
  • Expecting transitions to debounce — startTransition doesn't delay execution. It just marks the update as interruptible. You still need debounce for reducing request frequency.
  • Using setTimeout for scheduling — setTimeout has a 4ms floor and doesn't integrate with React's priority system. Use startTransition or useDeferredValue instead.
  • Ignoring isPending from useTransition — Always show loading indicators for transitions. Users need feedback that something is happening, even if it's deferred.
