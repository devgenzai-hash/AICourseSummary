Frontend Concepts / Selective Hydration

Selective Hydration

React 18's ability to hydrate parts of the page independently and prioritize hydrating the component the user is interacting with — making large SSR pages interactive without a full-page hydration bottleneck.

Advanced React 18 SSR
⚡ Analogy: Power Grid Zones

Traditional hydration is like turning on power to an entire city at once — everything must be ready before the switch flips. Selective hydration is like powering up neighborhoods independently. If someone in Zone 3 flips a light switch (user clicks), that zone gets power first, even if Zone 1 and Zone 2 are still being wired up.

The Problem: Full Hydration Is Blocking

Traditional React hydration has three serial bottlenecks:

  1. Fetch all data before rendering any HTML on server
  2. Load all JavaScript before hydrating anything on client
  3. Hydrate everything before anything becomes interactive

Each step must complete fully before the next begins. For a complex page, this means seconds of non-interactive HTML.

How Selective Hydration Works

// Selective hydration requires two things:
// 1. Streaming SSR (renderToPipeableStream)
// 2. Suspense boundaries around independently-hydratable sections

import { renderToPipeableStream } from 'react-dom/server';

function App() {
    return (
        <Layout>
            {/* Each Suspense boundary = independently hydratable chunk */}
            <Suspense fallback={<NavSkeleton />}>
                <Navigation />  {/* Can hydrate independently */}
            </Suspense>
            
            <Suspense fallback={<ContentSkeleton />}>
                <MainContent /> {/* Hydrates on its own schedule */}
            </Suspense>
            
            <Suspense fallback={<CommentsSkeleton />}>
                <Comments />    {/* Can hydrate last — below fold */}
            </Suspense>
        </Layout>
    );
}

// Server streams HTML progressively:
// 1. Sends Layout + fallbacks immediately
// 2. As each section's data resolves, streams the real HTML
// 3. Client starts hydrating sections as their JS chunks arrive
// 4. Each section becomes interactive independently

Priority-Based Hydration: User Interaction Wins

// The killer feature: React detects user interaction and REPRIORITIZES

// Scenario: Page has 4 Suspense boundaries (Nav, Hero, Feed, Comments)
// React is hydrating them top-to-bottom: Nav → Hero → Feed → Comments

// While hydrating Feed (takes 200ms), user CLICKS on Comments section

// React's internal priority logic:
function handleEvent(event) {
    const targetFiber = getClosestHydratableFiber(event.target);
    
    if (!targetFiber.isHydrated) {
        // User interacted with an unhydrated section!
        // 1. Record the event (it will be replayed after hydration)
        queueDiscreteEvent(event);
        
        // 2. BOOST this section's hydration priority
        // React pauses current hydration work and switches to Comments
        prioritizeHydration(targetFiber);
        
        // 3. After Comments hydrates, replay the captured click
        // User doesn't need to click again!
    }
}

// Result timeline:
// 0ms:    Start hydrating Nav
// 50ms:   Nav hydrated, start Hero
// 100ms:  Hero hydrated, start Feed
// 150ms:  User clicks Comments (still hydrating Feed)
// 150ms:  PAUSE Feed hydration, SWITCH to Comments
// 200ms:  Comments hydrated → REPLAY the click event
// 200ms:  Resume Feed hydration
// 300ms:  Feed hydrated → page fully interactive
⚠️ Event Replay Has Limits

React only replays discrete events (click, keydown, focus) — not continuous events (mousemove, scroll). If user scrolls during hydration, those events don't queue. Also, replayed events fire synchronously after hydration, which can cause unexpected rapid state changes if user clicked multiple times.

Code: Full Streaming + Selective Hydration Setup

// server.js — Streaming SSR with selective hydration support
import { renderToPipeableStream } from 'react-dom/server';

app.get('*', (req, res) => {
    const { pipe, abort } = renderToPipeableStream(<App />, {
        // bootstrapScripts: JS that hydrates the page
        bootstrapScripts: ['/main.js'],
        
        onShellReady() {
            // Shell = everything outside Suspense boundaries
            // Send this immediately — user sees page structure
            res.statusCode = 200;
            res.setHeader('Content-Type', 'text/html');
            pipe(res);
            // Stream remains OPEN — more HTML will arrive as data resolves
        },
        
        onAllReady() {
            // ALL Suspense boundaries resolved — only for bots/crawlers
            // For users, we start streaming at onShellReady
        },
        
        onError(err) {
            console.error(err);
            // Suspense boundaries that error show their fallback
        }
    });
    
    // Safety timeout — abort if streaming takes too long
    setTimeout(abort, 10000);
});

// client.js — Hydration (selective happens automatically)
import { hydrateRoot } from 'react-dom/client';

// hydrateRoot + Suspense boundaries = selective hydration enabled
// React will hydrate each boundary as its code chunk loads
hydrateRoot(document.getElementById('root'), <App />);

Selective Hydration vs Other Hydration Strategies

StrategyHow It WorksTrade-off
Full HydrationHydrate entire tree at onceSimple but slow TTI on large pages
Partial HydrationOnly hydrate interactive components (Islands)Fastest but requires framework support (Astro)
Progressive HydrationHydrate in priority order (above fold first)Better UX but manually managed priorities
Selective HydrationHydrate per-boundary + user-interaction priorityAutomatic prioritization, requires Suspense
ResumabilityNo hydration — serialize event handlers (Qwik)Zero hydration cost but different mental model

Where This Lives in Production

  • Next.js 13+ App Router — Uses streaming SSR with selective hydration by default. Every loading.tsx creates a Suspense boundary that enables independent hydration.
  • Meta (Facebook) — The News Feed uses selective hydration. Comments below the fold hydrate later; if user scrolls to them, they get priority-boosted.
  • Shopify Hydrogen — Product pages stream immediately. Buy button hydrates first (most likely user interaction), reviews hydrate later.

Common Mistakes

  • Not using Suspense boundaries at all — Without boundaries, selective hydration has nothing to select. You get full hydration behavior even with React 18.
  • Too many tiny boundaries — Each boundary adds overhead (scheduling, tracking). Group logically-related interactive elements.
  • Code-splitting without Suspense — React.lazy() needs a Suspense boundary. Without it, you don't get selective hydration benefits for that chunk.
  • Expecting instant interactivity — Selective hydration is FASTER but not instant. Critical interactions (nav, auth) should be in the shell, not behind Suspense.

✅ You Truly Understand Selective Hydration When...

You can explain the full sequence when a user clicks a button inside an un-hydrated Suspense boundary: what React captures, how it reprioritizes hydration work, and how the click handler eventually fires — all without the user needing to click again.

🧪 Try This Challenge

Build a page with 5 Suspense-wrapped sections. Add artificial delays (1s, 2s, 3s, 4s, 5s) to each section's data fetch. Click on section 5 before it hydrates and verify that: (a) it hydrates before sections 2-4, (b) the click replays automatically.
