ETag vs Cache-Control

The two pillars of HTTP caching — one controls HOW LONG to cache (expiration), the other validates IF the cache is still good (conditional requests). They complement each other, not compete.

Intermediate HTTP Caching
🥛 Daily-Life Analogy: Milk Expiration

Cache-Control (max-age) is the "Best Before" date on milk — don't even check, it's good until this date. ETag is like calling the dairy: "I have batch #A7F2 — is it still good?" The dairy says "Yes, still fine" (304 Not Modified, no new milk shipped) or "No, here's fresh batch #B3C1" (200, new content). One avoids the trip entirely; the other makes the trip cheap.

How They Work Together

// FIRST REQUEST: Browser fetches /api/user/42
// Server responds:
HTTP/1.1 200 OK
Cache-Control: max-age=60, stale-while-revalidate=300
ETag: "a1b2c3d4e5"
Content-Type: application/json

{"name": "Akash", "email": "akash@example.com"}

// For next 60 seconds: browser uses cache WITHOUT contacting server (Cache-Control)
// After 60 seconds: browser must revalidate

// REVALIDATION REQUEST (conditional):
GET /api/user/42 HTTP/1.1
If-None-Match: "a1b2c3d4e5"   ← sends the ETag back

// IF data hasn't changed:
HTTP/1.1 304 Not Modified      ← no body! Saves bandwidth
ETag: "a1b2c3d4e5"
Cache-Control: max-age=60

// IF data HAS changed:
HTTP/1.1 200 OK
ETag: "f6g7h8i9j0"            ← new ETag
Cache-Control: max-age=60

{"name": "Akash R.", "email": "akash@newdomain.com"}

Cache-Control Directives

DirectiveMeaningUse Case
max-age=NCache for N seconds without revalidatingStatic assets, API with known refresh interval
no-cacheAlways revalidate before using cache (can still cache!)HTML pages, dynamic content
no-storeNever cache at all (don't store any copy)Sensitive data (banking, PII)
publicCan be cached by CDN/shared cachesPublic content, static files
privateOnly browser can cache (not CDN)User-specific data, auth'd responses
immutableContent will NEVER change at this URLContent-hashed files (app.a1b2.js)
stale-while-revalidate=NServe stale for N seconds while refreshingFeeds, dashboards, non-critical data
must-revalidateAfter max-age expires, MUST revalidate (no stale serving)Legal content, financial data

ETag vs Last-Modified

ValidatorHow It WorksPrecisionUse Case
ETagHash of content (or opaque token)Byte-exact (detects any change)API responses, dynamic content
Last-ModifiedTimestamp of last change1-second resolution (can miss sub-second changes)Static files, simple cases

// Strong: ETag: "abc123" — byte-for-byte identical
// Weak: ETag: W/"abc123" — semantically equivalent (minor changes OK)

// Conditional request headers:
// If-None-Match: "etag" — used with ETag (preferred)

The Complete Caching Decision Tree

/*
  Is this response user-specific?
  ├─ Yes → Cache-Control: private, no-cache + ETag
  └─ No → Can it be shared by CDN?
           ├─ Yes → Cache-Control: public, max-age=N
           └─ Has a content-hash filename?
              ├─ Yes → Cache-Control: public, max-age=31536000, immutable
              └─ No → Cache-Control: public, max-age=0, must-revalidate + ETag
                       (Always check with server, but avoid re-downloading if unchanged)
*/

Where This Is Used in Production

  • GitHub API — Returns ETag with every response. Conditional requests count against a lower rate limit, encouraging ETag usage.
  • Cloudflare — Automatically generates ETags for static assets and handles conditional requests at the edge (304s never hit origin).
  • Next.js — Page responses include Cache-Control: s-maxage=1, stale-while-revalidate for ISR pages, with ETags for data routes.

Common Mistakes

  • Confusing no-cache with no-store — no-cache DOES cache! It just revalidates every time. no-store prevents all caching.
  • Setting ETag without supporting conditional requests — If your server sends ETag but ignores If-None-Match, you waste the header and never send 304s.
  • Using max-age=0 without a validator — Forces revalidation but without ETag/Last-Modified, the server must send the full response every time (defeats the purpose).
  • Relying only on Cache-Control for critical updates — Users behind aggressive CDNs or corporate proxies may get stale content regardless of your headers. Always have an invalidation plan.

✅ You Truly Understand ETag vs Cache-Control When...

You can explain the complete lifecycle: first request → stored with ETag + max-age → served from cache during freshness window → conditional request with If-None-Match after expiry → 304 (no body) or 200 (new content). And you know why no-cache still caches.

🧪 Try This Challenge

Set up an Express server that: serves JSON with ETag (computed from content hash), responds with 304 when If-None-Match matches, sets Cache-Control: no-cache (force revalidation). Verify with DevTools Network tab that subsequent requests get 304 (0 bytes transferred) when content hasn't changed.
