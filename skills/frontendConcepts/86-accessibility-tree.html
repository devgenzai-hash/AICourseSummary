Frontend Concepts / Accessibility Tree

Accessibility Tree

The parallel DOM that assistive technologies actually read — a stripped-down semantic representation of your page where visual styling is irrelevant and only roles, names, states, and relationships matter.

Intermediate Accessibility Browser Internals
🗺️ Analogy: Building Floor Plan vs Photo

The DOM is like a photograph of a building — every visual detail is captured. The accessibility tree is like the floor plan — it shows rooms (landmarks), doors (links/buttons), labels on rooms, and how to navigate between them. A blind person can navigate the building perfectly with the floor plan; they don't need the photo.

The Problem: Screen Readers Don't See Pixels

// Screen readers CANNOT see your beautifully styled CSS
// They read the ACCESSIBILITY TREE — a semantic abstraction
//
// What a sighted user sees:
// ┌─────────────────────────┐
// │ 🛒 My Store   [Search]  │  (visually styled navbar)
// │─────────────────────────│
// │ Welcome back, Alice!    │  (greeting with avatar)
// │ [Buy Now ▶]             │  (fancy animated button)
// └─────────────────────────┘
//
// What a screen reader "sees" (the accessibility tree):
// navigation "Main"
//   link "My Store" (href="/home")
//   search
//     textbox "Search products" (role=searchbox)
// main
//   heading level 1 "Welcome back, Alice!"
//   button "Buy Now" (state: enabled)
//
// If your HTML doesn't map to meaningful tree nodes,
// screen reader users get: "div div div div clickable div"

How the Accessibility Tree Is Built

// The browser builds the accessibility tree from the DOM by:
//
// 1. Starting with the DOM tree
// 2. Pruning nodes that are semantically irrelevant:
//    - display:none or visibility:hidden elements (pruned entirely)
//    - <div> and <span> without roles (may be pruned or flattened)
//    - Decorative images (role="presentation" or empty alt="")
//
// 3. Computing accessible properties for each remaining node:
//    - Role: what IS this element? (button, link, heading, etc.)
//    - Name: what is it CALLED? (text content, label, aria-label)
//    - State: what CONDITION is it in? (expanded, checked, disabled)
//    - Properties: additional info (required, haspopup, controls)
//    - Relations: what is it CONNECTED to? (labelledby, describedby)

// DOM → Accessibility Tree mapping example:

// DOM:
<nav aria-label="Main navigation">
    <ul>
        <li><a href="/home">Home</a></li>
        <li><a href="/products" aria-current="page">Products</a></li>
    </ul>
</nav>

// Accessibility Tree (what AT reads):
// navigation "Main navigation"
//   list (2 items)
//     listitem
//       link "Home" (href=/home)
//     listitem
//       link "Products" (href=/products, current=page)

Accessible Name Computation Algorithm

// The browser follows a PRIORITY ORDER to determine an element's name:
// (defined in the Accessible Name and Description Computation spec)
//
// Priority 1: aria-labelledby (references another element's text)
<button aria-labelledby="btn-label">X</button>
<span id="btn-label">Close dialog</span>
// Accessible name: "Close dialog" (NOT "X")

// Priority 2: aria-label (explicit string)
<button aria-label="Close dialog">X</button>
// Accessible name: "Close dialog"

// Priority 3: Native labeling mechanism
<label for="email">Email address</label>
<input id="email" type="email">
// Accessible name of input: "Email address"

// Priority 4: Text content (for elements that allow naming from content)
<button>Submit Form</button>
// Accessible name: "Submit Form"

// Priority 5: title attribute (fallback, least preferred)
<button title="Submit"><svg>...</svg></button>
// Accessible name: "Submit" (only because nothing else is available)

// Priority 6: placeholder (for inputs, even LOWER priority)
<input type="text" placeholder="Enter email">
// Accessible name: "Enter email" (BAD — use a real label!)

Inspecting the Accessibility Tree

// Method 1: Chrome DevTools → Elements → Accessibility pane
// Shows computed role, name, and full property tree for selected element

// Method 2: Chrome DevTools → Full Accessibility Tree toggle
// Elements panel → ☰ → Full-page accessibility tree
// Shows the ENTIRE page as screen readers perceive it

// Method 3: Programmatic access (testing)
// Using Playwright or Puppeteer:
const snapshot = await page.accessibility.snapshot();
console.log(JSON.stringify(snapshot, null, 2));
// Returns: { role: 'WebArea', name: 'Page Title', children: [...] }

// Method 4: aria-hidden inspector
// Find elements hidden from accessibility tree:
document.querySelectorAll('[aria-hidden="true"]').forEach(el => {
    // These are invisible to screen readers
    // Make sure they don't contain focusable elements!
    const focusable = el.querySelectorAll(
        'a, button, input, select, textarea, [tabindex]'
    );
    if (focusable.length > 0) {
        console.error('Focusable element inside aria-hidden!', el);
    }
});

Common Accessibility Tree Patterns

// PATTERN: Custom component with proper tree representation

// BAD: Looks like a tab panel visually, tree says "div div div"
<div class="tabs">
    <div class="tab active" onclick="...">Tab 1</div>
    <div class="tab" onclick="...">Tab 2</div>
    <div class="panel">Content for tab 1</div>
</div>

// GOOD: Proper accessibility tree representation
<div role="tablist" aria-label="Product information">
    <button role="tab" 
            aria-selected="true" 
            aria-controls="panel-1"
            id="tab-1">
        Description
    </button>
    <button role="tab" 
            aria-selected="false" 
            aria-controls="panel-2"
            id="tab-2"
            tabindex="-1">
        Reviews
    </button>
</div>
<div role="tabpanel" 
     id="panel-1" 
     aria-labelledby="tab-1">
    Product description content...
</div>

// Tree result:
// tablist "Product information"
//   tab "Description" (selected, controls=panel-1)
//   tab "Reviews" (controls=panel-2)
// tabpanel "Description"
//   statictext "Product description content..."


// PATTERN: Removing from accessibility tree intentionally

// Decorative elements that add no information:
<img src="decorative-swirl.svg" alt="" role="presentation">
// ↑ Completely hidden from accessibility tree

// Visually redundant icons next to text:
<button>
    <svg aria-hidden="true">...</svg> <!-- Icon hidden from tree -->
    Delete item <!-- This is the accessible name -->
</button>
// Tree: button "Delete item" (no duplicate icon announcement)

// Hiding entire sections during animations/transitions:
<div aria-hidden="true" class="modal-backdrop">
    <!-- Everything inside is removed from accessibility tree -->
    <!-- WARNING: Must NOT contain focusable elements! -->
</div>

Where This Lives in Production

  • Chrome DevTools — Full-page accessibility tree view (since Chrome 90) lets developers see exactly what screen readers read.
  • Playwright / Testing Library — getByRole() queries the accessibility tree directly, encouraging developers to write tests that match screen reader behavior.
  • macOS VoiceOver / NVDA / JAWS — All screen readers consume the platform accessibility API (MSAA/UIA on Windows, NSAccessibility on macOS) which browsers populate from the accessibility tree.
  • React Aria (Adobe) — A library that generates correct accessibility tree semantics for custom components (combobox, datepicker, etc.).

Common Mistakes

  • Using <div onclick> instead of <button> — Divs have no implicit role. Screen reader announces "clickable" (or nothing). Buttons announce "button, Submit Form".
  • Icon-only buttons without accessible names — A button with only an SVG and no aria-label/text is announced as "button" with no name.
  • Focusable elements inside aria-hidden="true" — Creates a "ghost" that keyboard users can tab to but screen readers can't announce. The worst of both worlds.
  • Redundant ARIA on semantic HTML — <nav role="navigation"> is redundant. <nav> already has implicit role="navigation". Adds no value, just noise.
  • Missing accessible names on landmarks — Two <nav> elements without aria-label are both "navigation" to screen readers — indistinguishable.

✅ You Truly Understand the Accessibility Tree When...

You can look at any HTML structure and predict exactly what the accessibility tree output will be — the role, name, state, and relationships of each node — and identify which elements will be pruned, which will be exposed, and how a screen reader will announce the component.

🧪 Try This Challenge

Build a custom dropdown/combobox component using only <div>s, then add proper ARIA roles, states, and properties until Chrome's accessibility tree view shows the same structure as a native <select>. Compare the two trees.

🔗 Connect It

Accessibility Tree connects to: ARIA Live Regions (dynamic updates to the tree that get announced), Shadow DOM (shadow roots create boundaries in the accessibility tree), and Custom Elements Lifecycle (when roles/states must be set for proper tree representation).
