Frontend Concepts / Concurrent Rendering

Concurrent Rendering

React's ability to work on multiple UI updates simultaneously, pausing and resuming rendering work without blocking the main thread.

Advanced Concept Performance
🍳 Analogy: Cooking Multiple Dishes

Synchronous rendering is like a chef who must finish one dish completely before starting another — even if a customer is waiting for just a glass of water. Concurrent rendering is like a chef who can pause chopping vegetables to quickly serve that water, then resume chopping. Work is interruptible and prioritized by urgency.

The Problem: Blocking Renders

In synchronous React (pre-18), once a render starts, it runs to completion. If a render takes 100ms (large list, complex tree), the main thread is blocked for 100ms. During that time:

  • User input is ignored (typing feels laggy)
  • Animations freeze
  • The page appears unresponsive

Concurrent rendering makes renders interruptible. React can pause work on a low-priority update to handle a high-priority one (like user input), then resume the paused work later.

How It Works: Interruptible Rendering

// Without concurrent rendering — this blocks for 100ms
function SearchResults({ query }) {
    // Filtering 10,000 items blocks the main thread
    const results = items.filter(item => item.name.includes(query));
    return results.map(item => <ResultCard key={item.id} item={item} />);
}

// With concurrent rendering — useTransition marks as low priority
function SearchPage() {
    const [query, setQuery] = useState('');
    const [deferredQuery, setDeferredQuery] = useState('');
    const [isPending, startTransition] = useTransition();
    
    function handleChange(e) {
        // HIGH priority: update input value immediately
        setQuery(e.target.value);
        
        // LOW priority: update search results (can be interrupted)
        startTransition(() => {
            setDeferredQuery(e.target.value);
        });
    }
    
    return (
        <>
            <input value={query} onChange={handleChange} />
            {isPending && <Spinner />}
            {/* This re-render can be paused if user types again */}
            <SearchResults query={deferredQuery} />
        </>
    );
}
💡 Key Mechanism: Time Slicing

Concurrent rendering uses time slicing — React works on rendering for ~5ms, then yields to the browser's event loop. If user input arrives during a yield point, React can abandon the in-progress render and start a new one for the high-priority update. The Fiber architecture makes this possible by tracking work in a linked-list structure that can be paused/resumed.

Real-World Usage

  • React 18+ — All React 18 apps opt into concurrent rendering via createRoot (vs legacy ReactDOM.render)
  • Facebook Feed — The infinite scrolling feed uses transitions so new posts rendering doesn't block scrolling
  • VS Code Web — Large file tree renders use concurrent-like patterns to keep the editor responsive

Common Mistakes

  • Expecting renders to always complete — A transition render may be abandoned if a higher-priority update arrives. Don't put side effects in render.
  • Using useTransition for everything — Only use it when you have low-priority updates that might block high-priority ones.
  • Not understanding tearing — In concurrent mode, two parts of the UI might show different versions of state momentarily. Use useSyncExternalStore for external stores.

✅ You Truly Understand Concurrent Rendering When...

You can explain what "interruptible" means at the Fiber level — how React tracks partially-completed work and can throw it away or resume it.

🧪 Try This Challenge

Build a typeahead search that filters 10,000 items. Without useTransition, notice how typing lags. Add useTransition and demonstrate the input stays responsive while results update in the background.
