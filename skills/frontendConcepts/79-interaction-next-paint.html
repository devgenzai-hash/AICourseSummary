Interaction to Next Paint (INP)

The Core Web Vital that measures the FULL latency of every user interaction — from input event to the next frame painted — and reports the worst one. The metric that replaced FID in March 2024.

Advanced Core Web Vital Responsiveness
⚡ Analogy: Complete Response Time

FID was like measuring how long a waiter takes to acknowledge your order. INP measures the complete experience: acknowledgment + kitchen prep + food delivery to your table. And it checks EVERY order you place during the meal, reporting your worst experience — because one terrible interaction ruins the whole dinner.

The Problem: FID's Blind Spots

// FID only measured delay of the FIRST interaction
// A site could have 5ms FID but terrible responsiveness after that
//
// Example: E-commerce product page
// - First click (navbar): FID = 10ms ✓ (page is idle by then)
// - Add to cart button: 350ms delay (React re-renders entire cart)
// - Filter dropdown: 500ms delay (re-renders product grid)
// - Accordion toggle: 200ms delay (forces layout recalculation)
//
// FID says: "10ms — Great!" 
// INP says: "500ms — Poor! Fix the filter interaction."
//
// INP captures what users ACTUALLY experience throughout their session

How INP Is Calculated

// INP = the WORST interaction latency, measured across the full page lifecycle
// (Technically: the interaction at the 98th percentile if >50 interactions)

// An "interaction" consists of related events grouped together:
// - Click: pointerdown → pointerup → click (grouped as ONE interaction)
// - Keyboard: keydown → keyup (grouped as ONE interaction)
// - Tap: pointerdown → pointerup → click (grouped as ONE interaction)

// For each interaction, latency = max(event durations in that group)
// where event duration includes ALL three phases:

// ┌─────────── Interaction Latency ──────────────────────────────────┐
// │                                                                  │
// │  ┌──────────┐  ┌──────────────────┐  ┌───────────────────────┐  │
// │  │  Input   │  │   Processing     │  │  Presentation         │  │
// │  │  Delay   │  │   Duration       │  │  Delay                │  │
// │  │          │  │                  │  │                       │  │
// │  │ (waiting │  │ (event handler   │  │ (style, layout, paint │  │
// │  │ for main │  │  execution time) │  │  compositing until    │  │
// │  │ thread)  │  │                  │  │  next frame appears)  │  │
// │  └──────────┘  └──────────────────┘  └───────────────────────┘  │
// │                                                                  │
// └──────────────────────────────────────────────────────────────────┘
//
// Google's thresholds:
// Good: ≤200ms | Needs Improvement: 200-500ms | Poor: >500ms

Measuring INP with PerformanceObserver

// INP uses the 'event' entry type from the Event Timing API
// Note: only events with duration >104ms are reported by default
// Use durationThreshold: 16 to capture more interactions

let worstInteraction = 0;
const interactions = new Map(); // interactionId → max duration

const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
        // Skip entries without interactionId (not discrete interactions)
        if (!entry.interactionId) continue;

        // Group events by interactionId
        // e.g., pointerdown + pointerup + click all share one interactionId
        const existing = interactions.get(entry.interactionId) || 0;
        const duration = entry.duration;
        
        // Keep the MAX duration within this interaction group
        if (duration > existing) {
            interactions.set(entry.interactionId, duration);
        }

        // INP = worst interaction (simplified; real impl uses p98)
        const allDurations = [...interactions.values()].sort((a, b) => b - a);
        
        // For <50 interactions: use the worst one
        // For ≥50 interactions: use the 98th percentile (skip worst 2%)
        const idx = Math.min(
            allDurations.length - 1,
            Math.floor(allDurations.length * 0.02) // p98 index
        );
        worstInteraction = allDurations[idx] || 0;
    }
});

observer.observe({
    type: 'event',
    buffered: true,
    // Lower threshold to capture more interactions (default is 104ms)
    durationThreshold: 16
});

// Report INP when page is being unloaded
document.addEventListener('visibilitychange', () => {
    if (document.visibilityState === 'hidden') {
        console.log(`INP: ${worstInteraction}ms`);
        navigator.sendBeacon('/api/inp', JSON.stringify({ inp: worstInteraction }));
    }
});

Diagnosing Slow INP: The Three Phases

// PHASE 1: Input Delay (waiting for main thread)
// Cause: Long tasks blocking when user interacts
// Fix: Break up long tasks, use scheduler.yield()

const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
        if (!entry.interactionId) continue;
        
        const inputDelay = entry.processingStart - entry.startTime;
        const processingTime = entry.processingEnd - entry.processingStart;
        const presentationDelay = entry.duration - (entry.processingEnd - entry.startTime);
        
        console.log({
            total: entry.duration,
            inputDelay,       // Phase 1: High = main thread was busy
            processingTime,   // Phase 2: High = event handler is slow
            presentationDelay // Phase 3: High = expensive rendering after handler
        });
        
        // Typical breakdown for a 400ms interaction:
        // inputDelay: 50ms (a timer callback was running)
        // processingTime: 200ms (handler does heavy state update)
        // presentationDelay: 150ms (React re-renders large tree)
    }
});

observer.observe({ type: 'event', buffered: true, durationThreshold: 16 });

Fixing Each Phase

// FIXING PHASE 1 (Input Delay): Break up long tasks
async function processDataInChunks(data) {
    for (let i = 0; i < data.length; i += 100) {
        processChunk(data.slice(i, i + 100));
        // Yield so pending interactions can be processed
        await scheduler.yield();
    }
}

// FIXING PHASE 2 (Processing Time): Optimize event handlers
function handleFilterChange(event) {
    // BAD: Synchronous computation in handler
    // const filtered = items.filter(expensiveCheck);
    // setState({ items: filtered });

    // GOOD: Defer heavy work, show immediate feedback
    setState({ isFiltering: true }); // Instant visual feedback (loading state)
    
    // Heavy work in next task — doesn't block THIS interaction's paint
    requestAnimationFrame(() => {
        setTimeout(() => {
            const filtered = items.filter(expensiveCheck);
            setState({ items: filtered, isFiltering: false });
        }, 0);
    });
}

// FIXING PHASE 3 (Presentation Delay): Reduce rendering cost
// - Avoid rendering 1000 items; use virtualization
// - Use CSS containment to limit layout scope
// - Avoid forced reflows in the rendering path
// - Use content-visibility: auto for off-screen content

Where This Lives in Production

  • Google Search — INP replaced FID as a ranking signal in March 2024. Sites with poor INP may rank lower in search results.
  • Chrome UX Report (CrUX) — Field INP data collected from opted-in Chrome users at the 75th percentile. Available in PageSpeed Insights.
  • web-vitals library v4+ — The onINP() function handles all the grouping, percentile calculation, and attribution logic.
  • Vercel / Next.js Speed Insights — Reports INP per route, helping identify which pages have slow interactions.
  • Shopify — Uses INP data to identify slow product page interactions (variant selectors, quantity inputs, add-to-cart buttons).

Common Mistakes

  • Optimizing only for first interaction — INP measures ALL interactions. A slow accordion, modal, or dropdown later in the session hurts just as much.
  • Ignoring presentation delay — Your handler runs in 5ms but triggers a 300ms re-render. INP includes the paint time.
  • Using setTimeout(0) to "fix" INP — This defers work but shows stale UI. Users see the old state for one frame, which can feel broken.
  • Not testing on real devices — A 100ms interaction on your MacBook Pro is 400ms on a budget Android phone. Test on representative hardware.
  • Forgetting that INP uses p98 — One bad interaction out of 100 won't tank your score, but one bad interaction out of 5 will.

✅ You Truly Understand INP When...

You can decompose a 400ms interaction into its three phases (input delay, processing, presentation), identify which phase dominates, and apply the correct fix for each — yielding for input delay, optimizing handlers for processing, and reducing render cost for presentation delay.

🧪 Try This Challenge

Build a page with a filter UI that has good FID (<50ms) but poor INP (>500ms). Show the Phase 2 breakdown proving the event handler is the bottleneck. Then fix it using startTransition or deferred rendering while keeping immediate visual feedback.

🔗 Connect It

INP connects to: Long Tasks API (input delay comes from long tasks), Concurrent Rendering / startTransition (React's solution for Phase 2), and Layout Thrashing (a common cause of high presentation delay).
