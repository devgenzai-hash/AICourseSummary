Frontend Concepts / SameSite Cookie Modes

SameSite Cookie Modes

The three-value attribute that controls when cookies travel cross-site — the primary browser defense against CSRF attacks, and why SameSite=Lax became the default in 2020.

Intermediate Security Cookies
🎫 Daily-Life Analogy: Event Wristbands

SameSite=None = a wristband that works at ANY venue (third-party cookies sent everywhere — tracking). SameSite=Lax = a wristband that only works at the venue you originally entered from (sent on top-level navigations, not embedded requests). SameSite=Strict = a wristband that ONLY works if you walked in through the front door of THIS specific venue (never sent on any cross-site request).

The Problem: CSRF Attacks

/*
  Without SameSite, cookies were ALWAYS sent to their origin, regardless of
  where the request originated. This enabled CSRF (Cross-Site Request Forgery):
  
  1. User is logged into bank.com (has session cookie)
  2. User visits evil.com
  3. evil.com has: <form action="https://bank.com/transfer" method="POST">
  4. Form auto-submits via JavaScript
  5. Browser attaches bank.com's session cookie (because it's going to bank.com)
  6. Bank processes the transfer — it sees a valid session cookie!
  
  SameSite prevents step 5: "Don't send my cookie if the request
  didn't originate from my own site."
*/

The Three Modes

ModeCross-site top-level navigation (clicking a link)Cross-site subresource (img, iframe, fetch)Same-site requests
SameSite=Strict❌ NOT sent❌ NOT sent✅ Sent
SameSite=Lax✅ Sent (GET only)❌ NOT sent✅ Sent
SameSite=None; Secure✅ Sent✅ Sent✅ Sent

Code: Setting SameSite Cookies

// Server-side (Express.js)
res.cookie('session', token, {
    httpOnly: true,       // Not accessible via JavaScript (XSS protection)
    secure: true,         // HTTPS only
    sameSite: 'lax',      // Sent on same-site + top-level navigation
    maxAge: 7 * 24 * 60 * 60 * 1000, // 7 days
});

// For cross-site cookies (e.g., OAuth, embedded widgets):
res.cookie('third_party_token', value, {
    httpOnly: true,
    secure: true,         // ⚠️ REQUIRED when SameSite=None
    sameSite: 'none',     // Sent on ALL requests (including cross-site)
});

// Raw Set-Cookie header equivalents:
// Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=604800
// Set-Cookie: widget=xyz; HttpOnly; Secure; SameSite=None; Max-Age=604800

When Each Mode Sends Cookies

// User is on social.com, and your cookie is for bank.com

// Scenario 1: User clicks a link to bank.com (top-level navigation)
// Strict: ❌ (user arrives "logged out" — bad UX!)
// Lax: ✅ (user arrives logged in — good UX)
// None: ✅

// Scenario 2: social.com has <img src="bank.com/avatar.png">
// Strict: ❌ (no cookie sent — image load fails if auth required)
// Lax: ❌ (no cookie sent — this is a subresource, not navigation)
// None: ✅ (cookie sent — enables cross-site tracking!)

// Scenario 3: social.com auto-submits a form POST to bank.com (CSRF!)
// Strict: ❌ (CSRF blocked ✅)
// Lax: ❌ (CSRF blocked ✅ — Lax only allows GET navigations)
// None: ✅ (CSRF succeeds! 💀 — need other defenses like CSRF tokens)

// Scenario 4: social.com fetches bank.com/api/data via JavaScript
// Strict: ❌
// Lax: ❌
// None: ✅ (only if CORS also allows it)

Why Lax Is the Default (Since Chrome 80, 2020)

💡 The Browser Changed the Default

Before 2020, cookies without SameSite behaved as SameSite=None (sent everywhere). Chrome 80 changed the default to SameSite=Lax. This broke: cross-site iframes relying on cookies, OAuth flows using POST redirects, payment gateways with POST callbacks, and ad/tracking cookies. Sites had to explicitly opt in to SameSite=None; Secure for cross-site use.

"Site" vs "Origin" — The Critical Distinction

/*
  "Origin" = scheme + host + port (strict)
  https://app.example.com:443  vs  https://api.example.com:443 → DIFFERENT origins
  
  "Site" = scheme + registrable domain (eTLD+1) (looser)  
  https://app.example.com  vs  https://api.example.com → SAME site!
  (Both share "example.com" as the registrable domain)
  
  SameSite uses the SITE definition:
  - app.example.com → api.example.com = SAME SITE (cookies sent with Lax!)
  - example.com → other-domain.com = CROSS SITE (cookies blocked with Lax)
  
  This means: subdomains of the same domain are "same-site" for cookies.
  Your SPA at app.example.com can share Lax cookies with api.example.com.
*/

Where This Is Used in Production

  • Every authenticated web app — Session cookies should be SameSite=Lax (or Strict for banking). This is the primary CSRF defense in modern browsers.
  • OAuth / SSO flows — OAuth callbacks often use POST redirects, which require SameSite=None; Secure on the state cookie (or switching to GET redirects).
  • Embedded payment forms (Stripe, PayPal) — Third-party payment iframes need SameSite=None; Secure to maintain session across the iframe boundary.
  • Google/Facebook login buttons — Third-party auth widgets embedded in your site need their cookies to work cross-site.

Common Mistakes

  • Setting SameSite=None without Secure — Browsers reject SameSite=None cookies that aren't Secure (HTTPS-only). The cookie is silently dropped.
  • Using SameSite=Strict for session cookies — Users clicking links from email/Slack arrive at your site "logged out" because the cookie wasn't sent on the top-level navigation. Use Lax instead.
  • Not testing OAuth/SSO flows after the Lax default — Many OAuth libraries broke when browsers changed the default. POST-based callbacks need explicit SameSite=None.
  • Confusing "same-site" with "same-origin" — a.example.com and b.example.com are same-site (SameSite cookies work) but different origin (CORS still applies).
  • Relying solely on SameSite for CSRF protection — SameSite=Lax allows GET requests. If your GET endpoints have side effects (bad practice!), they're still vulnerable. Use CSRF tokens as defense-in-depth.

✅ You Truly Understand SameSite Cookies When...

You can explain why SameSite=Lax blocks form POST CSRF attacks but allows users clicking links to arrive logged in, why Strict is too aggressive for most session cookies, and the difference between "same-site" (eTLD+1) and "same-origin" (scheme+host+port).

🧪 Try This Challenge

Set up two local domains (e.g., localhost:3000 and localhost:4000 — these are different origins but same site!). Set a cookie with SameSite=Lax on port 3000. From port 4000, try: (1) a link navigation, (2) a fetch request, (3) a form POST. Observe which scenarios include the cookie.

🔗 Connect It

SameSite cookies connect to: CORS Preflight (CORS controls whether cross-origin requests succeed; SameSite controls whether cookies travel with them), Service Workers (SW fetch events see cookies based on SameSite rules), and Third-Party Cookie Deprecation (Chrome's plan to block all SameSite=None cookies entirely by 2025).
