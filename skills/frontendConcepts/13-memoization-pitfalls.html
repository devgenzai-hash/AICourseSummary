Memoization Pitfalls

When useMemo and useCallback hurt more than they help — understanding the real cost of memoization and when to reach for it.

Intermediate Concept Code
💾 Analogy: Caching Leftovers

Memoization is like putting leftovers in the fridge. It saves you from cooking again — but only if you actually eat them. If you put everything in the fridge "just in case," you waste space and time wrapping/unwrapping food you'll never reuse. The cost of caching must be less than the cost of recomputing.

The Problem: Premature Memoization

Developers often wrap everything in useMemo and useCallback thinking "memoization = performance." In reality, memoization has costs:

  • Memory — Storing the cached value and its dependency array
  • Comparison overhead — Checking all dependencies on every render (O(n) where n = dependency count)
  • Complexity — Stale values from incorrect dependency arrays
  • GC prevention — Cached values can't be garbage collected
// WASTEFUL memoization — worse than not memoizing
function UserCard({ user }) {
    // This useMemo costs MORE than just computing the string
    // String concatenation: ~1 nanosecond
    // useMemo overhead: allocate array, compare deps, store result
    const fullName = useMemo(
        () => `\${user.first} \${user.last}`,
        [user.first, user.last]
    );
    
    // USEFUL memoization — expensive computation
    const sortedTransactions = useMemo(
        () => transactions.slice().sort((a, b) => b.date - a.date),
        [transactions]  // Only re-sort when transactions array changes
    );
}

When Memoization Actually Helps

ScenarioMemoize?Why
Expensive computation (>1ms)✅ YesSave CPU time on re-renders
Referential stability for child props✅ YesPrevent unnecessary child re-renders with React.memo
Dependency of useEffect/useMemo✅ YesPrevent effect re-runs
Simple string/number computation❌ NoComputation cheaper than memoization overhead
Object only used in same component❌ NoNo child to prevent re-rendering
Dependencies change every render❌ NoCache always misses — pure overhead

The useCallback Trap

// POINTLESS useCallback — Child is not memoized
function Parent() {
    // This useCallback does NOTHING useful
    // Child will re-render anyway when Parent re-renders
    const handleClick = useCallback(() => {
        doSomething();
    }, []);
    
    // Unless Child is wrapped in React.memo, this is wasted effort
    return <Child onClick={handleClick} />;
}

// USEFUL useCallback — paired with React.memo
const MemoChild = React.memo(function Child({ onClick, data }) {
    // Now React.memo can actually prevent re-renders
    // because onClick reference is stable
    return <button onClick={onClick}>{data.label}</button>;
});

Where This Is Used in Production

  • React Compiler (React 19+) — Automatically determines what to memoize, eliminating manual useMemo/useCallback. The compiler knows which values need stable references.
  • Reselect (Redux) — Memoized selectors that recompute only when input selectors return new values. Prevents entire selector chains from re-executing.
  • Virtualized lists (react-window) — Memoize row renderers to prevent re-rendering thousands of off-screen rows.

Common Mistakes

  • Memoizing with unstable deps — If a dependency changes every render, the memo cache always misses. You've added overhead with zero benefit.
  • Missing dependencies — Stale closures from incomplete dependency arrays. ESLint exhaustive-deps exists for a reason.
  • Memoizing inside loops — Hooks can't be called conditionally or in loops. Use a child component per item instead.
  • useCallback without React.memo — Stable function reference is meaningless if the child re-renders unconditionally.

✅ You Truly Understand Memoization Pitfalls When...

You can look at a component and identify which useMemo/useCallback calls are necessary versus which are pure overhead — and explain the cost model for each.
