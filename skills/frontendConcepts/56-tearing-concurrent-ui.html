Tearing in Concurrent UI

When a single render pass shows inconsistent data because external state changed mid-render — a fundamental challenge introduced by React's concurrent rendering model.

Advanced React Internals Concurrent Mode
📸 Analogy: Panoramic Photo Glitch

Imagine taking a panoramic photo of a street. Halfway through the sweep, a car moves. The result shows half the car on the left and the other half on the right — a torn image. In concurrent UI, the "camera sweep" is the render pass, and the "moving car" is external state changing between renders of sibling components.

The Problem: Concurrent Rendering + Mutable State

In synchronous rendering (React 17 and below), a render was atomic — start to finish without interruption. All components in one render always saw the same version of state.

Concurrent rendering (React 18+) can pause rendering mid-tree, yield to the browser, then resume. If external mutable state changes during that pause:

// External store (Redux, Zustand, or global variable)
let externalStore = { color: 'blue' };

// Component A renders first, reads color = 'blue'
function ComponentA() {
    const color = externalStore.color; // 'blue'
    return <div style={{ background: color }}>A is {color}</div>;
}

// --- React YIELDS here (concurrent pause) ---
// During the pause, an event fires:
externalStore = { color: 'red' };

// Component B renders after the pause, reads color = 'red'
function ComponentB() {
    const color = externalStore.color; // 'red'
    return <div style={{ background: color }}>B is {color}</div>;
}

// RESULT: A shows blue, B shows red — in the same render!
// This is TEARING — inconsistent UI from the same logical state
⚠️ useState/useReducer Are NOT Affected

React's own state primitives (useState, useReducer, Context) are immune to tearing because React controls their version. Tearing only happens with external mutable stores — globals, Redux stores read without proper hooks, mutable refs, browser APIs like window.innerWidth.

How React 18 Solves It: useSyncExternalStore

import { useSyncExternalStore } from 'react';

// This hook guarantees tear-free reads from external stores
// React will either:
//   1. Re-render the entire tree synchronously if store changes mid-render
//   2. Or detect the inconsistency and restart the render

function useStore(store, selector) {
    return useSyncExternalStore(
        store.subscribe,      // How to subscribe to changes
        () => selector(store.getState()), // How to get current value
        () => selector(store.getState())  // Server snapshot (SSR)
    );
}

// Internal mechanism:
// 1. Before yielding (concurrent pause), React snapshots the store version
// 2. After resuming, it checks: did the store change?
// 3. If YES: throw away partial render, restart synchronously
// 4. If NO: safe to continue concurrent render
// This means: tearing is prevented at the cost of occasionally falling
// back to synchronous rendering (losing concurrent benefits temporarily)

How Libraries Implement It

// Redux (react-redux v8+) uses useSyncExternalStore internally
// Before v8, Redux had its own complex subscription mechanism that
// was prone to tearing in React 18 concurrent features

// Zustand store — properly tear-free since v4:
import { create } from 'zustand';

const useColorStore = create((set) => ({
    color: 'blue',
    setColor: (c) => set({ color: c }),
}));

// Zustand's `create` returns a hook that uses useSyncExternalStore
// This guarantees Component A and B always see the same color
function ComponentA() {
    const color = useColorStore(state => state.color);
    return <div>{color}</div>; // Consistent with all other readers
}

When Tearing Actually Matters

// Tearing is most dangerous when components render related data
// from the same store that must be consistent:

// Example: Financial dashboard
function PortfolioHeader() {
    const total = store.totalValue;   // $10,000 (before update)
    return <h1>Portfolio: ${total}</h1>;
}

// Store updates to $12,000 during concurrent pause...

function PortfolioBreakdown() {
    const stocks = store.stocksValue;  // $8,000 (after update)
    const bonds = store.bondsValue;    // $4,000 (after update)
    return <p>Stocks: ${stocks}, Bonds: ${bonds}</p>;
}

// User sees: "Portfolio: $10,000" but "Stocks: $8,000, Bonds: $4,000"
// $8000 + $4000 = $12,000 ≠ $10,000 header — visually WRONG
// This is a tearing bug that confuses users and erodes trust

Where This Lives in Production

  • React 18 — Introduced useSyncExternalStore specifically to solve tearing. Part of the concurrent features release.
  • Redux (react-redux) — v8.0 rewrote internals to use useSyncExternalStore. Older versions (v7) had tearing issues with startTransition.
  • Zustand — v4+ uses useSyncExternalStore. The migration was transparent to users.
  • Jotai/Recoil — Atomic state libraries that work natively with React's state model, avoiding tearing by design (atoms are React state, not external stores).

Common Mistakes

  • Reading from refs during render — useRef is mutable and not tracked by React. Reading refs during render can tear in concurrent mode.
  • Using module-level variables as state — let count = 0; outside components is an external mutable store with no subscription mechanism.
  • Assuming useEffect callbacks see consistent renders — Effects fire after paint, so the DOM is committed. But during the render phase, external reads can tear.
  • Not migrating from store.subscribe + forceUpdate — Legacy patterns (pre-hooks era) are all prone to tearing. Must use useSyncExternalStore.

✅ You Truly Understand Tearing When...

You can explain why useState can never tear (React controls the version) but reading window.innerWidth directly in render can tear, and what useSyncExternalStore does differently than a simple subscription + setState pattern.
