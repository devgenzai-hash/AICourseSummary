Stale Closure Problem

When your event handler remembers yesterday's state — the closure trap that causes some of the most confusing bugs in React hooks.

Intermediate Concept Code
📸 Analogy: Photograph vs Window

A closure captures a photograph of variables at creation time. You're looking at a snapshot, not a live window. If the variable changes after the photo was taken, your closure still sees the old value. A stale closure is like making decisions based on an outdated photograph while the real world has moved on.

The Problem: Closures Freeze State

function Counter() {
    const [count, setCount] = useState(0);
    
    useEffect(() => {
        // This closure captures count = 0 at creation time
        const id = setInterval(() => {
            // BUG: Always logs 0, never the current count
            // The closure "closed over" the initial count value
            console.log(`Count is: \${count}`);  // Always 0!
        }, 1000);
        return () => clearInterval(id);
    }, []); // Empty deps = effect only runs once = closure never refreshes
    
    return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}

How Stale Closures Happen

  1. Component renders — count is 0
  2. useEffect runs — Creates an interval. The callback captures count = 0 in its closure scope.
  3. User clicks — count becomes 1, 2, 3... Component re-renders each time.
  4. Interval fires — Still has the OLD closure from step 2. It sees count = 0 forever.

The dependency array [] tells React "never re-run this effect," so the closure is never recreated with the new value.

Fixes

// FIX 1: Add count to dependencies (creates new interval each time)
useEffect(() => {
    const id = setInterval(() => {
        console.log(`Count is: \${count}`); // Fresh value each time
    }, 1000);
    return () => clearInterval(id); // Cleanup old interval
}, [count]); // Re-run effect when count changes

// FIX 2: useRef for mutable "box" that always has current value
const countRef = useRef(count);
countRef.current = count; // Update ref every render

useEffect(() => {
    const id = setInterval(() => {
        // Ref is a mutable container — always read current value
        console.log(`Count is: \${countRef.current}`);
    }, 1000);
    return () => clearInterval(id);
}, []); // Safe with empty deps because ref is a stable reference

// FIX 3: Functional updater (for setState specifically)
useEffect(() => {
    const id = setInterval(() => {
        // Functional form always receives the LATEST state
        setCount(prev => prev + 1); // No stale closure issue
    }, 1000);
    return () => clearInterval(id);
}, []);

Where This Bites You in Production

  • WebSocket handlers — Message handlers created once capture initial state. Use refs or re-subscribe on state change.
  • Event listeners in useEffect — Scroll/resize handlers with empty deps see stale state.
  • Debounced functions — A debounced callback might fire with state from when it was created, not when it fires.

Common Mistakes

  • Silencing ESLint warnings — // eslint-disable-next-line on exhaustive-deps is almost always a stale closure waiting to happen.
  • Thinking useCallback prevents staleness — It only stabilizes the reference. If deps are wrong, the callback itself is stale.
  • Async closures — await in a closure might resume with a stale snapshot if state changed during the await.

✅ You Truly Understand Stale Closures When...

You can look at any useEffect/useCallback/useMemo and predict whether the captured variables will be fresh or stale at execution time — without running the code.

Build a stopwatch component with start/stop/reset. Make it work correctly using only useRef for the interval ID and useState for display — no stale closure bugs.
