Frontend Concepts / SharedArrayBuffer

SharedArrayBuffer

True shared memory between the main thread and Web Workers — enabling lock-free data structures, Atomics, and C/C++-style concurrency in JavaScript, but requiring strict security headers to prevent Spectre attacks.

Advanced Concurrency Browser API
📋 Daily-Life Analogy: A Shared Whiteboard

Regular postMessage is like passing sticky notes between coworkers — each person gets their own copy. SharedArrayBuffer is like a shared whiteboard that everyone can read from and write to simultaneously. But without coordination rules (Atomics), two people might erase each other's work — a classic race condition.

The Problem: Why SharedArrayBuffer Exists

  • postMessage is slow for large data — Copying a 100MB ArrayBuffer takes time and doubles memory usage
  • WebAssembly needs shared memory — Multi-threaded C/C++/Rust programs compiled to Wasm expect shared address space between threads
  • Real-time applications — Audio processing, game physics, video encoding need workers to read/write the same buffer without copy overhead
  • Lock-free data structures — Concurrent queues, ring buffers, and counters need atomic operations on shared memory

Security Requirement: Cross-Origin Isolation

⚠️ SharedArrayBuffer Requires COOP + COEP Headers

After the Spectre vulnerability (2018), browsers disabled SharedArrayBuffer by default. To re-enable it, your server MUST send these headers:

Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp

This puts your page in a "cross-origin isolated" state where self.crossOriginIsolated === true. Without these headers, new SharedArrayBuffer() throws a TypeError.

Why: Spectre allows timing attacks that can read arbitrary memory. SharedArrayBuffer + high-resolution timers (built from Atomics.wait) would make Spectre trivially exploitable. COOP+COEP prevent cross-origin resources from being in the same process.

Code: Basic Shared Memory Between Threads

// main.js — Create shared memory and pass it to workers

// Allocate 1MB of memory visible to ALL threads simultaneously
const sharedBuffer = new SharedArrayBuffer(1024 * 1024);

// Create typed views into the shared memory
const sharedArray = new Int32Array(sharedBuffer);

// Workers receive the SAME memory — no copy!
const worker1 = new Worker('worker.js');
const worker2 = new Worker('worker.js');

// postMessage with SharedArrayBuffer does NOT copy — it shares
worker1.postMessage({ buffer: sharedBuffer, id: 0 });
worker2.postMessage({ buffer: sharedBuffer, id: 1 });

// Main thread can also read/write the same memory
console.log(sharedArray[0]); // May see values written by workers!

// worker.js — Both workers share the SAME memory
self.onmessage = (event) => {
    const { buffer, id } = event.data;
    const shared = new Int32Array(buffer);
    
    // ❌ RACE CONDITION: Two workers incrementing same location
    // shared[0]++; // NOT atomic! Read-modify-write can interleave
    
    // ✅ CORRECT: Use Atomics for thread-safe operations
    Atomics.add(shared, 0, 1); // Atomic increment — guaranteed no torn read/write
    
    // Atomic wait/notify — like a condition variable
    if (id === 1) {
        // Worker 1 waits until shared[1] changes from 0
        Atomics.wait(shared, 1, 0); // Blocks this thread (not main!)
        console.log('Worker 1 woken up! Value:', shared[1]);
    } else {
        // Worker 0 signals worker 1
        Atomics.store(shared, 1, 42);
        Atomics.notify(shared, 1, 1); // Wake 1 waiting thread
    }
};

Where This Is Used in Production

  • FFmpeg.wasm — Multi-threaded video transcoding in the browser using SharedArrayBuffer for the thread pool's shared memory.
  • Unity WebGL — Game engine's multi-threaded renderer uses SharedArrayBuffer for physics and rendering threads to share scene data.
  • Google Earth — The web version uses shared memory for parallel tile decompression and terrain mesh generation.
  • AutoCAD Web — Uses SharedArrayBuffer for WASM-compiled C++ rendering engine with worker thread parallelism.

Common Mistakes

  • Forgetting COOP/COEP headers — SharedArrayBuffer silently fails without cross-origin isolation. This breaks third-party iframes and images without CORP headers.
  • Non-atomic operations on shared memory — sharedArray[i]++ is NOT atomic. You MUST use Atomics.add() for concurrent access.
  • Using Atomics.wait on main thread — It blocks the thread! Only use in workers. Main thread gets "not-allowed" in most browsers.
  • Assuming SharedArrayBuffer with Service Workers — Service Workers do NOT support SharedArrayBuffer. Only dedicated Web Workers.

✅ You Truly Understand SharedArrayBuffer When...

You can explain why sharedArray[0]++ from two threads might result in 1 instead of 2 (torn read-modify-write), and how Atomics.add() prevents this with a hardware-level CAS instruction.
