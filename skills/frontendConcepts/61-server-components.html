Frontend Concepts / Server Components

Server Components

React components that execute exclusively on the server, never ship JavaScript to the client, can directly access databases and file systems, yet seamlessly compose with interactive client components.

Advanced React Architecture
📰 Analogy: Newspaper vs TV

Server Components are like newspaper articles — the content is produced at the press (server), delivered as static print (HTML/serialized tree), and requires no electricity (JavaScript) to read. Client Components are like TV programs — they need an active device (JS runtime) to display and respond to interaction. A modern page mixes both: static content rendered on server, interactive widgets hydrated on client.

The Problem: Client Components Ship Too Much JS

In traditional React (all client components):

  • Every component's code ships to the client, even if it just displays text
  • Dependencies (marked, syntax-highlighter, date-fns) inflate the bundle
  • Data fetching requires client-server roundtrips (waterfalls)
  • Sensitive logic (API keys, database queries) can't live in components

Server Components solve all four problems simultaneously.

How Server Components Work

// Server Component (default in Next.js App Router)
// This code NEVER reaches the client's JavaScript bundle

// app/blog/[slug]/page.tsx
import { db } from '@/lib/database';       // Direct DB access! Not in bundle
import { marked } from 'marked';             // 32KB lib — stays on server
import hljs from 'highlight.js';             // 1MB lib — stays on server
import { LikeButton } from './LikeButton';   // Client Component (interactive)

export default async function BlogPost({ params }) {
    // Direct database query — no API route needed
    // Executes in the same process, ~1ms latency to DB
    const post = await db.posts.findBySlug(params.slug);
    
    // Heavy markdown parsing happens on server only
    const html = marked.parse(post.content, {
        highlight: (code, lang) => hljs.highlight(code, { language: lang }).value
    });
    
    // Return JSX — but this renders to a SERIALIZED TREE, not client JS
    return (
        <article>
            <h1>{post.title}</h1>
            <div dangerouslySetInnerHTML={{ __html: html }} />
            
            {/* This IS interactive — its code ships to client */}
            <LikeButton postId={post.id} initialCount={post.likes} />
        </article>
    );
}

// Client component (has 'use client' directive)
// ONLY this file's code goes to the client bundle

// LikeButton.tsx — Client Component
'use client'; // ← This directive marks the client boundary

import { useState } from 'react';

export function LikeButton({ postId, initialCount }) {
    const [count, setCount] = useState(initialCount);
    const [liked, setLiked] = useState(false);
    
    async function handleLike() {
        setLiked(true);
        setCount(c => c + 1);
        await fetch(`/api/posts/${postId}/like`, { method: 'POST' });
    }
    
    // This component uses state + events → must be a Client Component
    return <button onClick={handleLike}>❤️ {count}</button>;
}

The Serialization Wire Format (RSC Payload)

// Server Components don't render to HTML strings (that's SSR)
// They render to a SERIALIZED REACT TREE (RSC payload)
// This is a streaming JSON-like format:

// Example RSC payload for BlogPost above:
0:["$","article",null,{"children":[
    ["$","h1",null,{"children":"My Blog Post Title"}],
    ["$","div",null,{"dangerouslySetInnerHTML":{"__html":"<p>rendered markdown...</p>"}}],
    ["$","$Lclient1",null,{"postId":"abc","initialCount":42}]
]}]

// "$Lclient1" = reference to LikeButton client component
// The client knows to load LikeButton.js and hydrate just that part
// Everything else is static — no JS required to display it

// KEY INSIGHT: This payload can be generated at:
// - Build time (static pages)
// - Request time (dynamic pages)
// - Revalidation time (ISR)
// The client doesn't care when it was generated

⚠️ The 'use client' Boundary Is Not Per-Component

'use client' marks a boundary. Everything imported by a client component is also client code. If you import a utility in a client component, that utility ships to the client — even if it could have stayed on the server. Structure imports carefully.

Composition Pattern: Server Wraps Client

// The correct pattern: Server Components can PASS data to Client Components
// but Client Components can't import Server Components directly

// CORRECT: Server fetches data, passes as props to Client
async function DashboardPage() {
    const data = await fetchDashboardMetrics(); // Server-side
    
    return (
        <div>
            <h1>Dashboard</h1>
            {/* Client component receives serializable data */}
            <InteractiveChart data={data.chartData} />
            
            {/* Server Component as children of Client Component */}
            <ClientTabs>
                <ServerRenderedContent /> {/* Passed as children prop */}
            </ClientTabs>
        </div>
    );
}

// The "children" pattern is how you compose Server + Client:
// Client component doesn't import the Server component —
// it receives already-rendered content via the children prop

Where This Lives in Production

  • Next.js App Router — All components are Server Components by default. Only add 'use client' when you need interactivity. This is the reference implementation.
  • Vercel — Their dashboard uses Server Components for data display (metrics, logs, deployments). Only interactive elements (filters, forms) are Client Components.
  • Shopify Hydrogen — Product pages use Server Components. Only Cart interactions and search use Client Components.
  • Waku — Minimal React framework built around Server Components, demonstrating the pattern outside Next.js.

Common Mistakes

  • Adding 'use client' everywhere — If all your components are client components, you've lost all Server Component benefits. Start server-first, add 'use client' only where needed.
  • Passing non-serializable props — Functions, classes, Dates, Maps cannot cross the server→client boundary. Only JSON-compatible values can be passed as props to Client Components.
  • Importing server-only code in client components — Use the server-only package to get build-time errors if server code accidentally reaches the client bundle.
  • Fetching in Client Components out of habit — If data doesn't need to be reactive, fetch it in a Server Component and pass it down. Saves a roundtrip.
  • Assuming Server Components replace API routes — Server Components handle READ operations well. For mutations (POST, PUT, DELETE), use Server Actions or API routes.

✅ You Truly Understand Server Components When...

You can trace exactly which bytes go over the wire: what's in the RSC payload, what's in the JS bundle, and what stays entirely on the server — for a page that mixes 3 Server Components and 2 Client Components.
