Frontend Concepts / Time Slicing

Time Slicing

Breaking long-running rendering work into small chunks that yield control back to the browser between frames, preventing UI freezes.

Advanced Concept Performance
⏰ Analogy: Microwave in 30-Second Bursts

Imagine you need to microwave food for 5 minutes, but you also need to answer the doorbell if it rings. Instead of running 5 minutes straight (blocking), you run 30 seconds at a time, check if the doorbell rang, then continue. Each 30-second burst is a "time slice." The food still gets cooked, but you remain responsive to interrupts.

The Problem: Long Tasks Block the Main Thread

The browser's main thread handles everything: rendering, user input, JavaScript execution. If a JavaScript task runs for 200ms straight, the browser can't:

  • Process user clicks or keypresses
  • Run CSS animations
  • Paint new frames (causes visible jank at 60fps = 16.67ms per frame)

How Time Slicing Works

// React's scheduler yields every ~5ms to check for higher-priority work
// Simplified model of how React's workLoop operates:

let deadline = 0;
const YIELD_INTERVAL = 5; // ms — React yields every 5ms

function workLoop() {
    // Process Fiber nodes one at a time
    while (currentWork !== null) {
        // Check: should we yield control back to the browser?
        if (shouldYield()) {
            // Stop working — let browser handle events, paint frames
            // Schedule ourselves to continue later
            scheduleCallback(workLoop);
            return;
        }
        
        // Process one unit of work (one Fiber/component)
        currentWork = performUnitOfWork(currentWork);
    }
    
    // All work complete — commit to DOM in one batch
    commitRoot();
}

function shouldYield() {
    // Have we used up our time slice?
    return performance.now() >= deadline;
}

function scheduleCallback(callback) {
    // Use MessageChannel for scheduling (not setTimeout which has 4ms min delay)
    const channel = new MessageChannel();
    channel.port1.onmessage = () => {
        deadline = performance.now() + YIELD_INTERVAL;
        callback();
    };
    channel.port2.postMessage(null);
}

Manual Time Slicing (Without React)

// Processing a large array without blocking the UI

async function processLargeList(items, processItem) {
    const CHUNK_SIZE = 100;
    const results = [];
    
    for (let i = 0; i < items.length; i += CHUNK_SIZE) {
        // Process a chunk
        const chunk = items.slice(i, i + CHUNK_SIZE);
        for (const item of chunk) {
            results.push(processItem(item));
        }
        
        // Yield to the browser — let it handle events and paint
        await yieldToMain();
    }
    
    return results;
}

function yieldToMain() {
    // scheduler.yield() is the modern API (Chrome 115+)
    if ('scheduler' in window && 'yield' in scheduler) {
        return scheduler.yield();
    }
    // Fallback: setTimeout(0) yields but has minimum 4ms delay
    return new Promise(resolve => setTimeout(resolve, 0));
}

// Usage: processing 50,000 items without freezing UI
await processLargeList(hugeArray, item => transform(item));

Real-World Usage

  • React Scheduler — Uses MessageChannel-based scheduling to slice rendering work into 5ms chunks. This is what makes concurrent features (useTransition, Suspense) possible.
  • Google Maps — Tile rendering is time-sliced so panning the map remains smooth even while loading new tiles.
  • scheduler.yield() — A new web platform API (Chrome 115+) designed specifically for cooperative yielding without the 4ms setTimeout penalty.

✅ You Truly Understand Time Slicing When...

You can explain why React uses MessageChannel instead of setTimeout for scheduling, and what the performance difference is (hint: setTimeout has a minimum 4ms delay after 5 nested calls).
