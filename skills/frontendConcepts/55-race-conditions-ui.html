Race Conditions in UI State

When multiple asynchronous operations compete to update the same state, the "winner" depends on timing — leading to stale data, UI glitches, and impossible-to-reproduce bugs.

Intermediate Async Patterns React/UI
🏁 Analogy: Two Delivery Drivers

You order pizza, then cancel and order sushi. Both delivery drivers are already en route. If the pizza arrives after the sushi, you're looking at pizza on your table (stale order). A UI race condition is exactly this: the response to an outdated request arrives last and overwrites the correct current state.

The Problem: Async Doesn't Guarantee Order

// The classic race condition: type-ahead search
// User types "re" → "rea" → "react" rapidly

function SearchComponent() {
    const [query, setQuery] = useState('');
    const [results, setResults] = useState([]);

    async function handleChange(e) {
        const value = e.target.value;
        setQuery(value);
        
        // BUG: Three requests fire in parallel
        // Request for "re"    takes 300ms (slow server)
        // Request for "rea"   takes 100ms
        // Request for "react" takes 150ms
        const data = await fetch(`/api/search?q=${value}`);
        const json = await data.json();
        
        // Responses arrive: "rea"(100ms) → "react"(150ms) → "re"(300ms)
        // Final state shows results for "re" — WRONG!
        // User typed "react" but sees results for "re"
        setResults(json);
    }

    return <input onChange={handleChange} />;
}

Solution 1: AbortController (Cancel Stale Requests)

function SearchWithAbort() {
    const [results, setResults] = useState([]);
    const controllerRef = useRef(null);

    async function handleChange(e) {
        const value = e.target.value;
        
        // Cancel the previous in-flight request
        // This tells the browser to abort the fetch AND reject the promise
        controllerRef.current?.abort();
        
        // Create new controller for this request
        const controller = new AbortController();
        controllerRef.current = controller;
        
        try {
            const res = await fetch(`/api/search?q=${value}`, {
                signal: controller.signal // Link fetch to this controller
            });
            const data = await res.json();
            setResults(data); // Only reached if not aborted
        } catch (err) {
            if (err.name === 'AbortError') {
                // Expected — request was superseded by newer one
                return;
            }
            throw err; // Re-throw real errors
        }
    }

    return <input onChange={handleChange} />;
}

Solution 2: Request ID / Staleness Check

function SearchWithId() {
    const [results, setResults] = useState([]);
    const latestRequestId = useRef(0);

    async function handleChange(e) {
        const value = e.target.value;
        
        // Increment the request counter — this is our "version"
        const requestId = ++latestRequestId.current;
        
        const res = await fetch(`/api/search?q=${value}`);
        const data = await res.json();
        
        // Only update state if this is still the latest request
        // If user typed again while we waited, requestId !== latestRequestId
        if (requestId === latestRequestId.current) {
            setResults(data);
        }
        // Otherwise: silently discard stale response
    }

    return <input onChange={handleChange} />;
}

Solution 3: useEffect Cleanup (React Pattern)

function SearchWithCleanup({ query }) {
    const [results, setResults] = useState([]);

    useEffect(() => {
        // This flag prevents stale closures from updating state
        let cancelled = false;
        const controller = new AbortController();

        async function fetchResults() {
            try {
                const res = await fetch(`/api/search?q=${query}`, {
                    signal: controller.signal
                });
                const data = await res.json();
                
                // Double-check: effect might have been cleaned up while awaiting
                if (!cancelled) {
                    setResults(data);
                }
            } catch (err) {
                if (!cancelled && err.name !== 'AbortError') {
                    console.error(err);
                }
            }
        }

        fetchResults();

        // Cleanup runs when query changes or component unmounts
        // This prevents the stale response from winning the race
        return () => {
            cancelled = true;
            controller.abort();
        };
    }, [query]); // Re-run when query changes → old effect cleaned up first

    return <ul>{results.map(r => <li key={r.id}>{r.title}</li>)}</ul>;
}

Other Race Condition Patterns

// Pattern: Optimistic update + server rejection
async function toggleLike(postId) {
    // Optimistically update UI immediately
    setLiked(prev => !prev);
    setCount(prev => liked ? prev - 1 : prev + 1);
    
    try {
        await fetch(`/api/posts/${postId}/like`, { method: 'POST' });
    } catch {
        // Server rejected — ROLL BACK the optimistic update
        // But what if user clicked again while request was in-flight?
        // Now we're rolling back a rollback... race condition!
        setLiked(prev => !prev); // This might not restore correct state
    }
}

// FIX: Use a version counter for the expected server state
async function toggleLikeSafe(postId) {
    const version = ++versionRef.current;
    const newLiked = !liked;
    setLiked(newLiked);
    
    try {
        const res = await fetch(`/api/posts/${postId}/like`, { method: 'POST' });
        const serverState = await res.json();
        // Only reconcile if this is still the latest action
        if (version === versionRef.current) {
            setLiked(serverState.liked); // Server is source of truth
        }
    } catch {
        if (version === versionRef.current) {
            setLiked(!newLiked); // Safe rollback — still latest version
        }
    }
}
⚠️ React 18's Automatic Batching Doesn't Fix This

React 18 batches state updates within the same event handler, but race conditions are about async timing between different events. Multiple fetches resolving out of order still cause stale state regardless of batching. You need explicit cancellation or staleness checks.

Where This Lives in Production

  • TanStack Query (React Query) — Built-in query cancellation. Each query has a queryKey; when the key changes, the previous fetch is automatically cancelled via AbortController.
  • SWR (Vercel) — Uses request deduplication and stale-while-revalidate pattern. Returns cached data immediately, then revalidates in the background.
  • Redux Toolkit (RTK Query) — Subscription-based queries are automatically cancelled when components unmount or args change.
  • Algolia InstantSearch — Their search client handles out-of-order responses internally with sequence numbers.

Common Mistakes

  • Not aborting on unmount — Setting state on an unmounted component causes memory leaks and React warnings.
  • Debouncing without cancellation — Debounce reduces requests but doesn't prevent the stale-response problem. The last debounced request can still lose to an earlier one.
  • Multiple setState calls in async functions — Each await point is a place where component might re-render with different props. Check staleness after every await.
  • Shared mutable state between effects — Refs can help, but multiple effects writing to the same ref create their own race.
