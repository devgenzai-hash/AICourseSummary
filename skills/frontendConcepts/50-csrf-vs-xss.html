CSRF vs XSS Mitigation

Two fundamentally different attack vectors that exploit trust — XSS exploits the user's trust in a site, CSRF exploits the site's trust in the user's browser.

Advanced Security Browser
🔐 Analogy: Impersonation vs Break-In

CSRF is like someone forging your signature on a check — the bank (server) sees your valid credentials (cookies) and processes the transaction. The attacker never sees your account details; they just trick the bank into acting on your behalf.

XSS is like someone planting a hidden camera in your house — the attacker gets full access to everything you can see and do. They inject their code into a trusted page and operate with your full privileges.

The Problem: Two Directions of Trust Exploitation

XSS: How It Works Internally

Three Variants

  1. Stored XSS — Malicious script saved to database, served to all users (e.g., forum comment with <script>)
  2. Reflected XSS — Script bounced off server in response to a crafted URL (e.g., search query reflected in page)
  3. DOM-based XSS — Script injected purely client-side via unsafe DOM manipulation (e.g., innerHTML = location.hash)
// DOM-based XSS vulnerability example
// An attacker crafts: https://site.com/page#<img src=x onerror=alert(document.cookie)>

// VULNERABLE CODE — never do this
document.getElementById('output').innerHTML = location.hash.slice(1);
// The hash content is parsed as HTML, executing the onerror handler

// SAFE CODE — use textContent for user-controlled data
document.getElementById('output').textContent = location.hash.slice(1);
// textContent treats everything as plain text — no parsing occurs

XSS Mitigation Strategy (Defense in Depth)

// Layer 1: Output encoding — context-aware escaping
function escapeForHTML(str) {
    // Replace characters that have special meaning in HTML
    // This prevents browser from interpreting user input as markup
    const map = {
        '&': '&amp;',
        '<': '&lt;',
        '>': '&gt;',
        '"': '&quot;',
        "'": '&#x27;',
    };
    return str.replace(/[&<>"']/g, c => map[c]);
}

// Layer 2: DOM API safety — use safe sinks instead of dangerous ones
// DANGEROUS sinks: innerHTML, outerHTML, document.write, eval()
// SAFE alternatives: textContent, setAttribute (for non-event attrs), createElement

// Layer 3: CSP headers — restrict what scripts can execute (see topic 51)
// Layer 4: Trusted Types — browser-enforced type safety for DOM sinks (see topic 52)
// Layer 5: HttpOnly cookies — prevent JS from reading session tokens

// Framework-level protection: React auto-escapes JSX expressions
// This is SAFE — React calls textContent internally:
const UserComment = ({ text }) => <p>{text}</p>;

// This BYPASSES React's protection — treat as red flag in code review:
const Dangerous = ({ html }) => <div dangerouslySetInnerHTML={{ __html: html }} />;
// Only use after sanitization with DOMPurify or similar

CSRF: How It Works Internally

// Attack scenario: User is logged into bank.com
// Attacker hosts evil.com with this hidden form:

// <form action="https://bank.com/transfer" method="POST" id="exploit">
//   <input type="hidden" name="to" value="attacker-account">
//   <input type="hidden" name="amount" value="10000">
// </form>
// <script>document.getElementById('exploit').submit();</script>

// WHY this works:
// 1. Browser automatically attaches bank.com cookies to the request
// 2. Server sees valid session cookie → processes transfer
// 3. Attacker never sees the cookie — just exploits automatic inclusion

CSRF Mitigation Strategy

// Defense 1: Synchronizer Token Pattern (most common)
// Server generates unique token per session/form, validates on submission

// Server-side (Node.js/Express example)
const crypto = require('crypto');

app.use((req, res, next) => {
    // Generate cryptographically random token bound to user's session
    if (!req.session.csrfToken) {
        req.session.csrfToken = crypto.randomBytes(32).toString('hex');
    }
    res.locals.csrfToken = req.session.csrfToken;
    next();
});

app.post('/transfer', (req, res) => {
    // Attacker cannot know this token — it's not in cookies
    if (req.body._csrf !== req.session.csrfToken) {
        return res.status(403).send('CSRF token mismatch');
    }
    // Process legitimate request...
});

// Defense 2: SameSite cookies (modern browsers)
// Set-Cookie: session=abc123; SameSite=Strict; Secure; HttpOnly
// SameSite=Strict: cookie NEVER sent on cross-origin requests
// SameSite=Lax: sent on top-level navigations (GET only), not POST/fetch

// Defense 3: Double-submit cookie pattern (stateless alternative)
// 1. Set CSRF token in a non-HttpOnly cookie
// 2. Client reads cookie, sends token in header/body
// 3. Server compares cookie value with header value
// WHY it works: attacker can trigger cookie sending but cannot READ it
//   due to Same-Origin Policy, so they can't duplicate it in the body

// Defense 4: Origin/Referer header checking
app.post('/api/*', (req, res, next) => {
    const origin = req.headers.origin || req.headers.referer;
    const allowed = ['https://mysite.com'];
    if (!allowed.some(o => origin?.startsWith(o))) {
        return res.status(403).send('Cross-origin request blocked');
    }
    next();
});
⚠️ XSS Defeats CSRF Protection

If an attacker achieves XSS on your site, they can read CSRF tokens from the DOM and submit valid forms. This is why XSS is considered the more severe vulnerability — it subsumes CSRF. Fix XSS first, then layer CSRF protection for defense in depth.

Where This Lives in Production

  • Django — Built-in CSRF middleware uses double-submit cookies + hidden form tokens. The {% csrf_token %} template tag is mandatory for forms.
  • Rails — protect_from_forgery generates per-session tokens. Rails 6+ uses SameSite=Lax as default cookie policy.
  • React (Next.js) — Auto-escapes JSX (XSS protection). For CSRF, Server Actions use bound tokens. API routes need manual CSRF checks or rely on SameSite cookies.
  • GitHub — Uses strict CSP + nonce-based script loading for XSS prevention, plus CSRF tokens on all state-changing forms.

Common Mistakes

  • Relying only on SameSite cookies — Doesn't protect against same-site subdomain attacks. Still need CSRF tokens for sensitive operations.
  • Escaping HTML but not JavaScript/URL contexts — <a href="javascript:alert(1)"> bypasses HTML encoding. Context matters.
  • CSRF tokens in GET requests — Tokens leak via Referer headers, browser history, and server logs.
  • Using blocklists for XSS filtering — WAFs that block <script> are trivially bypassed (<img onerror>, <svg onload>, mutation XSS).
  • Assuming APIs don't need CSRF protection — If your API accepts cookies for auth AND allows Content-Type: application/x-www-form-urlencoded, it's vulnerable.

You can explain why a JSON API endpoint with cookie auth might still be CSRF-vulnerable despite not accepting form submissions (hint: navigator.sendBeacon and simple requests that don't trigger preflight).
