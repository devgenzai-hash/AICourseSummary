Frontend Concepts / Structural Sharing

Structural Sharing

A technique where updated data structures reuse unchanged parts of the old structure rather than copying everything — the backbone of efficient immutable state management.

Intermediate Concept Code
🌲 Analogy: Changing a Leaf on a Tree

Imagine a tree with 1000 branches. If one leaf changes color, you don't grow an entirely new tree. You create a new path from root to the changed leaf, pointing to the same unchanged branches. The old tree still exists (immutability), but you only allocated memory for the changed path — not the whole tree.

The Problem: Naive Immutability is Expensive

// Naive deep copy for immutability — O(n) time and space EVERY update
const newState = JSON.parse(JSON.stringify(state));
newState.users[42].name = "Alice";
// Copied ALL 10,000 users just to change one name!

// Structural sharing — only copy the PATH to the change
const newState = {
    ...state,                    // Reuse top-level references
    users: [
        ...state.users.slice(0, 42),  // Reuse array prefix references
        { ...state.users[42], name: "Alice" }, // New object for changed item
        ...state.users.slice(43)   // Reuse array suffix references
    ]
};
// Only the users array and user[42] are new objects
// Everything else is SHARED with the old state (same memory)

How Immer Implements Structural Sharing

import { produce } from 'immer';

const state = {
    users: [{ id: 1, name: "Bob" }, { id: 2, name: "Carol" }],
    settings: { theme: "dark", lang: "en" }
};

const nextState = produce(state, draft => {
    // Immer uses Proxies to track which parts you actually modify
    draft.users[0].name = "Alice";
});

// What Immer produced via structural sharing:
nextState !== state;                   // true — new root
nextState.users !== state.users;       // true — users array changed
nextState.users[0] !== state.users[0]; // true — this user changed
nextState.users[1] === state.users[1]; // TRUE! Same reference — unchanged
nextState.settings === state.settings; // TRUE! Same reference — untouched

Persistent Data Structures (Tries)

// Libraries like Immutable.js use Hash Array Mapped Tries (HAMT)
// This gives O(log₃₂ n) ≈ O(1) updates with structural sharing

// Conceptual model of a 32-way branching trie:
//         ROOT
//       /   |   \
//     [0-31] [32-63] [64-95] ...
//     /  \
//   [0-15] [16-31]

// To update index 42:
// 1. Create new root pointing to new branch for [32-63]
// 2. Create new [32-63] node pointing to new leaf at position 42
// 3. All other branches are SHARED with old trie
// 4. Total new nodes: O(log₃₂ n) ≈ 4 for a million elements

Real-World Usage

  • Redux — Relies on structural sharing for change detection. useSelector uses === to check if state slices changed — only works because unchanged parts keep the same reference.
  • Immer (used by Redux Toolkit) — Automatically produces structurally-shared immutable updates using Proxies.
  • Immutable.js (Facebook) — Persistent data structures with O(log₃₂n) structural sharing via HAMTs.
  • Clojure/ClojureScript — Language-level persistent data structures that pioneered this approach in the frontend world.

✅ You Truly Understand Structural Sharing When...

You can explain why state.settings === nextState.settings being true lets React skip re-rendering the Settings component, and why deep-copying would break this optimization.

🧪 Try This Challenge

Create a Redux store with nested state. Log Object.is(prev.nested, next.nested) in a selector. Observe that untouched slices keep referential equality — then break it by accidentally spreading everything.
