First Input Delay (FID)

The time between a user's FIRST interaction (click, tap, keypress) and when the browser can BEGIN processing the event handler — measuring how blocked the main thread was at the critical moment of first engagement.

Intermediate Core Web Vital (Legacy) User Experience
🏪 Analogy: Walking Into a Store

You walk into a store and say "Hello!" to the employee. FID measures how long the employee takes to look up and acknowledge you — NOT how long it takes them to fully help you. They might be stocking shelves (running JavaScript), so your greeting waits. FID = the wait before they start responding. The actual help time is separate (processing + rendering).

The Problem: Pages That Look Ready But Aren't

// Classic scenario: Page renders content (good LCP!) but main thread is blocked
//
// Timeline:
// 0ms        1000ms      2000ms      3000ms      4000ms
// |──────────|──────────|──────────|──────────|
// [HTML parse]                                        
//      [CSS download + parse]                         
//            [Hero image loads → LCP at 1200ms]       
//                  [████ JS bundle executing (1500-3500ms) ████]
//                        ↑ USER CLICKS at 2000ms
//                        │                    ↑ Handler starts at 3500ms
//                        └── FID = 1500ms ────┘
//
// Page LOOKS interactive (content visible) but IS NOT interactive
// This is the "uncanny valley of interactivity"

How FID Is Measured

// FID uses the Event Timing API via PerformanceObserver
// It measures: event.processingStart - event.startTime
//
// event.startTime     = when the user physically interacted (hardware timestamp)
// event.processingStart = when the browser began running the event handler
// The gap between them IS the input delay

const fidObserver = new PerformanceObserver((list) => {
    const entry = list.getEntries()[0]; // Only first input matters for FID
    
    const fid = entry.processingStart - entry.startTime;
    
    console.log({
        fid: fid,                          // The actual delay in ms
        eventType: entry.name,             // 'pointerdown', 'click', 'keydown', etc.
        startTime: entry.startTime,        // When user interacted
        processingStart: entry.processingStart, // When handler began
        processingEnd: entry.processingEnd,     // When handler finished
        duration: entry.duration           // Total time including rendering
    });
    
    // Google's thresholds:
    // Good: ≤100ms | Needs Improvement: 100-300ms | Poor: >300ms
});

fidObserver.observe({ type: 'first-input', buffered: true });
// buffered:true is ESSENTIAL — first input often fires before analytics loads

What Counts as "First Input"?

// COUNTED (discrete events with clear start/end):
// - click / mousedown / pointerdown
// - keydown / keypress
// - touchstart / pointerdown (mobile tap)

// NOT COUNTED (continuous events without clear "first" moment):
// - scroll (starts from a scroll event, not pointer)
// - mousemove / pointermove (continuous)
// - wheel (scroll events)

// WHY scroll is excluded:
// Scroll is handled by the compositor thread (off main thread)
// It doesn't wait for JavaScript, so it has different perf characteristics

FID vs TBT: Field vs Lab

// FID is a FIELD metric — measured on real user devices
// You CANNOT measure FID in a lab (Lighthouse, WebPageTest) because
// there's no real user to provide the "first input"

// TBT (Total Blocking Time) is the LAB PROXY for FID:
// TBT = sum of blocking portions of all long tasks between FCP and TTI
//
// Long task: 250ms  → blocking time = 250 - 50 = 200ms
// Long task: 90ms   → blocking time = 90 - 50 = 40ms
// Long task: 45ms   → blocking time = 0 (under 50ms threshold)
// TBT = 200 + 40 = 240ms
//
// High TBT in lab → likely high FID in field
// The correlation isn't perfect because FID depends on WHEN the user clicks
// (if they click between long tasks, FID can be 0 even with high TBT)

What Causes High FID (and How to Fix It)

// CAUSE 1: Large JavaScript bundles executing during page load
// FIX: Code-split, defer non-critical JS, use dynamic imports

// Before: One massive bundle blocks the main thread
<script src="app-bundle.js"></script> // 500KB, takes 2000ms to parse+execute

// After: Split into critical path + deferred chunks
<script src="critical.js"></script>          // 50KB, 200ms
<script src="deferred.js" defer></script>     // Parses after HTML, lower priority
<link rel="modulepreload" href="lazy.js">    // Preload but don't execute yet

// CAUSE 2: Third-party scripts (analytics, ads, chat widgets)
// FIX: Load them after first interaction or in idle time

// Defer third-party loading until user shows engagement
const loadThirdParty = () => {
    const script = document.createElement('script');
    script.src = 'https://chat-widget.example.com/sdk.js';
    document.body.appendChild(script);
};

// Only load after user scrolls, clicks, or 5s passes (whichever first)
const triggers = ['scroll', 'click', 'touchstart', 'keydown'];
let loaded = false;
const onTrigger = () => {
    if (loaded) return;
    loaded = true;
    loadThirdParty();
    triggers.forEach(t => document.removeEventListener(t, onTrigger));
};
triggers.forEach(t => document.addEventListener(t, onTrigger, { once: true, passive: true }));
setTimeout(onTrigger, 5000); // Fallback: load after 5s regardless

// CAUSE 3: Hydration cost in SSR frameworks (React, Next.js, Nuxt)
// FIX: Progressive/selective hydration, Islands architecture

// CAUSE 4: Long synchronous operations (JSON parsing, list rendering)
// FIX: Use Web Workers for heavy computation

// Move JSON parsing off main thread
const worker = new Worker('json-parser.js');
worker.postMessage(hugeJsonString); // Parse in worker, not main thread
worker.onmessage = (e) => render(e.data); // Structured clone back

FID Is Being Replaced by INP (March 2024)

// WHY FID was retired as a Core Web Vital:
//
// 1. Only measures FIRST interaction — ignores all subsequent slow interactions
//    User could have great FID but terrible responsiveness after that
//
// 2. Only measures INPUT DELAY — ignores processing time and rendering
//    A handler could take 500ms but if input delay was 10ms, FID looks "good"
//
// 3. Most sites have good FID (>90% of sites pass)
//    The metric stopped differentiating good sites from great ones
//
// INP (Interaction to Next Paint) replaces FID because:
// - Measures ALL interactions throughout page lifetime
// - Measures full duration: input delay + processing + paint delay
// - Reports the WORST interaction (p98 of all interactions)
// - Much harder to "pass" — drives real improvements

Where This Lives in Production

  • Chrome UX Report (CrUX) — FID data collected from Chrome users with their consent. Available in BigQuery, PageSpeed Insights, and Search Console.
  • Google Search Ranking — FID was part of Core Web Vitals ranking signal from June 2021 to March 2024, when INP replaced it.
  • web-vitals library (Google) — The onFID() function wraps the PerformanceObserver setup with proper edge-case handling.
  • RUM tools (SpeedCurve, Calibre, mPulse) — All Real User Monitoring tools report FID alongside other vitals for field performance tracking.

Common Mistakes

  • Confusing FID with TTI — TTI is when the page becomes CONSISTENTLY interactive. FID is the delay at ONE specific moment (the first click).
  • Trying to measure FID in Lighthouse — Impossible. Use TBT as the lab proxy instead.
  • Thinking good FID = good interactivity — FID only captures the first interaction. A site can have 5ms FID but 500ms delays on subsequent interactions.
  • Optimizing for FID but not INP — Since March 2024, INP is the ranking signal. Fix all slow interactions, not just the first one.

✅ You Truly Understand FID When...

You can explain why a page with a 1200ms LCP and 5ms FID is possible (user clicked after JS finished), and why a page with 200ms LCP but 800ms FID is also possible (user clicked during JS execution) — and why INP is a better metric for both cases.

🧪 Try This Challenge

Build a page that intentionally has good FID (<50ms) but terrible subsequent interaction latency (>500ms). Then explain what code pattern creates this discrepancy and how INP would catch it.

🔗 Connect It

FID connects to: Long Tasks API (long tasks during load are the #1 cause of high FID), Interaction to Next Paint (INP replaces FID), and Hydration (framework hydration is often the long task blocking first input).
