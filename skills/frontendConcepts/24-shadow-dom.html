Frontend Concepts / Shadow DOM

Shadow DOM

The browser's native encapsulation mechanism — how to create DOM subtrees with their own isolated scope for styles and markup, invisible to outside JavaScript and CSS.

Intermediate Web Platform Browser API
🏠 Daily-Life Analogy: A House Within a Neighborhood

Think of the regular DOM as a neighborhood with open-plan houses — everyone can see into everyone else's house, and one person's loud paint colors (CSS) bleed into neighboring homes. Shadow DOM is like building a house with opaque walls and a private entrance. The neighborhood knows the house exists (the host element), but cannot see or modify the interior. The house has its own interior decorator (scoped styles) that doesn't affect — or get affected by — the neighborhood.

The Problem: Why Shadow DOM Exists

CSS has a fundamental scoping problem: everything is global. When you write .button { color: red }, it affects every element with class button on the page. This causes:

  • Style collisions — Third-party widgets (chat, analytics, ads) break your app's styles or vice versa
  • Specificity wars — Teams resort to BEM, CSS Modules, or CSS-in-JS just to avoid conflicts
  • DOM coupling — Scripts can accidentally query and modify internal elements of components they shouldn't touch
  • No true encapsulation — Even with naming conventions, nothing stops external code from reaching in

Shadow DOM provides browser-native encapsulation: styles don't leak in or out, and internal DOM is hidden from document.querySelector().

How Shadow DOM Works Internally

The DOM Tree Structure

<!-- What the HTML looks like -->
<my-card>
    <!-- #shadow-root (open) -->
    <!--   <style>.title { color: blue; }</style> -->
    <!--   <h2 class="title"><slot></slot></h2> -->
    Hello World
</my-card>

<!-- From outside: -->
<!-- document.querySelector('.title') → null (hidden!) -->
<!-- document.querySelector('my-card').shadowRoot.querySelector('.title') → works -->

Code: Creating and Using Shadow DOM

// Creating a Shadow DOM — the foundational API
class UserCard extends HTMLElement {
    constructor() {
        super();
        
        // 'open' mode: shadowRoot is accessible via element.shadowRoot
        // 'closed' mode: shadowRoot returns null (used by browser internals like <video>)
        const shadow = this.attachShadow({ mode: 'open' });
        
        // Styles defined here CANNOT leak out to the page
        // Page styles CANNOT leak in (except inherited properties)
        shadow.innerHTML = `
            <style>
                /* :host targets the custom element itself (the outer shell) */
                :host {
                    display: block;
                    border: 1px solid #333;
                    border-radius: 8px;
                    padding: 16px;
                    font-family: system-ui;
                }
                
                /* :host() with a selector — matches when host has that attribute/class */
                :host([variant="premium"]) {
                    border-color: gold;
                    background: linear-gradient(135deg, #1a1a2e, #16213e);
                }
                
                /* These styles are COMPLETELY isolated */
                h2 { color: #e0e0e0; margin: 0 0 8px; }
                .email { color: #888; font-size: 0.9em; }
                
                /* ::slotted() styles projected content (light DOM children) */
                ::slotted(span) { font-weight: bold; }
            </style>
            
            <h2><slot name="name">Anonymous</slot></h2>
            <p class="email"><slot name="email"></slot></p>
            <div class="content"><slot></slot></div>
        `;
    }
}

customElements.define('user-card', UserCard);

<!-- Usage in HTML — slots project light DOM content into shadow DOM -->
<user-card variant="premium">
    <span slot="name">Akash Ranjan</span>
    <span slot="email">akash@example.com</span>
    <p>This content goes into the default (unnamed) slot</p>
</user-card>

<!-- Even if the page has: h2 { color: red !important; } -->
<!-- The h2 inside shadow DOM stays #e0e0e0 — the boundary blocks it -->

Event Retargeting

// Events that originate inside shadow DOM are "retargeted"
// When they cross the shadow boundary, event.target becomes the host element

document.querySelector('user-card').addEventListener('click', (e) => {
    console.log(e.target);         // → <user-card> (retargeted!)
    console.log(e.composedPath()); // → [h2, shadow-root, user-card, body, html, document, window]
    // composedPath() reveals the full path including shadow internals
});

// Inside the shadow root, events behave normally:
shadow.querySelector('h2').addEventListener('click', (e) => {
    console.log(e.target); // → <h2> (not retargeted within same shadow)
});

Open vs Closed Shadow DOM

ModeAccessUse Case
openelement.shadowRoot worksMost components — allows testing, devtools, a11y tools
closedelement.shadowRoot returns nullBrowser builtins (<video>, <input type="range">). Rarely use in userland — breaks debugging.
💡 CSS Custom Properties Cross the Boundary

While regular CSS properties are blocked by Shadow DOM, CSS custom properties (variables) inherit through the shadow boundary. This is the official theming mechanism: define --primary-color on the host or :root, and shadow DOM internals can use var(--primary-color). This is by design — it's how you theme encapsulated components.

Where This Is Used in Production

  • YouTube — The entire YouTube player UI uses Shadow DOM internally (<ytd-player>) to prevent page styles from breaking the player controls.
  • Salesforce Lightning Web Components (LWC) — Their entire enterprise component framework is built on Shadow DOM for true encapsulation between components from different teams.
  • GitHub — Uses custom elements with Shadow DOM for interactive widgets like <details-dialog>, <clipboard-copy>, etc.
  • Chrome DevTools — The DevTools UI itself uses Shadow DOM extensively for its component architecture.

Common Mistakes

  • Expecting global styles to work inside Shadow DOM — They don't. You must include styles inside the shadow root or use CSS custom properties for theming.
  • Using document.querySelector to find shadow content — It can't pierce the boundary. Use element.shadowRoot.querySelector().
  • Forgetting event retargeting — Event delegation on the document won't see the original target. Use event.composedPath() if needed.
  • Over-isolating with closed mode — Closed shadow DOM breaks accessibility tools, testing libraries, and browser extensions. Almost never use it.
  • Not using <slot> for composition — If consumers can't inject content, your component is inflexible. Use named slots for structure.

✅ You Truly Understand Shadow DOM When...

You can explain why document.querySelector('h2') returns null when there's clearly an h2 visible on the page, and you can describe exactly which CSS properties cross the shadow boundary and why.
