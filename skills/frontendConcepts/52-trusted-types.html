Frontend Concepts / Trusted Types

Trusted Types

A browser API that eliminates DOM XSS by enforcing type safety on dangerous DOM sinks — making it impossible to pass raw strings to innerHTML, eval, or document.write.

Advanced Security Browser API
🔒 Analogy: Type-Checked Keys

Imagine a building where every door requires a specific shaped key — not just any piece of metal. Without Trusted Types, DOM sinks like innerHTML accept any string (any piece of metal). With Trusted Types, the browser requires a specially-crafted typed object that can only be created through your approved sanitization functions (the locksmith). Even if an attacker gets a string into your code, they can't open the door without going through your locksmith.

The Problem: Why Output Encoding Isn't Enough

The web platform has ~60 DOM sinks that interpret strings as code or markup:

  • element.innerHTML, element.outerHTML
  • document.write(), document.writeln()
  • eval(), setTimeout(string), setInterval(string)
  • new Function(string)
  • element.setAttribute('onclick', string)
  • location.href = 'javascript:' + string

Any one of these, if passed attacker-controlled input, causes DOM XSS. Trusted Types solves this at the browser level — the sink itself refuses raw strings.

How Trusted Types Works Internally

// Step 1: Enable Trusted Types via CSP header
// This tells the browser to REJECT raw strings at DOM sinks
Content-Security-Policy: require-trusted-types-for 'script';
                         trusted-types my-sanitizer default;

// Step 2: Create a Trusted Types policy (your "locksmith")
const sanitizerPolicy = trustedTypes.createPolicy('my-sanitizer', {
    // This function is the ONLY way to create TrustedHTML in your app
    // All innerHTML assignments must go through here
    createHTML: (input) => {
        // Use DOMPurify or similar battle-tested sanitizer
        return DOMPurify.sanitize(input, {
            ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'a'],
            ALLOWED_ATTR: ['href'],
        });
    },
    
    // Controls what can be passed to script URL sinks
    createScriptURL: (input) => {
        const url = new URL(input, document.baseURI);
        // Only allow scripts from our own CDN
        if (url.origin !== 'https://cdn.myapp.com') {
            throw new TypeError(`Blocked script URL: ${input}`);
        }
        return input;
    },
    
    // Controls what can be passed to eval-like sinks
    createScript: (input) => {
        // In production, you'd likely reject all eval usage
        throw new TypeError('eval is not allowed');
    }
});

// Step 3: Use the policy to create trusted values
const userContent = '<b>Hello</b><script>evil()</script>';

// WITHOUT Trusted Types: browser happily executes the script
// element.innerHTML = userContent;  ← XSS!

// WITH Trusted Types: browser throws TypeError for raw strings
// element.innerHTML = userContent;  ← TypeError: not a TrustedHTML

// CORRECT: pass through your sanitization policy
element.innerHTML = sanitizerPolicy.createHTML(userContent);
// Result: "<b>Hello</b>" — script tag stripped by DOMPurify

The Default Policy

// The "default" policy is special — it's a fallback for ALL untyped assignments
// Useful for large legacy codebases where you can't refactor everything at once

trustedTypes.createPolicy('default', {
    createHTML: (input, sink) => {
        // Log violations to your monitoring (like CSP reports)
        console.warn(`Untyped innerHTML assignment to ${sink}`, input);
        
        // Sanitize as best-effort — in strict mode you'd throw here
        return DOMPurify.sanitize(input);
    },
    createScriptURL: (input) => {
        // Block ALL dynamic script loading that bypasses your policy
        throw new TypeError(`Blocked dynamic script: ${input}`);
    }
});

// Now EVERY innerHTML assignment in your app (including third-party libs)
// goes through this default policy. No more unmonitored DOM sinks.
⚠️ Third-Party Library Compatibility

Many libraries (jQuery, rich text editors, analytics scripts) use innerHTML internally. Enabling Trusted Types will break them unless you either: (1) use the default policy as a compatibility shim, (2) patch the library, or (3) use the library's Trusted Types-compatible version. This is the biggest adoption challenge.

Browser Enforcement Flow

// What happens internally when Trusted Types is enforced:

// 1. Code attempts: element.innerHTML = someString
// 2. Browser's innerHTML setter checks:
//    - Is Trusted Types enforced? (CSP: require-trusted-types-for 'script')
//    - Is the value a TrustedHTML object? (created by a policy)
// 3. If raw string:
//    a. Is there a "default" policy? → Route through it
//    b. No default policy? → Throw TypeError, block assignment
// 4. If TrustedHTML object → Allow assignment, use inner string value

// The three trusted types:
// TrustedHTML    → for innerHTML, outerHTML, insertAdjacentHTML
// TrustedScript  → for eval(), setTimeout(string), inline event handlers
// TrustedScriptURL → for script.src, import(), Worker constructor

Where This Lives in Production

  • Google — Deployed across Google apps (Gmail, Maps, etc.). Google authored the spec after finding that Trusted Types eliminated DOM XSS in their internal apps. Published research showing 0 DOM XSS vulnerabilities in teams that adopted it.
  • Angular — Has built-in Trusted Types support. Angular's DomSanitizer produces Trusted Types when the API is available. bypassSecurityTrustHtml() returns a TrustedHTML-compatible value.
  • Lit — Google's web component library is Trusted Types-compatible out of the box. Template literals are statically analyzed for safety.

Common Mistakes

  • Creating a policy that doesn't actually sanitize — createHTML: (s) => s defeats the entire purpose. The policy must sanitize or validate.
  • Too many policies — Each policy is an attack surface. Minimize the number and audit each one. Google recommends 1-3 per application.
  • Not testing with enforcement — Report-only mode catches violations but enforcement reveals real breakage. Test in CI with enforcement enabled.
  • Forgetting script URLs — Trusted Types for script loading is critical. Dynamic import() and Worker() constructors are sinks too.

✅ You Truly Understand Trusted Types When...

You can explain how Trusted Types makes DOM XSS a compile-time-like error (TypeError at assignment) instead of a runtime vulnerability, and why this is fundamentally better than scanning for dangerous patterns in code review.

🧪 Try This Challenge

Create a Trusted Types policy for a markdown editor that allows <h1>-<h6>, <p>, <code>, <a href> (only https: URLs), and nothing else. Verify that injecting <img onerror> is blocked at the policy level.
