Browser Compositing Layers

How Chrome's compositor splits the page into independently-rasterized layers, uploads them to the GPU as textures, and composites the final frame — the secret behind smooth 60fps animations.

Advanced Rendering Pipeline Chrome Internals
🎬 Daily-Life Analogy: Animation Cels

Traditional animation uses transparent cels stacked on top of each other. The background stays static on one cel, the character is on another. To animate, you only redraw the character cel — the background never needs repainting. Compositing layers work the same way: each layer is rasterized independently, and the GPU composites (stacks) them together. When only one layer changes (e.g., a transform animation), only that layer's texture moves — no repaint needed.

The Problem: Why Layers Exist

  • Full-page repaints are expensive — Rasterizing the entire page (converting DOM+CSS to pixels) takes 5-50ms. At 60fps you have 16.6ms total.
  • Animations need isolation — If a spinning logo forces the entire page to repaint, scroll performance tanks
  • GPU acceleration — GPUs are designed to composite textured rectangles at hardware speed. Layers map directly to GPU textures.
  • Scrolling performance — Content layers can be pre-rasterized and shifted by the compositor without involving the main thread at all

How Layers Work in Chrome

The Layer Tree

/* Elements are promoted to their own compositing layer when: */

/* 1. Explicit will-change property */
.animated-element { will-change: transform; }

/* 2. 3D or perspective transform */
.card { transform: translateZ(0); } /* The classic "promote to layer" hack */

/* 3. Animated opacity or transform (browser auto-promotes) */
.fade-in { animation: fadeIn 0.3s; }

/* 4. position: fixed or sticky */
.header { position: fixed; top: 0; }

/* 5. Overlap with a composited layer (implicit promotion) */
/* If element B overlaps composited element A, B gets its own layer
   to maintain correct stacking order — "layer squashing" limits this */

/* 6. <video>, <canvas>, WebGL, plugins */
/* These always get their own layer */

What Happens Per Frame

  1. Style calculation — Compute final CSS for each element
  2. Layout — Calculate geometry (position, size)
  3. Layer assignment — Decide which elements get their own compositing layer
  4. Paint — Rasterize each layer into a bitmap (pixels). This is per-layer, not per-page!
  5. Composite — GPU takes all layer textures, applies transforms/opacity, composites into final frame
💡 Key Insight: Compositor-Only Animations

When you animate transform or opacity, the compositor can handle it WITHOUT the main thread. No layout, no paint — just move/fade the existing GPU texture. This is why transform: translateX() is smooth but left: 100px causes jank.

Where This Is Used in Production

  • Google Maps — Map tiles are individual layers. Panning just moves layer positions (compositor-only) while new tiles rasterize in background.
  • iOS Safari — Aggressively layers fixed-position elements for smooth scroll. This is why position: fixed elements sometimes have rendering artifacts on iOS.
  • Chrome's scroll — The scrolling content is a separate layer from fixed UI elements. Scroll is handled entirely by the compositor thread, not main thread.

Common Mistakes

  • Promoting everything with will-change: transform — Each layer costs GPU memory. 50 promoted elements on mobile = memory pressure and crashes.
  • Not removing will-change after animation — Apply it before animation starts, remove after. Permanent will-change wastes resources.
  • Animating width/height expecting GPU compositing — These trigger layout + paint on every frame. Only transform and opacity are compositor-only.
  • Ignoring layer explosion from overlap — A high z-index composited element can force everything overlapping it to also become layers.

✅ You Truly Understand Compositing Layers When...

You can open Chrome DevTools Layers panel, explain why each layer was promoted, calculate its memory cost, and predict which CSS animations will run without main-thread involvement.
