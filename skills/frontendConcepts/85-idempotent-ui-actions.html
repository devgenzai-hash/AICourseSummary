Idempotent UI Actions

Designing user interactions so that performing them multiple times produces the same result as performing them once — preventing double submissions, duplicate state mutations, and accidental repeated side effects.

Intermediate Architecture Reliability
🔘 Analogy: Elevator Button

Pressing an elevator's "up" button once calls the elevator. Pressing it 20 more times doesn't call 20 more elevators. The action is idempotent — the effect of pressing it N times is the same as pressing it once. Your UI actions should work the same way: double-clicking "Submit Order" shouldn't create two orders.

The Problem: Double Submissions and Replay Attacks

// Real-world scenarios where non-idempotent actions cause damage:
//
// 1. Double-click on "Place Order" → two charges on credit card
// 2. Network retry sends form data twice → duplicate database entries
// 3. React strict mode calls effect twice → double API call in dev
// 4. Browser back/forward replays form POST → duplicate submission
// 5. Optimistic UI retry on failure → action applied twice
// 6. User rage-clicks slow button → multiple requests in flight

// NON-IDEMPOTENT (dangerous):
async function handleSubmit() {
    // Every call creates a NEW order — double-click = double charge
    await fetch('/api/orders', { method: 'POST', body: orderData });
}

// IDEMPOTENT (safe):
async function handleSubmit() {
    // Uses idempotency key — server deduplicates
    await fetch('/api/orders', {
        method: 'POST',
        headers: { 'Idempotency-Key': uniqueOrderId },
        body: orderData
    });
    // Calling twice with same key → same result, no duplicate order
}

Frontend Idempotency Patterns

Pattern 1: Disable on Submit (UI Lock)

// Simplest approach: prevent the action from being triggered again

function SubmitButton({ onSubmit }) {
    const [isSubmitting, setIsSubmitting] = useState(false);

    const handleClick = async () => {
        if (isSubmitting) return; // Guard against race condition
        setIsSubmitting(true);
        
        try {
            await onSubmit();
        } finally {
            setIsSubmitting(false); // Re-enable on completion (or error)
        }
    };

    return (
        <button 
            onClick={handleClick} 
            disabled={isSubmitting}
            aria-busy={isSubmitting}
        >
            {isSubmitting ? 'Submitting...' : 'Submit Order'}
        </button>
    );
}

// LIMITATION: This only prevents UI-level duplicates
// Network retries, back button, and programmatic calls bypass it
// You STILL need server-side idempotency

Pattern 2: Idempotency Keys (Client-Generated)

// Generate a unique key per logical operation
// Send it with every request — server deduplicates

function useIdempotentSubmit(submitFn) {
    const [idempotencyKey, setIdempotencyKey] = useState(() => crypto.randomUUID());
    const [status, setStatus] = useState('idle'); // idle | pending | success | error

    const submit = async (data) => {
        if (status === 'pending') return; // Already in flight
        setStatus('pending');
        
        try {
            // Same key = same logical operation, even if called multiple times
            const result = await submitFn(data, idempotencyKey);
            setStatus('success');
            return result;
        } catch (error) {
            setStatus('error');
            // DON'T regenerate key on error — retry should use SAME key
            // This ensures the retry is idempotent
            throw error;
        }
    };

    const reset = () => {
        // New operation = new key (e.g., user starts a fresh form)
        setIdempotencyKey(crypto.randomUUID());
        setStatus('idle');
    };

    return { submit, reset, status, idempotencyKey };
}

// Usage:
function OrderForm() {
    const { submit, reset, status } = useIdempotentSubmit(
        (data, key) => fetch('/api/orders', {
            method: 'POST',
            headers: { 'Idempotency-Key': key },
            body: JSON.stringify(data)
        })
    );
    
    // Even if user double-clicks, network retries, or component re-renders
    // the server only processes the order ONCE per key
}

Pattern 3: State Machine Guards

// Model the action as a state machine — invalid transitions are impossible

const orderMachine = {
    idle: { SUBMIT: 'submitting' },
    submitting: { SUCCESS: 'confirmed', ERROR: 'error' },
    confirmed: { RESET: 'idle' }, // Can't submit from confirmed state
    error: { RETRY: 'submitting', RESET: 'idle' }
};

function useStateMachine(machine, initial) {
    const [state, setState] = useState(initial);
    
    const send = (event) => {
        const nextState = machine[state]?.[event];
        if (nextState) {
            setState(nextState);
            return true; // Transition accepted
        }
        return false; // Transition rejected (idempotent: no state change)
    };
    
    return [state, send];
}

// "SUBMIT" while already "submitting" → no transition → no duplicate request
// The state machine makes illegal states unrepresentable

Pattern 4: Debounce and Deduplication

// For actions that fire rapidly (search, autosave, etc.)

function useIdempotentFetch(url) {
    const inflightRef = useRef(null); // Track current request

    return async (params) => {
        const key = JSON.stringify(params); // Dedup key from params
        
        // If same request is already in flight, return its promise
        // (don't fire a duplicate)
        if (inflightRef.current?.key === key) {
            return inflightRef.current.promise;
        }
        
        // New request — cancel previous if different params
        inflightRef.current?.controller.abort();
        
        const controller = new AbortController();
        const promise = fetch(`${url}?${new URLSearchParams(params)}`, {
            signal: controller.signal
        }).then(r => r.json());
        
        inflightRef.current = { key, promise, controller };
        return promise;
    };
}

// Calling with same params multiple times → only ONE network request
// Calling with different params → cancels previous, starts new

Pattern 5: Optimistic UI with Rollback

// Optimistic updates must be idempotent when retried

function useLikeButton(postId, initialCount) {
    const [liked, setLiked] = useState(false);
    const [count, setCount] = useState(initialCount);
    const pendingRef = useRef(false);

    const toggleLike = async () => {
        if (pendingRef.current) return; // Prevent double-toggle
        pendingRef.current = true;
        
        const newLiked = !liked;
        const newCount = count + (newLiked ? 1 : -1);
        
        // Optimistic update
        setLiked(newLiked);
        setCount(newCount);
        
        try {
            // PUT is idempotent by HTTP spec — safe to retry
            // Server state: liked=true, not "add another like"
            await fetch(`/api/posts/${postId}/like`, {
                method: 'PUT', // PUT = set state (idempotent)
                body: JSON.stringify({ liked: newLiked })
            });
        } catch {
            // Rollback on failure
            setLiked(liked);
            setCount(count);
        } finally {
            pendingRef.current = false;
        }
    };

    return { liked, count, toggleLike };
}

// KEY INSIGHT: Use PUT/PATCH with absolute state ("liked: true")
// NOT POST with relative mutation ("add one like")
// PUT with same body twice → same result (idempotent)
// POST "increment" twice → count goes up by 2 (NOT idempotent)

Where This Lives in Production

  • Stripe API — Every mutating endpoint accepts an Idempotency-Key header. Replaying the same request returns the cached response without re-executing the charge.
  • React 18 Strict Mode — Calls effects twice in development to expose non-idempotent side effects (double mounting catches setup/teardown bugs).
  • Shopify Checkout — Uses client-generated idempotency tokens to prevent double-charges even on network timeout + retry scenarios.
  • Google Forms — Disables submit button + uses form token to prevent duplicate submissions from impatient double-clicks.

Common Mistakes

  • Only disabling the button — UI-level prevention doesn't protect against network retries, back button, or programmatic submission. Always pair with server-side idempotency.
  • Generating new idempotency key on retry — The SAME key must be used for retries of the same logical operation. New key = server treats it as a new operation.
  • Using POST for toggle-style actions — POST "like" is not idempotent. Use PUT with the desired state: { liked: true }.
  • Ignoring React Strict Mode double-invocation — If your effect fires an API call and crashes on double-mount, your action isn't idempotent.
  • Race conditions with async state updates — Two rapid clicks can both read isSubmitting === false before either sets it to true. Use refs or state machines.

✅ You Truly Understand Idempotent UI Actions When...

You can identify whether an action is idempotent (same result if applied 1× or N×), explain the difference between UI-level guards (button disable) and protocol-level idempotency (keys, PUT semantics), and design a system where network failures + retries NEVER cause duplicate side effects.
