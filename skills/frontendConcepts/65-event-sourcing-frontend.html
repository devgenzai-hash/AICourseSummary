Event Sourcing in Frontend

Instead of storing current state, store the sequence of events that produced it — enabling time-travel debugging, infinite undo, audit trails, and deterministic state reconstruction from any point in history.

Advanced Architecture State Management
📚 Analogy: A Bank Ledger vs. a Balance

A bank doesn't store just your current balance ($1,247.83). It stores every transaction: deposit $500, withdraw $20, transfer $100... The balance is derived by replaying all transactions in order. If there's a dispute, they can audit the full history. If they need your balance at 3pm Tuesday, they replay up to that point. This is event sourcing — your frontend state is the "balance," and user actions are the "transactions."

The Problem: State Mutations Destroy History

// Traditional state management: mutate in place, history is lost
let document = { title: 'Draft', body: '', tags: [] };

// User edits happen directly — each mutation overwrites the previous state
document.title = 'My Article';     // Previous title? Gone.
document.body = 'Hello world';     // Can we undo? Not without extra work.
document.tags.push('tech');         // When was this tag added? No idea.
document.body = 'Hello universe';  // Previous body? Overwritten.

// Questions you CANNOT answer with mutable state:
// - What did the document look like 5 minutes ago?
// - Who changed the title and when?
// - Can we undo the last 3 changes but keep the 4th?
// - Two users edited offline — how do we merge?
// - A bug corrupted state — can we replay to find when?

// Event sourcing answers ALL of these by storing events, not state

How It Works: Events → Reducer → State

// The core principle: State = fold(events, initialState)
// This is EXACTLY what Array.reduce does — and what Redux is built on

// Step 1: Define your events (the "ledger entries")
const events = [
  { type: 'TITLE_CHANGED', payload: 'My Article', timestamp: 1700000001, userId: 'u1' },
  { type: 'BODY_EDITED', payload: 'Hello world', timestamp: 1700000002, userId: 'u1' },
  { type: 'TAG_ADDED', payload: 'tech', timestamp: 1700000003, userId: 'u2' },
  { type: 'BODY_EDITED', payload: 'Hello universe', timestamp: 1700000004, userId: 'u1' },
];

// Step 2: The reducer (projection function) — pure, deterministic
function documentReducer(state, event) {
  switch (event.type) {
    case 'TITLE_CHANGED':
      return { ...state, title: event.payload };
    case 'BODY_EDITED':
      return { ...state, body: event.payload };
    case 'TAG_ADDED':
      return { ...state, tags: [...state.tags, event.payload] };
    case 'TAG_REMOVED':
      return { ...state, tags: state.tags.filter(t => t !== event.payload) };
    default:
      return state;
  }
}

// Step 3: Reconstruct state by replaying events
const initialState = { title: 'Untitled', body: '', tags: [] };
const currentState = events.reduce(documentReducer, initialState);
// Result: { title: 'My Article', body: 'Hello universe', tags: ['tech'] }

// TIME TRAVEL: Get state at any point by replaying subset of events
const stateAt2 = events.slice(0, 2).reduce(documentReducer, initialState);
// Result: { title: 'My Article', body: 'Hello world', tags: [] }

// UNDO: Remove last event and re-derive
const undone = events.slice(0, -1).reduce(documentReducer, initialState);
// Result: { title: 'My Article', body: 'Hello world', tags: ['tech'] }

Production Implementation: Event Store with Snapshots

// Full event sourcing system with performance optimization via snapshots
// Without snapshots, replaying 10,000 events on page load is too slow

class EventStore {
  constructor(reducer, initialState) {
    this.reducer = reducer;
    this.initialState = initialState;
    this.events = [];          // Append-only log — never mutate past events
    this.snapshots = [];       // Periodic checkpoints for fast reconstruction
    this.snapshotInterval = 50; // Take snapshot every 50 events
    this.subscribers = [];
    this._currentState = initialState;
  }

  // Append a new event — the ONLY way to change state
  append(event) {
    // Enrich event with metadata (timestamp, sequence number)
    const enrichedEvent = {
      ...event,
      id: crypto.randomUUID(),
      sequence: this.events.length,
      timestamp: Date.now(),
    };

    this.events.push(enrichedEvent);

    // Update current state incrementally (don't replay all events)
    this._currentState = this.reducer(this._currentState, enrichedEvent);

    // Take snapshot at intervals for fast future reconstruction
    if (this.events.length % this.snapshotInterval === 0) {
      this.snapshots.push({
        sequence: enrichedEvent.sequence,
        state: structuredClone(this._currentState)
      });
    }

    // Notify subscribers (React re-renders, persistence, sync, etc.)
    this.subscribers.forEach(fn => fn(this._currentState, enrichedEvent));

    return enrichedEvent;
  }

  // Reconstruct state at any point in time — the key superpower
  getStateAt(sequence) {
    // Find nearest snapshot BEFORE the target sequence
    let snapshot = this.snapshots
      .filter(s => s.sequence <= sequence)
      .pop();

    // Start from snapshot (or initial state) and replay remaining events
    const startState = snapshot ? snapshot.state : this.initialState;
    const startIdx = snapshot ? snapshot.sequence + 1 : 0;

    return this.events
      .slice(startIdx, sequence + 1)
      .reduce(this.reducer, startState);
  }

  // Undo: don't mutate — reconstruct without the last N events
  undo(count = 1) {
    const targetSequence = this.events.length - 1 - count;
    if (targetSequence < 0) return this.initialState;

    this._currentState = this.getStateAt(targetSequence);
    // Mark undone events (don't delete — preserve full audit trail)
    for (let i = 0; i < count; i++) {
      this.events[this.events.length - 1 - i].undone = true;
    }
    return this._currentState;
  }

  // Persist to IndexedDB/server — events are the source of truth
  async persist() {
    const unpersisted = this.events.filter(e => !e.persisted);
    await db.events.bulkAdd(unpersisted);
    unpersisted.forEach(e => e.persisted = true);
  }

  // Hydrate from persistence — rebuild entire state from stored events
  async hydrate() {
    this.events = await db.events.toArray();
    this._currentState = this.events
      .filter(e => !e.undone)
      .reduce(this.reducer, this.initialState);
  }

  subscribe(fn) {
    this.subscribers.push(fn);
    return () => { this.subscribers = this.subscribers.filter(s => s !== fn); };
  }

  get state() { return this._currentState; }
}

Real-World Usage

  • Redux DevTools — Time-travel debugging works because Redux IS event sourcing. Actions are events, the reducer is the projection function, and the store replays actions to reconstruct past states.
  • Figma — Every design operation (move, resize, style change) is an event. Undo/redo replays the event log. Multiplayer collaboration merges event streams from different users.
  • Google Docs — Operational Transformation is event sourcing for text. Every keystroke is an event. The document is reconstructed by replaying transformed operations.
  • Git — Commits are events. The working tree is derived state. You can reconstruct any file at any point by replaying commits. Branching creates divergent event streams; merging reconciles them.
  • EventStoreDB — A purpose-built database for event sourcing. Used by financial systems, healthcare, and e-commerce platforms where audit trails are legally required.

React Integration: useEventSource Hook

// Custom hook that exposes event sourcing semantics to React components

function useEventSource(reducer, initialState) {
  const storeRef = useRef(null);
  const [state, setState] = useState(initialState);

  // Initialize store once (persists across re-renders)
  if (!storeRef.current) {
    storeRef.current = new EventStore(reducer, initialState);
  }

  // Subscribe to state changes
  useEffect(() => {
    return storeRef.current.subscribe((newState) => setState(newState));
  }, []);

  const dispatch = useCallback((event) => {
    storeRef.current.append(event);
  }, []);

  const undo = useCallback((n = 1) => {
    const newState = storeRef.current.undo(n);
    setState(newState);
  }, []);

  const getStateAt = useCallback((seq) => {
    return storeRef.current.getStateAt(seq);
  }, []);

  const history = storeRef.current.events;

  return { state, dispatch, undo, getStateAt, history };
}

Trade-offs & Alternatives

ApproachStrengthsWeaknesses
Event Sourcing Full history; time-travel; audit; deterministic replay; undo/redo free Memory growth; snapshot complexity; eventual consistency thinking
Mutable state (useState) Simple; low memory; fast updates; familiar No history; undo requires manual implementation; no audit trail
Immutable snapshots (Immer) Structural sharing saves memory; simple undo via snapshot stack No semantic events; can't replay; no cross-client sync semantics
Command pattern Undo/redo via command inversion; familiar OOP pattern Each command needs inverse; harder to serialize; no projection flexibility

Common Mistakes

  • Storing derived data in events — Events should contain the minimal facts ("user clicked at x,y"), not computed state ("the shape is now at x,y with these styles"). Derived data belongs in the projection/reducer.
  • Unbounded event growth — Without snapshots and compaction, event logs grow forever. Implement snapshotting and optionally archive old events to cold storage.
  • Non-deterministic reducers — If your reducer uses Date.now() or Math.random(), replaying events produces different state each time. Pass non-deterministic values as event data, not inside the reducer.
  • Conflating events with commands — A command is a REQUEST ("please add this item"). An event is a FACT ("item was added"). Commands can be rejected; events have already happened.
  • Replaying without considering idempotency — If replaying an event triggers side effects (API calls, notifications), those effects fire again. Side effects must be separated from state reconstruction.

✅ You Truly Understand Event Sourcing When...

You can take any stateful UI component and redesign it so that the current state is never stored directly — only the append-only event log exists, and current state is always a deterministic function of those events. You know when snapshots are needed, how to handle offline/online replay, and why events should be immutable facts rather than mutable commands.
