Frontend Concepts / Content Security Policy

Content Security Policy (CSP)

A browser-enforced allowlist that controls which resources can load and execute — the single most effective defense against XSS after output encoding.

Advanced Security HTTP Headers
🏗️ Analogy: Building Access Control

Think of CSP as a security badge system for a building. Without it, anyone can walk in. With CSP, you give the security desk (browser) an explicit list: "Only people from Company A (scripts from cdn.example.com) and Company B (styles from fonts.google.com) are allowed in. Everyone else gets turned away at the door — even if someone inside (injected XSS) tries to invite them."

The Problem: Why CSP Exists

Output encoding catches most XSS, but it fails when:

  • A developer forgets to encode one field (one mistake = full compromise)
  • Third-party scripts introduce vulnerabilities you don't control
  • Complex rendering contexts (SVG, MathML) have encoding edge cases
  • Legacy code uses innerHTML in ways that can't be quickly refactored

CSP acts as a safety net — even if XSS payload reaches the DOM, the browser refuses to execute it unless it matches the policy.

How CSP Works Internally

The Enforcement Model

  1. Server sends Content-Security-Policy HTTP header (or <meta> tag)
  2. Browser parses the policy into a set of directives
  3. For every resource load or script execution, browser checks against policy
  4. Violation? Resource blocked + violation report sent (if configured)
/* CSP Header anatomy — each directive controls one resource type */

Content-Security-Policy:
    default-src 'self';                    /* Fallback for all resource types */
    script-src 'self' 'nonce-abc123'       /* Only scripts with this nonce execute */
               https://cdn.example.com;    /* Or loaded from this CDN */
    style-src 'self' 'unsafe-inline';      /* Allow inline styles (common compromise) */
    img-src 'self' data: https:;           /* Images from self, data URIs, or any HTTPS */
    connect-src 'self'                     /* Fetch/XHR only to same origin */
               https://api.example.com;    /* And this API endpoint */
    frame-ancestors 'none';                /* Cannot be embedded in iframes (clickjacking) */
    base-uri 'self';                       /* Prevent <base> tag hijacking */
    form-action 'self';                    /* Forms can only submit to same origin */
    report-uri /csp-violations;            /* Send violation reports here */

Nonce-Based CSP (Modern Best Practice)

// Server generates a unique nonce per request (Node.js/Express)
const crypto = require('crypto');

app.use((req, res, next) => {
    // Cryptographically random, unique per response
    // Attacker cannot predict this even with XSS on another page
    res.locals.nonce = crypto.randomBytes(16).toString('base64');
    
    res.setHeader('Content-Security-Policy', [
        `script-src 'nonce-${res.locals.nonce}' 'strict-dynamic'`,
        `style-src 'self' 'nonce-${res.locals.nonce}'`,
        `default-src 'self'`,
        `base-uri 'self'`,
        `object-src 'none'`,
    ].join('; '));
    
    next();
});

// In your HTML template — only scripts with matching nonce execute:
// <script nonce="abc123">legitimateCode();</script>  ← RUNS
// <script>injectedByAttacker();</script>             ← BLOCKED

// 'strict-dynamic' allows nonced scripts to load additional scripts
// This solves the problem of third-party scripts loading dependencies
// Without it, you'd need to whitelist every CDN domain recursively

CSP Levels and Evolution

CSP LevelKey FeatureXSS Protection
Level 1Domain allowlistsWeak — CDN hosting bypasses (Angular templates on CDN)
Level 2Nonces + hashesStrong — per-request unpredictable tokens
Level 3strict-dynamicStrongest — nonce propagation, ignores allowlists for scripts
⚠️ The 'unsafe-inline' Trap

script-src 'unsafe-inline' completely negates CSP's XSS protection. Any injected <script> tag will execute. If you need inline scripts, use nonces or hashes instead. For styles, 'unsafe-inline' is a common pragmatic choice (CSS injection is lower severity than JS execution).

Report-Only Mode: Deploying CSP Safely

// Start with report-only to find what breaks WITHOUT blocking
Content-Security-Policy-Report-Only:
    default-src 'self';
    script-src 'nonce-{random}' 'strict-dynamic';
    report-uri /csp-violations;

// Violation reports are JSON POSTed to your endpoint:
{
    "csp-report": {
        "document-uri": "https://example.com/page",
        "violated-directive": "script-src",
        "blocked-uri": "https://evil.com/inject.js",
        "source-file": "https://example.com/page",
        "line-number": 42
    }
}

// Workflow: Report-Only → analyze violations → fix code → enforce
// This can take weeks for large sites — expect 1000s of violations initially

Where This Lives in Production

  • GitHub — Strict nonce-based CSP since 2017. They process millions of violation reports to catch regressions. Their CSP is considered industry gold standard.
  • Google — Pioneered strict-dynamic and nonce-based CSP. Uses CSP across Gmail, Drive, YouTube with per-service policies.
  • Stripe — Extremely strict CSP on payment pages. No external scripts, no inline styles. Every resource must be from their own domain.
  • Next.js — Built-in nonce propagation in App Router. Automatically adds nonces to <Script> components when CSP is configured.

Common Mistakes

  • Allowlisting CDNs broadly — script-src https://cdn.jsdelivr.net lets attackers host payloads on that CDN. Use nonces instead.
  • Forgetting base-uri — Without it, attacker injects <base href="https://evil.com"> and all relative URLs resolve to their server.
  • Not restricting object-src — Flash/Java plugins can execute code. Always set object-src 'none'.
  • CSP via <meta> tag only — Meta tags don't support frame-ancestors or report-uri. Use HTTP headers for full protection.
  • Ignoring violation reports — CSP violations often indicate real attacks or regressions. Monitor them like error logs.

✅ You Truly Understand CSP When...

You can explain why script-src 'self' https://cdnjs.cloudflare.com is practically useless against a determined attacker (hint: JSONP endpoints and Angular template injection on CDNs).
