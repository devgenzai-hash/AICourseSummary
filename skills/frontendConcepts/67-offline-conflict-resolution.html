Frontend Concepts / Offline Conflict Resolution

Offline Conflict Resolution

When users make changes offline and reconnect, their local mutations may conflict with changes made by others. This is the fundamental distributed systems problem — brought to the browser — and there's no single "correct" answer, only trade-off strategies.

Advanced Distributed Systems Offline-First
📚 Analogy: Two People Editing a Whiteboard Photo

Imagine two people photograph the same whiteboard, go to separate rooms, and each draws additions on their photo. When they come back together, they need to merge their drawings onto one whiteboard. If they drew in different areas — easy merge. If they both changed the same spot — conflict. Do you keep both? Pick the most recent? Ask the users? This is exactly what offline-first apps face when clients reconnect.

The Problem: Divergent State

// The scenario that creates conflicts:
//
// Server state: { title: "Original", items: [A, B, C] }
//
// Alice goes offline, makes changes:
//   - Renames title to "Alice's Version"
//   - Deletes item B
//   - Adds item D
//
// Bob (online) simultaneously:
//   - Renames title to "Bob's Version"
//   - Edits item B's content
//   - Reorders items to [C, B, A]
//
// Alice reconnects. Now what?
// - Title conflict: "Alice's Version" vs "Bob's Version"
// - Item B: Alice deleted it, Bob edited it (delete-edit conflict)
// - Order: Alice assumes [A, C, D], Bob has [C, B, A]
//
// There is NO universally "correct" merge — only STRATEGIES

Strategy 1: Last-Write-Wins (LWW)

// Simplest strategy: most recent timestamp wins
// Used by: DynamoDB, Cassandra, many mobile apps

function lastWriteWins(localChange, serverChange) {
  // Compare timestamps — later write overwrites earlier
  if (localChange.timestamp > serverChange.timestamp) {
    return localChange.value;  // Local wins
  }
  return serverChange.value;    // Server wins
}

// PROBLEM 1: Clock skew — client clocks are unreliable
// Alice's laptop clock is 5 minutes ahead → she always "wins"
// Solution: Use Hybrid Logical Clocks (HLC) or server-assigned timestamps

// PROBLEM 2: Data loss — the "losing" write is silently discarded
// If Alice writes "Meeting at 3pm" and Bob writes "Meeting at 4pm",
// one of those is LOST without notification

// WHEN TO USE: Low-stakes data; user preferences; non-collaborative;
//              cases where any consistent value is acceptable

class LWWRegister {
  constructor(value, timestamp = 0) {
    this.value = value;
    this.timestamp = timestamp;
  }

  set(newValue) {
    this.value = newValue;
    this.timestamp = Date.now();
  }

  // Merge with a remote version — higher timestamp wins
  merge(remote) {
    if (remote.timestamp > this.timestamp) {
      this.value = remote.value;
      this.timestamp = remote.timestamp;
    }
    // If equal timestamps, use tiebreaker (e.g., client ID comparison)
  }
}

Strategy 2: Three-Way Merge

// Used by: Git, Google Docs (simplified), CouchDB
// Requires: knowing the COMMON ANCESTOR (state before divergence)

function threeWayMerge(base, local, remote) {
  const result = {};

  // For each field, determine who changed what relative to base
  const allKeys = new Set([
    ...Object.keys(base),
    ...Object.keys(local),
    ...Object.keys(remote)
  ]);

  for (const key of allKeys) {
    const baseVal = base[key];
    const localVal = local[key];
    const remoteVal = remote[key];

    const localChanged = !deepEqual(baseVal, localVal);
    const remoteChanged = !deepEqual(baseVal, remoteVal);

    if (!localChanged && !remoteChanged) {
      // Neither changed this field — keep base value
      result[key] = baseVal;
    } else if (localChanged && !remoteChanged) {
      // Only local changed — take local (clean merge)
      result[key] = localVal;
    } else if (!localChanged && remoteChanged) {
      // Only remote changed — take remote (clean merge)
      result[key] = remoteVal;
    } else if (deepEqual(localVal, remoteVal)) {
      // Both changed to SAME value — no conflict
      result[key] = localVal;
    } else {
      // CONFLICT: both changed to DIFFERENT values
      // This is where strategy matters — cannot auto-resolve
      result[key] = { conflict: true, local: localVal, remote: remoteVal, base: baseVal };
    }
  }

  return result;
}

// Usage with conflict UI
const merged = threeWayMerge(baseDoc, localDoc, remoteDoc);
const conflicts = Object.entries(merged).filter(([k, v]) => v?.conflict);

if (conflicts.length > 0) {
  // Show conflict resolution UI to the user
  showConflictDialog(conflicts);
} else {
  // Clean merge — apply automatically
  applyMergedState(merged);
}

Strategy 3: Operational Transform (OT) Queue

// Instead of merging STATE, merge OPERATIONS (actions/events)
// Each offline mutation is stored as an operation
// On reconnect, operations are transformed against concurrent ops

class OfflineQueue {
  constructor() {
    this.pendingOps = [];     // Operations made while offline
    this.baseVersion = 0;     // Server version when we went offline
  }

  // Record an operation while offline
  enqueue(operation) {
    this.pendingOps.push({
      ...operation,
      clientSeq: this.pendingOps.length,
      baseVersion: this.baseVersion
    });
  }

  // On reconnect: sync with server
  async sync(serverOps) {
    // serverOps = operations that happened on server while we were offline

    // Transform our pending ops against server ops
    // This adjusts indices, handles deletions, resolves conflicts
    let transformedOps = this.pendingOps;

    for (const serverOp of serverOps) {
      transformedOps = transformedOps.map(localOp =>
        transform(localOp, serverOp)
      );
    }

    // Send transformed operations to server
    for (const op of transformedOps) {
      await api.submitOperation(op);
    }

    this.pendingOps = [];
  }
}

// Transform function: adjust operation against concurrent operation
function transform(localOp, serverOp) {
  // Example: list insert position adjustment
  if (localOp.type === 'INSERT' && serverOp.type === 'INSERT') {
    // If server inserted before our position, shift our position right
    if (serverOp.index <= localOp.index) {
      return { ...localOp, index: localOp.index + 1 };
    }
  }
  if (localOp.type === 'INSERT' && serverOp.type === 'DELETE') {
    // If server deleted before our insert position, shift left
    if (serverOp.index < localOp.index) {
      return { ...localOp, index: localOp.index - 1 };
    }
  }
  if (localOp.type === 'DELETE' && serverOp.type === 'DELETE') {
    // Both deleted same item — our delete is now a no-op
    if (serverOp.index === localOp.index) {
      return { type: 'NOOP' };
    }
  }
  return localOp;
}

Strategy 4: Version Vectors

// Track causality: which updates has each client "seen"?
// Used by: CouchDB, Riak, Amazon DynamoDB (internally)

class VersionVector {
  constructor() {
    // Map of clientId → sequence number (how many ops this client has done)
    this.clock = {};
  }

  increment(clientId) {
    this.clock[clientId] = (this.clock[clientId] || 0) + 1;
  }

  // Can we determine ordering between two version vectors?
  compare(other) {
    let dominated = false, dominates = false;
    const allClients = new Set([
      ...Object.keys(this.clock),
      ...Object.keys(other.clock)
    ]);

    for (const client of allClients) {
      const mine = this.clock[client] || 0;
      const theirs = other.clock[client] || 0;
      if (mine < theirs) dominated = true;
      if (mine > theirs) dominates = true;
    }

    if (dominates && !dominated) return 'AFTER';   // We happened after them
    if (dominated && !dominates) return 'BEFORE';  // They happened after us
    if (!dominated && !dominates) return 'EQUAL'; // Same version
    return 'CONCURRENT';  // CONFLICT — neither dominates the other
  }

  merge(other) {
    // Take max of each component — the union of all known operations
    const merged = new VersionVector();
    const allClients = new Set([
      ...Object.keys(this.clock),
      ...Object.keys(other.clock)
    ]);
    for (const client of allClients) {
      merged.clock[client] = Math.max(
        this.clock[client] || 0,
        other.clock[client] || 0
      );
    }
    return merged;
  }
}

Real-World Usage

  • CouchDB/PouchDB — Multi-master replication with automatic conflict detection via revision trees. Conflicts are stored as document branches; apps choose resolution strategy.
  • Figma — Uses operational transform with a central server ordering. Offline changes are queued as operations and transformed against server operations on reconnect.
  • Linear — Offline-first architecture where all mutations are queued locally in IndexedDB. On reconnect, a sync engine replays mutations with server-side conflict resolution.
  • Apple Notes / iCloud — Uses three-way merge with Last-Write-Wins at the field level. Each note field has an independent timestamp; conflicts show "this note has conflicting changes."
  • Notion — Block-level operations with OT. Each block is independently versioned, so conflicts are localized to individual blocks rather than entire pages.

Implementation: Complete Offline Sync Engine

// A sync engine that handles: offline queue, reconnection, conflict resolution

class SyncEngine {
  constructor(store, api, conflictStrategy = 'server-wins') {
    this.store = store;            // Local state (IndexedDB)
    this.api = api;                // Server API
    this.strategy = conflictStrategy;
    this.offlineQueue = [];        // Mutations made while offline
    this.isOnline = navigator.onLine;
    this.lastSyncVersion = 0;

    // Listen for connectivity changes
    window.addEventListener('online', () => this.handleReconnect());
    window.addEventListener('offline', () => { this.isOnline = false; });
  }

  // Called for every local mutation (online or offline)
  async mutate(operation) {
    // Always apply locally first (offline-first principle)
    this.store.apply(operation);

    if (this.isOnline) {
      try {
        await this.api.submit(operation);
      } catch (e) {
        // Network failed mid-request — queue for retry
        this.offlineQueue.push(operation);
      }
    } else {
      // Offline — queue for later sync
      this.offlineQueue.push(operation);
      await this.persistQueue(); // Save to IndexedDB (survives page refresh)
    }
  }

  async handleReconnect() {
    this.isOnline = true;

    // Step 1: Fetch all server changes since our last sync
    const serverChanges = await this.api.getChangesSince(this.lastSyncVersion);

    // Step 2: Detect conflicts (our offline ops vs server ops)
    const conflicts = this.detectConflicts(this.offlineQueue, serverChanges);

    // Step 3: Resolve conflicts based on strategy
    const resolved = this.resolveConflicts(conflicts);

    // Step 4: Apply server changes + resolved conflicts locally
    for (const change of serverChanges) {
      if (!resolved.overriddenByLocal.has(change.id)) {
        this.store.apply(change);
      }
    }

    // Step 5: Push our non-conflicting offline ops to server
    for (const op of resolved.toSubmit) {
      await this.api.submit(op);
    }

    this.offlineQueue = [];
    this.lastSyncVersion = serverChanges.at(-1)?.version || this.lastSyncVersion;
  }

  detectConflicts(localOps, serverOps) {
    const conflicts = [];
    for (const localOp of localOps) {
      for (const serverOp of serverOps) {
        // Conflict = same entity modified by both sides
        if (localOp.entityId === serverOp.entityId) {
          conflicts.push({ local: localOp, server: serverOp });
        }
      }
    }
    return conflicts;
  }

  resolveConflicts(conflicts) {
    switch (this.strategy) {
      case 'server-wins':
        // Discard all conflicting local ops
        return { toSubmit: [], overriddenByLocal: new Set() };

      case 'client-wins':
        // Local ops override — submit them to server
        return {
          toSubmit: conflicts.map(c => c.local),
          overriddenByLocal: new Set(conflicts.map(c => c.server.id))
        };

      case 'manual':
        // Show conflict UI — let user choose
        this.showConflictUI(conflicts);
        return { toSubmit: [], overriddenByLocal: new Set() };

      case 'field-level-merge':
        // Merge at field level — non-conflicting fields auto-merge
        return this.fieldLevelMerge(conflicts);
    }
  }
}

Trade-offs & Alternatives

StrategyStrengthsWeaknesses
Last-Write-Wins Simplest; always converges; no user input needed Silent data loss; clock skew issues; no merge semantics
Three-Way Merge Preserves non-conflicting changes; familiar (Git-like) Needs common ancestor; true conflicts need manual resolution
Operational Transform Fine-grained merging; handles concurrent edits well Complex transform functions; server ordering required; hard to debug
CRDTs Conflict-free by design; no coordination needed; works P2P Limited data types; tombstone growth; can't express all operations
Manual Resolution UI User always in control; best for high-stakes data Interrupts workflow; requires UI design; user may not understand

Common Mistakes

  • Assuming "server wins" is always safe — If a user spent 30 minutes editing offline and reconnects to find all their work discarded, they'll never trust your app again. At minimum, preserve discarded changes somewhere recoverable.
  • Not persisting the offline queue — If the user closes the tab while offline, their pending mutations must survive in IndexedDB. In-memory queues lose data on page refresh.
  • Ignoring the base version — Without knowing what version both sides diverged from, you can't distinguish "Alice changed X" from "Alice left X unchanged." The base/ancestor is essential for three-way merge.
  • Merging at document level instead of field level — If Alice edits the title and Bob edits the body, a document-level merge sees a conflict. A field-level merge resolves cleanly: take Alice's title + Bob's body.
  • Not testing the offline→online transition — Most sync bugs appear in the reconnection flow. Test with: close WiFi → make changes → make changes on another device → restore WiFi. Automate this in CI with network throttling.

✅ You Truly Understand Offline Conflict Resolution When...

You can identify WHICH conflict strategy is appropriate for each field in your data model (LWW for user preferences, OT for text editing, CRDTs for counters, manual resolution for financial data) and implement a sync engine that handles all of these within a single application.
