CRDT Basics for Collaboration

Conflict-free Replicated Data Types — data structures mathematically guaranteed to merge without conflicts, enabling real-time collaboration without a central server, coordination, or consensus protocol.

Advanced Distributed Systems Collaboration
📚 Analogy: Tally Marks on a Scoreboard

Imagine 5 referees each keeping independent tally marks for fouls during a basketball game. At halftime, they compare boards. It doesn't matter what ORDER they made their marks or WHEN they compare — you just add all marks together and get the correct total. No conflicts, no coordination needed. This is what a G-Counter CRDT does: each node counts independently, and merging is just taking the max of each node's count.

The Problem: Coordination is Expensive

// Traditional distributed consistency requires COORDINATION:
//
// Client A: "I want to increment counter"
//   → Send to server
//   → Server locks the value
//   → Server increments
//   → Server unlocks
//   → Server broadcasts to all clients
//
// Problems:
// 1. Latency: every operation requires round-trip to server
// 2. Single point of failure: server down = app down
// 3. Offline: can't modify data without server connection
// 4. Scalability: lock contention under high concurrency
//
// CRDTs eliminate ALL of these by making the data structure itself
// conflict-free. Any two replicas can merge without coordination.
//
// The mathematical guarantee:
// merge(A, B) = merge(B, A)           — Commutative
// merge(A, merge(B, C)) = merge(merge(A, B), C)  — Associative
// merge(A, A) = A                     — Idempotent
//
// These three properties guarantee EVENTUAL CONSISTENCY
// regardless of message ordering, duplication, or timing.

CRDT Type 1: G-Counter (Grow-only Counter)

// The simplest CRDT: a counter that can only increment
// Each node maintains its own count; total = sum of all nodes

class GCounter {
  constructor(nodeId) {
    this.nodeId = nodeId;
    // Map: nodeId → that node's count
    // Each node only increments ITS OWN entry
    this.counts = {};
  }

  increment() {
    // Only modify our own node's entry — safe without coordination
    this.counts[this.nodeId] = (this.counts[this.nodeId] || 0) + 1;
  }

  value() {
    // Total = sum of all nodes' individual counts
    return Object.values(this.counts).reduce((sum, n) => sum + n, 0);
  }

  // MERGE: take the MAX of each node's count
  // This is where the magic happens — merge is conflict-free
  merge(remote) {
    const allNodes = new Set([
      ...Object.keys(this.counts),
      ...Object.keys(remote.counts)
    ]);
    for (const node of allNodes) {
      // MAX ensures we never "un-count" an increment
      // Even if messages arrive out of order or duplicated
      this.counts[node] = Math.max(
        this.counts[node] || 0,
        remote.counts[node] || 0
      );
    }
  }
}

// Example: Three users independently increment
const alice = new GCounter('alice');
const bob = new GCounter('bob');

alice.increment(); alice.increment();  // alice: {alice: 2}
bob.increment();                       // bob: {bob: 1}

// Merge in ANY order — result is always the same
alice.merge(bob);  // alice: {alice: 2, bob: 1}, value() = 3
bob.merge(alice);  // bob: {alice: 2, bob: 1}, value() = 3  ✓ Converged!

CRDT Type 2: PN-Counter (Positive-Negative Counter)

// G-Counter only grows. For increment AND decrement, use two G-Counters

class PNCounter {
  constructor(nodeId) {
    this.positive = new GCounter(nodeId);  // Tracks increments
    this.negative = new GCounter(nodeId);  // Tracks decrements
  }

  increment() { this.positive.increment(); }
  decrement() { this.negative.increment(); }

  value() {
    // Net value = total increments - total decrements
    return this.positive.value() - this.negative.value();
  }

  merge(remote) {
    this.positive.merge(remote.positive);
    this.negative.merge(remote.negative);
  }
}

CRDT Type 3: LWW-Register (Last-Writer-Wins Register)

// For single values (not collections) — whoever wrote last wins
// Used for: user preferences, single-field updates, cursor positions

class LWWRegister {
  constructor(value = null) {
    this.value = value;
    this.timestamp = 0;
    this.nodeId = ''; // Tiebreaker for equal timestamps
  }

  set(value, nodeId) {
    this.value = value;
    this.timestamp = Date.now();
    this.nodeId = nodeId;
  }

  merge(remote) {
    if (remote.timestamp > this.timestamp) {
      this.value = remote.value;
      this.timestamp = remote.timestamp;
      this.nodeId = remote.nodeId;
    } else if (remote.timestamp === this.timestamp) {
      // Tiebreaker: higher nodeId wins (deterministic)
      if (remote.nodeId > this.nodeId) {
        this.value = remote.value;
        this.nodeId = remote.nodeId;
      }
    }
    // If our timestamp is higher, we keep our value (no change)
  }
}

CRDT Type 4: OR-Set (Observed-Remove Set)

// The most practical CRDT for frontend: a set with add AND remove
// Solves the "add-remove" conflict: if Alice adds X and Bob removes X
// concurrently, what happens? OR-Set: add wins (observed-remove semantics)

class ORSet {
  constructor(nodeId) {
    this.nodeId = nodeId;
    // Each element has a UNIQUE TAG (not just the value)
    // This allows "remove" to target specific ADD operations
    this.elements = new Map(); // value → Set of {tag, nodeId}
    this.tombstones = new Set(); // Tags that have been removed
  }

  add(value) {
    // Generate unique tag for this specific ADD operation
    const tag = `${this.nodeId}-${Date.now()}-${Math.random().toString(36).slice(2)}`;
    if (!this.elements.has(value)) {
      this.elements.set(value, new Set());
    }
    this.elements.get(value).add(tag);
  }

  remove(value) {
    // Remove ALL tags currently associated with this value
    // Key insight: we only remove tags we've OBSERVED (seen)
    const tags = this.elements.get(value);
    if (tags) {
      for (const tag of tags) {
        this.tombstones.add(tag);
      }
      this.elements.delete(value);
    }
  }

  has(value) {
    const tags = this.elements.get(value);
    return tags && tags.size > 0;
  }

  values() {
    return [...this.elements.keys()].filter(v => this.has(v));
  }

  merge(remote) {
    // Merge tombstones (union)
    for (const tag of remote.tombstones) {
      this.tombstones.add(tag);
    }

    // Merge elements: add remote's tags, remove tombstoned ones
    for (const [value, remoteTags] of remote.elements) {
      if (!this.elements.has(value)) {
        this.elements.set(value, new Set());
      }
      const localTags = this.elements.get(value);
      for (const tag of remoteTags) {
        if (!this.tombstones.has(tag)) {
          localTags.add(tag);
        }
      }
    }

    // Clean up: remove locally tombstoned tags
    for (const [value, tags] of this.elements) {
      for (const tag of tags) {
        if (this.tombstones.has(tag)) tags.delete(tag);
      }
      if (tags.size === 0) this.elements.delete(value);
    }
  }
}

// Example: concurrent add and remove
const alice = new ORSet('alice');
const bob = new ORSet('bob');

alice.add('task-1'); // Alice adds task-1
// Sync to Bob...
bob.merge(alice);     // Bob now sees task-1

// CONCURRENT operations (no communication between them):
alice.add('task-1');    // Alice re-adds task-1 (new tag!)
bob.remove('task-1');   // Bob removes task-1 (only removes tags he's seen)

// After merge: task-1 EXISTS (Alice's new add wins over Bob's remove
// because Bob only removed the OLD tag, not Alice's new tag)
alice.merge(bob);  // alice.has('task-1') === true
bob.merge(alice);  // bob.has('task-1') === true — converged!

Real-World Usage

  • Yjs — The most popular CRDT library for JavaScript. Powers collaborative editing in Notion (internal), VS Code Live Share, and many collaborative apps. Implements a document CRDT with text, arrays, maps, and XML types.
  • Automerge — A JSON-like CRDT library by Martin Kleppmann (the "Designing Data-Intensive Applications" author). Used for local-first applications. Stores full change history for time-travel.
  • Redis CRDTs — Redis Enterprise uses CRDTs (counters, sets, registers) for active-active geo-replication. Two Redis clusters in different continents merge conflict-free.
  • Figma — Uses a custom CRDT-like data structure for their canvas. Each design object is a CRDT register; the tree structure uses a CRDT-aware ordering.
  • Riak (database) — A distributed key-value store that offers CRDT data types (counters, sets, maps, flags) as native storage primitives with automatic conflict resolution.

Trade-offs & Alternatives

ApproachStrengthsWeaknesses
CRDTs Conflict-free by math; works P2P; no server needed; offline-capable Metadata overhead (tombstones, tags); limited expressiveness; memory growth
Operational Transform More expressive operations; less metadata; established in Google Docs Requires central server for ordering; complex transform functions; hard to verify
Server authority (lock-based) Simple; always consistent; deterministic Single point of failure; can't work offline; high latency
Last-Write-Wins (simple) Trivial to implement; low overhead; always converges Loses concurrent writes silently; no merge semantics

Common Mistakes

  • Tombstone accumulation — OR-Sets store tombstones forever (to prevent re-adding removed items). Without garbage collection, metadata grows unboundedly. Implement periodic tombstone pruning when all nodes have observed the removal.
  • Using CRDTs for everything — Not all data fits CRDT semantics. "Set the due date to March 5" doesn't compose well — two concurrent date changes must pick one (LWW), which isn't truly conflict-free in user intent.
  • Ignoring intent vs. mechanism — CRDTs resolve mechanical conflicts but not semantic ones. Two users concurrently editing a budget to add $100 and $200 — the CRDT counter gives $300, but maybe the intent was "set budget to $200." Design your CRDT types around user intent.
  • Confusing state-based and operation-based CRDTs — State-based (CvRDT) sends full state on sync. Operation-based (CmRDT) sends only operations. Op-based needs exactly-once delivery; state-based is idempotent. Choose based on your network guarantees.
  • Not testing with network partitions — CRDTs shine during partitions. Test with: diverge two clients for many operations, then merge. Verify convergence. The merge function must be tested with arbitrary operation orders.

✅ You Truly Understand CRDTs When...

You can explain why merge must be commutative, associative, and idempotent — and why those three properties together guarantee eventual consistency. You can choose the right CRDT type for a given data structure (counter for likes, OR-Set for todo lists, LWW-Register for user profiles, sequence CRDT for text) and explain the tombstone garbage collection problem.
