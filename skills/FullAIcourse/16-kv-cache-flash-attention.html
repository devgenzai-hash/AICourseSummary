KV Cache & Flash Attention

Why does the model seem slow on the first token but fast after that? How does vLLM serve thousands of requests? The answer: clever memory tricks that changed how we run AI models.

🏠 Daily Life Analogy

KV Cache = taking notes during a meeting. Instead of re-reading all previous meeting minutes every time someone asks a question, you keep running notes (Key-Value cache). For each new question, you just consult your notes + add the new info.

Flash Attention = speed-reading a book in chunks. Instead of loading the entire book into your tiny desk (GPU memory), you read one chapter at a time, take notes, then move to the next chapter. Same result, way less desk space needed.

Understanding KV Cache

The Problem Without KV Cache:

When generating text token-by-token, the model needs to look at ALL previous tokens. Without caching:

  • Token 1: Process 1 token
  • Token 2: Process tokens 1-2 (re-process token 1!)
  • Token 3: Process tokens 1-3 (re-process tokens 1-2!)
  • Token 100: Process all 100 tokens (re-process 99 tokens!)

This is O(n²) — wastefully recomputing everything!

With KV Cache:

  • Token 1: Compute attention → save K₁, V₁ to cache
  • Token 2: Use cached K₁,V₁ + compute new K₂,V₂ → save to cache
  • Token 100: Use cached K₁..K₉₉, V₁..V₉₉ + compute K₁₀₀,V₁₀₀

Now each new token only does O(1) new computation (plus looking up the cache)!

# How KV cache works conceptually
import torch

class SimpleKVCache:
    """Simplified KV Cache for understanding."""
    
    def __init__(self, num_layers, num_heads, head_dim, max_seq_len):
        self.num_layers = num_layers
        # Pre-allocate memory for K and V for each layer
        self.key_cache = torch.zeros(num_layers, max_seq_len, num_heads, head_dim)
        self.value_cache = torch.zeros(num_layers, max_seq_len, num_heads, head_dim)
        self.seq_len = 0
    
    def update(self, layer_idx, new_keys, new_values):
        """Add new K,V to cache (called for each new token)."""
        self.key_cache[layer_idx, self.seq_len] = new_keys
        self.value_cache[layer_idx, self.seq_len] = new_values
        self.seq_len += 1
    
    def get(self, layer_idx):
        """Get all cached K,V up to current position."""
        return (
            self.key_cache[layer_idx, :self.seq_len],
            self.value_cache[layer_idx, :self.seq_len]
        )

# KV cache size calculation:
# Size = 2 × num_layers × seq_len × num_heads × head_dim × bytes_per_param
# For Llama-3.1-8B with 4096 context:
# = 2 × 32 × 4096 × 32 × 128 × 2 bytes = ~2 GB per request!
print("KV cache for 8B model, 4K context ≈ 2 GB per request")
print("That's why long contexts are expensive!")

Flash Attention

Flash Attention is a revolutionary algorithm that makes attention computation 2-4x faster and uses much less GPU memory. It's now used by default in all modern inference engines.

The Key Insight:

Standard attention loads the entire attention matrix into GPU HBM (High Bandwidth Memory). Flash Attention instead:

  1. Computes attention in small tiles/blocks
  2. Keeps intermediate results in fast SRAM (like L1 cache)
  3. Never materializes the full N×N attention matrix in memory
# Using Flash Attention in practice
from transformers import AutoModelForCausalLM

# Method 1: Enable Flash Attention 2 in transformers
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B-Instruct",
    torch_dtype="auto",
    attn_implementation="flash_attention_2",  # ← This!
    device_map="auto",
)
# Requires: pip install flash-attn --no-build-isolation
# Only works on NVIDIA GPUs (Ampere or newer: A100, 4090, etc.)

# Method 2: SDPA (Scaled Dot-Product Attention) - works everywhere
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B-Instruct",
    torch_dtype="auto",
    attn_implementation="sdpa",  # PyTorch native, auto-selects best
    device_map="auto",
)
# SDPA automatically uses Flash Attention if available,
# falls back to efficient alternatives if not

PagedAttention (vLLM)

PagedAttention is what makes vLLM so fast for serving many users. It treats KV cache like virtual memory pages in an operating system.

The Problem:

Without PagedAttention, each request pre-allocates a full KV cache for the maximum sequence length, even if the response is short. This wastes 60-80% of GPU memory!

The Solution:

# PagedAttention concept (how vLLM works internally)
# Instead of: allocate 128K tokens of KV cache per request
# PagedAttention: allocate in small "pages" (blocks of 16 tokens)

class PagedKVCache:
    """Simplified PagedAttention concept."""
    
    def __init__(self, block_size=16, num_blocks=1000):
        self.block_size = block_size
        # Pool of memory blocks (like OS memory pages)
        self.block_pool = [torch.zeros(block_size, head_dim) for _ in range(num_blocks)]
        self.free_blocks = list(range(num_blocks))
        self.request_blocks = {}  # request_id -> list of block indices
    
    def allocate(self, request_id):
        """Allocate one new block for a request."""
        block_idx = self.free_blocks.pop()
        if request_id not in self.request_blocks:
            self.request_blocks[request_id] = []
        self.request_blocks[request_id].append(block_idx)
        return block_idx
    
    def free(self, request_id):
        """Free all blocks when request completes."""
        blocks = self.request_blocks.pop(request_id)
        self.free_blocks.extend(blocks)

# Benefits:
# 1. No wasted memory (allocate only what's needed)
# 2. Requests can share blocks (e.g., same system prompt)
# 3. Can serve 2-4x more concurrent requests!

Grouped-Query Attention (GQA)

Another optimization used in modern models (Llama 3, Mistral) to reduce KV cache size:

# Multi-Head Attention (MHA) vs Grouped-Query Attention (GQA)

# MHA: Each attention head has its own K and V
# 32 heads → 32 K matrices + 32 V matrices in cache

# GQA: Multiple heads SHARE K and V
# 32 query heads, but only 8 KV heads (groups of 4 share KV)
# Cache size: reduced by 4x!

# Multi-Query Attention (MQA): Extreme version
# 32 query heads, only 1 KV head (all share the same KV)
# Cache size: reduced by 32x! (but slight quality loss)

# Llama 3.1 uses GQA with 8 KV heads (32 query / 8 KV = 4:1 ratio)
print("GQA reduces KV cache by 4x in Llama 3.1")
print("This is why Llama 3 can handle 128K context!")

🏭 Industry Standards

  • Flash Attention 2 is mandatory — Every production system uses it. Without it, long contexts are impossible.
  • vLLM uses PagedAttention — Industry standard for serving. 2-4x more throughput than naive serving.
  • GQA is the standard architecture — All modern models (Llama 3, Mistral, Gemma 2) use GQA for efficient caching.
  • KV cache is THE bottleneck — For serving, memory is usually limited by KV cache, not model weights.
  • Prefix caching — vLLM and TGI cache common prefixes (system prompts) across requests to save memory.
  • Flash Attention 3 — Coming for Hopper GPUs (H100). Even faster with FP8 support.

📝 Summary

  • KV Cache = stores computed Keys/Values so you don't recompute for every new token
  • Flash Attention = computes attention in tiles, 2-4x faster, enables long contexts
  • PagedAttention = allocates KV cache in pages (like OS memory), 2-4x more concurrent users
  • GQA = share KV heads across query heads, 4-8x smaller cache
  • KV cache is the main memory bottleneck for serving at scale

🧠 Mental Model

Without KV Cache: "Read entire book for each new sentence" → Slow!
With KV Cache: "Keep running notes, add one line per token" → Fast!

Standard Attention: Load N×N matrix into slow memory → Memory hog
Flash Attention: Process in tiles, keep in fast SRAM → Memory efficient

Regular allocation: Reserve hotel room for a year, even if staying 1 night
PagedAttention: Book night-by-night, share rooms when empty

❌ Beginner Mistakes to Avoid

  • Ignoring KV cache in VRAM calculations — Model weights are only part of the memory. KV cache can be 2x the model size at long contexts!
  • Not enabling Flash Attention — If you're on an Ampere+ GPU and not using FA2, you're leaving free performance on the table.
  • Setting max_seq_len too high — Higher context = more KV cache memory. Set it to what you actually need.
  • Forgetting about concurrent users — Each user needs their own KV cache. 10 users = 10x the cache memory.
