Stage 7: Hallucination Fallback Layer

If retrieval confidence drops below a threshold: "Insufficient evidence found." It's better to say nothing than to say something wrong.

Intermediate Concept Production
🏠 Daily-Life Analogy: A Doctor Saying "I Need More Tests"

Imagine you go to a doctor with a strange symptom. A bad doctor might guess: "It's probably just stress, take some vitamins." A good doctor says: "I'm not sure what's causing this. I need to run more tests before I can give you a diagnosis."

The good doctor would rather say "I don't know yet" than risk giving you wrong medical advice.

The hallucination fallback layer is your system's "good doctor." When the evidence isn't strong enough to give a confident answer, it says so — instead of making something up.

What Is the Hallucination Fallback?

The hallucination fallback is a safety net that activates when your system detects it cannot produce a reliable answer. It checks multiple signals and decides: "Should I answer, or should I refuse?"

When it triggers:

  • Retrieval confidence is too low (no good sources found)
  • Source chunks contradict each other with no clear winner
  • The generated answer failed grounding verification (Stage 5)
  • Citation coverage is too low (claims without sources)
  • The query is outside the scope of available documents
✅ The Core Philosophy

"I don't have sufficient information" is ALWAYS better than a confidently wrong answer. In enterprise, medical, legal, and financial contexts, a hallucination can be catastrophic. Saying "I don't know" is safe. Making stuff up is dangerous.

The Threshold System

Multiple Checkpoints

The fallback isn't a single check — it's multiple checkpoints throughout the pipeline:

Checkpoint What It Checks Threshold Action If Failed
Retrieval confidence Avg confidence of top-k chunks < 0.4 Refuse to answer
Rerank score Best reranker score for any chunk < 0.3 Refuse to answer
Source agreement Do sources agree or contradict? Contradiction detected Present both views with caveat
Grounding score % of answer supported by context < 0.8 Regenerate or refuse
Citation coverage % of claims with valid citations < 0.85 Remove uncited claims or refuse

Implementation

from enum import Enum
from dataclasses import dataclass

class FallbackDecision(Enum):
    ANSWER = "answer"              # Confident, proceed normally
    ANSWER_WITH_CAVEAT = "caveat"  # Answer but warn about uncertainty
    PARTIAL_ANSWER = "partial"     # Provide what we can, flag gaps
    REFUSE = "refuse"              # Don't answer, explain why
    ESCALATE = "escalate"          # Route to human expert

@dataclass
class ConfidenceSignals:
    retrieval_confidence: float    # 0-1: avg confidence of retrieved chunks
    best_rerank_score: float      # 0-1: top reranker score
    grounding_score: float        # 0-1: % answer supported by context
    citation_coverage: float      # 0-1: % claims with citations
    source_agreement: float       # 0-1: do sources agree?
    num_relevant_chunks: int      # How many chunks passed confidence threshold

class HallucinationFallback:
    """
    Decision engine that determines whether to answer,
    caveat, partially answer, or refuse.
    """
    
    def __init__(self, config: Dict = None):
        self.config = config or {
            "min_retrieval_confidence": 0.4,
            "min_rerank_score": 0.3,
            "min_grounding_score": 0.8,
            "min_citation_coverage": 0.85,
            "min_source_agreement": 0.6,
            "min_relevant_chunks": 2,
            "caveat_threshold": 0.6,  # Below this: caveat warning
        }
    
    def decide(self, signals: ConfidenceSignals) -> FallbackDecision:
        """
        Determine what action to take based on confidence signals.
        
        Decision tree:
        1. If any CRITICAL signal is below threshold → REFUSE
        2. If multiple signals are borderline → CAVEAT
        3. If only partial info available → PARTIAL
        4. Otherwise → ANSWER
        """
        
        # CRITICAL FAILURES: Immediate refusal
        if signals.num_relevant_chunks == 0:
            return FallbackDecision.REFUSE
        
        if signals.retrieval_confidence < self.config["min_retrieval_confidence"]:
            return FallbackDecision.REFUSE
        
        if signals.best_rerank_score < self.config["min_rerank_score"]:
            return FallbackDecision.REFUSE
        
        # POST-GENERATION CHECKS
        if signals.grounding_score < self.config["min_grounding_score"]:
            if signals.grounding_score > 0.5:
                return FallbackDecision.PARTIAL_ANSWER
            return FallbackDecision.REFUSE
        
        # BORDERLINE: Answer with warning
        borderline_count = 0
        if signals.retrieval_confidence < self.config["caveat_threshold"]:
            borderline_count += 1
        if signals.source_agreement < self.config["min_source_agreement"]:
            borderline_count += 1
        if signals.citation_coverage < self.config["min_citation_coverage"]:
            borderline_count += 1
        
        if borderline_count >= 2:
            return FallbackDecision.ANSWER_WITH_CAVEAT
        
        # ALL GOOD: Confident answer
        return FallbackDecision.ANSWER

Full Pipeline Integration

class RAGPipelineWithFallback:
    """Complete RAG pipeline with hallucination safety net."""
    
    def __init__(self, retriever, generator, fallback):
        self.retriever = retriever
        self.generator = generator
        self.fallback = fallback
    
    def answer_query(self, query: str) -> Dict:
        """End-to-end query answering with fallback safety."""
        
        # Step 1: Retrieve and score
        chunks = self.retriever.retrieve(query, top_k=10)
        
        # Step 2: Pre-generation confidence check
        pre_signals = ConfidenceSignals(
            retrieval_confidence=avg_confidence(chunks),
            best_rerank_score=chunks[0]["rerank_score"] if chunks else 0,
            grounding_score=1.0,  # Unknown yet
            citation_coverage=1.0,  # Unknown yet
            source_agreement=compute_agreement(chunks),
            num_relevant_chunks=len(chunks)
        )
        
        pre_decision = self.fallback.decide(pre_signals)
        
        if pre_decision == FallbackDecision.REFUSE:
            return self._format_refusal(query, pre_signals)
        
        # Step 3: Generate answer
        result = self.generator.generate(query, chunks)
        
        # Step 4: Post-generation confidence check
        post_signals = ConfidenceSignals(
            retrieval_confidence=pre_signals.retrieval_confidence,
            best_rerank_score=pre_signals.best_rerank_score,
            grounding_score=result["grounding_score"],
            citation_coverage=result["citation_coverage"],
            source_agreement=pre_signals.source_agreement,
            num_relevant_chunks=pre_signals.num_relevant_chunks
        )
        
        final_decision = self.fallback.decide(post_signals)
        
        # Step 5: Apply decision
        if final_decision == FallbackDecision.ANSWER:
            return {"answer": result["answer"], "confidence": "high"}
        elif final_decision == FallbackDecision.ANSWER_WITH_CAVEAT:
            return self._format_caveat(result, post_signals)
        elif final_decision == FallbackDecision.PARTIAL_ANSWER:
            return self._format_partial(result, post_signals)
        else:
            return self._format_refusal(query, post_signals)
📊 At 10M Documents Scale
  • Fallback rate matters: If your system refuses too often (>20% of queries), your retrieval is probably broken. If it never refuses (<1%), your thresholds are too lenient.
  • Target fallback rate: 5-15% depending on domain. Legal/medical: higher refusal is acceptable. Customer support: lower refusal needed.
  • Monitor and tune: Track refusal reasons over time. If most refusals are "no relevant documents found," you may have a coverage gap in your index.
  • User feedback loop: When users disagree with a refusal ("but the info IS in the system!"), log it as a retrieval failure for investigation.

🏢 What Production Systems Actually Do

  • ChatGPT Enterprise — Trained to say "I'm not sure about that based on your documents" rather than guessing
  • Legal AI tools — Strict refusal with "No relevant precedent found" messages + human escalation
  • Financial RAG systems — Dual-threshold: soft (warning) and hard (refusal) with automatic audit log
  • Best practice: Every refusal is logged with full context for weekly review meetings
  • Smart routing: Refused queries automatically routed to specialized retrieval or human experts

📋 Summary

  • The fallback layer is your last line of defense against hallucination
  • Multiple checkpoints: retrieval confidence, rerank scores, grounding verification, citation coverage
  • Four response levels: confident answer → caveat → partial answer → refuse
  • "I don't know" is ALWAYS better than a wrong answer in production
  • Monitor fallback rates — too high means bad retrieval, too low means bad thresholds
  • Every refusal should suggest next steps (search differently, ask human, etc.)

🧠 Mental Model

Query enters pipeline: ↓ [Retrieve] → Got good chunks? │ NO → ❌ REFUSE: "No relevant documents found" │ YES ↓ [Score confidence] → Confidence above threshold? │ NO → ❌ REFUSE: "Sources too unreliable" │ YES ↓ [Generate answer] → Answer grounded in context? │ NO → 🔄 Retry once, then ❌ REFUSE │ PARTIAL → ⚠️ PARTIAL ANSWER + gaps listed │ YES ↓ [Verify citations] → Claims properly cited? │ SOME ISSUES → ⚠️ CAVEAT warning │ ALL GOOD ↓ ✅ SERVE CONFIDENT ANSWER

Think of it as: A security checkpoint with multiple guards. Each guard checks a different thing. You only pass if ALL guards approve.

❌ Beginner Mistakes to Avoid

  • No fallback at all: "The model is good enough" — it's NOT. Even GPT-4 hallucinates. Always have a safety net.
  • Binary threshold: Don't just have answer/refuse. Gradual degradation (caveat → partial → refuse) gives users more value.
  • Unhelpful refusals: "I can't answer that" is bad UX. Always explain WHY and suggest WHAT the user can do next.
  • Not tuning thresholds: Default thresholds won't work for every domain. A/B test and adjust based on actual refusal quality.
  • Ignoring refusal analytics: Refusals are a gold mine of insight. Every refusal tells you where your system has gaps.
