System Design/ Failure Detection

Failure Detection

Helping nodes decide who is alive, who is dead, and who is just slow. The foundation of fault-tolerant distributed systems.

Intermediate Distributed Concept
🏠 Daily-Life Analogy: Is Your Friend Ignoring You?

You text your friend. No reply for 5 minutes. Are they:

  • Dead (crashed)? Phone is off
  • Slow (overloaded)? In a meeting, will reply later
  • Partitioned? In a subway tunnel with no signal

You can't tell! All you know is "I haven't heard back." This is the fundamental challenge — you cannot distinguish between crashed, slow, and partitioned.

Why Is Failure Detection Hard?

The Core Problem: In an asynchronous network, there is NO way to reliably distinguish between a crashed node and a very slow one. Any timeout will either be too aggressive (false positives) or too lenient (slow detection).

Heartbeat-Based Detection

import time

class HeartbeatDetector:
    """Simple heartbeat-based failure detection"""

    def __init__(self, timeout=5.0):
        self.timeout = timeout
        self.last_heartbeat = {}
        self.node_status = {}

    def receive_heartbeat(self, node_id):
        self.last_heartbeat[node_id] = time.time()
        self.node_status[node_id] = "alive"

    def check_nodes(self):
        """Periodically check for timeouts"""
        now = time.time()
        for node_id, last_seen in self.last_heartbeat.items():
            if now - last_seen > self.timeout:
                if self.node_status.get(node_id) != "dead":
                    self.node_status[node_id] = "dead"
                    print(f"Node {node_id} DEAD (no heartbeat for {self.timeout}s)")

    def is_alive(self, node_id):
        return self.node_status.get(node_id) == "alive"

Phi Accrual Failure Detector

Instead of binary alive/dead, the Phi detector outputs a suspicion level (0 to infinity). The application chooses what threshold means "dead."

import math
import statistics

class PhiAccrualDetector:
    """Adaptive failure detection that learns network conditions"""

    def __init__(self, threshold=8.0, window_size=100):
        self.threshold = threshold  # phi > threshold = dead
        self.intervals = []
        self.window_size = window_size
        self.last_heartbeat = None

    def heartbeat(self):
        """Record heartbeat arrival"""
        now = time.time()
        if self.last_heartbeat is not None:
            interval = now - self.last_heartbeat
            self.intervals.append(interval)
            if len(self.intervals) > self.window_size:
                self.intervals.pop(0)
        self.last_heartbeat = now

    def phi(self):
        """Calculate suspicion level"""
        if len(self.intervals) < 2 or self.last_heartbeat is None:
            return 0.0

        time_since = time.time() - self.last_heartbeat
        mean = statistics.mean(self.intervals)
        std = statistics.stdev(self.intervals)
        if std == 0:
            std = 0.001

        # Higher phi = more suspicious (longer gap)
        y = (time_since - mean) / std
        prob = 1.0 - 0.5 * (1 + math.erf(y / math.sqrt(2)))
        if prob <= 0:
            return 16.0
        return -math.log10(prob)

    def is_available(self):
        return self.phi() < self.threshold

# Cassandra uses phi=8 as default threshold
# phi=1: 10% false positive chance
# phi=8: 0.000001% false positive chance

Real-World Failure Detection

  • Cassandra — Phi accrual with configurable threshold, adapts to datacenter latency
  • Kubernetes — kubelet heartbeats to control plane, "NotReady" after 40s
  • Consul — SWIM protocol with gossip-based propagation
  • AWS ELB — HTTP health checks every 30s, 3 failures = removed
  • ZooKeeper — Session heartbeats with configurable timeout

📝 Summary

  • Cannot distinguish between crashed, slow, and partitioned — only "no response"
  • Heartbeat + timeout is simplest but has a fixed accuracy trade-off
  • Phi accrual adapts to actual network conditions — fewer false positives
  • SWIM uses indirect probes to confirm suspicion before declaring death
  • Every system must decide: how long to wait before declaring failure?

🧠 Mental Model

The Timeout Dilemma: Short timeout (1s): + Fast detection of real failures - False positives (GC pause = declared dead) - Unnecessary failovers Long timeout (30s): + Fewer false positives - Slow detection (30s downtime before reaction) - Stale connections pile up Phi Accrual (adaptive): + Learns what "normal" looks like for THIS network + Adjusts automatically (LAN vs WAN) + Suspicion LEVEL, not binary

❌ Common Beginner Mistakes

  • Too aggressive timeout — GC pauses can freeze a JVM for 2-5s. 1s timeout = false deaths.
  • Not distinguishing crash from partition — A partitioned node still serves OTHER clients.
  • Single health check path — Health endpoint works but main service doesn't = false alive.
  • No backoff on reconnection — Don't hammer a "dead" node with reconnect attempts.

🏋 Hands-On Exercise

  1. Implement HeartbeatDetector. Simulate nodes sending heartbeats at varied intervals. Add a node that "dies."
  2. Implement PhiAccrualDetector. Feed realistic intervals, then add a long gap and watch phi spike.
  3. Reduce timeout to 0.5s, make one node occasionally slow (1s pause). Count false death declarations.
  4. Research: What is Kubernetes' default node timeout? What happens when a node is "NotReady"?
