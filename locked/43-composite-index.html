Database Engineering → Composite Index
Intermediate Database Concept

Composite Index

Multi-column indexes that accelerate queries filtering on multiple columns — but only when you understand the leftmost prefix rule and column ordering strategy that determines whether the index is used or ignored entirely.

💡 Real-World Analogy

Think of a phone book sorted by last name, then first name. You can quickly find all “Smith” entries (using the first column). You can find “Smith, John” even faster (using both columns). But if you only know the first name “John” — the phone book is useless because it’s not sorted by first name alone. That’s the leftmost prefix rule: a composite index on (last_name, first_name) helps queries on last_name or (last_name + first_name), but NOT first_name alone. Order matters!

What is a Composite Index?

A composite (multi-column) index is a single B-Tree index built on the concatenation of multiple columns. The tree is sorted by column 1, then within equal values of column 1, sorted by column 2, and so on:

  • Also called: multi-column index, compound index, concatenated index
  • Stored as a single B-Tree with composite sort keys
  • Maximum columns: 16 (PostgreSQL), 16 (MySQL), 32 (SQL Server)
  • Key insight: the index is a sorted structure on the combined key

The Leftmost Prefix Rule

For an index on (a, b, c), the database can use the index for queries that filter on:

Query Filter Uses Index? Why
WHERE a = ? ✅ Yes Matches leftmost prefix (a)
WHERE a = ? AND b = ? ✅ Yes Matches prefix (a, b)
WHERE a = ? AND b = ? AND c = ? ✅ Yes (full) Matches full index
WHERE a = ? AND c = ? ⚠️ Partial Uses (a) only, c filtered after
WHERE b = ? ❌ No Skips leftmost column — cannot use index
WHERE b = ? AND c = ? ❌ No Skips leftmost column
WHERE c = ? ❌ No Skips leftmost columns
WHERE a = ? ORDER BY b ✅ Yes Prefix (a) + sort on next column (b)

Column Ordering Strategy

The order of columns in a composite index dramatically affects performance. General rules:

  • Equality columns first: Columns used with = should come before range columns
  • Range column last: Only one column can use a range scan per index lookup
  • High selectivity first: Among equality columns, put the most selective (most unique values) first to narrow results fastest
  • ORDER BY alignment: If the query sorts, align the index tail with the sort order

Example: Optimizing Column Order

-- Query: Find active users in a city, ordered by signup date
SELECT * FROM users
WHERE status = 'active'       -- equality (low selectivity: 2 values)
  AND city = 'New York'       -- equality (medium selectivity: ~1000 cities)
  AND age BETWEEN 25 AND 35  -- range
ORDER BY created_at DESC;

-- BAD index: (status, age, city) -- range on age stops prefix matching
-- GOOD index: (city, status, age) -- equalities first, range last
-- BEST index: (city, status, age, created_at) -- covers ORDER BY too

CREATE INDEX idx_users_composite
  ON users(city, status, age, created_at);

Covering Indexes & Index-Only Scans

A covering index contains all columns needed by a query, eliminating the need to fetch the actual table row. PostgreSQL calls this an “Index Only Scan”:

-- Query only needs columns in the index itself
SELECT city, status, count(*)
FROM users
WHERE city = 'London' AND status = 'active'
GROUP BY city, status;

-- Index (city, status) covers this query completely
-- No heap/table access needed → Index Only Scan

-- PostgreSQL INCLUDE: add columns without affecting sort order
CREATE INDEX idx_covering ON users(city, status)
  INCLUDE (email, name);

-- Now this query is also covered (no heap fetch):
SELECT email, name FROM users
WHERE city = 'London' AND status = 'active';

Selectivity & Column Order

Selectivity measures how well a column narrows results. Higher selectivity (more unique values) means the index eliminates more rows per level:

Column Cardinality Selectivity Position in Index
user_id 1,000,000 (unique) 1 / 1,000,000 First (most selective)
email 999,500 (near-unique) ~1 / 999,500 First or second
city 1,000 1 / 1,000 Middle
status 3 (active/inactive/banned) 1 / 3 Last (least selective)
is_deleted 2 (true/false) 1 / 2 Last or use partial index

EXPLAIN Output: Seeing Index Usage

-- Create table and composite index
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    customer_id INT,
    status VARCHAR(20),
    created_at TIMESTAMP,
    total DECIMAL(10,2)
);

CREATE INDEX idx_orders_composite
  ON orders(customer_id, status, created_at);

-- ✅ Uses full index (all 3 prefix columns)
EXPLAIN ANALYZE SELECT * FROM orders
WHERE customer_id = 42
  AND status = 'shipped'
  AND created_at > '2024-01-01';
-- → Index Scan using idx_orders_composite
--   Index Cond: (customer_id=42 AND status='shipped' AND created_at > ...)

-- ⚠️ Partial index use (skips created_at in index cond)
EXPLAIN ANALYZE SELECT * FROM orders
WHERE customer_id = 42
  AND created_at > '2024-01-01';
-- → Index Scan using idx_orders_composite
--   Index Cond: (customer_id = 42)
--   Filter: (created_at > '2024-01-01')  ← filtered AFTER index

-- ❌ Cannot use index (skips leftmost column)
EXPLAIN ANALYZE SELECT * FROM orders
WHERE status = 'shipped';
-- → Seq Scan on orders
--   Filter: (status = 'shipped')  ← full table scan!

Python Demo: Prefix Matching Simulation

from typing import List, Tuple, Optional
import bisect

class CompositeIndex:
    """Simulates a composite B-Tree index on multiple columns.

    Demonstrates the leftmost prefix rule by storing sorted
    tuples and performing prefix-based binary search.
    """

    def __init__(self, columns: List[str]):
        self.columns = columns
        self.entries: List[Tuple] = []  # Sorted composite keys
        self.name = f"idx_({'_'.join(columns)})"

    def insert(self, values: Tuple):
        """Insert a composite key maintaining sorted order."""
        bisect.insort(self.entries, values)

    def lookup(self, prefix: dict) -> dict:
        """Lookup using leftmost prefix rule.

        Returns which columns were used as index conditions
        vs. which required post-filtering.
        """
        index_cols_used = []
        filter_cols = []

        # Check leftmost prefix rule
        for col in self.columns:
            if col in prefix:
                if not filter_cols:  # Still in prefix
                    index_cols_used.append(col)
                else:
                    filter_cols.append(col)
            else:
                # Gap breaks the prefix
                filter_cols.extend(
                    c for c in self.columns[len(index_cols_used):]
                    if c in prefix and c not in filter_cols
                )
                break

        # Count matching entries using prefix
        prefix_key = tuple(prefix.get(c) for c in index_cols_used)
        matches = 0
        scanned = 0

        for entry in self.entries:
            entry_prefix = entry[:len(prefix_key)]
            if entry_prefix == prefix_key:
                scanned += 1
                # Apply remaining filters
                match = True
                for fc in filter_cols:
                    col_idx = self.columns.index(fc)
                    if entry[col_idx] != prefix[fc]:
                        match = False
                        break
                if match:
                    matches += 1

        used_index = len(index_cols_used) > 0
        return {
            "index": self.name,
            "used_index": used_index,
            "index_cond": index_cols_used,
            "filter_cond": filter_cols,
            "rows_scanned": scanned if used_index else len(self.entries),
            "rows_matched": matches,
            "scan_type": "Index Scan" if used_index else "Seq Scan",
        }


# --- Demo: leftmost prefix rule in action ---

import random

# Create index on (city, status, age)
idx = CompositeIndex(["city", "status", "age"])

cities = ["NYC", "London", "Tokyo", "Berlin", "Paris"]
statuses = ["active", "inactive", "banned"]

# Insert 10000 rows
for _ in range(10000):
    idx.insert((
        random.choice(cities),
        random.choice(statuses),
        random.randint(18, 65)
    ))

# Test various query patterns
queries = [
    {"city": "NYC"},                                    # ✅ prefix (city)
    {"city": "NYC", "status": "active"},               # ✅ prefix (city, status)
    {"city": "NYC", "status": "active", "age": 30}, # ✅ full index
    {"city": "NYC", "age": 30},                       # ⚠️ partial (city only)
    {"status": "active"},                              # ❌ skips leftmost
    {"age": 30},                                        # ❌ skips leftmost
]

print("=== Composite Index: Leftmost Prefix Rule ===")
print(f"Index: {idx.name} on {idx.columns}")
print(f"Total rows: {len(idx.entries):,}\n")

for q in queries:
    result = idx.lookup(q)
    status = "✅" if result["used_index"] else "❌"
    print(f"{status} WHERE {q}")
    print(f"   Scan: {result['scan_type']}")
    print(f"   Index Cond: {result['index_cond']}")
    print(f"   Filter: {result['filter_cond']}")
    print(f"   Rows scanned: {result['rows_scanned']:,}")
    print()

🏭 Industry Practice

MySQL InnoDB: Composite indexes are stored as a single B+Tree with concatenated key values. InnoDB always appends the primary key to secondary indexes, so an index on (city, status) is actually stored as (city, status, id). This means the PK is implicitly included — queries ordering by PK after the index columns get it “for free.”

PostgreSQL INCLUDE: Since v11, PostgreSQL supports INCLUDE columns that are stored in the index leaf pages but not part of the sort key. This creates covering indexes without bloating the internal nodes. Use INCLUDE for columns you SELECT but don’t filter on.

Index Advisor Tools: Tools like pg_qualstats + hypopg (PostgreSQL), MySQL’s sys.schema_unused_indexes, and cloud-native advisors (AWS RDS Performance Insights, Azure Index Advisor) analyze query patterns and recommend optimal composite indexes automatically.

MongoDB Compound Indexes: Follow the ESR rule — Equality, Sort, Range. Put equality-match fields first, then sort fields, then range fields last. The .explain("executionStats") output shows indexBounds revealing exactly which portions of the compound index were used.

📋 Key Takeaways

  • Composite indexes sort by column 1, then column 2, then column 3 — order determines usability
  • The leftmost prefix rule: index (a,b,c) only helps queries starting from (a), (a,b), or (a,b,c)
  • Put equality columns first, range columns last, and the most selective equality column first among equals
  • Covering indexes (with INCLUDE) eliminate heap lookups entirely — fastest possible reads
  • One composite index often replaces 2–3 single-column indexes with better performance
  • Always verify with EXPLAIN ANALYZE that your index is actually being used as intended

🧠 Mental Model

A composite index is a sorted phone book. The sort order determines what lookups are fast. You can jump to “S” instantly (first column), then within “S” find “Smith” (second column), but you cannot jump to all “Johns” without scanning the entire book.

  COMPOSITE INDEX on (city, status, age):

  Sorted like a multi-level phone book:
  ┌─────────────────────────────────────────────┐
  │ Berlin, active, 22  │ ← B-Tree leaf entries │
  │ Berlin, active, 35  │   sorted by all 3     │
  │ Berlin, banned, 19  │   columns combined    │
  │ London, active, 28  │                       │
  │ London, active, 41  │                       │
  │ London, inactive, 30│                       │
  │ NYC, active, 25     │                       │
  │ NYC, active, 30     │                       │
  │ NYC, inactive, 22   │                       │
  │ Tokyo, active, 33   │                       │
  └─────────────────────────────────────────────┘

  QUERY: WHERE city='NYC' AND status='active'
  ─────────────────────────────────────────────
  Jump to 'NYC' section → narrow to 'active'
  ✅ Uses index: (city, status) prefix

  QUERY: WHERE status='active'
  ─────────────────────────────────────────────
  'active' entries are SCATTERED across cities!
  ❌ Cannot use index: must scan everything

  COVERING INDEX:
  ┌──────────────────────────────────────────────┐
  │ Index Key (sorted)  │  INCLUDE columns       │
  │ (city, status)      │  (email, name)         │
  ├─────────────────────┼────────────────────────┤
  │ Berlin, active      │  alice@x.com, Alice    │
  │ London, active      │  bob@y.com, Bob        │
  │ NYC, inactive       │  eve@z.com, Eve        │
  └─────────────────────┴────────────────────────┘
  SELECT email, name WHERE city='NYC' → Index Only Scan!
  No need to visit the actual table at all.

⚠️ Common Mistakes

  • Creating separate indexes instead of one composite: Three single-column indexes on (a), (b), (c) are NOT equivalent to one composite index on (a, b, c). The database can only use one index per table access (bitmap index scan aside). A composite index handles multi-column WHERE clauses in a single B-Tree traversal.
  • Wrong column order: Putting the range column before equality columns wastes the index. Index (age, city) cannot efficiently handle WHERE city='NYC' AND age BETWEEN 25 AND 35 because the city filter requires a full scan within each age bucket. Reverse the order: (city, age).
  • Too many columns in the index: A 6-column composite index is expensive to maintain and only benefits the exact query pattern it was designed for. Wide indexes slow every INSERT/UPDATE. Prefer 2–4 columns targeted at your top queries, with INCLUDE for coverage.
  • Not checking EXPLAIN output: Developers assume their index is being used without verifying. The planner may choose a sequential scan if statistics are stale (ANALYZE the table), the selectivity is too low, or the query pattern doesn’t match the leftmost prefix. Always validate with EXPLAIN (ANALYZE, BUFFERS).

🎯 Exercises

  1. Prefix rule verification: Create a table with 1M rows and a composite index on (country, city, zip_code). Write 6 queries testing each prefix combination and use EXPLAIN ANALYZE to verify which ones use the index and which fall back to sequential scan.
  2. Column ordering experiment: For the query WHERE status='active' AND created_at > '2024-01-01' AND country='US', create indexes with different column orders: (status, created_at, country), (country, status, created_at), (country, created_at, status). Benchmark all three and explain why one wins.
  3. Covering index optimization: Find a query in your application that performs an index scan followed by a heap fetch (look for “Index Scan” without “Index Only Scan” in EXPLAIN). Add INCLUDE columns to make it covering and measure the buffer hit reduction.
  4. Index consolidation: Audit a table with 5+ single-column indexes. Identify which queries hit multiple columns and design 1–2 composite indexes that replace 3–4 single-column indexes while maintaining or improving query performance.
