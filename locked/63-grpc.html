Intermediate API Concept

gRPC

High-performance, language-agnostic remote procedure calls — built on Protocol Buffers and HTTP/2 for blazing-fast inter-service communication.

💡 Analogy

Imagine two computers communicating. REST is like writing full English letters — verbose, readable by anyone, but slow to compose and deliver. gRPC is like speaking efficient shorthand — both sides agree on a compact vocabulary beforehand (the .proto file), then exchange tiny coded messages at lightning speed over a dedicated phone line (HTTP/2). The conversation is faster, but you need the shared codebook to understand it.

What Is gRPC?

gRPC (gRPC Remote Procedure Calls) is an open-source framework developed by Google that enables efficient communication between distributed services. It uses Protocol Buffers (protobuf) as the interface definition language and serialization format, and runs over HTTP/2 for multiplexed, bidirectional streaming.

Core Components

  • Protocol Buffers — A language-neutral, platform-neutral mechanism for serializing structured data. Messages are defined in .proto files and compiled into language-specific code.
  • HTTP/2 Transport — Provides multiplexing (multiple requests over one connection), header compression, and server push capabilities.
  • Code Generation — The protoc compiler generates client stubs and server skeletons in 10+ languages from a single .proto definition.
  • Interceptors — Middleware for logging, auth, retries, and metrics — similar to HTTP middleware in REST frameworks.

Streaming Types

gRPC supports four communication patterns, each suited to different use cases:

1. Unary RPC

The simplest pattern — client sends one request, server returns one response. Equivalent to a traditional function call.

2. Server-Streaming RPC

Client sends one request, server returns a stream of responses. Ideal for large result sets or real-time feeds.

3. Client-Streaming RPC

Client sends a stream of messages, server returns one response after processing all messages. Great for file uploads or batch ingestion.

4. Bidirectional Streaming

Both sides send streams of messages independently. The ultimate pattern for real-time collaboration, chat systems, or multiplayer games.

Protocol Buffer Definition

user_service.proto
// Define the service contract
syntax = "proto3";

package userservice;

// Message definitions
message GetUserRequest {
    string user_id = 1;
}

message User {
    string id = 1;
    string name = 2;
    string email = 3;
    int32 age = 4;
    repeated string roles = 5;
}

message UserList {
    repeated User users = 1;
}

// Service definition with all streaming types
service UserService {
    // Unary — single request, single response
    rpc GetUser(GetUserRequest) returns (User);

    // Server streaming — one request, stream of responses
    rpc ListUsers(GetUserRequest) returns (stream User);

    // Client streaming — stream of requests, one response
    rpc UploadUsers(stream User) returns (UserList);

    // Bidirectional streaming
    rpc SyncUsers(stream User) returns (stream User);
}

gRPC Server Implementation

server.py
import grpc
from concurrent import futures
import user_service_pb2
import user_service_pb2_grpc

class UserServiceServicer(user_service_pb2_grpc.UserServiceServicer):
    def __init__(self):
        self.users = {
            "1": user_service_pb2.User(
                id="1", name="Alice",
                email="alice@example.com", age=30
            ),
            "2": user_service_pb2.User(
                id="2", name="Bob",
                email="bob@example.com", age=25
            ),
        }

    def GetUser(self, request, context):
        # Unary RPC — return single user
        user = self.users.get(request.user_id)
        if not user:
            context.set_code(grpc.StatusCode.NOT_FOUND)
            context.set_details(f"User {request.user_id} not found")
            return user_service_pb2.User()
        return user

    def ListUsers(self, request, context):
        # Server streaming — yield users one by one
        for user in self.users.values():
            yield user

    def UploadUsers(self, request_iterator, context):
        # Client streaming — collect all users
        uploaded = []
        for user in request_iterator:
            self.users[user.id] = user
            uploaded.append(user)
        return user_service_pb2.UserList(users=uploaded)

    def SyncUsers(self, request_iterator, context):
        # Bidirectional streaming — echo back with confirmation
        for user in request_iterator:
            self.users[user.id] = user
            user.name = f"[synced] {user.name}"
            yield user


def serve():
    server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
    user_service_pb2_grpc.add_UserServiceServicer_to_server(
        UserServiceServicer(), server
    )
    server.add_insecure_port("[::]:50051")
    server.start()
    print("gRPC server running on port 50051")
    server.wait_for_termination()

if __name__ == "__main__":
    serve()

gRPC Client with Streaming

client.py
import grpc
import user_service_pb2
import user_service_pb2_grpc

def run_client():
    channel = grpc.insecure_channel("localhost:50051")
    stub = user_service_pb2_grpc.UserServiceStub(channel)

    # Unary call
    user = stub.GetUser(
        user_service_pb2.GetUserRequest(user_id="1")
    )
    print(f"Got user: {user.name}")

    # Server streaming — iterate over response stream
    for user in stub.ListUsers(
        user_service_pb2.GetUserRequest(user_id="")
    ):
        print(f"Streamed: {user.name} ({user.email})")

    # Client streaming — send batch of users
    def user_generator():
        for i in range(3, 6):
            yield user_service_pb2.User(
                id=str(i),
                name=f"User_{i}",
                email=f"user{i}@example.com",
                age=20 + i
            )

    result = stub.UploadUsers(user_generator())
    print(f"Uploaded {len(result.users)} users")

    # Bidirectional streaming
    responses = stub.SyncUsers(user_generator())
    for resp in responses:
        print(f"Synced: {resp.name}")

if __name__ == "__main__":
    run_client()

gRPC vs REST vs GraphQL

Feature gRPC REST GraphQL
Protocol HTTP/2 HTTP/1.1 or HTTP/2 HTTP/1.1 or HTTP/2
Serialization Protocol Buffers (binary) JSON (text) JSON (text)
Streaming Bidirectional native Not built-in Subscriptions only
Code Generation Built-in (10+ languages) OpenAPI/Swagger Schema-based tools
Browser Support Limited (gRPC-Web) Native Native
Performance Fastest (binary + HTTP/2) Moderate Moderate
Best For Microservices, real-time Public APIs, CRUD Flexible queries, frontends

When to Use gRPC

Ideal Use Cases

  • Microservice-to-microservice — Internal service communication where performance matters and browser support is not needed.
  • Real-time streaming — Live data feeds, telemetry, IoT sensor data where bidirectional communication is essential.
  • Polyglot environments — Teams using different languages benefit from generated stubs and shared contracts.
  • Low-latency systems — Financial trading, gaming, and any system where microseconds matter.

When NOT to Use gRPC

  • Public-facing APIs — REST remains easier for third-party developers and browser clients.
  • Simple CRUD — The overhead of protobuf definitions is not worth it for basic operations.
  • Human-readable debugging — Binary serialization makes it harder to inspect traffic without tooling.

🏭 Industry Usage

  • Google — Created gRPC; uses it for internal services handling billions of RPCs per second.
  • Kubernetes — All internal component communication (kubelet → API server) uses gRPC.
  • Envoy Proxy — Native gRPC support for service mesh communication and load balancing.
  • Netflix — Migrated inter-service communication from REST to gRPC for performance gains.
  • Dropbox — Uses gRPC for internal APIs, replacing a custom RPC framework — reduced latency by 50%.

📋 Summary

  • gRPC uses Protocol Buffers for compact, strongly-typed binary serialization.
  • HTTP/2 enables multiplexing, header compression, and native streaming.
  • Four streaming patterns — unary, server-streaming, client-streaming, bidirectional.
  • Code generation produces type-safe client/server code in 10+ languages.
  • Best for internal microservice communication — not ideal for browser-facing APIs.
  • Performance advantage of 2–10x over REST/JSON for serialization and transport.

⚠️ Common Mistakes

  • Exposing gRPC directly to browsers — Use gRPC-Web or a REST gateway (like Envoy) for browser clients. Native gRPC requires HTTP/2 trailers which browsers don't fully support.
  • Ignoring backward compatibility in .proto files — Never change field numbers or remove fields. Use reserved to retire fields and always add new fields with new numbers.
  • Not handling streaming errors — Streams can fail mid-transfer. Always implement proper error handling and reconnection logic for long-lived streams.
  • Skipping deadlines/timeouts — Every gRPC call should have a deadline. Without one, a failed downstream service can cause resource leaks and cascading failures.

  2. Implement server streaming — Build a stock price ticker service that streams price updates every second using server-streaming RPC. Handle client cancellation gracefully.
  3. Add interceptors — Write a gRPC interceptor that logs the method name, request duration, and status code for every RPC call. Add a second interceptor for authentication via metadata.
  4. Build a gateway — Create a REST-to-gRPC gateway using grpc-gateway or a simple Flask wrapper that translates JSON requests into protobuf calls and back. Compare latency with direct gRPC.
