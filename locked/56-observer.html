Intermediate Pattern Design Pattern

Observer

Defining a one-to-many dependency between objects — when one changes state, all dependents are notified and updated automatically.

💡 Real-World Analogy

Think of a newsletter subscription. When the newspaper publishes a new edition, all subscribers receive it automatically — they don’t need to check the newsstand every morning. New readers can subscribe at any time, and existing readers can unsubscribe whenever they want. The publisher doesn’t need to know who the subscribers are or what they do with the paper — it just delivers to everyone on the list. That’s the Observer pattern: publish once, notify many.

What Is the Observer Pattern?

  • Intent: Define a one-to-many dependency so that when one object (Subject) changes, all its dependents (Observers) are notified automatically
  • Classification: Behavioral pattern (GoF) — controls how objects communicate
  • Also known as: Publish-Subscribe, Event-Listener, Signal-Slot
  • Loose coupling: The subject knows nothing about observers except that they implement an interface — you can add/remove observers without touching the subject
  • Foundation: Event-driven architecture, reactive programming, and GUI frameworks all build on this pattern

Push vs Pull Models

  • Push model: Subject sends all relevant data to observers in the notification — observers get everything they need immediately
  • Pull model: Subject sends minimal notification (“I changed”); observers query the subject for the data they need
  • Push advantage: Observers don’t need a reference back to the subject; simpler for observers
  • Pull advantage: Subject doesn’t need to know what data each observer wants; more flexible
  • Hybrid: Most real systems push an event type + payload, letting observers filter by event type

Observer in GUI Frameworks

  • DOM Events: element.addEventListener('click', handler) — the element is the subject, handlers are observers
  • React: useState triggers re-renders of all components that read that state — components are observers of state
  • Vue: Reactive data system automatically tracks dependencies and re-renders — built-in observer pattern
  • Qt Signals/Slots: Objects emit signals; connected slots (observer methods) are called automatically

Memory Leaks from Unsubscribed Observers

  • If an observer subscribes but never unsubscribes, the subject holds a reference to it → garbage collector can’t reclaim it
  • Classic source of memory leaks in long-lived applications (servers, SPAs, games)
  • Solution: Always unsubscribe in cleanup/destructor methods; use weak references where possible
  • React’s useEffect return function exists specifically to clean up subscriptions

Python EventEmitter — Generic Observer

from typing import Callable, Dict, List, Any
import weakref


# ═══════════════════════════════════════════════════
# Generic EventEmitter — subject that manages observers
# ═══════════════════════════════════════════════════

class EventEmitter:
    """A generic observer/event system — subscribe, emit, unsubscribe."""

    def __init__(self):
        self._listeners: Dict[str, List[Callable]] = {}

    def on(self, event: str, callback: Callable) -> Callable:
        """Subscribe a callback to an event. Returns the callback for chaining."""
        if event not in self._listeners:
            self._listeners[event] = []
        self._listeners[event].append(callback)
        return callback

    def off(self, event: str, callback: Callable) -> None:
        """Unsubscribe a callback from an event."""
        if event in self._listeners:
            self._listeners[event] = [
                cb for cb in self._listeners[event]
                if cb != callback
            ]

    def emit(self, event: str, *args, **kwargs) -> None:
        """Notify all observers subscribed to this event."""
        for callback in self._listeners.get(event, []):
            callback(*args, **kwargs)

    def once(self, event: str, callback: Callable) -> Callable:
        """Subscribe a callback that fires only once, then auto-unsubscribes."""
        def wrapper(*args, **kwargs):
            callback(*args, **kwargs)
            self.off(event, wrapper)
        self.on(event, wrapper)
        return callback


# ═══════════════════════════════════════════════════
# Demo: Using the EventEmitter
# ═══════════════════════════════════════════════════

emitter = EventEmitter()

# Subscribe observers
emitter.on("user:login", lambda user: print(f"  [Analytics] {user} logged in"))
emitter.on("user:login", lambda user: print(f"  [Audit] Login event for {user}"))
emitter.on("user:login", lambda user: print(f"  [Welcome] Hello, {user}!"))

print("=== User Login Event ===")
emitter.emit("user:login", "Alice")

# One-time observer
emitter.once("first:purchase", lambda item: print(f"  [Promo] First purchase: {item}! 10% off next!"))

print("\n=== First Purchase ===")
emitter.emit("first:purchase", "Laptop")
print("=== Second Purchase (no promo) ===")
emitter.emit("first:purchase", "Mouse")  # observer already removed

Stock Price Observer — Classic Example

from abc import ABC, abstractmethod
from typing import List


# ═══════════════════════════════════════════════════
# Observer interface
# ═══════════════════════════════════════════════════

class StockObserver(ABC):
    """Interface that all observers must implement."""

    @abstractmethod
    def update(self, symbol: str, price: float) -> None:
        ...


# ═══════════════════════════════════════════════════
# Subject — the stock ticker
# ═══════════════════════════════════════════════════

class StockTicker:
    """Subject that notifies observers when stock prices change."""

    def __init__(self):
        self._observers: List[StockObserver] = []
        self._prices: dict = {}

    def subscribe(self, observer: StockObserver) -> None:
        self._observers.append(observer)
        print(f"  [Ticker] {observer.__class__.__name__} subscribed")

    def unsubscribe(self, observer: StockObserver) -> None:
        self._observers.remove(observer)
        print(f"  [Ticker] {observer.__class__.__name__} unsubscribed")

    def set_price(self, symbol: str, price: float) -> None:
        """Update price and notify all observers."""
        old_price = self._prices.get(symbol, 0)
        self._prices[symbol] = price
        if price != old_price:
            self._notify(symbol, price)

    def _notify(self, symbol: str, price: float) -> None:
        for observer in self._observers:
            observer.update(symbol, price)


# ═══════════════════════════════════════════════════
# Concrete observers — each reacts differently
# ═══════════════════════════════════════════════════

class PriceDisplay(StockObserver):
    def update(self, symbol: str, price: float) -> None:
        print(f"  [Display] {symbol}: ${price:.2f}")

class PriceAlert(StockObserver):
    def __init__(self, threshold: float):
        self._threshold = threshold

    def update(self, symbol: str, price: float) -> None:
        if price > self._threshold:
            print(f"  [ALERT] {symbol} exceeded ${self._threshold}! Now ${price:.2f}")

class TradeBot(StockObserver):
    def update(self, symbol: str, price: float) -> None:
        if price < 150:
            print(f"  [Bot] BUY {symbol} at ${price:.2f} (below $150)")
        elif price > 200:
            print(f"  [Bot] SELL {symbol} at ${price:.2f} (above $200)")


# Demo
ticker = StockTicker()
display = PriceDisplay()
alert = PriceAlert(threshold=180.0)
bot = TradeBot()

ticker.subscribe(display)
ticker.subscribe(alert)
ticker.subscribe(bot)

print("\n=== Price Updates ===")
ticker.set_price("AAPL", 145.50)
print()
ticker.set_price("AAPL", 185.00)
print()
ticker.set_price("AAPL", 210.75)

Chat Room with Observers

from typing import Set
from datetime import datetime


# ═══════════════════════════════════════════════════
# Chat Room — Subject that broadcasts messages
# ═══════════════════════════════════════════════════

class ChatRoom:
    """A chat room where users observe messages from others."""

    def __init__(self, name: str):
        self.name = name
        self._members: Set['ChatUser'] = set()

    def join(self, user: 'ChatUser') -> None:
        self._members.add(user)
        self._broadcast(f"[{user.username} joined #{self.name}]", sender=None)

    def leave(self, user: 'ChatUser') -> None:
        self._members.discard(user)
        self._broadcast(f"[{user.username} left #{self.name}]", sender=None)

    def send_message(self, sender: 'ChatUser', message: str) -> None:
        """Broadcast message to all members except sender."""
        formatted = f"[{sender.username}]: {message}"
        self._broadcast(formatted, sender=sender)

    def _broadcast(self, message: str, sender) -> None:
        for member in self._members:
            if member != sender:
                member.receive(self.name, message)


class ChatUser:
    """Observer — receives messages from chat rooms."""

    def __init__(self, username: str):
        self.username = username
        self.inbox: List[str] = []

    def receive(self, room: str, message: str) -> None:
        formatted = f"  [{self.username}] #{room}: {message}"
        self.inbox.append(formatted)
        print(formatted)


# Demo
room = ChatRoom("general")
alice = ChatUser("Alice")
bob = ChatUser("Bob")
charlie = ChatUser("Charlie")

print("=== Chat Room Observer ===")
room.join(alice)
room.join(bob)
room.join(charlie)
print()

room.send_message(alice, "Hello everyone!")
print()
room.send_message(bob, "Hey Alice!")
print()

room.leave(charlie)
room.send_message(alice, "Where did Charlie go?")

🏭 Industry Practice

JavaScript addEventListener: The DOM event system is the Observer pattern in action. button.addEventListener('click', handler) subscribes an observer; removeEventListener unsubscribes. The browser’s event loop is the notification mechanism. Multiple handlers can observe the same event independently.

React useState/useEffect: When state changes via setState, React re-renders all components that read that state — they’re observers. useEffect’s cleanup function (return () => unsubscribe()) prevents memory leaks by removing observers when components unmount.

Redux store.subscribe: Redux is a centralized subject. store.subscribe(listener) adds an observer that fires on every dispatch. React-Redux’s connect() and useSelector() optimize this with shallow equality checks — only re-rendering when relevant state slices change.

RxJS Observables: RxJS takes the Observer pattern to its extreme — everything is a stream of events. observable.pipe(filter(), map()).subscribe(observer) composes transformations on event streams. Used heavily in Angular for HTTP calls, form changes, and WebSocket data.

Django Signals: Django’s signal system (post_save.connect(handler, sender=User)) is a decoupled observer — models emit signals, handlers react without the model knowing about them. Used for audit logs, cache invalidation, and sending notifications on data changes.

📋 Key Takeaways

  • Observer defines a one-to-many dependency — subject notifies all observers automatically on state change
  • Loose coupling — subject and observers can evolve independently as long as they share the notification interface
  • Push model sends data with the notification; pull model lets observers query the subject
  • Memory leaks occur when observers forget to unsubscribe — always clean up in destructors/unmount hooks
  • Foundation for event-driven architecture, reactive programming, and modern UI frameworks
  • Pub/Sub is the distributed version — same concept, but with a message broker decoupling publishers from subscribers

🧠 Mental Model

Think of the Observer pattern as a radio broadcast. The radio station (Subject) transmits on a frequency. Anyone with a receiver tuned to that frequency (Observer) hears the broadcast. The station doesn’t know how many listeners there are. Listeners can tune in or out at any time. The broadcast happens regardless of whether anyone is listening.

⚠️ Common Mistakes

  • Memory leaks from forgotten unsubscriptions: The #1 Observer bug. If observers subscribe in a constructor but never unsubscribe, the subject holds references forever. In web apps, this means event listeners accumulating on every page navigation. Always pair subscribe() with unsubscribe() in cleanup logic.
  • Notification order dependency: If Observer A must run before Observer B, you have a hidden coupling. The Observer pattern makes no ordering guarantees. If order matters, use a priority queue or chain the observers explicitly rather than relying on registration order.
  • Cascading updates (notification storms): Observer A updates state in response to a notification, which triggers another notification to Observer B, which triggers another update… infinite loops or performance collapse. Guard against re-entrant notifications with a “notifying” flag or batch updates.
  • Observing too broadly: If every observer gets every event type, they waste time checking if the event is relevant. Use event names/topics (on("price:AAPL", ...)) so observers only receive events they care about. This is why Pub/Sub uses topic-based routing.
