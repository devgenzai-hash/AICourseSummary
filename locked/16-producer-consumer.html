System Design/ Producer-Consumer Pattern

Producer-Consumer Pattern

One of the most important patterns in all of computing: one side creates work, the other side processes it, with a buffer in between.

Intermediate Pattern Code
The Assembly Line

A factory assembly line: one station makes parts (producer) and places them on a conveyor belt (queue). Another station assembles them (consumer).

  • If the belt is full, the maker pauses (backpressure)
  • If the belt is empty, the assembler waits
  • The belt decouples production speed from consumption speed

The Pattern

import threading
from queue import Queue
import time, random

def producer(q, name):
    for i in range(10):
        item = f"{name}-item-{i}"
        q.put(item)  # Blocks if queue is full
        print(f"[{name}] Produced: {item}")
        time.sleep(random.uniform(0.1, 0.5))

def consumer(q, name):
    while True:
        item = q.get()  # Blocks if queue is empty
        if item is None:  # Poison pill = shutdown signal
            break
        print(f"  [{name}] Consumed: {item}")
        time.sleep(random.uniform(0.2, 0.8))
        q.task_done()

# Bounded queue (max 5 items) provides backpressure
buffer = Queue(maxsize=5)

# Multiple producers and consumers
producers = [threading.Thread(target=producer, args=(buffer, f"P{i}")) for i in range(3)]
consumers = [threading.Thread(target=consumer, args=(buffer, f"C{i}")) for i in range(2)]

for t in producers + consumers: t.start()
for t in producers: t.join()

# Send poison pills to stop consumers
for _ in consumers: buffer.put(None)
for t in consumers: t.join()

Bounded vs Unbounded Queues

TypeBehavior when fullRiskUse case
BoundedProducer blocks (backpressure)Producer slowdownProduction systems (safe)
UnboundedNever blocks, grows foreverOOM (out of memory)Low-volume, trusted input

Async Version

import asyncio

async def async_producer(queue, name):
    for i in range(10):
        await queue.put(f"{name}-{i}")
        await asyncio.sleep(0.1)

async def async_consumer(queue, name):
    while True:
        item = await queue.get()
        if item is None: break
        print(f"[{name}] Processing: {item}")
        await asyncio.sleep(0.2)

async def main():
    queue = asyncio.Queue(maxsize=5)
    producers = [async_producer(queue, f"P{i}") for i in range(3)]
    consumers = [async_consumer(queue, f"C{i}") for i in range(2)]
    await asyncio.gather(*producers)
    for _ in range(2): await queue.put(None)
    await asyncio.gather(*consumers)

asyncio.run(main())

Everywhere in Industry

  • Kafka — Producers publish messages, consumers process them (millions/sec)
  • RabbitMQ/SQS — Message queues are exactly this pattern
  • Web servers — Accept connections (producer) → worker pool processes (consumer)
  • ETL pipelines — Extract (produce) → Transform/Load (consume)

📝 Summary

  • Producer creates data/tasks; consumer processes them; queue buffers in between
  • Bounded queue provides backpressure (producer slows down when consumer is slow)
  • Unbounded queue risks OOM — always prefer bounded in production
  • Use poison pill (None) or Event to signal shutdown
  • Python: queue.Queue (threads), asyncio.Queue (async)
  • Every message broker (Kafka, RabbitMQ, SQS) is this pattern at scale

🧠 Mental Model

Producer → [Queue/Buffer] → Consumer P1 ──┐ P2 ──┤──→ [ _ _ _ _ _ ] ──→ C1 P3 ──┘ (bounded: 5) C2 Queue full? → Producers BLOCK (backpressure) Queue empty? → Consumers BLOCK (wait for work)

❌ Common Beginner Mistakes

  • Unbounded queue in production — If consumers are slower, queue grows until OOM crash.
  • No shutdown mechanism — Consumers loop forever. Use poison pill or Event for graceful stop.
  • Single consumer bottleneck — If processing is slow, add more consumers.
  • Not calling task_done() — queue.join() will hang forever if task_done() is not called.

🏋 Hands-On Exercise

  1. Build producer-consumer with 3 producers, 2 consumers, bounded queue of 5.
  2. Add monitoring: print queue size every second to see backpressure in action.
  3. Implement priority queue: urgent items processed before normal ones.
  4. Add error handling: if consumer fails on an item, put it in a dead-letter queue.
