System Design/ Context Switching

Context Switching and Its Cost

Every time a CPU switches from one task to another, it pays a hidden tax. Understanding this cost is why you don't just throw more threads at a problem.

Beginner Concept Production
🏠 Daily-Life Analogy: The Chef Switching Dishes

Imagine a chef cooking 5 dishes at once. Every time they switch from chopping vegetables to stirring soup, they have to:

  • Put down the knife (save current state)
  • Remember where they were with the vegetables (save progress)
  • Pick up the spoon (load new tool)
  • Remember the soup recipe (load new context)
  • Figure out where they left off with the soup (restore state)

Each switch takes real time. If the chef switches between dishes every 2 seconds, they spend more time switching than cooking. This is exactly what happens when a CPU has too many threads — it spends more time switching between them than actually running code.

What Is Context Switching?

A context switch happens when the operating system stops one thread/process and starts running another one on the same CPU core. The OS must:

  1. Save the state of the currently running thread (registers, program counter, stack pointer)
  2. Update the scheduler data structures (bookkeeping)
  3. Load the state of the next thread to run (its registers, program counter)
  4. Resume execution of the new thread from where it left off

This happens thousands of times per second on a typical system. The OS scheduler typically gives each thread a time slice (quantum) of 1-10 milliseconds before switching.

The Hidden Costs

Direct Costs (the obvious ones)

  • Register save/restore — ~1 microsecond to save and load all CPU registers
  • Kernel mode transition — Switching from user space to kernel space and back
  • Scheduler decision — The OS must decide who runs next

Indirect Costs (the real killers)

  • CPU cache pollution — The new thread's data isn't in cache. It has to be loaded from RAM (100x slower than cache)
  • TLB flush — Translation Lookaside Buffer must be refreshed for process switches (virtual address translations lost)
  • Pipeline flush — The CPU's instruction pipeline gets cleared
  • Branch predictor confusion — The CPU's branch prediction tables become useless for the new thread
🔥 The Real Cost

The direct cost of a context switch is ~1-5 microseconds. But the indirect cost (cache misses, TLB misses) can add 5-50 microseconds of slowdown as the new thread "warms up" the cache. At 10,000 context switches/second, that's up to 500ms/second wasted — half your CPU just switching!

Thread Switch vs Process Switch

Cost Component Thread Switch Process Switch
Save/restore registers Yes (~1μs) Yes (~1μs)
Switch stack Yes (fast) Yes (fast)
TLB flush No (same address space) Yes (EXPENSIVE — ~5-10μs)
Cache pollution Moderate (shared code/data) Severe (completely different data)
Memory map switch No Yes (page table base register)
Typical total cost ~1-10 μs ~10-50 μs

When Context Switches Happen

  • Time slice expires — The scheduler preempts the thread after its quantum (typically 1-10ms)
  • I/O wait — Thread calls read(), network recv(), etc. — OS switches to another thread while waiting
  • Synchronization — Thread tries to acquire a lock that's held — blocked, OS switches away
  • Higher priority thread wakes — A more important thread becomes ready
  • System call — Any kernel interaction (even clock reads) can trigger a switch

Code: Measuring Context Switch Cost

import threading
import time
import os

def measure_context_switch_overhead(num_threads, iterations_per_thread):
    """Demonstrate how more threads = more context switching = slower."""
    barrier = threading.Barrier(num_threads)
    results = []
    
    def worker():
        barrier.wait()  # Ensure all threads start together
        total = 0
        for i in range(iterations_per_thread):
            total += i * i  # CPU work
        results.append(total)
    
    start = time.perf_counter()
    threads = [threading.Thread(target=worker) for _ in range(num_threads)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    elapsed = time.perf_counter() - start
    
    return elapsed

# Same total work, different thread counts
total_work = 10_000_000

for num_threads in [1, 2, 4, 8, 16, 64, 256, 1000]:
    per_thread = total_work // num_threads
    elapsed = measure_context_switch_overhead(num_threads, per_thread)
    print(f"{num_threads:4d} threads: {elapsed:.3f}s")
    
# You'll see: beyond CPU core count, more threads = SLOWER
# 1 thread:    ~0.5s
# 4 threads:   ~0.5s (your core count)
# 64 threads:  ~0.8s (context switch overhead)
# 1000 threads: ~2.0s (massive overhead!)

Measuring with OS Tools

# Linux: See context switches per process
# In terminal:
# cat /proc/<PID>/status | grep ctxt
# voluntary_ctxt_switches: 142    (thread gave up CPU willingly - I/O wait)
# nonvoluntary_ctxt_switches: 89  (OS took CPU away - time slice expired)

import subprocess
import os

def get_context_switches(pid=None):
    """Read context switch counts from /proc (Linux only)."""
    if pid is None:
        pid = os.getpid()
    
    try:
        with open(f"/proc/{pid}/status") as f:
            for line in f:
                if "ctxt" in line:
                    print(line.strip())
    except FileNotFoundError:
        print("Not on Linux — use Windows Performance Monitor or macOS Instruments")

How to Reduce Context Switching

Strategy How It Works Used By
Thread pools Fixed number of threads, reuse them for tasks Every web server (Nginx, Tomcat)
CPU affinity Pin a thread to a specific CPU core High-frequency trading, game engines
Async I/O (epoll/io_uring) One thread handles thousands of connections without blocking Nginx, Node.js, Redis
User-space scheduling Don't involve the OS kernel at all Go runtime (goroutine scheduler)
Batch processing Do more work per time slice, switch less often Database query engines

🏢 Industry Examples

  • Redis — Single-threaded by design. Zero context switches for data operations = blazing fast.
  • Nginx — Small number of worker processes, each handling thousands of connections with epoll. Minimal switching.
  • LMAX Disruptor — Java financial trading framework. Pins threads to cores, uses lock-free ring buffers, achieves 6 million transactions/second.
  • Go runtime — Multiplexes millions of goroutines onto a small number of OS threads. User-space scheduling = almost no kernel context switches.

📝 Summary

  • Context switching is the OS pausing one thread and resuming another
  • Direct cost: ~1-5μs. Indirect cost (cache/TLB misses): 5-50μs
  • Process switches are 5-10x more expensive than thread switches (TLB flush)
  • More threads than CPU cores = more switching = slower performance
  • Solutions: thread pools, CPU affinity, async I/O, user-space scheduling
  • Rule of thumb: threads = CPU cores for CPU-bound work

🧠 Mental Model

Time slice: |--Thread A--|--SWITCH--|--Thread B--|--SWITCH--|--Thread A--| Switch cost: [save regs] [scheduler] [load regs] [cache warmup!!!] 1μs 0.5μs 1μs 5-50μs Rule: If switch_cost > useful_work_per_slice → TOO MANY THREADS Sweet spot: threads ≈ CPU cores (for CPU-bound work) threads >> CPU cores is OK for I/O-bound (blocked = no switch cost)

❌ Common Beginner Mistakes

  • Creating one thread per request — 10,000 concurrent users ≠ 10,000 threads. Use a thread pool with ~core_count threads.
  • Ignoring cache effects — The 1μs register save is nothing. The 50μs cache warmup is the real killer.
  • Thinking "more threads = faster" — Beyond core count, adding threads for CPU work makes things SLOWER.
  • Not distinguishing CPU-bound vs I/O-bound — I/O-bound work benefits from more threads (blocked threads don't consume CPU). CPU-bound work doesn't.

🏋️ Hands-On Exercise

  1. Write a CPU-intensive function (matrix multiplication, prime finding, etc.)
  2. Run it with 1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024 threads
  3. Plot execution time vs thread count — find the sweet spot where adding threads starts hurting
  4. Now change the function to be I/O-bound (use time.sleep(0.01) to simulate network calls)
  5. Re-plot — notice that for I/O-bound work, more threads helps up to much higher counts

Bonus: Use Python's concurrent.futures.ThreadPoolExecutor and experiment with different pool sizes.
