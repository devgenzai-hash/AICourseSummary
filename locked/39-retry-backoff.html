Intermediate Resilience Pattern

Retry with Backoff

Automatically retrying failed operations with progressively increasing delays — recovering from transient failures without overwhelming already-stressed systems.

💡 Real-World Analogy

Imagine calling a busy restaurant for a reservation. If you get a busy signal, you don’t slam redial immediately — that just keeps the line jammed. Instead, you wait 1 minute, try again. Still busy? Wait 2 minutes. Then 4. Then 8. You also add a little randomness — maybe you wait 7.3 minutes instead of exactly 8 — so you don’t collide with the 50 other people doing the same thing (that’s jitter).

Why Naive Retry Is Dangerous

Immediate retry without backoff creates a thundering herd — when a server recovers from a brief failure, all clients retry simultaneously and crash it again:

Retry Strategy Behavior After Failure Server Impact Recovery
No retry Give up immediately None (but poor UX) N/A
Immediate retry Retry 0ms after failure Amplifies load 3-5x Prevents recovery
Fixed interval Retry every N seconds Synchronized bursts Slow — bursts align
Exponential backoff 1s, 2s, 4s, 8s, 16s… Decreasing over time Good — spreads load
Backoff + jitter Random within [0, 2^n] Minimal — desynchronized Best — no bursts

Exponential Backoff Formula

The base formula for exponential backoff:

delay = min(base_delay * 2^attempt, max_delay)

With full jitter (recommended by AWS):

delay = random(0, min(base_delay * 2^attempt, max_delay))

Jitter Strategies

Jitter Type Formula Behavior Use Case
No jitter base * 2^n All clients retry at same time Never use in production
Full jitter random(0, base * 2^n) Uniform spread across window Default choice; best spread
Equal jitter base*2^n/2 + random(0, base*2^n/2) At least half the backoff guaranteed When min delay matters
Decorrelated jitter random(base, prev_delay * 3) Each delay independent of attempt count AWS SDK default

Retry with Backoff Decorator

A production-ready retry decorator with exponential backoff, jitter, and configurable retryable exceptions:

import time
import random
import functools
from typing import Tuple, Type

def retry_with_backoff(
    max_retries: int = 5,
    base_delay: float = 1.0,
    max_delay: float = 60.0,
    jitter: str = "full",
    retryable_exceptions: Tuple[Type[Exception], ...] = (Exception,)
):
    """Decorator that retries with exponential backoff.

    Args:
        max_retries: Maximum number of retry attempts.
        base_delay: Initial delay in seconds.
        max_delay: Cap on delay (prevents absurd waits).
        jitter: "full", "equal", or "decorrelated".
        retryable_exceptions: Only retry on these errors.
    """
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last_exception = None
            prev_delay = base_delay

            for attempt in range(max_retries + 1):
                try:
                    return func(*args, **kwargs)
                except retryable_exceptions as e:
                    last_exception = e
                    if attempt == max_retries:
                        break

                    # Calculate backoff delay
                    exp_delay = min(
                        base_delay * (2 ** attempt),
                        max_delay
                    )

                    if jitter == "full":
                        delay = random.uniform(0, exp_delay)
                    elif jitter == "equal":
                        delay = exp_delay / 2 + random.uniform(
                            0, exp_delay / 2
                        )
                    elif jitter == "decorrelated":
                        delay = random.uniform(
                            base_delay, prev_delay * 3
                        )
                        delay = min(delay, max_delay)
                        prev_delay = delay
                    else:
                        delay = exp_delay

                    print(f"Attempt {attempt + 1} failed: {e}")
                    print(f"Retrying in {delay:.2f}s...")
                    time.sleep(delay)

            raise last_exception
        return wrapper
    return decorator

)
def call_payment_api(order_id: str):

Retryable vs Non-Retryable Errors

Not all errors should be retried. Retrying a 400 Bad Request wastes resources and will never succeed:

Error Type Retryable? Examples Reason
Transient network ✓ Yes Connection timeout, DNS failure Likely to resolve on next attempt
Server overload ✓ Yes HTTP 429, 503 Server will recover with time
Conflict/lock ✓ Yes HTTP 409, deadlock detected Concurrent operation will finish
Client error ✗ No HTTP 400, 401, 403, 404 Request itself is wrong
Validation failure ✗ No HTTP 422, schema mismatch Data won’t magically fix itself
Business logic ✗ No Insufficient funds, quota exceeded Requires user action to resolve

Retry Budget

A retry budget limits the total percentage of requests that can be retries. This prevents cascading failures where retries dominate traffic:

import time
import threading
from collections import deque

class RetryBudget:
    """Limits retry attempts to a percentage of total requests.

    Prevents retry storms: if more than budget_percent of
    recent requests are retries, new retries are denied.
    Google SRE recommends a 10% retry budget.
    """

    def __init__(self, budget_percent: float = 10.0,
                 window_seconds: float = 60.0):
        self._budget = budget_percent / 100.0
        self._window = window_seconds
        self._requests: deque = deque()  # (timestamp, is_retry)
        self._lock = threading.Lock()

    def _cleanup(self, now: float):
        cutoff = now - self._window
        while self._requests and self._requests[0][0] < cutoff:
            self._requests.popleft()

    def record_request(self, is_retry: bool = False):
        """Record a request (first attempt or retry)."""
        with self._lock:
            now = time.monotonic()
            self._cleanup(now)
            self._requests.append((now, is_retry))

    def can_retry(self) -> bool:
        """Check if retry budget allows another retry.

        Returns False if retries exceed budget_percent
        of total requests in the current window.
        """
        with self._lock:
            now = time.monotonic()
            self._cleanup(now)

            if not self._requests:
                return True

            total = len(self._requests)
            retries = sum(
                1 for _, is_retry in self._requests
                if is_retry
            )
            return (retries / total) < self._budget

    @property
    def retry_ratio(self) -> float:
        """Current retry ratio (0.0 to 1.0)."""
        with self._lock:
            self._cleanup(time.monotonic())
            if not self._requests:
                return 0.0
            retries = sum(
                1 for _, is_retry in self._requests
                if is_retry
            )
            return retries / len(self._requests)


# Usage with retry logic
budget = RetryBudget(budget_percent=10.0, window_seconds=60.0)

def make_request_with_budget(url: str):
    budget.record_request(is_retry=False)
    try:
        # response = requests.get(url)
        return "success"
    except ConnectionError:
        if budget.can_retry():
            budget.record_request(is_retry=True)
            # ... retry with backoff
        else:
            print("Retry budget exhausted — failing fast")
            raise

Combining Backoff with Retry-After Header

When a server returns HTTP 429 or 503 with a Retry-After header, always respect it — it supersedes your calculated backoff:

import time
import random

def get_retry_delay(
    attempt: int,
    base_delay: float,
    max_delay: float,
    retry_after_header: str = None
) -> float:
    """Calculate retry delay, respecting Retry-After header.

    The server knows best when it will recover.
    Always use Retry-After if provided.
    """
    if retry_after_header:
        try:
            # Retry-After can be seconds or HTTP-date
            server_delay = float(retry_after_header)
            # Add small jitter to avoid synchronized retries
            return server_delay + random.uniform(0, 1.0)
        except ValueError:
            pass  # Fall through to calculated backoff

    # Exponential backoff with full jitter
    exp_delay = min(base_delay * (2 ** attempt), max_delay)
    return random.uniform(0, exp_delay)


# Example delays for 5 attempts (base=1s, max=30s):
# Attempt 0: random(0, 1)   → ~0.5s
# Attempt 1: random(0, 2)   → ~1.0s
# Attempt 2: random(0, 4)   → ~2.0s
# Attempt 3: random(0, 8)   → ~4.0s
# Attempt 4: random(0, 16)  → ~8.0s

🏭 Industry Practice

AWS SDK Retry Behavior: Uses exponential backoff with full jitter. Default is 3 retries for most services, 5 for DynamoDB. The SDK respects Retry-After headers and automatically classifies errors as retryable or terminal. Configurable via RetryMode.ADAPTIVE which includes a client-side token bucket.

gRPC Retry Policy: Configured per-method in service config. Specifies maxAttempts, initialBackoff, maxBackoff, backoffMultiplier, and retryableStatusCodes. Supports hedging (sending parallel requests) as an alternative to retry for latency-sensitive calls.

HTTP Retry-After Header: RFC 7231 standard. Can be seconds (Retry-After: 120) or an HTTP-date (Retry-After: Thu, 26 May 2026 12:00:00 GMT). Clients that ignore this risk being permanently banned by rate limiters.

Kubernetes Pod Restart Backoff: When a container crashes, kubelet restarts it with exponential backoff: 10s, 20s, 40s… up to 5 minutes (CrashLoopBackOff). Resets after 10 minutes of successful running. This prevents a buggy container from consuming all node resources in a tight restart loop.

📋 Key Takeaways

  • Never retry immediately — exponential backoff prevents thundering herds on recovery
  • Always add jitter — full jitter provides the best load distribution across retrying clients
  • Classify errors: only retry transient failures (429, 503, timeouts), never client errors (400, 401)
  • Cap delays with max_delay to bound worst-case latency
  • Use retry budgets (10% of traffic) to prevent retries from dominating system load
  • Respect Retry-After headers — the server knows when it will recover better than your formula

🧠 Mental Model

Exponential backoff with jitter is like a polite crowd at a closed store. Without jitter, everyone rushes the door the moment it opens (stampede). With jitter, each person checks at a slightly different random time — the store handles them smoothly one by one.

  EXPONENTIAL BACKOFF + FULL JITTER:

⚠️ Common Mistakes

  • Retrying non-idempotent operations: Retrying a POST /charge without an idempotency key can charge the customer multiple times. Always pair retry with idempotency — use a unique request ID so the server deduplicates repeated attempts.
  • No maximum retry limit: Without max_retries, a permanently broken endpoint causes clients to retry forever, consuming resources indefinitely. Always set a cap (3-5 retries) and fail fast after exhausting attempts.
  • Exponential backoff without jitter: Pure exponential (1s, 2s, 4s, 8s) without randomness causes all clients to retry at the same moment after each interval. The server sees periodic spikes instead of smooth load. Always add jitter.
  • Ignoring Retry-After headers: When a server says “retry after 60 seconds,” retrying after your calculated 4-second backoff is aggressive and may result in IP bans. Always check and respect the header before using your own calculation.

🎯 Exercises

  1. Implement all jitter strategies: Build a retry function that supports no-jitter, full-jitter, equal-jitter, and decorrelated-jitter. Run 100 simulated clients retrying simultaneously and plot the retry distribution over time for each strategy.
  2. Build a retry budget: Implement the RetryBudget class with a 10% budget over a 60-second window. Simulate a 50% failure rate and verify that retries are denied once the budget is exceeded, preventing retry amplification.
  3. Retry-aware HTTP client: Wrap requests or httpx with automatic retry logic that classifies HTTP status codes (retry on 429/503, fail on 400/401), respects Retry-After headers, and logs each attempt with delay.
  4. Combine retry with circuit breaker: Build a client that uses exponential backoff for transient failures but trips a circuit breaker after N consecutive failures. Verify the circuit breaker prevents retries entirely when the downstream is completely down.
