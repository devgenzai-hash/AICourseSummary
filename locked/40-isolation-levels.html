Database Engineering → Isolation Levels
Intermediate Database Concept

Isolation Levels

Controlling how much of one transaction’s uncommitted work is visible to other concurrent transactions — the fundamental trade-off between correctness and performance in database systems.

💡 Real-World Analogy

Imagine a library with different study room types. At an open table (Read Uncommitted), you can see everyone’s half-written notes — even drafts they might erase. In a cubicle (Read Committed), you only see final submitted papers, but someone could update a paper between your two reads. In a private room (Repeatable Read), once you pick up a document, no one can change it until you leave — but new documents can still appear on the shelf. In a sound-proof room (Serializable), you have the entire library frozen in time — nothing changes, nothing appears, complete isolation.

The Three Read Anomalies

Isolation levels exist to prevent three categories of read anomalies that occur when transactions run concurrently:

Anomaly What Happens Example Danger
Dirty Read Reading uncommitted data from another transaction TX-A writes balance=0, TX-B reads 0, TX-A rolls back to 500 Decisions based on data that never existed
Non-Repeatable Read Same row returns different values on re-read TX-B reads price=100, TX-A commits price=200, TX-B re-reads 200 Inconsistent calculations within one transaction
Phantom Read New rows appear in a repeated range query TX-B counts 5 orders, TX-A inserts order #6, TX-B re-counts 6 Aggregations change mid-transaction

The Four SQL Isolation Levels

SQL standard defines four levels with increasing strictness. Higher isolation means fewer anomalies but more locking and lower throughput:

1. Read Uncommitted

The weakest level — transactions can read data written by other uncommitted transactions. Almost never used in production because dirty reads make data unreliable.

2. Read Committed

Guarantees you only see committed data. Each statement gets a fresh snapshot. This is the default in PostgreSQL and Oracle. Non-repeatable reads are still possible because another transaction can commit between your two reads.

3. Repeatable Read

Once you read a row, it stays the same for the entire transaction. This is the default in MySQL InnoDB. In standard SQL, phantoms are possible, but InnoDB’s gap locks prevent them in practice.

4. Serializable

The strongest level — transactions execute as if they ran one at a time. No anomalies possible. This is the default in CockroachDB. Implementation varies: lock-based (SQL Server), SSI/Serializable Snapshot Isolation (PostgreSQL), or optimistic concurrency (CockroachDB).

Isolation Levels vs Phenomena

Isolation Level Dirty Read Non-Repeatable Read Phantom Read Performance
Read Uncommitted ✗ Possible ✗ Possible ✗ Possible Fastest
Read Committed ✓ Prevented ✗ Possible ✗ Possible Fast
Repeatable Read ✓ Prevented ✓ Prevented ✗ Possible* Moderate
Serializable ✓ Prevented ✓ Prevented ✓ Prevented Slowest

*MySQL InnoDB’s Repeatable Read uses gap locks to also prevent phantoms in practice.

MVCC — Multi-Version Concurrency Control

Modern databases avoid heavy locking by keeping multiple versions of each row. Readers don’t block writers, and writers don’t block readers:

Aspect Lock-Based MVCC
Reads block writes? Yes (shared locks held) No (reads see a snapshot)
Writes block reads? Yes (exclusive locks held) No (old version still visible)
Storage overhead Minimal (one version) Higher (multiple versions + vacuum)
Deadlock risk High Lower (but write-write conflicts remain)
Used by SQL Server (default) PostgreSQL, MySQL InnoDB, Oracle

Demonstrating Isolation Levels in Python

Using sqlite3 to show how isolation levels affect concurrent access. SQLite uses a simpler model but demonstrates the core concepts:

import sqlite3
import threading
import time

def setup_database(db_path: str):
    """Create a test database with account balances."""
    conn = sqlite3.connect(db_path)
    conn.execute("CREATE TABLE IF NOT EXISTS accounts "
                 "(id INTEGER PRIMARY KEY, name TEXT, balance REAL)")
    conn.execute("DELETE FROM accounts")
    conn.execute("INSERT INTO accounts VALUES (1, 'Alice', 1000.0)")
    conn.execute("INSERT INTO accounts VALUES (2, 'Bob', 500.0)")
    conn.commit()
    conn.close()


def demonstrate_dirty_read(db_path: str):
    """Show dirty read: reading uncommitted data.

    Transaction A updates but doesn't commit.
    Transaction B reads the uncommitted value.
    Transaction A rolls back -- B saw data that never existed.
    """
    results = {}

    def writer():
        conn = sqlite3.connect(db_path, isolation_level="DEFERRED")
        conn.execute("UPDATE accounts SET balance = 0 WHERE id = 1")
        time.sleep(0.5)  # Hold uncommitted change
        conn.rollback()   # Rollback -- balance stays 1000
        conn.close()

    def reader():
        time.sleep(0.1)   # Ensure writer started
        conn = sqlite3.connect(db_path, isolation_level=None)
        # In READ UNCOMMITTED, we'd see balance=0 (dirty read)
        cursor = conn.execute(
            "SELECT balance FROM accounts WHERE id = 1"
        )
        results["read_value"] = cursor.fetchone()[0]
        conn.close()

    t1 = threading.Thread(target=writer)
    t2 = threading.Thread(target=reader)
    t1.start(); t2.start()
    t1.join(); t2.join()

    print(f"Reader saw balance: {results['read_value']}")
    print("With READ UNCOMMITTED: would see 0 (dirty!)")
    print("With READ COMMITTED+: sees 1000 (correct)")


def demonstrate_non_repeatable_read(db_path: str):
    """Show non-repeatable read at Read Committed level.

    Transaction B reads a row twice.
    Between reads, Transaction A commits an update.
    B sees different values for the same row.
    """
    results = {}

    def updater():
        time.sleep(0.2)  # After first read
        conn = sqlite3.connect(db_path)
        conn.execute("UPDATE accounts SET balance = 750 WHERE id = 1")
        conn.commit()
        conn.close()

    def reader():
        conn = sqlite3.connect(db_path, isolation_level="DEFERRED")
        # First read
        cur = conn.execute(
            "SELECT balance FROM accounts WHERE id = 1"
        )
        results["first_read"] = cur.fetchone()[0]

        time.sleep(0.5)  # Allow updater to commit

        # Second read -- different value at Read Committed!
        cur = conn.execute(
            "SELECT balance FROM accounts WHERE id = 1"
        )
        results["second_read"] = cur.fetchone()[0]
        conn.close()

    t1 = threading.Thread(target=updater)
    t2 = threading.Thread(target=reader)
    t2.start(); t1.start()
    t2.join(); t1.join()

    print(f"First read:  {results['first_read']}")
    print(f"Second read: {results['second_read']}")
    print("At READ COMMITTED: values may differ (non-repeatable)")
    print("At REPEATABLE READ: both reads return same value")


def demonstrate_phantom_read(db_path: str):
    """Show phantom read: new rows appearing in range query.

    Transaction B counts rows matching a condition.
    Transaction A inserts a new matching row and commits.
    Transaction B re-counts and gets a different number.
    """
    results = {}

    def inserter():
        time.sleep(0.2)
        conn = sqlite3.connect(db_path)
        conn.execute(
            "INSERT INTO accounts VALUES (3, 'Charlie', 2000.0)"
        )
        conn.commit()
        conn.close()

    def counter():
        conn = sqlite3.connect(db_path, isolation_level="DEFERRED")
        # First count
        cur = conn.execute(
            "SELECT COUNT(*) FROM accounts WHERE balance > 0"
        )
        results["first_count"] = cur.fetchone()[0]

        time.sleep(0.5)

        # Second count -- phantom row appeared!
        cur = conn.execute(
            "SELECT COUNT(*) FROM accounts WHERE balance > 0"
        )
        results["second_count"] = cur.fetchone()[0]
        conn.close()

    t1 = threading.Thread(target=inserter)
    t2 = threading.Thread(target=counter)
    t2.start(); t1.start()
    t2.join(); t1.join()

    print(f"First count:  {results['first_count']}")
    print(f"Second count: {results['second_count']}")
    print("At REPEATABLE READ: new row appears (phantom)")
    print("At SERIALIZABLE: count stays consistent")

🏭 Industry Practice

PostgreSQL (Read Committed default): Uses MVCC with transaction snapshots. Each SQL statement sees a snapshot as of statement start. Serializable mode uses SSI (Serializable Snapshot Isolation) — detects serialization conflicts and aborts one transaction rather than holding locks. Applications must be prepared to retry aborted transactions.

MySQL InnoDB (Repeatable Read default): Uses MVCC with consistent reads and next-key locking. Gap locks prevent phantoms even at Repeatable Read, making it stronger than the SQL standard requires. Serializable mode converts all reads to SELECT ... LOCK IN SHARE MODE.

CockroachDB (Serializable default): Uses a timestamp-ordered optimistic concurrency scheme. All transactions run at Serializable — there is no weaker option. This simplifies reasoning about correctness at the cost of higher abort rates under contention. Retries are built into the client drivers.

SQL Server: Offers both lock-based isolation and snapshot isolation (MVCC). READ_COMMITTED_SNAPSHOT ON makes Read Committed use row versioning instead of shared locks — similar to PostgreSQL’s behavior. This dramatically reduces blocking in OLTP workloads.

📋 Key Takeaways

  • Isolation levels trade correctness for performance — higher isolation means more locking or aborts
  • Read Committed (PostgreSQL default) prevents dirty reads but allows non-repeatable reads and phantoms
  • Repeatable Read (MySQL default) freezes row values but standard allows phantom inserts
  • Serializable guarantees correctness equivalent to serial execution — use for financial transactions
  • MVCC avoids read/write blocking by maintaining multiple row versions — used by PostgreSQL, MySQL, Oracle
  • Always design applications to handle transaction aborts and retries at Serializable level

🧠 Mental Model

Think of isolation levels as a spectrum from “everyone sees everything instantly” to “each transaction operates in a private universe.” The key insight: you’re choosing where on the consistency-performance slider your application sits.

⚠️ Common Mistakes

  • Using Read Uncommitted for “performance”: The speed gain is negligible in MVCC databases (PostgreSQL, MySQL) because reads don’t take locks anyway. You get all the anomalies with almost no performance benefit. Use Read Committed instead — it’s nearly as fast and prevents dirty reads.
  • Assuming Repeatable Read prevents all anomalies: Standard Repeatable Read still allows phantom reads. Your aggregate queries (COUNT, SUM) can return inconsistent results if new rows are inserted. Only Serializable guarantees complete consistency for range queries.
  • Not handling serialization failures: At Serializable level, databases will abort conflicting transactions. If your application doesn’t catch and retry these errors (SQLSTATE 40001 in PostgreSQL), users see random failures. Always wrap Serializable transactions in a retry loop.
  • Holding transactions open too long: Long-running transactions at Repeatable Read or higher hold snapshots that prevent MVCC cleanup (vacuum). This causes table bloat in PostgreSQL and undo log growth in MySQL. Keep transactions short — milliseconds, not minutes.
