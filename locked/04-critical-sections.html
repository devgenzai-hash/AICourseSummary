System Design/ Critical Sections

Critical Sections

The danger zones in your code where only one thread should be allowed at a time. Master this and your concurrent code is safe.

Beginner Concept Code
The Single-Occupancy Bathroom

A critical section is like a single-occupancy bathroom in an office:

  • Only one person can be inside at a time
  • When you go in, you lock the door
  • Others must wait outside
  • When you leave, you unlock

The bathroom is the critical section. The lock on the door is the mutex. If two people could be in at the same time — chaos.

What Is a Critical Section?

A critical section is a piece of code that accesses a shared resource that must not be accessed by more than one thread at a time.

Identifying Critical Sections

Ask: "If two threads ran this code at the EXACT same time, could something go wrong?" If yes — it is a critical section.

import threading

balance = 1000
transaction_log = []

def transfer(amount):
    global balance
    # --- CRITICAL SECTION START ---
    if balance >= amount:
        balance -= amount
        transaction_log.append(f"Transferred {amount}")
    # --- CRITICAL SECTION END ---

    # This is NOT critical (local variable only)
    receipt = f"Receipt: {amount}"
    print(receipt)

Four Requirements for Safe Critical Sections

RequirementMeaningAnalogy
Mutual ExclusionOnly one thread in CS at a timeOne person in bathroom
ProgressIf CS is empty, waiting thread can enterEmpty bathroom = next person goes in
Bounded WaitingNo thread waits foreverEveryone gets a turn eventually
No speed assumptionsWorks regardless of thread speedWorks whether 1 min or 30 min

Implementation in Python

import threading

class ThreadSafeCounter:
    def __init__(self):
        self._count = 0
        self._lock = threading.Lock()

    def increment(self):
        with self._lock:  # Critical section
            self._count += 1

    def get(self):
        with self._lock:  # Even reads need protection!
            return self._count

counter = ThreadSafeCounter()
threads = [threading.Thread(target=lambda: [counter.increment() for _ in range(10000)])
           for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()
print(f"Count: {counter.get()}")  # Always 100,000

Critical Section Size Matters

Keep Critical Sections SHORT

The longer a thread holds a lock, the longer others wait. Long critical sections destroy parallelism.

# BAD: Too much inside the critical section
def process_bad(data):
    with lock:
        result = expensive_computation(data)  # 100ms others wait!
        shared_list.append(result)

# GOOD: Minimize critical section
def process_good(data):
    result = expensive_computation(data)  # No lock needed
    with lock:
        shared_list.append(result)  # Only this needs the lock

Industry Practice

  • Linux kernel — Moved from Big Kernel Lock (one giant CS) to fine-grained locks (many small CS).
  • Java ConcurrentHashMap — Locks individual buckets, not the whole map.
  • Database engines — Row-level vs table-level locking. Smaller CS = more concurrency.

📝 Summary

  • A critical section is code accessing shared mutable state
  • Only one thread may be in a critical section at a time (mutual exclusion)
  • Use locks to protect critical sections
  • Always use context managers (with lock:) to ensure release
  • Keep critical sections as SHORT as possible
  • Move expensive computation OUTSIDE the critical section

🧠 Mental Model

Thread A: ---- [LOCK] --- critical section --- [UNLOCK] -------- Thread B: ---- (waiting...) ---------------------- [LOCK] --- CS --- [UNLOCK] RULE: Keep the CS small! BAD: [LOCK] ---- 100ms work ---- [UNLOCK] (everyone waits) GOOD: -- 100ms work -- [LOCK] 1us [UNLOCK] (minimal waiting)

❌ Common Beginner Mistakes

  • Forgetting to release the lock — Always use with lock: or try/finally.
  • Making critical sections too large — Only protect shared state access.
  • Not protecting reads — Reads of shared data need locks too.
  • Using different locks for the same data — All threads must use THE SAME lock.

🏋 Hands-On Exercise

  1. Write a thread-safe queue (push/pop) using a list and a lock.
  2. Have 5 producers and 5 consumers use it simultaneously.
  3. First without lock — show corruption. Then with lock — show correctness.
  4. Measure: what % of time do threads spend waiting vs doing useful work?
