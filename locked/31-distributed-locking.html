System Design/ Distributed Locking

Distributed Locking

Coordinating access to shared resources when many nodes want to do the same thing at once. Mutexes for the distributed world.

Advanced Distributed Pattern
🏠 Daily-Life Analogy: The Bathroom Key

Some gas stations have a single key for the restroom, attached to a large object. Only one person can use it at a time:

  • The key = the distributed lock
  • Getting the key = acquiring the lock
  • Using the bathroom = accessing the shared resource
  • Returning the key = releasing the lock
  • Key has a timer = lock TTL (auto-returns if you pass out)

Why Distributed Locks?

A local mutex only protects ONE server. In a distributed system, you need a lock that ALL servers respect.

  • Prevent duplicate processing: Only one worker processes a job
  • Resource coordination: One node writes to a shared file
  • Leader election: Lock holder is the leader
  • Global rate limiting: Enforce limits across servers

Redis-Based Lock (Simplest)

import redis
import uuid
import time

class RedisDistributedLock:
    """Distributed lock using Redis SET NX EX"""

    def __init__(self, redis_client, lock_name, ttl=10):
        self.redis = redis_client
        self.lock_name = f"lock:{lock_name}"
        self.ttl = ttl
        self.lock_value = str(uuid.uuid4())  # Unique token

    def acquire(self, retry_count=3, retry_delay=0.5):
        """Try to acquire the lock"""
        for attempt in range(retry_count):
            # SET NX = set if not exists (atomic!)
            acquired = self.redis.set(
                self.lock_name,
                self.lock_value,
                nx=True,   # Only if key doesn't exist
                ex=self.ttl # Auto-expire (prevents deadlock)
            )
            if acquired:
                return True
            time.sleep(retry_delay)
        return False

    def release(self):
        """Release only if WE hold it (compare-and-delete)"""
        # Lua script for atomic check-and-delete
        lua_script = """
        if redis.call("get", KEYS[1]) == ARGV[1] then
            return redis.call("del", KEYS[1])
        else
            return 0
        end
        """
        self.redis.eval(lua_script, 1, self.lock_name, self.lock_value)

    def __enter__(self):
        if not self.acquire():
            raise Exception("Could not acquire lock")
        return self

    def __exit__(self, *args):
        self.release()

# Usage
r = redis.Redis()
with RedisDistributedLock(r, "payment-processing") as lock:
    process_payment(order_id)  # Only ONE server at a time

The Fencing Problem

Dangerous scenario: Client A acquires lock, then has a long GC pause. Lock TTL expires. Client B acquires the same lock. Client A wakes up thinking it still holds the lock. Both access the resource simultaneously!

Solution: Fencing tokens. Each acquisition gets a monotonically increasing token. The resource rejects requests with old tokens.

class FencedLock:
    def __init__(self, redis_client, lock_name):
        self.redis = redis_client
        self.lock_name = lock_name
        self.token_key = f"fence:{lock_name}"

    def acquire(self):
        token = self.redis.incr(self.token_key)  # Monotonic
        acquired = self.redis.set(self.lock_name, token, nx=True, ex=10)
        if acquired:
            return token  # Give token to resource
        return None

# Resource validates token:
def write_to_storage(data, fencing_token, storage):
    if fencing_token <= storage.last_token:
        raise Exception("Stale lock! Rejecting.")
    storage.last_token = fencing_token
    storage.write(data)  # Safe!

Redlock Algorithm

Single Redis = single point of failure. Redlock uses multiple independent Redis instances:

  1. Acquire lock on N/2 + 1 (majority) Redis instances
  2. If majority acquired within timeout → lock obtained
  3. If not → release partial locks and retry

Real-World Distributed Locks

  • Redis + Redlock — Most common for application-level locking
  • ZooKeeper — Ephemeral nodes (auto-delete on disconnect)
  • etcd — Lease-based locks with automatic expiration
  • Google Chubby — Paxos-based lock service (internal)
  • DynamoDB — Conditional writes as locks

📝 Summary

  • Distributed locks coordinate access across multiple servers
  • Redis SET NX EX is simplest (atomic set-if-not-exists with expiry)
  • Always use TTL — prevents deadlock if holder crashes
  • Always use unique tokens — only release YOUR lock
  • Fencing tokens prevent stale-lock problems (GC pause scenario)
  • Redlock uses multiple Redis instances for higher safety

🧠 Mental Model

Lock lifecycle: [UNLOCKED] --SET NX--> [LOCKED] --DEL (if mine)--> [UNLOCKED] | TTL expires (safety net) | v [UNLOCKED] (holder crashed) DANGER: GC pause between acquire and use: [A acquires] → [A pauses 15s] → [TTL expires] → [B acquires] → [A wakes up] → CONFLICT! Fix: Fencing token (A's old token rejected by resource)

❌ Common Beginner Mistakes

  • No TTL — Holder crashes = lock held forever = deadlock.
  • Releasing someone else's lock — Always verify lock_value before DEL.
  • Ignoring clock skew — TTL assumes synchronized clocks. Skew causes early expiry.
  • Long operations without renewal — If work > TTL, lock expires mid-operation.
  • Single Redis SPOF — Use Redlock or ZooKeeper for critical locks.

🏋 Hands-On Exercise

  1. Implement RedisDistributedLock. Run 5 workers trying the same lock. Verify mutual exclusion.
  2. Simulate GC pause: acquire lock, sleep longer than TTL. Show how fencing tokens prevent bugs.
  3. Implement lock renewal: background thread extends TTL while holder is working.
  4. Research Martin Kleppmann's critique of Redlock. What edge cases can fail?
