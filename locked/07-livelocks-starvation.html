System Design/ Livelocks & Starvation

Livelocks & Starvation

Deadlock's sneaky cousins. In a livelock, threads are active but make no progress. In starvation, one thread never gets a turn.

Beginner Concept Code
The Hallway Dance & the Polite Person

Livelock: Two people meet in a narrow hallway. Both step left to let the other pass. Then both step right. Then left again. They keep "dancing" but neither passes. They are active (moving) but make ZERO progress.

Starvation: A polite person at a buffet who always says "after you." Everyone else keeps going first. The polite person never gets food — starved out by others.

Livelock: Active but No Progress

Unlike deadlock (threads frozen), in a livelock threads are running, consuming CPU, responding to each other — but no useful work gets done.

import threading, time

class Worker:
    def __init__(self, name, partner=None):
        self.name = name
        self.working = False
        self.partner = partner

    def work(self):
        while True:
            if self.partner.working:
                # "Politely" wait — but partner does the same!
                print(f"{self.name}: Partner busy, backing off")
                time.sleep(0.01)
                continue
            self.working = True
            print(f"{self.name}: Working!")
            time.sleep(0.01)
            self.working = False
            break

# Both see the other as "working" and back off forever
alice = Worker("Alice")
bob = Worker("Bob")
alice.partner = bob
bob.partner = alice

Starvation: Never Getting a Turn

import threading, time, random

resource_lock = threading.Lock()
access_count = {"high_priority": 0, "low_priority": 0}

def high_priority_worker():
    for _ in range(1000):
        with resource_lock:
            access_count["high_priority"] += 1
        time.sleep(0.0001)  # Tiny gap — grabs lock again quickly

def low_priority_worker():
    for _ in range(10):
        with resource_lock:
            access_count["low_priority"] += 1

# With many high-priority threads, low-priority gets starved
threads = [threading.Thread(target=high_priority_worker) for _ in range(10)]
threads.append(threading.Thread(target=low_priority_worker))
for t in threads: t.start()
for t in threads: t.join()
print(access_count)  # low_priority might be way behind

Deadlock vs Livelock vs Starvation

ProblemThreads Active?Progress?Fix
DeadlockNo (blocked)NoneLock ordering, timeouts
LivelockYes (running)NoneRandom backoff, priority
StarvationSome yes, victim noOthers progress, victim does notFair locks, aging

Solutions

# Fix Livelock: Random backoff (like Ethernet CSMA/CD)
import random

def work_with_backoff(worker):
    retries = 0
    while True:
        if worker.partner.working:
            # Random backoff breaks the symmetry!
            time.sleep(random.uniform(0.001, 0.01) * (2 ** retries))
            retries += 1
            continue
        worker.working = True
        break

# Fix Starvation: Fair lock (FIFO ordering)
import queue

class FairLock:
    def __init__(self):
        self._queue = queue.Queue()
        self._lock = threading.Lock()

    def acquire(self):
        event = threading.Event()
        self._queue.put(event)
        while True:
            with self._lock:
                if self._queue.queue[0] is event:
                    return
            event.wait(timeout=0.01)

    def release(self):
        self._queue.get()

Industry Examples

  • Ethernet (CSMA/CD) — Random exponential backoff prevents livelock when multiple devices transmit simultaneously.
  • Java ReentrantLock(fair=true) — FIFO ordering prevents starvation.
  • OS schedulers — Priority aging: low-priority processes slowly gain priority to prevent starvation.
  • Database write-starved readers — Too many readers can starve writers. Fixed with write-preferring locks.

📝 Summary

  • Livelock: threads are active but make no progress (hallway dance)
  • Starvation: one thread never gets access to a resource
  • Fix livelock: random backoff breaks symmetry between competing threads
  • Fix starvation: fair/FIFO locks, priority aging
  • Unlike deadlock, livelocked threads consume CPU doing nothing useful

🧠 Mental Model

DEADLOCK: T1 blocked, T2 blocked. Neither moves. LIVELOCK: T1 backs off, T2 backs off, T1 backs off... (infinite loop) STARVATION: T1 gets lock, T2 gets lock, T3 gets lock... T4 NEVER gets lock. Random backoff fix: T1 waits 3ms, T2 waits 7ms --> T1 goes first, T2 follows. Progress!

❌ Common Beginner Mistakes

  • Confusing livelock with deadlock — In livelock, threads ARE running (check CPU usage).
  • Symmetric retry logic — If all threads retry identically, they stay synchronized. Add randomness!
  • Ignoring fairness — Default locks are not fair. Under contention, some threads may starve.
  • Priority inversion — High-priority thread starved because low-priority thread holds a lock it needs.

🏋 Hands-On Exercise

  1. Create a livelock: two threads that back off when they see the other working (both stay stuck).
  2. Fix it with random exponential backoff.
  3. Demonstrate starvation: 10 aggressive threads vs 1 that rarely gets the lock.
  4. Implement a fair lock using a queue and show it prevents starvation.
