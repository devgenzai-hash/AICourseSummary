System Design/ Atomic Operations & CAS

Atomic Operations & CAS

Operations that complete in a single indivisible step — no other thread can see them half-done. The foundation of lock-free programming.

Intermediate Concept Code
The Light Switch

Flipping a light switch is atomic — it is either ON or OFF, never halfway. You cannot catch it between states.

Compare-And-Swap (CAS) is like a safe with a combination: "Change the code to 5678 ONLY IF it is currently 1234." If someone already changed it, your attempt fails and you must retry with the new code.

What Are Atomic Operations?

An atomic operation completes in a single indivisible step at the hardware level. No thread can observe it half-done. No lock needed.

Why Locks Are Slow

Locks require: acquire (system call) → do work → release (system call). That is expensive. Atomic operations do the same thing with a single CPU instruction.

OperationDescriptionCPU Instruction
Atomic LoadRead a value atomicallyMOV (aligned)
Atomic StoreWrite a value atomicallyMOV (aligned)
Atomic AddIncrement in one stepLOCK XADD
Compare-And-SwapUpdate only if current value matches expectedLOCK CMPXCHG

Compare-And-Swap (CAS)

The most important atomic operation. Pseudocode:

# CAS(location, expected_value, new_value)
# Atomically:
#   if memory[location] == expected_value:
#       memory[location] = new_value
#       return True
#   else:
#       return False  (someone else changed it first)

Python Implementation (using ctypes for true atomics)

import threading
import ctypes

# Python doesn't have built-in atomics, but we can simulate CAS logic
class AtomicCounter:
    def __init__(self, initial=0):
        self._value = initial
        self._lock = threading.Lock()  # Simulates hardware CAS

    def compare_and_swap(self, expected, new_value):
        with self._lock:
            if self._value == expected:
                self._value = new_value
                return True
            return False

    def increment(self):
        while True:
            current = self._value
            if self.compare_and_swap(current, current + 1):
                return current + 1
            # CAS failed — someone else changed it. Retry!

    def get(self):
        return self._value

# Lock-free increment using CAS retry loop
counter = AtomicCounter()
threads = [threading.Thread(target=lambda: [counter.increment() for _ in range(10000)])
           for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()
print(f"Counter: {counter.get()}")  # Always 100,000

The ABA Problem

CAS Pitfall: ABA

Thread reads value A. Another thread changes it to B, then back to A. CAS succeeds (sees A) but the state may have changed semantically. Fix: use version counters or tagged pointers.

package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

func main() {
    var counter int64
    var wg sync.WaitGroup

    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < 10000; j++ {
                atomic.AddInt64(&counter, 1)  // True hardware atomic!
            }
        }()
    }
    wg.Wait()
    fmt.Println("Counter:", counter)  // Always 100,000
}

Industry Usage

  • Java AtomicInteger/AtomicReference — Built-in CAS via Unsafe class
  • Linux kernel — atomic_t type for reference counting, spinlock implementation
  • Lock-free queues — Michael-Scott queue uses CAS for enqueue/dequeue
  • Database MVCC — Version numbers are atomic counters

📝 Summary

  • Atomic operations complete in one indivisible CPU instruction — no lock needed
  • CAS (Compare-And-Swap): update only if current value matches expected
  • CAS retry loop: read → compute new value → CAS. If fails, retry.
  • Faster than locks for simple operations (no system call overhead)
  • ABA problem: value changes and returns — CAS succeeds incorrectly. Fix with version numbers.
  • Python lacks true atomics; use locks to simulate. Go/Java/C++ have hardware atomics.

🧠 Mental Model

CAS RETRY LOOP: 1. Read current value (e.g., 42) 2. Compute new value (e.g., 43) 3. CAS(expected=42, new=43) - SUCCESS: value was still 42, now 43. Done! - FAIL: someone changed it (it's now 44). Go to step 1. LOCK vs CAS: Lock: [acquire] --- work --- [release] (blocks others) CAS: read, compute, attempt. Fail? Retry. (no blocking!)

❌ Common Beginner Mistakes

  • Using CAS for complex operations — CAS works for single values. For multi-field updates, use locks.
  • Ignoring ABA — Always consider if "same value" means "same state."
  • Infinite retry under high contention — Many threads CASing the same value = many retries. Locks may be faster.
  • Thinking Python has true atomics — CPython GIL is not a substitute for proper atomics.
