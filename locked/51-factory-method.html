Beginner Pattern Design Pattern

Factory Method

Define an interface for creating objects, but let subclasses decide which class to instantiate — decoupling the what from the how of object creation.

💡 Real-World Analogy

A restaurant menu — you order “pasta” and the kitchen decides how to make it. You don’t need to know the recipe, which chef prepares it, or whether it’s made from scratch or reheated. You just say what you want, and the kitchen (the factory) handles the creation details. Tomorrow the kitchen might change the recipe entirely, but your ordering experience stays the same. That’s the Factory Method — you request a product by type, and the factory decides exactly which concrete class to build.

What Is the Factory Method Pattern?

  • Intent: Define a method that creates objects without specifying the exact class to instantiate
  • Classification: Creational pattern (GoF) — controls object creation through polymorphism
  • Key idea: Replace direct constructor calls (obj = ConcreteClass()) with a factory call (obj = factory.create(type))
  • Benefit: Client code depends on abstractions, not concrete implementations
  • Principle: Follows the Open/Closed Principle — add new types without modifying existing code

Simple Factory vs Factory Method vs Abstract Factory

  • Simple Factory: A single function/class with a switch/if-else that returns different objects — not a GoF pattern, but common in practice
  • Factory Method: An abstract method in a base class that subclasses override to create specific products — uses inheritance
  • Abstract Factory: A factory of factories — creates families of related objects (e.g., Windows buttons + Windows scrollbars vs Mac buttons + Mac scrollbars)

When to Use Factory Method

  • You don’t know ahead of time which exact class you need to create
  • You want subclasses to specify the objects they create
  • Object creation involves complex logic (validation, config lookup, caching) that shouldn’t live in the constructor
  • You need to return different implementations based on runtime conditions (env, config, input)
  • You want to centralize object creation so changes happen in one place

Open/Closed Principle

  • Open for extension: Add a new notification type by creating a new class and registering it
  • Closed for modification: Existing factory code and client code don’t change
  • Without a factory, adding a new type means modifying every if/elif chain that creates objects
  • With a factory, you register the new class and existing code picks it up automatically

Polymorphic Creation

  • The factory returns an object typed to the abstract base class, not the concrete implementation
  • Client code calls methods on the interface — it never knows (or cares) which concrete class it got
  • This enables swapping implementations without touching client code (e.g., switch from email to SMS)
  • In Python, use ABC and @abstractmethod to enforce the contract

Python Implementations

from abc import ABC, abstractmethod
from typing import Dict, Type


# ═══════════════════════════════════════════════════
# EXAMPLE 1: Notification Factory
# ═══════════════════════════════════════════════════

class Notification(ABC):
    """Abstract base — all notifications must implement send()."""

    @abstractmethod
    def send(self, recipient: str, message: str) -> str:
        ...


class EmailNotification(Notification):
    def send(self, recipient: str, message: str) -> str:
        return f"📧 Email to {recipient}: {message}"


class SMSNotification(Notification):
    def send(self, recipient: str, message: str) -> str:
        return f"📱 SMS to {recipient}: {message}"


class PushNotification(Notification):
    def send(self, recipient: str, message: str) -> str:
        return f"🔔 Push to {recipient}: {message}"


class SlackNotification(Notification):
    def send(self, recipient: str, message: str) -> str:
        return f"💬 Slack to #{recipient}: {message}"


# Simple Factory: dict-based registry (Pythonic approach)
class NotificationFactory:
    """Registry-based factory — Open/Closed compliant."""
    _registry: Dict[str, Type[Notification]] = {}

    @classmethod
    def register(cls, channel: str, notification_cls: Type[Notification]):
        cls._registry[channel] = notification_cls

    @classmethod
    def create(cls, channel: str) -> Notification:
        if channel not in cls._registry:
            raise ValueError(f"Unknown channel: {channel}")
        return cls._registry[channel]()

    @classmethod
    def available(cls) -> list:
        return list(cls._registry.keys())


# Register notification types
NotificationFactory.register("email", EmailNotification)
NotificationFactory.register("sms", SMSNotification)
NotificationFactory.register("push", PushNotification)
NotificationFactory.register("slack", SlackNotification)


# ═══════════════════════════════════════════════════
# EXAMPLE 2: Database Connector Factory (Factory Method)
# ═══════════════════════════════════════════════════

class DatabaseConnector(ABC):
    """Abstract base for database connections."""

    @abstractmethod
    def connect(self, host: str, port: int) -> str:
        ...

    @abstractmethod
    def execute(self, query: str) -> str:
        ...


class PostgresConnector(DatabaseConnector):
    def connect(self, host: str, port: int = 5432) -> str:
        return f"Connected to PostgreSQL @ {host}:{port}"

    def execute(self, query: str) -> str:
        return f"[PG] Executing: {query}"


class MySQLConnector(DatabaseConnector):
    def connect(self, host: str, port: int = 3306) -> str:
        return f"Connected to MySQL @ {host}:{port}"

    def execute(self, query: str) -> str:
        return f"[MySQL] Executing: {query}"


class SQLiteConnector(DatabaseConnector):
    def connect(self, host: str = ":memory:", port: int = 0) -> str:
        return f"Connected to SQLite @ {host}"

    def execute(self, query: str) -> str:
        return f"[SQLite] Executing: {query}"


# Factory Method pattern using ABC
class DatabaseFactory(ABC):
    """Abstract creator — subclasses override create_connector()."""

    @abstractmethod
    def create_connector(self) -> DatabaseConnector:
        ...

    def get_connection(self, host: str, port: int) -> str:
        """Template method — uses the factory method internally."""
        connector = self.create_connector()
        return connector.connect(host, port)


class PostgresFactory(DatabaseFactory):
    def create_connector(self) -> DatabaseConnector:
        return PostgresConnector()


class MySQLFactory(DatabaseFactory):
    def create_connector(self) -> DatabaseConnector:
        return MySQLConnector()


# ═══════════════════════════════════════════════════
# EXAMPLE 3: Auto-registering factory with decorator
# ═══════════════════════════════════════════════════

class SerializerFactory:
    """Factory with decorator-based registration."""
    _formats: Dict[str, Type] = {}

    @classmethod
    def register(cls, format_name: str):
        """Decorator to auto-register serializer classes."""
        def decorator(serializer_cls):
            cls._formats[format_name] = serializer_cls
            return serializer_cls
        return decorator

    @classmethod
    def create(cls, format_name: str):
        if format_name not in cls._formats:
            raise ValueError(f"Unknown format: {format_name}")
        return cls._formats[format_name]()


@SerializerFactory.register("json")
class JSONSerializer:
    def serialize(self, data) -> str:
        return f"{{JSON: {data}}}"


@SerializerFactory.register("xml")
class XMLSerializer:
    def serialize(self, data) -> str:
        return f"<data>{data}</data>"


@SerializerFactory.register("yaml")
class YAMLSerializer:
    def serialize(self, data) -> str:
        return f"data: {data}"


# ═══════════════════════════════════════════════════
# Demo: Using the factories
# ═══════════════════════════════════════════════════

print("=== Factory Method Pattern ===")
print()

# Notification factory
print("--- Notification Factory ---")
for channel in NotificationFactory.available():
    notif = NotificationFactory.create(channel)
    print(f"  {notif.send('alice', 'Hello!')}")
print()

# Database factory method
print("--- Database Factory Method ---")
pg_factory = PostgresFactory()
mysql_factory = MySQLFactory()

print(f"  {pg_factory.get_connection('db.prod', 5432)}")
print(f"  {mysql_factory.get_connection('db.legacy', 3306)}")
print()

# Serializer factory with decorator registration
print("--- Serializer Factory ---")
for fmt in ["json", "xml", "yaml"]:
    serializer = SerializerFactory.create(fmt)
    print(f"  {fmt}: {serializer.serialize({'name': 'Alice'})}")
print()

# Adding a new type WITHOUT modifying existing code
print("--- Open/Closed in Action ---")

@SerializerFactory.register("csv")
class CSVSerializer:
    def serialize(self, data) -> str:
        return f"name,{data.get('name', '')}"

csv_s = SerializerFactory.create("csv")
print(f"  New format: {csv_s.serialize({'name': 'Bob'})}")
print("  (Added without modifying any existing class!)")

🏭 Industry Practice

Django Form Fields: Django uses factory-like patterns throughout — models.CharField(), models.IntegerField() etc. create appropriate form widgets and validators without you knowing the internals. The formfield() method on model fields is a textbook Factory Method — each field type overrides it to produce the correct form field.

SQLAlchemy create_engine: create_engine("postgresql://...") is a factory function that examines the URL scheme and returns the appropriate dialect/driver combination. You pass a connection string and get back an engine without knowing whether it’s psycopg2, asyncpg, or mysqlclient under the hood.

React.createElement: In React, createElement(type, props, children) is a factory that produces different virtual DOM nodes based on the type argument. Whether it’s a string (HTML element) or a component class, the same factory handles creation polymorphically.

Java Collections: Collections.unmodifiableList(), List.of(), Map.of() are factory methods that return optimized implementations without exposing their concrete classes. The implementation can change between Java versions without breaking client code.

📋 Key Takeaways

  • Factory Method decouples object creation from usage — client code depends on abstractions, not concrete classes
  • Use it when you need to create objects polymorphically based on runtime conditions
  • In Python, a registry dict + ABC is the most idiomatic Factory Method implementation
  • The pattern follows Open/Closed — add new types by registering them, not modifying existing code
  • Simple Factory (if/else) works fine for a small, stable set of types — don’t over-engineer
  • Abstract Factory is for when you need to create families of related objects together

🧠 Mental Model

Think of a vending machine. You press button A5 (the request), and the machine (the factory) figures out which item to drop. You never reach inside to grab it yourself — the machine handles the “creation” and just gives you the product through the slot.

⚠️ Common Mistakes

  • Over-engineering with factories for 2 types: If you only have EmailNotification and SMSNotification and no plans to add more, a simple if/else is fine. Factory Method adds indirection — it’s only worth the cost when the type set is expected to grow or change.
  • Forgetting to enforce the interface: If your factory returns objects that don’t share a common interface (ABC), client code can’t treat them polymorphically. Always define an abstract base class with the expected methods — this catches missing method implementations at class definition time, not at runtime.
  • Putting business logic in the factory: The factory’s job is only to create the right object. It should not validate input, send emails, or do work. If your factory has 50 lines of logic, it’s doing too much — move that logic into the product classes or a separate service.
  • Confusing Factory Method with Abstract Factory: Factory Method creates one product via inheritance (subclass overrides a create method). Abstract Factory creates families of products via composition (a factory object with multiple create methods). Using Abstract Factory when you only need one product type adds unnecessary complexity.

🎯 Exercises

  1. Build a payment gateway factory: Create an abstract PaymentProcessor with charge(amount) and refund(transaction_id). Implement StripeProcessor, PayPalProcessor, and SquareProcessor. Build a registry-based factory that creates the right processor from a config string. Write tests that verify all processors share the same interface.
  2. Decorator-based auto-registration: Implement a @register("type_name") decorator that automatically adds classes to the factory registry at import time. Create a plugin system where new serializer formats (JSON, XML, CSV, Protobuf) are registered simply by decorating the class. Verify that adding a new format requires zero changes to existing code.
  3. Factory with dependency injection: Build a LoggerFactory that creates loggers configured differently based on environment (dev → console logger, prod → file logger, test → null logger). The factory should accept the environment as a constructor parameter. Write tests that verify each environment produces the correct logger type without touching real files.
  4. Abstract Factory for UI components: Create an abstract factory that produces Button, Checkbox, and TextField objects. Implement MaterialUIFactory and BootstrapFactory, each returning themed components. Write client code that renders a form using whichever factory is injected — proving the client is fully decoupled from the concrete UI library.
