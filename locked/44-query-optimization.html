Intermediate Database Concept

Query Optimization

Understanding how the database query planner transforms your SQL into an efficient execution plan — choosing between index scans, join algorithms, and access paths to return results in the fewest possible I/O operations.

💡 Real-World Analogy

Think of the query planner as a GPS navigation system. You type in a destination (your SQL query), and the GPS evaluates multiple possible routes — highway vs side streets, toll roads vs free roads, current traffic conditions. It doesn’t blindly follow one path; it estimates the cost of each route (time, distance, fuel) and picks the cheapest. Similarly, the query planner evaluates dozens of execution strategies, estimates their I/O and CPU costs using table statistics, and picks the plan with the lowest estimated total cost.

How the Query Planner Works

When you execute a SQL statement, the database doesn’t run it literally. It goes through a multi-stage pipeline:

  • Parsing: SQL text → abstract syntax tree (AST). Validates syntax and object references.
  • Rewriting: Applies view expansion, rule-based transformations, and subquery flattening.
  • Planning/Optimization: Generates candidate execution plans, estimates costs, selects cheapest plan.
  • Execution: Runs the chosen plan using the query executor engine.

Cost-Based Optimization

Modern databases use cost-based optimizers (CBO) that rely on statistics about your data:

  • Table statistics: Row count, page count, average row width
  • Column statistics: Number of distinct values (n_distinct), most common values, histograms
  • Index statistics: Index size, correlation (physical order vs logical order)
  • Cost parameters: seq_page_cost, random_page_cost, cpu_tuple_cost, cpu_index_tuple_cost

EXPLAIN & EXPLAIN ANALYZE

EXPLAIN shows the planned execution without running the query. EXPLAIN ANALYZE actually executes it and shows real timing:

-- EXPLAIN: shows the plan WITHOUT executing
EXPLAIN SELECT * FROM orders
WHERE customer_id = 42 AND total > 100;

-- Output:
-- Index Scan using idx_orders_customer on orders
--   Index Cond: (customer_id = 42)
--   Filter: (total > 100)
--   Rows Removed by Filter: 3
--   (cost=0.43..8.50 rows=5 width=48)

-- EXPLAIN ANALYZE: executes and shows REAL timings
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders
WHERE customer_id = 42 AND total > 100;

-- Output:
-- Index Scan using idx_orders_customer on orders
--   Index Cond: (customer_id = 42)
--   Filter: (total > 100)
--   Rows Removed by Filter: 3
--   Buffers: shared hit=4
--   (actual time=0.025..0.031 rows=5 loops=1)
-- Planning Time: 0.102 ms
-- Execution Time: 0.048 ms

Scan Types: Index Scan vs Sequential Scan

Scan Type When Used Cost Characteristics
Sequential Scan No usable index, or selecting large % of table Reads every page sequentially — cheap per-page I/O
Index Scan Selective filter with matching index Random I/O to fetch heap tuples — expensive per-page
Index Only Scan Covering index has all needed columns No heap access — fastest for covered queries
Bitmap Index Scan Moderate selectivity, or combining multiple indexes Builds bitmap, then fetches pages in order

Join Algorithms

When your query joins multiple tables, the planner picks one of three algorithms based on data size and available indexes:

Algorithm Best For Complexity Needs Index?
Nested Loop Small outer table, indexed inner table O(n × m) worst, O(n × log m) with index Benefits greatly
Hash Join Large tables, equality joins, no useful index O(n + m) with memory for hash table No
Merge Join Pre-sorted inputs (from index), large datasets O(n log n + m log m) or O(n + m) if pre-sorted Optional (pre-sorted helps)

The N+1 Query Problem

The most common performance killer in application code — executing one query per item instead of one query for all items:

# ❌ N+1 Problem: 1 query for orders + N queries for customers
def get_order_details_slow(db):
    """Executes 1 + N queries — catastrophic at scale."""
    orders = db.execute("SELECT * FROM orders LIMIT 100").fetchall()

    results = []
    for order in orders:
        # Each iteration fires a separate query!
        customer = db.execute(
            "SELECT name, email FROM customers WHERE id = %s",
            (order["customer_id"],)
        ).fetchone()
        results.append({"order": order, "customer": customer})

    return results  # 101 total queries!


# ✅ Fixed: Single JOIN query replaces N+1
def get_order_details_fast(db):
    """Single query with JOIN — constant regardless of row count."""
    return db.execute("""
        SELECT o.*, c.name, c.email
        FROM orders o
        JOIN customers c ON c.id = o.customer_id
        LIMIT 100
    """).fetchall()  # 1 query total!


# ✅ Alternative: Batch IN query (when JOIN isn't practical)
def get_order_details_batch(db):
    """Two queries instead of N+1 — still much better."""
    orders = db.execute("SELECT * FROM orders LIMIT 100").fetchall()

    customer_ids = [o["customer_id"] for o in orders]
    placeholders = ",".join(["%s"] * len(customer_ids))
    customers = db.execute(
        f"SELECT * FROM customers WHERE id IN ({placeholders})",
        customer_ids
    ).fetchall()  # 2 queries total!

    customer_map = {c["id"]: c for c in customers}
    return [
        {"order": o, "customer": customer_map.get(o["customer_id"])}
        for o in orders
    ]

Query Rewriting Techniques

The optimizer and experienced developers apply transformations that produce equivalent results with better performance:

-- ❌ SLOW: Correlated subquery (runs per row)
SELECT * FROM orders o
WHERE o.total > (
    SELECT AVG(total) FROM orders
    WHERE customer_id = o.customer_id
);

-- ✅ FAST: Rewrite as JOIN with pre-computed aggregate
SELECT o.* FROM orders o
JOIN (
    SELECT customer_id, AVG(total) AS avg_total
    FROM orders
    GROUP BY customer_id
) agg ON agg.customer_id = o.customer_id
WHERE o.total > agg.avg_total;

-- ❌ SLOW: Function on indexed column prevents index use
SELECT * FROM users
WHERE YEAR(created_at) = 2024;

-- ✅ FAST: Rewrite as range scan (index-friendly)
SELECT * FROM users
WHERE created_at >= '2024-01-01'
  AND created_at < '2025-01-01';

-- ❌ SLOW: OR conditions often prevent index use
SELECT * FROM products
WHERE category = 'electronics' OR price < 10;

-- ✅ FAST: UNION ALL with separate indexed lookups
SELECT * FROM products WHERE category = 'electronics'
UNION ALL
SELECT * FROM products WHERE price < 10
  AND category != 'electronics';

Python Demo: Query Plan Analysis

import time
from dataclasses import dataclass
from typing import List, Dict, Any
from enum import Enum


class ScanType(Enum):
    SEQ_SCAN = "Seq Scan"
    INDEX_SCAN = "Index Scan"
    INDEX_ONLY_SCAN = "Index Only Scan"
    BITMAP_SCAN = "Bitmap Index Scan"


class JoinType(Enum):
    NESTED_LOOP = "Nested Loop"
    HASH_JOIN = "Hash Join"
    MERGE_JOIN = "Merge Join"


@dataclass
class QueryPlan:
    scan_type: ScanType
    join_type: JoinType = None
    estimated_cost: float = 0.0
    estimated_rows: int = 0
    index_used: str = None
    notes: List[str] = None


class SimpleQueryOptimizer:
    """Simulates cost-based query optimization decisions.

    Demonstrates how a planner chooses between scan types
    based on selectivity and available indexes.
    """

    def __init__(self, table_rows: int, page_size: int = 8192):
        self.table_rows = table_rows
        self.page_size = page_size
        self.row_width = 100  # bytes per row
        self.rows_per_page = page_size // self.row_width
        self.total_pages = table_rows // self.rows_per_page + 1

        # PostgreSQL-style cost parameters
        self.seq_page_cost = 1.0
        self.random_page_cost = 4.0
        self.cpu_tuple_cost = 0.01
        self.cpu_index_tuple_cost = 0.005

    def estimate_seq_scan_cost(self) -> float:
        """Cost of reading every page sequentially."""
        io_cost = self.total_pages * self.seq_page_cost
        cpu_cost = self.table_rows * self.cpu_tuple_cost
        return io_cost + cpu_cost

    def estimate_index_scan_cost(self, selectivity: float) -> float:
        """Cost of index lookup + random heap fetches."""
        rows_returned = int(self.table_rows * selectivity)
        # Each row requires a random page read (worst case)
        io_cost = rows_returned * self.random_page_cost
        cpu_cost = rows_returned * self.cpu_index_tuple_cost
        return io_cost + cpu_cost

    def choose_plan(self, selectivity: float, has_index: bool) -> QueryPlan:
        """Decide between seq scan and index scan based on cost."""
        seq_cost = self.estimate_seq_scan_cost()
        notes = [f"Table: {self.table_rows:,} rows, {self.total_pages:,} pages"]
        notes.append(f"Selectivity: {selectivity:.4f} ({int(self.table_rows * selectivity):,} rows expected)")
        notes.append(f"Seq Scan cost: {seq_cost:,.1f}")

        if not has_index:
            notes.append("No index available → forced Seq Scan")
            return QueryPlan(
                scan_type=ScanType.SEQ_SCAN,
                estimated_cost=seq_cost,
                estimated_rows=int(self.table_rows * selectivity),
                notes=notes
            )

        idx_cost = self.estimate_index_scan_cost(selectivity)
        notes.append(f"Index Scan cost: {idx_cost:,.1f}")

        # Planner picks the cheaper option
        if idx_cost < seq_cost:
            notes.append("✅ Index Scan wins (fewer random reads than full scan)")
            return QueryPlan(
                scan_type=ScanType.INDEX_SCAN,
                estimated_cost=idx_cost,
                estimated_rows=int(self.table_rows * selectivity),
                index_used="idx_column",
                notes=notes
            )
        else:
            notes.append("❌ Seq Scan wins (too many rows → random I/O too expensive)")
            return QueryPlan(
                scan_type=ScanType.SEQ_SCAN,
                estimated_cost=seq_cost,
                estimated_rows=int(self.table_rows * selectivity),
                notes=notes
            )


# --- Demo: Watch the optimizer choose plans ---

optimizer = SimpleQueryOptimizer(table_rows=1_000_000)

print("=== Query Optimizer: Scan Type Selection ===")
print(f"Table: 1,000,000 rows\n")

test_cases = [
    (0.0001, True,  "WHERE id = 42 (unique lookup)"),
    (0.001,  True,  "WHERE status = 'vip' (0.1% of rows)"),
    (0.05,   True,  "WHERE city = 'NYC' (5% of rows)"),
    (0.30,   True,  "WHERE status = 'active' (30% of rows)"),
    (0.80,   True,  "WHERE created_at > '2020-01-01' (80%)"),
    (0.001,  False, "WHERE email LIKE '%@gmail%' (no index)"),
]

for selectivity, has_index, description in test_cases:
    plan = optimizer.choose_plan(selectivity, has_index)
    print(f"Query: {description}")
    print(f"  Plan: {plan.scan_type.value}")
    print(f"  Cost: {plan.estimated_cost:,.1f}")
    print(f"  Rows: {plan.estimated_rows:,}")
    for note in plan.notes[-1:]:
        print(f"  → {note}")
    print()

🏭 Industry Practice

PostgreSQL Query Planner: Uses a genetic query optimizer (GEQO) for joins of 12+ tables. The planner considers partial indexes, expression indexes, and parameterized paths. Run EXPLAIN (ANALYZE, BUFFERS, WAL) for full visibility. Keep random_page_cost lower (1.1–2.0) for SSDs vs HDDs (default 4.0).

MySQL Optimizer Hints: MySQL 8.0+ supports optimizer hints like /*+ INDEX(table idx_name) */, /*+ NO_INDEX_MERGE() */, and /*+ HASH_JOIN(t1, t2) */ to override the planner when you know better. Use sparingly — hints become stale as data changes.

Query Plan Caching: PostgreSQL caches plans for prepared statements after 5 executions (custom_plan_cost > generic_plan_cost). This avoids repeated planning overhead but can choose suboptimal generic plans. Monitor with pg_prepared_statements view.

Query Performance Monitoring: Use pg_stat_statements (PostgreSQL), Performance Schema (MySQL), or Query Store (SQL Server) to identify your top-10 slowest queries by total time, calls, and mean execution time. Focus optimization effort on queries that consume the most total resources.

📋 Key Takeaways

  • The query planner is a cost-based optimizer that evaluates multiple execution plans and picks the cheapest
  • EXPLAIN ANALYZE is your primary debugging tool — always check actual vs estimated rows
  • Index scans are only faster when selectivity is high (few rows returned relative to table size)
  • Join algorithm choice depends on table sizes, sort order, and available memory
  • The N+1 problem is the #1 performance killer in application code — fix with JOINs or batch queries
  • Never apply functions to indexed columns in WHERE clauses — rewrite as range predicates

The query optimizer is a GPS routing engine for your data. It evaluates all possible access paths, estimates cost using statistics about road conditions (data distribution), and picks the fastest route to your result set.

⚠️ Common Mistakes

  • Applying functions to indexed columns: Writing WHERE LOWER(email) = 'foo@bar.com' or WHERE YEAR(created_at) = 2024 prevents index usage because the planner cannot map the function output back to the index’s sort order. Use expression indexes or rewrite as range predicates.
  • Ignoring stale statistics: If you bulk-load data without running ANALYZE, the planner uses outdated row counts and cardinality estimates, often choosing catastrophically wrong plans (like a seq scan on a billion-row table). Auto-vacuum handles this in PostgreSQL, but after large loads, run ANALYZE manually.
  • Over-relying on EXPLAIN without ANALYZE: EXPLAIN alone shows estimated rows. The actual rows (from EXPLAIN ANALYZE) may differ by orders of magnitude when statistics are stale or data is skewed. Always compare estimates vs actuals to spot planner misestimates.
  • Premature optimization without measurement: Adding indexes “just in case” without profiling actual slow queries. Every index slows writes and consumes storage. Use pg_stat_statements or slow query logs to identify the actual top-10 worst queries before optimizing.

🎯 Exercises

  1. EXPLAIN comparison: Create a table with 1M rows. Write the same logical query three ways (subquery, JOIN, EXISTS) and compare their EXPLAIN ANALYZE outputs. Document which approach the planner converts them to internally.
  2. Tipping point experiment: With an indexed column containing 100 distinct values, measure at what selectivity percentage the planner switches from index scan to sequential scan. Vary random_page_cost and observe the threshold shift.
  3. N+1 detection: Instrument your ORM queries with logging. Find an N+1 pattern in your codebase, measure total query time, then fix with eager loading or a JOIN. Document the before/after query counts and latency.
  4. Join algorithm forcing: Write a query joining 3 tables. Use SET enable_hashjoin = off and SET enable_mergejoin = off to force different join strategies. Compare costs and understand when each algorithm wins.
