System Design/ Quorum Reads/Writes

Quorum Reads/Writes

Using voting across replicas so you can balance consistency, latency, and fault tolerance. The W + R > N rule that makes distributed databases work.

Advanced Distributed Concept
🏠 Daily-Life Analogy: Asking Multiple Witnesses

A crime happened. There are 5 witnesses. To determine what really happened, you don't need ALL 5 to agree — you just need a majority.

If 3 out of 5 witnesses say "the car was red," you're confident it was red. Even if 2 witnesses were confused or lying, the majority tells you the truth.

That's a quorum — getting enough "votes" (confirmations from replicas) to be confident your data is correct.

What Is a Quorum?

In a replicated system with N nodes, a quorum is the minimum number of nodes that must participate in a read or write for the operation to be considered valid.

The Magic Formula: W + R > N

VariableMeaningExample (N=3)
NTotal number of replicas3 copies of data
WWrite quorum — nodes that must ACK a writeW=2: write to at least 2 nodes
RRead quorum — nodes to read fromR=2: read from at least 2 nodes
Rule: If W + R > N, then reads are guaranteed to see the latest write. This is because at least one node in the read set must have the latest write (the sets overlap). 
class QuorumStore:
    """Distributed store with configurable quorum"""

    def __init__(self, n=3, w=2, r=2):
        self.n = n   # Total replicas
        self.w = w   # Write quorum
        self.r = r   # Read quorum
        self.replicas = [{} for _ in range(n)]
        self.version = 0
        assert w + r > n, "Quorum condition not met!"

    def write(self, key, value):
        """Write to W replicas"""
        self.version += 1
        acks = 0
        for i, replica in enumerate(self.replicas):
            replica[key] = {"value": value, "version": self.version}
            acks += 1
            if acks >= self.w:
                return f"OK (written to {acks}/{self.n}, v{self.version})"
        return "FAILED"

    def read(self, key):
        """Read from R replicas, return latest version"""
        responses = []
        for i in range(self.r):
            if key in self.replicas[i]:
                responses.append(self.replicas[i][key])
        if not responses:
            return None
        latest = max(responses, key=lambda x: x["version"])
        return latest["value"]

# Strong consistency: W=2, R=2, N=3 (2+2=4 > 3)
store = QuorumStore(n=3, w=2, r=2)
store.write("user:1", "Alice")
print(store.read("user:1"))  # "Alice" - guaranteed fresh

Sloppy Quorum & Hinted Handoff

In a strict quorum, reads/writes must go to the designated nodes for that key. In a sloppy quorum, if a designated node is down, another node temporarily accepts the write.

class SloppyQuorum:
    def write_with_hinted_handoff(self, key, value, designated, all_nodes):
        acks = 0
        hints = []

        for node in designated:
            if node.is_alive():
                node.write(key, value)
                acks += 1
            else:
                # Node down! Use a substitute with a "hint"
                substitute = self.find_available(all_nodes, designated)
                substitute.write_hint(key, value, intended_for=node)
                hints.append((substitute, node))
                acks += 1

        # Later: when original node recovers,
        # substitute forwards the hinted data
        return acks >= self.w

Read Repair

During a quorum read, if some replicas have stale data, the reader can repair them:

def read_with_repair(self, key):
    responses = []
    for replica in self.replicas[:self.r]:
        responses.append((replica, replica.read(key)))

    # Find the latest version
    latest = max(responses, key=lambda x: x[1]["version"])

    # Repair stale replicas in background
    for replica, data in responses:
        if data["version"] < latest[1]["version"]:
            replica.write(key, latest[1])  # Fix stale replica

    return latest[1]["value"]

Real-World Quorum Usage

  • Cassandra — Fully configurable: ONE, QUORUM, ALL, LOCAL_QUORUM per query
  • DynamoDB — Eventually consistent reads (R=1) or strongly consistent (R=quorum)
  • Riak — Configurable N, W, R per bucket. Default: N=3, W=2, R=2
  • Consul — Uses Raft quorum (majority) for KV store writes

📝 Summary

  • Quorum = minimum nodes that must participate for an operation to succeed
  • W + R > N guarantees strong consistency (read/write sets overlap)
  • Tune W and R to trade off read speed vs write speed vs fault tolerance
  • Sloppy quorum: use substitute nodes when designated ones are down
  • Read repair: fix stale replicas during reads (background healing)

🧠 Mental Model

N=3, W=2, R=2: Write "x=5" (need W=2 acks): [Node A] ← write "x=5" ACK [Node B] ← write "x=5" ACK → W=2 met! [Node C] ← (slow, hasn't received yet) Read "x" (need R=2): [Node A] → "x=5, v2" [Node B] → "x=5, v2" → R=2 met! Overlap guarantees freshness!

❌ Common Beginner Mistakes

  • Setting W=1, R=1 — Violates W+R>N. No consistency guarantee.
  • Confusing quorum with consensus — Quorum is simpler (counting acks). Consensus (Raft/Paxos) gives stronger ordering.
  • Forgetting sloppy quorum limits — Writes to non-designated nodes can violate consistency.
  • Not considering tail latency — W=3 means waiting for the slowest of 3 nodes.

  2. Simulate node failure: show W=2, R=2, N=3 works with 1 failure but fails with 2.
  3. Implement read repair: write different versions to replicas, do a quorum read, verify stale replicas get updated.
