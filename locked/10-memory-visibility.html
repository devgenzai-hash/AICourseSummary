System Design/ Memory Visibility

Memory Visibility

Why changes made by one thread may be INVISIBLE to another — even after they happen. The most surprising aspect of modern CPU architecture.

Intermediate Concept Code
Drafts vs Published Documents

Imagine each person has a personal notebook (CPU cache) and there is one shared whiteboard (main memory).

  • When you write, you write in your notebook first (fast)
  • The whiteboard is only updated later (when the system decides to sync)
  • Your colleague reads the whiteboard — they see the OLD value because your notebook has not been synced yet!

This is memory visibility. Your thread wrote the value, but other threads cannot see it yet because it is still in your CPU's cache.

Why Can't Other Threads See My Writes?

Modern CPUs have multiple levels of cache (L1, L2, L3). Each core has its own L1/L2 cache. When a thread writes a value, it goes to the local cache first — NOT to main memory immediately.

The Visibility Problem Demonstrated

import threading, time

# This can loop FOREVER in languages without a memory model (C/C++ without volatile)
# Python's GIL mostly prevents this, but the concept is critical for system design

running = True  # Shared flag

def worker():
    count = 0
    while running:  # May never see running=False without memory barrier!
        count += 1
    print(f"Worker did {count} iterations")

def stopper():
    global running
    time.sleep(1)
    running = False  # Written to local cache — when does worker see it?

t1 = threading.Thread(target=worker)
t2 = threading.Thread(target=stopper)
t1.start(); t2.start()
t1.join(); t2.join()

Memory Barriers (Fences)

A memory barrier forces the CPU to sync its cache with main memory:

  • Store barrier: flush writes from cache to memory (make visible)
  • Load barrier: refresh reads from memory (see latest)
  • Full barrier: both — all writes visible AND all reads fresh
# In Python, locks act as memory barriers
lock = threading.Lock()
shared_value = 0

def writer():
    global shared_value
    with lock:  # Release = store barrier (flushes writes)
        shared_value = 42

def reader():
    with lock:  # Acquire = load barrier (refreshes reads)
        print(shared_value)  # Guaranteed to see 42 after writer releases

CPU Reordering

CPUs Reorder Instructions!

CPUs can execute instructions out of order for performance. Thread A writes x=1 then y=2. Thread B might see y=2 but x=0! Memory barriers prevent this reordering.

Industry Impact

  • Java volatile — Forces reads/writes through main memory with barriers
  • C++ std::atomic — Provides memory_order options (relaxed, acquire, release, seq_cst)
  • Linux kernel — mb(), rmb(), wmb() macros for explicit barriers
  • ARM vs x86 — ARM has weaker memory model (more reordering) than x86

📝 Summary

  • Each CPU core has its own cache — writes may not be immediately visible to other cores
  • Memory barriers force cache synchronization between cores
  • Locks provide implicit memory barriers (acquire = load barrier, release = store barrier)
  • CPUs reorder instructions for performance — barriers prevent this
  • Python's GIL provides some protection, but the concept matters for system design
  • Different architectures (ARM vs x86) have different memory ordering guarantees

🧠 Mental Model

Core 1 Cache: [x=42] ← written here first Main Memory: [x=0] ← stale! Core 2 Cache: [x=0] ← reads stale value After MEMORY BARRIER on Core 1: Main Memory: [x=42] ← flushed! After LOAD BARRIER on Core 2: Core 2 Cache: [x=42] ← refreshed!

❌ Common Beginner Mistakes

  • Assuming writes are instantly visible — They are NOT without barriers or synchronization.
  • Relying on timing — "I wrote it 1ms ago so it must be visible" — NO guarantee.
  • Ignoring reordering — x=1; y=2 may be seen as y=2; x=0 by another thread.
  • Not understanding your platform — x86 is strongly ordered, ARM is weakly ordered.

🏋 Hands-On Exercise

  1. Research: What memory ordering does your CPU architecture use? (x86 = TSO, ARM = relaxed)
  2. In Java/C++: demonstrate that a flag set by one thread is not seen by another without volatile/atomic.
  3. Show that Python locks act as memory barriers: write+release, then acquire+read.
  4. Draw the cache hierarchy of a modern multi-core CPU and trace a write through all levels.
