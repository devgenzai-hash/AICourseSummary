Intermediate Resilience Pattern

Rate Limiting

Controlling the number of requests a client can make within a time window — protecting APIs from abuse, ensuring fair usage, and preventing resource exhaustion.

💡 Real-World Analogy

Think of a bouncer at a nightclub. The club has a fire-code capacity of 200 people. The bouncer counts everyone entering — once 200 are inside, the next person in line is told “you’ll have to wait until someone leaves.” VIP guests might get a higher limit (500 entries per night vs 100 for general admission). The bouncer doesn’t care who you are after checking your tier — it’s purely about the numbers within a time window.

Rate Limiting Algorithms

There are four primary algorithms for rate limiting, each with different trade-offs:

Algorithm How It Works Burst Handling Memory Precision
Token Bucket Tokens added at fixed rate; each request consumes one Allows bursts up to bucket capacity O(1) High
Leaky Bucket Requests queued and processed at constant rate Smooths traffic; no bursts allowed O(1) High
Fixed Window Counter resets at fixed intervals (e.g., every minute) Allows 2x burst at window boundary O(1) Low
Sliding Window Weighted combination of current and previous window Prevents boundary bursts O(1) to O(n) High

Token Bucket Implementation

The most widely used algorithm. Tokens are added at a steady rate; requests consume tokens. When the bucket is empty, requests are rejected.

import time
import threading

class TokenBucket:
    """Token bucket rate limiter.

    Allows bursts up to max_tokens, refills at
    refill_rate tokens per second.
    """

    def __init__(self, max_tokens: int,
                 refill_rate: float):
        self._max_tokens = max_tokens
        self._refill_rate = refill_rate  # tokens/sec
        self._tokens = float(max_tokens)
        self._last_refill = time.monotonic()
        self._lock = threading.Lock()

    def _refill(self):
        """Add tokens based on elapsed time."""
        now = time.monotonic()
        elapsed = now - self._last_refill
        new_tokens = elapsed * self._refill_rate
        self._tokens = min(
            self._max_tokens,
            self._tokens + new_tokens
        )
        self._last_refill = now

    def consume(self, tokens: int = 1) -> bool:
        """Try to consume tokens. Returns True if allowed."""
        with self._lock:
            self._refill()
            if self._tokens >= tokens:
                self._tokens -= tokens
                return True
            return False

    @property
    def tokens_remaining(self) -> float:
        with self._lock:
            self._refill()
            return self._tokens

    def time_until_available(self) -> float:
        """Seconds until at least 1 token is available."""
        with self._lock:
            self._refill()
            if self._tokens >= 1:
                return 0.0
            deficit = 1.0 - self._tokens
            return deficit / self._refill_rate


# Example: 100 requests per minute (burst of 10)
limiter = TokenBucket(max_tokens=10, refill_rate=100/60)

for i in range(15):
    allowed = limiter.consume()
    status = "✓ allowed" if allowed else "✗ rejected"
    print(f"Request {i+1}: {status}")

Sliding Window Rate Limiter

Fixes the boundary burst problem of fixed windows by tracking individual request timestamps:

from collections import deque

class SlidingWindowRateLimiter:
    """Sliding window log rate limiter.

    Tracks exact timestamps of each request within
    the window. Most precise but uses more memory.
    """

    def __init__(self, max_requests: int,
                 window_seconds: float):
        self._max_requests = max_requests
        self._window = window_seconds
        self._requests: deque = deque()
        self._lock = threading.Lock()

    def _cleanup(self, now: float):
        """Remove requests outside the window."""
        cutoff = now - self._window
        while self._requests and self._requests[0] < cutoff:
            self._requests.popleft()

    def allow(self) -> bool:
        """Check if request is allowed under the limit."""
        with self._lock:
            now = time.monotonic()
            self._cleanup(now)
            if len(self._requests) < self._max_requests:
                self._requests.append(now)
                return True
            return False

    @property
    def remaining(self) -> int:
        with self._lock:
            self._cleanup(time.monotonic())
            return max(0, self._max_requests - len(self._requests))

    @property
    def reset_time(self) -> float:
        """Seconds until the oldest request expires."""
        with self._lock:
            if not self._requests:
                return 0.0
            oldest = self._requests[0]
            return max(0.0,
                (oldest + self._window) - time.monotonic())


# Example: 5 requests per 10-second window
window_limiter = SlidingWindowRateLimiter(
    max_requests=5, window_seconds=10.0
)

Distributed Rate Limiting with Redis

In a multi-server deployment, rate limiting must be centralized. Redis is the standard choice due to atomic operations and sub-millisecond latency:

import time

class RedisRateLimiter:
    """Distributed sliding window using Redis sorted sets.

    Each request is stored as a member with score = timestamp.
    ZREMRANGEBYSCORE removes expired entries atomically.
    """

    def __init__(self, redis_client, key_prefix: str,
                 max_requests: int, window_seconds: int):
        self._redis = redis_client
        self._prefix = key_prefix
        self._max_requests = max_requests
        self._window = window_seconds

    def _key(self, client_id: str) -> str:
        return f"{self._prefix}:{client_id}"

    def is_allowed(self, client_id: str) -> dict:
        """Check if client_id can make a request.

        Uses a Redis pipeline for atomicity:
        1. Remove entries outside the window
        2. Count remaining entries
        3. If under limit, add new entry
        4. Set TTL for automatic cleanup
        """
        key = self._key(client_id)
        now = time.time()
        window_start = now - self._window

        pipe = self._redis.pipeline()
        # Remove old entries
        pipe.zremrangebyscore(key, 0, window_start)
        # Count current entries
        pipe.zcard(key)
        results = pipe.execute()

        current_count = results[1]

        if current_count < self._max_requests:
            # Add this request
            pipe = self._redis.pipeline()
            pipe.zadd(key, {str(now): now})
            pipe.expire(key, self._window + 1)
            pipe.execute()
            return {
                "allowed": True,
                "remaining": self._max_requests - current_count - 1,
                "reset_at": now + self._window
            }

        return {
            "allowed": False,
            "remaining": 0,
            "retry_after": self._window - (now - window_start)
        }

HTTP Rate Limit Headers

APIs communicate rate limit status via standard HTTP headers:

Header Meaning Example Value
X-RateLimit-Limit Maximum requests allowed in window 100
X-RateLimit-Remaining Requests remaining in current window 67
X-RateLimit-Reset Unix timestamp when window resets 1716739200
Retry-After Seconds to wait before retrying (on 429) 30

Fixed Window Boundary Problem

The fixed window algorithm has a well-known flaw: a client can make 2x the limit at the boundary of two windows. If the limit is 100/minute and a client sends 100 requests at 0:59 and 100 at 1:00, they’ve made 200 requests in 2 seconds while staying within the per-window limit.

Time Fixed Window Count Sliding Window Count Allowed?
0:59.500 100 (window 1) 100 (last 60s) Fixed: Yes; Sliding: No
1:00.000 0 (new window!) 100 (last 60s) Fixed: Yes; Sliding: No
1:00.500 100 (window 2) 100 (last 60s) Fixed: Yes; Sliding: No

🏭 Industry Practice

Stripe API: 100 requests per second in live mode, 25 in test mode. Uses token bucket with per-key limits. Returns 429 Too Many Requests with a Retry-After header. Differentiates between read and write rate limits.

GitHub API: 5,000 requests per hour for authenticated users, 60 for unauthenticated. Uses fixed window with X-RateLimit-* headers. GraphQL API counts “points” per query complexity rather than raw request count.

Cloudflare: Offers rate limiting at the edge (CDN layer) before requests reach origin servers. Supports IP-based, path-based, and header-based rules with configurable responses (block, challenge, JS challenge).

nginx: Built-in limit_req module uses leaky bucket. Configured per-zone with burst capacity: limit_req zone=api burst=20 nodelay; allows 20 excess requests to be served immediately before enforcing the rate.

📋 Key Takeaways

  • Token bucket is the most versatile — allows controlled bursts while enforcing average rate
  • Sliding window prevents the boundary burst problem but costs more memory
  • Distributed rate limiting requires centralized state (Redis, Memcached)
  • Always return rate limit headers so clients can self-regulate
  • Differentiate limits by tier (free/paid), endpoint (/search vs /profile), and method (GET vs POST)
  • Rate limiting protects against both abuse and accidental thundering herds

🧠 Mental Model

Think of rate limiting as a water faucet with a meter. The meter counts gallons used this hour. Once you hit your allocation, the faucet shuts off until the meter resets. VIP customers get a bigger allocation. The token bucket adds a small tank (burst capacity) — you can use water quickly from the tank, but it refills slowly.

⚠️ Common Mistakes

  • Rate limiting only at the application layer: If your rate limiter runs inside your app server, a DDoS attack still saturates your network and load balancer. Apply rate limiting at the edge (CDN, API gateway, load balancer) as the first line of defense.
  • Using fixed windows without understanding boundary bursts: A “100 requests per minute” fixed window actually allows 200 requests in a 2-second span across window boundaries. Use sliding window or token bucket for accurate enforcement.
  • Not differentiating by operation cost: A GET /user and a POST /search?query=complex have vastly different server costs. Use weighted rate limiting where expensive operations consume more tokens than cheap reads.
  • Race conditions in distributed limiters: A naive “read count, check, increment” pattern in Redis allows race conditions. Always use atomic operations (Lua scripts or Redis transactions) for check-and-increment.

🎯 Exercises

  1. Implement all four algorithms: Build TokenBucket, LeakyBucket, FixedWindow, and SlidingWindow rate limiters. Benchmark each with a burst of 1000 requests and compare which ones allow boundary exploits.
  2. Build a multi-tier rate limiter: Create a limiter that enforces different rates per tier (free: 10/min, basic: 100/min, pro: 1000/min). Use a decorator that reads the user’s tier from a request context.
  3. Distributed rate limiter with Redis: Implement the Redis sorted-set pattern. Test with multiple “servers” (threads) hitting the same Redis instance and verify the global limit is respected.
  4. Rate limit HTTP middleware: Build an HTTP middleware (Flask/FastAPI) that returns proper 429 responses with X-RateLimit-* headers. Test with concurrent requests and verify headers are accurate.
