Cache Stampede

When a popular cache entry expires and dozens (or thousands) of concurrent requests all race to regenerate it simultaneously — overwhelming the database with duplicate work.

💡 Real-World Analogy

Imagine a popular restaurant with a single bathroom. While it’s occupied, a queue of 50 people forms. The moment the door opens, all 50 people rush for it at once — they shove, push, and jam the doorway. Only one person can use it at a time, but the surge itself causes chaos. A cache stampede works the same way: a hot cache key expires, and hundreds of concurrent requests all see the miss simultaneously. They all hit the database at once to regenerate the same value, creating a thundering herd that can crash the backend.

What Is Cache Stampede?

Also known as the thundering herd problem, a cache stampede occurs when:

  1. A frequently-accessed cache entry expires (or is invalidated)
  2. Many concurrent requests arrive and all see a cache miss
  3. All requests simultaneously query the database to regenerate the value
  4. The database is overwhelmed with N identical queries instead of 1
  5. Response times spike, timeouts cascade, and the system may crash

Why It Happens

  • Hot keys with fixed TTL: A key accessed 10,000 times/second expires — all 10,000 requests hit DB in the next second
  • Synchronized expiration: Many keys set with the same TTL expire at the same instant (e.g., all cached at startup)
  • Slow regeneration: If the DB query takes 500ms to rebuild the cache, 500+ requests pile up during that window
  • Cold cache after restart: A fresh cache node receives full production traffic with 0% hit rate

Solution 1: Mutex / Lock Approach

Only one request regenerates the cache; others wait for it or get a stale value:

  • On cache miss, try to acquire a lock (e.g., Redis SETNX)
  • If lock acquired → query DB, populate cache, release lock
  • If lock not acquired → wait briefly and retry (or return stale data)
  • Advantage: Database sees exactly 1 query regardless of concurrency
  • Risk: Lock holder crashes → set a TTL on the lock itself as a safety valve

Solution 2: Probabilistic Early Expiration

Instead of all requests seeing the miss at the same instant, each request has a small random chance of refreshing the cache before it actually expires:

  • Formula: should_refresh = random() < (time_since_set / ttl) * beta
  • As the entry ages, the probability of early refresh increases
  • On average, exactly one request triggers a refresh just before expiry
  • Advantage: No locks, no coordination, statistically prevents stampede
  • Trade-off: Slight increase in DB queries (occasional early refreshes)

Solution 3: Request Coalescing

Multiple concurrent requests for the same key are collapsed into a single backend call. All waiters receive the same result:

  • First request initiates the DB query and registers a “pending” future
  • Subsequent requests for the same key await the existing future (no new DB query)
  • When the first request completes, all waiters are notified with the result
  • Also known as: Single-flight, request deduplication, in-flight coalescing
  • Used by: nginx proxy_cache_lock, Go’s singleflight package

Solution 4: Cache Warming

Proactively refresh cache entries before they expire, ensuring they never actually go stale:

  • Background worker monitors hot keys and refreshes them at 80% of their TTL
  • After deployments, warm the cache from access logs before routing traffic
  • Gradual traffic ramp: new cache node gets 5% → 25% → 100% of traffic
  • Advantage: Zero stampede risk for known hot keys
  • Limitation: Only works for predictable access patterns

Solution 5: Stale-While-Revalidate

Keep serving the expired (stale) value while one request refreshes in the background:

  • Cache stores both the value AND a “soft expiry” timestamp
  • After soft expiry: serve stale data, trigger exactly one background refresh
  • After hard expiry (much later): force a synchronous refresh
  • Advantage: Zero latency impact on users, no stampede
  • Trade-off: One request cycle sees slightly stale data

Python Implementations

import time
import random
import asyncio
import threading
from typing import Any, Optional, Callable, Dict


# ═══════════════════════════════════════════════════
# SOLUTION 1: Mutex/Lock-Based Protection
# ═══════════════════════════════════════════════════

class MutexCache:
    """Cache with lock-based stampede protection.

    Only one thread regenerates a cache entry on miss.
    Others wait for the lock holder to finish.
    """

    def __init__(self, ttl: int = 300):
        self._store: Dict[str, Any] = {}
        self._expiry: Dict[str, float] = {}
        self._locks: Dict[str, threading.Lock] = {}
        self._lock_guard = threading.Lock()
        self.ttl = ttl
        self.db_queries = 0

    def _get_lock(self, key: str) -> threading.Lock:
        with self._lock_guard:
            if key not in self._locks:
                self._locks[key] = threading.Lock()
            return self._locks[key]

    def get(self, key: str, loader: Callable) -> Any:
        # Check cache first
        if key in self._store:
            if time.time() < self._expiry.get(key, 0):
                return self._store[key]  # Cache HIT

        # Cache MISS — acquire lock for this key
        lock = self._get_lock(key)
        with lock:
            # Double-check after acquiring lock
            if key in self._store:
                if time.time() < self._expiry.get(key, 0):
                    return self._store[key]

            # Only ONE thread reaches here — load from DB
            self.db_queries += 1
            value = loader()
            self._store[key] = value
            self._expiry[key] = time.time() + self.ttl
            return value


# ═══════════════════════════════════════════════════
# SOLUTION 2: Probabilistic Early Expiration
# ═══════════════════════════════════════════════════

class ProbabilisticCache:
    """Cache with probabilistic early refresh to prevent stampede.

    As entries age toward their TTL, random requests trigger
    early refresh — statistically one request refreshes just
    before the actual expiry.
    """

    def __init__(self, ttl: int = 300, beta: float = 1.0):
        self._store: Dict[str, Any] = {}
        self._expiry: Dict[str, float] = {}
        self._set_time: Dict[str, float] = {}
        self.ttl = ttl
        self.beta = beta  # Controls eagerness (higher = more early refreshes)
        self.db_queries = 0

    def _should_early_refresh(self, key: str) -> bool:
        """Probabilistic check — higher chance as entry ages."""
        if key not in self._set_time:
            return False
        age = time.time() - self._set_time[key]
        probability = (age / self.ttl) * self.beta
        return random.random() < probability

    def get(self, key: str, loader: Callable) -> Any:
        now = time.time()

        # Hard expiry — must refresh
        if key not in self._store or now > self._expiry.get(key, 0):
            self.db_queries += 1
            value = loader()
            self._store[key] = value
            self._expiry[key] = now + self.ttl
            self._set_time[key] = now
            return value

        # Probabilistic early refresh
        if self._should_early_refresh(key):
            self.db_queries += 1
            value = loader()
            self._store[key] = value
            self._expiry[key] = now + self.ttl
            self._set_time[key] = now
            return value

        return self._store[key]  # Serve cached value


# ═══════════════════════════════════════════════════
# SOLUTION 3: Request Coalescing (Single-Flight)
# ═══════════════════════════════════════════════════

class CoalescingCache:
    """Async cache with request coalescing.

    Multiple concurrent requests for the same key are collapsed
    into a single backend call. All waiters get the same result.
    """

    def __init__(self, ttl: int = 300):
        self._store: Dict[str, Any] = {}
        self._expiry: Dict[str, float] = {}
        self._in_flight: Dict[str, asyncio.Future] = {}
        self.ttl = ttl
        self.db_queries = 0

    async def get(self, key: str, loader: Callable) -> Any:
        now = time.time()

        # Cache hit
        if key in self._store and now < self._expiry.get(key, 0):
            return self._store[key]

        # Check if another request is already fetching
        if key in self._in_flight:
            # Wait for the existing request to finish
            return await self._in_flight[key]

        # First request — create a future for others to wait on
        loop = asyncio.get_event_loop()
        future = loop.create_future()
        self._in_flight[key] = future

        try:
            # Only ONE request hits the database
            self.db_queries += 1
            value = await asyncio.to_thread(loader)
            self._store[key] = value
            self._expiry[key] = time.time() + self.ttl
            future.set_result(value)
            return value
        except Exception as e:
            future.set_exception(e)
            raise
        finally:
            del self._in_flight[key]

# Demo: Mutex-based stampede protection
# ═══════════════════════════════════════════════════

print("=== Cache Stampede Protection ===")
print()

def expensive_db_query():
    """Simulates a slow database query."""
    time.sleep(0.1)  # 100ms query
    return {"product": "Widget", "price": 29.99}

# Without protection: N threads = N DB queries
print("--- Without Protection (stampede!) ---")
unprotected_queries = 0

def unprotected_fetch():
    global unprotected_queries
    unprotected_queries += 1
    expensive_db_query()

threads = [threading.Thread(target=unprotected_fetch) for _ in range(20)]
for t in threads: t.start()
for t in threads: t.join()
print(f"  20 concurrent requests → {unprotected_queries} DB queries")
print()

# With mutex protection: only 1 DB query
print("--- With Mutex Protection ---")
mutex_cache = MutexCache(ttl=60)
results = []

def protected_fetch():
    result = mutex_cache.get("product:1", expensive_db_query)
    results.append(result)

threads = [threading.Thread(target=protected_fetch) for _ in range(20)]
for t in threads: t.start()
for t in threads: t.join()
print(f"  20 concurrent requests → {mutex_cache.db_queries} DB query")
print(f"  All 20 got result: {all(r is not None for r in results)}")
print()

# Probabilistic early refresh
print("--- Probabilistic Early Expiration ---")
prob_cache = ProbabilisticCache(ttl=10, beta=2.0)
for i in range(100):
    prob_cache.get("hot_key", expensive_db_query)
print(f"  100 requests, DB queries: {prob_cache.db_queries}")
print(f"  (Early refreshes prevented a single expiry spike)")

🏭 Industry Practice

Facebook Memcached Leases: Facebook’s paper “Scaling Memcache at Facebook” introduced leases to prevent stampedes. On a cache miss, Memcached issues a lease token to the first requester. Other requests for the same key get a “wait” signal. Only the lease holder can write back to cache, preventing thundering herd at scale across billions of requests per second.

Redis SETNX for Stampede Protection: SET lock:key NX EX 10 acts as a distributed mutex. The first request that wins the SETNX loads from DB and populates cache. Others either spin-wait or return stale data. The EX 10 provides automatic lock expiry if the holder crashes.

nginx proxy_cache_lock: nginx’s reverse proxy has built-in stampede protection. When proxy_cache_lock on; is set, only the first request for an expired cache entry is forwarded to the backend. All others wait up to proxy_cache_lock_timeout for the first response to populate the cache.

📋 Key Takeaways

  • Cache stampede occurs when a hot key expires and N concurrent requests all hit the database simultaneously
  • The mutex/lock approach guarantees exactly 1 DB query but adds wait time for other requests
  • Probabilistic early expiration prevents stampedes without coordination — statistically elegant
  • Request coalescing collapses duplicate in-flight requests into a single backend call
  • Stale-while-revalidate provides zero-latency responses while refreshing in the background
  • Combine strategies: TTL jitter + probabilistic refresh + stale-while-revalidate for maximum protection

🧠 Mental Model

Cache stampede is a concurrency problem at the application layer. The solutions mirror classic concurrency patterns: mutual exclusion (locks), optimistic approaches (probabilistic), and batching (coalescing).

⚠️ Common Mistakes

  • Locks without TTL (deadlock risk): If the lock holder crashes or times out, the lock is held forever and all subsequent requests block indefinitely. Always set a TTL on the lock itself (e.g., SET lock:key NX EX 10) so it auto-expires and another request can take over.
  • Fixed TTL without jitter: Setting all cache entries to exactly the same TTL (e.g., 300 seconds) means they all expire at the same instant, causing a mass stampede. Add random jitter: ttl = base_ttl + random(0, base_ttl * 0.2) to spread expirations over time.
  • Ignoring stampede for “small” traffic: Stampede doesn’t require massive scale. Even 50 concurrent requests hitting a slow 2-second DB query creates 50 connections and 100 seconds of total DB time. At moderate traffic, a single hot key expiry during a spike can saturate your connection pool.
  • Stale-while-revalidate without a hard expiry cap: If the background refresh keeps failing silently, you serve increasingly stale data forever. Always pair stale-while-revalidate with a hard expiry (e.g., serve stale for 5 minutes max, then force a synchronous refresh or return an error).
