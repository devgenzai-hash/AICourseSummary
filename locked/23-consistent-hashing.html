System Design/ Consistent Hashing

Consistent Hashing

A clever way to distribute data across servers so that adding or removing a server only moves a tiny fraction of data — not everything.

Intermediate Concept Distributed
🏠 Daily-Life Analogy: Assigned Parking Spots in a Circle

Imagine a circular parking lot with 360 spots (numbered 0-359). There are 4 parking attendants, each responsible for a section of the circle.

When a car arrives, you look at the license plate, do a simple calculation (like summing the digits), and get a number 0-359. The car goes to whichever attendant is next clockwise from that number.

Now an attendant quits: Only the cars that were assigned to THAT attendant need to be redistributed to the next attendant clockwise. Everyone else's cars stay put!

Traditional approach (modulo): If you used "license number % 4 attendants," removing one attendant would require almost ALL cars to move. That's terrible.

Consistent hashing = the circular parking lot approach. Add/remove servers with minimal data movement.

The Problem: Why Simple Hashing Breaks

The naive approach to distributing data across N servers:

# Naive approach: modulo hashing
def get_server_naive(key, num_servers):
    return hash(key) % num_servers

# With 4 servers:
servers = ["Server-A", "Server-B", "Server-C", "Server-D"]

# key "user:123" → hash = 7 → 7 % 4 = 3 → Server-D
# key "user:456" → hash = 12 → 12 % 4 = 0 → Server-A

# NOW: Server-C dies. We have 3 servers.
# key "user:123" → hash = 7 → 7 % 3 = 1 → Server-B  ← MOVED!
# key "user:456" → hash = 12 → 12 % 3 = 0 → Server-A ← stayed (lucky)

# PROBLEM: ~75% of ALL keys move to different servers!
# With a cache, this means 75% cache misses = thundering herd = crash
The Disaster: With modulo hashing, adding or removing a single server causes ~(N-1)/N of all keys to be remapped. For 100 servers, removing 1 server moves 99% of data. In a cache system, this means instant cache stampede.

How Consistent Hashing Works

Step 1: The Hash Ring

Instead of mapping to server slots (0 to N-1), we map everything onto a circle (ring) with positions 0 to 2^32 - 1 (or any large number).

Step 2: Place Servers on the Ring

Hash each server's name/IP to get its position on the ring.

Step 3: Place Keys on the Ring

Hash each data key to get its position on the ring.

Step 4: Walk Clockwise

Each key belongs to the first server you encounter going clockwise from the key's position.

import hashlib
import bisect

class ConsistentHashRing:
    """A consistent hash ring for distributing keys across nodes."""

    def __init__(self, nodes=None, replicas=150):
        """
        Args:
            nodes: List of server names/IPs
            replicas: Virtual nodes per physical node (for balance)
        """
        self.replicas = replicas
        self.ring = []          # Sorted list of hash positions
        self.node_map = {}      # hash_position → node name

        if nodes:
            for node in nodes:
                self.add_node(node)

    def _hash(self, key):
        """Generate a consistent hash for a key (0 to 2^32 - 1)"""
        md5 = hashlib.md5(key.encode()).hexdigest()
        return int(md5, 16) % (2 ** 32)

    def add_node(self, node):
        """Add a node to the ring (with virtual nodes for balance)"""
        for i in range(self.replicas):
            # Create virtual node: "ServerA-0", "ServerA-1", etc.
            virtual_key = f"{node}-{i}"
            hash_val = self._hash(virtual_key)
            bisect.insort(self.ring, hash_val)
            self.node_map[hash_val] = node

    def remove_node(self, node):
        """Remove a node — only its keys move to the next node clockwise"""
        for i in range(self.replicas):
            virtual_key = f"{node}-{i}"
            hash_val = self._hash(virtual_key)
            self.ring.remove(hash_val)
            del self.node_map[hash_val]

    def get_node(self, key):
        """Find which node a key belongs to (walk clockwise)"""
        if not self.ring:
            return None

        hash_val = self._hash(key)

        # Find first ring position >= key's hash (clockwise)
        idx = bisect.bisect_right(self.ring, hash_val)

        # Wrap around if we passed the end of the ring
        if idx == len(self.ring):
            idx = 0

        return self.node_map[self.ring[idx]]


# Demo: Create ring with 3 servers
ring = ConsistentHashRing(["Server-A", "Server-B", "Server-C"])

# Assign keys to servers
keys = ["user:1", "user:2", "user:3", "order:100", "session:xyz"]
print("=== Before removing server ===")
for key in keys:
    print(f"  {key} → {ring.get_node(key)}")

# Remove Server-B — only ~1/3 of keys move!
ring.remove_node("Server-B")
print("\n=== After removing Server-B ===")
for key in keys:
    print(f"  {key} → {ring.get_node(key)}")

Virtual Nodes: Solving the Balance Problem

With just 3 physical servers on a ring, the distribution is often uneven — one server might get 60% of the keys while another gets only 10%. Virtual nodes fix this:

ApproachNodes on RingDistributionWhen a Server Dies
No virtual nodes3 pointsVery uneven (could be 60/30/10)All its keys go to ONE neighbor
150 virtual nodes each450 pointsNearly uniform (~33/33/33)Its keys spread across ALL remaining servers
 
# Demonstrating virtual node distribution
def test_distribution(replicas):
    ring = ConsistentHashRing(
        ["Server-A", "Server-B", "Server-C"],
        replicas=replicas
    )
    counts = {"Server-A": 0, "Server-B": 0, "Server-C": 0}

    # Assign 10,000 keys
    for i in range(10000):
        node = ring.get_node(f"key:{i}")
        counts[node] += 1

    print(f"Replicas={replicas}: {counts}")

test_distribution(1)    # Very uneven: {A: 5832, B: 1209, C: 2959}
test_distribution(50)   # Better:      {A: 3512, B: 3201, C: 3287}
test_distribution(150)  # Near-perfect: {A: 3345, B: 3318, C: 3337}

Consistent Hashing vs Modulo Hashing

FeatureModulo HashingConsistent Hashing
Add/remove server~N-1/N keys move (disaster)Only ~1/N keys move (minimal)
ImplementationSimple: hash % NMore complex: ring + binary search
Load balanceGood if hash is uniformNeeds virtual nodes for balance
Lookup speedO(1)O(log N) with binary search
Used bySimple caches, hash tablesDynamoDB, Cassandra, CDNs, load balancers

Where Consistent Hashing Is Used

Real-World Usage

  • Amazon DynamoDB — Partitions data across storage nodes using consistent hashing
  • Apache Cassandra — Ring-based architecture; each node owns a range of the hash ring
  • Akamai CDN — Routes requests to the nearest cache server using consistent hashing
  • Discord — Routes messages to the correct server/shard for each channel
  • Memcached clients — libmemcached uses ketama (consistent hashing) for cache distribution
  • Load Balancers (Nginx, HAProxy) — Sticky sessions using consistent hashing

Advanced: Weighted Nodes

Not all servers are equal. A beefy server with 64GB RAM should get more data than a small one with 8GB. Solution: give bigger servers more virtual nodes.

class WeightedConsistentHash:
    """Servers with different capacities get proportional load"""

    def __init__(self):
        self.ring = []
        self.node_map = {}

    def add_node(self, node, weight=1):
        """
        weight=1: normal server (100 virtual nodes)
        weight=2: beefy server (200 virtual nodes = gets 2x the data)
        """
        replicas = 100 * weight
        for i in range(replicas):
            hash_val = self._hash(f"{node}-{i}")
            bisect.insort(self.ring, hash_val)
            self.node_map[hash_val] = node

    def _hash(self, key):
        return int(hashlib.md5(key.encode()).hexdigest(), 16) % (2**32)

# Big server gets 2x the traffic
ring = WeightedConsistentHash()
ring.add_node("small-server-1", weight=1)   # 100 virtual nodes
ring.add_node("small-server-2", weight=1)   # 100 virtual nodes
ring.add_node("beefy-server", weight=3)    # 300 virtual nodes → 3x data
Advanced: Jump Consistent Hashing (Google's Optimization)

Google published a simpler algorithm called Jump Consistent Hash that achieves perfect balance without virtual nodes. It's faster (O(log N) with no memory overhead) but only works when nodes are numbered 0 to N-1.

def jump_consistent_hash(key, num_buckets):
    """Google's jump consistent hash — O(log N), no memory"""
    b, j = -1, 0
    while j < num_buckets:
        b = j
        key = ((key * 2862933555777941757) + 1) & 0xFFFFFFFFFFFFFFFF
        j = int((b + 1) * (1 << 31) / ((key >> 33) + 1))
    return b

# Perfectly balanced, minimal remapping on resize
# Limitation: buckets must be numbered 0..N-1 (can't name them)

📝 Summary

  • Modulo hashing (key % N) causes massive data movement when N changes
  • Consistent hashing uses a ring — adding/removing a server only moves ~1/N of keys
  • Virtual nodes (replicas) solve the imbalance problem
  • Weighted nodes let bigger servers take proportionally more data
  • Used by DynamoDB, Cassandra, CDNs, load balancers, and caching layers
  • Lookup is O(log N) via binary search on the ring

🧠 Mental Model

The Hash Ring (0 to 2^32): 0 / \ / \ ● = server position S-A S-B ○ = key position / \ | ○key1 | key1 walks clockwise → hits S-B | ○key2 | key2 walks clockwise → hits S-C \ / S-C / \ / \ / 2^32 Remove S-B: - key1 now walks clockwise → hits S-C (moved!) - key2 still hits S-C (unchanged!) - Only keys between S-A and S-B move. Everything else stays!

❌ Common Beginner Mistakes

  • Forgetting virtual nodes — Without them, 3 servers on a ring will have wildly uneven distribution.
  • Using a weak hash function — MD5/SHA are fine for distribution (not security). Don't use Python's built-in hash() — it's not consistent across runs!
  • Too few virtual nodes — 10 isn't enough. Use 100-200 per physical node for good balance.
  • Not handling replication — In practice, each key is stored on the next K nodes clockwise (for redundancy), not just one.
  • Using consistent hashing when simple modulo works — If your server count never changes, modulo is simpler and faster.
