System Design/ Partitioning & Sharding

Partitioning & Sharding

Splitting data across multiple machines so one server doesn't carry the pain of all traffic alone. The key to horizontal scaling.

Advanced Distributed Database
🏠 Daily-Life Analogy: Splitting a Library Across Buildings

Imagine a city library with 10 million books in one building. The building is overcrowded — people wait 30 minutes just to check out a book.

Solution: Split into multiple branches.

  • By genre (range-based): Fiction in Building A, Science in Building B, History in Building C
  • By author first letter (hash-based): A-F in Building A, G-M in Building B, N-Z in Building C

Each building is a shard. The system that tells you "go to Building B for that book" is the routing layer. The challenge: what if everyone wants fiction? Building A is overloaded while B and C are empty (hotspot problem).

Partitioning vs Sharding: What's the Difference?

TermMeaningExample
PartitioningGeneric term: splitting data into subsetsPostgreSQL table partitioning (same server)
ShardingPartitioning across DIFFERENT servers/machinesMongoDB sharded cluster (multiple servers)
Vertical PartitioningSplit by columns (different tables for different attributes)User profile → one table; User activity → another table
Horizontal PartitioningSplit by rows (same schema, different data subsets)Users 1-1M on Shard A, Users 1M-2M on Shard B

Sharding Strategies

1. Range-Based Sharding

Split data by ranges of the shard key. E.g., users with IDs 1-1,000,000 on Shard A, 1,000,001-2,000,000 on Shard B.

class RangeBasedSharding:
    """Route data to shards based on key ranges"""

    def __init__(self):
        # Define range boundaries
        self.shards = {
            "shard_a": (1, 1_000_000),          # Users 1 to 1M
            "shard_b": (1_000_001, 2_000_000),  # Users 1M to 2M
            "shard_c": (2_000_001, 3_000_000),  # Users 2M to 3M
        }
        self.data = {"shard_a": {}, "shard_b": {}, "shard_c": {}}

    def get_shard(self, user_id):
        """Determine which shard a user belongs to"""
        for shard_name, (low, high) in self.shards.items():
            if low <= user_id <= high:
                return shard_name
        raise ValueError(f"No shard for user_id {user_id}")

    def write(self, user_id, data):
        shard = self.get_shard(user_id)
        self.data[shard][user_id] = data
        return f"Written to {shard}"

    def read(self, user_id):
        shard = self.get_shard(user_id)
        return self.data[shard].get(user_id)

# Pro: Range scans are efficient (all nearby IDs on same shard)
# Con: HOTSPOTS! If new users have high IDs, shard_c gets all the write traffic

2. Hash-Based Sharding

Hash the shard key and distribute evenly. Eliminates hotspots but makes range queries expensive.

import hashlib

class HashBasedSharding:
    """Route data using hash of the key — even distribution"""

    def __init__(self, num_shards=4):
        self.num_shards = num_shards
        self.shards = {i: {} for i in range(num_shards)}

    def get_shard(self, key):
        """Hash the key to determine shard"""
        hash_val = int(hashlib.md5(str(key).encode()).hexdigest(), 16)
        return hash_val % self.num_shards

    def write(self, key, data):
        shard_id = self.get_shard(key)
        self.shards[shard_id][key] = data
        return f"Written to shard_{shard_id}"

    def read(self, key):
        shard_id = self.get_shard(key)
        return self.shards[shard_id].get(key)

    def range_query(self, start_key, end_key):
        """Range queries are EXPENSIVE — must query ALL shards!"""
        results = []
        for shard in self.shards.values():
            for key, value in shard.items():
                if start_key <= key <= end_key:
                    results.append((key, value))
        return results  # Had to scan ALL shards — scatter-gather!

# Pro: Even distribution, no hotspots
# Con: Range queries require scatter-gather across all shards

3. Directory-Based Sharding

A lookup table (directory) maps each key to its shard. Most flexible but adds a single point of failure (the directory).

The Hotspot Problem

Hotspot: When one shard gets disproportionately more traffic than others. Example: A celebrity's account on a social media platform — all reads/writes for their profile go to one shard. 
# Solutions to hotspots:

# 1. Add randomness to hot keys
def spread_hot_key(key, num_splits=10):
    """Split a hot key across multiple shards"""
    import random
    # Append random suffix: "celebrity:123" → "celebrity:123_7"
    suffix = random.randint(0, num_splits - 1)
    return f"{key}_{suffix}"

Cross-Shard Queries: The Pain

When a query needs data from multiple shards, you must:

  1. Send the query to ALL relevant shards (scatter)
  2. Wait for all responses
  3. Merge results locally (gather)

This is slow and expensive. Design your shard key to minimize cross-shard queries.

Resharding: When You Need More Shards

As data grows, you need to split shards. This is painful — you must move data between servers while the system is running.

  • Consistent hashing (Topic 23) minimizes data movement during resharding
  • Virtual shards: Create many more logical shards than physical servers. When you add a server, just reassign some virtual shards.

Real-World Sharding

  • MongoDB — Built-in sharding with configurable shard keys. Auto-balancer moves chunks between shards.
  • Vitess (YouTube) — Sharding middleware for MySQL. Used by YouTube, Slack, Square.
  • Instagram — Shards PostgreSQL by user ID. Each logical shard maps to a physical server.
  • Discord — Shards by guild (server) ID. Each shard handles ~1000 guilds.
  • Cassandra — Uses consistent hashing. Each node owns a range of the token ring.

📝 Summary

  • Sharding = splitting data across multiple servers for horizontal scaling
  • Range-based: good for range queries, bad for hotspots
  • Hash-based: even distribution, bad for range queries
  • Hotspots happen when one shard gets disproportionate traffic — split hot keys
  • Cross-shard queries are expensive — choose shard key carefully
  • Resharding is painful — use consistent hashing or virtual shards to minimize it

❌ Common Beginner Mistakes

  • Sharding too early — Sharding adds massive complexity. Don't shard until you've exhausted vertical scaling (bigger machine), read replicas, and caching.
  • Wrong shard key — Choosing a key that creates hotspots (like timestamp) or requires many cross-shard queries (like country for a global query).
  • Forgetting cross-shard JOINs — After sharding, JOINs between shards become application-level scatter-gather. Plan for this.
  • Not planning for resharding — If you hardcode 4 shards, growing to 8 is painful. Use consistent hashing from the start.
