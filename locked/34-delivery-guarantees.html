Delivery Guarantees

Understanding at-most-once, at-least-once, and exactly-once semantics — and why true exactly-once delivery is a distributed systems myth.

💡 Real-World Analogy

Think of three ways to send an important document. Regular mail (at-most-once): you drop it in the mailbox and hope it arrives — no confirmation, no retry. Registered mail (at-least-once): if you don’t get a delivery receipt within a week, you send another copy — the recipient might get duplicates. Courier with signature (exactly-once approximation): the courier retries until someone signs, and the recipient checks if they’ve already received this tracking number before opening it.

The Three Delivery Semantics

In any distributed messaging system, there are three fundamental guarantees about how messages are delivered between producers and consumers:

At-Most-Once

The message is sent once and never retried. It may be lost, but it will never be delivered more than once. This is the simplest and fastest approach — fire and forget.

  • No acknowledgment required from consumer
  • No retry logic needed
  • Acceptable for metrics, logs, or non-critical notifications

At-Least-Once

The message is retried until the consumer acknowledges receipt. This guarantees delivery but may result in duplicates if the acknowledgment is lost after processing.

  • Requires acknowledgment (ACK) from consumer
  • Producer retries on timeout or NACK
  • Consumer must handle duplicate messages (ideally via idempotency)

Exactly-Once (The Myth)

Each message is processed exactly one time — no loss, no duplicates. In theory, this is ideal. In practice, it’s impossible to achieve in a truly distributed system due to the Two Generals Problem. What systems actually implement is effectively-once: at-least-once delivery combined with idempotent processing.

Guarantee Message Loss Duplicates Complexity Use Case
At-Most-Once Possible Never Low Metrics, logging, real-time feeds
At-Least-Once Never Possible Medium Payments, orders, notifications
Exactly-Once Never Never Very High Financial transactions (approximated)

Message Acknowledgment Patterns

The acknowledgment mechanism is what determines the delivery guarantee:

import uuid
import time
from typing import Callable, Dict, Set
from collections import deque

class Message:
    def __init__(self, msg_id: str, payload: dict):
        self.msg_id = msg_id
        self.payload = payload
        self.attempts = 0
        self.created_at = time.time()

class AtMostOnceQueue:
    """Fire and forget — no retries, no acks."""

    def __init__(self):
        self._queue = deque()

    def publish(self, payload: dict) -> str:
        msg = Message(str(uuid.uuid4()), payload)
        self._queue.append(msg)
        return msg.msg_id

    def consume(self) -> Message:
        # Message is immediately removed — no retry possible
        return self._queue.popleft()


class AtLeastOnceQueue:
    """Retries until acknowledged. May deliver duplicates."""

    def __init__(self, max_retries: int = 5, visibility_timeout: float = 30.0):
        self._queue = deque()
        self._in_flight: Dict[str, Message] = {}
        self._max_retries = max_retries
        self._visibility_timeout = visibility_timeout

    def publish(self, payload: dict) -> str:
        msg = Message(str(uuid.uuid4()), payload)
        self._queue.append(msg)
        return msg.msg_id

    def consume(self) -> Message:
        """Get a message. It remains in-flight until ACKed."""
        msg = self._queue.popleft()
        msg.attempts += 1
        self._in_flight[msg.msg_id] = msg
        return msg

    def ack(self, msg_id: str) -> None:
        """Acknowledge successful processing."""
        self._in_flight.pop(msg_id, None)

    def nack(self, msg_id: str) -> None:
        """Negative ack — return to queue for retry."""
        msg = self._in_flight.pop(msg_id, None)
        if msg and msg.attempts < self._max_retries:
            self._queue.append(msg)

    def requeue_expired(self) -> None:
        """Return timed-out messages to the queue."""
        now = time.time()
        expired = [
            mid for mid, msg in self._in_flight.items()
            if now - msg.created_at > self._visibility_timeout
        ]
        for mid in expired:
            self.nack(mid)

Effectively-Once with Deduplication

The practical way to approximate exactly-once is combining at-least-once delivery with consumer-side deduplication:

class ExactlyOnceConsumer:
    """Approximates exactly-once via deduplication."""

    def __init__(self, queue: AtLeastOnceQueue, handler: Callable):
        self._queue = queue
        self._handler = handler
        self._processed_ids: Set[str] = set()

    def process_next(self) -> bool:
        try:
            msg = self._queue.consume()
        except IndexError:
            return False  # Queue empty

        # Deduplication check
        if msg.msg_id in self._processed_ids:
            self._queue.ack(msg.msg_id)  # ACK duplicate without processing
            return True

        try:
            self._handler(msg.payload)
            self._processed_ids.add(msg.msg_id)
            self._queue.ack(msg.msg_id)
        except Exception:
            self._queue.nack(msg.msg_id)  # Retry later

        return True


# Kafka-style offset-based consumption
class KafkaStyleConsumer:
    """Offset-based consumption with commit semantics."""

    def __init__(self):
        self._committed_offset = 0
        self._current_offset = 0

    def poll(self, messages: list) -> dict:
        """Read next message from current offset."""
        if self._current_offset >= len(messages):
            return None
        msg = messages[self._current_offset]
        self._current_offset += 1
        return msg

    def commit(self) -> None:
        """Commit current offset — marks messages as processed."""
        self._committed_offset = self._current_offset

    def reset_to_committed(self) -> None:
        """On failure, rewind to last committed offset."""
        self._current_offset = self._committed_offset

Offset Management in Kafka

Kafka’s delivery guarantee depends on when you commit offsets relative to processing:

Strategy Commit Timing Guarantee Risk
Auto-commit Periodic (before processing) At-most-once Message loss on crash
Commit after processing After handler completes At-least-once Duplicates on crash after process, before commit
Transactional Atomic with processing Effectively-once Higher latency, complexity

🏭 Industry Practice

Kafka Transactions: Kafka 0.11+ introduced idempotent producers and transactions. A producer can atomically write to multiple partitions and commit offsets in the same transaction — achieving effectively-once within the Kafka ecosystem. Outside Kafka, you still need application-level deduplication.

AWS SQS FIFO: SQS FIFO queues accept a MessageDeduplicationId. If the same dedup ID is sent within a 5-minute window, SQS discards the duplicate. Combined with exactly-once processing mode, this approximates exactly-once for many use cases.

Stripe Webhooks: Stripe sends webhooks with at-least-once semantics. They recommend storing processed event IDs and skipping duplicates — the classic deduplication pattern.

📋 Key Takeaways

  • At-most-once is fast but loses messages; at-least-once is safe but produces duplicates
  • True exactly-once delivery is impossible in distributed systems (Two Generals Problem)
  • Effectively-once = at-least-once delivery + idempotent consumer
  • Acknowledgment timing determines the guarantee: before processing → at-most-once, after → at-least-once
  • Kafka uses offset commits; RabbitMQ uses per-message ACKs; SQS uses message deletion
  • Always design consumers to handle duplicates regardless of broker guarantees

🧠 Mental Model

Think of delivery guarantees as a spectrum trading off data loss against duplicates. You can never eliminate both simultaneously in a distributed system — you choose which side to favor and compensate on the other.

     DATA LOSS ◄────────────────────► DUPLICATES
         │                                  │
    At-Most-Once                     At-Least-Once
    (fire & forget)                  (retry until ACK)
         │                                  │
         └──────────┐      ┌────────────────┘
                    ▼      ▼
              ┌──────────────────┐
              │  Exactly-Once    │
              │  (approximated)  │
              │                  │
              │  = At-Least-Once │
              │  + Deduplication │
              └──────────────────┘

⚠️ Common Mistakes

  • Assuming exactly-once from the broker alone: Even Kafka’s exactly-once only applies within Kafka. If your consumer writes to an external database, you need application-level idempotency to prevent duplicates.
  • Committing offsets before processing: Auto-commit in Kafka commits periodically regardless of processing status. A crash after commit but before processing means lost messages. Always commit after successful processing.
  • Unbounded deduplication sets: Storing every processed message ID forever consumes infinite memory. Use a time-windowed deduplication store (e.g., only keep IDs from the last hour) matched to your retry window.
  • Ignoring ordering with retries: Retrying a failed message while continuing to process subsequent messages breaks ordering. Use per-partition sequential processing or accept out-of-order delivery.

🎯 Exercises

  1. Implement all three guarantees: Build a message queue simulator that demonstrates at-most-once, at-least-once, and effectively-once delivery. Inject random failures and verify each guarantee holds.
  2. Build a deduplication layer: Create a time-windowed deduplication store backed by a dictionary with TTL. Test that duplicates within the window are rejected and messages after TTL are accepted.
  3. Simulate Kafka offset management: Implement a consumer that reads batches, processes them, and commits offsets. Simulate crashes at different points and verify which messages get reprocessed.
  4. Design a webhook receiver: Build an HTTP endpoint that receives webhooks with at-least-once delivery. Store processed event IDs in a database and return 200 for duplicates without reprocessing.
