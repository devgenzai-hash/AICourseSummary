System Design/ Thread Safety

Thread Safety

How to write code that works correctly even when multiple threads use it simultaneously. The gold standard for shared code in concurrent programs.

Beginner Concept Code
The Vending Machine

A thread-safe vending machine works perfectly even when 10 people press buttons at the same time:

  • It processes one transaction at a time internally
  • It never gives two people the same item
  • It never takes money without dispensing

A non-thread-safe vending machine might give the same soda to two people or eat your money when two people insert coins simultaneously.

What Is Thread Safety?

Code is thread-safe if it behaves correctly when accessed from multiple threads simultaneously, with no additional synchronization needed by the caller.

Levels of Thread Safety

LevelDefinitionExample
ImmutableCannot be modified after creationPython tuples, frozensets, strings
Thread-safeInternal synchronization handles everythingqueue.Queue, logging module
Conditionally safeSafe for specific operations onlyPython dict (single ops safe, compound ops not)
Not thread-safeCaller must provide synchronizationlist.append is safe, but read+modify+write is not

Strategies for Thread Safety

import threading
from queue import Queue

# Strategy 1: Immutability (safest)
class ImmutableConfig:
    def __init__(self, host, port):
        self._host = host
        self._port = port
    @property
    def host(self): return self._host
    @property
    def port(self): return self._port
    # No setters! Cannot be modified = always thread-safe

# Strategy 2: Thread-local storage (no sharing)
local_data = threading.local()

def worker():
    local_data.request_id = threading.current_thread().name
    # Each thread has its own copy — no sharing, no conflict
    print(f"My request: {local_data.request_id}")

# Strategy 3: Synchronized access (locks)
class ThreadSafeList:
    def __init__(self):
        self._items = []
        self._lock = threading.Lock()

    def append(self, item):
        with self._lock:
            self._items.append(item)

    def pop(self):
        with self._lock:
            return self._items.pop() if self._items else None

    def size(self):
        with self._lock:
            return len(self._items)

# Strategy 4: Message passing (no shared state)
def producer(q):
    for i in range(100):
        q.put(i)  # Queue handles synchronization internally

def consumer(q):
    while True:
        item = q.get()  # Blocks until item available
        if item is None: break
        process(item)

Python GIL and Thread Safety

The GIL Does NOT Make Your Code Thread-Safe!

Python's GIL prevents two threads from executing Python bytecodes simultaneously, but it does NOT make compound operations atomic. counter += 1 is still three bytecodes (LOAD, ADD, STORE) and the GIL can release between any of them.

# GIL does NOT protect this!
counter = 0
def unsafe():
    global counter
    for _ in range(100000):
        counter += 1  # LOAD_GLOBAL, then BINARY_ADD, then STORE_GLOBAL
        # GIL can switch threads between any of these!

Thread-Safe by Design

  • Go — "Don't communicate by sharing memory; share memory by communicating" (channels)
  • Rust — Ownership system prevents data races at compile time
  • Erlang/Elixir — All data is immutable, communication via message passing only
  • Java ConcurrentHashMap — Thread-safe without external synchronization

📝 Summary

  • Thread-safe code works correctly under concurrent access without caller synchronization
  • Strategies: immutability, thread-local storage, locks, message passing
  • Immutability is the safest — data that cannot change cannot race
  • Python's GIL does NOT make code thread-safe for compound operations
  • Prefer message passing (queues) over shared mutable state when possible
  • queue.Queue is Python's best friend for thread-safe communication

🧠 Mental Model

THREAD SAFETY HIERARCHY (safest to least safe): 1. IMMUTABLE -- Cannot be changed, always safe 2. THREAD-LOCAL -- Each thread owns its copy, no sharing 3. MESSAGE PASSING-- Communicate via queues, no shared state 4. SYNCHRONIZED -- Shared state + locks = safe but complex 5. UNSAFE -- Shared state + no locks = BUGS

❌ Common Beginner Mistakes

  • Relying on the GIL — GIL protects CPython internals, NOT your logic.
  • Marking a class "thread-safe" without testing — Test with 100+ concurrent threads to find races.
  • Thread-safe individual ops but unsafe compound ops — dict[key] is safe, but check-then-set is not.
  • Mixing strategies — Using both locks AND queues for the same data creates confusion.

🏋 Hands-On Exercise

  1. Create a thread-safe stack (push, pop, peek) using locks.
  2. Create the same stack using queue.LifoQueue — compare code complexity.
  3. Show that Python's list is NOT thread-safe: have threads do check-length-then-pop.
  4. Rewrite a shared-state solution to use message passing (Queue) instead.
