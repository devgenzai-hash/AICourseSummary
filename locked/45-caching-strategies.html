Caching Strategies

Patterns for storing frequently accessed data in fast storage layers — choosing between cache-aside, read-through, write-through, and write-behind strategies based on your consistency, latency, and durability requirements.

💡 Real-World Analogy

Think of caching like organizing your kitchen spices. Spices you use daily (salt, pepper, garlic) stay on the counter — instant access. Spices used weekly go in the front of the cabinet. Exotic spices used once a year sit in the back of the pantry. You don’t keep everything on the counter (limited space), and you promote items based on usage frequency. That’s exactly how caching works: hot data near the CPU/application, warm data in a cache layer, cold data on disk. The “strategy” is how you decide what goes where and when to update it.

Why Cache? The Latency Hierarchy

  • L1 CPU Cache: ~1 ns (reference from register)
  • L2 CPU Cache: ~4 ns
  • L3 CPU Cache: ~12 ns
  • RAM (main memory): ~100 ns
  • Redis/Memcached (in-memory over network): ~0.5–1 ms
  • SSD random read: ~0.1 ms
  • Database query (indexed): ~1–10 ms
  • Database query (complex join): ~50–500 ms
  • Cross-region network call: ~50–150 ms

Cache-Aside (Lazy Loading)

The application manages the cache explicitly. On read: check cache first, on miss load from DB and populate cache. On write: update DB, then invalidate/delete cache entry.

Aspect Cache-Aside
Who manages cache? Application code
Read miss penalty One extra round-trip to DB
Consistency Eventual (stale reads possible between write and invalidation)
Best for Read-heavy workloads, tolerance for brief staleness

Read-Through & Write-Through

Read-through: The cache itself loads data from the DB on a miss (cache acts as abstraction layer). Write-through: Every write goes to cache AND database synchronously before returning success.

Strategy Read Path Write Path Consistency Latency
Cache-Aside App → Cache? Miss → DB → populate cache App → DB → delete cache Eventual Low reads, low writes
Read-Through App → Cache (auto-loads from DB on miss) App → DB (cache updated on next read) Eventual Low reads after warm-up
Write-Through App → Cache (always fresh) App → Cache + DB (synchronous) Strong Higher write latency
Write-Behind App → Cache (always fresh) App → Cache (async flush to DB) Eventual Lowest write latency

Write-Behind (Write-Back)

Writes go only to the cache initially, and are flushed to the database asynchronously in batches. Offers the lowest write latency but risks data loss if the cache crashes before flushing:

  • Advantage: Absorbs write bursts, batches DB writes, reduces DB load
  • Risk: Data loss window between cache write and DB flush
  • Mitigation: Replicated cache (Redis Cluster), write-ahead log in cache, short flush intervals

TTL Strategies & Cache Hit Ratio

Time-to-live (TTL) determines when cached entries expire. The cache hit ratio = hits / (hits + misses) — aim for >95% in production:

  • Fixed TTL: Every entry expires after N seconds — simple but may cause stampedes
  • Jittered TTL: TTL + random(0, jitter) — prevents synchronized expiration
  • Sliding TTL: Resets on every access — keeps hot data alive indefinitely
  • Adaptive TTL: Longer TTL for stable data, shorter for frequently-changing data

Cache Warming

Pre-loading the cache with expected hot data before traffic hits — critical after deployments or cache restarts:

  • Load top-N most accessed keys from access logs
  • Replay recent queries against the new cache instance
  • Gradual traffic shift: route 10% → 50% → 100% to new cache while it warms

Python Implementations

import time
import json
import random
from typing import Any, Optional, Callable
from dataclasses import dataclass, field


# --- Simulated Redis client for demonstration ---

class FakeRedis:
    """In-memory Redis simulator for demonstrating caching patterns."""

    def __init__(self):
        self._store: dict = {}
        self._expiry: dict = {}
        self.stats = {"hits": 0, "misses": 0}

    def get(self, key: str) -> Optional[str]:
        if key in self._expiry:
            if time.time() > self._expiry[key]:
                del self._store[key]
                del self._expiry[key]
                self.stats["misses"] += 1
                return None
        if key in self._store:
            self.stats["hits"] += 1
            return self._store[key]
        self.stats["misses"] += 1
        return None

    def set(self, key: str, value: str, ex: int = None):
        self._store[key] = value
        if ex:
            self._expiry[key] = time.time() + ex

    def delete(self, key: str):
        self._store.pop(key, None)
        self._expiry.pop(key, None)

    @property
    def hit_ratio(self) -> float:
        total = self.stats["hits"] + self.stats["misses"]
        return self.stats["hits"] / total if total > 0 else 0.0


# --- Simulated Database ---

class FakeDatabase:
    def __init__(self):
        self._data = {
            "user:1": {"name": "Alice", "email": "alice@example.com"},
            "user:2": {"name": "Bob", "email": "bob@example.com"},
            "user:3": {"name": "Charlie", "email": "charlie@example.com"},
        }
        self.query_count = 0

    def read(self, key: str) -> Optional[dict]:
        self.query_count += 1
        time.sleep(0.001)  # Simulate DB latency
        return self._data.get(key)

    def write(self, key: str, value: dict):
        self.query_count += 1
        time.sleep(0.002)  # Simulate write latency
        self._data[key] = value


# ═══════════════════════════════════════════════════
# STRATEGY 1: Cache-Aside (Lazy Loading)
# ═══════════════════════════════════════════════════

class CacheAside:
    """Cache-Aside pattern: application manages cache explicitly.

    Read: check cache → miss → load from DB → store in cache
    Write: update DB → delete from cache (invalidate)
    """

    def __init__(self, cache: FakeRedis, db: FakeDatabase, ttl: int = 300):
        self.cache = cache
        self.db = db
        self.ttl = ttl

    def read(self, key: str) -> Optional[dict]:
        # Step 1: Check cache first
        cached = self.cache.get(key)
        if cached:
            return json.loads(cached)  # Cache HIT

        # Step 2: Cache MISS → load from database
        data = self.db.read(key)
        if data:
            # Step 3: Populate cache for next time
            self.cache.set(key, json.dumps(data), ex=self.ttl)
        return data

    def write(self, key: str, value: dict):
        # Step 1: Write to database (source of truth)
        self.db.write(key, value)
        # Step 2: Invalidate cache (delete, don't update)
        self.cache.delete(key)


# ═══════════════════════════════════════════════════
# STRATEGY 2: Read-Through
# ═══════════════════════════════════════════════════

class ReadThrough:
    """Read-Through: cache itself handles DB loading on miss.

    The application only talks to the cache layer.
    On miss, the cache transparently loads from DB.
    """

    def __init__(self, cache: FakeRedis, db: FakeDatabase, ttl: int = 300):
        self.cache = cache
        self.db = db
        self.ttl = ttl

    def read(self, key: str) -> Optional[dict]:
        # Cache handles everything — acts as the data source
        cached = self.cache.get(key)
        if cached:
            return json.loads(cached)

        # Cache auto-loads from DB (transparent to caller)
        data = self.db.read(key)
        if data:
            self.cache.set(key, json.dumps(data), ex=self.ttl)
        return data


# ═══════════════════════════════════════════════════
# STRATEGY 3: Write-Through
# ═══════════════════════════════════════════════════

class WriteThrough:
    """Write-Through: every write updates BOTH cache and DB synchronously.

    Guarantees cache is always consistent with DB.
    Trade-off: higher write latency (two writes per operation).
    """

    def __init__(self, cache: FakeRedis, db: FakeDatabase, ttl: int = 300):
        self.cache = cache
        self.db = db
        self.ttl = ttl

    def read(self, key: str) -> Optional[dict]:
        cached = self.cache.get(key)
        if cached:
            return json.loads(cached)
        # Miss: load from DB and cache it
        data = self.db.read(key)
        if data:
            self.cache.set(key, json.dumps(data), ex=self.ttl)
        return data

    def write(self, key: str, value: dict):
        # Write to BOTH synchronously
        self.db.write(key, value)         # DB first (source of truth)
        self.cache.set(key, json.dumps(value), ex=self.ttl)  # Then cache


# ═══════════════════════════════════════════════════
# STRATEGY 4: Write-Behind (Write-Back)
# ═══════════════════════════════════════════════════

class WriteBehind:
    """Write-Behind: writes go to cache, flushed to DB asynchronously.

    Lowest write latency but risk of data loss if cache crashes.
    Batches writes for efficiency.
    """

    def __init__(self, cache: FakeRedis, db: FakeDatabase, ttl: int = 300):
        self.cache = cache
        self.db = db
        self.ttl = ttl
        self._write_buffer: list = []  # Pending DB writes

    def read(self, key: str) -> Optional[dict]:
        cached = self.cache.get(key)
        if cached:
            return json.loads(cached)
        data = self.db.read(key)
        if data:
            self.cache.set(key, json.dumps(data), ex=self.ttl)
        return data

    def write(self, key: str, value: dict):
        # Write ONLY to cache (fast return)
        self.cache.set(key, json.dumps(value), ex=self.ttl)
        # Buffer for async DB flush
        self._write_buffer.append((key, value))

    def flush_to_db(self):
        """Flush buffered writes to database (called by background worker)."""
        flushed = 0
        while self._write_buffer:
            key, value = self._write_buffer.pop(0)
            self.db.write(key, value)
            flushed += 1
        return flushed

strategies = {
    "Cache-Aside": CacheAside(FakeRedis(), FakeDatabase()),
    "Read-Through": ReadThrough(FakeRedis(), FakeDatabase()),
    "Write-Through": WriteThrough(FakeRedis(), FakeDatabase()),

for name, strategy in strategies.items():
    print(f"--- {name} ---")

    # Simulate: 3 reads of same key (1 miss + 2 hits)
    for i in range(3):
        result = strategy.read("user:1")

    # Write update
    strategy.write("user:1", {"name": "Alice Updated", "email": "alice@new.com"})

    # Read after write
    result = strategy.read("user:1")
    print(f"  After write-read: {result['name']}")
    print(f"  DB queries: {strategy.db.query_count}")
    print(f"  Cache hit ratio: {strategy.cache.hit_ratio:.1%}")

    # Flush for write-behind
    if hasattr(strategy, "flush_to_db"):
        flushed = strategy.flush_to_db()
        print(f"  Flushed {flushed} buffered write(s) to DB")
    print()

🏭 Industry Practice

Redis: The dominant caching layer in production. Supports TTL with EXPIRE, atomic operations with SETNX/SET NX EX, and pub/sub for cache invalidation across instances. Redis Cluster provides automatic sharding across nodes with 16,384 hash slots.

Memcached: Simpler than Redis — pure key-value with LRU eviction. No persistence, no data structures. Best for simple cache-aside patterns where you need maximum throughput and don’t need Redis’s advanced features. Facebook runs Memcached at massive scale for user session and feed caching.

CDN Caching: Cloudflare, CloudFront, and Fastly cache HTTP responses at edge locations worldwide. Cache-Control headers (max-age, s-maxage, stale-while-revalidate) control TTL. Purge APIs handle invalidation. Edge caching reduces origin load by 90%+ for static content.

CPU L1/L2/L3 Caches: Hardware implements write-back (write-behind) caching with MESI protocol for coherence across cores. The same principles — spatial locality, temporal locality, cache lines, eviction policies — apply at every layer from CPU to CDN.

📋 Key Takeaways

  • Cache-aside gives the application full control — most flexible but requires careful invalidation logic
  • Write-through guarantees consistency but doubles write latency
  • Write-behind provides the lowest write latency but risks data loss on cache failure
  • TTL with jitter prevents cache stampedes caused by synchronized mass expiration
  • Aim for >95% cache hit ratio in production — below 90% indicates poor key design or TTL strategy
  • Cache warming is critical after deployments — cold caches under full traffic cause cascading failures

🧠 Mental Model

Caching strategies represent a spectrum from full application control (cache-aside) to full cache autonomy (write-behind). The further right you go, the lower your latency but the higher your consistency risk.

  CACHING STRATEGY SPECTRUM:
  ══════════════════════════════════════════════════════

  More Control                              Less Control
  More Consistency                     Less Consistency
  Higher Latency                         Lower Latency

⚠️ Common Mistakes

  • Caching mutable data without invalidation strategy: Storing user profiles in cache with a 1-hour TTL means users won’t see their own updates for up to an hour. Always pair caching with explicit invalidation on writes, or use write-through for data that users expect to see immediately after updating.
  • No TTL (caching forever): Entries without TTL accumulate until memory is exhausted, then random eviction kicks in. Always set a TTL — even a generous 24-hour TTL provides a safety net against stale data and unbounded memory growth.
  • Cache-aside with update instead of delete: On write, some developers update the cache instead of deleting it. This creates a race condition: if two concurrent writes occur, the cache may end up with the older value. Delete on write is safer — the next read will reload fresh data.
  • Ignoring cold-start performance: After a deployment or cache restart, hit ratio drops to 0% and all traffic hits the database simultaneously. Without cache warming or gradual traffic ramp-up, this causes a “thundering herd” that can crash the database under load.

🎯 Exercises

  1. Implement cache-aside with Redis: Build a REST API endpoint that reads user profiles using cache-aside with Redis. Measure the hit ratio after 1000 requests with a Zipfian access pattern (80% of requests hit 20% of keys). Experiment with TTL values and observe the ratio change.
  2. Write-through consistency test: Implement write-through caching and run a concurrent test: 10 writers updating the same key simultaneously while 100 readers observe. Verify that readers never see stale data (no inconsistency window).
  3. Write-behind durability analysis: Implement write-behind with a 5-second flush interval. Simulate a crash (kill the process) at random points. Measure how many writes are lost on average. Then add a write-ahead log and repeat the test.
  4. TTL jitter experiment: Cache 10,000 entries with identical TTL. Measure the “miss spike” when they all expire simultaneously. Then add random jitter (TTL ± 20%) and compare the miss pattern — graph the results.
