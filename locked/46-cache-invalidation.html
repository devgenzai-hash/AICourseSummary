Cache Invalidation

Knowing when cached data is stale and must be refreshed — famously called “one of the two hard problems in computer science” alongside naming things and off-by-one errors.

💡 Real-World Analogy

Imagine you have a printed map of a city that keeps changing — new roads are built, old ones are demolished, buildings appear and disappear. When do you print new maps? Print too often and you waste paper and money. Print too rarely and people get lost following outdated directions. You need a strategy: maybe you reprint every month (TTL), or you reprint only when someone reports an error (event-based), or you stamp a version number on each map and let people check if theirs is current (ETags). Cache invalidation is deciding when your “map” (cached data) no longer reflects reality.

Why Cache Invalidation Is Hard

Phil Karlton famously said: “There are only two hard things in Computer Science: cache invalidation and naming things.” The difficulty arises because:

  • Distributed state: Cache and database are separate systems — no atomic operation spans both
  • Race conditions: Between reading stale data and writing fresh data, another process may write again
  • Cascading dependencies: Invalidating one key may require invalidating dozens of derived keys
  • Invisible staleness: You don’t know data is stale until someone checks the source of truth
  • Cost of over-invalidation: Invalidating too aggressively destroys hit ratio and hammers the database

TTL-Based Expiry

The simplest approach — every cached entry has a Time-To-Live after which it’s automatically discarded:

  • Pros: Zero coordination needed, eventual consistency guaranteed, bounded staleness window
  • Cons: Data is stale until TTL expires, choosing the right TTL is guesswork, cache misses spike at expiry
  • Best for: Data that changes infrequently or where brief staleness is acceptable (product catalog, config settings)

Event-Based Invalidation

When the source of truth changes, it actively notifies the cache to discard stale entries. This gives near-real-time consistency:

  • Database triggers: A trigger fires on UPDATE/DELETE and publishes an invalidation event
  • Application-level events: The write path explicitly invalidates after a successful DB write
  • Change Data Capture (CDC): Tools like Debezium stream DB changes to Kafka, consumers invalidate caches

Write-Through Invalidation

Every write to the database simultaneously updates or deletes the corresponding cache entry. The cache is always consistent because writes flow through it:

  • Update approach: Write new value to both DB and cache atomically — higher write latency but zero stale reads
  • Delete approach: Write to DB, then delete cache key — next read triggers a cache miss and refill
  • Delete is safer: Avoids race conditions where two concurrent updates leave stale data in cache

Pub/Sub Invalidation

A publish-subscribe channel broadcasts invalidation messages to all cache nodes. When any node writes to the DB, it publishes a message; all subscribers evict the stale key:

  • Redis Pub/Sub: PUBLISH invalidate:users user:42 — all subscribers evict user:42
  • Kafka topics: Invalidation events consumed by all application instances
  • Advantage: Works across multiple cache instances and data centers
  • Risk: Message loss (pub/sub is fire-and-forget) — pair with TTL as a safety net

Version-Based Invalidation (ETags)

Each cached entry stores a version identifier. On read, the client sends its version to the server; if it matches, the server returns “304 Not Modified” (no data transfer). If it doesn’t match, the server returns fresh data:

  • HTTP ETags: ETag: "abc123" header, client sends If-None-Match: "abc123"
  • Database version columns: Every row has a version or updated_at column compared on read
  • Advantage: No unnecessary data transfer, precise freshness check
  • Disadvantage: Still requires a round-trip to check — not a true “zero-latency” cache hit

Tag-Based Invalidation

Cache entries are tagged with categories. Invalidating a tag purges all entries with that tag — useful for cascading invalidation:

  • Example: A user profile page is tagged ["user:42", "team:engineering", "org:acme"]
  • Invalidation: When team membership changes, invalidate tag "team:engineering" — all related pages are purged
  • CDN support: Fastly Surrogate-Key headers, Cloudflare Cache Tags, Varnish hashtwo

Stale-While-Revalidate

Serve stale data immediately while asynchronously fetching fresh data in the background. The user gets instant response; the cache is refreshed for the next request:

  • HTTP: Cache-Control: max-age=60, stale-while-revalidate=300
  • Application-level: Return stale value, trigger background refresh, update cache when fresh data arrives
  • Advantage: Zero-latency responses even on cache expiry, smooth transition to fresh data
  • Trade-off: The first requester after expiry sees stale data (usually acceptable)
Strategy Consistency Complexity Latency Impact Best For
TTL-Based Eventual (bounded by TTL) Very Low None (until expiry spike) Infrequently changing data
Event-Based Near-real-time Medium Slight write overhead User-facing mutable data
Write-Through Strong Low Higher write latency Read-heavy, consistency-critical
Pub/Sub Near-real-time (multi-node) High Minimal Distributed cache clusters
Version/ETag Strong (on access) Medium Validation round-trip HTTP caching, API responses
Tag-Based Near-real-time Medium Bulk purge cost Content with shared dependencies
Stale-While-Revalidate Eventual (one-request delay) Low Zero (serves stale) Latency-sensitive UIs

Python Implementation

import time
import json
import hashlib
import threading
from typing import Any, Optional, Dict, Set
from dataclasses import dataclass, field


# ═══════════════════════════════════════════════════
# STRATEGY 1: TTL-Based Invalidation
# ═══════════════════════════════════════════════════

class TTLCache:
    """Simple TTL-based cache — entries auto-expire after a set duration."""

    def __init__(self, default_ttl: int = 300):
        self._store: Dict[str, Any] = {}
        self._expiry: Dict[str, float] = {}
        self.default_ttl = default_ttl

    def get(self, key: str) -> Optional[Any]:
        if key in self._expiry:
            if time.time() > self._expiry[key]:
                # Expired — remove and return None
                del self._store[key]
                del self._expiry[key]
                return None
        return self._store.get(key)

    def set(self, key: str, value: Any, ttl: int = None):
        self._store[key] = value
        self._expiry[key] = time.time() + (ttl or self.default_ttl)

    def delete(self, key: str):
        self._store.pop(key, None)
        self._expiry.pop(key, None)


# ═══════════════════════════════════════════════════
# STRATEGY 2: Event-Based with Pub/Sub
# ═══════════════════════════════════════════════════

class InvalidationBus:
    """Simple pub/sub bus for broadcasting cache invalidation events."""

    def __init__(self):
        self._subscribers: list = []

    def subscribe(self, callback):
        self._subscribers.append(callback)

    def publish(self, event_type: str, key: str):
        """Broadcast invalidation to all subscribers."""
        for callback in self._subscribers:
            callback(event_type, key)


class EventDrivenCache:
    """Cache that listens for invalidation events via pub/sub."""

    def __init__(self, bus: InvalidationBus, ttl: int = 600):
        self._cache = TTLCache(default_ttl=ttl)
        self._bus = bus
        # Subscribe to invalidation events
        self._bus.subscribe(self._on_invalidate)

    def _on_invalidate(self, event_type: str, key: str):
        if event_type == "invalidate":
            self._cache.delete(key)
            print(f"  [Cache] Invalidated key: {key}")

    def get(self, key: str) -> Optional[Any]:
        return self._cache.get(key)

    def set(self, key: str, value: Any):
        self._cache.set(key, value)


class DatabaseWithEvents:
    """Database that publishes invalidation events on writes."""

    def __init__(self, bus: InvalidationBus):
        self._data = {"user:1": {"name": "Alice", "v": 1}}
        self._bus = bus

    def write(self, key: str, value: dict):
        self._data[key] = value
        # Publish invalidation event after write
        self._bus.publish("invalidate", key)

    def read(self, key: str) -> Optional[dict]:
        return self._data.get(key)


# ═══════════════════════════════════════════════════
# STRATEGY 3: Version-Based (ETag-style)
# ═══════════════════════════════════════════════════

class VersionedCache:
    """Cache that stores version hashes and validates before serving."""

    def __init__(self):
        self._store: Dict[str, dict] = {}  # key → {data, etag}

    def _compute_etag(self, data: Any) -> str:
        return hashlib.md5(json.dumps(data, sort_keys=True).encode()).hexdigest()[:8]

    def get(self, key: str, current_etag: str = None) -> dict:
        """Returns {data, etag, fresh} — fresh=True if etag matches."""
        entry = self._store.get(key)
        if not entry:
            return {"data": None, "etag": None, "fresh": False}
        if current_etag and current_etag == entry["etag"]:
            return {"data": None, "etag": entry["etag"], "fresh": True}
        return {"data": entry["data"], "etag": entry["etag"], "fresh": False}

    def set(self, key: str, data: Any):
        etag = self._compute_etag(data)
        self._store[key] = {"data": data, "etag": etag}
        return etag

# Demo: All strategies in action
# ═══════════════════════════════════════════════════

print("=== Cache Invalidation Strategies ===")
print()

# 1. TTL-Based
print("--- TTL-Based Invalidation ---")
ttl_cache = TTLCache(default_ttl=2)  # 2-second TTL for demo
ttl_cache.set("product:99", {"price": 29.99})
print(f"  Cached: {ttl_cache.get('product:99')}")
time.sleep(2.1)
print(f"  After TTL: {ttl_cache.get('product:99')}")  # None
print()

# 2. Event-Based with Pub/Sub
print("--- Event-Based Invalidation ---")
bus = InvalidationBus()
cache = EventDrivenCache(bus)
db = DatabaseWithEvents(bus)
cache.set("user:1", {"name": "Alice"})
print(f"  Before write: {cache.get('user:1')}")
db.write("user:1", {"name": "Alice Updated"})
print(f"  After write: {cache.get('user:1')}")  # None (invalidated)
print()

# 3. Version-Based
print("--- Version-Based (ETag) Invalidation ---")
vcache = VersionedCache()
etag = vcache.set("config", {"theme": "dark"})
print(f"  Stored with ETag: {etag}")
result = vcache.get("config", current_etag=etag)
print(f"  Same ETag → fresh={result['fresh']}, no data transfer")
vcache.set("config", {"theme": "light"})
result = vcache.get("config", current_etag=etag)
print(f"  Stale ETag → fresh={result['fresh']}, new data: {result['data']}")

🏭 Industry Practice

Cloudflare / Fastly CDN Purge: CDNs cache HTTP responses at edge locations worldwide. Invalidation happens via purge APIs — purge by URL, purge by tag (Surrogate-Key/Cache-Tag), or purge everything. Fastly purges propagate globally in ~150ms. Cloudflare supports instant purge by cache tag for Enterprise plans.

Redis Keyspace Notifications: Redis can publish events when keys are modified, expired, or evicted. Clients subscribe to __keyevent@0__:expired to react to key expiry. Used for building real-time invalidation across distributed application instances.

Facebook TAO Cache: Facebook’s graph cache uses write-through invalidation with a pub/sub layer. When a user updates their profile, the write propagates through the TAO cache hierarchy. TAO handles billions of reads/second with sub-millisecond consistency across data centers using an invalidation daemon called “cache refill.”

HTTP Cache-Control: The Cache-Control header is the web’s built-in invalidation mechanism. Key directives: max-age (TTL), must-revalidate (check server after TTL), stale-while-revalidate (serve stale, refresh in background), no-cache (always revalidate), no-store (never cache).

📋 Key Takeaways

  • TTL is the simplest invalidation — set it as a safety net even when using other strategies
  • Event-based invalidation gives near-real-time consistency but requires infrastructure (pub/sub, CDC)
  • Write-through delete (not update) avoids race conditions between concurrent writers
  • Version-based (ETag) avoids unnecessary data transfer but still requires a validation round-trip
  • Tag-based invalidation solves cascading dependencies — invalidate a category, not individual keys
  • Stale-while-revalidate is the best UX trade-off — instant response with background refresh
  • Always combine strategies: event-based for writes + TTL as a safety net for missed events

🧠 Mental Model

Cache invalidation strategies form a spectrum from passive (time-based) to active (event-driven). The more active your invalidation, the fresher your data — but the more infrastructure complexity you take on.

  Passive                                        Active
  Simple                                        Complex
  Stale window                             Near-realtime

  ┌─────────────────────────────────────────────────────┐

⚠️ Common Mistakes

  • No TTL safety net: Relying solely on event-based invalidation without a TTL fallback. If an event is lost (network partition, bug in publisher), the cache entry stays stale forever. Always set a maximum TTL even when using active invalidation — it’s your last line of defense.
  • Updating cache instead of deleting on write: When two concurrent writes happen, updating the cache can leave it holding the older value (last-write-wins race). Deleting the key is safer — the next read will fetch the latest value from the database, eliminating the race window.
  • Invalidating before the DB write commits: If you delete the cache entry before the database transaction commits, a concurrent reader may refill the cache with the old DB value. Always invalidate AFTER the write is confirmed: DB.commit() → cache.delete(key).
  • Over-invalidation destroying hit ratio: Invalidating entire cache partitions when only one key changed. For example, purging all product cache when one product’s price changes. Use fine-grained key-level or tag-level invalidation to keep hit ratios above 95%.

🎯 Exercises

  2. ETag-based HTTP caching: Build a REST API with proper ETag support. Return ETag headers on GET, handle If-None-Match on subsequent requests. Measure bandwidth savings when clients cache responses and only receive 304 Not Modified.
  3. Tag-based invalidation engine: Implement a cache where entries can have multiple tags. Support invalidate_by_tag("team:engineering") that purges all entries with that tag. Test with a blog system where posts belong to categories and authors.
