System Design/ False Sharing

False Sharing

When threads working on completely independent data accidentally slow each other down because of how CPU caches work. A hidden performance killer.

Advanced Performance Hardware
Roommates Sharing a Fridge Shelf

Imagine two roommates share one fridge shelf. Person A's food is on the left, Person B's on the right. They never touch each other's food.

But every time A rearranges their food, the entire shelf shakes and B has to check if their food moved. And vice versa.

They are not actually sharing anything, but the shared shelf (cache line) means every change forces the other to re-check. This is false sharing.

What Is False Sharing?

CPUs load memory in chunks called cache lines (typically 64 bytes). If two threads modify different variables that happen to sit on the same cache line, the CPU must invalidate and reload the entire line for both cores — even though they don't actually share data.

Why It Kills Performance

Each write by Core 1 forces Core 2 to reload the cache line from memory (~100ns penalty). Multiply by millions of operations = massive slowdown.

import threading
import time
import ctypes

# Simulating false sharing impact
# Two counters side by side in memory (same cache line)

class FalseSharingDemo:
    def __init__(self):
        # These are likely on the same cache line (adjacent in memory)
        self.counter_a = 0
        self.counter_b = 0

    def increment_a(self):
        for _ in range(10_000_000):
            self.counter_a += 1

    def increment_b(self):
        for _ in range(10_000_000):
            self.counter_b += 1

# Fix: Add padding between variables
class NoPaddingCounters(ctypes.Structure):
    _fields_ = [
        ("a", ctypes.c_long),  # 8 bytes
        ("b", ctypes.c_long),  # 8 bytes — same cache line as 'a'!
    ]

class PaddedCounters(ctypes.Structure):
    _fields_ = [
        ("a", ctypes.c_long),
        ("_pad1", ctypes.c_byte * 56),  # Padding to fill cache line
        ("b", ctypes.c_long),               # Now on DIFFERENT cache line!
    ]

Solutions

# Solution 1: Padding (most common)
class PaddedCounter:
    def __init__(self):
        self.value = 0
        self._padding = [0] * 7  # Fill rest of 64-byte cache line

# Solution 2: Thread-local accumulation
def worker_with_local_accumulator(shared_result, lock):
    local_count = 0  # Thread-local — no sharing!
    for _ in range(1_000_000):
        local_count += 1
    # Only touch shared state once at the end
    with lock:
        shared_result[0] += local_count

# Solution 3: Per-thread arrays with alignment
import numpy as np
# Each thread gets its own cache-line-aligned slot
counters = np.zeros(64, dtype=np.int64)  # 64 slots, 8 bytes each
# Thread i uses counters[i * 8] — separated by 64 bytes (one cache line)

Real-World Impact

  • Java @Contended — Annotation that adds padding to prevent false sharing (used in ConcurrentHashMap)
  • Linux kernel — ____cacheline_aligned macro pads structures to cache line boundaries
  • LMAX Disruptor — Sequence counters are padded to avoid false sharing (critical for low-latency trading)
  • Go runtime — Internal structures use padding to avoid false sharing between goroutines

📝 Summary

  • False sharing: independent variables on the same cache line cause invalidation overhead
  • Cache lines are 64 bytes — variables within 64 bytes of each other share a line
  • Each write by one core invalidates the line for all other cores
  • Fix: padding (add dummy bytes), thread-local accumulation, cache-line alignment
  • Can cause 10-100x slowdown in tight loops on multi-core systems
  • Use perf c2c or Intel VTune to detect

🧠 Mental Model

CACHE LINE (64 bytes): [counter_a | counter_b | ........... ] ↑ ↑ Core 1 Core 2 writes here writes here Every write invalidates the ENTIRE line for the other core! FIX WITH PADDING: [counter_a | padding................. ] ← Cache line 1 (Core 1 only) [counter_b | padding................. ] ← Cache line 2 (Core 2 only) No interference! Each core owns its cache line.

❌ Common Beginner Mistakes

  • Ignoring cache line size — Putting frequently-written variables next to each other in structs.
  • Over-padding — Wasting memory by padding everything. Only pad hot (frequently-written) data.
  • Not measuring — Assuming false sharing without profiling. Always measure first.
  • Python-specific — Due to GIL, false sharing is less impactful in CPython but critical in C extensions and multiprocessing.

🏋 Hands-On Exercise

  1. Create two counters in adjacent memory. Increment each from a different thread. Measure time.
  2. Add 64 bytes of padding between them. Measure again. Compare.
  3. Use the thread-local accumulation pattern: accumulate locally, merge once at end. Measure improvement.
  4. Research: what is your CPU's cache line size? (Usually 64 bytes, some ARM = 128 bytes)
