Load Balancer

Distributing incoming network traffic across multiple servers — ensuring no single server bears too much load, improving availability, reliability, and response times.

💡 Real-World Analogy

Imagine a supermarket with multiple checkout lanes. Without any guidance, customers cluster at one lane while others sit empty. The “next available” sign (or a staff member pointing) directs customers to the shortest queue, balancing the load across all cashiers. If a cashier goes on break (server down), customers are simply directed to the remaining open lanes. A load balancer does exactly this for your servers — directing each request to the best available instance.

Load Balancing Algorithms

Round Robin

  • Requests are distributed sequentially: Server 1, Server 2, Server 3, Server 1, Server 2…
  • Simple and fair when all servers have equal capacity
  • Ignores current server load — a server processing a heavy request still gets the next one
  • Best for stateless services with uniform request complexity

Weighted Round Robin

  • Each server gets a weight proportional to its capacity — a 4-core server gets weight 4, a 2-core gets weight 2
  • The 4-core server receives twice as many requests as the 2-core
  • Useful when servers have different hardware specs in the same pool
  • Weights are configured statically — doesn’t adapt to real-time load

Least Connections

  • Routes to the server with the fewest active connections right now
  • Adapts to varying request durations — slow requests naturally reduce a server’s share
  • Ideal for long-lived connections (WebSockets, database queries, file uploads)
  • Requires the load balancer to track connection counts per server

IP Hash

  • Hashes the client’s IP address to determine which server receives the request
  • Same client always goes to the same server — “sticky sessions” without cookies
  • Useful when servers have local caches that benefit from repeated access
  • Problem: if a server goes down, all its clients get re-mapped

Random

  • Pick a random server from the pool — statistically uniform over time
  • Zero state to track — simplest possible implementation
  • “Power of two choices” variant: pick two random servers, send to the less-loaded one. Dramatically reduces worst-case imbalance

Layer 4 vs Layer 7 Load Balancing

  • L4 (Transport layer): Routes based on IP address and TCP port. Cannot inspect HTTP headers, URLs, or cookies. Extremely fast — just forwards TCP packets. Used for raw throughput.
  • L7 (Application layer): Inspects HTTP headers, URL paths, cookies, and request body. Can route /api/* to one pool and /static/* to another. Supports content-based routing, SSL termination, and request modification.
  • When to use L4: Database connections, non-HTTP protocols, maximum performance needed
  • When to use L7: HTTP services, content-based routing, A/B testing, canary deployments

Health Checks

  • Active checks: Load balancer pings servers periodically (every 5–10s) on a health endpoint
  • Passive checks: Monitor real traffic — if a server returns 5xx errors or times out, mark it unhealthy
  • Graceful removal: Drain existing connections before removing a server (connection draining)
  • Recovery: After N consecutive successful health checks, mark the server healthy again

Session Stickiness

  • Some applications store session state in server memory — switching servers loses the session
  • Cookie-based: Load balancer sets a cookie identifying the target server
  • IP-based: Hash the client IP to always route to the same server
  • Better alternative: Make services stateless and store sessions in Redis/database — eliminates the need for stickiness entirely

Python Implementations

import time
import random
import hashlib
from dataclasses import dataclass, field
from typing import List, Optional
from collections import defaultdict


# ═══════════════════════════════════════════════════
# Server model with health tracking
# ═══════════════════════════════════════════════════

@dataclass
class Server:
    host: str
    port: int
    weight: int = 1
    healthy: bool = True
    active_connections: int = 0

    @property
    def address(self) -> str:
        return f"{self.host}:{self.port}"


# ═══════════════════════════════════════════════════
# Round Robin Load Balancer
# ═══════════════════════════════════════════════════

class RoundRobinBalancer:
    def __init__(self, servers: List[Server]):
        self.servers = servers
        self.current = 0

    def next_server(self) -> Optional[Server]:
        healthy = [s for s in self.servers if s.healthy]
        if not healthy:
            return None
        server = healthy[self.current % len(healthy)]
        self.current += 1
        return server


# ═══════════════════════════════════════════════════
# Weighted Round Robin Load Balancer
# ═══════════════════════════════════════════════════

class WeightedRoundRobinBalancer:
    def __init__(self, servers: List[Server]):
        self.servers = servers
        self.current = 0
        # Build expanded pool: [A, A, A, B, B] for weights 3, 2
        self._pool = []
        for server in servers:
            self._pool.extend([server] * server.weight)

    def next_server(self) -> Optional[Server]:
        healthy_pool = [s for s in self._pool if s.healthy]
        if not healthy_pool:
            return None
        server = healthy_pool[self.current % len(healthy_pool)]
        self.current += 1
        return server


# ═══════════════════════════════════════════════════
# Least Connections Load Balancer
# ═══════════════════════════════════════════════════

class LeastConnectionsBalancer:
    def __init__(self, servers: List[Server]):
        self.servers = servers

    def next_server(self) -> Optional[Server]:
        healthy = [s for s in self.servers if s.healthy]
        if not healthy:
            return None
        # Pick the server with fewest active connections
        return min(healthy, key=lambda s: s.active_connections)

    def connect(self, server: Server):
        server.active_connections += 1

    def disconnect(self, server: Server):
        server.active_connections = max(0, server.active_connections - 1)


# ═══════════════════════════════════════════════════
# IP Hash Load Balancer
# ═══════════════════════════════════════════════════

class IPHashBalancer:
    def __init__(self, servers: List[Server]):
        self.servers = servers

    def next_server(self, client_ip: str) -> Optional[Server]:
        healthy = [s for s in self.servers if s.healthy]
        if not healthy:
            return None
        # Hash the IP to get a consistent server index
        hash_val = int(hashlib.md5(client_ip.encode()).hexdigest(), 16)
        index = hash_val % len(healthy)
        return healthy[index]


# ═══════════════════════════════════════════════════
# Health Checker
# ═══════════════════════════════════════════════════

class HealthChecker:
    def __init__(self, servers: List[Server], threshold: int = 3):
        self.servers = servers
        self.threshold = threshold
        self.fail_counts: Dict[str, int] = defaultdict(int)
        self.recovery_counts: Dict[str, int] = defaultdict(int)

    def record_success(self, server: Server):
        self.fail_counts[server.address] = 0
        if not server.healthy:
            self.recovery_counts[server.address] += 1
            if self.recovery_counts[server.address] >= self.threshold:
                server.healthy = True
                self.recovery_counts[server.address] = 0
                print(f"  ✓ {server.address} marked HEALTHY")

    def record_failure(self, server: Server):
        self.recovery_counts[server.address] = 0
        self.fail_counts[server.address] += 1
        if self.fail_counts[server.address] >= self.threshold:
            server.healthy = False
            print(f"  ✗ {server.address} marked UNHEALTHY")


# ═══════════════════════════════════════════════════
# Demo: Load balancer algorithms in action
# ═══════════════════════════════════════════════════

servers = [
    Server("web-1", 8080, weight=3),
    Server("web-2", 8080, weight=2),
    Server("web-3", 8080, weight=1),
]

print("=== Round Robin ===")
rr = RoundRobinBalancer(servers)
for i in range(6):
    s = rr.next_server()
    print(f"  Request {i+1} → {s.address}")

print("\n=== Weighted Round Robin ===")
wrr = WeightedRoundRobinBalancer(servers)
for i in range(6):
    s = wrr.next_server()
    print(f"  Request {i+1} → {s.address}")

print("\n=== Least Connections ===")
lc = LeastConnectionsBalancer(servers)
servers[0].active_connections = 5
servers[1].active_connections = 2
servers[2].active_connections = 1
s = lc.next_server()
print(f"  Picked: {s.address} (conns={s.active_connections})")

print("\n=== IP Hash (sticky sessions) ===")
ip_lb = IPHashBalancer(servers)
for ip in ["192.168.1.10", "10.0.0.5", "192.168.1.10"]:
    s = ip_lb.next_server(ip)
    print(f"  {ip} → {s.address}")

print("\n=== Health Check ===")
checker = HealthChecker(servers, threshold=2)
checker.record_failure(servers[0])
checker.record_failure(servers[0])  # 2nd failure → marked unhealthy
s = rr.next_server()
print(f"  After failure: next → {s.address}")  # Skips web-1

🏭 Industry Practice

nginx: The most popular open-source load balancer. Supports round-robin, least connections, IP hash, and generic hash. Handles millions of concurrent connections with minimal memory. Used as both a reverse proxy and load balancer at companies like Netflix, Dropbox, and WordPress.com.

HAProxy: High-performance TCP/HTTP load balancer used by GitHub, Reddit, and Stack Overflow. Supports advanced health checks, connection draining, and stick tables for session persistence. Known for sub-millisecond latency overhead and extreme reliability.

AWS ALB/NLB: Application Load Balancer (L7) routes based on URL path, host header, or HTTP method. Network Load Balancer (L4) handles millions of requests per second with ultra-low latency. Both integrate with Auto Scaling to add/remove targets automatically.

DNS Load Balancing: Route 53 (AWS), Cloudflare, and other DNS providers distribute traffic at the DNS level. Simple but coarse-grained — TTL caching means changes propagate slowly. Often used for geographic routing (US users → US servers, EU users → EU servers).

📋 Key Takeaways

  • Load balancers distribute traffic across servers — preventing any single server from becoming a bottleneck
  • Round-robin is simplest but ignores actual load. Least-connections adapts to varying request durations
  • L4 balancing is faster (TCP packets only), L7 balancing is smarter (can inspect HTTP content and route by path/header)
  • Health checks detect failed servers and remove them from the pool — always implement both active and passive checks
  • Session stickiness solves stateful problems but creates uneven load — prefer stateless services with external session stores
  • The load balancer itself must be redundant — use active-passive failover or DNS-level distribution across multiple LB instances

🧠 Mental Model

Think of a load balancer as a traffic controller at a busy intersection. It doesn’t process requests itself — it just decides which lane (server) each car (request) should take to keep traffic flowing smoothly.

⚠️ Common Mistakes

  • No health checks: The load balancer keeps sending traffic to a dead server, causing 50% of requests to fail. Always configure active health checks with appropriate intervals (5–10s) and failure thresholds (2–3 consecutive failures before removal).
  • Sticky sessions hiding scaling problems: Using session affinity to avoid making services stateless. When that one server goes down, all its users lose their sessions. Externalize state to Redis or a database, then use stateless round-robin for true horizontal scaling.
  • Single load balancer without failover: Your load balancer is the single point of failure. If it dies, everything dies. Deploy LBs in active-passive (VRRP/keepalived) or active-active pairs. Use DNS failover to switch between LB clusters in different availability zones.
  • Ignoring connection draining: Removing a server from the pool while it’s still processing requests causes those requests to fail. Always drain existing connections gracefully — stop sending new requests, wait for active ones to complete (with a timeout), then remove the server.

🎯 Exercises

  1. Implement “Power of Two Choices”: Build a load balancer that picks 2 random servers and routes to the one with fewer connections. Simulate 10,000 requests with varying durations. Compare the max server load against pure random and round-robin. Graph the results.
  2. Build a health-aware weighted balancer: Combine weighted round-robin with health checks. When a server fails health checks, redistribute its weight among remaining servers proportionally. When it recovers, gradually ramp its weight back up (slow start) to avoid a sudden flood of traffic.
  3. Simulate session stickiness vs stateless: Create 100 “users” with sessions. Run scenario A (sticky sessions, in-memory state) and scenario B (stateless, Redis store). Kill a random server. Measure how many users lose their session in each scenario. Calculate the availability difference.
  4. L7 content-based routing: Build an L7 load balancer that routes based on URL path: /api/* → API pool (3 servers), /static/* → CDN pool (2 servers), /ws/* → WebSocket pool (2 servers). Add the ability to split traffic for A/B testing: 10% of /api/* goes to a canary server.
