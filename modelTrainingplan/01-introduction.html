Chapter 1: Introduction & Overview

Understanding what fine-tuning is, why we chose Google's Gemma model, and the complete roadmap from raw PDFs to a deployed scripture-expert AI.

🤔 What is Fine-Tuning?

The Non-Technical Explanation

Imagine you hire a brilliant university graduate who has read millions of books on every subject. They're intelligent and articulate, but they've never specifically studied Hindu scriptures in depth. Fine-tuning is like giving this person intensive specialized training — months of focused study on the Vedas, Upanishads, Bhagavad Gita, and other sacred texts until they become an expert in that specific domain.

The "university graduate" is the pre-trained model (Gemma). It already knows language, reasoning, and general knowledge. Fine-tuning adds domain expertise — deep knowledge of Hindu philosophy, Sanskrit terminology, specific verses, commentaries, and the ability to answer questions about these texts accurately.

The Technical Explanation

Fine-tuning is the process of taking a pre-trained Large Language Model (LLM) and continuing its training on a smaller, domain-specific dataset. The model's weights are adjusted (either all of them or a subset) to optimize for your specific task.

💡 Key Insight

Pre-training costs millions of dollars and uses trillions of tokens. Fine-tuning leverages that investment and costs a fraction — typically $100-$10,000 depending on scale — while making the model an expert in your domain.

Gemma Architecture Deep Dive

🔍 Technical Details: Transformer Architecture

Gemma uses a decoder-only transformer architecture with these key components:

  • Multi-Head Attention (MHA): Allows the model to focus on different parts of the input simultaneously. For the 27B model, there are multiple attention heads per layer.
  • Grouped Query Attention (GQA): An optimization where key-value heads are shared across multiple query heads, reducing memory usage during inference.
  • RMSNorm: A normalization technique (instead of LayerNorm) that's more computationally efficient.
  • Rotary Position Embeddings (RoPE): Enables the 128K context length by encoding position information into the attention mechanism.
  • SwiGLU Activation: The feed-forward network uses SwiGLU instead of ReLU for better performance.
# Gemma model architecture (simplified)
# Each transformer layer:
class GemmaDecoderLayer:
    def forward(self, x):
        # 1. Self-attention with RoPE
        residual = x
        x = rms_norm(x)
        x = grouped_query_attention(x, rope_embeddings)
        x = residual + x
        
        # 2. Feed-forward with SwiGLU
        residual = x
        x = rms_norm(x)
        x = swiglu_ffn(x)  # gate_proj, up_proj, down_proj
        x = residual + x
        
        return x

Key modules for LoRA fine-tuning:

  • q_proj, k_proj, v_proj, o_proj — Attention projections
  • gate_proj, up_proj, down_proj — Feed-forward network

When fine-tuning with LoRA, we inject small trainable matrices into these layers while keeping the original weights frozen.

📚 Key Concepts Explained

🔤 Tokens & Tokenization

LLMs don't read text character-by-character. They split text into tokens — chunks that can be whole words, parts of words, or individual characters. For Devanagari script (Hindi/Sanskrit), tokens often represent syllables or common word fragments.

# Example: How Gemma tokenizes Hindi text
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("google/gemma-3-27b-it")

# English
text_en = "The Bhagavad Gita teaches the path of righteousness"
tokens_en = tokenizer.tokenize(text_en)
print(f"English: {len(tokens_en)} tokens")
# Output: ~10 tokens

# Hindi
text_hi = "भगवद्गीता धर्म का मार्ग सिखाती है"
tokens_hi = tokenizer.tokenize(text_hi)
print(f"Hindi: {len(tokens_hi)} tokens")
# Output: ~15-20 tokens (Devanagari uses more tokens per word)

# Sanskrit
text_sa = "धर्मक्षेत्रे कुरुक्षेत्रे समवेता युयुत्सवः"
tokens_sa = tokenizer.tokenize(text_sa)
print(f"Sanskrit: {len(tokens_sa)} tokens")
# Output: ~20-25 tokens
⚠️ Token Efficiency

Hindi/Sanskrit text typically uses 1.5-2× more tokens than equivalent English text. This means you need proportionally more compute for the same amount of content. Budget accordingly.

🧮 Parameters & Model Size

A model's "size" is measured in parameters — the numbers (weights) that the model has learned during training. More parameters = more knowledge capacity, but also more memory and compute needed.

🎛️ LoRA & QLoRA (Parameter-Efficient Fine-Tuning)

Instead of updating ALL 27 billion parameters (which requires massive GPU memory), LoRA (Low-Rank Adaptation) only trains a tiny fraction — typically 0.1-1% of parameters — while keeping the rest frozen.

How it works:

  • Original weight matrix W (huge, e.g., 4096×4096)
  • LoRA adds two small matrices: A (4096×64) and B (64×4096)
  • Output = W×x + A×B×x (original + learned adjustment)
  • Only A and B are trained — 99% memory savings

QLoRA goes further: it loads the frozen base model in 4-bit precision (quantized), reducing memory by another 4×.

# Memory comparison for Gemma 27B:
# Full fine-tuning:  ~200 GB GPU memory (need 4-8 GPUs)
# LoRA (BF16):       ~60 GB GPU memory (need 1-2 GPUs)
# QLoRA (4-bit):     ~20 GB GPU memory (fits on 1 GPU!)
⚖️ DPO vs RLHF (Preference Alignment)

The Problem: After SFT, the model can follow instructions, but it might generate responses that are technically correct but poorly formatted, overly verbose, culturally insensitive, or not aligned with what humans actually prefer.

RLHF (Reinforcement Learning from Human Feedback):

  1. Train a separate "reward model" that scores responses
  2. Use PPO (a reinforcement learning algorithm) to optimize the main model
  3. Complex, unstable, requires careful hyperparameter tuning

DPO (Direct Preference Optimization):

  1. Skip the reward model entirely
  2. Directly train on pairs of (preferred response, rejected response)
  3. Simple, stable, computationally lightweight
  4. Achieves similar or better results than RLHF
✅ Recommendation

Use DPO as your primary alignment method. It's simpler, cheaper, and equally effective for most use cases. Reserve RLHF/GRPO only if DPO doesn't achieve your quality goals.
